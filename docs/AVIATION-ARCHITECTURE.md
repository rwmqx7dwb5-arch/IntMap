# IntMap — 航空プラットフォームの構造 (Aviation architecture)

> **「1回だけ上流を読み、全利用者へ配り、GPU で描く」**——その1本の筋を書き留めた文書。

## 1. 何を変えたのか

### 旧構造 —— 利用者ごとに世界を組み立て直す

```
ブラウザ A ──► api.airplanes.live へ最大128回（1.2秒間隔・逐次）
ブラウザ B ──► api.airplanes.live へ最大128回
ブラウザ C ──► api.airplanes.live へ最大128回
```

1回の掃引を**発行し終える**だけで約154秒。ズーム2未満では `planesData=[]` にして
「Zoom in to load live aircraft」を出す。3D は最大4,000機で、超えたら地図中心からの距離で切る。
**上流負荷が利用者数に比例する構造**であり、それが 403 を招いた（→ データ源の文書 §0）。

### 新構造 —— 上流を読むのは1本だけ

```
                          ┌─ .github/workflows/aviation-sweep.yml （5分ごと・?refresh=1）
                          │
provider ◄── aviation-feed ──► Supabase Storage: aviation/world.bin （公開・CDN）
                  ▲
                  │ IMAV/1（バイナリ）
                  │
   ブラウザ ── src/aviation-worker.js ──► typed-array ストア ──► GPU バッファ（transfer）
                                                                      │
                                        js/aviation-live.js ──► GE().layers.setAircraftCloud()
                                                                      │
                                              MapLibre: js/aircraft-points.js（custom WebGL layer）
                                              Cesium  : js/cesium-engine.js（2つの primitive collection）
```

**上流リクエスト数は時間に比例し、利用者数には比例しない。** それがこの構造の全部で、
残りはそのための事務手続き。

## 2. 実測値（2026-08-23・本番の Edge Function に対して）

| 経路 | 応答 | 内容 |
|---|---|---|
| `?ch=world`（スナップショットから） | **0.35 s** | 全機・age をヘッダで正直に申告 |
| `?ch=view`（既知の空域） | **0.38 s** | 視野内の機体 |
| `?ch=view`（未知の空域） | 6.1 s | タイルを直列で読む代金。**1空域につき1回**、全利用者で共有 |
| `?ch=world&refresh=1`（掃引役） | 4.5 s | 格子を3タイル進めてスナップショットを書く |
| `?meta=1` | 即時 | provider・被覆率・上流カウンタ・鍵の**有無**（値は出さない） |

量子化誤差（実データで測定）: **位置 0.70 m ・ 高度 0.0 ft ・ 針路 0.0000°**。

## 3. IMAV/1 —— ワイヤ形式

正本は [`../js/aviation-codec.js`](../js/aviation-codec.js)。
`supabase/functions/_shared/aviation-codec.js` は `node scripts/sync-aviation.mjs` が作る
**バイト同一の写し**で、`scripts/static-checks.mjs` が食い違いを落とす。

⚠ **この写しの食い違いは newsgeo のそれより高くつく。** newsgeo が食い違うと見出しが
違うピンに乗る。**codec が食い違うと、encoder と decoder が1バイトのずれで一致しなくなり、
世界中の航空機が「もっともらしく間違った場所」に着地する。**

- ヘッダ 40 B（magic / version / flags / seq / baseSeq / serverTimeMs / 機数 / 削除数 / テキスト長）
- レコード **24 B 固定長** × 機数
- 削除リスト u32 × 削除数
- 識別情報（hex / 便名 / 型式 / 登録記号 / 運航者）—— **機体につき1回だけ**送る

⚠ **「無い」と「ゼロ」は別のビット。** `AC_ALT_VALID` が落ちていれば高度は `NaN` にデコードされ、
0 ft にはならない。旧実装はこれを混同していて、高度を報告しない機体を海面高度として 3D の地面に置いていた。

## 4. サーバー側 —— `supabase/functions/aviation-feed`

### 4.1 チャンネル

| `?ch=` | 誰が呼ぶか | 何を返すか |
|---|---|---|
| `world` | ブラウザ | 既知の全機。スナップショットから即答し、age を申告する |
| `world&refresh=1` | **掃引役だけ** | 格子を進め、スナップショットを書き、返す |
| `view&bbox=w,s,e,n` | ブラウザ | 視野内。空域が古ければタイルを読んでから返す |
| `meta=1` | UI と監視 | provider・被覆率・上流カウンタ・鍵の有無 |

### 4.1b 応答ヘッダ —— **齢は2つあり、2つとも別のヘッダで返す**

| ヘッダ | 意味 |
|---|---|
| `x-intmap-provider` / `x-intmap-attribution` | どの provider が答えたか・その表記義務の文面 |
| `x-intmap-count` | この応答に入っている機数 |
| **`x-intmap-age-ms`** | **この「答え」自体の齢**（world＝スナップショットを組み立ててから／view＝箱を作ってから） |
| **`x-intmap-oldest-ms`** | **この答えに入っている「最も古い観測」の齢** |
| `x-intmap-seq` / `x-intmap-channel` / `x-intmap-coverage` / `x-intmap-save` | 版・チャンネル・被覆率・スナップショット書き込みの結果 |

⚠ **この2つは以前1つのヘッダだった。** `x-intmap-age-ms` は world では「スナップショットの齢」、
view では「箱の中で最も古い機体の齢」を運んでいた。本番実測で **world 12.7〜13.5 s ／ view 531〜564 s**
——同じフィールドに交互に入るので、**どちらの意味でも読めなかった**。
指示書 §22.2 は「取得元の観測時刻・IntMap が受け取った時刻・クライアントが描画した時刻」を
区別できることを要求している。**1つのヘッダに2つの事実を入れると、その区別が消える。**

⚠ **チャンネルを足すときは両方を書くこと。** `tests/r352-checks ⑤` が `binResponse()` の呼び出しを
すべて数え上げ、`ageMs` と `oldestMs` の**両方を名乗らない呼び出しがあれば落ちる**。
⚠ **新しいヘッダは `Access-Control-Expose-Headers` にも足すこと**——無いとブラウザは
エラーも警告も出さずに `null` を読む（#R341 で ODbL の表記が一度も出なかった原因）。

### 4.2 スナップショットが isolate の外にある理由（実測）

最初の実装は isolate のメモリをキャッシュにしていた。**同じ viewport を3回続けて呼んだ実測**:

```
call 1  200  7,140 B  5.64 s   x-intmap-age-ms: 2
call 2  200  7,140 B  5.76 s   x-intmap-age-ms: 1
call 3  200  7,089 B  6.39 s   x-intmap-age-ms: 1
```

**毎回 age が 1 ms** ＝ 毎回作り直している。Supabase は十分な頻度で冷えた isolate を割り当てるので、
**isolate メモリはキャッシュではない。** 上流リクエストは利用者数に比例したままで、
構造をブラウザからサーバーへ移しただけになっていた。

⇒ スナップショットは **Supabase Storage の `aviation` bucket**（migration
`20260823130000_aviation_snapshot_bucket.sql`）に置く。冷えた isolate はそこから復元する。

### 4.3 掃引を「背景仕事」にしない理由（実測）

`EdgeRuntime.waitUntil` に渡した Promise は**応答をまたいで生き残らなかった**。
world を6回続けて呼んでも **27機・0/980タイルのまま**、書き込みも起きなかった。
⇒ **背景仕事に依存する設計は、単発の試験では全部正しく見えて、本番では一度も前に進まない。**
実際に前に進めているのは次の2つだけ:

- 古い空域を見た `?ch=view` が、その場でタイルを直列に読む
- `.github/workflows/aviation-sweep.yml` が5分ごとに叩く `?refresh=1`

### 4.4 上流に対する作法

- **直列＋1.2秒間隔。** 並列はバースト予算を一度に使い切る（→ データ源の文書 §1.1）。
- **429 を受けたらそのスライスを止める。** 止まれと言われた後も叩き続けるのが、
  アドレスごと遮断される道。以後 60 秒はこの関数全体が上流に触らない。
- **429 と「そこに機体がいない」を同じ値にしない。** 前者はタイルを「未探査」のままにし、
  後者はそのタイルの探査頻度を下げる。混同すると `coveragePct` が嘘になる。
- 格子の巡回順は**黄金比ストライドで攪拌**してある。行優先のまま歩くと、
  予算の小さい掃引は**緯度の1本の帯から出られない**。攪拌すると**12タイルで全緯度帯**に届く。

### 4.5 視野に対してどのタイルを読むか — **中心から外へ**

`?ch=view` が読むタイルは `MODEL.tilesForBbox()` が決める。**候補は視野の中心から外向きに
生成する**（`fanOut`）。上限（`max × 8`）はいちばん遠い候補を捨てるためだけにあり、
どのタイルを読むかを決めてはならない。

⚠ **#R341 の実装は南西の角から行優先で歩き、`max × 8` 個で打ち切ってから中心距離で並べ替えて
いた。** 視野が 40° より広いと打ち切りは**最初の行**で起きるので、並べ替えは「箱の南端の
タイル」の中からしか選べない。実測（`max = 4`）:

| 視野 | 中心 | 返っていたタイル |
|---|---|---|
| 全球（東京中心） | 139.8, 35.7 | 緯度 **−58** に4枚（南極海） |
| ヨーロッパ z2 | 10.0, 45.0 | 緯度 **26** に4枚（サハラ） |
| 日本 z3 | 139.5, 31.5 | 緯度 **18** に4枚（フィリピン海） |

**選別より先に効く上限は、それ自体が選別である**（#R320・#R388 と同じ形）。

⚠ **視野の中心は「緯度の平均」ではない。** メルカトルは赤道から離れるほど引き伸ばすので、
下端 58°S・上端 81°N の視野の中心は 11.6°N ではなく **35.6°N**（`mercMidLat`）。
IntMap がその bbox を出したときのカメラ緯度は 35.68°——つまりこれが視野の中心である。

### 4.5b いつ読むか・その4枚をどこに使うか — **最後にその空を訊いた時刻**（#R434）

**予算は変えていない**（`VIEW_MAX_TILES = 4`・`VIEW_STALE_S = 45` 秒）。上流の予算は
測定値であって好みではない（§1.1）。変わったのは、**その4枚をどう選び、そもそも出すかどうかを
何で決めるか**である。#R341 の決め方は2つとも別の量を見ていて、広い視野は両方で損をしていた。

| | #R341 | #R434 |
|---|---|---|
| 出すかどうか | **箱の中のいちばん新しい機体**が 45 秒より古いか | **選んだタイルの空**を最後に訊いたのが 45 秒より前か |
| どの4枚 | 視野の**中心にいちばん近い4枚**（毎回同じ） | 候補 24 枚のうち**いちばん長く訊いていない4枚** |
| 間隔 | bbox ごと | **この関数ぜんぶで1回**（バースト予算はアドレスのもの） |

⚠ **本番実測（world 1,683機・2026-08-25）。** 日本 z6 の箱は 89 機、日本 z3 の箱——面積で 150 倍——は
**97 機**。ヨーロッパを含む広い箱は片隅がいつも新しいので**一度も読まず**、逆に大洋上の箱は
`!inBox.length` が真なのでキャッシュが切れるたびに読んでいた。

⚠ **`once()` は「起動して走っている Promise」を返す。** #R341 は分岐の**外**でそれを組み立て、
`boxStale` は「呼び出し側が待つかどうか」だけを決めていた。つまり **15 秒キャッシュを外した
リクエストは全部、4枚の上流読み取りを出していた**——測定されたバースト予算の3倍で、429 と
`RATE_BACKOFF_MS` の沈黙を全チャンネルに配る道である。#R434 は分岐の**中**で組み立てる。

⚠ **台帳が記録するのは「訊いたこと」であって「獲れたこと」ではない。** 地球の3分の2は受信機の
無い海で、「30 秒前に**何もいない**と答えたタイル」と「誰も見たことのないタイル」は別物である。
機体しか覚えない台帳では、広い視野は同じ空の海に予算を使い続ける。
`STATE.asked` は **2° セル**（250 nm タイルの約半分）で、`readSerial` が**読み終えたタイルを
その場で**刻む——視野チャンネルと格子掃引の**両方**が同じ台帳に書く。

⚠ **効果は「10 回のポーリングが買う空の広さ」で測れる**（`tests/r434-checks.test.mjs` ⑤、
実際の `tilesForBbox` と実際の並べ替えを、アプリが本当に出す日本 z3 の bbox に対して回す）:
**同じ4区画 → 24 区画**。冷えた台帳では並べ替えが同点なので、**最初の1回は今までどおり
視野の中心**（狭い視野は候補が4枚しかないので、そもそも何も変わらない）。

⚠ **冷えた isolate は、台帳をスナップショットから作り直す**（#R434 追記）。Supabase は冷えた
isolate をよく配る（§4.2）ので、空の台帳のままだと**冷えた側は毎回「視野の中心がいちばん古い空だ」と
判断して**、共有スナップショットが既にその空を持っていても1回ぶんの読み取りをそこへ使う。
本番実測（本ラウンドのデプロイ直後・同じ広い視野を3回）: **`askedCells` が 3 → 0 → 0**
＝3つの別々の isolate が答えていた。

**ある時刻 T にそのセルで観測された機体は、「誰かが少なくとも T にはその空を訊いた」証拠である**
——観測はそれ無しには存在し得ない。だから `hydrate()` が機体を積むときに `markAsked(lat, lon, seenAt)`
を打つ。新しい状態もスナップショットの形式変更も要らない。
⚠ **同じセルの中で「いちばん新しい」を採る**——hydrate は順不同で届き、1セルに50機いれば50通りの
観測時刻がある。無条件に上書きすると**いちばん古い観測時刻が残り**、よく見えている空が古く見える。
⚠ **空の空（機体が1機もいない海）はこの方法では学習できない**。何も観測されなければ痕跡が残らない。
それを「まだ訊いていない」として扱うのは**安全な側の誤り**で、最悪でも1回ぶんの読み取りが
「やはり何もいない」の確認に使われるだけである。

### 4.6 どの機体が「視野の中」か — **経度は角度であって実数ではない**（#R411）

視野に入る機体の判定は `MODEL.lonInSpan(lon, w, e)` **1本**で行う。剰余1回と比較1回で、
**日付変更線の特別扱いは無い**（特別な継ぎ目が無いから）。幅が 360° 以上なら惑星全体。

⚠ **タイルの選び方は #R401 で正しくなっていたが、「どれが箱の中か」を決める側は大小比較のまま
だった。** MapLibre の `getBounds()` は z4 あたりより低いと**巻き戻していない**箱を返す——
東端が +180 を越えるか、西端が −180 を下回る——ので、`e < w` は偽になり日付変更線の枝に入らず、
自分の経度を [−180, 180] で報告する機体が `lo < w` で落ちる。実行中のアプリで実測:

| 視野 | `getBounds()` が返した経度 | 通っていた子午線 | 修正後 |
|---|---|---|---|
| 全球 z1 | −180.0 … 180.0 | 72 / 72 | 72 / 72 |
| 日本 z3 | **43.568 … 232.432** | **28 / 72** | **38 / 72** |
| 北米 z3 | **−197.494 … −2.506** | **35 / 72** | **39 / 72** |
| 日本 z6 | 130.156 … 140.844 | 2 / 72 | 2 / 72 |

サーバーが**既に持っている**集合から、広い視野の一部が捨てられていた——上流を1回も読まずに
戻せる分である。⚠ **同じ述語は2箇所にあった**（最初の収集と、古い箱がタイルを待ったあとの
再収集）。後者こそ広い視野が通る経路なので、片方だけ直すと効かない。いまは
`collectBox()` 1本で、`tests/r411-checks.test.mjs ①c` が本数を数えている。

### 5.1 速度は「触らないこと」から来ている

- **1機につき1頂点。** 1フレームあたり: バッファ束縛7回・uniform 6個・`drawArrays` 1回。
- **publish の間、CPU は機体を1つも触らない。** 位置は頂点シェーダが速度から外挿する。
- **バッファは転送される（コピーされない）。** worker が pack し、`postMessage` の transfer list に
  載せてそのまま GPU へ行く。
- 進行方向はフラグメントシェーダが `gl_PointCoord` を回して出す。**テクスチャアトラスは無い。**

⚠ **マークは「機体自身の水平面に置かれたプランフォーム」を、このカメラが見た絵である**（#R434）。
`gl.POINTS` のスプライトは**ビューポートに軸を揃えて**描かれるので、`track` をそのまま渡すと
「画面に無い方位磁針」に対して機首を向けることになる。だが**角度だけを地面へ投影する**のも同じく
変換の半分でしかない——形が潰れないまま向きだけ地平線へ寝ると、**その機体は地平線に沿って
飛んでいる**と読める。渡すべきは 2×2 の**全部**である。

頂点シェーダは**3回投影する**——機体・**東へ1歩**・**北へ1歩**。この2つの差が
地面→画面のヤコビ行列 `J = [dE dN]`。`track` はそれを**マーク自身の軸**（右翼と機首）へ回す:

```
A = [ J·(cos t, −sin t)   J·(sin t, cos t) ] / σ₁      （σ₁ = J の最大特異値）
```

`σ₁` で割るのは、`u_sizePx` が今までどおり「いちばん長い方向の画素数」を意味し続けるため。
フラグメントシェーダには **`A` の逆行列**を渡す（1機につき1回。画素ごとの回転より安い）。
平面・北上の地図では `A` は純粋な回転で、**報告された track そのもの**——#R411 と1ビットも
変わらない。地図を回せばその分だけ回り、**傾ければ地面と同じだけ潰れる**。
方位・透視除算・globe 投影はすべて `projectTileFor3D` の中に既にあるので、この層で導出し直す
ものは何も無い。

⚠ **同じ依頼が3回来た。#R401 と #R411 は同じ 2×2 の別々の半分を使っていた。**

| | #R401 | #R411 | #R434 |
|---|---|---|---|
| 角度 | 投影した向き | 極分解の回転だけ | **投影した向き** |
| 形 | 潰れない | 潰れない | **地面と同じだけ潰れる** |
| 傾けたとき | 5機に4機が地平線を向く | **何も起きない** | 地面と同じ絵になる |

#R401 の実測（日本上空 z6.2・400機。報告された track 自体はほぼ一様 0.214）:

| pitch | 0° | 30° | 60° | 75° | 78° |
|---|---|---|---|---|---|
| 水平±20° に入る機数 | 121 | 128 | 181 | 287 | **315** / 400 |
| 軸の集中度 | 0.238 | 0.291 | 0.485 | 0.711 | **0.768** |

#R411 の実測（`tests/r379.spec.js`・画面中心の試験機・スプライト 128 px）——**傾けても
1画素も変わらなかった**:

| pitch | 0° | 60° |
|---|---|---|
| 描かれた角度 | 45.0° | **45.0°** |
| 投影が言う角度 | 45.0° | 63.5° |
| マークの面積 | 1368 px | **1368 px** |

同じ計器で #R434 を測ると **45.0° / 64.2° / 79.3°**（pitch 0 / 60 / 78）に対し投影は
**45.0° / 63.5° / 78.3°**、面積は **1368 / 706 / 349 px**（投影が言う潰れは 1.000 / 0.500 / 0.207）。

⚠ **潰しには床がある。** スプライトの**大きさは距離で小さくならない**（それが全機を読める
ようにしている当のもの）ので、潰しだけを距離なりに走らせると、傾いた視野の地平線近くの機体は
幅そのままで**画素以下の細さ**になる。床はこの層自身の LOD（`LOD_DOT_PX = 5` 画素——それ未満では
シェーダは飛行機ではなく点を描く）で、**クランプではなく #R411 の回転への混合**として当たる:
`mix(A, R, t)` は極分解 `A = R·S` の両特異値を `(1−t)σ + t` へ持ち上げるので、`t = 1` は
**#R411 のマークそのもの**である。マークの大きさ別の短軸（画面中心 ＝ cos(pitch)）:

| `v_px` | 11 | 16 | 22 | 43 | 86 |
|---|---|---|---|---|---|
| 床 = 5/`v_px` | 0.455 | 0.313 | 0.227 | 0.116 | 0.058 |
| pitch 78° の短軸 | 0.455 | 0.313 | 0.227 | **0.208** | **0.208** |
| pitch 60° の短軸 | 0.500 | 0.500 | 0.500 | 0.500 | 0.500 |

つまり **63° あたりまではどの画面でも投影そのまま**、**40 画素以上に描かれていればどの傾きでも
投影そのまま**で、床が当たるのは「当たらなければ細片になる」ところだけ。

⚠ **縁は今も1画素だが、その1画素は画面で測る。** `planeSD` が返す距離は**マークの単位**で、
潰れた軸ではそれが画面の 5/`v_px` 画素にしかならない。そこで `aa` を**その画素での場の勾配**
（場自身の単位勾配を同じ逆行列で運んだもの）で割る。回転しかないときこの係数は厳密に 1 なので、
平面地図での §5.1b の表は1つも動かない。

⚠ **Cesium はここまでは行けない**（`_airHeading` は**回転だけ**を返し続ける）。
`BillboardCollectionVS` は軸に揃えた四角形に大きさを与えてから回すので、描ける絵は
**(回転 × 対角)** に限られる。地面の絵は **(対角 × 回転)** で、両者が一致するのは回転が直角の
倍数のときだけ。アートワークでは直交している**翼幅と胴体**が、投影ではどれだけ直交から外れるか:

| pitch | 0° | 30° | 60° | 78° |
|---|---|---|---|---|
| 直交からのずれ（track 045°） | 0.0° | 8.2° | 36.9° | **66.5°** |

78° では「丸め誤差」ではなく**形のほとんど**である。ここで **(回転 × 対角)** を描けば、
それは #R401 が却下された絵（全長そのままで地平線を向く機体）に戻ることになるので、
このエンジンは**表現できる正直な半分**を保つ。合わせるなら別の角度ではなく別のプリミティブが要る。

⚠ **78° はアプリ自身の天井**（`js/view-controls.js` の `STANDARD`）。「無制限」は設定でのオプトインなので、
`jumpTo({pitch:85})` は既定の読者に対しては **78 に丸められる**（実測: `getMaxPitch()` = 78、
要求 85 → 実際 78）。#R411 の最初の表はこの列を 85 と書いていたが、**その角度は測っていない**。

### 5.1b 不透明度100%は本当に100%（#R411）

マークの縁は**1画素**（`aa = 1.0 / v_px`。`q` は `v_px` 画素にわたって [−1,1] を張るので、
`1/v_px` は片側 0.5 画素）。⚠ **以前は `max(0.06, 3.0 / v_px)` ＝ 6 画素の傾斜**で、胴体
(4.4/44) も白縁 (2.6/44) もそれより細いため、`smoothstep` が底に着かず**マークはどこも
不透明になれなかった**。実際の輪郭で `v_col.a = 1`・`u_opacity = 1` として計算:

| `v_px` | 5 | 8 | **11**（既定） | 14 | 22 | 40 | 64 |
|---|---|---|---|---|---|---|---|
| 6画素の縁: ピーク被覆 | 0.819 | 0.889 | **0.954** | 0.995 | 1.000 | 1.000 | 1.000 |
| 　　　　　 ≥0.99 の割合 | 0.0% | 0.0% | **0.0%** | 0.0% | 3.0% | 18.3% | 25.0% |
| 1画素の縁: ピーク被覆 | 1.000 | 1.000 | **1.000** | 1.000 | 1.000 | 1.000 | 1.000 |
| 　　　　　 ≥0.99 の割合 | 0.1% | 4.3% | **12.6%** | 19.8% | 35.1% | 48.8% | 53.3% |

⚠ **下限 `0.06` が効き幅と同じくらい効いていた**——`v_px` 64 でも 1.9 画素の傾斜が残るので、
拡大しても solid にならなかった。

⚠ **これは不透明度の配管の話ではない。** スライダは `a_col.a * u_opacity` として**1回だけ**掛かる。
100% にして実測すると 3,780 機のうち **3,121 機 (82.6%) が alpha ちょうど 1.0**、
348 機が 0.72、311 機が 0.40——後者2つは §25.2 項9 の**鮮度フェード**（`live` ≤30秒 = 1.0 /
`lagging` ≤120秒 = 0.72 / `stale` = 0.40）であって、これは仕様どおりで残す。

⚠ **1.0 に届かず残るものは、マーク自身の宣言である。** 白縁の `STROKE_ALPHA = 0.95` は、
`js/plane-glyph.js` が symbol layer の原画だったころ `ctx.stroke()` が 0.95 で塗っていた値。
Cesium はいまも同じ path を canvas に `fill()` しており、**そちらの中身は常に不透明だった**——
2エンジン・1つのマークで、合っていなかったのは MapLibre 側である。

### 5.2 外挿は3秒で頭打ち

衛星は4秒でよい（運動が決定論的だから）。**航空機は3秒。** 旋回し、水平飛行に移り、着陸する。
頭打ちを過ぎたら glyph は**その場で止まる**——行っていない場所へ滑らかに線を引くのは、
止まっている機影より悪い答えだから。

### 5.3 ズームが決めるのは大きさと細かさだけ

| ズーム | スプライトの箱 | 形 |
|---|---|---|
| z0–2 | 3.5 px | 点（箱が 5 device px 未満） |
| z2–5 | 5.5–9 px | 5 device px を越えたものからシルエット |
| z5–8 | 9–40.15 px | シルエット（進行方向を向く） |
| z8–9 | 40.15–42.9 px | 同じマークが元の大きさへ |
| z9+ | 42.9 px（一定） | 元のマークそのもの |

⚠ **ズームが変えるのはこの2つだけ**（大きさと、点かシルエットか）。
**実高度で浮かせるかどうかは設定**（`lift`）であってズームの段ではない。

形は **旅客機のプランフォーム（胴体・後退翼・水平尾翼）＋白い縁取り**。宣言は
[`../js/plane-glyph.js`](../js/plane-glyph.js) に1箇所だけあり、MapLibre はそれを GLSL の SDF として、
Cesium は canvas のパスとして読む。箱の 92 % がマークで、z9 以上の機体は **全長 36.1 CSS px**。

⚠ **高ズーム側の値はここで選んだ数字ではない**。`icon-size` が掛けていた元の表（44 × icon-size）を
`IntMapPlaneGlyph.boxPx(z)` がそのまま返す。z9 で頭打ちなのも、元の表の最後の段が z9 だから。
低ズーム側（z0–5）は意図的に従来のまま——世界表示では数万機を同時に描く。

⚠ **取得を止めるズームは存在しない。** 本番では z1 で「Zoom in to load live aircraft」が
**270機が描かれている最中に**出ていた——ヒントと絵が同じ事実について食い違っていた。

⚠ **どちらのチャンネルを訊くかもズームでは決めない（#R401）。** `view` には z3.5 の下限が
あり、理由は「それ未満では視野がほぼ世界なので `world` が既に答えている」だった。
**本番で実測すると、`world` は世界の大半について答えていない**——その集合は掃引が払った格子
スライスと、他の利用者が見た視野の合併なので、ヨーロッパの外はほとんど空である。
北米上空でレイヤーを点けたまま45秒:

| ズーム | 出た要求 | 画面上の機数 |
|---|---|---|
| z3.2 | `?ch=world` ×3 だけ | **4 → 4** |
| z4.2 | `?ch=view` ×4 と world ×3 | **0 → 177** |

下限は2つの答えのどちらかを選んでいたのではない——その下には**2つ目の答えが無かった**。
⚠ **低ズームで訊くことは高ズームで訊くより高くつかない。** サーバーは視野1件あたりの上流読み
取りを `VIEW_MAX_TILES` に抑え、キャッシュ鍵を 0.5° に丸め、その空域が古いときだけ上流に触る。

## 6. Cesium 側

`PointPrimitiveCollection`（**全機**）＋ `BillboardCollection`（カメラに近い 4,000 機だけ
向き付きのシルエット）。補間は 10 Hz のタイマで、外挿は MapLibre 側と**同じ 3 秒**。

⚠ **1機に billboard は 2 枚**。billboard のテクセルは自分の色と**乗算**されるので、
1 枚の色付けで「色のついた機体＋白い縁取り」は作れない（しかも機体色は高度の連続ランプ）。
縁取りの環と中身を**重ならない 2 枚**に分けてあるので、どちらを先に描いても絵は変わらない。

⚠ **`billboard.alignedAxis` は使えない。** Cesium 1.143 の `BillboardCollectionVS` は
`acos(cos²θ)` を計算しており（正しくは `acos(cosθ)`）、東西南北の4方向以外では最大 **15.79°** ずれる
（45° の軸が 60° で描かれる）。機首方位が16度ずれるのは交通表示として嘘なので、
画面角を CPU で厳密に出して `rotation` に渡している。

## 7. 障害時（§25）

- **失敗しても画面は空にならない。** worker は持っている機体を保持し続け、経年で薄くなり、
  やがて落ちる。「取得できていない」と「0機」は**別の絵**。
- **合成データはこの経路に1機も無い。** 旧経路の `genSyntheticPlanes()` は
  `?aviation=v1` を明示したときだけ到達できる。
- `stats().updating` は**フィードについての主張**であって在庫についてではない。
  2万機を持っていてフィードが死んでいる状態は、「本物の機体が古くなりつつある」。

## 8. 切り替えと巻き戻し

```
?aviation=v1     旧経路（利用者ごとの掃引）
?aviation=v2     新経路
localStorage 'intmap_aviation_v2' = '0' | '1'
```

既定は **v2**——v1 の provider が消えているため。旧経路は §28 Phase G の巻き戻し期間のために
**1行も変えずに**残してある。
