## 0. なぜこの層があるのか

これより前、IntMap には「データセット」という語が 2 つの無関係なものを指していた。

- **地図に載せたもの** — 落としたファイルは `ugj-<n>` という描画ソースと 3 枚のレイヤーになり、
  あとに残るのは取り込み一覧の 1 行（名前・色・ソース id）だった。**地物は描画器の中にあり、属性は
  文字列で、その取り込みに何かを訊く経路は 1 本も無かった。**
- **分析できるもの** — `js/atlas-query.js` の 5 つの内蔵表。`from` はその 5 つの名前しか取らず、
  **利用者が持ち込んだものを 6 つ目にする経路が存在しなかった。**

つまり「CSV を落としたら地図に出る」と「その CSV を他のデータと同じように分析できる」は別々の
仕組みで、後者に入口が無かった。この層は**その 1 点**を埋めるものである。

## 1. データセットの契約 — `js/gis-datasets.js` (`window.IntMapData`)

```
{ id, title, kind:'vector', geometryType, withGeometry, crs, sourceCrs, fields[], count, time,
  features(), provenance, createdAt, stale }
```

**#R735 以降、payload は 2 種類ある。** `kind:'raster'` は地物ではなく**数値の格子**を持ち、
それ以外（id・provenance・lineage・`stale`）は全部同じ機械である（§1.4）。

| 欄 | 意味 |
|---|---|
| `geometryType` | `Point` / `LineString` / `Polygon`（`Multi*` はその単数に畳む）／全部が一致しなければ `Mixed`／地物ゼロなら `null` |
| `crs` | **常に `EPSG:4326`**。下流（描画・内包判定・切り取り）が全部 lng/lat 度を前提にしているので、各自の暗黙の前提ではなく**値として**述べる |
| `sourceCrs` | **届いた座標系**。GeoJSON（RFC 7946 §4）・KML・GPX は仕様が WGS 84 を固定するので `EPSG:4326`、区切りテキストは `null`。⚠ `null` は「名乗っていない」であって「4326 だった」ではない。**`crs` と違う値なら「その座標系で届き、取り込みのときに 4326 へ変換した」**（§1.3） |
| `fields[]` | 列ごとに `{name, type, empty, filled, total}`（数値列は `min`/`max` も。先頭ゼロで数から外れたセルの数は `padded`）。読者が宣言すれば `typeStated` / `typeRefused` / `unit` / `unitStated` が並ぶ（§5.2） |
| `withGeometry` | **幾何を持つ地物の件数**（測定値。ラスターでは `null`）。⚠ `geometryType` の `null` は「表」「空」「格子」の 3 つを同じ答えにするので、その 3 つを分けるのはこの欄である。`count > 0` かつ `withGeometry === 0` ＝ **座標を持たない統計表** |
| `time` | **時刻の宣言、または `null`**（§1.5）。⚠ `null` は「時刻の宣言が無い」であって「時刻が無い」ではない |
| `timeRefused` | 宣言が実データで**成り立たなかった**理由（`{why, detail}`）。宣言を写して持つのではなく**検証して**持つので、この欄が「誰も述べていないことを述べてしまう」ことを防ぐ |
| `features()` | **関数**。一覧・連鎖・クエリの橋はどれも metadata しか要らないので、地物の実体化はこの 1 つの扉だけ |
| `provenance` | 札ではなく**レシピ**（§3） |
| `stale` | `null`＝「この地物はこのレコードのレシピが出すもの」。`{why, since}`＝**上流の再計算が失敗したので、前の引数での答えが残っている**（§4.1）。レコードは常に `null` で生まれる——作り直しはフラグを消すのではなく**新しいレコードを作る**ので、消し忘れという状態が存在しない |

### 1.1 列の型は列名ではなく値で決める

⚠ **先頭ゼロのセルは符号であって数ではない（#R735）。** 十進の記法に無意味な先頭ゼロは無いので、
それが付いているセルは**識別子を綴ったもの**である。この規則が無かった間、`"01100"` は `number` と
判定され、`js/gis-ops.js` の比較は全部 `asNumber` を通るので **`"01100" == "1100"` が真**だった
——統計を隣の自治体に結合し、大きさを持たない列に min/max を印字する。
⚠ **規則は記法であって、列名の一覧ではない**（`/code|id|_cd$/` は
`.agents/rules/no-ad-hoc-hardcoding.md` が禁じる形で、次の国の綴りを取り落とす）。
`0`・`0.5`・`-0.25`・`0e3` は数のまま（そのゼロは有意）、`01`・`00`・`+007` は数ではない。
外した件数は `fields[].padded` に載るので、読者は「番号なのに計算できない」理由を見られる。

- **`number`** — 空でない値が**全部**「セル全体が数」として解けるとき。`12 km` は text（`parseFloat`
  が 12 と言い、その列は合計できるふりを始める）。
- **`date`** — 空でない値が全部**年から始まる ISO-8601 系**で解けるとき。⚠ `Date.parse` だけに任せない
  ——`03/04/2020` は**読む人によって違う日**になり、意味が読者で変わる列は text より悪い。
- **`text`** — それ以外。
- **空セルは型を決めない。** 900 個の数と 3 個の空白は「空白 3 個の数値列」で、そこで text と言うと
  列全体から算術を取り上げる。空セル数は判定の隣に持つ。
- **同点は `number` が勝つ**（`2020` は両方に解ける）。裸の年は数として比較・集計でき、時間軸として
  使いたい読者も何も失わない。

⚠ **列名の一覧（`lat`・`pop`・`年` …）で決めない。** それは
[`../.agents/rules/no-ad-hoc-hardcoding.md`](../.agents/rules/no-ad-hoc-hardcoding.md) が禁じる
「事例ごとの記述」で、書いた人が思いついた列については当たり、**次に来る列を黙って誤判定する**。

⚠ **この判定は 1 か所にしかない。** `js/gis-ops.js` は自分の出力の列を `IntMapData.typeColumn` で
型づける。2 つ持つと、**パネルでは比較できて問い合わせではできない列**という形で必ず離れる。

### 1.2 列の集合は全地物の和集合

先頭の地物の鍵ではない。GeoJSON は地物ごとに違う属性を持てるので、`features[0]` だけを読むと
**途中から始まる列が全部落ちる**。

### 1.3 座標変換 — `js/gis-crs.js` (`window.IntMapGisCrs`)

内部形式は経度・緯度に統一したままで、**変わったのは入口**。取り込みは
① GeoJSON の `crs` メンバ（`urn:ogc:def:crs:EPSG::NNNN` / `EPSG:NNNN` / 旧 `{"type":"EPSG",…}`。
`OGC:1.3:CRS84` は経度が先の WGS 84 なので 4326 と同じ）を読み、
② 4326 でなければ **proj4 で実際に変換**し、`sourceCrs` に**元のコード**を残す。

⚠ **EPSG の一覧を持たない。** 使える定義の出どころは 3 つの**規則**だけ:
proj4 自身が知るもの（4326 / 3857 / WGS84）、**UTM の算術**（`EPSG:326NN`＝北半球 zone NN・
`327NN`＝南半球。zone は 1..60）、読者が `define()` で渡した WKT または proj 文字列（`.prj` の中身）。
⚠ **③ には呼び出し元が 2 ラウンド無かった**（規則は在り、`.prj` を渡せる経路が無かった）。いまは
Shapefile の `.prj` がそれで、`js/geo-import.js` が変換の**前に**登録する——だから
`EPSG:6675` のような、内蔵の表が知らない国の座標系が**ファイル自身の定義**で読める。
GeoPackage の `gpkg_spatial_ref_sys` も同じ形の WKT を持つ。⚠ AUTHORITY を述べない `.prj` は
`PRJ:<基底名>` という**定義そのものの名前**で登録する——EPSG 番号を発明しない。
それ以外は **`crs-unknown` で断る**——近い定義を当てない。

⚠ **出力は常に `[lng, lat]`**。変換後に |緯度| > 90 なら `crs-axis-suspect` で断る。軸順序を
取り違えた変換は例外を出さず、地物を世界の裏側に静かに置くので、**測って拒む**。

⚠ **「述べていない」と「度ではない」は別**。座標が度の範囲に収まらないファイル（区切りテキストは
座標系を名乗らない）は `looksProjected()` が**測り**、`crs-not-stated-and-not-degrees` で取り込みを
断る。⚠ この判定は `IntMapGeodesy.sanitizeFeatures` **より前**に置く——あれは緯度を ±89.9999 に
**クランプ**するので、後ろに置くと投影座標が「北極に載ったもっともらしい形」になって証拠が消える。

変換できないファイルは `crs-unsupported` で**取り込みごと断る**。⚠ **黙って 4326 として置かない。**

### 1.4 数値ラスター — `kind:'raster'` と `js/gis-raster.js` (`window.IntMapGisRaster`)

```
{ id, title, kind:'raster', crs:'EPSG:4326', sourceCrs, width, height,
  grid:{ west, north, pixelLng, pixelLat }, bands:[{name,unit,nodata}], time,
  read(bandIndex), raster(), provenance, createdAt, stale }
```

**なぜ在るのか。** アプリの中には数値グリッドを読む経路が既に幾つもある（降水・気温・土地被覆・DEM）が、
どれも専用の読み手の中にあって、**処理器を向けられる相手ではなかった**。だから「この区域の人口」
「区域内の標高分布」「土地被覆ごとの面積」は 1 つずつ別の機能として作るしかなく、どれも次の分析へ
繋がらなかった。

- **行は北から南へ進む**（row 0 の中心緯度は `north − pixelLat/2`）。`pixelLng`・`pixelLat` は**常に正**。
- `read(bandIndex)` は長さ `width*height` の数値配列（row-major）。**`raster()` が扉**で、`features()` と
  同じ理由でそこに在る——4,000 × 4,000 は倍精度で 128 MB あり、一覧や連鎖や保存は metadata しか要らない。
- **`NaN` は常に欠損**で、バンドごとの `nodata` もそれとして扱う。⚠ 欠損を 0 で埋めない（0 は海面の標高で、
  雨量ゼロである）。
- **格子が格子でないものは登録の時点で拒む**（幅が整数でない・画素の大きさが 0 か負・`read` が関数でない）。
  そこを通してしまうと、以降の標本は全部**黙って間違う**。
- **バンドはその格子の列である。** `fields[]` にバンドが並ぶので、パネルの「どの列で」がそのまま
  「どのバンドで」になる（一つの操作、二つの実装を作らない）。

計器（`js/gis-raster.js`）が持つのは格子の算術だけ:
**地点値**（`nearest` / `bilinear`。⚠ **欠損を混ぜない**——隅のどれかが欠けたら nearest に落ち `partial`
を添える。実測の理由は `js/map-readout.js` の注記＝void 1 つと実測 3 つの混合が −7,800 m を出した）／
**区域内集計**（画素の所属は**中心の内外**で決め、平均は**面積重み付き**＝緯度で画素の面積が変わるので
単純平均は高緯度を過大に重く数える。`areaKm2` と `valueAreaKm2` を**両方**返すので「一部だけ」が見える）／
**値ごとの面積**（分類の格子だけ。測定値は `values-not-integer` で拒み、勝手に丸めない）／
**条件による抽出**（比較の正本は §2 の `evalCondition`）／**同じ格子同士の差分**
（⚠ 格子が違えば `grid-mismatch` で拒む——再標本化は**選択**であって、差分の中で黙って行えば全画素が
誰も名づけていない補間の合成になる）。

⚠ **既存の数値レイヤーは `fromSampler()` / `IntMapGisLayers.toRaster()` でこの契約に入る。** 1 画素 1 await
なので**中止でき、進捗を報告する**（§2.6）。焼いた格子は「レイヤーの標本」であることを provenance が述べる。

### 1.4a 格子の入口 — GeoTIFF / COG (`js/gis-geotiff.js`)

**#R749 まで、格子を持ち込む汎用の入口は 1 つも無かった。** アプリの中に数値グリッドを読む経路は
幾つもあったが（降水・気温・土地被覆・DEM）、どれも専用の読み手の中にあり、読者が自分のファイルを
落とす先は無かった。⚠ **依存は足していない**——TIFF 6.0 を自前で読む（前例は
`js/gis-geopackage.js` が依存を足さずに SQLite を読むこと）。

読むもの: II/MM 両バイト順・strip と tile（**COG は tile の TIFF**）・無圧縮／LZW／Deflate／
PackBits・predictor 1 と 2・uint / int / float × 8〜64 bit・ModelTiepoint+PixelScale と
ModelTransformation の両方・GeoKey の CRS・`GDAL_NODATA`・複数 IFD（**フル解像度を読み、
overviews は数だけ報告する**）。

⚠ **扱えないものは名前を付けて断る**（`refusals()` がその一覧を持つ）。BigTIFF・JPEG-in-TIFF・
登録名つきのその他の圧縮・8 の倍数でない bit 深度・PlanarConfiguration 2・**地理参照の無い TIFF**。
最後のものは他と種類が違う——**どこにあるかを述べていない画像は地図ではなく絵**で、どこかに置けば
それは誰も述べていない主張になる。

⚠ **`read(i)` は扉である**（§1.4 と同じ理由）。開いただけでは画素を 1 つも展開しない。

### 1.4b 格子を合わせる — `js/gis-warp.js` (`window.IntMapGisWarp`)

GDAL の warp が担っている役——**座標系・解像度・範囲・再標本化・NoData を 1 つの層で扱う**。
`to4326(grid,{method})` / `resample(grid,target,{method})` / `align(a,b,{rule})` / `methods()`。

- ⚠ **`method` に既定が無い。** 省略は `resample-method-not-stated` で断る。黙って選んだ補間は、
  §1.4 が差分について拒んでいるものと同じ——**誰も名づけていない補間の合成**である。
- ⚠ **欠損の規則を写さない。** 値はすべて `IntMapGisRaster.sample` が出す（隅が欠けたら nearest へ
  落ちて `partial` を数える、という 1 つの規則を 2 か所に持たない）。
- ⚠ **分類の格子を bilinear で補間しない。**「3」と「5」の中間の「4」は別の分類であって中間ではない。
  ただし**整数だから分類だとは推測しない**——バンドが `categorical` を述べているときだけ断る。
- **逆写像で走る**（出力画素の中心 → 4326 → 入力 CRS → 入力の画素）。順写像は穴を作る。
- **出力範囲は周を 1 画素刻みで歩いて求める**——投影された辺は度では曲線なので、四隅では足りない。
- `align` の**規則は呼び出し元が述べる**（`finer` / `coarser` / `first`）。交差が空なら `grids-disjoint`。

⇒ §1.4 の `grid-mismatch` は**今も正しい拒否**だが、行き先ができた: *「`js/gis-warp.js` で明示的に
合わせてから、もう一度」*。

### 1.5 時刻 — 宣言し、検証する

```
null                                          何も宣言されていない（≠ 時刻が無い）
{ kind:'instant',  field }                     地物ごとに 1 瞬
{ kind:'interval', startField, endField }      期間（どちらの端も空＝開いた端でよい）
{ kind:'track',    timesField, elevationField } 位置 1 つごとに 1 時刻（と標高）
{ kind:'constant', start, end }                データセット全体が 1 瞬／1 期間（レイヤーの有効時刻・
                                               ラスターの時期）
```

⚠ **宣言は実データに対して検証され、成り立たないものは名前で拒まれる**（`timeRefused`）。
呼び出し側が言ったことを写して持つのは、`.agents/rules/historical-verification.md` が禁じる形＝
**誰も述べていない主張が欄に入っている**状態である。

⚠ **`track` は取り分け信用できない。** 並行配列が時間軸であるのは**その長さが位置の数と等しい間だけ**で、
IntMap にはまさにそれを壊す経路がある——`js/geodesy.js` の `sanitizeFeatures` は直せない位置を**落とし**、
第 3 の座標成分を**畳む**（だから標高は座標の中ではなく**隣に**運ぶ）。位置 1 つが落ちれば以降の時刻が
全部 1 つずれる。だから長さは**地物ごとに測り**、1 件でも合わなければ宣言全体を拒む。

⚠ **裸の年はその年 1 年**である。`asDate` は `1889` を ISO の年接頭辞として受け、
`1889-01-01T00:00:00Z`＝**1 ミリ秒**を答える——年の列に対して「1889 年」の窓がほとんど何も掴まなくなる。
だから年の規則を**先に**訊く。⚠ 年の作り方は `Date.UTC` ではない（100 未満の年が 1900+y になる・#R602）。

## 2. 処理 — `js/gis-ops.js` (`window.IntMapGisOps`)

**この層の存在理由は「出力が入力と同じ形で登録される」こと。**「5km バッファ」→「その中だけ」→
「区域ごとに数える」は、作り込んだ 1 本のパイプラインではなく**登録 3 回**である。

### 2.1 宣言を読むのは UI の仕事、持つのは op の仕事

`ops()` が返す宣言（`inputs` / `accepts` / `output` / `params[]`）**だけ**を読んで画面を作る。
`params[].input` が「その列名をどの入力から選ぶか」を、`requiredWhen` が条件つき必須を、
`needsGeodesy` が「`window.IntMapGeodesy` が無ければ走れない」ことを、`needsGeometry` が
「`window.IntMapGisGeometry`（§2.5）が要る」ことを**データとして**述べる。
⚠ UI 側に「buffer は半径を聞く」という手書きの一覧を作らない（#R725 と同じ方針）。

⚠ **一覧は `DECL` 1 つだけ。** `ops()` はかつて `ORDER = ['filter','buffer','clip','aggregate']` を
map していて、**`DECL` に足して `ORDER` に足し忘れた op は run() に答えるのに画面に出なかった**
——上の段落が禁じている手書きの一覧が、その段落の真下にあった。いまは `Object.keys(DECL)` で、
`run()` の dispatch も **op id を鍵にした表**（以前の if 連鎖は無条件の `else` で終わっていたので、
配線し忘れた op は黙って aggregate を走らせていた。今は `op-not-wired`）。

| op | 入力 | 受ける geometry | 出力 | 引数 |
|---|---|---|---|---|
| `filter` | 1 | 何でも | 入力と同じ | `where`（`{field, op, value}` の配列・全条件 AND） |
| `buffer` | 1 | **何でも** | `Polygon` | `radiusKm`（必須。**負＝内向き**、面のみ）・`steps` |
| `clip` | 2（対象・窓） | 何でも／`Polygon` | 対象と同じ | 無し |
| `intersect` | 2 | `Polygon`／`Polygon` | `Polygon` | 無し |
| `difference` | 2 | `Polygon`／`Polygon` | `Polygon` | 無し |
| `union` | 2 | `Polygon`／`Polygon` | `Polygon` | 無し |
| `dissolve` | 1 | `Polygon` | `Polygon` | `by`（列名。省略＝全部で 1 群） |
| `relate` | 2 | 何でも／何でも | 入力と同じ | `predicate`（`intersects`/`within`/`contains`/`disjoint`/`nearer-than`）・`maxKm` |
| `aggregate` | 2（面・相手） | `Polygon`／**何でも** | `Polygon` | `stat`（`count`/`sum`/`mean`/`min`/`max`）・`field`・`outName` |
| `sample` | 2（点・**格子**） | `Point`／— | 入力と同じ | `band`・`method`（`nearest`/`bilinear`）・`outName` |
| `zonal` | 2（面・**格子**） | `Polygon`／— | `Polygon` | `band`・`stat`（`mean`/`sum`/`min`/`max`/`count`/`classes`）・`outName` |
| `rasterMask` | 1（**格子**） | — | **格子** | `band`・`op`・`value` |
| `rasterDiff` | 2（**格子**・**格子**） | — | **格子** | `band` |
| `timeWindow` | 1 | 何でも | 入力と同じ | `from`・`to`・`mode`（`overlaps`/`within`） |
| `join` | 2（対象・**表**） | 何でも／何でも | 対象と同じ | `leftField`・`rightField`（必須）・`fields`・`prefix`・`unmatched`・`duplicates` |
| `compute` | 1 | 何でも | 入力と同じ | `outName`・`expr`（必須）・`replace` |

⚠ **`kinds` が入力ごとの中身（vector / raster）を宣言し、既定は `vector`。** `accepts` が訊くのは
geometry で、格子はそれを持たない——この鍵が無ければ、**格子より前に書かれた 9 つの op が
`geometryType:null` の格子を受け取り**、`Mixed` として拒むか（`any` の枠では）在りもしない
`features()` を歩くかのどちらかだった。宣言と既定があるので、**9 つ全部が一度に**
`input-kind` で名前を付けて拒む。

⚠ **`zonal` の `classes` は分類の格子だけ。** 測定値の格子は `values-not-integer` で拒む——丸めれば
誰も定義していない区分を作ってしまう。行には `_gridAreaKm2` と `_valueAreaKm2` が付き、
**その差が答えの被覆**である（件数で報告すると「一部だけ」が原理的に見えない）。

⚠ **`join` が結ぶのは識別子であって数ではない（#R738）。** この層の他の比較は全部 `asNumber` を
通る——量を比べているからである。結合が比べるのは**符号**で、両者は**まさに問題になるセルで別の
答えを返す**: `"01100"`（札幌市中央区）と `"1100"` は 1 つの数で 2 つの場所である。だから比較は
セルの文字列（前後の空白を落としたもの）で、**一致した件数・しなかった件数・一致しなかった鍵の実例**を
**答えとして返す**——同じ市区町村コードを違う綴りで書いた 2 ファイルは、構造的には完璧で情報の無い
結合を作り、それを読者が見る方法は「何行が相手を見つけたか」を告げられることしか無い。
⚠ 同じ鍵が右側に 2 度あれば**拒む**（`duplicates:'first'` と述べれば通る）。黙って 1 つ選ぶことも、
黙って行を増やすことも、**読者が見ていないデータで行数が決まる**ことを意味する。
⚠ 列名がぶつかれば拒む（`prefix` が読者の答え）。上書きは画面に出ているデータを壊し、ここで改名すれば
**誰も知らない名前**を発明することになる。

⚠ **`compute` の式は解釈されるのであって評価されない（#R738）。** `js/gis-expr.js` は自前の
トークナイザと再帰下降パーサで、**`eval` も `new Function` も使わない**。空は 0 ではなく**伝播**し
（`coalesce(x,0)` は読者が述べる）、先頭ゼロのセルは算術に入らず（規則は `IntMapData` に訊く。
§1.1）、0 除算は `null`、`'a' + 1` は連結ではなく `expr-type`。⚠ **式が名指す列はデータセットに
対して検査される**——`filter` の条件と同じ規則で、綴り違いは**null の列**ではなく拒否になる。

⚠ **`accepts:'any'` は「どんな形でも」であって「形が無くてもよい」ではない（#R738）。**
統計表は `geometry:null` の行として取り込まれ、`geometryType` はそれでも `null`・空の
データセットでも `null`・格子でも `null` ——1 つの欄が分けられない 3 つである。だから
`js/gis-datasets.js` が `withGeometry` を**測り**、**幾何カーネルか測地を要する op** は
`input-has-no-geometry` で拒む。そうでなければ buffer は全行を歩き、座標を 1 つも見つけず、
**空の面のレイヤーを登録する**——成功した処理・0 件の答え・入力に場所が無かったことを述べるものが
どこにも無い状態である。⚠ `filter`・`timeWindow`・`join`・`compute` はどちらも宣言しないので
**表の上で動き続ける**。それが表を取り込める理由そのものである。

⚠ **`timeWindow` が読むのはデータセットの宣言（§1.5）であって、ここで打ったの列名ではない。**
だから出来事の表・治世の表・GPS の軌跡に同じ op が効き、軸を宣言していないデータセットは
`time-not-declared` で拒まれる（推測で絞り込まない）。⚠ **軌跡に対しては「選ぶ」ではなく「切る」**
——「17 時台に通った区間」は線の一部であって、4,000 点のうち 1 点が入っているからといって
乗車まるごとを返すのは、誰も訊いていない問いへの答えである。**並行配列も一緒に切る**（切らなければ、
以降の時刻が全部ずれた軌跡になる——それは §1.5 が測っている不変条件そのもの）。

⚠ `relate` の `nearer-than` は**形そのものからの最短測地距離**で、測った値を `_distanceKm` に書く。
⚠ `aggregate` は「面に含まれる**点**」ではなく「その面に**重なるもの**」を数える。線が境界をまたげば
**両方の面に数えられる**——それが「重なる」の意味であって、区画分割は別の問いである（だから行に
`_areaKm2` が付く）。

### 2.2 拒否は文ではなくコード

`{ok:false, why, detail}` を返し、**9 言語の文面は呼び出し側**（`js/gis-panel.js` の `reasonText`）が
持つ。`js/geo-import.js` と同じ作法——decoder に UI の言語を持たせない。

⚠ **コードを足したら文も足す。** `tests/r729-gis-core-checks.test.mjs` が、`js/gis-ops.js` ・
`js/gis-project.js` ・ `js/gis-core.js` ・ `js/gis-layers.js` ・ `js/gis-raster.js` が
**返しうるコードの集合**を構文から集め、
`js/gis-panel.js` が**文を持つコードの集合**と一致することを測る（`tests/r576-checks.test.mjs` ⑩ と
同じ形）。片方だけ足すと赤くなる。

### 2.3 本当に拒む——もっともらしいものを描かない

いま断るのは、**その op がその入力では意味を持たないとき**だけである。

- **内向きバッファ（負の半径）は、内側を持つものにしか無い。** 点や線には縮める内側が無いので
  `inward-buffer-needs-area` で名指して断る。0 に丸めない。
- **重ね合わせの相手に面が無い**なら `no-overlay-polygons`、切り抜きの窓に面が無いなら
  `no-clip-polygons`。
- **古い入力（`stale`）は `input-stale` で断る**（§4.1）。消費すると、古さが「現行」と名乗る新しい
  レコードの中へ入ってしまう——**そこが、古さが見えなくなる唯一の場所**である。
- **幾何カーネルが届かなかったセッションでは `geometry-unavailable`。**
  ⚠ 「訊けなかった」と「0 件だった」を同じ答えにしない。

⚠ **かつてここにあった 3 つの拒否は、実装に置き換わった。** `buffer-needs-points`（線・面の
バッファが無かった）・`clip-window-not-convex`（S-H は凸窓でしか正しくない）・
`clip-window-crosses-antimeridian`（継ぎ目をどちら側と読むか推測できなかった）は、どれも
**engine が無かったときの正直な断り**であって、いまはどれも仕事である（§2.5）。
検査もそう移した：`tests/r729-gis-core-checks.test.mjs` ③ からこの 3 つが消え、
`tests/r732-gis-geometry-crs-checks.test.mjs` ②③④ が**同じ入力が正しく計算されること**を測る。
**拒否が実装になった回に検査を消すだけにすると、それは見るのをやめた回になる。**

### 2.4 どの面で計算しているか（誤差はここから来る）

- **ブール演算も内包判定も平面** — 生の lng/lat 度（plate carrée）。
  - **日付変更線**: 隣り合う頂点の経度差が 180° を超えたら、それは継ぎ目である（この地図が読む
    どのデータにも、半周ぶんの長さを持つ**辺**は無い）。だから環は**ほどき**（unwrap）、両辺を
    **同じ 360° 窓へ揃え**、その平面で計算し、`IntMapGeodesy._splitPolyToWindows` で
    `[-180, 180]` に**戻す**——`diskFillPolys` が出す円盤が通っているのと同じ分割器。
  - **いまも断る唯一のもの**: ほどいたあと経度幅が 360° 以上になる環（極冠・全球環）。
    それは**どの円筒平面でも単純な環になれない**ので、断っているのはデータではなく平面のほうである。
- **面積は平面ではない** — `areaKm2` は球面過剰（Chamberlain–Duquette）、外側 ring を足し穴を引く。
  半径は `IntMapGeodesy._R_EARTH_KM`（アプリが持つ唯一の半径）。⚠ 度の平面で面積を測ると cos φ 分
  ——**緯度 60° で半分**——ずれる。そこはヨーロッパの大半である。
- **距離は測地線** — `distanceKm` は点と点は haversine、点と線分は**問い合わせ点を中心にした
  局所の等距円筒面で「どの点が最も近いか」だけを選び、距離そのものは本物の測地線で測る**。
  投影は返す数に現れない。

### 2.5 幾何カーネル — `js/gis-geometry.js` (`window.IntMapGisGeometry`)

boolean 演算は **`polygon-clipping`（Martinez–Rueda の sweep line）** に訊く。**このアプリが既に
持っている依存**で、`js/world-packs.js` と `js/cesium-vector-tiles.js` が同じように動的 import して
いる。**2 つ目の boolean engine をここに書くのは「同じ判断を 2 か所に持たせる」こと**で、しかも
出来の悪いほうになる。⚠ **読み込みは遅延**——重ね合わせを 1 度も走らせない読者は sweep line を
ダウンロードしない。

**バッファはオフセット曲線ではなく Minkowski 和である。** 半径 r のバッファの定義が「その形から
r 以内の点の集合」＝「その形と半径 r の円盤の Minkowski 和」なので、そのとおりに作る:
頂点ごとに**測地円盤**（`diskFillPolys`。点バッファがずっと使ってきたもの）、辺ごとに**測地の
四辺形**（両端を方位角 ±90° に r ずらす）、全部を union する。union が自己交差を消し、円盤が継ぎ目を
丸める。⚠ `@turf/buffer` を使わないのは、turf-jsts（332 kB）に届くことと、**オフセットを平面で
計算するので緯度 60° の「5 km」が 5 km ではない**ことの 2 つ。
⚠ **内接近似であることを述べる**: `steps` 枚の円盤と四辺形は弦で接するので、境界は真のバッファの
内側に最大 r·(1−cos(π/steps))——既定の 64 で 5 km バッファなら 3 m——入る。丸めずに
`_bufferSteps` として行に書く。

#### 2.5.1 ⚠ 「答えは空だった」と「答えられなかった」は同じ null ではない（#R743）

カーネルの入口はどれも `null` を返していた。**交わらなかった 2 つの県も、クリッパが例外を投げた
ときも、環が世界を一周していたときも、同じ 1 つの `null`** で、このファイルのヘッダは
`clipper-unavailable` / `geometry-wraps-world` という**語で断ると書いていた**——その 2 つの綴りは
**リポジトリ全体でコメントの中にしか無かった**。名前で断ることになっている拒否が、名前を持って
いなかった。

読み手の側がそれをどう読んでいたか（実測・全 8 runner）: `js/gis-ops.js` は `null` を
「この行は答えに入らない」と読んで `continue` し、**`{ ok: true }` で一回り小さい答えを返して
いた**。述語 2 つはそれより悪い——`disjoint` は `!intersects` で、`intersects` は計算できないとき
`false` を返す。つまり**失敗が「この二つは離れている」と断言していた**。`contains` は
`!difference(b, a)` なので、**例外が「b は a に完全に含まれる」になった**。

いまは同じ演算に**読める形の扉**がある（`attempt`。plain な名前はその 1 行のラッパで、外から見た
挙動は 1 文字も変わらない）:

| 返り値 | 意味 |
|---|---|
| `{ ok: true, geometry: <G> }` / `{ ok: true, value: v }` | 計算できた |
| `{ ok: true, geometry: null }` | 計算できて、**答えが空だった** |
| `{ ok: false, why, detail }` | **計算できなかった**。`why` は `clipper-unavailable` / `clipper-failed` / `geometry-wraps-world` / `geodesy-unavailable` / `bad-radius` / `inward-buffer-needs-area` / `missing-geometry` / `no-comparable-parts` |

`js/gis-ops.js` 側の規則は 2 つで、**op ごとではなく 1 か所**にある（`makeGeoLedger` /
`withGeoStats`）:

- **一部が計算できなかった実行は、その件数と最初の理由を `stats` で述べる**（`geometryFailed` /
  `geometryWhy`）。`js/gis-panel.js` は op が何を測ったかを知らずに `stats` を印字するので、
  足した日から 9 言語すべての読者に届く。
- **何も計算できなかった実行は `geometry-failed` で拒む。**「0 件でした」と
  「0 件しか計算できませんでした」は読者に区別できず、**前者だけが読者のデータについての答え**である。

線の切り抜きだけは sweep line の仕事ではない（面しか取らない）。各線分を**窓の全環との交点で切り**、
**各片の中点が内側か**で採否を決める——凹んだ窓でも穴があっても正しい唯一の判定で、連続する交点の
あいだは丸ごと内か丸ごと外だから成り立つ。---

#### 2.5.2 ⚠ `union` は和集合であって、対ごとの結合ではない（#R743）

`union` は重ね合わせのループの 1 分岐で、**そのループは対のループだった**。B の窓のうち箱が
重なるものを候補源に訊き、対ごとに `GG.union([a, b])` を 1 行として出していた。ここから 2 つが
出荷されていた:

- **離れている入力では答えが空になる。** 触れていない 2 つの四角は対を作らないので、ループは
  1 行も出さず、op は**どちらの入力も現れないデータセット**を `ok:true` で返した。
- **重なっている入力では面積が壊れる。** 対ごとに a 全体と b 全体を出すので、同じ土地が対の数だけ
  数えられ、`_areaKm2` の総和は地球を何個も超えた。

和集合には**3 種類の部分**があり、どちらの入力のどの点もちょうど 1 つに属する:
**a ∩ b**（両方の表を持つ）・**a − B**（A の表）・**b − A**（B の表）。**離れている入力は特別扱いでは
なく、1 つ目が空の実行にすぎない**——これが「事例ではなく、その事例を生んだ構造を直す」の中身である。
行は `_overlaySide`（`both` / `a` / `b`）で自分がどれかを述べる。2 つのファイルから来た行が混ざった
表がそれを言わないなら読めないし、**列からは復元できない**（b − A の行は A の列が無く、それは空欄と
同じ見た目である）。

#### 2.5.3 ⚠ ふるいの余白は km で渡す——「度」にした瞬間に緯度で壊れる（#R743）

`nearer-than` は候補を箱で絞る。その余白は**呼び出し側が km を度に直して**渡していて、箱の判定は
その 1 つの数を**両方の軸**に当てていた。しかもそれを正しいと述べる註が付いていた——
「経度 1 度は緯度 1 度より短いので、緯度の度を両軸に使えば経度方向は過大に見積もる」。

⚠ **この文は逆で、ふるいは内側に誤っていた。** 経度 1 度が km で短いことは、d km を覆うのに
**より多くの度が要る**理由である。北緯 60° では経度 1 度は 55.66 km なので、80 km は**経度 1.437°・
緯度 0.719°**。両軸に渡されていたのは緯度のほうなので、**60°N で経度 1 度離れた 2 点（55.66 km、
80 km の問い合わせに十分入る）は、距離を測る前に落ちていた**。

⚠ **索引あり／なしの比較ではこれは見えない。** `tests/r735` ⑥ は索引経路と全件走査を突き合わせる
が、**どちらも同じ 1 つの関数を同じ数で呼ぶ**。1 つの誤った規則の 2 人の読み手が一致しても、
規則を測ったことにはならない。いまは `padBoxKm` が**箱の緯度から両軸の余白を導き**、その**箱**を
索引と走査の両方に渡す（規則も継ぎ目の判定も 1 つになる）。⚠ 余白が ±180 を越えるときは
**経度全域**にする——継ぎ目で止めるのは内側の誤りだからである。

### 2.6 対の数え上げと、止められること（#R735）

**索引 — `js/gis-index.js` (`window.IntMapGisIndex`)。** `aggregate`・`relate`・`clip`・重ね合わせはかつて
「面をループ × 相手をループ」で、外接矩形は**定数を下げるだけ**だった（ファイル自身がそう書いていた）。
一様格子が対の数え上げそのものを止める。実測 40,000 × 1,000 で **756 ms → build 79 ms + query 3 ms**。

- **セルの大きさはデータから導く**（定数で決め打ちしない）。
- ⚠ **不変条件は偽陰性ゼロ。** 落として速くする仕組みなので、落としてはならないものを落とすと
  **集計が静かに少ない数を答える**。子午線をまたぐ箱・世界を覆う箱・箱を持たないものは
  「どの問い合わせにも出す」箱に入れ、その件数は `stats().oversize` で**外から見える**
  （1 セルに全件入っている索引は、外から見ると動いている索引とまったく同じ振る舞いをする）。
- **索引が無くても答えは同じ**（遅いだけ）。`tests/r735-…` ⑥ は**索引を外した同じ run** と突き合わせる
  ——取りこぼしは「間違った答え」ではなく「少し小さい数」なので、それ以外では捕まらない。

**中止と進捗 — `run(step, {signal, onProgress})`（対で走る 5 つの op）。** ⚠ **同期のループは中止できない**、これは UI の
制約ではない。`run()` は前から `async` だったが、中の走者は 1 本の切れないループで、
40,000 面の集計はその間ずっと単一スレッドを握る——地図が止まり、進捗は描けず、
`AbortSignal` は**立てることすらできない**（立てるコードがループが手放すまで走らないので）。
その上に中止ボタンを出すのは、効果のない操作を出すことである。

- ⚠ **刻みの単位は件数ではなく時間。** 「1,000 面ごと」はあるデータでは 3 ms、別のデータでは 40 秒。
  意味があるのは**スレッドを握っていた長さ**で、60 Hz の 1 フレームがレンダラの要求である。
  だから経過ミリ秒で譲り、データセットごとに調整する数が存在しない。
- ⚠ **これは Worker ではない。** この層が呼ぶカーネル（sweep-line・レジストリ・測地）は全部この
  スレッドに居るので、ループだけ移せば呼び出しは全部置いていかれる。Worker が足すのは**並列性**で、
  これが足したのは**読者に応えるスレッド**——足りていなかったのは「止められる」の側だった（§6）。

## 3. 由来 — `provenance` は札ではなくレシピ

```
{kind:'import', file, format, readAt}        取り込み — 再実行するものが無い。バイトが起源
{kind:'op', op, inputs:[id…], params:{…}}    処理   — これだけで、もう一度走らせられる
{…, edits:{count, lastAt}}                   読者が値を編集した記録（§5.2）。種類は変わらない
```

`IntMapData.lineage(id)` が上流から順に、`dependents(id)` が「これを入力にしているもの」を返す。
**「半径を 5km から 10km に変えて再計算する」の実体はこれ**である（§4）。

## 4. プロジェクト保存 — `js/gis-project.js` (`window.IntMapGisProject`)

**保存する**: 取り込みは**本体ごと**（features）、処理は**段だけ**（`op`/`inputs`/`params`）。
順序は `lineage()` 展開＝**入力が必ず先**。置き場は **IndexedDB**（`intmap-gis` / `projects`）。

**保存しない**: 基図・カメラ・有効レイヤー・タブ・年。それは `js/session-tabs.js` の持ち物で、
**同じ事実を 2 か所に持たない**。

**処理の結果を保存しないのはなぜか** — レシピがあるなら再生できるし、保存すると**入力を変えた
ときに結果だけが古いまま残る**。

**`setParams(datasetId, params)`** が引数を差し替えて（渡した鍵だけ・渡さない鍵は保持）、対象と
**その下流**をトポロジ順に、**同じ id のまま**走らせ直す。循環は `cycle` で拒む。

⚠ **保存するものが #R749 で 2 つ増えた。両方とも「レシピで再生する」設計の帰結である。**

**① 利用者が宣言した列の型・単位。** `IntMapData.declarations(id)` が出し、
`restoreDeclarations(id, decls)` が戻す。取り消し履歴とは**寿命が違う**——undo はキーストロークだが、
「この列は人数か、人口密度か」「単位は m か km か」は**操作履歴ではなくデータの意味**である。
⚠ **戻すときも実データに対して検証する**（宣言したときと同じ経路を通る）。データが動いていて
成り立たなくなった宣言は**写さずに断り**、`declarationsRefused` として読者に届く——保存された
宣言を無検証で写すのは、`.agents/rules/historical-verification.md` §2 の 3 が禁じる形そのもの。

**② どの実装が計算したか。** op の段は `engine:{ops, geometry}` を持つ。⚠ **同じレシピは、実装が
違えば同じ答えではない**——#R743 が `union` と距離のふるいの**答えそのもの**を変えたので、その前に
保存されたプロジェクトは今日ひらくと違う数を持つ。読み込みは **「同じ」「違う」「測れなかった」の
3 つ**を区別して返し（`engineChanged` / `engineUnknown`）、パネルがそれを文にする。
⚠ **再計算は止めない**（読者のプロジェクトを開けなくするのは過剰）。⚠ **測れなかったものを
「同じ」に畳まない**——「読めなかった」を「同じ」の証拠に使う形は、この記録が繰り返し捕まえている。

版そのものは各カーネルが持ち（`IntMapGisOps.version()` / `IntMapGisGeometry.version()`）、
**バイトが動いたのに版が動いていなければ門が落ちる**（台帳 `scripts/gis-kernel-versions.mjs`、
測るのは `tests/r749-gis-raster-pipeline-checks` ⑨）。手で保つ版は最初の 1 回で腐り、
**腐った版は版が無いより悪い**——変わったエンジンについて「同じです」と述べるから。

### 4.1 失敗した再計算は、鎖をその場に残して印をつける

ここは 2 つとも壊れていた。**⑴ 失敗した段は既に消されていた**——id を空けるのは作り直しに必要な
手順だが、**失う**のは違う。op が断る半径を打った読者は編集中のデータセットごと失い、次の
`setParams` は `no-such-dataset` としか答えられなかった。**⑵ その下流は触られもしなかった**ので、
**古い引数での答えを持ったまま**レジストリに残り、パネルは並べ、地図は描き、次の op は食べた。

いまは **各段が commit-or-restore** である。古いレコードを保持したまま走らせ、失敗したら**戻して**
`stale` を立て、そこから下流全部へ伝播する。

- `failed[]` は呼び出し元への報告（実行されなかった段は `upstream-failed`）。
- `stale` は**データセット自身が持つ状態**で、パネル・地図・次の op が読むのはこちら。
  ⚠ 伝わるのは**根本の理由**（実際に断られたコード）であって `upstream-failed` ではない——
  読者が直すのは根本のほうで、症状の言い換えに上書きすると診断が消える。
- 地物は**消さずに残す**。実際に計算された最後の答えは、空のパネルより読者にとって価値がある——
  **ただし、全員がそれを何であるかと述べている限り**。だから `js/gis-ops.js` が `input-stale` で
  断り（§2.3）、パネルがバッジを出す。**誰も検査しない状態は、状態ではなく飾りである。**

⚠ **`ok` は部分成功を true にしない**（`failed[]` が空のときだけ true）。

⚠ `failed[].why` には **op が返した `why` がそのまま入ることがある**。`op-failed` に潰すと、
読者に必要な 1 文（何が悪かったのか）が消える。
⚠ IndexedDB が無い環境では**黙って成功を返さない**——`storage-unavailable` を返し、
`available()` が false を返す。1 回 open に失敗しただけでは殺さない（「今ディスクが一杯」と
「そもそも無い」は別の主張）。

## 5. 横断クエリがこの層を読む向き — `js/atlas-query.js`

`data.query` の `from` に**データセットの id をそのまま書ける**。列は `fields[]` そのもので、
cost 0 ・ origin `raw`（＝出典レコードの項目の写し。この行が持っている）。

⚠ **押し込み（登録）ではなく引き（pull）である。** クエリ engine は遅延読み込みなので、
セッションの早い段階で「engine に登録する」経路は**まだ存在しないモジュールへの登録**になり、
その取りこぼしを直す**再生**という 2 つ目の正本ができる。代わりに `run()` / `catalogue()` /
`tables()` の入口で `syncUserTables()` がレジストリを**その瞬間に読む**。規則は 1 つ、評価は遅く、
ファイルがいつ来ても正しい。

⚠ **線と面は自分の形を持ったまま渡る。** 行は元の geometry への**参照**（コピーではない）と
その外接矩形を持ち、**空間の判定は全部その形で行う**。表に出る 1 点はいまも外接矩形の中心だが、
**そこからは何も測らない**——そして**行が自分で**「この座標はここで計算した代表点である」と述べる
（以前は注記が結果全体に 1 回付くだけで、どの行が実点でどの行が導出点かを読者は区別できなかった）。

⚠ **これが `near` にできないことである。** `near` はピンとピンのあいだを測る。線や面には 1 つの
ピンが無く、その代わりが外接矩形の中心だった——C 字の区域や湾曲した道路では、**その中心は形の外**
にある。だから `spatial` 句が別にある:
`{"rel":"within"|"contains"|"intersects"|"nearer_than","of":TABLE|"geometry":GeoJSON,"km":num,…}`。
`within` は相手の表を**1 つの集合として**扱う（どの構成員の中にも無いが和集合の中にある行が、
正しく中に入る）。`catalogue()` はこの一覧を**実行する側の宣言から導出**して返すので、
planner が見られない述語を足すには、宣言に無いものを実行するしかない（#R582 の形を避ける）。

⚠ 述語は 1 種類しか書かない。形を持たない行（内蔵の点の表）には `[lng,lat]` の Point を組んで
**同じ述語へ渡す**。

## 5.1 地図のレイヤーを入力にする — `js/gis-layers.js` (`window.IntMapGisLayers`)

`sources()` は**一覧を持たずに数え上げる**——`IntMapLayers.list()` のうち `featuresIn` に答える行と、
geo-engine が持つ geojson source。手で並べた一覧は、次に足されたレイヤーを黙って落とす。
`read()` は**形状も属性も落とさない**。`toDataset()` が `IntMapData` に登録し、`provenance` は
`{kind:'layer', layer, bounds, at, statedTime}`＝**いつ・どのレイヤーの・どの範囲を読んだか**。

⚠ **#R732 の時点で、このファイルの呼び出し元は 0 件だった（#R735 で直した）。** 橋は作られ、検査され、
3 つの文書に書かれ、そしてプログラムの中で参照していたのは**その検査とその散文だけ**——読者は地図の
レイヤーを分析に入れられなかった。入口は `js/gis-panel.js` の「地図から取り込む」節で、
`sources()` を並べ、`toDataset()` と `toRaster()` を呼ぶ。**呼ばれない export は機能ではない。**

⚠ **レイヤーが述べる時刻は文であって時刻ではない。** `IntMapLayers.state(id).time` は読者に向けて
書かれている（「直近 24 h」「2020-06-15 12:00 UTC」「1889」）。だから 2 通りに運ぶ——文は
`provenance.statedTime` にそのまま、`time` の宣言は**その文が実際に時刻として読めるときだけ**。
「直近 24 h」を瞬間として宣言するのは、この製品が記録している
「誰も述べていないことを地図が述べる」欠陥を別の場所で再演することである。

⚠ **数値レイヤーは `toRaster()` で格子になる**（§1.4）。半分は地物ではなく**場**で、
`sampleAt` に 1 点ずつ訊く契約しか無いので、**1 画素 1 await** である——だから上限を書く代わりに
`signal` で中止でき `onProgress` で進捗を述べ、行ごとにイベントループへ譲る。
⚠ 消えているレイヤーは `layer-not-sampling` で拒む（消えているレイヤーは格子を読み込んでいないので、
全画素が穴になる＝「何も無い」ように見える測定になる）。

⚠ **保存は body（地物そのもの）で、レシピの再実行ではない。** レイヤーの中身は時刻で変わるので、
残すべきは「あのとき読んだもの」である。

⚠ **地図側の窓も直した。** `js/map-ui.js` の `_srcFeatsIn` は「箱に入っているか」という問いを
`geometry.type === 'Point'` で代用していたので、**レイヤーが持つ線と面は必ず 0 件**だった。

## 5.2 属性の編集と取り消し — `js/gis-datasets.js`

取り込んだ値は**読み取り専用ではない**。`editValues` / `addField` / `removeField` / `renameField` が
値と列を変え、`undo` / `redo` / `history` が戻す。⚠ **この機能の本体は、何を拒むかである。**

- **op の出力は編集しない**（`edit-would-contradict-recipe`）。その記録の地物は**自分のレシピが出す
  もの**であり（§3）、編集するとその等式が壊れる——`setParams` の再計算が読者の編集を黙って消し、
  §4 の「結果を保存しないのはレシピがあれば再生できるから」が同時に偽になる。**取り込んだ側を
  編集するか、編集用の複製を作る**。
- **ラスターは編集しない**（`edit-needs-features`）。画素は属性ではない。
- **`stale` な記録は編集しない**（§4.1 と同じ理由。古さが編集で見えなくなる）。
- **下流のある列は消さない・改名しない**（`field-has-dependents`）。その列を読んでいるレシピが
  再実行できなくなり、そのとき列はもう戻せない。`time` の宣言が名指す列も同じ
  （`field-in-time-axis`。無い列を名指す宣言は §1.5 が防いでいる形そのもの）。
- 値を編集すると `fields[]` と `count` と `withGeometry` を**測り直す**。宣言した型が成り立た
  なくなれば外して `fields[].typeRefused` を立てる——編集で `"abc"` が入った number 列は、もう
  number ではない。黙って number のままにするのは**誰も述べていない主張**である。
- 編集は `dependents()` を `stale`（`input-edited`）にする。**入力が変わったのだから下流は答えでない。**

⚠ **`provenance.kind` は `import` のまま**で、`provenance.edits = {count, lastAt}` が足される。
バイトが起源であることは編集で変わらないが、**読者が触ったことは読者に見える**必要がある。

⚠ **取り消しは session の中だけ。** 履歴は**逆操作**（どの行のどの列が何だったか）で持つので、
4 万件の表を 20 回編集しても地物の複製は積まれない。保存に乗るのは**編集後の本体そのもの**
（取り込みは body ごと保存される・§4）——だから編集は再読み込みを越えて残り、取り消しの履歴は残らない。

**列の型と単位は宣言できる**（`declareField`）。⚠ **型の宣言は実データに対して検証する**
（§1.5 と同じ規則。`number` と宣言された列に数として解けないセルが 1 つでもあれば、件数と実例を
添えて `field-type-refused`）。⚠ **単位は検証できない**——`km` と書かれた列が km である保証は
どこにも無いので、`fields[].unit` の隣に `unitStated`（`reader` か、ラスターの band なら `source`）を
持つ。**測ったことにしない。** 測定値の `type` は宣言で上書きされず、読者は
「測ると text・読者が number と宣言」を区別できる。

## 5.3 属性値による着色 — `js/map-ui.js`

取り込みは 8 色パレットの循環 1 色で描かれていた。いまは `GeoJSONUpload.style(ref, spec)` が
**列の値で塗る**——`categorical`（値ごと）と `graduated`（`quantile` / `equal`）。

- ⚠ **数かどうかを自分で判定しない**——`IntMapData` に訊く（§1.1 が「型づけの規則は 1 か所」と
  述べている。特に `"01100"` は数ではない）。訊けないセッションでは `graduated` を名前を付けて断る。
- ⚠ **欠損は色ではない。** 値の無い地物は「0 の色」ではなく**欠損の色**で描き、件数を凡例に出す。
  0 として塗れば、読者は空欄を最小値として読む。
- ⚠ **上限を超えた分を捨てない。** 色より多い分類は「その他」に畳み、**畳んだ件数を凡例が述べる**。
- ⚠ **地図と凡例は同じ snapshot**。凡例は `style()` が返したものを描くだけで、数え直さない。
- 描かれたレイヤーとデータセットは**識別子で結ぶ**（`GeoJSONUpload.link` / `find`）。綴り（title）で
  結ぶと、同じ名前の 2 ファイルで壊れる。

## 5.4 Atlas がこの層に処理を依頼する — `js/gis-atlas.js` (`window.IntMapGis.atlas`)

§5 の `data.query` は取り込んだデータセットを**読む**。⚠ **作らせる経路は #R743 まで 1 件も無かった**
——だから Atlas ができる空間解析は、誰かが既にアプリの機能として作ったものだけだった。

**能力は 2 つで、op ごとには 1 つも無い。**

| 能力 | 何をするか |
|---|---|
| `data.gis` | `{"type":"gis","op":OP,"inputs":[REF,…],"params":{…}}` を走らせ、**登録されたデータセットの id** を返す |
| `map.drawDataset` | `{"type":"gisDraw","dataset":REF}` — 出来たものを地図に描く |

⚠ **目録は `ops()` そのもので、写しではない。** op を `DECL` に 1 本足せば、その日のうちに画面にも
Atlas にも出る。Atlas 側に op の一覧を書くことは、#R732 が画面で測った欠陥（`ORDER` が 4・`DECL` が 9）
を別の場所で作ることである。⚠ **ひとつだけ導出できない一覧がある**——読者（模型）が読む案内文は
GIS のチャンクが読み込まれる前に送られるので `DECL` に訊けない。だから**検査が案内文を `DECL` と
突き合わせる**（`tests/r743-gis-atlas-surface-checks` ⑨）。名指しするのは #R733 の実測が理由で、
**渡されていることを知らされていない能力は使われない**（模型は 8 手すべてを検索に使った）。

**入力**は登録済みの id・題名・`layer:<id>`（地図のレイヤー）。⚠ **レイヤーを入口にしていないと
Atlas は鎖を始められない**——何も取り込んでいないセッションは、空の台帳と、データで埋まった地図を
持っている。格子の枠（`sample`）は**述べさせる**——ここで決めた窓と解像度は、誰も頼んでいない測定に
なる。**解決できない参照は、何が在るかを添えて断る。**

⚠ **計算と描画が別の能力なのは観測器のため**（#R736/#R737）。「訊かれたときだけ描く」ものが
「地図に書き込む」と宣言すると、動かなかった地図を観測器が測って**正しい答えを `not_rendered` と
呼ぶ**——実測で 21 手・10 分がその再試行に費やされた。パネルでも「作る」と「地図に描く」は
別のボタンである。

## 5.5 描画と分析が同じ供給元を読む — `js/gis-sources.js` (`window.IntMapGisSources`)

§5.1 の橋は**描画器が持っているものを分析へ取り出す**ものだった。ベクタはレンダラの GeoJSON ソース、
ラスターは `sampleAt()` に 1 画素ずつ。⚠ **全世界の矩形を渡したことと、元データを全件取得したことは
同義ではない**——解析の完全性は、そのレイヤーが**何を保持・取得しているか**に依存するのに、
橋はそれを述べていなかった。だから分析の結果が「世界について」なのか「いま画面に載っているものに
ついて」なのかを、読者も Atlas も区別できなかった。

`list()` / `features(id, req)` / `region(id, box)` / `acquire(id, req)` / `declare(id, decl)`。
⚠ **一覧は手で並べず数え上げる**（§5.1 と同じ規則）。

**取得はすべて `coverage` を伴う**（省略できない）:

```
{ completeness: 'all' | 'partial' | 'sample',
  reason, requested, served, count, asOf, resolution }
```

⚠ **`all` は推測からは届かない。** レンダラが 400 機を持っていることは、外から見て「世界の一覧」とも
「いまの視野ぶんを取ってきた」とも区別がつかない。だから測れないものは `partial` と**理由**を述べる
——「知らない」を「全部だ」の代わりにしない（[[intmap-coverage-counted-is-not-coverage-seen]] が
件数について記録しているのと同じ形）。`all` を出せるのは**供給元自身の宣言**だけで、今日それを
述べているのは**取り込んだファイル**（`js/map-ui.js`）——ファイルが復号した地物が全部そこに在り、
それは視野ではないから、構造として完全だと言える唯一の供給元である。

⚠ **レイヤーがオフでも、答えるものからは読む。** 旧 `toRaster()` は「オフ ⇒ 値が無い」を全行に
ついての事実として断っていた。いまは 1 点試して、数が返れば読み、返らなければ
`layer-not-visible` で断る（黙って空を返さない）。

## 6. 何をやらないか（現時点）

- **Worker が無い。** 重い処理は**中止でき、進捗を述べ、フレームごとに譲る**（§2.6）が、走るのは
  メインスレッドである。⚠ ここで足りないのは**並列性**であって応答性ではない。
- **分割読み込みが無い。** `features()` は**保持している配列を返す**（扉が 1 つ、という意味であって
  ストリーミングではない）。ラスターの `read(i)` も band 全体を返す。⇒ 取り込めるデータの大きさは、
  いまも「メモリに載るか」で決まる。
- **格子の再標本化は選べる方法が 2 つだけ。** nearest と bilinear（§1.4b）。cubic・平均・最頻値は
  無い。⚠ 一覧は `IntMapGisRaster.sampleMethods()` を母集合にしているので、カーネルに足された日に
  ひとりでに現れる。
- **解析用の座標系を選べない。** 格子は §1.4b で 4326 へ**持ってこられる**ようになったが、
  データセットの `crs` は常に `EPSG:4326` で、面積も距離も測地の km 固定（§2.4）。読者が
  「この解析はこの投影で」と述べる欄は無い。
- **GeoTIFF の overviews を読まない**（数えるだけ）。BigTIFF・JPEG-in-TIFF・1/4 bit も読まない
  （どれも名前を付けて断る。§1.4a）。
- **供給元の `completeness` は、今日どの内蔵レイヤーでも `all` にならない**（§5.5）。
  `declare()` を呼んでいるのは取り込んだファイルだけで、世界の一覧を丸ごと持っている module
  （heritage・volcanoes など）は自分でそう述べていない。⚠ これはこの層の欠陥ではなく、
  **アプリの真の状態が初めて述べられた結果**である。
- **`js/gis-geopackage.js` は読むだけ**で、書き込みも tiles も曲線幾何も扱わない（どれも名前を付けて
  断る）。WAL の残ったファイルも、サイドカーが手元に無いので断る。
