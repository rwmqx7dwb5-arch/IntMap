## 0. なぜこの層があるのか

これより前、IntMap には「データセット」という語が 2 つの無関係なものを指していた。

- **地図に載せたもの** — 落としたファイルは `ugj-<n>` という描画ソースと 3 枚のレイヤーになり、
  あとに残るのは取り込み一覧の 1 行（名前・色・ソース id）だった。**地物は描画器の中にあり、属性は
  文字列で、その取り込みに何かを訊く経路は 1 本も無かった。**
- **分析できるもの** — `js/atlas-query.js` の 5 つの内蔵表。`from` はその 5 つの名前しか取らず、
  **利用者が持ち込んだものを 6 つ目にする経路が存在しなかった。**

つまり「CSV を落としたら地図に出る」と「その CSV を他のデータと同じように分析できる」は別々の
仕組みで、後者に入口が無かった。この層は**その 1 点**を埋めるものである。

## 1. データセットの契約 — `js/gis-datasets.js` (`window.IntMapData`)

```
{ id, title, kind:'vector', geometryType, withGeometry, crs, sourceCrs, fields[], count, time,
  features(), provenance, createdAt, stale }
```

**#R735 以降、payload は 2 種類ある。** `kind:'raster'` は地物ではなく**数値の格子**を持ち、
それ以外（id・provenance・lineage・`stale`）は全部同じ機械である（§1.4）。

| 欄 | 意味 |
|---|---|
| `geometryType` | `Point` / `LineString` / `Polygon`（`Multi*` はその単数に畳む）／全部が一致しなければ `Mixed`／地物ゼロなら `null` |
| `crs` | **常に `EPSG:4326`**。下流（描画・内包判定・切り取り）が全部 lng/lat 度を前提にしているので、各自の暗黙の前提ではなく**値として**述べる |
| `sourceCrs` | **届いた座標系**。GeoJSON（RFC 7946 §4）・KML・GPX は仕様が WGS 84 を固定するので `EPSG:4326`、区切りテキストは `null`。⚠ `null` は「名乗っていない」であって「4326 だった」ではない。**`crs` と違う値なら「その座標系で届き、取り込みのときに 4326 へ変換した」**（§1.3） |
| `fields[]` | 列ごとに `{name, type, empty, filled, total}`（数値列は `min`/`max` も。先頭ゼロで数から外れたセルの数は `padded`）。読者が宣言すれば `typeStated` / `typeRefused` / `unit` / `unitStated` が並ぶ（§5.2） |
| `withGeometry` | **幾何を持つ地物の件数**（測定値。ラスターでは `null`）。⚠ `geometryType` の `null` は「表」「空」「格子」の 3 つを同じ答えにするので、その 3 つを分けるのはこの欄である。`count > 0` かつ `withGeometry === 0` ＝ **座標を持たない統計表** |
| `time` | **時刻の宣言、または `null`**（§1.5）。⚠ `null` は「時刻の宣言が無い」であって「時刻が無い」ではない |
| `timeRefused` | 宣言が実データで**成り立たなかった**理由（`{why, detail}`）。宣言を写して持つのではなく**検証して**持つので、この欄が「誰も述べていないことを述べてしまう」ことを防ぐ |
| `features()` | **関数**。一覧・連鎖・クエリの橋はどれも metadata しか要らないので、地物の実体化はこの 1 つの扉だけ |
| `provenance` | 札ではなく**レシピ**（§3） |
| `stale` | `null`＝「この地物はこのレコードのレシピが出すもの」。`{why, since}`＝**上流の再計算が失敗したので、前の引数での答えが残っている**（§4.1）。レコードは常に `null` で生まれる——作り直しはフラグを消すのではなく**新しいレコードを作る**ので、消し忘れという状態が存在しない |

### 1.1 列の型は列名ではなく値で決める

⚠ **先頭ゼロのセルは符号であって数ではない（#R735）。** 十進の記法に無意味な先頭ゼロは無いので、
それが付いているセルは**識別子を綴ったもの**である。この規則が無かった間、`"01100"` は `number` と
判定され、`js/gis-ops.js` の比較は全部 `asNumber` を通るので **`"01100" == "1100"` が真**だった
——統計を隣の自治体に結合し、大きさを持たない列に min/max を印字する。
⚠ **規則は記法であって、列名の一覧ではない**（`/code|id|_cd$/` は
`.agents/rules/no-ad-hoc-hardcoding.md` が禁じる形で、次の国の綴りを取り落とす）。
`0`・`0.5`・`-0.25`・`0e3` は数のまま（そのゼロは有意）、`01`・`00`・`+007` は数ではない。
外した件数は `fields[].padded` に載るので、読者は「番号なのに計算できない」理由を見られる。

- **`number`** — 空でない値が**全部**「セル全体が数」として解けるとき。`12 km` は text（`parseFloat`
  が 12 と言い、その列は合計できるふりを始める）。
- **`date`** — 空でない値が全部**年から始まる ISO-8601 系**で解けるとき。⚠ `Date.parse` だけに任せない
  ——`03/04/2020` は**読む人によって違う日**になり、意味が読者で変わる列は text より悪い。
- **`text`** — それ以外。
- **空セルは型を決めない。** 900 個の数と 3 個の空白は「空白 3 個の数値列」で、そこで text と言うと
  列全体から算術を取り上げる。空セル数は判定の隣に持つ。
- **同点は `number` が勝つ**（`2020` は両方に解ける）。裸の年は数として比較・集計でき、時間軸として
  使いたい読者も何も失わない。

⚠ **列名の一覧（`lat`・`pop`・`年` …）で決めない。** それは
[`../.agents/rules/no-ad-hoc-hardcoding.md`](../.agents/rules/no-ad-hoc-hardcoding.md) が禁じる
「事例ごとの記述」で、書いた人が思いついた列については当たり、**次に来る列を黙って誤判定する**。

⚠ **この判定は 1 か所にしかない。** `js/gis-ops.js` は自分の出力の列を `IntMapData.typeColumn` で
型づける。2 つ持つと、**パネルでは比較できて問い合わせではできない列**という形で必ず離れる。

### 1.2 列の集合は全地物の和集合

先頭の地物の鍵ではない。GeoJSON は地物ごとに違う属性を持てるので、`features[0]` だけを読むと
**途中から始まる列が全部落ちる**。

### 1.3 座標変換 — `js/gis-crs.js` (`window.IntMapGisCrs`)

内部形式は経度・緯度に統一したままで、**変わったのは入口**。取り込みは
① GeoJSON の `crs` メンバ（`urn:ogc:def:crs:EPSG::NNNN` / `EPSG:NNNN` / 旧 `{"type":"EPSG",…}`。
`OGC:1.3:CRS84` は経度が先の WGS 84 なので 4326 と同じ）を読み、
② 4326 でなければ **proj4 で実際に変換**し、`sourceCrs` に**元のコード**を残す。

⚠ **EPSG の一覧を持たない。** 使える定義の出どころは 3 つの**規則**だけ:
proj4 自身が知るもの（4326 / 3857 / WGS84）、**UTM の算術**（`EPSG:326NN`＝北半球 zone NN・
`327NN`＝南半球。zone は 1..60）、読者が `define()` で渡した WKT または proj 文字列（`.prj` の中身）。
⚠ **③ には呼び出し元が 2 ラウンド無かった**（規則は在り、`.prj` を渡せる経路が無かった）。いまは
Shapefile の `.prj` がそれで、`js/geo-import.js` が変換の**前に**登録する——だから
`EPSG:6675` のような、内蔵の表が知らない国の座標系が**ファイル自身の定義**で読める。
GeoPackage の `gpkg_spatial_ref_sys` も同じ形の WKT を持つ。⚠ AUTHORITY を述べない `.prj` は
`PRJ:<基底名>` という**定義そのものの名前**で登録する——EPSG 番号を発明しない。
それ以外は **`crs-unknown` で断る**——近い定義を当てない。

⚠ **出力は常に `[lng, lat]`**。変換後に |緯度| > 90 なら `crs-axis-suspect` で断る。軸順序を
取り違えた変換は例外を出さず、地物を世界の裏側に静かに置くので、**測って拒む**。

⚠ **「述べていない」と「度ではない」は別**。座標が度の範囲に収まらないファイル（区切りテキストは
座標系を名乗らない）は `looksProjected()` が**測り**、`crs-not-stated-and-not-degrees` で取り込みを
断る。⚠ この判定は `IntMapGeodesy.sanitizeFeatures` **より前**に置く——あれは緯度を ±89.9999 に
**クランプ**するので、後ろに置くと投影座標が「北極に載ったもっともらしい形」になって証拠が消える。

変換できないファイルは `crs-unsupported` で**取り込みごと断る**。⚠ **黙って 4326 として置かない。**

### 1.4 数値ラスター — `kind:'raster'` と `js/gis-raster.js` (`window.IntMapGisRaster`)

```
{ id, title, kind:'raster', crs:'EPSG:4326', sourceCrs, width, height,
  grid:{ west, north, pixelLng, pixelLat }, bands:[{name,unit,nodata}], time,
  read(bandIndex), raster(), provenance, createdAt, stale }
```

**なぜ在るのか。** アプリの中には数値グリッドを読む経路が既に幾つもある（降水・気温・土地被覆・DEM）が、
どれも専用の読み手の中にあって、**処理器を向けられる相手ではなかった**。だから「この区域の人口」
「区域内の標高分布」「土地被覆ごとの面積」は 1 つずつ別の機能として作るしかなく、どれも次の分析へ
繋がらなかった。

- **行は北から南へ進む**（row 0 の中心緯度は `north − pixelLat/2`）。`pixelLng`・`pixelLat` は**常に正**。
- `read(bandIndex)` は長さ `width*height` の数値配列（row-major）。**`raster()` が扉**で、`features()` と
  同じ理由でそこに在る——4,000 × 4,000 は倍精度で 128 MB あり、一覧や連鎖や保存は metadata しか要らない。
- **`NaN` は常に欠損**で、バンドごとの `nodata` もそれとして扱う。⚠ 欠損を 0 で埋めない（0 は海面の標高で、
  雨量ゼロである）。
- **格子が格子でないものは登録の時点で拒む**（幅が整数でない・画素の大きさが 0 か負・`read` が関数でない）。
  そこを通してしまうと、以降の標本は全部**黙って間違う**。
- **バンドはその格子の列である。** `fields[]` にバンドが並ぶので、パネルの「どの列で」がそのまま
  「どのバンドで」になる（一つの操作、二つの実装を作らない）。

計器（`js/gis-raster.js`）が持つのは格子の算術だけ:
**地点値**（`nearest` / `bilinear`。⚠ **欠損を混ぜない**——隅のどれかが欠けたら nearest に落ち `partial`
を添える。実測の理由は `js/map-readout.js` の注記＝void 1 つと実測 3 つの混合が −7,800 m を出した）／
**区域内集計**（画素の所属は**中心の内外**で決め、平均は**面積重み付き**＝緯度で画素の面積が変わるので
単純平均は高緯度を過大に重く数える。`areaKm2` と `valueAreaKm2` を**両方**返すので「一部だけ」が見える）／
**値ごとの面積**（分類の格子だけ。測定値は `values-not-integer` で拒み、勝手に丸めない）／
**条件による抽出**（比較の正本は §2 の `evalCondition`）／**同じ格子同士の差分**
（⚠ 格子が違えば `grid-mismatch` で拒む——再標本化は**選択**であって、差分の中で黙って行えば全画素が
誰も名づけていない補間の合成になる）。

⚠ **既存の数値レイヤーは `fromSampler()` / `IntMapGisLayers.toRaster()` でこの契約に入る。** 1 画素 1 await
なので**中止でき、進捗を報告する**（§2.6）。焼いた格子は「レイヤーの標本」であることを provenance が述べる。

### 1.4a 格子の入口 — GeoTIFF / COG (`js/gis-geotiff.js`)

**#R749 まで、格子を持ち込む汎用の入口は 1 つも無かった。** アプリの中に数値グリッドを読む経路は
幾つもあったが（降水・気温・土地被覆・DEM）、どれも専用の読み手の中にあり、読者が自分のファイルを
落とす先は無かった。⚠ **依存は足していない**——TIFF 6.0 を自前で読む（前例は
`js/gis-geopackage.js` が依存を足さずに SQLite を読むこと）。

読むもの: II/MM 両バイト順・strip と tile（**COG は tile の TIFF**）・無圧縮／LZW／Deflate／
PackBits・predictor 1 と 2・uint / int / float × 8〜64 bit・ModelTiepoint+PixelScale と
ModelTransformation の両方・GeoKey の CRS・`GDAL_NODATA`・複数 IFD（**フル解像度を読み、
overviews は数だけ報告する**）。

⚠ **扱えないものは名前を付けて断る**（`refusals()` がその一覧を持つ）。BigTIFF・JPEG-in-TIFF・
登録名つきのその他の圧縮・8 の倍数でない bit 深度・PlanarConfiguration 2・**地理参照の無い TIFF**。
最後のものは他と種類が違う——**どこにあるかを述べていない画像は地図ではなく絵**で、どこかに置けば
それは誰も述べていない主張になる。

⚠ **`read(i)` は扉である**（§1.4 と同じ理由）。開いただけでは画素を 1 つも展開しない。

### 1.4b 格子を合わせる — `js/gis-warp.js` (`window.IntMapGisWarp`)

GDAL の warp が担っている役——**座標系・解像度・範囲・再標本化・NoData を 1 つの層で扱う**。
`to4326(grid,{method})` / `resample(grid,target,{method})` / `align(a,b,{rule})` / `methods()`。

- ⚠ **`method` に既定が無い。** 省略は `resample-method-not-stated` で断る。黙って選んだ補間は、
  §1.4 が差分について拒んでいるものと同じ——**誰も名づけていない補間の合成**である。
- ⚠ **欠損の規則を写さない。** 値はすべて `IntMapGisRaster.sample` が出す（隅が欠けたら nearest へ
  落ちて `partial` を数える、という 1 つの規則を 2 か所に持たない）。
- ⚠ **分類の格子を bilinear で補間しない。**「3」と「5」の中間の「4」は別の分類であって中間ではない。
  ただし**整数だから分類だとは推測しない**——バンドが `categorical` を述べているときだけ断る。
- **逆写像で走る**（出力画素の中心 → 4326 → 入力 CRS → 入力の画素）。順写像は穴を作る。
- **出力範囲は周を 1 画素刻みで歩いて求める**——投影された辺は度では曲線なので、四隅では足りない。
- `align` の**規則は呼び出し元が述べる**（`finer` / `coarser` / `first`）。交差が空なら `grids-disjoint`。

⇒ §1.4 の `grid-mismatch` は**今も正しい拒否**だが、行き先ができた: *「`js/gis-warp.js` で明示的に
合わせてから、もう一度」*。

### 1.5 時刻 — 宣言し、検証する

```
null                                          何も宣言されていない（≠ 時刻が無い）
{ kind:'instant',  field }                     地物ごとに 1 瞬
{ kind:'interval', startField, endField }      期間（どちらの端も空＝開いた端でよい）
{ kind:'track',    timesField, elevationField } 位置 1 つごとに 1 時刻（と標高）
{ kind:'constant', start, end }                データセット全体が 1 瞬／1 期間（レイヤーの有効時刻・
                                               ラスターの時期）
```

⚠ **宣言は実データに対して検証され、成り立たないものは名前で拒まれる**（`timeRefused`）。
呼び出し側が言ったことを写して持つのは、`.agents/rules/historical-verification.md` が禁じる形＝
**誰も述べていない主張が欄に入っている**状態である。

⚠ **`track` は取り分け信用できない。** 並行配列が時間軸であるのは**その長さが位置の数と等しい間だけ**で、
IntMap にはまさにそれを壊す経路がある——`js/geodesy.js` の `sanitizeFeatures` は直せない位置を**落とし**、
第 3 の座標成分を**畳む**（だから標高は座標の中ではなく**隣に**運ぶ）。位置 1 つが落ちれば以降の時刻が
全部 1 つずれる。だから長さは**地物ごとに測り**、1 件でも合わなければ宣言全体を拒む。

⚠ **暦にある日だけを受ける**（#R774）。`asDate` は形だけを見て `Date.parse` に渡していたので、
`2026-02-30` が **2026-03-02** に、平年の `2026-02-29` が **3-01** に、`2026-04-31` が **5-01** に
黙って化けていた——述べられた年月日を UTC で組み直し、組み直した日が同じ年月日を述べるときだけ受ける
（月ごとの日数表を書かない。うるう年の規則は暦の側が既に持っている）。時刻・タイムゾーンが付いていても
判定するのは**述べられた暦日**で、瞬間そのものはこれまでどおりゾーンを反映する。

⚠ **`constant` は `start ≤ end` が要る**（#R774）。終わりが始まりより前の期間は期間ではないので
`time-constant-reversed` で拒む（両端が同じ瞬間は長さ 0 の期間で、拒まない）。`interval` は行ごとに
数え、逆転した行は `readable` に数えず `reversed` に載る——全行が逆転していれば既存の
「1 行も読めない宣言は拒む」規則がそのまま `time-unreadable` を返す。

⚠ **裸の年はその年 1 年**である。`asDate` は `1889` を ISO の年接頭辞として受け、
`1889-01-01T00:00:00Z`＝**1 ミリ秒**を答える——年の列に対して「1889 年」の窓がほとんど何も掴まなくなる。
だから年の規則を**先に**訊く。⚠ 年の作り方は `Date.UTC` ではない（100 未満の年が 1900+y になる・#R602）。

## 2. 処理 — `js/gis-ops.js` (`window.IntMapGisOps`)

**この層の存在理由は「出力が入力と同じ形で登録される」こと。**「5km バッファ」→「その中だけ」→
「区域ごとに数える」は、作り込んだ 1 本のパイプラインではなく**登録 3 回**である。

### 2.1 宣言を読むのは UI の仕事、持つのは op の仕事

`ops()` が返す宣言（`inputs` / `accepts` / `output` / `params[]`）**だけ**を読んで画面を作る。
`params[].input` が「その列名をどの入力から選ぶか」を、`requiredWhen` が条件つき必須を、
`needsGeodesy` が「`window.IntMapGeodesy` が無ければ走れない」ことを、`needsGeometry` が
「`window.IntMapGisGeometry`（§2.5）が要る」ことを**データとして**述べる。
⚠ UI 側に「buffer は半径を聞く」という手書きの一覧を作らない（#R725 と同じ方針）。

⚠ **一覧は `DECL` 1 つだけ。** `ops()` はかつて `ORDER = ['filter','buffer','clip','aggregate']` を
map していて、**`DECL` に足して `ORDER` に足し忘れた op は run() に答えるのに画面に出なかった**
——上の段落が禁じている手書きの一覧が、その段落の真下にあった。いまは `Object.keys(DECL)` で、
`run()` の dispatch も **op id を鍵にした表**（以前の if 連鎖は無条件の `else` で終わっていたので、

⚠ **`kinds` が入力ごとの中身（vector / raster）を宣言し、既定は `vector`。** `accepts` が訊くのは
geometry で、格子はそれを持たない——この鍵が無ければ、**格子より前に書かれた 9 つの op が
`geometryType:null` の格子を受け取り**、`Mixed` として拒むか（`any` の枠では）在りもしない
`features()` を歩くかのどちらかだった。宣言と既定があるので、**9 つ全部が一度に**
`input-kind` で名前を付けて拒む。

⚠ **`zonal` の `classes` は分類の格子だけ。** 測定値の格子は `values-not-integer` で拒む——丸めれば
誰も定義していない区分を作ってしまう。行には `_gridAreaKm2` と `_valueAreaKm2` が付き、
**その差が答えの被覆**である（件数で報告すると「一部だけ」が原理的に見えない）。

⚠ **`join` が結ぶのは識別子であって数ではない（#R738）。** この層の他の比較は全部 `asNumber` を
通る——量を比べているからである。結合が比べるのは**符号**で、両者は**まさに問題になるセルで別の
答えを返す**: `"01100"`（札幌市中央区）と `"1100"` は 1 つの数で 2 つの場所である。だから比較は
セルの文字列（前後の空白を落としたもの）で、**一致した件数・しなかった件数・一致しなかった鍵の実例**を
**答えとして返す**——同じ市区町村コードを違う綴りで書いた 2 ファイルは、構造的には完璧で情報の無い
結合を作り、それを読者が見る方法は「何行が相手を見つけたか」を告げられることしか無い。
⚠ 同じ鍵が右側に 2 度あれば**拒む**（`duplicates:'first'` と述べれば通る）。黙って 1 つ選ぶことも、
黙って行を増やすことも、**読者が見ていないデータで行数が決まる**ことを意味する。
⚠ 列名がぶつかれば拒む（`prefix` が読者の答え）。上書きは画面に出ているデータを壊し、ここで改名すれば
**誰も知らない名前**を発明することになる。

⚠ **`compute` の式は解釈されるのであって評価されない（#R738）。** `js/gis-expr.js` は自前の
トークナイザと再帰下降パーサで、**`eval` も `new Function` も使わない**。空は 0 ではなく**伝播**し
（`coalesce(x,0)` は読者が述べる）、先頭ゼロのセルは算術に入らず（規則は `IntMapData` に訊く。
§1.1）、0 除算は `null`、`'a' + 1` は連結ではなく `expr-type`。⚠ **式が名指す列はデータセットに
対して検査される**——`filter` の条件と同じ規則で、綴り違いは**null の列**ではなく拒否になる。

⚠ **`accepts:'any'` は「どんな形でも」であって「形が無くてもよい」ではない（#R738）。**
統計表は `geometry:null` の行として取り込まれ、`geometryType` はそれでも `null`・空の
データセットでも `null`・格子でも `null` ——1 つの欄が分けられない 3 つである。だから
`js/gis-datasets.js` が `withGeometry` を**測り**、**幾何カーネルか測地を要する op** は
`input-has-no-geometry` で拒む。そうでなければ buffer は全行を歩き、座標を 1 つも見つけず、
**空の面のレイヤーを登録する**——成功した処理・0 件の答え・入力に場所が無かったことを述べるものが
どこにも無い状態である。⚠ `filter`・`timeWindow`・`join`・`compute` はどちらも宣言しないので
**表の上で動き続ける**。それが表を取り込める理由そのものである。

⚠ **`timeWindow` が読むのはデータセットの宣言（§1.5）であって、ここで打ったの列名ではない。**
だから出来事の表・治世の表・GPS の軌跡に同じ op が効き、軸を宣言していないデータセットは
`time-not-declared` で拒まれる（推測で絞り込まない）。⚠ **軌跡に対しては「選ぶ」ではなく「切る」**
——「17 時台に通った区間」は線の一部であって、4,000 点のうち 1 点が入っているからといって
乗車まるごとを返すのは、誰も訊いていない問いへの答えである。**並行配列も一緒に切る**（切らなければ、
以降の時刻が全部ずれた軌跡になる——それは §1.5 が測っている不変条件そのもの）。

⚠ `relate` の `nearer-than` は**形そのものからの最短測地距離**で、測った値を `_distanceKm` に書く。
⚠ `aggregate` は「面に含まれる**点**」ではなく「その面に**重なるもの**」を数える。線が境界をまたげば
**両方の面に数えられる**——それが「重なる」の意味であって、区画分割は別の問いである（だから行に
`_areaKm2` が付く）。

持つ。`js/geo-import.js` と同じ作法——decoder に UI の言語を持たせない。

`js/gis-panel.js` が**文を持つコードの集合**と一致することを測る（`tests/r576-checks.test.mjs` ⑩ と

### 2.3 本当に拒む——もっともらしいものを描かない

いま断るのは、**その op がその入力では意味を持たないとき**だけである。

- **内向きバッファ（負の半径）は、内側を持つものにしか無い。** 点や線には縮める内側が無いので
  `inward-buffer-needs-area` で名指して断る。0 に丸めない。
- **重ね合わせの相手に面が無い**なら `no-overlay-polygons`、切り抜きの窓に面が無いなら
  `no-clip-polygons`。
- **古い入力（`stale`）は `input-stale` で断る**（§4.1）。消費すると、古さが「現行」と名乗る新しい
  レコードの中へ入ってしまう——**そこが、古さが見えなくなる唯一の場所**である。
- **幾何カーネルが届かなかったセッションでは `geometry-unavailable`。**
  ⚠ 「訊けなかった」と「0 件だった」を同じ答えにしない。

⚠ **かつてここにあった 3 つの拒否は、実装に置き換わった。** `buffer-needs-points`（線・面の
バッファが無かった）・`clip-window-not-convex`（S-H は凸窓でしか正しくない）・
`clip-window-crosses-antimeridian`（継ぎ目をどちら側と読むか推測できなかった）は、どれも
**engine が無かったときの正直な断り**であって、いまはどれも仕事である（§2.5）。
検査もそう移した：`tests/r729-gis-core-checks.test.mjs` ③ からこの 3 つが消え、
`tests/r732-gis-geometry-crs-checks.test.mjs` ②③④ が**同じ入力が正しく計算されること**を測る。
**拒否が実装になった回に検査を消すだけにすると、それは見るのをやめた回になる。**

### 2.4 どの面で計算しているか（誤差はここから来る）

- **ブール演算も内包判定も平面** — 生の lng/lat 度（plate carrée）。
  - **日付変更線**: 隣り合う頂点の経度差が 180° を超えたら、それは継ぎ目である（この地図が読む
    どのデータにも、半周ぶんの長さを持つ**辺**は無い）。だから環は**ほどき**（unwrap）、両辺を
    **同じ 360° 窓へ揃え**、その平面で計算し、`IntMapGeodesy._splitPolyToWindows` で
    `[-180, 180]` に**戻す**——`diskFillPolys` が出す円盤が通っているのと同じ分割器。
  - **いまも断る唯一のもの**: ほどいたあと経度幅が 360° 以上になる環（極冠・全球環）。
    それは**どの円筒平面でも単純な環になれない**ので、断っているのはデータではなく平面のほうである。
- **面積は平面ではない** — `areaKm2` は球面過剰（Chamberlain–Duquette）、外側 ring を足し穴を引く。
  半径は `IntMapGeodesy._R_EARTH_KM`（アプリが持つ唯一の半径）。⚠ 度の平面で面積を測ると cos φ 分
  ——**緯度 60° で半分**——ずれる。そこはヨーロッパの大半である。
  - ⚠⚠⚠ **(#R774) 面積も、継ぎ目を跨いだ環は巻き直してから測る。** 上の内包判定は `alignTo` で
    ほどいてから測るのに、面積は辺を**書かれたまま**読んでいた。**実測**: 179°E→179°W × 0°–1° の
    未分割の帯が **4,426,211 km²**（同じ緯度の幅 2° の帯は 24,727 km²。**179 倍**）で、同じ多角形を
    `pointInPolygon` は幅 2° の帯として読んでいた——**ひとつの面に 2 つの読み方があり、読者はどちらにも
    出会えた**。⚠ `js/gis-crs.js` の `areaOn`（平面路）は同じ環を `plane-seam-crossed` で**拒んでいる**。
    答えていたのは測地路だけ。
  - ⚠ **極の読み方は 1 バイトも動いていない。** 辺を「短い方」へ正規化すると
    `IntMapGeodesy.diskFillPolys` が 89.9999° 線に沿って書く **360° の閉じ辺**が消え、面積は補集合に
    なる（実測 89°N の 500 km buffer が 785,022 km² ではなく 509,280,824 km²）。⇒ **見分けるのは辺**:
    **180° を超え 360° 未満**の辺は未分割の継ぎ目で、その環だけを `js/gis-geometry.js` の
    `unwrapRing`（この app の唯一の巻き直し）に通す。ちょうど 360° の辺は全幅の帯が意図して書いた
    閉じ辺なので触らない。⚠ これは**表現についての規則**であって事例ごとの特例ではない——この地図が
    読むどのデータにも半周より長い**辺**は無い（`SEAM_STEP` が同じことを述べている）。
- **距離は測地線** — `distanceKm` は点と点は haversine、点と線分は**問い合わせ点を中心にした
  局所の等距円筒面で「どの点が最も近いか」だけを選び、距離そのものは本物の測地線で測る**。
  投影は返す数に現れない。

#### 2.4.1 ⚠⚠⚠ (#R764) 球はどこまで信用してよいのか — 推測ではなく実測

上の 3 行は**どの面で測るか**を述べており、正しい。述べていなかったのは**差の大きさ**で、
「500 km の圏はこの用途に十分か」「楕円体に替える価値はあるか」を決める材料が誰にも無かった。
⇒ `tests/r764-gis-error-domain-checks.test.mjs` が **WGS-84 楕円体上の Vincenty 逆解法**（テストの
中に別途実装した、測る対象の外にある参照）と突き合わせて掃引する。緯度 7 点 × 距離 6 点 × 方位 4 点。
**結論から言えば、球面近似の相対誤差はどこでも 0.6 % を超えない。**

| 実測（球 6371.0088 km 対 WGS-84） | 値 |
|---|---|
| 相対誤差の範囲（全掃引） | **0.007 % 〜 0.56 %** |
| 最大が出る場所 | **赤道を南北**（0.561 %。極半径がいちばん小さいところ） |
| 最小が出る場所 | 緯度 15〜30° の斜め方向（0.007 %） |
| 10 km での差 | **100 m 未満**（都市の規模なら問題にならない） |

⚠ **誤差を決めるのは「どこで・どちら向きに」であって「どれだけ長いか」ではない**——同じ緯度・
同じ方位なら 1 km でも 1,000 km でも相対誤差は 0.1 ポイント以内に収まる。⚠ **ただし 5,000 km では
崩れる**（赤道・北向きで 0.561 % → 0.378 %）。長い経路は通過する緯度を平均するので、
**その場所の誤差ではなくなる**——近似が良くなったのではなく、別の量になったということ。

⚠ **この数はこのアプリが最適化した結果ではない。** 球と楕円体という 2 つの形の差そのもので、
半径・式・単位を取り違えない限り動かない。だから検査はこれを**上限としてではなく範囲として**
測る（差が小さすぎるときも落ちる——参照が実装と同じものになった合図）。

⚠ **極は別の主題**。緯度 ±89.5° を超える対はこの掃引に入れていない（§2.4 が全球環を断る理由と同じ
ところで、別の答えが要る）。

### 2.5 幾何カーネル — `js/gis-geometry.js` (`window.IntMapGisGeometry`)

boolean 演算は **`polygon-clipping`（Martinez–Rueda の sweep line）** に訊く。**このアプリが既に
持っている依存**で、`js/world-packs.js` と `js/cesium-vector-tiles.js` が同じように動的 import して
いる。**2 つ目の boolean engine をここに書くのは「同じ判断を 2 か所に持たせる」こと**で、しかも
出来の悪いほうになる。⚠ **読み込みは遅延**——重ね合わせを 1 度も走らせない読者は sweep line を
ダウンロードしない。

**バッファはオフセット曲線ではなく Minkowski 和である。** 半径 r のバッファの定義が「その形から
r 以内の点の集合」＝「その形と半径 r の円盤の Minkowski 和」なので、そのとおりに作る:
頂点ごとに**測地円盤**（`diskFillPolys`。点バッファがずっと使ってきたもの）、辺ごとに**測地の
四辺形**（両端を方位角 ±90° に r ずらす）、全部を union する。union が自己交差を消し、円盤が継ぎ目を
丸める。⚠ `@turf/buffer` を使わないのは、turf-jsts（332 kB）に届くことと、**オフセットを平面で
計算するので緯度 60° の「5 km」が 5 km ではない**ことの 2 つ。
⚠ **内接近似であることを述べる**: `steps` 枚の円盤と四辺形は弦で接するので、境界は真のバッファの
内側に最大 r·(1−cos(π/steps))——既定の 64 で 5 km バッファなら 3 m——入る。丸めずに
`_bufferSteps` として行に書く。

#### 2.5.1 ⚠ 「答えは空だった」と「答えられなかった」は同じ null ではない（#R743）

カーネルの入口はどれも `null` を返していた。**交わらなかった 2 つの県も、クリッパが例外を投げた
ときも、環が世界を一周していたときも、同じ 1 つの `null`** で、このファイルのヘッダは
`clipper-unavailable` / `geometry-wraps-world` という**語で断ると書いていた**——その 2 つの綴りは
**リポジトリ全体でコメントの中にしか無かった**。名前で断ることになっている拒否が、名前を持って
いなかった。

読み手の側がそれをどう読んでいたか（実測・全 8 runner）: `js/gis-ops.js` は `null` を
「この行は答えに入らない」と読んで `continue` し、**`{ ok: true }` で一回り小さい答えを返して
いた**。述語 2 つはそれより悪い——`disjoint` は `!intersects` で、`intersects` は計算できないとき
`false` を返す。つまり**失敗が「この二つは離れている」と断言していた**。`contains` は
`!difference(b, a)` なので、**例外が「b は a に完全に含まれる」になった**。

いまは同じ演算に**読める形の扉**がある（`attempt`。plain な名前はその 1 行のラッパで、外から見た
挙動は 1 文字も変わらない）:

| 返り値 | 意味 |
|---|---|
| `{ ok: true, geometry: <G> }` / `{ ok: true, value: v }` | 計算できた |
| `{ ok: true, geometry: null }` | 計算できて、**答えが空だった** |
| `{ ok: false, why, detail }` | **計算できなかった**。`why` は `clipper-unavailable` / `clipper-failed` / `geometry-wraps-world` / `geodesy-unavailable` / `bad-radius` / `inward-buffer-needs-area` / `missing-geometry` / `no-comparable-parts` |

`js/gis-ops.js` 側の規則は 2 つで、**op ごとではなく 1 か所**にある（`makeGeoLedger` /
`withGeoStats`）:

- **一部が計算できなかった実行は、その件数と最初の理由を `stats` で述べる**（`geometryFailed` /
  `geometryWhy`）。`js/gis-panel.js` は op が何を測ったかを知らずに `stats` を印字するので、
  足した日から 9 言語すべての読者に届く。
- **何も計算できなかった実行は `geometry-failed` で拒む。**「0 件でした」と
  「0 件しか計算できませんでした」は読者に区別できず、**前者だけが読者のデータについての答え**である。

線の切り抜きだけは sweep line の仕事ではない（面しか取らない）。各線分を**窓の全環との交点で切り**、
**各片の中点が内側か**で採否を決める——凹んだ窓でも穴があっても正しい唯一の判定で、連続する交点の
あいだは丸ごと内か丸ごと外だから成り立つ。---

#### 2.5.2 ⚠ `union` は和集合であって、対ごとの結合ではない（#R743）

`union` は重ね合わせのループの 1 分岐で、**そのループは対のループだった**。B の窓のうち箱が
重なるものを候補源に訊き、対ごとに `GG.union([a, b])` を 1 行として出していた。ここから 2 つが
出荷されていた:

- **離れている入力では答えが空になる。** 触れていない 2 つの四角は対を作らないので、ループは
  1 行も出さず、op は**どちらの入力も現れないデータセット**を `ok:true` で返した。
- **重なっている入力では面積が壊れる。** 対ごとに a 全体と b 全体を出すので、同じ土地が対の数だけ
  数えられ、`_areaKm2` の総和は地球を何個も超えた。

和集合には**3 種類の部分**があり、どちらの入力のどの点もちょうど 1 つに属する:
**a ∩ b**（両方の表を持つ）・**a − B**（A の表）・**b − A**（B の表）。**離れている入力は特別扱いでは
なく、1 つ目が空の実行にすぎない**——これが「事例ではなく、その事例を生んだ構造を直す」の中身である。
行は `_overlaySide`（`both` / `a` / `b`）で自分がどれかを述べる。2 つのファイルから来た行が混ざった
表がそれを言わないなら読めないし、**列からは復元できない**（b − A の行は A の列が無く、それは空欄と
同じ見た目である）。

#### 2.5.3 ⚠ ふるいの余白は km で渡す——「度」にした瞬間に緯度で壊れる（#R743）

`nearer-than` は候補を箱で絞る。その余白は**呼び出し側が km を度に直して**渡していて、箱の判定は
その 1 つの数を**両方の軸**に当てていた。しかもそれを正しいと述べる註が付いていた——
「経度 1 度は緯度 1 度より短いので、緯度の度を両軸に使えば経度方向は過大に見積もる」。

⚠ **この文は逆で、ふるいは内側に誤っていた。** 経度 1 度が km で短いことは、d km を覆うのに
**より多くの度が要る**理由である。北緯 60° では経度 1 度は 55.66 km なので、80 km は**経度 1.437°・
緯度 0.719°**。両軸に渡されていたのは緯度のほうなので、**60°N で経度 1 度離れた 2 点（55.66 km、
80 km の問い合わせに十分入る）は、距離を測る前に落ちていた**。

⚠ **索引あり／なしの比較ではこれは見えない。** `tests/r735` ⑥ は索引経路と全件走査を突き合わせる
が、**どちらも同じ 1 つの関数を同じ数で呼ぶ**。1 つの誤った規則の 2 人の読み手が一致しても、
規則を測ったことにはならない。いまは `padBoxKm` が**箱の緯度から両軸の余白を導き**、その**箱**を
索引と走査の両方に渡す（規則も継ぎ目の判定も 1 つになる）。⚠ 余白が ±180 を越えるときは
**経度全域**にする——継ぎ目で止めるのは内側の誤りだからである。

### 2.5.4 ⚠⚠⚠ (#R764) 境界の画素をどう数えるか — 判断であって、既定の変更ではない

`zonal` は「画素の中心を含む区域がその画素を取る」で採否を決める。§2.5 の註がその判断を述べ、
理由も正しい——**分類コードを按分するのは無意味**で、点で測った量を按分するのは**誰も頼んでいない
内挿**である。どちらも「**値**を割る」話で、そこは動かない。

⚠ **決まっていなかったのは「面積」のほう。**「この流域の面積」「この区の平均標高」は画素の**地面**
から出るので、区域が画素を半分に切っているとき、**丸ごと数えても 0 と数えても答えではない**。
粗い格子に対する狭い流域・海岸線・小さい行政区では、その差が答えそのものになる。

| `boundary` | 何をするか |
|---|---|
| `center` | 中心が区域の中にあれば 1、無ければ 0。**既定。出荷前と 1 ビットも変わらない** |
| `allTouched` | 区域が触れた画素は丸ごと 1 |
| `fractional` | 画素の面積のうち区域に入っている割合（0〜1） |

⚠ **重みが効くのは「地面」についての統計だけ**——`areaKm2` / `valueAreaKm2` / `sumTimesAreaKm2` /
`mean` / 区分ごとの面積。`count` と `sum` は**画素を 1 つとして数える**（「観測値の合計」において、
読み取り値の 3 分の 2 は読み取り値ではない）。⚠ **区分の面積が重みを取るのは「分類を割る」ことでは
ない**——割られるのは面積で、その面積が属する区分は画素自身のものである。

⚠ **面積の規則は注入される。**「この多角形は何 km² か」は `js/gis-ops.js` が持っており、`zonal` は
それを**渡される**（`areaOf`）。渡されなければ `fractional` は `fraction-needs-area-rule` で断る
——**黙って `center` に落ちない**（別の問いに、完全に見える数で答えることになる）。
球の綴りをこの層にもう 1 つ作らないためで、規則は `.agents/rules/no-ad-hoc-hardcoding.md` §2-3。

⚠ **内側の画素に多角形の演算は走らない。** 4 隅と中心が全部内側なら重みは 1 で、そこで打ち切る
（穴を持つ区域だけは、1 画素より小さい穴がどの隅にも当たらないので交差まで確かめる）。
⚠ **逆向きの近道は無い**——4 隅が全部外側でも、画素より細い区域が真ん中を通り抜けることがあるので、
隅だけで「外」と決めることはしない。

⚠ **使った規則は答えにも行にも載る**（`stats.boundary` と各行の `_boundary`）。行こそが後で結合・
書き出し・比較されるものなので、規則が「その場の表示」にしか無い数は、誰も検算できない。

### 2.6 対の数え上げと、止められること（#R735）

**索引 — `js/gis-index.js` (`window.IntMapGisIndex`)。** `aggregate`・`relate`・`clip`・重ね合わせはかつて
「面をループ × 相手をループ」で、外接矩形は**定数を下げるだけ**だった（ファイル自身がそう書いていた）。
一様格子が対の数え上げそのものを止める。実測 40,000 × 1,000 で **756 ms → build 79 ms + query 3 ms**。

- **セルの大きさはデータから導く**（定数で決め打ちしない）。
- ⚠ **不変条件は偽陰性ゼロ。** 落として速くする仕組みなので、落としてはならないものを落とすと
  **集計が静かに少ない数を答える**。子午線をまたぐ箱・世界を覆う箱・箱を持たないものは
  「どの問い合わせにも出す」箱に入れ、その件数は `stats().oversize` で**外から見える**
  （1 セルに全件入っている索引は、外から見ると動いている索引とまったく同じ振る舞いをする）。
- **索引が無くても答えは同じ**（遅いだけ）。`tests/r735-…` ⑥ は**索引を外した同じ run** と突き合わせる
  ——取りこぼしは「間違った答え」ではなく「少し小さい数」なので、それ以外では捕まらない。

**中止と進捗 — `run(step, {signal, onProgress})`（対で走る 5 つの op）。** ⚠ **同期のループは中止できない**、これは UI の
制約ではない。`run()` は前から `async` だったが、中の走者は 1 本の切れないループで、
40,000 面の集計はその間ずっと単一スレッドを握る——地図が止まり、進捗は描けず、
`AbortSignal` は**立てることすらできない**（立てるコードがループが手放すまで走らないので）。
その上に中止ボタンを出すのは、効果のない操作を出すことである。

- ⚠ **刻みの単位は件数ではなく時間。** 「1,000 面ごと」はあるデータでは 3 ms、別のデータでは 40 秒。
  意味があるのは**スレッドを握っていた長さ**で、60 Hz の 1 フレームがレンダラの要求である。
  だから経過ミリ秒で譲り、データセットごとに調整する数が存在しない。
- ⚠ **これは Worker ではない。** この層が呼ぶカーネル（sweep-line・レジストリ・測地）は全部この
  スレッドに居るので、ループだけ移せば呼び出しは全部置いていかれる。Worker が足すのは**並列性**で、
  これが足したのは**読者に応えるスレッド**——足りていなかったのは「止められる」の側だった（§6）。

## 3. 由来 — `provenance` は札ではなくレシピ

```
{kind:'import', file, format, readAt}        取り込み — 再実行するものが無い。バイトが起源
{kind:'op', op, inputs:[id…], params:{…}}    処理   — これだけで、もう一度走らせられる
{…, edits:{count, lastAt}}                   読者が値を編集した記録（§5.2）。種類は変わらない
```

`IntMapData.lineage(id)` が上流から順に、`dependents(id)` が「これを入力にしているもの」を返す。
**「半径を 5km から 10km に変えて再計算する」の実体はこれ**である（§4）。

### 3.1 意味は演算をまたぐ — 継承されるもの（#R759）

⚠ **たどれることは、述べていることではない。** `kind:'op'` の記録は入力の id を持っていたので
**上流までたどれば** coverage も単位も時点も読めた。だが読む者が居なかった——`js/gis-atlas.js` の
`datasetRow()` は**目の前の記録の** `provenance.coverage` を読むので、演算を 1 つ通った瞬間に
「一部しか取れていない」は planner から消えていた。**そこで、演算の出力が自分で述べる。**

| 欄 | 規則 | なぜその規則か |
|---|---|---|
| `coverage` | 述べた入力のうち**最も弱いもの**が残る（`partial` > `sample` > `all`）。`from` がどの入力の判定か、`inputs` が全入力の申告、`undeclaredInputs` が**何も述べなかった入力** | 答えは、それを作った入力より完全になれない。⚠ **沈黙は `all` ではない**ので、述べていない入力が 1 つでもあれば `completeness` を書かない（問いは開いたまま） |
| `time`（格子） | **標本が出力に入った入力**＝格子だけが投票する。1 つならそのまま・全部同じならそのまま・違えば**両方を含む区間**・1 つでも述べていなければ `null` ＋ `inputTimes` | 2020 年と 2025 年の差は 2020 年ではない。⚠ `rasterMask` の 2 番目（面）は画素を選ぶだけなので投票しない——**一覧ではなく事実**（それが格子か）で決まる |
| 列の `unit` | **名前が残った列**だけが、著者ごと引き継ぐ（`unitStated:'inherited'`・`unitStatedAt` が最初の主張者・`unitFrom` が出どころ） | 単位は値から測れない。⚠ 演算の出力は読者が宣言できない（`edit-would-contradict-recipe`）ので、運ばれなければ二度と付かない。⚠ 型は出力自身の測定のまま |

⚠⚠⚠ **(#R763) 継承は入力についてしか語っていなかった。** 上の 3 行はどれも「入力が何と述べたか」で、
**その run 自身が失ったもの**を運ぶ欄が無かった。`withGeoStats` は計算できなかった件数を数えて
`stats.geometryFailed` で返し、それを読むのは**そのターンの画面と応答だけ**で、記録には 1 バイトも
残らない。⇒ **入力が全部 `all` の buffer が 1,000 行のうち 120 行を落としても、出力は `all` を名乗った**
（系譜を遡っても見つからない——欠落は上流ではなく**ここ**で起きているから。
[[intmap-records-with-no-reader]]）。

| 欄 | 規則 |
|---|---|
| `computed` | その run が計算できなかった件数と理由（`{failed, why}`）。⚠ **取得の陳述とは別の欄**——「求めた範囲のうちどこまで取れたか」と「取れたもののうちどこまで計算できたか」は別の問いで、直し方も別 |
| `completeness` | 行を落とした run は **`partial`**。⚠ **入力の判定に上書きされない**（完全な入力から作られ、自分の一部を計算できなかった答えは、完全ではない） |
| `reason` | `op-rows-not-computed`。⚠ **語彙は `js/gis-sources.js` の `REASONS` 1 つ**——「なぜ `all` ではないか」の一覧が 2 つになってはならない |
| `from` | 入力の id ではなく **op の id**（どこで失われたのかを読者に述べる） |

⚠ **入力が 1 つも述べていなくても、run 自身の欠落は述べる。** 取り込んだファイルは coverage を持たない
ので、そこに buffer をかけて 120 行落とした記録が**何も述べない**のが同じ欠陥の後半だった。

⚠⚠⚠ **(#R763) 「どの入力が投票するか」が、代理で訊かれていた。** 上の `time` の規則は正しく書かれて
いる（「**標本が出力に入った入力**」）のに、実装は「**それは格子か**」を訊いていた。2 つは `rasterMask`
では一致する（面は格子ではない）が、**`resample` では一致しない**——2 番目の入力は**格子の形だけ**を
貸し、値を 1 つも出さない。⇒ 2020 年の a を 2025 年の b の格子へ合わせた記録が **2020–2025** を名乗り、
b が時点を述べていなければ **a の日付ごと消えた**（[[intmap-one-predicate-three-dimensions]]）。
⇒ **借りただけの入力を述べるのは、走った runner である**。それを知っているのは「`bDs.grid` だけを読む」
と決めたコードだけで、しかもそれは**この run についての陳述**であって op ごとの表ではない。

⚠⚠ **(#R763) 名前が変わった列の単位は、新しい名前へ付いていく。** `fieldStatements` は入力の単位を
**列名で**引き、`join` は**この app で唯一列名を変える op** である。⇒ `mass`（kg）は `joined_mass`
（無単位）になり、派生記録は読者の宣言を拒む（`edit-would-contradict-recipe`）ので**二度と付かなかった**。
⚠ 同じ関数の 11 行上にある衝突検査は `prefix + n` を見ていた——**片方の端では prefix が理解され、もう
片方では理解されていなかった**。改名を述べるのは改名した runner で、`fieldStatements` は渡されたものを
読むだけ（別の op の引数を推測しない）。

⚠ `provenance.coverage` は**取得の観測ではなく導出された陳述**なので `derived:true` を持つ。
Atlas へは `datasetRow()` が**投影**する（欄を書き写さない）——1 つの契約に読み手が 2 つあって、
片方しか知らない欄が蒸発する形は本番で 1 度出荷している（[[intmap-two-readers-one-field-list]]）。

### 3.2 ⚠⚠⚠ (#R774) 単位は運ばれていた。使われていなかった — `js/gis-units.js`

§3.1 は単位が**残る**ことについての節で、この層が単位を**読んだ**ことは一度も無かった。

**実測（出荷されていたビルド、どちらも `ok:true`）**:

| A | B | 返った値 | 出力単位 | 正しい答え |
|---|---|---:|---|---|
| 1,000 **m** | 1 **km** | **999** | null | 0 |
| 10 **°C** | 283.15 **K** | **−273.15** | null | 0 |

`diffResult` は綴りが一致すれば単位を継承し、違えば null にして、**引き算そのものは生の数で**やって
いた。⚠ **札を外しても数は正しくならない**——消えるのは誤りではなく証拠のほうで、
[[intmap-a-fix-that-removes-the-evidence]] が記録している形。

⇒ 規則は **`js/gis-units.js`** が 1 つだけ持ち、**op ではなく事実**（2 つの量が算術で組み合わされる）
に付く。`compare` の答えは 5 つ:

| 答え | 何が起きるか |
|---|---|
| `unstated` | 片方でも述べていなければ**何もしない**。⚠ **沈黙は不一致ではない**——この app の格子の大半は単位を述べておらず、それを拒むのは誰もしていない主張を理由にデータを断ること |
| `identical` | 綴りが同じ。表を引きもしない（この回の前とバイトで同じ） |
| `convertible` | 同じ量・違う大きさ。**格子では B を A の単位へ換算してから**引く／混ぜる |
| `incompatible` | 別の量。`unit-mismatch` で**拒む** |
| `unknown` | 綴りが違い、少なくとも片方が表に無い。⚠ **「わからない」は「同じ」ではない**ので拒む |

- **表は SI の定義値の原子だけ**で、`mm/h`・`kg/m^2`・`µg/m³`・`W/m2` は並べずに**解析**する
  （`m2`・`m²`・`m^2` は 1 つの式の 3 通りの書き方）。原子を足しても**拒否が答えに変わるだけ**で、
  答えが別の答えに変わることはない。
- **°C と °F はオフセットを持つ**ので、**読みの換算と差の換算が別**（`convert(…, {difference:true})`）。
  合成の中の `°C`（`°C/km` ＝ 気温減率）はオフセットを落とす。
- **式の中では換算しない。** `compute` と `rasterCalc` は読者が書いた算術なので、`+` と `−` は
  **同じ綴り**だけを通し、違えば `unit-mismatch` で**演算子と両方の綴りを名指して**拒む
  （評価器は換算しないので、`m` と名乗った答えを返すのは誰も述べていない主張になる）。
  読者は `a + b * 1000` と自分で書き、その主張はレシピに残る。
- **リテラルは中立**（`t − 273.15` は拒まない）。⚠ これは計測ではなく**判断**で、
  `js/gis-units.js` の頭にそう書いてある。
- `×` と `÷` は**綴りを作らない**（`km·kg` は誰も書いていない単位）。ただし `compute` は
  **導けた単位を出力の列に付ける**——#R759 が付けられなかった半分で、
  `applyInherited` は列**名**で引くのに、その列はこの瞬間まで存在しなかった。

## 4. プロジェクト保存 — `js/gis-project.js` (`window.IntMapGisProject`)

**保存する**: 取り込みは**本体ごと**（features）、処理は**段だけ**（`op`/`inputs`/`params`）。
順序は `lineage()` 展開＝**入力が必ず先**。置き場は **IndexedDB**（`intmap-gis` / `projects`）。

**保存しない**: 基図・カメラ・有効レイヤー・タブ・年。それは `js/session-tabs.js` の持ち物で、
**同じ事実を 2 か所に持たない**。

**処理の結果を保存しないのはなぜか** — レシピがあるなら再生できるし、保存すると**入力を変えた
ときに結果だけが古いまま残る**。

**`setParams(datasetId, params)`** が引数を差し替えて（渡した鍵だけ・渡さない鍵は保持）、対象と
**その下流**をトポロジ順に、**同じ id のまま**走らせ直す。循環は `cycle` で拒む。

⚠ **保存するものが #R749 で 2 つ増えた。両方とも「レシピで再生する」設計の帰結である。**

**① 利用者が宣言した列の型・単位。** `IntMapData.declarations(id)` が出し、
`restoreDeclarations(id, decls)` が戻す。取り消し履歴とは**寿命が違う**——undo はキーストロークだが、
「この列は人数か、人口密度か」「単位は m か km か」は**操作履歴ではなくデータの意味**である。
⚠ **戻すときも実データに対して検証する**（宣言したときと同じ経路を通る）。データが動いていて
成り立たなくなった宣言は**写さずに断り**、`declarationsRefused` として読者に届く——保存された
宣言を無検証で写すのは、`.agents/rules/historical-verification.md` §2 の 3 が禁じる形そのもの。

**② どの実装が計算したか。** op の段は `engine:{ops, geometry}` を持つ。⚠ **同じレシピは、実装が
違えば同じ答えではない**——#R743 が `union` と距離のふるいの**答えそのもの**を変えたので、その前に
保存されたプロジェクトは今日ひらくと違う数を持つ。読み込みは **「同じ」「違う」「測れなかった」の
3 つ**を区別して返し（`engineChanged` / `engineUnknown`）、パネルがそれを文にする。
⚠ **再計算は止めない**（読者のプロジェクトを開けなくするのは過剰）。⚠ **測れなかったものを
「同じ」に畳まない**——「読めなかった」を「同じ」の証拠に使う形は、この記録が繰り返し捕まえている。

版そのものは各カーネルが持ち（`version()` を述べる `IntMapGis*` の module）、
**バイトが動いたのに版が動いていなければ門が落ちる**（台帳 `scripts/gis-kernel-versions.mjs`、
測るのは `tests/r749-gis-raster-pipeline-checks` ⑨）。手で保つ版は最初の 1 回で腐り、
**腐った版は版が無いより悪い**——変わったエンジンについて「同じです」と述べるから。

⚠⚠⚠ **#R752: 台帳そのものが手で並べた一覧だった。** `engineNow()` は `{ops, geometry}` の 2 つを
名前で訊いており、**書かれた時点で既に誤っていた**——#R749 は `js/gis-raster.js` と `js/gis-warp.js` を
**同じ回に**作って、どちらも訊いていない。だから bilinear で再標本化した段は、今日の bilinear が
何であれ黙って再生され、`engineChanged` は何も言わなかった。`js/gis-expr.js`（`compute` が計算する
もの）も、`js/gis-index.js`（#R743 が**本物の対を捨てている**と実測したふるい）も同じ。

⇒ **いまは発見される。** カーネルとは「`version()` を述べる `IntMapGis*` の module」という**事実**で
あって、このファイルに書かれた名前ではない。比べる部分も一覧ではなく**保存側と現在側の和集合**で、
保存に在って今 measurable でないものは `unknown` になる（「もう載っていない」は本物の違いである）。
⚠ そして **GIS の module は、記録されたカーネルか、`NOT_A_KERNEL` で理由を述べた非カーネルかの
どちらかでなければならない**（`tests/r752-gis-core-checks` ⑤）。どちらでもないファイルは門が落とす
——**省略と決定の違い**がそこにある。⚠「まだ版を付けていない」は理由ではない。

### 4.1 失敗した再計算は、鎖をその場に残して印をつける

ここは 2 つとも壊れていた。**⑴ 失敗した段は既に消されていた**——id を空けるのは作り直しに必要な
手順だが、**失う**のは違う。op が断る半径を打った読者は編集中のデータセットごと失い、次の
`setParams` は `no-such-dataset` としか答えられなかった。**⑵ その下流は触られもしなかった**ので、
**古い引数での答えを持ったまま**レジストリに残り、パネルは並べ、地図は描き、次の op は食べた。

いまは **各段が commit-or-restore** である。古いレコードを保持したまま走らせ、失敗したら**戻して**
`stale` を立て、そこから下流全部へ伝播する。

- `failed[]` は呼び出し元への報告（実行されなかった段は `upstream-failed`）。
- `stale` は**データセット自身が持つ状態**で、パネル・地図・次の op が読むのはこちら。
  ⚠ 伝わるのは**根本の理由**（実際に断られたコード）であって `upstream-failed` ではない——
  読者が直すのは根本のほうで、症状の言い換えに上書きすると診断が消える。
- 地物は**消さずに残す**。実際に計算された最後の答えは、空のパネルより読者にとって価値がある——
  **ただし、全員がそれを何であるかと述べている限り**。だから `js/gis-ops.js` が `input-stale` で
  断り（§2.3）、パネルがバッジを出す。**誰も検査しない状態は、状態ではなく飾りである。**

⚠ **`ok` は部分成功を true にしない**（`failed[]` が空のときだけ true）。

⚠ `failed[].why` には **op が返した `why` がそのまま入ることがある**。`op-failed` に潰すと、
読者に必要な 1 文（何が悪かったのか）が消える。
⚠ IndexedDB が無い環境では**黙って成功を返さない**——`storage-unavailable` を返し、
`available()` が false を返す。1 回 open に失敗しただけでは殺さない（「今ディスクが一杯」と
「そもそも無い」は別の主張）。

### 4.2 ⚠⚠⚠ (#R765) 「作業を再開できる」と「その結果をもう一度出せる」は別のこと

§4 の保存は分析を**再開可能**にする——入力は本体ごと戻り、処理は再計算され、エンジンが変わっていれば
そう報告される。それは正しい設計で、**再現性ではない**。別のエンジンで、更新された上流に対して、
別の時刻に再生されたレシピは、**古い答えの名前を着た新しい答え**である。

⚠ **足りなかったのは倉庫ではなく文書だった。** 分析を他人に——あるいは自分の半年後に——渡すとき、
問いは「**この数は何から、どうやって出たのか**」で、その答えは 4 つのモジュールに散らばっていて、
手で歩かないと集まらなかった。`manifest(id)` が 1 度歩いて書き出す。

```
{ id, title, producedAt, manifestVersion,
  engineNow,                      いまの版（各段の engineThen とは別の主張）
  steps: [ 入力が先の順に
    { id, title, kind, origin,    'import' | 'layer' | 'layer-raster' | 'op' | …
      recipe,                     op のとき: {op, inputs, params} ——もう一度走らせられる形
      engineThen,                 その段を計算した版（記録されていなければ null）
      acquisition,                取得のとき: {layer, bounds, statedTime, at}
      coverage,                   どこまで答えられたか＋演算が何行落としたか（丸めず全部）
      crs / sourceCrs / time,
      fields,                     列と、その単位と、誰が述べたか
      bands,                      格子のとき
      fingerprint } ],            中身の SHA-256（正規化 JSON）
  answer: { fingerprint, count, kind },
  gaps: [ { step, gap, means } ] }
```

⚠⚠ **いちばん重要な欄は `gaps` である。** このアプリが**自分の答えについて本当に知らないこと**を
並べる——版を持たない上流・バイトを保存していない取り込み・エンジンが自分を刻む前に計算された段・
指紋を取れなかった環境。知っていることだけを並べた文書は「**知らない**」を「**全部だ**」の代わりに
する形（[[intmap-one-store-was-asked]]）で、他人の数を検算する読者が最初に要るのはこちらである。
⚠ **`gap` は読者向けの文を持つ**（`means`）。コードだけでは届かない。

⚠ **指紋はレシピではなく答えに対して取る。** 1 つのレシピの 2 回の実行は同じ分析で、
**同じ答えかどうかは別の問い**であり、出てきたものをハッシュしないと答えられない。
`verify(id, manifest)` が **「同じ」「違う」「測れなかった」の 3 つ**を返す
——指紋を取れなかったものは一致ではない。

⚠ **正規化しないと指紋ではない。** `JSON.stringify` は挿入順にキーを書くので、同じ地物を別の経路で
組んだだけで別の指紋になる。深さを問わずキーを整列させる。⚠ **配列の順は保つ**——地物の並びは
答えの一部である。⚠ **格子は画素の並びと「どこに置かれているか」の両方**から取る（同じ画素が別の
場所に置かれているのは別のデータで、#R756 の往復検査が捕まえたのもその種類である）。

⚠ **記録が、自分を計算したエンジンを述べる**（#R765）。#R749 は保存する段に版を書き込んだが、
それは**開き直したプロジェクトだけ**を覆う。いまレジストリに在る記録——読者が見ていて、いま
書き出そうとしているもの——は何も述べていなかった。後からカーネルに訊くのは**別の問い**
（「いま何が載っているか」）で、2 つが食い違う場合こそ版が在る理由である。
⚠ **配る者が居なければ黙る**——`js/gis-project.js` が載っていない状態で計算された記録は版を持たず、
`manifest()` はそれを**今日の版で埋めずに** `engine-not-recorded` の gap として報告する。

### 4.3 ⚠⚠ (#R765) 自分の読み手で読み直せることは、他人が開けることではない

#R756 は「**書き出せた**」と「**読み直せた**」を分け、3 形式すべてを既存の読み手で許容幅 0 で
読み返した。正しい第一段で、その註が述べていなかった限界がある:

> **一緒に作られた書き手と読み手は、他の誰にも開けないファイルについて一致できる。**

タグの順を間違えても、QGIS が要るタグを落としても、述べたバイト順と実際が違っても、
**同じ仕様書の同じ読み方から作られた読み手**は、いちばん許してしまう読み手である。往復は緑のまま、
ファイルは他所で開けない。**不一致を出せない比較は何も測っていない**
（[[intmap-prefilter-erred-inward-under-a-comment-saying-outward]]）。

⇒ `tests/r765-gis-external-reader-checks` は **TIFF 6.0 / GeoTIFF 1.0 の仕様から書いた読み手**を
テストの中に持つ。`js/gis-geotiff.js` も `js/gis-export.js` の定数も**取り込まない**——タグは
**番号で**知っている（33550 / 33922）。バイト順の印・magic 42・IFD の項目数・オフセットがファイルの
中に収まっていること・**述べた `SampleFormat` と実際に書いたバイトが一致すること**を、
寛容な読み手なら素通りするところで厳しく見る。⚠ **参照が本当に不合格を出せることも測る**
（壊したファイルを 3 通り作って、実際に拒むこと）。

⚠⚠ **これが主張していないこと。** この読み手は **GDAL ではない**。ここが緑なのは
「**仕様どおりに書けている**」であって「**QGIS で開ける**」ではない——後者は実際に第三者の実装で
読んで初めて言えることで、**このリポジトリはオフラインではそれを言えない**。その線は、
埋めずにここに書いておく。

## 5. 横断クエリがこの層を読む向き — `js/atlas-query.js`

`data.query` の `from` に**データセットの id をそのまま書ける**。列は `fields[]` そのもので、
cost 0 ・ origin `raw`（＝出典レコードの項目の写し。この行が持っている）。

⚠ **押し込み（登録）ではなく引き（pull）である。** クエリ engine は遅延読み込みなので、
セッションの早い段階で「engine に登録する」経路は**まだ存在しないモジュールへの登録**になり、
その取りこぼしを直す**再生**という 2 つ目の正本ができる。代わりに `run()` / `catalogue()` /
`tables()` の入口で `syncUserTables()` がレジストリを**その瞬間に読む**。規則は 1 つ、評価は遅く、
ファイルがいつ来ても正しい。

⚠ **線と面は自分の形を持ったまま渡る。** 行は元の geometry への**参照**（コピーではない）と
その外接矩形を持ち、**空間の判定は全部その形で行う**。表に出る 1 点はいまも外接矩形の中心だが、
**そこからは何も測らない**——そして**行が自分で**「この座標はここで計算した代表点である」と述べる
（以前は注記が結果全体に 1 回付くだけで、どの行が実点でどの行が導出点かを読者は区別できなかった）。

⚠ **これが `near` にできないことである。** `near` はピンとピンのあいだを測る。線や面には 1 つの
ピンが無く、その代わりが外接矩形の中心だった——C 字の区域や湾曲した道路では、**その中心は形の外**
にある。だから `spatial` 句が別にある:
`{"rel":"within"|"contains"|"intersects"|"nearer_than","of":TABLE|"geometry":GeoJSON,"km":num,…}`。
`within` は相手の表を**1 つの集合として**扱う（どの構成員の中にも無いが和集合の中にある行が、
正しく中に入る）。`catalogue()` はこの一覧を**実行する側の宣言から導出**して返すので、
planner が見られない述語を足すには、宣言に無いものを実行するしかない（#R582 の形を避ける）。

⚠ 述語は 1 種類しか書かない。形を持たない行（内蔵の点の表）には `[lng,lat]` の Point を組んで
**同じ述語へ渡す**。

## 5.1 地図のレイヤーを入力にする — `js/gis-layers.js` (`window.IntMapGisLayers`)

`sources()` は**一覧を持たずに数え上げる**——`IntMapLayers.list()` のうち `featuresIn` に答える行と、
geo-engine が持つ geojson source。手で並べた一覧は、次に足されたレイヤーを黙って落とす。
`read()` は**形状も属性も落とさない**。`toDataset()` が `IntMapData` に登録し、`provenance` は
`{kind:'layer', layer, bounds, at, statedTime}`＝**いつ・どのレイヤーの・どの範囲を読んだか**。

⚠ **#R732 の時点で、このファイルの呼び出し元は 0 件だった（#R735 で直した）。** 橋は作られ、検査され、
3 つの文書に書かれ、そしてプログラムの中で参照していたのは**その検査とその散文だけ**——読者は地図の
レイヤーを分析に入れられなかった。入口は `js/gis-panel.js` の「地図から取り込む」節で、
`sources()` を並べ、`toDataset()` と `toRaster()` を呼ぶ。**呼ばれない export は機能ではない。**

⚠ **レイヤーが述べる時刻は文であって時刻ではない。** `IntMapLayers.state(id).time` は読者に向けて
書かれている（「直近 24 h」「2020-06-15 12:00 UTC」「1889」）。だから 2 通りに運ぶ——文は
`provenance.statedTime` にそのまま、`time` の宣言は**その文が実際に時刻として読めるときだけ**。
「直近 24 h」を瞬間として宣言するのは、この製品が記録している
「誰も述べていないことを地図が述べる」欠陥を別の場所で再演することである。

⚠ **数値レイヤーは `toRaster()` で格子になる**（§1.4）。半分は地物ではなく**場**で、
`sampleAt` に 1 点ずつ訊く契約しか無いので、**1 画素 1 await** である——だから上限を書く代わりに
`signal` で中止でき `onProgress` で進捗を述べ、行ごとにイベントループへ譲る。
⚠ 消えているレイヤーは `layer-not-sampling` で拒む（消えているレイヤーは格子を読み込んでいないので、
全画素が穴になる＝「何も無い」ように見える測定になる）。

⚠ **保存は body（地物そのもの）で、レシピの再実行ではない。** レイヤーの中身は時刻で変わるので、
残すべきは「あのとき読んだもの」である。

⚠ **地図側の窓も直した。** `js/map-ui.js` の `_srcFeatsIn` は「箱に入っているか」という問いを
`geometry.type === 'Point'` で代用していたので、**レイヤーが持つ線と面は必ず 0 件**だった。

## 5.2 属性の編集と取り消し — `js/gis-datasets.js`

取り込んだ値は**読み取り専用ではない**。`editValues` / `addField` / `removeField` / `renameField` が
値と列を変え、`undo` / `redo` / `history` が戻す。⚠ **この機能の本体は、何を拒むかである。**

- **op の出力は編集しない**（`edit-would-contradict-recipe`）。その記録の地物は**自分のレシピが出す
  もの**であり（§3）、編集するとその等式が壊れる——`setParams` の再計算が読者の編集を黙って消し、
  §4 の「結果を保存しないのはレシピがあれば再生できるから」が同時に偽になる。**取り込んだ側を
  編集するか、編集用の複製を作る**。
- **ラスターは編集しない**（`edit-needs-features`）。画素は属性ではない。
- **`stale` な記録は編集しない**（§4.1 と同じ理由。古さが編集で見えなくなる）。
- **下流のある列は消さない・改名しない**（`field-has-dependents`）。その列を読んでいるレシピが
  再実行できなくなり、そのとき列はもう戻せない。`time` の宣言が名指す列も同じ
  （`field-in-time-axis`。無い列を名指す宣言は §1.5 が防いでいる形そのもの）。
- 値を編集すると `fields[]` と `count` と `withGeometry` を**測り直す**。宣言した型が成り立た
  なくなれば外して `fields[].typeRefused` を立てる——編集で `"abc"` が入った number 列は、もう
  number ではない。黙って number のままにするのは**誰も述べていない主張**である。
- 編集は `dependents()` を `stale`（`input-edited`）にする。**入力が変わったのだから下流は答えでない。**

⚠ **`provenance.kind` は `import` のまま**で、`provenance.edits = {count, lastAt}` が足される。
バイトが起源であることは編集で変わらないが、**読者が触ったことは読者に見える**必要がある。

⚠ **取り消しは session の中だけ。** 履歴は**逆操作**（どの行のどの列が何だったか）で持つので、
4 万件の表を 20 回編集しても地物の複製は積まれない。保存に乗るのは**編集後の本体そのもの**
（取り込みは body ごと保存される・§4）——だから編集は再読み込みを越えて残り、取り消しの履歴は残らない。

**列の型と単位は宣言できる**（`declareField`）。⚠ **型の宣言は実データに対して検証する**
（§1.5 と同じ規則。`number` と宣言された列に数として解けないセルが 1 つでもあれば、件数と実例を
添えて `field-type-refused`）。⚠ **単位は検証できない**——`km` と書かれた列が km である保証は
どこにも無いので、`fields[].unit` の隣に `unitStated`（`reader` か、ラスターの band なら `source`）を
持つ。**測ったことにしない。** 測定値の `type` は宣言で上書きされず、読者は
「測ると text・読者が number と宣言」を区別できる。

## 5.3 属性値による着色 — `js/map-ui.js`

取り込みは 8 色パレットの循環 1 色で描かれていた。いまは `GeoJSONUpload.style(ref, spec)` が
**列の値で塗る**——`categorical`（値ごと）と `graduated`（`quantile` / `equal`）。

- ⚠ **数かどうかを自分で判定しない**——`IntMapData` に訊く（§1.1 が「型づけの規則は 1 か所」と
  述べている。特に `"01100"` は数ではない）。訊けないセッションでは `graduated` を名前を付けて断る。
- ⚠ **欠損は色ではない。** 値の無い地物は「0 の色」ではなく**欠損の色**で描き、件数を凡例に出す。
  0 として塗れば、読者は空欄を最小値として読む。
- ⚠ **上限を超えた分を捨てない。** 色より多い分類は「その他」に畳み、**畳んだ件数を凡例が述べる**。
- ⚠ **地図と凡例は同じ snapshot**。凡例は `style()` が返したものを描くだけで、数え直さない。
- 描かれたレイヤーとデータセットは**識別子で結ぶ**（`GeoJSONUpload.link` / `find`）。綴り（title）で
  結ぶと、同じ名前の 2 ファイルで壊れる。

## 5.4 Atlas がこの層に処理を依頼する — `js/gis-atlas.js` (`window.IntMapGis.atlas`)

§5 の `data.query` は取り込んだデータセットを**読む**。⚠ **作らせる経路は #R743 まで 1 件も無かった**
——だから Atlas ができる空間解析は、誰かが既にアプリの機能として作ったものだけだった。

**能力は 2 つで、op ごとには 1 つも無い。**

| 能力 | 何をするか |
|---|---|
| `data.gis` | `{"type":"gis","op":OP,"inputs":[REF,…],"params":{…},"acquire":{…}}` を走らせ、**登録されたデータセットの id** を返す。⚠ **`op` を述べなければ「取得だけ」**（#R759） |
| `map.drawDataset` | `{"type":"gisDraw","dataset":REF}` — 出来たものを地図に描く |

⚠ **取得条件は #R759 まで 1 つも渡っていなかった。** この扉は `layers.toDataset(id, {})` ——
**空の object** を渡していたので、`js/gis-sources.js` が持つ 8 欄の契約のうち planner が使えるものは
**0 個**だった（画面のパネルは 3 分の 1 を使っていた）。いまは `acquire` が要求そのもので、
**カメラではない**:

- ベクタ: `bounds` / `where` / `fields` / `limit` / `cursor` / `time`
- 格子: `bounds` / `width` / `height` / `where` / `unit`（`sample` は #R743 の綴りで、同じ 3 欄。
  **両方に別々の窓を書いたら断る**——どちらを意味したかはこの file には分からない）

⚠ **語彙の正本は `js/gis-layers.js` の `acquireFields()` 1 か所**で、Atlas 側は**訊く**。
知らない欄は**名前を挙げて断り、拒否が語彙を運ぶ**。⚠ **`op` の無い依頼は取得**であり、答えは
取れたものの行・その `coverage`・続きがあるときの `next`（次は `acquire.cursor` に載せる）。
これは能力の追加ではなく**同じ `data.gis` の別の形**である——形ごとに能力の行を足すのは、この層が
作らないと決めている手書きの一覧そのもの。

⚠ **目録は `ops()` そのもので、写しではない。** op を `DECL` に 1 本足せば、その日のうちに画面にも
Atlas にも出る。Atlas 側に op の一覧を書くことは、#R732 が画面で測った欠陥（`ORDER` が 4・`DECL` が 9）
を別の場所で作ることである。⚠ **ひとつだけ導出できない一覧がある**——読者（模型）が読む案内文は
GIS のチャンクが読み込まれる前に送られるので `DECL` に訊けない。だから**検査が案内文を `DECL` と
突き合わせる**（`tests/r743-gis-atlas-surface-checks` ⑨）。名指しするのは #R733 の実測が理由で、
**渡されていることを知らされていない能力は使われない**（模型は 8 手すべてを検索に使った）。

**入力**は登録済みの id・題名・`layer:<id>`（地図のレイヤー）。⚠ **レイヤーを入口にしていないと
Atlas は鎖を始められない**——何も取り込んでいないセッションは、空の台帳と、データで埋まった地図を
持っている。格子の枠（`sample`）は**述べさせる**——ここで決めた窓と解像度は、誰も頼んでいない測定に
なる。**解決できない参照は、何が在るかを添えて断る。**

⚠ **計算と描画が別の能力なのは観測器のため**（#R736/#R737）。「訊かれたときだけ描く」ものが
「地図に書き込む」と宣言すると、動かなかった地図を観測器が測って**正しい答えを `not_rendered` と
呼ぶ**——実測で 21 手・10 分がその再試行に費やされた。パネルでも「作る」と「地図に描く」は
別のボタンである。

## 5.5 描画と分析が同じ供給元を読む — `js/gis-sources.js` (`window.IntMapGisSources`)

§5.1 の橋は**描画器が持っているものを分析へ取り出す**ものだった。ベクタはレンダラの GeoJSON ソース、
ラスターは `sampleAt()` に 1 画素ずつ。⚠ **全世界の矩形を渡したことと、元データを全件取得したことは
同義ではない**——解析の完全性は、そのレイヤーが**何を保持・取得しているか**に依存するのに、
橋はそれを述べていなかった。だから分析の結果が「世界について」なのか「いま画面に載っているものに
ついて」なのかを、読者も Atlas も区別できなかった。

`list()` / `features(id, req)` / `region(id, box)` / `acquire(id, req)` / `declare(id, decl)`。
⚠ **一覧は手で並べず数え上げる**（§5.1 と同じ規則）。

**取得はすべて `coverage` を伴う**（省略できない）:

```
{ completeness: 'all' | 'partial' | 'sample',
  reason, requested, served, count, asOf, resolution }
```

⚠ **`all` は推測からは届かない。** レンダラが 400 機を持っていることは、外から見て「世界の一覧」とも
「いまの視野ぶんを取ってきた」とも区別がつかない。だから測れないものは `partial` と**理由**を述べる
——「知らない」を「全部だ」の代わりにしない（[[intmap-coverage-counted-is-not-coverage-seen]] が
件数について記録しているのと同じ形）。`all` を出せるのは**供給元自身の宣言**だけで、今日それを
述べているのは**取り込んだファイル**（`js/map-ui.js`）——ファイルが復号した地物が全部そこに在り、
それは視野ではないから、構造として完全だと言える唯一の供給元である。
⚠ **(#R756) 「取り込んだファイルだけ」は #R756 で終わった。** レイヤーの登録が自分について述べる道と、
その宣言から供給元を作る道ができたので、`heritage` と `volcanoes` も `all` に到達する——§5.6。

⚠ **レイヤーがオフでも、答えるものからは読む。** 旧 `toRaster()` は「オフ ⇒ 値が無い」を全行に
ついての事実として断っていた。いまは試して、供給元が**答えれば**読み、答えなければ
`layer-not-visible` で断る（黙って空を返さない）。
⚠ **(#R763) ただし 1 点で全体を断じない。** 窓の中央 1 画素だけを試していたので、**日本を覆う窓の
中央は海**で、陸のデータを持つ場が「このレイヤーは見えていない」と答えていた。窓の複数箇所を試す
ようにしたが、**それでも測っていたのは「その座標に値があるか」だった**。

⚠⚠⚠ **(#R774) 試すのは「この供給元は答えるか」であって、「この座標に値があるか」ではない。**
実測（外部監査）: `[0,0]–[1,1]` の窓で**北東の 1 画素だけが値を持つ**場は、**表示 ON では読め
（100 画素を読み、有効値 1 件）、表示 OFF では `layer-not-visible` で窓ごと拒まれた**——同じ範囲・
同じ供給元・同じ問いが、**チェックボックスの状態で別の答えを返していた**。試す点を増やすのは直しに
ならない（次の隅が同じように落ちる。`.agents/rules/no-ad-hoc-hardcoding.md`）。⇒ **分けたのは
2 つの事実で、潰れていた場所は `js/map-ui.js` の `sampleAt`**——訊いた登録が null を返すと**行を
1 つも返さなかった**ので、「訊いたが、そこに値が無い」と「そもそも訊ける登録が無い」が同じ沈黙に
なっていた。いまは**訊いた登録は必ず 1 行返り**（`asked:true`・値があるときだけ `value`）、試験は
**行が返ったか**を読む。行が返れば窓を全部読み、値がどこにも無ければ **`layer-values-all-missing`**
——「訊けなかった」ではなく「そこには無い」という別の事実で、読者への文は既にある（§5.5 の拒否語彙）。
⚠ **`layer-not-visible` は、どの位置でも行が返らなかった行のために残る**（表示が ON のときも同じ
——読み終えて 1 行も返っていなければ同じ拒否になる）。**5 点すべてが投げたときは `layer-sample-failed`。**

### ⚠⚠⚠ (#R763) 表示用に整えた値は、解析用の値ではない

**実測**: 点の標本を実装している登録 **18 行のうち、数を返すものは 0 行だった。** どれも値を丸めて
単位を連結し（`「12.3°C」`・`「0.2 mm/h」`・`「1240 m」`）、`asNumber` は**セル全体が数でなければ
数と認めない**（正しい——`「12 km」` は 12 ではない）。⇒ **気温・降水・標高・NO₂・海面水温・積雪・
年間降水量・GIBS の 5 目盛り、どれも区域統計に対して `layer-values-not-numeric` を返していた。**
唯一通っていた `aod` が通っていたのは、その単位文字列が**たまたま空**だったからである。
⇒ 「区域統計の関数がある」と「内蔵の気温レイヤーで区域統計を実行できる」は別の事実で、真だったのは
前者だけだった。

**直したのは分解ではなく契約**（`parseFloat` で割り直すと、単位も丸める前の桁も分類コードも風の 2 成分も
戻らないし、`「45% (sparse → dense)」` からは数を発明することになる）:

- 登録は **`measure(lng,lat)`** で**数量**（`{value, unit}`）または**分類**（`{code, label}`）を述べ、
  `text` が読者に見せる文。**両方が 1 つの値から、1 か所で**作られる（単位は元から kind ごとに 1 度だけ
  書かれていた——新しい一覧は増えていない）。
- `sampleAt()` の行は今までどおり `value`（文）を運び、述べた行だけが `number` / `unit` / `code` を添える。
- `region()` は**その数を先に読む**。`asNumber` は**second road として残る**（文しか作らない行が裸の数を
  作っていることはあり、それを落とすのは在るデータを断ること）。⚠ **文から単位を剥がすことはしない**
  ——剥がした単位は誰も述べていない単位である。
- ⚠ **数量は上流が公表した単位で持つ。** GIBS の目盛りは読者が °F を選んでいると °F へ換算するので、
  **表示の好みが、解析の数を変えていた。**

⚠ **(#R763) 「取得に失敗した」「値がどこにも無い」「文字列だった」は 3 つの答えである。** `js/gis-raster.js`
は `failed` と `empty` を別に数えているのに、`js/gis-sources.js` が**その 1 段上で例外を握り潰して `null` を
返していた**ので `failed` は**構造として常に 0** だった。⇒ 上流が落ちた窓に対して、読者は「このレイヤーは
数値ではなく文字列を返す」という**事実と違う文**を見ていた。いまは `layer-sample-failed` /
`layer-values-all-missing` / `layer-values-not-numeric` の 3 つに分かれ、`failed` と `empty` は**重ならない**。

## 5.6 内蔵レイヤーが供給元になる — 宣言・属性条件・ページ送り（#R756）

§5.5 の契約には**入口が無かった**。`supply(id, impl)` の呼び出し元がリポジトリに 1 件も無く、
`prepare()` の 2 つの門は「実装が申告していない能力」を断るので、結果として:

- `where`（属性条件）は**アプリのどの id に出しても** `where-not-supported` で断られた
- `cursor`（続き）も同様に `cursor-not-supported` で、成功する経路が 1 本も無かった
- `declare()` の呼び出し元は取り込み経路だけで、**内蔵レイヤーは宣言を運ぶ道を持たなかった**
  ——`IntMapLayers.state()` は読者に見せる 6 欄（`id/on/label/time/source/legend`）を組み立てるもので、
  **「その供給元が何を保持しているか」はその 6 欄ではない**

直したのは 3 か所で、どれも**一覧ではなく経路**である。

1. **登録が自分について述べる。** レイヤーの登録は `holds`（関数または object）で
   `{extent, complete, viewBound, live, asOf, resolution}` のうち**述べられるものだけ**を書く。
   `IntMapLayers.declarationOf(id)` がそれを渡し、`js/gis-sources.js` の `declarationOf()` が
   `declare()` と**同じ正規化**を通す。⚠ 明示の `declare()` が優先する（取り込みは、いま自分が
   埋めたソースについて述べているから）。⚠ **述べられないものは欄を空にする**——`null` と `false` は
   別の主張（[[intmap-data-must-not-claim-an-author-it-lacks]]）。

2. **供給元は登録から発見する。** `js/gis-layers.js` の `supplierFor(id)` は、**その行自身の宣言**が
   「宣言した範囲の中を全部持っている・視野に縛られていない」と述べ、かつ実際に地物を渡すときだけ
   実装を作る。⚠ **どの id が供給元かはどこにも書かれていない**——明日登録される行は、そう述べる
   ことで供給元になる。`js/gis-sources.js` は供給元を探す唯一の入口（`sup()`）でこれを訊く。

3. **申告した能力は実際に効く。** ⚠⚠⚠ **#R783 まで、この文は描画済みの経路についてだけ真だった。**
   `supplierFor()` は**両方**の供給元について `where:true / cursor:true / limit:true` と申告する一方、
   未描画の loader 経路（`loadedFetch`）は矩形で絞るだけで条件・件数・位置を適用せず、
   しかも `coverage.filteredBy` は `'supplier'` と述べていた（3 行 v=1,2,3 で実測: `where v>=2` →
   `1,2,3` ／ `limit 1` → `1,2,3` かつ `next:null` ／ カーソルは読まれず）。**絞られていない答えに、
   絞ったという記録が付いていた**のが 3 つのうち最悪だった。
   ⇒ 直したのは**道が 2 本あったこと**で、`if` を 3 つ足したのではない——`pageOf()` が条件・カーソル・
   件数・`available` / `complete` / `next` の**唯一の実装**で、両経路がそこを通る。`filteredBy` は
   **実行した側の申告**から取る（「要求された」からは導かない）。
   ⚠ **カーソルは問いとデータに結び付く**（`<layer>@<sig>@<offset>`。`sig` は窓・条件・時刻と、
   順序どおりの答えの digest）。一致しないものは `bad-param` ＋ `detail.reason`
   （`query-or-data-changed` / `cursor-of-another-layer` / `cursor-not-recognised` / `past-the-end`）で
   断る。⚠ digest は同一性の証明ではなく「**認識できるものを断る**」ためのもの。
   ⚠ **`canSample()` は表示状態を読まない**（#R783 まで実質 `state.on` だった＝非表示が「能力が無い」
   になり、表示中は「数値サンプラーが在る」の証明にならなかった）。4 つの事実は別々に読める
   ——`samplingOf(id)` の `capable`（**測定値**。未測定は `null`＝候補）/ `door` / `visible` と、
   `js/gis-sources.js` の `list()` が運ぶ `sampling.prepared`（`needsVisible` の三値をそのまま）。

   供給元が申告するのは `where` / `cursor` / `limit` で、`fields` は
   申告しない（射影は `js/gis-sources.js` が 1 か所でやる）。⚠ **演算子の語彙は `js/gis-ops.js` の
   `filter` op が正本**で、この実行器が持たない名前は**名前を挙げて断る**（黙って false にしない）。
   ⚠ 意味が離れないことは主張ではなく**計測**である: `tests/r754-gis-supply-checks` ④ が
   9 演算子と空セルを**両方の実行器に通して同じ行**を要求する（同期の扉は出荷済みの契約なので、
   非同期の `ops.run('filter')` へ行を流すことはできない——だから等価性を測る）。

いま宣言している行（#R756 時点・**表ではなく実測の記録**）:

| レイヤー | 述べていること | 根拠 |
|---|---|---|
| `heritage` | `complete:true` / `viewBound:false` / `live:false` | 同梱文書の全地点を `whs-src` に書く。絞り込みは paint 側 |
| `volcanoes` | `complete:true` / `viewBound:false`（`live` は述べない） | `data/volcanoes_gvp.json` 全件。⚠ 観測所の状態は同じ地物へ更新されるので「更新されない」とは言えない |
| `aircraft` | `complete:false` / `viewBound:true` / `live:true` | airplanes.live に**カメラ矩形**で問い合わせる |
| `ships` | `complete:false` / `viewBound:true` / `live:true` | AIS の購読も中継も**カメラの bbox** を運ぶ |
| `pharma` | `complete:true` / `viewBound:false` / `live:false`（#R759） | 同梱の配列を丸ごと `ph-src` に書く。bbox・上限・ズーム・視野が読み込み経路に 1 つも無い |

⚠ **#R759 は 30 の登録行を全部読んで、この 5 行以外は述べられないことを実測した。** 内訳は
**地物を持たない 17 行**（ラスタ／タイル／点の標本だけ。`featuresIn` が無いので `holds` を足しても
供給元にはなれない）と、**読み込み経路に絞り込みが実在する 8 行**——カメラ矩形（`webcams`・
`datacenters`）、件数上限（`webcams` は 1500・`earthquakes` は 2000）、下限マグニチュードと時間窓
（`earthquakes` の `4.5_month`）、provider ごとのページ取得と実行時の打ち切り（`radiation`）、
時間窓と病原体の絞り込み（`outbreaks`）、読者が選んだ群だけを保持する（`satellites`）、
非表示なら空を書く（`news`）。⚠ **「宣言が足りない」のではなく、上流の実態がそうなっている。**
一律に `complete:true` を足すことは、この層が測るためにある主張を偽ることになる。

⚠ **供給元の採用は時点に依存した。** `supplierFor()` の 2 つ目の条件は「実際に地物を渡すか」で、
`_srcFeatsIn` は**レイヤーがまだソースを作っていないと `null`** を返す。⇒ **一度も点けていない
レイヤーは、宣言していても供給元になれなかった**（取得は `layer-not-sampling` で断られた）。

⚠⚠⚠ **(#R763) その扉ができた。** 依存していたのは**データではなく描画**である——`heritage`・
`volcanoes`・`pharma` はどれも同梱文書を fetch してレンダラのソースへ書くだけで、fetch に地図は
要らない。足りなかったのは、その fetch を**ここから訊けること**だった。

- 登録が **`load()`** を述べる（「頼まれたら、描かずに自分の保持を全部渡せる」）。`IntMapLayers.loaderOf`
  がそれを渡す。⚠ **一覧はどこにも無い**——述べた行が、述べたことによって読めるようになる。
- `supplierFor()` は、地物を渡せない行に loader があれば **非同期の供給元**（`sync:false`）を組み立てる。
  ⚠ **`sync:true` を名乗らせない**——同期の扉がそれを呼ぶと fetch を投げて答えを捨てる。
- だから **`acquire()` に呼び手ができた**。それまで `js/` からの呼び出しは **0 件**で、非同期の半分は
  配線だけで通電していなかった（[[intmap-wiring-complete-is-not-wiring-live]]）。`js/gis-layers.js` の
  **`acquireDataset()`** がその扉で、`js/gis-atlas.js` はこちらを使う。⚠ `toDataset()` は同期のまま
  （パネルが await 無しで呼ぶ出荷済みの契約で、対称性のために壊すものではない）。両者は**同じ要求を
  組み立て、同じ登録へ渡す**。
- ⚠ **範囲の判定は 1 つ**（`IntMapLayers.narrow`）。loader 経路が自前の判定を持てば、同じ依頼が
  「いま描かれているか」で違う行を返す。
- ⚠ **どの種類の行かも、描画に訊いていた。** `list()` はレンダラの source から id を取るので、描かれて
  いない行は `grid` に落ち、`acquire()` がその分類で分岐して**地物の依頼を region() へ送り**「幅が
  無い」と断っていた。いまは **供給元が地物を渡せるかどうか**で決める。

⚠ **ページの継ぎ目は「重複も欠落も無いこと」で測る。** `next` は**終わりのときも `null` として
在る**（欄が在ること自体が「継続について述べた」）——欄が無いのは `continuation-unstated` であって
「これで全部」ではない。

## 5.7 取得の前に何が選べるか — `describe()`（#R783）

⚠⚠⚠ **取得後の記述のほうが、取得前の記述より厚かった。** `datasetRow()`（取得後）は属性の型・
min/max・単位とその著者・時刻・CRS・バンド・格子・被覆・鮮度・出自を渡す一方、`mapRows()`
（取得前）が渡していたのは **`ref` / `label` / `geometryType` / `count` / `samplable` の 5 欄だけ**で、
**何の量か・どの時期か・どの範囲か・どの解像度か・どの条件で検索できるか**は 1 つも渡っていなかった
（うち 4 つは**ゼロ**）。⚠ しかも `toRaster` は幅と高さの無い呼びを `raster-sample-needs-window` で
断るので、**見せていない数を要求していた**。

⇒ `describe(ref)` が、供給元が既に持っている答えを**訊いて**投影する（新しいカタログを手書きしない）。

- **24 slot を宣言**し、各 slot は **stated / undeclared / notApplicable のどれか 1 つに必ず入る**
  ——空欄は存在しない。主題名は slot 名から**導出**する（2 つ目の一覧を作らない）。
- 値は 1 つも手書きしていない: `declarationOf` / `supplierOf` / `conditionOps` / `acquireFields` /
  `samplingOf` / `state` の答えそのもの。⚠ 単位は**取得前には誰も述べていない**ので
  `unit-stated-only-by-the-samples` として沈黙する（label から推測しない）。
- 一覧は `layers.sources()` ∪ `sources.list()` の**和集合**——描かれていない行も出る。
  ⚠ 登録が 1 つ増えた日に**自動で現れる**ことを検査が測る（一覧が手書きでないことの証明）。
- **標本の 4 欄**（`sampleCapable` / `samplePrepared` / `sampleAvailable` / `sampleVisible`）が
  §5.6 の 3 で述べた 4 事実を運ぶ。⚠ `samplable` は消していない。⚠ 未測定を `false` にしない。
- hot path は分離してある: 参照の解決と薄い拒否は記述の組み立てを払わない。

## 5.8 画面の無いところで同じ GIS を動かす — `makeGisRuntime()`（#R783）

この層が**所有していない**外部依存は 6 つだけだった（`IntMapGeodesy`・`IntMapLayers`・
`IntMapGeoEngine`・`GeoJSONUpload`・`IntMapLang`・`IntMapHost`）。⚠ **本当の欠陥は組み立て側**で、
`js/gis-core.js` の 1 行目が無防備な `window.IntMapModules = …` だったため、**15 モジュールのうち
この 1 本だけが Node から import すらできなかった**——何が・どの順で mount されるかを決める
ファイルが、画面の無いところから測れなかった。

- `makeGisRuntime(deps)` が**同じ `mount()`** をブラウザ入口と共有する
  （**Atlas 用 GIS と外部 AI 用 GIS を別に作らない**）。
- `EXTERNALS` が借り物の全一覧で、各項に**読み手の file:line** を書く⇒誰も読まない依存名は書けない。
- モードは 2 つ。差は**供給者の性質**だけ: `externals` 無し＝生きた scope（**ブラウザ経路は不変**）、
  `externals` あり＝**閉じた集合**で、渡していないものは `scope` に偶然載っていても使わない
  （`scope-carries-uninjected`）。required 欠落は `dependency-missing` が名前・global・用途を述べる。
- mount のあと **14 の global が同一オブジェクトとして見えるか照合**する
  （`kernel-not-reachable`）。⚠ published と述べられていることを信じない。
- ⚠ **拒否が scope を置き去りにしてはならない**: plan → 検査 → install → mount の順で、
  mount が失敗したら install を巻き戻す（初版は据えてから断っていて、次の呼び出しが
  **自分の作った状態を理由に**断られた）。
- 二度目の呼びは**同じ組**を返す（`reused: true`）。以前は 2 回呼ぶと registry が 2 つできた。

### 5.8.1 manifest v2 — 「辿れる」を欄の有無で言わない

`manifestVersion` が 2 になった。既存（レシピ・エンジン版・取得条件・指紋・gaps）は**そのまま**で、
足したのは「**後から本当に取り出せるか**」:

- `trace.data` は `recipe` / `recipe-inputs-missing` / `body` / `body-unverifiable` を**導出**する
  ——レシピの入力が**この文書の中に実在するか**を照合して決める（欄の有無ではない）。
- `trace.retrieval` は再取得の参照そのもの（op は実引数＋期待指紋、取得レイヤーは `reacquire` と
  `acquiredAt`）。⚠ **時刻で変わるレイヤーは取得時の本体を保つ既存方針のまま**で、本体が manifest に
  入らないことを `inThisDocument:false` / `keptBy` が明言する。
- `trace.environment` は `recorded` / `partly-recorded` / `not-recorded` / `not-computed-here`。
  `environment.statesNoVersion` は**載っているのに版を黙っている module**（版の帳簿からは原理的に
  見えない）。
- `traceability.blockedBy` が**空であること**が「辿れる」であって、欄が埋まっていることは代わりに
  ならない（[[intmap-data-must-not-claim-an-author-it-lacks]]）。
- `verify()` は環境の脚も答える。⚠ 「測れなかった」を「同じ」と言わない。

## 5.9 幾何の妥当性は 3 段である（#R783）

⚠⚠⚠ **`MultiPolygon` の妥当性を、誰も全体について検査していなかった。** `validate()` は各 Polygon を
順に `checkPolygon()` へ渡すだけで、**パート同士の重なりも包含も見ていなかった**——単体で有効な正方形
2 つを一部重ねれば `valid:true` が返った（OGC の妥当性は構成要素の内部が重ならないことも要求する）。

⇒ **座標・環 → 1 パート内 → パート間**の 3 段に分け、第 3 段だけが `MultiPolygon` の枝から呼ばれる
（走査も判定も二重に持たない）。理由コードは 3 つ: `parts-overlap` / `part-inside-part` /
`part-duplicates-part`。

- 判定は ⑴ 外接矩形の掃引で足切り ⑵ **横断的**な交差（「触れたか」は別の問いなので分ける。接触が
  通過と読まれない） ⑶ 走査線で求めた**内部の点**（⚠ 頂点は境界上なので判定できない——外接した
  菱形が実測で無検出だった） ⑷ 方向は包含判定で、**相手の穴が自分の中にあるなら包含ではない**。
- `repair()` はパート間の問題を `union` で解決し、`resolved-part-overlap` などを `changes` に残す。
  ⚠ 直せないときは `remaining` が述べる（黙って `valid` を返さない）。
- ⚠⚠⚠ **「既存の正常データを落第させていないか」は、実測では逆だった。**
  `data/ecoregions_2017.geojson`（635 MultiPolygon / 87,783 パート）のうち **126 件が本当に
  パート間の欠陥を持ち**、独立した sweep-line（Martinez–Rueda）が **568/568 を裏付けた**
  ——交差面積が小さいパートの面積と完全に一致した＝同じ地面が二度入っている。
  ⇒ 不変条件は件数ではなく**別の engine との一致**にした（誤検出 0・見落とし 0・分類の不一致 1）。
  ⚠ 追った 2 件の不一致は**閾値ではなく判定**を直した（面積を持たないパートを比較から外す・
  包含に穴の条件を足す）。
- 性能: 全レコードの validate 218ms → 783ms（≈6.4µs/パート）。全対が重なる 400 パートでも 4ms。
- ⚠ **データセット全体の位相（地物同士の重なり・区域間の隙間）は今回やっていない。** 主題が違う
  ——それは**地物コレクション**の性質で、全地物と共有の精度モデル、そして**誰かが述べた許容幅**が要る
  （市区町村界の 1µm の隙間は書き出した float64 であって世界の穴ではない）。このカーネルの扉は幾何 1 つを
  取るので、ここで答えれば許容幅を発明することになる。

### 5.9.1 ⚠ 経度の枠を合わせる関数が、渡されたものの深さを決めつけていた

`alignTo` の `lonRange` は引数を「環の配列」と決めつけていたが、`boolOpR` / `unionR` / `bufferKmR` の
**3 経路が multi（パートの配列）を渡す**。⇒ 範囲が `null` になり、**1 周ずれた枠で書かれた 2 つの
図形の boolean が常に空**になっていた。⚠ 直したのは呼び手ごとの分岐ではなく**値に付けた規則**
（位置は数の配列、それ以外は何かの配列なので深さは値自身が答える）。
⚠ 実測: 120 地物 × 720 回答のうち動いたのは 15 件で、union は**面積が完全同一**（書き方だけ変わる）。
値が動いた buffer の 1 件は**旧値が幾何的に不可能**だった（周長 6,921km に 5km の縁で 63,867km²、
上限は 34,603km²）。
## 5.10 誤差は面と場所で桁が違う — 測って申告する（#R783）

⚠⚠⚠ **操作ごとの計算面は宣言されていたが、誤差範囲は誰も測っていなかった。** 実測（地面＝WGS 84 に
対する相対誤差）:

| 条件 | 面 | 面積の誤差 | 長さの誤差 |
|---|---|---|---|
| 35°N の 1° 方形 | EPSG:3857 | **+51.2%** | +23.3% |
| 60°N の 1° 方形 | EPSG:3857 | **+311%** | +103% |
| 84°N の 1° 方形 | EPSG:3857 | **+10744%** | +943% |
| ゾーン 2 つ外 | UTM 54N | **+19408%** | +2326% |
| 35°N の 1° 方形 | 球面（既定） | 0.0039% | 0.22% |
| 35°N の 1° 方形 | UTM 54N | 0.033% | 0.016% |

- ⚠ **`areaScale` はその面自身の台（datum）に対する比**で、4 面のうち 2 面は球面の上に描かれている。
  誰も測っていなかった台の項は、アプリの球面で赤道 **+0.449%** / 60°N **−0.577%** / 84°N **−0.881%**。
- ⚠ **`exact: true` は「その面の台に対して」の主張だった。** Mollweide は自分の球面上で厳密な等積だが、
  地面に対しては台の項ぶん外れ、長さは **2.9〜113%** 外れる。
- ⚠ **長さの誤差の主項は投影ではなく辺の規則**（頂点間を平面上の直線で結ぶ）で、Tissot の数値には
  原理的に見えない。⚠ **球面の面積と球面の長さは、同じ辺を別の曲線として読んでいる**
  （面積は (λ, sinφ) の台形、長さは大円）——60°N で 1,000km 辺の三角形は **3.3%**、5,000km 辺で
  **5.1%** 食い違う。⇒ 辺の規則は**面ごとではなく測る量ごと**に持たせた。
- `certify(surface, data, opts)` が `bound`（投影の Tissot × 台の比）/ `checked`（独立参照との実測）/
  `within` / `worst` / `blocked` / `verified` を返す。参照は WGS 84 の閉形式と Vincenty 逆解で、
  **測る対象の外にある**（テスト側の Gauss–Legendre 重積分と子午線弧の求積が反証できることも測った）。
- ⚠ **`tolerance` は呼び出し元が述べる要求**で、満たせないときは**数を出さず**
  `crs-accuracy-outside-tolerance` と**満たせる面の一覧**を返す。⚠ これは上限ではなく**経路**である
  （`CONSTITUTION.md` §5）。述べなければ何も拒まない。
- 数を作らない条件: 日付変更線を跨ぐ環（`crs-plane-seam-crossed`。外接矩形では見えないので**データの
  辺**に訊く）／ほぼ対蹠の区間（Vincenty が収束しない＝`crs-reference-unavailable`。「確認できなかった」を
  「一致した」にしない）／面積の図形が無い点（理由の無い false を作らない）。
- ⚠ **`bound` は保守的な区間積**なので、実際より厳しく拒むことがある（767km の UTM で実誤差 4e-5 に
  対し bound 1.2e-3）。同位置での同時評価は次の回の仕事。
## 6. どこまでやるか・何をやらないか（現時点）

- **⚠ #R759 まで、Worker には呼び出し元が 1 つも無かった。** `run` / `register` / `probe` を呼ぶコードは
  `js/` にも `tests/` にも**0 件**で、登録ジョブは 1 本、その 1 本も誰も走らせていなかった。
  ⇒ **いま `rasterDiff` の画素ループは別スレッドで走る**（`js/gis-ops.js` が口を渡し、
  `js/gis-raster.js` の `diff()` が使えるときだけ使う）。⚠ **算術の実装は 1 本**——ジョブ関数が
  画素ごとの規則を持ち、**主スレッドの腕も同じ関数を呼ぶ**（2 つの綴りは 2 つの答えになる）。
  結果は `transferable` で戻り、複製を作らない。⚠ **中止は走行中の算術に届く**（実測: 400 万画素の
  うち報告できたのは 1.6% で、閉じの進捗は来ない＝殺されている）。⚠ **使えなかったことは結果に
  書かれる**（`worker: {used:false, reason}` ／ op の `stats.worker`）——成功した実行の診断なので
  `why` ではない（`why` は拒否のコード）。
- **⚠⚠⚠ (#R783) カーネルの関数そのものを運ぶ扉ができた。** `provide(name, fn)` が `fn.toString()` を
  Blob の中で `LIBS["name"]` に組み、ジョブは `ctx.lib.<name>` で呼ぶ。⚠ **自由名にしない**のが要点
  ——自由名は `check-split-scope` が正しく落とし、Worker の中では intrinsic の遮蔽が観測できない。
  `register(…, {uses:[…]})` が参照先を宣言し、未提供なら**登録の時点で** `job-library-missing`
  （4096² の 1 画素目で TypeError にしない）。⚠ これは「規則をジョブの中に書き写す」道ではない
  ——**第二の実装を作らない**ための扉である。
- **実際に移した演算: `warp.geometry`。** 出力画素中心の逆アフィン写像と areal のフットプリント箱が
  別スレッドで走る。⚠ **実装は 1 本**（`invAt` / `boxOf`）で、主スレッドの腕も同じ関数を呼ぶ。
  ⚠ **標本抽出は移していない。** 規則の持ち主は `js/gis-raster.js` で、`window` を読み、
  `read(bandIndex)` は復号し得る——「nearest は索引参照だけ」と書けば void 規則・端クランプ・
  sentinel 判定が 2 か所になる。投影された格子も移せない（画素ごとに proj4 が要る）ので
  `crs-not-in-worker` を述べて**その場で完走する**（分割・非分割・扉却下の 3 つがバイト一致であることを
  検査が測る）。
- **⚠ 上限は件数ではなくメモリ予算である。** `BLOCK_BUDGET_BYTES` = 64 MiB
  （**観測**: 4096² の float64 が 1 面 128 MiB で、呼び出し側と二重に常駐する。**失効条件**:
  SharedArrayBuffer 化、またはタブの上限を測り直したとき。**正本**: この定数と `budgetBytes()`）。
  `planBlocks({units, bytesPerUnit, budgetBytes, inFlight})` が**在空中の全部**に対する天井として割り、
  4 並列は「4 倍の常駐」ではなく「1/4 のブロック」になる。⚠ **全単位は走る**——ブロック数が増えるだけで、
  打ち切りではない。1 単位が入らなければ `budget-too-small` と述べる（無言の超過にしない）。
  実測（37×29・nearest・1 行 592 B）: 予算 1 MiB → 1 ブロック／4,736 B → 4 ブロック・ピーク 4,736 B／
  592 B → 29 ブロック・ピーク 592 B。
- ⚠ **この実装中に見つけた欠陥**: `runBlocks` が `take` を await していなかったので、非同期の消費者を
  持つ呼び手では 29 ブロックが同時に在空し、**読者の中止が落ち、ピークが格子全体になっていた**
  （同期の呼び手からは見えない）。中止は走行中の算術に届くことを実測で確認した
  （2000×2000 を 1 ブロックにして progress の瞬間に abort → 完了画素は 400 万未満）。
- **まだ運べないもの: `combine` と `rasterCalc`。** `fn` はクロージャ（`js/gis-expr.js` の compile 済みで
  AST と数値規則を閉じ込めている）で、Worker は `fn.toString()` を評価するので
  `job-not-self-contained` になる。⚠ **運べるようにする道は在る**（AST は JSON なので、評価器そのものを
  ジョブの本文にして `{ast, rule}` を渡す。`provide()` ＋ `uses` がその扉）——`mask` / `merge` / `zonal` と
  一緒に次の回の主題。⚠ **近傍依存（バッファ・近傍検索・和集合の縫い直し）は未着手**で、今回分割したのは
  「出力画素ごとに独立な位置計算」だけ。⚠ 出力格子そのものはひとまとめに確保する（予算で割れるのは
  幾何だけ。ブロックを受け取る消費者 API は `to4326`/`resample` の契約変更になる）。
- **幾何の runner（sweep line そのもの）はまだ載っていない。** `js/gis-worker.js`（`IntMapGisWorker`）が
  **純粋な算術**——数値配列の上の画素ループ——をメインスレッドの外へ運ぶ。⚠ §2.6 の yield の
  **代わりではなく隣**である: あちらが足すのは応答性、こちらが足すのは**並列性**。⚠ 幾何の runner は
  今も 1 本の thread で走る。そこが呼ぶもの（sweep line・レジストリ・測地）が全部この thread に在り、
  ループだけ動かせば呼び出しが全部残されるから——**半分だけ移した移植**を作らないための線引きである。
  ⚠ **`available()`（能力）と `probe()`（実測）は別の問い**: CSP が `blob:` を拒むことは throw では
  なく error イベントで出るので、同期では原理的に答えられない。
- **分割読み込みは格子にはあり、地物にはまだ無い。** GeoTIFF は **`{size, read(offset,length)}` と
  いう 1 つの契約**でバイトを取り、HTTP Range の供給元と全バイトの供給元が同じ画素を返す（§1.4a）。
  窓を覆う tile／strip だけを読み、overviews から**要求を満たす最も粗い段**を選べる。⚠ 一方
  `features()` は今も**保持している配列を返す**（扉が 1 つ、という意味であってストリーミングでは
  ない）。⇒ 地物の大きさは、いまも「メモリに載るか」で決まる。
- **格子の再標本化は 6 方式**（§1.4b）。nearest・bilinear・cubic が**点**を訊き、average・sum・mode は
  出力画素が**覆う範囲**を集約する。⚠ その違いは `kind:'point'|'areal'` として**宣言されて**おり、
  areal の方式は footprint を要求する（無ければ `sample-cell-not-stated` で断る）。⚠ `sum` は
  **総量を保つ**ので average とは別の実装である（人口を平均すると人が消える）。一覧は
  `IntMapGisRaster.sampleMethods()` が母集合。
- **解析用の座標系は選べる。ただし選ぶのは読者で、格納は動かない。** データセットの `crs` は
  **今も常に `EPSG:4326`**（下流の全部が lng/lat 度を前提にしているので、ここは動かさない）。動いた
  のは**測る面**のほう: `measure` op が `crs` を取り、`js/gis-crs.js` の `projection()` が作る面
  （UTM 60 帯・Web メルカトル・Mollweide・正距方位）の上で面積と長さを測る。⚠ **歪みが同じ行に
  載る**（`…ScaleMin` / `…ScaleMax`）——60°N の Web メルカトルの面積は真値の 4 倍で、註の無いその数は
  この記録が繰り返し捕まえている形そのものだから。⚠ **自動では選ばない**: `suggest()` は並べるだけで、
  `assess()` は「何度はみ出したか」を返す。
- **GeoTIFF は #R756 で BigTIFF・PlanarConfiguration 2・predictor 3 を読むようになった。**
  ⚠ **分岐を足したのではない**——BigTIFF は offset 幅・IFD の項目数・項目長が違うだけなので、
  その 4 つを読み取り器の引数にした（同じ 1 本の walk が両方の容器を読む）。predictor 3 は
  **バイト平面を分けてから差分を取る**ので、整数の predictor 2 の一般化ではなく別の算法である。
  **読まないものは今も名前を付けて断る**: JPEG-in-TIFF・**8 バイト以外の offset 幅を述べる BigTIFF**・
  登録名つきのその他の圧縮・8 の倍数でない bit 深度・**地理参照の無い TIFF**（§1.4a）。
  ⚠ JPEG-in-TIFF が残るのは手抜きではない: 量子化表とハフマン表がタグ 347 に分離され、
  プラットフォームの復号器は 8bit sRGB を返す——**この扉が運ぶ標本ではない**。⚠ 範囲取得に
  対応していないサーバも同じ——黙って全体を落とさず `range-unsupported` で断り、全体取得でよいと
  読者が述べたときだけそうする（そのときは答えが `wholeFile` と述べる）。
- **供給元の `completeness` が `all` になるのは、その行が自分でそう述べたときだけ**（§5.5・§5.6）。
  #R756 で `heritage` と `volcanoes` が述べるようになり、**取り込んだファイル以外で初めて `all` が
  到達可能**になった。⚠ **(#R763) それが「点けてから」でなくなった**——`load()` を述べる 3 行
  （`heritage`・`volcanoes`・`pharma`）は**一度も描かれていなくても**読める。残りの行が今も読めない
  のは宣言が足りないからではなく、**上流の実態がカメラ矩形や件数上限を持つから**である（#R759 の実測）。
### ⚠⚠⚠ (#R783) 「宣言を足せば取れる」ではない — 航空を実測した

`aircraft` は #R783 で**窓を指定した取得口**を持った（`acquire(req)` は `req.bbox` を使い、
**カメラを 1 度も読まない**）。本番の `aviation-feed` を 4 窓で叩いた実測:

| 窓 | 件数 | 箱の外 | 上流の被覆 |
|---|---|---|---|
| 日本 128,30,146,40 | 605 | **0** | `lattice 856/980` |
| 西欧 −10,40,10,55 | 2,661 | **0** | 同 |
| 米 −125,30,−70,50 | 6,111 | **0** | 同 |
| 世界 | 15,116 | **0** | 同 |

**取れるもの**: 窓（上流が本当に実行する。箱の外 0 件・日本と西欧の交わり 0 件）／安定 ID＝ICAO の
24bit hex（重複ゼロ）／機体ごとの観測時刻／答えの組立時刻／出典。
**取れないもの**: **全件性**（980 格子タイルのうち 856 しか一度も訊かれていない＝124 は未知の空）／
ページングと `cursor`／`where`・`fields`／過去の時点（now 専用）。

⇒ ⚠ **`complete` は定数ではなく上流の文である。** `readReach()` の戻りで、`lattice p/t` の `p<t` は
`false`、**`p===t` でも `null`**（一度訊いた空 ≠ いま保持する空）。結果 `completeness` は `partial` に
固定され、**`all` には到達できない**。`resolution` に `lattice 856/980` をそのまま載せて読者に見せる。
⚠ `where` / `cursor` / `fields` は**申告しない**＝名指しで拒否する（持っていない能力を宣言しない）。
⚠ **同じ窓を 2 回訊くと ID 集合は時間で変わる**（実測 604 → 611・削除 0）。カメラでは変わらない
——それが完了条件で、時刻で変わることは実データの性質であり `asOf` と `resolution` がそう述べる。

⚠ **束（layer-packs）の 3 分岐は表になった。** 束が自分で `id` / `row` / `label` / `source` / `holds` /
`get` を名乗り、汎用ループが回る——**新しい束は登録するだけで取得可能になる**（一覧を手書きしない）。
⚠ そして `acquireBundle()` は**必ず決着する**: 旧分岐は `if(!M||!M.features) return;` で callback を
呼ばず、`js/map-ui.js` の promise が**永久に pending** だった（拒否でもエラーでもなく、無言）。

⚠ 実測の副産物: `js/aviation-model.js` は worker からしか import されておらず、**メインスレッドに
`window.IntMapAviationModel` は存在しなかった**（worker の module graph は別物——#R341 が codec で
踏んだ罠の後半）。
⚠ 残りの行は今も `partial` で、それは欠陥ではなく**アプリの真の状態**である
  ——カメラ矩形で取る行（`aircraft`・`ships`）は `viewBound:true` と述べ、何も述べていない行は
  `extent-undeclared` のままにする（「知らない」を「全部だ」の代わりにしない）。
- **`js/gis-geopackage.js` は #R783 で書き手を持った。** ベクタ 1 レイヤーを書き出す（`write`）。
  ⚠ tiles も曲線幾何も今も扱わない（どれも名前を付けて断る）。WAL の残ったファイルも、サイドカーが
  手元に無いので断る。⚠ **b-tree は平衡させずに構築する**——行は rowid 昇順で一度だけ書かれ、挿入経路が
  存在しないので葉を前から詰めて interior を下から積むだけでよい。⚠ **標準が含意する auto-index 4 本を
  実際に建てる**（宣言だけして索引を建てないファイルは `integrity_check` が落ちる壊れた DB である）。
- **出口は #R756 でできた**（`js/gis-export.js`）。ベクタは GeoJSON と CSV、ラスタは GeoTIFF
  （無圧縮）。⚠ **「書き出せた」は「読み直せた」ではない**ので、3 形式とも既存の読み手
  （`js/geo-import.js`・`js/gis-geotiff.js`）が読み返し、**許容幅 0** で一致を測る。
  ⚠ **画素が一致しても場所が違えば別のデータ**なので grid の west/north/pixel も測る。
  ⚠ **持っていない出典を主張しない**——述べていないデータセットには欄自体を作らない。
  ⚠ CSV は**形式に出典の欄が無い**ので運ばず、運べなかったことを画面が述べる。
  ⚠⚠⚠ **#R783 まで、この節の「読み返した」は自前の読み手だけだった。** 同じ前提を共有した 2 つは
  互いを反証できない（[[intmap-co-designed-reader-cannot-falsify]]）。⇒ **第三者の実装に訊く**
  ——`python -m pip install rasterio pyogrio rio-cogeo` で **GDAL 3.12.4** が wheel ごと入り、以後
  ネットワークは要らない（`gdalinfo` はこのマシンに無い）。`sqlite3` は python の標準ライブラリなので、
  **素の python だけのマシンでも b-tree・索引・overflow 鎖の健全性は第三者が検証する**。
  ⚠ **読み手が無い環境では `skip` にしない**——`UNVERIFIED` を理由つきで印字し、
  `INTMAP_REQUIRE_THIRD_PARTY=1` では赤にする（「確認できなかった」を「成功」と同じ答えにしない）。
  ⚠ **第三者は必要な証人だが十分な証人ではない**: 初版の COG は IFD 0 に nodata の tag を 2 回
  書いていて、**GDAL も `cog_validate` も両方それを受理した**（先頭一致を取る）。捕まえたのは
  独立に書いた IFD walker で、修正は呼び手ではなく `assembleTiff` 自身に「1 IFD に 1 tag」を拒ませた。
- **#R783 で足した出力: COG とベクタ GeoPackage。** COG は 512×512 タイル・内部 overview・
  IFD が全部画素より前・overview 画素が先。⚠ **「圧縮した GeoTIFF」を COG と名乗らない**ので、
  名乗れる根拠は自分の表ではなく外の判定（`rio_cogeo.cog_validate` が `(True,[],[])`・GDAL の
  `LAYOUT=COG`）と、**同じ writer の strip GeoTIFF を同じ検査器が落とすこと**（参照が反対を
  言えることの測定）。⚠ ghost area は **BLOCK_LEADER / BLOCK_TRAILER を実装したうえで**宣言する。
  ⚠ **GeoParquet は入れていない**——thrift のメタデータ・符号化・圧縮を 1 から書くのは上の 2 つと
  同規模で、部分実装を「対応した」と名乗らない（`AGENTS.md` §3 の 3）。
- **中止は #R756 でラスタの画素ループの内側まで届いた。** それまで `js/gis-warp.js` の行ごとの
  `ctx.tick` は **#R749 以来 1 度も評価されていなかった**（`ctx:` を渡す呼び出しが `js/` に 0 件）。

  **いつスレッドを手放すかだけ**を変える。⚠ 刻みは**時間**（1 フレーム）であって件数ではない。
