### 7.1 気象・災害警報

**「どこで／何が／どれほど危険か／情報は新鮮か」の4つに答える**（`js/world-packs.js`）。
**その機関が発令した単位で塗る。** 世界の事象フィード（GDACS）は**完全に撤廃されている**——
コードは1行も残っておらず、`tests/r273-checks.test.mjs` が**書かれていた構文**で不在を確認する。
撤廃したからこそ、**未対応国を「静かな国」に見せない**仕組みが要る（下の3状態）。

自前フィードは **13本**（下表の 12 か国 ＋ MeteoAlarm）で、MeteoAlarm が EUMETNET の残り 35 か国を運ぶ。
合計 **47 か国**。**その外側は WMO の CAP 登録簿（SWIC）**が運ぶ——下表の最終行。
さらに、**その機関の管轄がその機関の国境と一致しない**分（`ALSO`）が 8 か国・地域ある——下表の最終行の一つ上。
実測、対応 **148 か国・地域**（対応外 252 → 104）。

- ⚠⚠⚠ **「発令された」は「発令中」ではない。**（#R383）CAP の有効期間（`onset`/`effective` ≦ 現在 ≦ `expires`）
  の外にあるものは**塗らない**。判定は relay の `forceState()` 1本で、MeteoAlarm・PAGASA・CAP 索引の
  3つの要約器すべてがこれを呼ぶ（WMO 登録簿は CAP の `<info>` ではなく WFS の行なので自前の
  `expires` 判定を持つ）。⚠ **判定は fail-open**——`expires` も `onset` も無い電文は落とさない
  （時計を出さなくなったフィードが地図を黙って空にしてはならない。実測、34 加盟国で `noExpires` は 0）。
  ⚠ **黙って切らない**——`expired` / `upcoming` / `upcomingAreas` が要約と一緒に返り、
  国別の凡例が言葉で印字する（`notInForceLine`）。
  実測（feeds.meteoalarm.org・到達できた 34 加盟国・同一分）: 緑以外の電文 **2,990 件のうち
  2,546 件が期限切れ・327 件が未発効・発令中は 117 件**。区域では **1,158 → 183（過剰塗り 84.2%）**
  ——オーストリア 116→0（全件が 5 日前に失効した雷雨警報）・ポーランド 319→1・スイス 107→0・
  チェコ 25→0・ギリシャ 16→0・フランス 96→15・スペイン 147→37。同じ分の本番実測では、この地図が
  世界中で塗っていた **1,811 区域のうち 1,015 がそのヨーロッパの区域**だった。
  ⚠ MeteoAlarm の `feeds-<country>` は**その機関が発令した記録の流れ**であって、発令中の一覧ではない。
- ⚠⚠⚠ **米国の警報は、その 96.9% が「形を持たない発表」だった。**（#R383）
  実測 `api.weather.gov/alerts/active`: **発令中 127 件のうち幾何を持つのは 4 件**。残る 123 件は
  UGC の予報区コードで発令され `geometry: null` で配信される（Extreme Heat Warning 6・Heat Advisory 14・
  Gale Warning 11・Air Quality Alert 9・Small Craft Advisory 68・Red Flag Warning 1 ほか）。
  同じ分の本番実測 `PLACED.USA = [11, 135]`。#R302 はこれを 201/281（71.5%）で測って
  「置けなかった」と数えるところまでを直し、割合はその後 96.9% まで上がっていた。
  → **形は NOAA 自身が公開している予報区レイヤーから引く**（`nws_reference_map`：8 公共予報区 4,080・
  9 火災気象予報区 3,603・5 沿岸海域 569・6 沖合 130・2 郡 3,284）。**索引であって第2の意見ではない**
  ——Eurostat NUTS・国土数値情報・DataV と同じ扱いで、**何が発令されているか・階級・文言は
  `api.weather.gov` のみ**が決める。実測（**出荷コードそのものを実サービスに当てて**）、発令中の **339 の予報区コードが 339/339 解決**——4.0 秒・幾何 572,659 B・32,078 頂点。
  ⚠ **種別が鍵の一部**——火災予報区と公共予報区は UGC の名前空間を共有する（どちらも `state_zone='AK317'`）
  ので、`/zones/fire/` と `/zones/forecast/` を区別しない索引は Red Flag Warning に公共予報区の輪郭を渡す。
  ⚠ **簡略化は宣言する**——`maxAllowableOffset` 0.004°（≈440 m、この地図自身の世界 ADM1 索引 0.01° より細かい）。
  実測、116 区域で **1,099,442 B → 80,503 B**。
  ⚠ **答えは保存する**——予報区の境界は年 2 回程度しか改定されないので、他の境界集合と同じく
  Cache Storage に置く（`intmap-nwszone-v1`・180 日）。
  ⚠ **素の `geocode.UGC` は代替であって2つ目の登録ではない**——火災気象の電文は同じ区域を
  `affectedZones` と `geocode.UGC` の**両方**で名乗るので、UGC を無条件に足すと `f:` の隣に `z:` の鍵ができ、
  **同じ地面を2度主張**する（実測、110 件中 10 件が「登録簿に無い区域」として現れていた）。
  ⚠ **冷えた索引は駆ける**（#R284 と同じ形）——1 バッチ 110 に対し発令中の区域は実測 339 なので、
  ティック待ちにすると米国が描き終わるまで数分かかる。バッチは**連鎖**し、待つのは**失敗した掃引だけ**。
- ⚠⚠⚠ **CAP の 1 ファイルは 1 件の警報ではなく、`<info>` ブロックごとの 1 件である。**（#R383）
  `xmlOne(cap,'event')` は文書中の**最初の** `<event>` で、`xmlAll(cap,'area')` は**全部の** `<area>`
  ——つまり 2 つ目以降の帯に属する区域まで**最初の帯の階級と有効期間**で塗っていた。実測（台湾・降雨）:
  **286 区域が全部「紅色/Extreme」**。`<info>` ごとに読むと **紅色 125・橙色 108・黃色 53** で、これが
  中央氣象署の発表そのもの。⚠ 多言語の電文では**同じ区域が言語ごとに 2 回**数えられていた
  （`areaTotal` 694 → 386）。→ **同一言語の `<info>` を単位に読む**。
- ⚠⚠⚠ **集約フィードは 1 つの機関ではない。**（#R383）NCDR が返した電文の発令者は実測で
  **農業部農村發展及水土保持署 ×31・中央氣象署 ×17・交通部公路局 ×10・高雄市政府 ×1** の 4 者で、
  そのすべてに「CWA (Taiwan)」という出典が付いていた（#R352 と同じ欠陥——**間違った出典を名乗るのは、
  名乗らないより悪い**）。水土保持署は台湾の**土石流警戒の正規の発表機関**なのでここに属するが、
  公路局の**道路封閉**と高雄市の**開放臨時停車**は警報への「対応」であって警報ではない
  （実測、道路封閉は `Extreme` で塗られ、開放臨時停車は `<areaDesc>` が**小学校名**の区域を 45 件作っていた）。
  → **CAP 自身の語彙で決める**: `<category>` が `Met`/`Geo`/`Fire`/`Env`/`Health` でなければ警報ではなく
  （実測 Geo 253・Met 59・**Transport 15**）、`severity: Unknown`＝**発令者が階級を付けなかった**ものは
  色にできない（実測 1 件）。⚠ **どちらも件数が要約に載る**（`notHazard` / `ungraded` / `senders`）ので、
  絞り込みは黙って行われない。出典名は集約体を名乗り、**行ごとに実際の発令機関**（`by`）が付く。
- ⚠⚠ **鮮度の計器は「機関の時計」を読む。**（#R383）#R269 が `FEED_AT` を作った理由は
  「止まったフィードは、失敗したフィードではない」であるのに、MeteoAlarm と WMO 登録簿には
  **relay がフィードを読んだ時刻（`fetchedAt`）**が渡っていた＝常に「いま」。本番実測
  `feedAgeH.meteoalarm = 0`、その裏でルクセンブルクは 104 時間・ベルギー 94 時間・英国 82 時間・
  キプロス 78 時間・アイルランド 66 時間なにも発表していなかった。→ relay が `newest`
  （その加盟国の CAP `sent` の最大）を返し、`seenAt` はそれだけを読む。
- ⚠⚠⚠ **「いつ答えたか」と「いつ訊いたか」は別の時計である。** MeteoAlarm と WMO 登録簿は**年齢順の
  輪番**で回り、その年齢（`maAt` / `swicAt`）は**読み取りが成功したときだけ**書かれる——パネルが出す
  「データの古さ」だからで、楽観的に書けば停滞が隠れる。⚠ **同じ時計に「もう一度訊く時か」を答え
  させてはならない**。一度も答えていない国には時計が無いので、取得が失敗すると何も動かず、
  バッチ自身の終了処理が呼ぶ次の pump が**同じ国**を返し、同じように失敗する——**輪はマイクロタスクの
  速さで回り、`.catch` はどれも `showPanel()` で終わるので1周ごとにパネル再描画と全凡例の再配置が付く**。
  リレー障害・429・圏外の携帯で、接続が悪いほど速く回る。
  → **試行の時計を別に持つ**（バッチを発行したときに書く）。失敗が続くあいだ **2 → 6 → 20 → 60 秒**と
  後退し、答えた瞬間に消える。障害の費用は「国あたり・後退の段あたり1回」。
  ⚠ 併せて、レイヤーのパネルは**同じ本文・同じレイヤー id・同じ名前なら、不透明度の再登録と
  凡例カラムの再配置（`tileLegends()`）を飛ばす**（`makePanel` の `open`）——再描画1回は再配置**2回**だった。
  ⚠ **本文の書き直しは飛ばさない**: `wireControls` は `addEventListener` で付けるので、同じノードを
  返すと自動再描画のたびにリスナーが積み上がる。
- ⚠⚠ **黙って切った一覧は、完全な一覧に見える。**（#R383・#R320）relay の `AREA_CAP` は区域一覧を
  400 件で切るのに、アプリは分母に `areas.length`（＝切った後）を数えていた。実測、台湾は
  `areaTotal` 694 に対して読み手には「286 / 400」と印字されていた。→ 分母は `areaTotal`。
- ⚠⚠ **ドイツの Bundesland のために、毎回もう1本 HTTP を投げていた。**（#R383）`loadDWD` は WFS と
  並行して `dwd.de/DWD/warnungen/warnapp/json/warnings.json` を取り、`st[p.WARNCELLID]` で引いていた。
  実測、WFS の項目名は **`GC_WARNCELLID`** で、素の `WARNCELLID` を持つ地物は 1 つも無い
  ——つまり毎行 `st['undefined']` で、州は一度も解決せず、タップカードは郡名を 2 回印字していた。
  同じ応答が **`GC_STATE`** を持っている。→ 1 応答・1 真実・**10 秒ごとの 1 リクエストが消えた**。
- **状態は3つで、見え方も3つ。**
  ⑴ **この地図がここについて何も述べていない**＝**灰色斜線**（`fill-pattern`・`wp-alert-hatch`。
  `washTier` = 0）。フィードが無い国と、フィードはあるが**まだ読めていない／読めなかった**国の両方。
  ⑵ **読んだうえで何も出ていない**＝**灰色**（国 1 枚のときは `QUIET_COL`／単位で描くときは `NONE_COL`）、
  ⑶ **発令中**＝その階級の色。
  ⚠⚠⚠ **斜線のタイルは<b>線だけ</b>で、下に灰色を敷かない。** タイルは `clearRect` から始まり、
  線が信号のすべてを運ぶ（かつては `fillRect` で灰色を敷いてから斜線を引いていたので、
  ⑴ が「灰色＋斜線」・⑵ が「灰色」になり、**斜線の国は静かな国の見え方を下に着ていた**）。
  2つの主張は**見た目として排他**でなければならない。
  ⚠⚠ **その線は<b>縁取りを持つ</b>**（`hatchCanvas()`：薄色の太い線を先に、濃い線をその上に）。
  単色の中間灰色は明るい基図では読めても、衛星画像とダークテーマではほとんど見えない。
  縁取りは線に付くだけなので**隙間は完全に透明のまま**——`tests/r293 ②` が被覆率を計算する。
  ⚠⚠ **凡例の見本はこのタイルそのもの**（`hatchSwatch()` が `toDataURL()` を読む）。
  「斜線塗がなんなのか分かるように、凡例に追加しろ」に対する行は**両モードの凡例に**あり、
  手書きの `repeating-linear-gradient` は**1つも残っていない**（かつては数値の違う2つがあった）。
  灰色（`NONE_COL` / `QUIET_COL`）は**白に少し近づけてある**——読み手の指定による。
  **「警報なし」と「データなし」は別**であり、**どちらの沈黙なのか**（未対応／順番待ち／取得不可）は
  タップした地点のカードが**言葉で**言う（見本は地図と同じ斜線）。
  パネルの `unread` は**0 に落ちなければならない数**である（実測、レイヤー投入から 80 秒で 29 → 3）。
  ⚠ この 3 状態は #R284 の 4 状態（未読＝何も描かない、`washTier` = −1）を**置き換えている**。
  −1 は「対応国まで斜線で塗るな」への答えだったが、読み手が同じ文の中で
  「まだ対応していない、**もしくはデータがまだ入っていない**ところは灰色斜線で」と指定した。
  #R284 が同時に入れた**冷たい輪番のバースト**（`COLD_CALLS`）があるので、斜線を着ている時間は
  1 分に満たない——「対応地域まで斜線で塗るな」は、**データが入った国は決して斜線にならない**という
  形で今も成り立っている。
- ⚠⚠⚠ **斜線は、この層が答えを描いている地面の上には<b>決して</b>出ない。**（#R308）
  「発令されている・されてない地域にまで斜線かけるな」——「情報あるのに、そこに斜線が上塗りされてる
  ところ」。塗り順の問題ではない（斜線は #R277 以来ちゃんと単位の**下**にある）。原因は、**斜線を描く
  索引と答えを描く索引が同じ分割ではない**こと——`countries` は飛び地と係争地を**それぞれ独立した
  ポリゴン**として持ち、単位の索引（NUTS・admin-1・気象機関自身の予報区）はそれらを刳り抜いていない。
  だから「配信元の無い国」の輪郭が、隣国が答えている地面の上に重なる。そして単位の塗りは半透明
  （0.38）なので、**下にある斜線はそのまま透けて見える**。本番実測（`queryRenderedFeatures`・
  キャンバス 880×720・12 px 格子・斜線が塗られている点のうち同じ点に発令中／発表なしの単位があるもの）:

  | 地点 | z | 斜線の点 | うち答えの上 | 何が何の上に |
  |---|---:|---:|---:|---|
  | リヒテンシュタイン | 9 | 87 | **87 (100 %)** | LIE × CHE 発令中 |
  | 北キプロス | 8 | 447 | **420 (94 %)** | 北キプロス × CYP 発表なし |
  | マカオ | 10 | 43 | **43 (100 %)** | MAC × CHN 発令中／発表なし |
  | ソマリランド | 6 | 838 | **791 (94 %)** | ソマリランド × SOM 発表なし |
  | カシミール | 6 | 1,598 | **532** | PAK の輪郭 × IND 発表なし |
  | コソボ | 7 | 1,147 | **375** | コソボ × SRB 発令中 |
  | モナコ | 10 | 45 | **38** | MCO × FRA 発令中 |
  | サンマリノ | 9 | 35 | **12** | SMR × ITA 発令中 |

  → **#R307 が灰色のために書いた引き算を、そのまま斜線に使う**（`rebuildHatchCut` → `_cutOne` →
  `subtractWarnings`）: **斜線 ＝ 国 − ∪(この層が単位で答えている地面)**。1つの式が3つの答えを出す
  ——地面ぜんぶが答えられていれば斜線は消え、一部なら残りだけが斜線になり、重なりが無ければ何も
  変わらない。切り取れた国は `wp-alert-hatch-cut`（自前の GeoJSON ソース・**同じパターン画像**）へ移り、
  `wp-alert-hatch` のフィルタがその国を外す——**同じ地面が二度斜線になることはない**。
  ⚠ **引き算できなかったときは従来の斜線がそのまま残る**（クリッパ未着・頂点が天井超え）＝
  **機能が減る瞬間は無い**。
  ⚠ **段は3つあり、どれも「面」ではない。** 素直に書くと 1 回の再構築が **19,588 ms**（箱が重なる相手を
  全部クリッパへ）、内点で篩っても **16,263 ms**（環の長さが効くものは何であれ高い）——#R290 / #R297 で
  この層が払った費用の払い方そのもの。→ ⑴ **箱の比**で篩う（重なりが**小さいほうの箱の 4 割以上**：
  飛び地と係争地は必ず当たり、ただ隣り合う国は当たらない）⑵ **1 publish あたり `CUT_BUDGET_MS` の予算**
  （使い切ったら残しておき、次の窓で続ける。答えは国ごとに `cutMemo` に残るので2回目以降は無料）
  ⑶ **減った面積が「割合<b>か</b>絶対面積」で足りていなければ「重なっていない」**（境界の薄片のために
  国の輪郭を GeoJSON へ移さない。⚠ 割合だけだと**パキスタンが落ちる**——国の 2 % に届かないが、
  そこは z6 で 519 点の上塗りである）。実測、収束後の再構築は **5〜19 ms**。
  ⚠⚠ **切るのは<b>画面の中の国だけ</b>で、その中では<b>輪郭の小さい順</b>。**（#R308 追記）
  最初の版は画面の中を「先に」やって残りを予算の続きに回した。MEASURED on production: リヒテン
  シュタインは直ったのに**コソボ 379・北キプロス 420 は一度も切られない**（`hatchCut.isos` が空のまま
  `more:true` で回り続ける）——本番では警報が絶えず届いて `shown` が変わるので、**予算を使い切るたびに
  最初からやり直し**になり、順番の後ろには永久に順番が来ない。ローカルは feed が落ち着くので収束して
  いた＝**本番でしか出ない**。→ 画面の外の国は**そもそも切らない**（`quietISOs` が単位を視野で区切るのと
  同じ理由・同じ境）。そして視野の中でも**頂点数の小さい順**に切る: MEASURED, z8 のキプロスでは視野に
  5 か国しかないのに 3 か国目で予算が尽きていた——トルコとシリアの輪郭は数千頂点、この round が切りたい
  北キプロスは数百である。**小さいものは同時に「まるごと他人の答えの上に乗っているもの」でもある**ので、
  安い順は defective 順でもある。
  ⚠⚠⚠ **鍵は視野そのものではなく「視野に入っている tier 0 の国の集合」である**（`zeroSeen`）。
  切る対象が視野で決まる以上、パンしても作り直されないと前の視野の答えが残る——だが**鍵を視野の矩形に
  すると、指が動かすどのパンでも必ず外れる**（0.25 度に丸めても細かすぎる）。外したあとに走るのは
  数千地物からの「答えている地面」の一覧・そこから作る 10 度の格子・視野の旗・頂点数での整列で、
  引き算だけが `cutMemo` で無料——そして出力署名が「変わっていない」と結果を捨てる。
  切った結果は `sig` と tier 0 の集合と**どの tier 0 の国が視野にいるか**の関数なので、**同じ国の集合の
  中で動くかぎり出力は 1 地物も変わりえない**。だから鍵はその集合を名指し、そのために必要な視野の旗は
  早期 return の**前**で数える（数え直すと、鍵が指すものと実際に回すものが 2 か所で決まることになる）。
  ⚠ **1 国ぶんの頂点の天井（`CUT_ONE_V`）は 20,000。** 12,000 まで下げたら**カシミールが落ちた**
  （パキスタンの輪郭＋8 単位で 18,971 頂点で、そこは z6 で 519 点の上塗りである）——1 回が長いことの
  対処は予算と安い順であって、係争地を天井の外に置くことではない。⚠ **残差は中国側**（実測、カシミール
  z6 で上塗り **532 → 249**、残る 249 は `CHN OVER IND/Q`。中国の輪郭は 54,752 頂点で天井の外にある。
  ⚠ そもそも中国が斜線になるのは CMA の取得が失敗している間だけである）。
- ⚠⚠⚠ **自分の単位を描いている国は、斜線にならない。**（#R308 追記2）本番実測（カシミール z6）:
  上塗り **525 点のうち 276 点が `CHN OVER CHN/W`**——**中国の斜線が、中国自身の発令中の区域の上に
  乗っていた**。CMA の取得が一度失敗すると `readState` が `ok` でなくなって `washTier` が 0（斜線）を
  返す一方、**直前まで読めていた警報は描かれ続ける**からである。引き算はこれを直さない——候補から
  **同じ国の地物を除いている**（他人の答えの上に乗る場合だけを見ている）。そして中国の輪郭は 54,752 頂点で
  `CUT_ONE_V` の外にあるので、clipper では届かない。→ **その国自身の単位をいま描いているなら、この地図は
  述べている**ので斜線にはならない（`washTier` は 2＝透明を返す）。#R288 の言葉がそのまま根拠になる——
  「データが入った国は決して斜線にならない」。⚠ **灰色（1）は今も `ok` しか得られない**（#R277）——
  2 は透明であって「発表なし」の主張ではなく、取得が失敗していることはタップカードとパネルが言葉で言い続ける。
- ⚠⚠⚠ **「発令なし」は<b>区分単位</b>で決まる。** 発令中は #R271 から発令単位で描いていたのに、
  発令なしは**国ぜんぶを覆う 1 枚の灰色**だった——警報の出た郡の隣にある静かな郡が、国の他の部分と
  区別できない。主張は単位ごとに真なので、塗りも単位ごとにする。
- ⚠⚠⚠ **「発表なし」の表現は<b>1つだけ</b>である。** 単位の灰色は**発令中の区域と同じコレクション・
  同じレイヤー**（`wp-alert` / `wp-alert-fill`）の中の、`norm` が 0 の地物であり、色は `NONE_COL` 1つ、
  不透明度は**そのレイヤーの不透明度**＝**利用者のスライダー**である。国も特別扱いしない。
  ⚠ かつては 2 つあった: 日本だけが `quietFeature()` を通って `wp-alert` に入り（`NONE_COL`・スライダーに従う）、
  それ以外は**別ソース `wp-alert-quiet-src` / 別レイヤー `wp-alert-quiet`** に入って
  `rgba(220,220,224,0.42)`・`fill-opacity` は **1 固定＝スライダーの対象外**だった。
  さらにその灰色は `wp-alert-fill` の**下**に置かれ、`UNITS` の**全単位**を（発令中の単位も含めて）
  出していたので、**発令中の区域の下にも灰色が敷かれていた**。2 つのソースは tolerance も違った
  （1.2 と 2.5）ので、同じ行政界が二通りに簡略化されて**縁が噛み合わなかった**。
  ⚠⚠ **発令が覆っている単位には灰色を出さない**（`warnMeeting` → `unitCovered` 相当の判定）
  ——単位の重心が、同じ国のどれかの発令ポリゴンの中に落ち、**その発令のほうが単位より大きい**とき。
  同一性では足りない: 自分でポリゴンを出す機関（DWD・NWS・MET Norway・CAP の `<polygon>`）の形は
  単位索引のオブジェクトではない。
  ⚠⚠⚠ **灰色の形は「単位 − その単位に重なる発令すべて」である**（`subtractWarnings`）。
  **警報を公表している索引と、この地図が灰色を描く単位の索引は、同じ分割ではない**——カナダの
  ECCC は自前の予報区で、ロシア・カザフ・アルジェリアは WMO 登録簿が持つそれぞれの形で発表する。
  分割が違えば発令は単位の**内にも外にもまたがる**ので、「単位の中に収まるか」で分けているかぎり
  ほとんどが「捨てる」側に落ちる。実測（本番・z2・陸 6,133 点・キャンバス 1000×820）:
  **728 点＝11.87% が何にも塗られていない**（カナダ 329・ロシア 197・ブラジル 133・アルジェリア 25・
  カザフ 17）、層全体で**灰色になった単位 1,942 に対し捨てられた単位 2,123・穴を開けられたのは 6 個**。
  → **差そのものを計算する**。またぐ発令は切り取られ、単位より小さい発令は穴になり、単位を覆う
  発令は結果を空にする——3つの場合が1つの式の3つの答えになる。重ならない規則は**強くなる**
  （以前は点の判定に引っかかった発令しか避けていないので、辺にまたがる発令の上に灰色が残り得た）。
  ⚠ 判定に使う候補は**境界箱が重なる発令すべて**（`warnsNear`）であって、点の判定に当たったものだけ
  ではない。⚠ MapLibre は**巻き方**で外環と穴を区別する（`classifyRings`）ので、穴の巻きは
  外環と逆向きに揃える——揃えないと**塗られて**、二度塗りに戻る。
  ⚠ **クリッパは遅延で届き、必須ではない**——`polygon-clipping` はこのレイヤーを最初に点けたときに
  別チャンクで届く。届くまでの間（あるいは届かなかったとき）は、単位の中に**収まる**発令を穴にする
  従来の経路（`punchQuiet`）がそのまま動く。**機能が減る瞬間は無い。**
  ⚠ `IntMapWorld.alerts()` が `quietCut`（切り取って残した単位）/ `quietCleared`（差が空になった
  単位）/ `quietClipper`（`on` / `pending` / `failed`）を出すので、効いているかは数えられる。
  ⚠⚠⚠ **包含は、<b>その形の中にある点</b>で訊く**（`geomInside`）。`geomCentre`＝**最大の環の
  頂点の平均**は**その多角形の点ではない**——凹んだ単位や多島の単位では**自分の形の外**に落ち、
  しばしば**隣の中**に入る。`geomInside` は最大の環の**縦の真ん中を横切る走査線**を引き、
  **いちばん広い内側区間の中点**を取る（O(n)）。⚠ 走査線は**穴を横切ることがある**ので、
  `inGeom` で幾何に確かめてから採用し、駄目なら従来の重心へ落ちる。
  ⚠ **古い重心はそのまま使う**——`dedupeSameShape` とタップカードの「どの区域を触ったか」は
  **同一性と近さ**の問いであって、包含の問いではない。
  ⚠ かつては包含も `geomCentre` で訊いていたので、**隣の単位について答えていた**。
  それを「中に発令がある」と読むと、**発令が置かれているのが自分の単位の索引そのものである国**
  （ロシア・サウジ・アルジェリア・カザフ——タップカードが `Republic of Karelia` のように
  行政単位名を出す国）で、**静かな隣が丸ごと消える**。同じ索引から出た2つの地物は重ならないので、
  **どちらも他方の穴にはなり得ない**。→ **輪郭がこの国の単位のどれかと一致する発令は、その単位で
  あって「中にあるもの」ではない**（`unitBoxes`。判定は `sameOutline` と同じ bbox 4桁≈11 m）。
  実測（本番・z2・陸 3,400 点）**275 → 152**、ロシア **83 → 0**・サウジ 15→0・アルジェリア 13→0・
  カザフ 13→0。⚠ **隣は「覆う」こともできない**ので、覆い判定の側にも同じ除外が要る。
  ⚠ **はみ出す発令も差なら扱える**——「穴」は外環の中に収まる環にしか使えず（外環と交差する内環は
  三角形分割が壊れる）、MeteoAlarm のスイス・オーストリアの区域は NUTS-3 と**本当に重なっていない**
  （却下された環の頂点内包率は **0.5〜0.6** に山があり、許容誤差では解けない）。差は切り取るだけなので
  この場合が特別ではなくなる。⚠ ただし**入力が大きすぎるときは差を計算しない**——単位＋発令の頂点が
  6 万を超えると 1 フレーム止まるので、そこは従来の経路に落ちる（この地図が持つ最大の単位は
  ヌナブト準州の **15,133 頂点**で、そこから 20 区域を引くのに **129 ms**）。
  重なりが無いので、灰色と色は**1枚のレイヤー**に同居できる（配列順に描くので灰色が先）。
  ⚠ **単位はこの地図が既に持っているものだけ**——気象庁の市町村、Eurostat NUTS-3、CMA の行政区画、
  CWA の郷鎮市区、Natural Earth admin-1、**同梱の世界行政区画索引**、geoBoundaries ADM1。つまり
  **灰色に塗れる単位は、警報が出れば色を塗れたはずの単位**であり、それが灰色を「主張」にしている。
  ⚠⚠⚠ **世界の第1級行政区画は<b>1ファイルとして同梱している</b>**——`data/admin1-world.json.gz`、
  **247 か国・4,515 区分・2.38 MB（gzip）**、`scripts/build-admin1.mjs` が Natural Earth 10m を
  0.01°（≈1.1 km）で間引いて生成する。これが無かったとき、閉じた索引を持たない国は
  **geoBoundaries を1国ずつ**（0.3–2 MB × 同時2本）取りに行くしかなく、実測**95 か国が国全体の
  灰色1枚のまま**で、単位で描けていたのは 50 か国だけだった。ブラウザが払える世界 ADM1 は
  公開されていない——Natural Earth 50m は**9 か国**、同 10m は **40.7 MB**、geoBoundaries CGAZ は
  **360 MB**。だから**ビルド時に一度**間引いて配る。
  ⚠ **地図が読む索引であって、気象についての第2の意見ではない**（NUTS や国土数値情報と同じ扱い）。
  **何が発令されているか・その階級・その文言はすべて各国機関のもの**。
  ⚠ **区分の灰色は「視野」と「ズーム」で切る。** 単位の集合は貯まるので、貯まったものを全部
  publish すると視点を動かすたびにコレクションが育つ——実測、世界ズームで **6,101 区分・10.0 MB**。
  `QUIET_UNIT_Z`（= 3）未満では区分の境界線は 0.25 px で、国 1 枚と 500 枚は**同じ絵**になるため、
  国全体の灰色に戻す。持っていない国も同じく国全体の灰色（`washTier` = 1）で、パネルが
  **その差を数えて印字する**（`unitLine`）。
  ⚠ `washTier` が問うのは「**いま単位レイヤーがこの国を描いているか**」であって「形を持っているか」
  ではない（`quietSet`）——持っているが画面外の国を 2 にすると、**誰も塗らない**国ができる。
  ⚠⚠⚠ **「発令中の国」に国全体の灰色を敷いてはならない**（`drawnISO`。主張そのものが偽になる）。
  → **その国は「単位で」塗る。** ここは `washTier` の判定を変えるところではない——
  国1枚を取り下げるのは正しく、間違っていたのは**引き継ぐはずの単位レイヤーが動いていない**ことだった。
  `QUIET_UNIT_Z` は**区別が見えるか**についての床であって
  **地面が塗られるか**についての床ではないので、**発令中の国には床を適用しない**
  （`warnedISOs`）——世界ズームでもその国だけは単位で描き、発令のある単位には灰色を出さない。
  ⚠ かつては「何かを描いている国は wash しない」だけで、単位レイヤーがその国を描いていない窓
  （`QUIET_UNIT_Z` 未満・単位索引が届くまで）では**誰も塗らなかった**。実測——**同じカメラ・
  同じキャンバス・同じ標本格子で改修前後を通して**（z2・7,154 点・陸 3,404 点）
  **759 点＝22.3% → 217 点＝6.4%**〈中国 186→4・アメリカ 101→0・ブラジル 58→0〉。
  ⚠ **その残差はカナダで、それを消したのが上の「差」である**——ECCC は**自前の予報区ポリゴン**で
  発表し、この地図が持つのは州・準州 13 個なので、警報がその中に落ちるたびに州が消えていた。
  差を計算するようになってからは、実測（同じカメラ・同じキャンバス 1000×820・陸 6,133 点）
  **カナダ 329 点 → 4 点・13 州すべてが灰色を持つ**、ブラジル 133 → 0。
  MeteoAlarm のスイス・オーストリアも同じ形で、同じように解ける。
  ⚠ **視野の判定は publish 側と取得側で同じ箱を使う**（`paddedView`）——publish は半画面ぶん
  padding するのに取得は素の bounds を見ていたので、その差の帯にある国は
  「灰色として出されるが単位を取りに行かれない」状態になり得た。
  ⚠ geoBoundaries は**世界索引にも無かった国**にだけ、同時 2 本まで。
- ⚠⚠⚠ **対応国は<b>書き足す</b>のではなく<b>学習する</b>。** #R284 は NWS の UGC を読んで 8 か国・
  地域を手で書き足した。実測、同じ形が他にもある——フィンランドの機関は **Ahvenanmaa（オーランド、
  独自の ISO コードを持つ国）** に発令していて、そのポリゴンは既に描かれているのに、国の層は下で
  「未対応」の斜線を塗っていた。手書きの一覧は**増える日に嘘になる**（#R271）ので、
  `learnCoverage` が**描いた単位の重心**を `countryAt` に通し、自分のフィードを持たない国に落ちたら
  **その形を描いた機関がその国を担当している**と記録する。証拠はポリゴンそのもの。
  ⚠ **重心であって頂点ではない**（粗い輪郭が国境を数 km 越えても隣国を主張してはならない）。
  ⚠ **足すことしかしない**——自分のフィードを持つ国は決して割り当て直さない（「一国一ソース」）。
  ⚠ **保存しない**——いま地図にあるものから毎回導くので、発令をやめた機関は担当から外れる。
  実測、この仕組みだけでコソボとリヒテンシュタインが自動的に対応国になった。
- ⚠⚠⚠ **このレイヤーの重さは「1つのコレクションを何回貼り直すか」で決まる。** 実測（本番・対照つき・
  z4 で欧州・60 秒）: **レイヤー無し 36.5 fps / 警報オン 3.4 fps**、主スレッド遮断は 19.5 s に対し
  **49.0 s**。78 秒で `wp-alert` に **62 回**（最大 3,792 地物）貼り直していた。原因は4つあり、
  4つとも「絵は変わっていないのにやり直している」形をしている——
  ① **機関の発表一覧を全地物の文字列プロパティに入れていた**（`items:JSON.stringify(rows)`）。
     スタイルは一度も読まないのに、毎回シリアライズしてワーカーへ複製していた。→ `ROWS`（`rid` で
     引く手前側の表）へ。カードと国別凡例が読むものは同じ。

     鍵（索引の顔ぶれ・その国の取得時刻・表示言語）が変わった国だけ組み直す。WMO 側も同じ。
  ③ **貼り直しの合流窓が 160 ms** で、1フレーム内の2件しか合流しない。→ `PUBLISH_MS`（貼り直しは
     多くても窓に1回・末尾）。国の薄塗り（`paintCountries`）も同じ窓に乗る。`force` は即時。

  4千件の衝突判定を走らせるが、世界ズームではそのどれも読めない。→ z2.5 未満は色と輪郭が答える。
- ⚠⚠⚠ **コレクションは「変化」として送る。**（#R344）
  本番ビルドの CPU プロファイル・70 秒: MapLibre 自身の `serialize` **5,910 ms** ＋ その手前の `sendAsync`
  **5,594 ms** ＝ **11.5 秒のメインスレッド**を、`wp-alert` の **26 回**のアップロードのために
  （積荷は **13.3 MB・5,163 地物・455,886 頂点**）。このレイヤー自身のコードで最も高い関数の 18 倍である。
  `setData` には**「今動いたのはこの3件だけだ」と言う方法が無い**——#R290 / #R297 が消したのは
  「何も言っていない」アップロードで、残るのは**本当に違うもの**、その違いは 5,000 のうち数十である。
  → **`GeoJSONSource.updateData({add,remove})`**（`setSourceData(id,data,opts)` の3引数目）。

  **黙って地物を落とさない**。

  **丸ごと書き**に落ちる。`RESYNC_EVERY` 回ごとにも丸ごと書く。

  **serialize+post 2,206 → 832 ms・`xs` 711 → 239・MapLibre 全体 3,215 → 1,279・GC 623 → 173**。

  ⚠ **「差分で送っているつもり」と「差分で送っている」は別**なので、アダプタが実際にどちらを呼んだかを
  census が数える（`diffed`・**計器 OFF でも読める**）。
- ⚠⚠⚠ **記憶の鍵は<b>内容</b>であって、配列の同一性ではない。**（#R344）

  `concat` で作り直されるので、**フィードが何も言わなくても毎回別のオブジェクト**——3つとも

- ⚠⚠ **同じ図形の同じ鍵を綴り直さない。**（#R344）`_bboxKey` はこの層が単位と警報を比べる同一性そのもので、
  実測 **0.63 秒 / 70 秒** ＝ プロファイル中の第一者最大だった。`geomKey(g)` が `geomBox` の隣に焼く。
  ⚠ 併せて: `subtractWarnings` の memo は満杯で **`clear()` せず古い 1/4 を捨てる**（(単位×警報) の組は

- ⚠⚠ **簡略化は<b>1つ</b>。** `wp-alert` の `tolerance` は MapLibre の既定 **0.375**（ズームごとに

  無くなり、単位を二度（灰色で一度・色で一度）貼ることも無くなったので、節約する相手のほうが消えた。
- ⚠⚠ **境界線の解像度は2段。** Eurostat NUTS の**床は 20M** のまま（欧州全体が画面に入るズームでは

  ローマ中心は穴の外になる。⚠ 同じ穴は 20M の LEVL_3 にもあるが、そちらは 03M が届いた時点で**自然に治る**

  **中に何も入っていない穴はこの 1 本だけ**（他は全部、中に別の単位が入っている正当な穴）。
  ⚠⚠⚠ **日本も同じ2段にする。** 全国1ファイルの `s0001` は**1,894 市町村で 33,394 頂点＝1区域あたり

- **塗りは薄い。** 既定の不透明度は **0.38**（他レイヤーと同じ `_registerLayerOpacity` の**共通スライダー**が
  動かす。専用のボタンは作らない）。階級は**輪郭線**が持つので、塗りを透かしても答えは残る。
- **更新は 10 秒**（`TICK_MS`）＋タブ復帰で即時。**フィードの鮮度は4段階**——
  Fresh（≤6h）／ Delayed（≤48h）／ Stale ／ Error。⚠ これは**フィードについての語**であって、
  発表が無い機関は「静か」であって「故障」ではない、とパネルが自分で書く。
- ⚠⚠ **多国フィードは「初回読み込みの待ち行列」ではなく「輪番」である。** MeteoAlarm は1リクエスト
  6か国（relay の上限）× 2本／tick、対象は**最後に読んだ時刻が古い順**（未読が先）。35 か国を約 90 秒で
  一周する。**「まだ持っていない国」だけを候補にすると、届いた瞬間に候補から外れて二度と更新されない**
  ——実測、修正前は8分間・80回の更新で MeteoAlarm へのリクエストは**3本**で、以後は**ゼロ**だった。
  `maAt` / `swicAt` が国ごとの取得時刻を持ち、パネルの `maOldestS` / `swic.oldestS` が
  「最後に読んだのが一番古い国の年齢」を印字する（**増え続けたらそれが凍結**である）。
- ⚠⚠ **一周は「エッジキャッシュの寿命」に合わせる。** relay のキャッシュは **15 秒**なので、
  それより速く同じ国を聞いても**同じバイトが返るだけ**で上流は新しくならない。床が下がれば一周も
  速くできる: tick **10 秒** × **1リクエスト6か国 × 3本**。
- ⚠⚠ **定常の速さと「最初の1分」の速さは別物である。** 3本は正しい**定常**の速さで、正しくない
  **出だし**の速さだった——実測、レイヤーを入れて 45 秒の時点で MeteoAlarm 30/35・WMO 登録簿 78/93 で、
  世界の4分の1がまだ白いまま読み手が見ていた。まだ一度も読んでいない国はキャッシュを消費しない
  （キャッシュされたものが無い）ので、**未読が残っている間だけ 6 枠**（`COLD_CALLS`）で走り、
  一周したら 3 枠に戻る。実測、45 秒で **35/35・93/93**、未読は **26 → 1**。
  バーストは国の数で上限が決まるので、**1セッションに1回しか起きない**。
- ⚠⚠ **`busy` はラッチではなく<b>数</b>である。** 全バッチを1つの `Promise.all` に入れて1つの真偽値で
  守ると、**一番遅い国が次の tick を決める**——実測、3本にしたのに最古が 108 秒まで伸び、2本のときより
  悪化した（10 MB の上流取得が 30 秒を超えると次の tick が丸ごと空振りする）。`maBusy` / `swicBusy` は
  **飛んでいるバッチの数**で、遅い1本は3枠のうち1枠を占めるだけ。`maPend` / `swicPend` が
  「いま飛んでいる国」を持ち、二重取得を防ぐ。⚠ `maAt` は**完了時にだけ**書く（先に書くと停止が隠れる）。
- ⚠ **WMO 登録簿は「誰かに何か出ているか」を先に1回で聞く。** `?swicscan=1` は GeoServer の
  `propertyName` から**幾何列を外した**同じ問い合わせ（実測 1.53 MB・1.5 秒で全世界 4,427 区域）で、
  形を落とさずに「どの加盟国に何件あるか」を答える。形を取りに行くのはそこに出ている国だけなので、
  93 か国が**最初の tick で読み終わる**。⚠ `propertyName` に `wkb_geometry` を書き忘れると
  GeoServer は**全地物を `geometry: null` で返す**（実測、韓国 37 区域が形なしで「取得成功」した）。
- **パネルは「危険以上の警報が出ている国」から始まり、そこは1国1行である。** 〈色・国・災害（最悪順、
  入り切らない分は `+N`）・階級・区域数〉。**上限は16か国**（超過分は「+N か国」）、**1行の災害名は3つ**まで。
  ⚠ **国 × 災害で並べると1国が何行も占める**——実測、14行のうち**5行が中国**、
  4行がイタリア、2行が豪で、残りの世界は「+59」だった。⚠ **行に印字する階級はその行の階級**である
  （旧実装は国全体の最悪値を1つの災害名の横に出し、CMA の**黄色**に「Red (I)」と書いていた）。
  ⚠⚠ **一覧は IntMap 換算で `HOT_MIN`（= 3 ＝ `NORM_NAME(3)` の「危険」）以上の国だけ**を出す。
  しきい値は**1か所（`HOT_MIN`）にだけ書く**——見出し・空のときの1行・絞り込みが別々の数を言わないため。
  ⚠ **見出しは絞り込みを名乗る**（「危険以上の警報が出ている国」）。一覧でないものを「いま発表されている
  警報」と呼ぶのは、この層が何度も払ってきた「偽の見出し」である。
  ⚠ **空のときの文は「どこにも何も出ていない」ではない**——下位の階級は出ていて地図に描かれうるので、
  「いま『危険』以上に達している国はありません」と、**答えた問いのほうを言う**。
  取得先の一覧（`Source status`）とその下の `Diagnostics`（置けなかった区域）は畳んである。
  数字は**全ソースで「区域数」に統一**する。
- **押した地点の警報は別のカードに出る**（`.country-panel` ではなく `.country-popup`＝アプリ共通の詳細カード）。
  当たり判定は**描かれている地物の幾何**（`ptInGeom` / `alertsAt`）なので、答えは「日本なら市町村、ドイツなら郡、
  その他はその機関が描いたポリゴン」。⚠ **凡例は上書きしない**——タップで「いま世界で何が起きているか」が
  消えるのが旧実装で、国全体の一覧はカードのボタンから開く。同じ答えは `__wpAlerts.at(lng,lat)` でも取れる。
- `drawnISO` は**実際にソースに載った地物から毎回作り直す**（`publish()`）。「自分の単位を描いている国」は
  表ではなく**測定**である。⚠ **手書きの対象一覧を作らない**——その一覧に国が増える日に嘘になる。
- 名前の突き合わせは**両側に同じ正規化**（`_norm`：アクセント畳み・記号除去・単位語の除去）を通し、
  `_alias()` が `|` `/`・括弧つきの別綴り・**先頭の行政語**（`Prov.` / `Région de` / `Landkreis` …）を外した形・
  **`A; B; C` の各要素**を索引に入れる。`lookupUnit()` は完全一致 → 語の接頭辞・接尾辞（4文字以上）→
  **索引側の接頭辞**（＝索引の鍵が問い合わせで始まる。「Antwerp」→「Prov. Antwerpen」、
  「Viseu」→「Viseu Dão Lafões」）の順に試し、⚠ **索引側は一意に決まるときだけ**採用する
  （二つに当たる語幹はコイン投げであり、違う区域に警報を描くのは描かないより悪い）。
  ⚠ **片側だけの正規化はコイン投げ**になる。

**発令区域の形を、5段のはしごで探す**

実測、MeteoAlarm の35か国で公表 1,127 区域のうち**置けたのは 754**——373 区域が地図から静かに落ちていた
（オーストリア 86／スロバキア 59 全部／ベルギー 9 全部／クロアチア 13 全部／スペイン 64／モルドバ 42 全部）。
原因は1つで、**MeteoAlarm の CAP はそれらにポリゴンを持たず**（`<geocode>` は `EMMA_ID` だけ）、
区域名が**その機関自身の呼び名**で Eurostat NUTS の名前ではないこと——「Rijeka region」「Wien Brigittenau」
「Meseta cacereña」「Košice okolie」。

| 段 | 形の出どころ | 効く国（実測） |
|---|---|---|
| ① | CAP 自身の `<polygon>` | 英国・オランダ |
| ② | **同じ機関が WMO 登録簿に出している形**（relay `?swicgeo=<mid>`） | 墺・斯・西・波・塞・波黒・克・希・斯洛 … |
| ③ | Eurostat NUTS 2/3（＋ **その機関が英語名で呼ぶ NUTS-2 の別名表** `MA_ALIAS`） | 伊・仏・独・洪 … |
| ④ | **geoBoundaries gbOpen ADM1 → ADM2**（今日の天気に左右されない行政界） | 葡（distrito）・モルドバ（raion）・立陶宛 … |
| ⑤ | 国境そのもの（**区域名が国名のときだけ**） | 塞浦路斯 |

はしごの効き目は**数えられる**。実測、MeteoAlarm の35か国で **965 / 1,127**。
⚠⚠ **② は「いま発令中の区域の形」しか返さないので、その機関が静かな日には空になる。** 実測（同じ分）:
墺 112・波 126・西 86・斯 54 の形が返る一方、**葡 0・モルドバ 0・洪 0・伊 0・白 0**——だから
モルドバは **0 / 42**、ポルトガルは **1 / 18** しか置けていなかった（＝機関が発表しているのに国が真っ白）。
→ ②の索引は**セッション中ためる**（後から来た形は**併合**であって置き換えではない）、
空で返った機関は**一定時間後に聞き直す**、そして④が**天気に依存しない行政界**を持つ。
実測（同じビルド・同じ手順）: **2,737 / 2,923 → 2,877 / 2,961**（欠落 186 → 84）。
モルドバ 0→32 / 42、ポルトガル 1→17 / 18、リトアニア 7→10 / 11、伊 18→19 / 20。
残りは国ごとに「置けた数／公表数」を**言葉で**印字する（丸めない）。
⚠ ④ は **`media.githubusercontent.com/media/…` から読む**。`raw.githubusercontent.com` は
Git-LFS の**ポインタ**（実測 131 バイト・`version https://git-lfs…`）を返し、`github.com/…/raw/…` は
CORS ヘッダを返さない。media ホストだけが実体を `Access-Control-Allow-Origin: *` で返す
（実測、ポルトガル 595 KB・373 ms）。**ADM2 が無い国は 404**（実測、モルドバ・モンテネグロ）で、それは
握り潰さずフォールバックとして扱う。⚠ ④ は **④ より上が答えられなかった区域にだけ**効かせる——実測、
希と白は既存の段のほうが良い（希 10/16 対 3/16）。出典・ライセンスは `js/reference-data.js`・
`js/legal.js`・sources ページに記載（CC BY 4.0）。
⚠ **② は「第2の警報ソース」ではない**——`?swicgeo=` が返すのは **区域名と形だけ**（event も severity も
時刻も入っていない）。何が発令されているかは今もその国のフィードが答えるので、**一国一ソース**は保たれる。
⚠ **② は有効期限で絞らない。** 警報は期限切れになるが、その警報を描いた郡は期限切れにならない。
⚠ 座標は小数4桁（約 11 m）に丸める——実測、オーストリアの生データは 1.5 MB、要約後 1.07 MB。

**出典の言葉で読む**

- ⚠ **気象庁のコード表は気象庁のものを置く。** `JMA_CODE` は気象庁自身の警報ページが持つオブジェクトから
  取った「コード → 要素 ＋ **レベル**（20/30/40/50）」で、**階級はレベルだけ**から決める
  （コードの数値範囲から決めてはならない）。⚠ 指定河川洪水予報の表は混ぜない（コードが衝突する）。
  検証は出典自身の言葉で行う（`headlineText` の文言と要素名が一致するか）。
- ⚠ **現在の状態は「官署ごと・速報種別ごとの最新1件」。** `r8` は**種別ごとに1行**を持つ現況スナップショット
  であって履歴ではない（実測: 287行 / 58官署 / **1組につきちょうど1行**）。`dataTypeCode` は災害の系統で、
  1官署が **VPWW55 大雨系・56 土砂系・57 高潮・58 風・59 波浪・61 雷/濃霧/乾燥** をそれぞれ独立に出す。
  各行はその系統について、その官署の**全 class20 を「発表なし」まで含めて**列挙する。
  だから**種別を鍵に含めずに「官署ごとの最新1件」にすると、系統1つを残して残り4つを捨てる**。
  ⚠ **古い行を捨ててはならない。** 再発表されていない系統は「その系統は変わっていない」という意味である
  （実測: 14日より古い41行のうち**発表中の項目を持つものは0**）。
  最新が 72 時間より古ければ **throw** する——これは「このフィードが生きているか」の判定であって、
  「全系統が新しいか」ではない。
  ⚠⚠⚠ **同じ速報の中では `class20Items` が `class10Items` に勝つ。** 1つの速報は一次細分区域
  (`class10Items`) と市町村 (`class20Items`) を**両方**載せている。区域の行をその中の全市町村へ配ると、
  **同じ速報が「発表警報・注意報はなし」と書いている市町村まで塗る**——実測、青森 020010 津軽は 19 市町村
  のうち **14 が「なし」**、名瀬 460040 奄美地方は 13 のうち 7 が「なし」で、**合わせて 21 市町村が
  何も発令されていないのに塗られ**、宮古郡多良間村は2階級高く塗られていた。
  → **区域の行が埋めるのは、その速報自身が名前を挙げていない市町村だけ**（「区域の注意報でその町が
  空白に見える」のを防ぐという元の意図はそのまま残る）。
  ⚠ 気象庁自身のマップも区域と市町村を混ぜない——**class10 は z4–7、class20 は z8–11 の別レイヤー**で、
  一方を他方へ配ることはしない。実測、この規則にしたあと気象庁の表示と**塗りすぎ0・塗り漏れ0・
  階級違い0**で一致する。
- ⚠⚠⚠ **同じ「形」を12本のローダ全部に当てた結果**（「機関が名指していない範囲を塗る」）:
  - **カナダ (ECCC)** — `status_en:"ended"` を**印字するだけでフィルタしていなかった**。実測
    **159件中35件が解除済み**（マニトバ州インターレイクの14自治体が連続）。→ 落とす。
    他のローダは既に落としている（HKO の `CANCEL`・INMET の `encerrado`・relay の CAP `msgType:cancel`）。
  - **中国 (CMA)** — `alertid` が自分の区・県にも `slice(0,4)+'00'` の地級市にも当たらないとき、
    **省まで繰り上げて省全体を塗っていた**。実測 `500157 重慶市両江新区` → **重慶市 82,400 km² 全域**
    （名指された範囲の約69倍）。省直轄県級行政区（`429004`・`469001`・`659001`）も同じ経路に落ちる。
    → **省の段を廃止**し、置けないものは `UNPL` に数える。⚠ 地級市の段は残す（DataV の
    `100000_full_city` は477単位で**県を1つも含まない**ので、県級の発表には元から形が無い。
    実測 941件の内訳＝区146・市794・省1）。
  - **米国 (NWS)** — 実測 **281件中201件 (71.5%) が `geometry:null`**（UGC 区域コードで発表され、
    形はクライアント側が持つ）。黙って捨てたうえで `PLACED.USA=[80,80]`＝「全部置けた」と印字していた。
    → **分母に数え `UNPL` に立てる**。⚠ これは描けるようにする変更ではない（UGC の区域索引が要る）。
    「発表なし」ではなく「置けなかった」と言うようにしただけ。
  - **香港 (HKO)** — 地物を1つも作らないローダなのに `PLACED.HKG=[1,1]` だった。→ `[0,1]`。
  - **ヨーロッパ (NUTS)** — 警報は 03M へ昇格するのに `UNITS[iso]` が 20M のままで、34か国で
    **警報＝細かい形／隣の「発表なし」＝粗い形**という縁の食い違いが残っていた（#R298 が消した欠陥の
    ヨーロッパ側）。→ 昇格時に単位も作り直す。日本側の規則（「昇格したら警報も置き直す」）の裏返し。
  - **オーストラリア (BoM)** は変えていない。1件の警報を `a.states` の全州へ配るので、実測
    1つの川の1区間の洪水警報が **NSW（80.1万 km²）と VIC（22.7万 km²）の全面**を塗るが、BoM は
    州より細かい単位で発表しておらず、この地図もオーストラリアの州より細かい境界を持っていない。
    ＝**機関自身の単位**であって、上書きしている細かい主張が存在しない。
- ⚠ **全フィードが自分の時計を持つ。** `seenAt(feed, iso)` が**そのペイロードの一番新しい時刻**を記録し、
  パネルが機関ごとに年齢を印字する。**年齢は常に印字する。**
  ⚠ **有効期間は発表時刻ではない**——CAP の `onset`/`expires` は有効期間なので、`seenAt` は未来を拒否し、
  リレーの `fetchedAt` を使う。
- ⚠ **上流の「悪い日」より短い制限時間は、生きたフィードをランダムに落とす。** 上流の期限は 45 秒＋1回の
  リトライ。投げっぱなしのローダには**自前の in-flight ガード**を持たせる（`Promise.all` する側の
  `busy` は自分しか守らない）。
- ⚠ ライブ取得は全て `cache:'no-store'`（付けないと定期タイマがキャッシュを読み直す）。
- ⚠ **遅いフィードを `Promise.all` に入れない。** 公開される地物は「待ち合わせた分＋各ローダが着地させた分」を
  1か所（`publish()`）で組み立てるので、遅いフィードが早いフィードを白紙にできない。
- タップは `grouped()` の3段（admin-1 → sub → 市区町村）。同じ災害の組合せを持つ市区町村は1行にまとめる
  （**markup にも予算がある**）。
- ⚠⚠⚠ **CORS が開いていることと、「本番のオリジンから読める」ことは別である。** 中国の行政区画
  （DataV.GeoAtlas）は `Access-Control-Allow-Origin: *` を返し、**同時に hotlink を防いでいる**——
  実測、同じ秒・同じ URL で `Referer: http://127.0.0.1:4277/` は **200 / 569 KB**、
  `Referer: https://rwmqx7dwb5-arch.github.io/IntMap/` は **403**。ローカルのプレビューでは
  見えないので、中国が 127.0.0.1 では 223 区画描かれ、本番では `PLACED.CHN = [0, 1217]` になった。
  → **relay 経由で読む**（relay は Referer を送らない）。`?cngeo=` は境界データなので**1日**のエッジキャッシュ。
- ⚠⚠⚠ **座標を1つも持たない図形は「図形」ではない。**（#R344）
  公開されたコレクションに **27 地物の `{"type":"Polygon","coordinates":[]}`** が混ざっていた。全部が台湾で、
  原因は上流——郷鎮市区の 1982 年ファイル（g0v/twgeojson `legacy/twTown1982.json`）が **378 件のうち 19 件を
  座標ゼロで出荷している**（台北市中正區・台中市中區・高雄市鹽埕區・連江縣東引鄉・澎湖縣七美鄉 …）。
  索引の篩は `f.geometry` が**在るか**しか訊いていなかったので、名前は索引に入り、`shapeOf` がそれを答えとして
  返し、**実測で発令中の警報 8 件——うち 5 件は大雨の rank 3——が「決して描かれない地物」になっていた**。
  見えないより悪い: `PLACED` は**置けたほうに数え**、`UNPL` は上がらないので、
  **「ここで何かが起きているがどこかは言えない」と言うためだけに在る国 1 枚の薄塗りが一度も呼ばれない**。
  `dedupeSameShape` が素通りさせたのも同じ理由（`geomBox` はそういう図形に **null** を返す）。
  → **述語はもとから在り、誰も訊いていなかった。** `shaped()` が `geomBox` を名乗り、
  **図形が入ってくる3つの扉が全部それを訊く**——境界索引・`setUnits`・`unitFeature`。
  ⚠ **直したのは述語であって国ではない**：将来どの境界データが同じことをしても通らない。
  実測 **27 → 0**、TWN の `PLACED` は 331/396 と正直になった。
- ⚠ **公開フィードが見つからない国は、灰色斜線で「データなし」と言う。** 空の地図に「平穏」を含意させない。
- **「対応国をどこまで増やせるか」は測れる。** 実測（同じ分）: WMO の加盟表に ISO コードを持つ加盟機関は
  **198**、そのうち WMO 自身が「CAP 実装 Completed」と記録しているのは **139**——この地図はその全部を
  読んでいる（自前フィードの国を含めて **140**）。残りは **Development 37 ／ Not started 20** で、
  **登録簿の全球スキャンに1件も現れない**（実測、スキャンに出た 37 機関はすべて Completed）。
  つまり **「CAP を出しているのに読んでいない加盟機関」は 0 である。**
  ⚠ 加盟表の外を足すには、その機関が**機械可読で、発令単位ごとに**出していなければならない。
  実測（12機関を叩いた結果）: 印 IMD **401**（IP 制限）／土 MGM **500**（Not allowed）／墨 **500**／
  南ア **404**／泰・尼・越・智・亜・以 **404 または 403**／新 SGP はデータ無し。
  唯一答えたのは **馬 MET Malaysia**（`api.data.gov.my/weather/warning` · 200 · JSON）だが、
  中身は**散文**で（「over the waters of Pahang • Terengganu • Northern Sarawak」）、
  `<area>` も geocode もポリゴンも無い——**出典が分けていないものを地図が分けてはいけない**ので、
  これを区域に切り出すのは実装ではなく捏造になる。よって**足していない**。
- ⚠⚠ **MeteoAlarm の「緑」は警報ではない。** CAP の `parameter[awareness_level]` が `1; green; Minor` の行は
  「注意の必要なし」で、**発表中の警報ではない**。実測、イタリアの 474 件のうち **201 件が緑**、ベルギーは
  フィード全体（10 区域）が緑だった——`severity` だけを読むと緑が `Minor`/`Moderate` として警報の色になる。
  ⚠ **災害名の文字列で代用してはならない**：イタリアは event に色名を書くが、オーストリアは書かない
  （`Thunderstormwarning` 796 件、すべて awareness 2）。階級は **2/3/4 → CAP の 1/2/3**、緑は**落として数える**
  （relay が `green` を返し、黙って消さない）。

### 7.2 レイヤー欄の分類

**レイヤー欄は右サイドバー（タイル）ひとつだけ。** `Layers` ボタンは `IntMapLayerSidebar.toggle()` しか
呼ばない。携帯では同じタイル盤が「Map & layers」シートに載る。**「どちらのレイヤー欄を使うか」という
設定は無い。**

⚠ **`#layer-dropdown` という要素は残っていて、それは UI ではなくレジストリである。**
このアプリのレイヤーの**チェックボックスは全部この要素の中にいる**——右サイドバーのタイルは
`rowsFromDropdown()` がこの要素を歩いて組み立てるし、レイヤープリセット・Atlas のレイヤーカタログ・
不具合報告・共有リンクも同じ要素を数える。だから要素は残り、**常時 `display:none`**（表示させる
`.show` クラスは存在しない）。**新しいレイヤーの行はこれまでどおりここに追加する。**

`js/data-layers.js` の `GROUPS` が **18 の棚に 140 行**を配る。`GROUPS` に無い行は末尾の
**「Others」**と**「ベータ」**へ自動的に掃かれる（ベータは削除ではなく1段下の棚）。

**各要素は `[キー, id の配列, 名指しされた件数]` の3つ組である。**
id の配列は**利用者が挙げた順**で、先頭の「名指しされた件数」本だけがカテゴリを開いたときに並ぶ。
残りは**カテゴリの中の「その他N件」**の後ろに畳まれる（実測 **名指し 56 行 / 畳み 84 行**）。
3つ目を省くと全件が名指し扱いになる。

⚠ **その数はカテゴリの並び順と同じ場所に置く。** どのレイヤーを最初に見せるかは利用者が決めたことで、
順序と不可分だから同じ行に書く。描画側（`js/map-ui.js` の `buildTiles`）はこの配列を読まない——
`reorganizeLayerPanel` が畳む行に `data-lyr-rest="1"` を書き、`rowsFromDropdown()` がそれを運ぶ。
⚠ **ベータには畳みを適用しない。** 利用者のカテゴリ一覧にベータは無く、適用すると全行が
「その他N件」の中に隠れて見出しの下が1行になる。掃き出しは印を**明示的に消す**
（この関数は冪等なので、棚から出た行が古い印を持ち込みうる）。

規約:

- ⚠ **1つの id は1つのグループにしか書けない。** `order.push` は要素を**移動**させるので、2箇所に書くと
  最後のグループにしか出ない。`tests/r271-checks.test.mjs` が全 id の一意性を検査する。
- ⚠ **全グループキーは9言語すべてに見出しを持つ**こと（同テストが検査する）。
- ⚠ **行が0のグループはキーを残す**（保存済みセッションや共有リンクが名指しできる。描画はされない）。
- ⚠ **`lyrGrpOthers` のキーは変えない。** `js/map-ui.js`（タイルのベータ判定）と `js/layer-dropdown.js`
  （携帯での折りたたみ）が名指しで使っているので、改名すると携帯でベータ節が畳まれなくなる。
- **基本表示カテゴリ（`Base map & labels`）は「地図をどう描くか」の常設スイッチであって、レイヤーではない。**
  中身は **11 行**——地名・水と地形のラベル・施設名・国境・**海岸線**・州県境・道路・鉄道・グリッドの
  9 個の `cb-*` に、**昼夜の表示**（`dl-nightside`）・**3D 建物**（`beta-dl-bldg3d`）が加わる。
  ⚠ **その一覧の正本は `window.IntMapBasicLayers` ただ1つ**（`js/data-layers.js` の先頭で宣言）。
  「レイヤーが何個オンか」を数えるものは**全部これを引く**——`_refreshActiveLayers()` の `skip`
  （＝パネル上部の `Active layers (N)`）、`window._imActiveLayerCount`（携帯 FAB の着色）、
  `IntMapWidgetCore.activeLayers()`（ウィジェットの `N layers on` と**おすすめレイヤーのルーレット**）。
  ⚠ **手で書き写さない。** 以前はこの一覧が4か所に別々に書いてあって、`dl-tz`（#R271 が移動）と
  `beta-dl-bldg3d`（#R273 が移動）はどの写しにも追加されず、**両方がレイヤーとして数えられていた**。
  ⚠ 常設スイッチへ移した行は `placed` にも入れること（入れないと掃き出しでベータにも現れて二重になる）。
  ⚠ **例外が1つある**——`js/data-layers.js` 末尾の「OFF を再送しない」除外リストは**同じ id を並べた
  別の規則**である（#R38: 状態を持つハンドラを再 dispatch すると勝手に ON へ戻る）。`dl-nightside` /
  `beta-dl-bldg3d` は再送してよい普通の非同期レイヤーなので、**そこには足さない**。
- ⚠⚠ **その節の答えは、11 個のスイッチではなく「デフォルト／クリーン／カスタム」の 3 択である。**
  正本は **`window.IntMapBaseDisplay`**（`js/data-layers.js` の先頭）。`js/map-ui.js` の `modeRows()` は
  その**表示**であって、状態の写しを持たない（#R232 が昼夜行と `IntMapNightSide` に与えたのと同じ関係）。
  - **デフォルト** = 11 行を出荷時の状態にする。**その集合は導出する**——9 個の `cb-*` は
    `window.IntMapDefaultOn`、残る 2 行はそこに載っていないので `IntMapBaseDisplay` が明示する。
    ⚠ **手で書いた既定値の写しを作らない。** #R309 が membership の写し4本を1本にしたのと同じ欠陥が、
    1つ隣の欄で起きる。
  - **クリーン** = 11 行を全部オフ。
  - **カスタム** = 何も変えず、11 行の一覧を出すだけ。
  - ⚠ **排他はコードではなく「値が1つであること」から出る。** 真偽値を3つ持つと3か所を同期する羽目になる。
  - ⚠⚠ **モードは状態についての主張なので、状態より長生きしてはならない。** Atlas でも、風レイヤーの
    海岸線の1回きりの提案（#R289）でも、セッション復元でも、基本表示が動いた瞬間にモードは
    **「カスタム」へ降格する**（`reconcile`）。「デフォルト」と書かれた見出しの下がデフォルトでない、
    という状態を作らないための唯一の仕組み。
  - ⚠ **降格の判定は落ち着いた状態に対して行う（400 ms のデバウンス）。** 復元は change イベントの
    **列**であって、その途中の状態は利用者が選んだ状態ではない。デバウンスが無いと毎回の読み込みが
    半分適用されたセッションを見て「カスタム」と判定する。
- ⚠⚠ **レジストリに在って、パネルが描かない行がある。** `window.IntMapHiddenLayerRows` がその一覧で、
  今は **`cb-countries`（国境・国情報）と `dl-contours`（等高線）** の 2 つ。
  チェックボックスは `#layer-dropdown` に残るので、レイヤー本体・ハンドラ・凡例・不透明度・
  セッションの保存/復元・Atlas の入口は**1バイトも変わらない**。無くなるのは行だけ。
  ⚠ **行を配る掃き出しには全部教えること。** `order.push` は要素を**移動**させるので、誰も引き取らない
  行はベータに落ちる（#R271 で 🕒 タイムゾーンが実際にそこへ出た）。`reorganizeLayerPanel` は
  これらを `placed` に入れ、`rowsFromDropdown()`（`js/map-ui.js`）はタイルを作らない。
- **この節だけタイルではなく行で並ぶ。** `buildTiles()` は全セクションを 3 列のタイルで描くが、
  基本表示は**全幅の行＋iOS 風トグル**（`.lst-tile.lst-row` ＋ `.lst-sw`）で、
  **サムネイル画像を持たない**——「地名」の写真は言葉以上のことを何も言わないため。
  ⚠ 行も `.lst-tile` クラスを持ち続ける（`syncTiles` / `filterTiles` と
  「行数が変わったら建て直す」3つの門が全部このクラスを問い合わせている）。変わるのは中身と形だけ。
  ⚠⚠ **ただし「行数が変わったら建て直す」門は `.lst-tile[data-lid]:not([data-fav="1"])` を数える。**
  3 択の行も `.lst-tile` なので、素朴に数えると `have` は永久に `want + 3` になり、**パネルは正しいまま
  開くたびに全部組み直される**——#R72 が「layersをクリックしたときの反応が非常に遅い」に対して
  書いた安い経路が、見た目には何も壊さずに死ぬ。**お気に入りの棚が作る複製も同じ理由で数から引く**
  （下記）。門は 4 本あり、**1 本でも漏れれば同じ症状になる。**
- **カスタムの 11 行は、3 択の行より縦に小さい**（`.lst-tile.lst-row.lst-basic`：高さ 34 px・行間 4 px。
  3 択の行は 46 px・行間 6 px のまま）。一度に 11 行が並ぶのはこの節だけで、46 px では
  電話の画面から溢れる。⚠ **縮むのは `.lst-basic` に限る。** `.lst-sw`（42×26・つまみ 20 px・
  移動 16 px）は**ウィジェット群の `.wgt-sw` と同じ 1 つの物**なので、base を縮めると依頼と無関係な
  ウィジェット側のスイッチが黙って一緒に縮む。小さいほうは同じ 3 px の余白を保った小さい実例
  （34×21・つまみ 15 px・移動 13 px）。⚠ 行間は grid の `gap` で子ごとに変えられないため、
  **隣り合う `.lst-basic` の間だけ**を負の `margin-top` で詰める（先頭の 1 行は「カスタム」との
  境界なので 6 px のまま）。
  ⚠ **11 行は「カスタム」でないときも組み立てて、隠すのは `filterTiles` である。** モードごとに
  タイルの数が変わると上の門が毎回建て直しになるし、表示/非表示を CSS と inline の2系統で決めると
  検索の強制展開とモードが同じ `display` を奪い合う。決めるのは1か所。
- **「お気に入りレイヤー」は基本表示の直後に立つ、ほかと同じ形のカテゴリである**
  （`.lst-grid.lst-favgrid`。見出し・シェブロン・件数バッジ・畳みは他カテゴリと同一）。
  中身は `window.imLayerFavs`（★の保存先。`intmap_settings.layerFavs`）が名指す行のタイルで、
  **★を付けた順**に並ぶ。名前は既存の i18n キー `favLayers` から引くので、9 言語すべてに既に訳がある。
  ⚠ **これは「移動」ではなく「2 枚目」である。** 行を移すと誰も引き取らない行がベータへ落ちる
  （上の `order.push` の ⚠）。複製ならレイヤーは自分のカテゴリに残り、件数バッジも
  「その他N件」も分類について嘘をつかない。複製は `data-fav="1"` を持ち、**建て直しの門 4 本すべてが
  それを数から引く。**
  ⚠ **1 枚のレイヤーに 2 枚のタイルがある以上、状態を配る側は複数形でなければならない**——
  チェックボックスの `change` を受けるリスナは `querySelectorAll` で**全部**の `.on` を塗る
  （単数形だと 2 枚目が古いまま残り、「地図と一致しない」に見える）。
  ⚠ **「お気に入りがある場合のみ出す」を分岐で書かない。** `filterTiles` は可視タイル 0 のグリッドと
  その見出しを既に隠すので、空の棚はその機構で消える。同じ `display` を 2 つの機構で決めないこと。
  ⚠ **★を書き換える口は 2 つある**（タイルの `.lst-star`＝`js/map-ui.js`、classic 行の `.lyr-star`＝
  `js/layer-favs.js`）。どちらも `window.imLayerFavs` を直接触るので、**両方が
  `intmap-layerfavs` イベントを撃ち**、タイル閲覧側がそれを購読して棚と全部の★を塗り直す
  （`js/layer-favs.js` は `js/map-ui.js` を import しない——契約はストア、イベントは「動いた」の合図）。
  ⚠ `IntMapHiddenLayerRows` の行（`cb-countries` / `dl-contours`）は**タイルを持たないので棚にも出ない**。
  ★自体は付けられ、classic 側のチップには出る。
- **海岸線・湖岸線**（`cb-coast` → `js/coast-line.js`）は**国境線と全く同じ手法**で描く：
  同じ `ofm` ベクタソース・同じ `BORDER_COLOR`・同じ `BORDER_WIDTH`／`BORDER_CASING`・同じ「黒縁を線の下に」の対。
  違うのは `source-layer` だけ（`boundary` → `water`）で、**海のポリゴンの輪が海岸線、湖のポリゴンの輪が湖岸線**
  ——1つの幾何なので1レイヤーが両方に答える。`swimming_pool` は除く。
  ⚠ **タイルの継ぎ目は出ない**（実タイル復号：切断は extent 4096 に対し −64 / +4160 ＝バッファ内で、
  タイル境界に乗る線分は 0。MapLibre のステンシルがバッファを捨てる）。
  ⚠ **既定は ON**（#R476「Coastlines & shoresはデフォルトでオンにして」）。⚠⚠ **既定オンは2か所で
  1つの編集**——`index.html` の `checked` と `window.IntMapDefaultOn`（`js/data-layers.js`）の両方が要る。
  片方だけだと**両方向とも無症状で壊れる**: `checked` だけなら線は出るが `IntMapBaseDisplay.matches()` が
  食い違い**起動 400 ms 後に基本表示が毎回「カスタム」へ降格**し、id だけなら boot dispatcher が
  点いていない箱に `change` を投げないので**何も描かれない**（#R34）。`tests/r476-checks` ① が
  **両方向を導出して**照合する（#R225 ⑤ はリスト→markup の一方向しか歩いていなかった）。
  ⚠ **届くのは初回訪問者だけ。** 保存済みセッションには id が無く、復元の off-sweep はそれを
  「読み手が消した」と読む（#R186/#R225）。既存利用者へ届かせる手当ては `defv` の世代を上げること
  （#R189/#R190）で、#R476 はしていない。⚠ **代わりに off-sweep を緩めてはならない**——緩めれば
  意図して消したレイヤーがリロードで復活する。
  ⚠ **<b>風レイヤーか気温レイヤー</b>を点けたとき1回だけ提案する**（`window._imCoastAuto` のラッチ）機構は
  そのまま残っている。既定オンの初回訪問では空振りするが、**#R476 以前の保存を持つ読み手にとっては
  唯一の戻り道**である。ラッチであることが「既定」と「連動」を分ける——消した読み手を
  次の点灯で覆さない。⚠ **気温だけで、他の 8 つのラスタには広げない**——理屈は同じでも、
  指示が名指ししたのは気温である。
  ⚠⚠⚠ **「どこに生まれるか」を決める `before` アンカーは、「どこに居るか」を決めていない。**
  上に居続けるかを決めるのは **`js/label-occlusion.js` の `STACK`**（#R19「地名や国境はどのレイヤー
  よりも最前部に」）で、これが **idle と styledata のたびに再表明される**ので、追加順は必ず上書き
  される。**海岸線はこの一覧に入っていなかった**——色も幅も縁取りの梯子も国境線と同一なのに、
  順序だけが逆だった。実測（`dl-ec-gust` を点灯、`raster-opacity` は 1）:
  `coast-only-line` 23 / `ec-gust-0` 32 / `borders-only-line` 34 ＝ **国境は不透明ラスタの上、
  海岸線は9層下**。`queryRenderedFeatures` はどちらでも 15 本返す——幾何は常にあり、上に不透明な
  一枚が載っていただけである。
  ⚠⚠ **黒縁（`*-casing`）は線の一部なので、一覧では線の直前に置く。** 縁は線を `beforeId` にして
  追加され、**直下に居ることで淡い基図の上でも読める**ようにする対（#R210）。`raise()` は一覧に
  在るものを動かし、無いものを置いていくので、**線だけを一覧に書くと線は上がらず、対が割れる**
  ——`borders-only-casing` は #R210 以来ずっと割れており、上の実測では 13 層離れていた。
  ⚠ **国境と海岸線が同じ地物の上を走るときは国境が勝つ**（一覧では海岸線の対を国境の対より前に
  置く＝あとから描かれるのが国境）。⚠ 門は `tests/r477-checks`（①〜⑤・一覧と
  `js/data-layers.js` の `BASE` の**両方を解析**して照合、写しを持たない）、
  `tests/smoke.spec.js` ㉑（**最上段に層を1枚足して自己修復を実際に走らせる**）、
  `tests/prod-smoke.spec.js`（**本番の実ラスタの上に本当に載っているか**）。
- **行 id の接頭辞**は `rowFor()` が知っている必要がある（世界データ層 `wp-dl-`、施設層 `fac-dl-` など）。
- **分類の規則は1つ——レイヤーは、それが測っている主題に属する**（作った計器でも、対象の場所でも、
  出てきた表でもない）。
- ⚠ **過去の指示で beta へ降格されたものを、勝手に昇格させない**（「beta」は品質の判断、分類は主題の判断）。
- ⚠⚠ **等高線（`dl-contours`）はレイヤーの行ではなく、3つの凡例の中のトグルである。**
  持ち場は **標高（カラー段彩）`relief`・陰影起伏（標高）`hillshade`・カラー段彩・陰影（ASTER）`gxrelief`**
  の凡例（`CONTOUR_HOSTS`）。**組み立ては1本**（`ensureContourSwitch`）で、3枚に markup を書き写さない
  ——1枚だけ直る欠陥の作り方だから。**細かさスライダはそのトグルの直下**に付き、オフの間は隠れる。
  ⚠ **状態は今までどおり `dl-contours` のチェックボックス**なので、トグル経路・不透明度・自己修復監査・
  セッション・Atlas の入口は1バイトも書き換えていない。凡例は**そこを押すだけ**。
  ⚠ **3つの持ち場が全部オフになったら等高線もオフにする。** そうしないと、線は地図に残り、
  スイッチのある凡例は1枚も無い、という到達不能な状態ができる。
- ⚠ **「ツール」節もカテゴリと同じように畳める**（`.lst-tools > .lst-sech` ＋ `.lst-toolbody`）。
  かつては chevron もクリックリスナーも件数も無い `.lst-sech` で、`:hover` だけが当たっていた
  ——**押せそうに見えて何も起きない見出し**だった。
  ⚠ **畳めるようにしたら、検索は畳みを飛び越えなければならない。** `filterTiles` は問い合わせがある間
  `.lst-toolbody` を inline の `display` で開ける（`.closed` の `display:none` に勝つ）。
  同じ規則がカテゴリの「その他N件」と基本表示の 11 行にも効く——**問い合わせは畳みより強い**。
  畳んでいるから見つからない、は計器が製品について嘘をついている状態。

### 7.5 地図の初期化・基図・投影

- **初期化**：`map = new maplibregl.Map(...)`。`renderWorldCopies` は投影／自由パンに応じて切り替える。
  基盤は CARTO / Esri のラスタ ＋ OpenFreeMap のベクタ（`ofm`）。
  ⚠ **CARTO のラスタは API キーが要る**（2026-08 から）。組み立ては `window.cartoTiles()` の1か所、
  キーは `js/carto-basemap.js`。キー無しでも 200 で返るが、絵に「API KEY REQUIRED」が焼かれている。
- **基図の帰属表示は地図カラムの最下行**（`#map-credit`）。⚠ **オーバーレイではない**——
  `.map-column` が縦 flex で、地図がその上を取り、帯が下の行になる。#R479 は右下に絶対配置した
  pill で出したが、本番の実測でレイヤーパネル（desktop）と下部ツールバー（携帯）に**全ビューポートで
  覆われていた**——地図カラムには全状態で空く矩形が存在しない。CARTO の Basemap Terms が
  無料枠の対価として「読者に見える帰属表示」を求めるため。⚠ **描かれている基図を名乗る**——
  CARTO 基図なら CARTO ＋ OpenStreetMap、衛星なら Esri。衛星の上に「© CARTO」を出すのは
  省略より悪い偽の帰属である。⚠ capture mode でも消さない（スクリーンショットこそ帰属が
  一緒に旅する必要のある成果物）。
- **基盤切替**：`btn-view-map/sat` と `applyTheme()` ＋ `_reassertBase()`（スタイルロード競合に強い
  ポーリング再適用）。⚠ `applyTheme` は `styledata` を同期で発火しうるので**再入禁止フラグ**を持つ。
- **投影**：Flat (mercator) / Globe。3D 地形は terrarium DEM（複数ホストで並列取得。携帯は maxzoom 13）。
- **タイルの密度はバイトで言う**：`maxTileCacheSize` は 512² のタイルを前提に決める（256² 前提の枚数を
  そのまま使うとメモリが4倍になる）。
- **衛星タイルは `imapsat://` プロトコル**（`js/sat-proto.js`）。@2x の綴じ合わせは「無い画像」に払わない
  ——z10 近傍ごとに `have`（実画像が見えた最深）と `stop`（次の段が灰色だと**観測された**最深）を
  **別々に**持ち、止めてよいのは `stop` だけ。記録は**訊かれたタイル**に対して行う（祖先に対してではない）。
  観測は `window.IntMapSatProto.depth/wouldStitch/hiDPI`。
- **粗い地球全体の衛星ベース**：`js/world-base.js` が同梱の正距円筒画像から `imapworld://` で低ズーム
  衛星タイルを**ネットワーク無しで**生成し、`layer-sat` の下に敷く。
- **極冠 (±85.0511°〜±90°)**：Mercator にそこのタイルは存在しないので、`layer-polar-cap`
  （スタイル配列の先頭に宣言された `background`）が**どのベースマップでも**敷かれる。
- **背後の星空・太陽・月**：`js/space-sky.js`。ダークテーマ ＋ globe ＋ 自前の空を持たないエンジンのときだけ、
  `#map` の**下**の `#space-canvas` に実カタログの星（`data/stars.bin`）と実位置の太陽・月を描く。
  月は満ち欠けを描く（照射率・明縁の位置角・明暗境界楕円・地球照）。太陽は周縁減光した円盤＋光冠＋コロナ。
  数値は `window.IntMapEphemeris` から来る（テクスチャではない）。
- **大気の縁**：`js/limb-layer.js`。`js/theme-sky.js` の `_sunElevAtCentre()` は
  ⑴ 衛星写真でなければ `null`（標準マップに大気は出さない）、⑵ **昼夜表示がオフなら 90°**
  （`_aimSun()` がカメラ中心の真上へ向けた光の読み戻し）、⑶ それ以外は実際の太陽高度を返す。
  ⚠ **「モードをオフ」は「その量が不明」ではない**——`null` を返すとアプリ自身の大気がそもそも点かない。

### 7.6 ラベル

- **地名ラベル**：`ensurePlaceLabels()` が `ofm` の `place` レイヤから `ofm-country` / `ofm-city` /
  `ofm-other` を生成する（冪等）。`cb-names`（既定 ON）で表示。
  ⚠ **市区町村より下の階層は `ofm-other`**：`village` / `suburb` / `hamlet` に加えて
  `borough` / `quarter` / **`neighbourhood`** / `isolated_dwelling` / `farm`。
  綴りは **`neighbourhood`**（OpenMapTiles のスキーマ値。US 綴りは1件もマッチしない）。
  クラスを3段に分け、`['step',['zoom'],1, 13,2, 14,3]` で開く。⚠ **段は整数**
  （`['zoom']` はフィルタ内では整数ズームでしか再評価されない）。
- **地方行政区分ラベル**：同じ `place` レイヤの `state` / `province` クラスから `ofm-admin1`。
  ここでの `rank` は**面積で世界規模にそろった順序**なので、ズームの階段は国別ではなく rank 別。
  ⚠ **色は「その区分を描いている線の色」**＝`js/border-style.js` の `ADMIN1_COLOR` を**そのモジュールから
  読む**ので、破線とラベルが食い違わない。⚠ ハローは**両基図で暗色**にする（コントラストはハローの仕事）。
  ⚠ **クリック／ホバーの一覧に入っている**（地図の上では都市名と見分けがつかないので、答えないラベルは
  壊れた機能である）。4つの一覧（レイヤー別クリック・カーソル・厳密ヒット・パディング付きタップ）は
  `PLACE_LBL` / `ALL_LBL` から**導出**するので、片方だけ更新できない。
- **ポップアップは名前を2つ出す**：「現地名（地図がそう描いた名前）」。`showPopup(…,{title})` は
  **見出しだけ**を差し替え、`name`（コピー・Wikipedia 照会・AI ブリーフ・境界検索が使う識別子）は
  タイルの `name` のまま。2つ目の名前は `applyLabelLang()` が `text-field` を組むのと**同じ**
  `OSM_NAME_KEYS(lang)`（`window.IntMapOsmNameKeys`）から求めるので、言語一覧は1つしかない。
- **細かい地名ラベルの範囲ハイライト**：`IntMapOutline.fetchPolygon` は Nominatim を**2段**で引く。
  ① クリック地点の ±0.06°・`bounded=1` ＝結果をその近傍に**限定**、② 見つからなければ ±8° の viewbox
  （ヒントであって限定ではない）。⚠ 順序が本体（±8° は再ランクするだけなので、細かい地名は同名の有名地に
  枠を奪われる）。⚠ ポリゴンが存在しない place ノードには**何も描かない**（点に長方形を被せない）。
- **水域・地形ラベルと河川**：`geo-sea` / `ofm-water` / `ofm-water2` / `ofm-river` / `ofm-peak` は
  クリックでポップアップ（面が無いので「この地域だけ」「移動」は出さない）。
  **`ofm-river` だけは、その河川を線でハイライトする**。選び方は `js/river-course.js`：
  **名前の集合**（`name`・`name:xx`・`name_xx`・`int_name`・`alt_name` を正規化）を作り、
  **共有する名前で推移的に**タイル内の `waterway` 区間を繋ぐ。⚠ **1つの名前で比較してはいけない**
  （河川は国境ごとに改名され、`name:en` だけが共通という形が普通）。
  そのうえで `course()` が OSM に実流路を訊く（Nominatim →（駄目なら）Overpass）。
  ⚠ **タイルのハイライトを先に描き、それを取り上げない**（取得は後から届き、届かないこともある）。
  ⚠ `course()` が受け取るのは「押された区間」ではなく**閉包そのもの**（全名前・範囲・代表点）。
  ⚠ 門は「クリックからの 40 km」ではなく「**すでに一致しているタイル区間のどれかからの 40 km**」。
- **昔の国名ラベル**（`imtb-lbl` ＝改名・消滅した国 / `imtb-lbl2` ＝今と同名の国。`js/time-borders.js`）は
  **`ofm-country` と同じラベルである**——同じサイズのランプ・同じ字間 0.08・同じ `text-max-width` 8・
  同じハロー幅 1.7・同じ `maxzoom` 7、そして**基図の明暗に合わせた塗り直しも同じ**
  （`applyLabelLang()` がこの2層も回す）。⚠ 書体は `placeFont()` ではなく **`readerFont()`**：
  era の文字列は `_locName` / `_modName` として**すでに読み手の言語**で焼き込まれており、地物に
  `name:*` キーが1つも無いので、`placeFont()` の per-label `case` は必ず汎 Han 面へ倒れてしまう。
  （`visibility` だけは `window._applyBorders()` の持ち物——時間旅行中は**常に**表示する。#R94l）
- ⚠ **昔の国名ラベルのクリックは `claimClick` を必ず呼ぶ。** 配線があってもポップアップは出ない——
  `js/map-ui.js` の汎用クリック fallback は「自分の `ALL_LBL` に当たらなかった」ときに `clearHL()` を
  呼び、それがポップアップを**消す**。fallback は microtask（`_deferLabel`）なので、同期で開いた
  ポップアップを**必ず後から**取り消せてしまう。#R210 の `claimClick` / `clickClaimed` がこの衝突の
  ための機構で、era 側がそれを名乗ることで fallback が身を引く。
- ⚠ **昔の国名ラベルにもパディング付きタップがある**（マウス 6px・指 15px）。現代のラベルは #R23 から
  持っており、era 側だけ「グリフに正確に当てないと開かない」＝携帯では死んだ文字に見えていた。
- **ポイント地物はタイル直描画／ラベル線地物は初見ピン留め。** 見えているアンカーを「改善」目的で動かさない。
- **ラベルのサイズ**：全レイヤーが `window.IntMapLabelScale`（`js/label-scale.js`）から取る。
  地名以外は必ず地名の基準の 0.88 倍以下。
- **施設・店舗名**：同じ `ofm` の `poi` レイヤから `ofm-poi`（テキスト）＋ `ofm-poi-dot`（点）。z14 〜、
  `rank` の窓をズームで開き、`symbol-sort-key` で衝突順も同じ順序にする。`cb-poi`（既定 OFF）。
- ⚠ **閉じる × は U+00D7 ひとつに統一する。** 実測 `measureText` 16px で **U+2715 は Inter・Noto Sans JP・
  system-ui・sans-serif・Arial の全部で 13.07px**（＝どれも持たず記号フォント落ち）、**U+00D7 は
  10.59/16.00/10.95/16.00/9.34**（＝Inter が持っている）。定義は `window.IntMapClearGlyph()` ただ1つで、
  `tests/r273-checks.test.mjs` が js/ と css/ の**全ファイル**を掃く。位置は**それが属する入力欄の矩形**から
  決める（`top:50%` は位置指定の祖先に解決されるため、包み箱と入力欄の高さが違うとずれる）。

### 7.7 レイヤー個別の注意

- **世界の鉄道**（`beta-dl-rail` / `js/railways.js`）— **仕様の正本は `Architecture.md` §7.3c**。
  ここに書くのはレイヤー欄からだけ見える3点。
  ⚠ **「鉄道」と名の付く行は3つあり、別のもの**である。`cb-rail2` は**基図の参照線**（既定 ON）、
  `beta-dl-rail` が**この鉄道アトラス**（既定 OFF）、`ox-oxrail` は **OpenRailwayMap のラスタタイル**。
  Atlas の別名表では、素の「鉄道 / railways / gauge / 軌間」は**アトラスに向く**——
  参照線は既定で ON なので、素の語をそちらに向けると「表示して」が**何も起こさずに成功する**。
  ⚠ **凡例に軸のボタンが並ぶ**（軌間／電化方式／最高速度／複線・単線／旅客・貨物／運行状態／線種）。
  凡例の行は `IntMapRailways.key()` に**訊いて**作る——色を凡例側に書き写さない。
  ⚠ **不透明度は5つのレイヤー id をまとめて動かす**（`rail-ln` / `rail-det-ln` / `rail-cons-ln` /
  `rail-st` / `rail-st-lbl`）。詳細セルと駅を登録から落とすと、ズームした先だけスライダーが効かなくなる。

- **年降水量**（`dl-annprecip` / `js/precip-annual.js`）— **平年値**は CHELSA V2.1 bio12（30秒角 ≒ 1 km、
  1981–2010）をメルカトルに再投影したもの、**年別**は GPCC Full Data Monthly V2022（DWD、0.5°、
  陸上の雨量計解析）の 1981–2020 を1枚に縦積みしたもの。**色は16段の帯**（連続ランプではない——
  色から範囲へ正確に戻せる）。数値の読み出しは絵を読まず `data/precip-mm.png`（8bit の log(mm)）を読む。
  ⚠ **格子と帯と色は `data/precip-mm.json` / `data/precip-year.json` から読む**（JS 側に写さない）。
  ⚠ 海の上で雨量計解析は何も言わないので、陸だけを塗る。
- **GIBS ラスタ** — 各プロダクトの**実配信期間**は `data/gibs-range.json`（範囲外 404・範囲内 200 を
  二分探索して実測したもの）。⚠ NDVI はローリング窓、土壌水分は配信終了済みのものがある——
  「今日−2日」を既定にすると**何も描かない**日ができる。⚠ 2層同時に切り替えるときは、
  フラグではなく**飛んでいる Promise を共有**する（2つ目が「まだ着かない答え」を `null` として受けない）。
- **宇宙基地・地上局**（`js/osm-facilities.js`）— 同梱スナップショット `data/osm-space.json`（14,965件）と
  ライブ Overpass を **id で合成**する（ライブがスナップショットを上書きすると、ズームで件数が減る）。
  外交公館も同じ形。⚠ 疎な集合は「視野内 Overpass」では答えが出ないので、全球スナップショットを同梱する。
- **宗教・言語のポップアップ**は棒グラフ＋**データの年**を出す。
  ⚠ **出典が分けていないものを地図が分けてはいけない**（自由文の括弧を採るのは限定された語のときだけ）。
  ⚠ **出典が分けているものを地図がまとめてはいけない**（旧ユーゴの4標準は別々の分類）。
- **GDP 成長率は発散配色**（0 ＝ 白・負 ＝ 赤・正 ＝ 青・0 について対称）。
- **データセンター層**は表示範囲の集計を**レイヤー自身の凡例**に出す（浮くポップアップにしない）——
  「この点は何か」は浮き、「表示範囲に何があるか」はレイヤーの答えである。
- **海底ケーブル**（`dl-subcables` / `js/data-layers.js`）— 描くのは **`data/subcables.json`**。
  TeleGeography の模式線ではなく、`scripts/build-subcables.mjs` がオフラインで組み直した経路である。
  実測できた区間は各国政府・水路機関の公開経路（NOAA Marine Cadastre / EMODnet BSH・
  Rijkswaterstaat・Malta・SIG / ACMA）、残りは 1/12°（9.26 km）の海底格子上の最小コスト経路。
  区間ごとに `quality`（`verified` / `reconstructed` / `estimated`）と `src` を持つ。
  ⚠⚠ **格子は入り江・フィヨルド・河口を「池」にする。** 9.26 km のセルでは、その水域が
  外洋とセル同士で繋がらないことがあり、`snapToSea` が見つけるのは**出られない数セル**である。
  ⇒ ルータは**連結成分**を持ち、両端が**同じ水域**に落ちる組を選ぶ（`sharedSnap`。
  #R355 が置いた 60 km の上限はそのまま——**遠くへ動かすのではなく、別の水を選ぶ**）。
  ⚠⚠ **ケーブルが川に敷かれていることがある**（ブラジルの Norte Conectado / Projeto Amazônia
  Conectada）。標高格子に川は無いので、`data/subcable-overrides.json` の `rivers` が
  **名前と bbox で** Natural Earth 1:10m の川の中心線を選び、運河と同じ機構で掘る
  （名前だけでは足りない——`Negro` はこのデータで4本あり、うち3本はアルゼンチンとウルグアイ）。
  ⚠ **`quality` で色や太さを変えない**——線のグラフィックは1つで、`color` は
  TeleGeography 由来のケーブル色のまま（`['coalesce',['get','color'],'#30b0c7']`）。
  ⚠ **取得は4段**（自オリジンの `data/subcables.json` → その Cache API の写し →
  TeleGeography の写し → 中継。`js/data-layers.js` `fetchSubcables()`）。
  ⚠ **クリックの当たり判定は箱**（マウス ±8px・タッチ ±16px）で、**線は太くしない**。

### 7.8 地形と水

`js/terrain-water.js`。

- **DEM の穴は「地面が無い」ではなく「キャッシュに無い」かもしれない。** 判定の閾値は**物理**で置く
  （−12,000 m ＝ チャレンジャー海淵の下・符号化の最小の上）。穴に当たったら終わりにせず
  **ピラミッドを1段降りる**。残った穴は**数えて印字**する。
- **basin の拡張は DEM タイルのブロック単位**（`growBasin`）。LRU に丸ごと収まる大きさで読み、
  `null` は1回だけ再試行する。⚠ セルの密度で温めると、広い basin ではタイルの大半が未要求のまま残り、
  未取得タイルの矩形の辺で水が止まる。
- **新しい水源を置いても、既にある水はリセットされない。** 作業矩形の外を押したときは
  `padsToReach()` → `extendToPoint()` が**盆地を広げて**そこに届く（`sim.grow` は水深をそのまま運ぶ）。
  予算 `basinMaxCells()` を超えるときだけ `rebuildAround`（＝リセット）に落ちる。
  Atlas の `addSource()` も同じ経路を通る。
- **リセットは1本の関数**（`resetTerrainNow()`）。⚠ **「この関数を通れ」という注記が2本あったら、
  通らない道を無くす番**である（`editDirty()` を呼ばない経路を作らない）。
- **ツールは4つ**——盛る・削る・堤防・ダム・**水源**。一行の帯に出るのは短い語で、`modeName()` が正式名を持つ（キャプション・Atlas・検査が同じ関数を読むので、二つがずれない）。
- **`cont` / `rate` は水源自身の属性**（最後に置いた水源だけを太らせない）。継続の水源は緑＋輪、
  1回きりは青い点。
- ⚠⚠⚠ **1回きりと継続の差は「水が出続けるか否か」だけである。** どちらも**流量を持つ蛇口**で、
  `feedTaps(dt)` が**両方**に `rate × dt` を注ぐ。違うのは `cap`（＝出し切る総量）が有限か `Infinity` かの
  1点で、`owed(x) = cap − m3` が 0 になったら止まる。`m3` は**これまでに出した量**（両方とも）。
  ⚠ 旧実装は1回きりを `pool()` で**最初から静止した湖**として置いていたので、置いた瞬間に
  `simMoving()` が偽 → `canPour()` が偽 → **▶ が無効・↺ を押しても再生できない**という状態になっていた。
  ▶ は「まだ出し切っていない水源がある**か**、水がまだ動いている」ときに有効。
- ⚠⚠⚠ **その差は「量」と「速さ」の2つの数で、m³/s の箱は<b>1つ</b>である。** 旧実装は
  「1クリックの水量 m³」「注水量 m³/s」「流量 m³/s」の**3つ**を並べていて、後ろ2つは**同じ量**だった——
  `placeSource` が `rate:(flowM3s!=null?flowM3s:pourRate)`、`srcRate` が `pourRate` に落ちる、つまり
  1つの数に2つの操作子があった。いまは `pourRate` **1本**（`setRate()` が唯一の書き手で、置いてある
  水源すべての `rate` も同時に動かす。Atlas の `setFlow()` も同じ関数を通る）と、1回きりだけが持つ
  `srcM3`（総量）。⚠ **パネルが割り算を自分でする**——「1クリックで合計 X m³ を、毎秒 Y m³ の速さで
  出します（シミュレーション時間で約 Z）」を2つの箱の下に印字するので、2つの数が**何をするのか**が
  読める。継続では総量の箱ごと消え、「止めるまで出し続けます」と書く。
  ⚠ この文の鍵は**静的な文字列**でなければならない（`L('One click pours '+n+…)` は英語の引数を自分で
  組み立ててしまい、6言語目以降の索引は**英語の文字列で引く**ので永久に一致しない）。`{v}`/`{r}`/`{t}`
  を後から差し替える。
- **水は届くまでに時間がかかる**（`js/water-dynamics.js`）——浅水方程式の局所慣性形＋q 中心化、
  マニング n。閉じた形の答えで検証してある（等流水深・静水で max|q|＝0・質量保存）。
  ⚠ **予算は実時間の上限で持つ**（格子が育つとステップの値段が変わるので、ステップ数は予算にならない）。
- **パネルは1本の列。** `.tw-body` は `scrollbar-gutter:stable`、スクロールバーの幅は `_squareColumn()` が
  **実測**して `.tw-head` / `.tw-foot` の `padding-right` にインラインで書く
  （⚠ **インラインの padding にスタイルシートは勝てない**）。
  ⚠ **寸法は1か所の宣言**（`TW_FS`/`TW_FS_S`/`TW_FS_H`/`TW_ROW`/`TW_CTL`/`TW_IN`/`TW_PAD`/`TW_GAP`/`TW_INSET`）で、
  **端末クラスで2組**ある——デスクトップは**他の凡例と同じ寸法**（本文 11 px・行 30 px・操作 28 px）、
  携帯は指の寸法（12 px・44 px・36 px）。⚠ 44 px は iOS のグループ化リストの行高で、**デスクトップの
  凡例の列では他のどの行の3倍近く**になる（実測、警報凡例は本文 10.5 px・行 13〜16 px）。
- **ツール選択は上部に<b>一行で</b>ピン留めされる。** `.tw-tools` は `.tw-body` の**兄弟**（`.tw-foot` と
  同じ作り）で、head → tools → body → foot の順。⚠ **`position:sticky` はスクローラの中では効かない**
  ——ピン留めは CSS ではなく **DOM の親子関係**である（不均衡な `</div>` 1個でピン留めが黙って失われる）。
  スクロールバー幅は `.tw-head` / `.tw-tools` / `.tw-foot` の3枚に配る。
  ⚠ **ピン留めするのは「切替」だけで、設定は流れる。** 実測、`.tw-tools` は 591.7 px のパネルのうち
  **131.7 px**（「ツール」見出し 17.7 ＋ 2×2 の選択 58 ＋「着色」チェック 31.3）を占めていた——
  ピン留めする要素は正しかったが、**3行あった**。いまは `grid-template-columns:repeat(4,1fr)` の
  **1行 46.7 px**で、着色チェックは本文（「表示」）へ移した。
  ⚠ 4つの**正式名**は 306 px に入らない（実測）ので、帯には短い語を出し、正式名は `title` と、
  そのツールが開くパラメータ欄の見出し（`modeName()`＝**唯一の宣言**）に出る。
- **計算解像度は読み手が選ぶ**（`RES_D=[384,512,768,1024]`・既定 **512**・`im.twRes` に保存）。
  解像度の変更は `build({keep:true})` で**同じ作業矩形のまま**作り直す。セル寸法と格子数はパネルが印字する。
- ⚠⚠⚠ **標高のレベルは「作業矩形」から選ぶ。カメラからではない。** 作業矩形は `MAXKM`（60 km／携帯 26 km）で
  切られるので、切る**前**の視野で `_demZoomForSpan` を呼ぶと格子より粗い DEM を読むことになる——実測、
  カメラ z6 で矩形 47.2 km・セル 92 m のところ **DEM は z10（124 m 標本）**で、**格子より粗い地面**を
  読んでいた。矩形から選べば z13（15.5 m）。`viewKm`（視野）と `spanKm`（矩形）は別の名前を持つ。
- ⚠ **ツールを開くことは「地図を動かせ」という要求ではない。** `open({lng,lat})` はその点が**画面外のときだけ**
  カメラを動かし、**ズームは変えない**。旧実装は `zoom: max(現在,11)` で飛んでいたので、z6 で開くと z11 に
  なった（`js/map-ui.js` のツール行は**カメラの中心そのもの**を渡す）。矩形は `build({center})` で直接狙う。
- **↺ 再生**は時計・水・各水源の供給量を 0 に戻し、**同じ地形と同じ水源のまま** t=0 から流す。
  `m3` は「これまでに出した量」なので**両方の種類とも 0 に戻す**——それが再生そのものである。
  ⚠ `editDirty()` を通すこと。⚠ **⏭（静止まで進める）も蛇口に注ぎ続ける**（`settle({onStep:feedTaps})`）——
  注がない静止状態は「置いた水の一部の静止状態」でしかない。
- パネルは他の浮遊ウィンドウと同じ帯にいる（`registerWindow`）。開く位置は `placeClear()` が
  **地図を覆っているものの矩形を実測**して決める（サイドバーは開閉するので定数にできない）。
  読者が動かした後は動かさない。

⚠ **津波シミュレーターにボタンは無い。** 地震シミュレーターが震源（規模と深さ）を持ってから渡す
機能なので、単独の入口を置くと読み手に断層を発明させることになる。Atlas と共有リンクからは届く。

⚠ **どの行も `mod` にモジュール名を持ち、そのモジュールは `isOpen` と `close` を答えられる**
（行のハイライトと2度押しでの解除がそれを読む）。

**地震波（`js/seismic.js` ほか）**

- **初動の等時線は、破壊速度 Vr ≤ 波速 V であるかぎり厳密に震央中心の円である。**
  `t(x) = min_k( off_k/Vr + dist(k,x)/V )` の括弧が常に ≥ 0 だからで、これは改善できる近似ではなく物理。
  だが有限の破壊が持つ境界は**2つ**あり、もう一方は円ではない:

  ```
  T_first(x) = min over k ( off_k/Vr + dist(k,x)/V )    ← 円（定理）
  T_last (x) = MAX over k ( off_k/Vr + dist(k,x)/V )    ← 断層の形が出る
  ```

  その間が「いま揺れている」**帯**で、`T_last − T_first` は継続時間そのもの。破壊が向かった側では
  狭く（＝指向性）、背後では広い。⚠ **後端に枝刈りを掛けてはいけない**——最大値に勝てないとして
  捨てられる点こそが、最小値を決める点である。⚠ 点震源では両境界が一致するので**帯は描かれない**
  （長さが無ければ到達時刻は広がらない）。
- **場址項は周波数の関数**（`js/seismic-site.js`）。上位 30 m を Vs30、その下を CRUST1.0 の実層構造と
  した速度柱から `A(f)` を積分する。⚠ 高周波の極限は 1/4 波長を 30 m で1点評価した従来値と厳密に一致し、
  変わるのは**その下の周波数だけ**＝盆地効果。⚠ 速度反転は作らない（Vs30 を下回らないようクランプ）。
- **破壊は1枚のすべる矩形ではない**（`js/seismic-subfault.js`）。k⁻² すべり／**総モーメント厳密保存**／
  破壊時刻 |r−r_hypo|/Vr／ライズタイムは公表式。位相は断層形状を種にした決定的生成なので、
  **同じ断層なら常に同じすべり分布**になる。
- **その土地の分類は測って決める**（`js/earth-structure.js`）。同梱の CRUST1.0 / Slab2 / PB2002 から
  interface / intraslab / active-crustal / stable-continental を判定し、**区分ごとに公表された
  パラメータ一式**を返す。⚠ 幾何減衰の折れ点は**その土地の Moho 深さ**に比例させる。
  ⚠ **出典が確認できない係数は書かない**（出典のない閾値はファイル冒頭に明記してある）。
- ⚠ **地域限定の補正に依存しない。** 検証は観測から作る（`scripts/build-seismic-observations.mjs` /
  `scripts/seismic-validate.mjs` の `--baseline` で A/B）。
- これらのファイルは**純粋な算術**（DOM・レンダラ・fetch・アプリ状態を参照しない）なので、
  Node から直接検証できる。

**津波・水（`js/tsunami.js` / `js/water-dynamics.js`）**

- 浅水方程式の局所慣性形＋q 中心化、マニング n。**閉じた形の答えで検証する**
  （等流水深との比・静水で max|q| ＝ 厳密に 0・質量保存）。
- ⚠ **「このモデルは X を扱いません」と自分で書いてある機能は、いつか X を要求される。**
  到達時間を隣に表示しているなら、到達時間はそのモデルが答えるべき量である。
- ⚠ **2つ目の時計を作らない**（フッタと詳細が別々の到達時刻を出さない）。

### 7.10 気象モデル（複数）・風・レーダー

**どのモデルが存在するかの正本は [`js/wx-models.js`](../js/wx-models.js) 1本**（`window.IntMapWxModels`）。
そこが宣言するのは**提供の可否・表示名・公称解像度・出典機関・ライセンス・役割だけ**で、
格子・カバー範囲・変数・気圧面・予報期間は SDK の domain 表と各モデル自身の `latest.json` から
**導出する**（書き写した変数表は、上流が1つ足した日から**黙って**間違いになる）。

`js/wx-ecmwf.js` は `createModel(cfg)` でモデルごとのインスタンスを作り、
`window.IntMapWxEngine.model(id)` が取り出す。
⚠ **`window.IntMapECMWF` は既定モデルのインスタンスそのもの**であって写しではない
（12 ファイル 64 呼び出しが名指ししており、ファサードを作れば状態が二重になる）。
⚠ **ページに 1 つしか無いもの**は factory の外にある——SDK・`om://` の登録・開いたファイルの
プール（`READER_MAX` は**ページ全体**の予算）・32 MB のブロックキャッシュ・色の ramp・
スタイルレイヤーの索引・`Intl` の memo。

提供モデルは **ECMWF IFS HRES（約 9 km・6 日）／NOAA GFS（約 13 km・16 日）／
DWD ICON（約 13 km・5 日）**。**選択はレイヤーごと**（`js/weather.js` の `state[id].model`）。

⚠⚠ **変数はモデルごとに違う。** 実測: ECMWF IFS HRES に気圧面は **0 面**、`ncep_gfs013` に

**理由コード**を返し、ピッカーは選択肢を無効化し、`setModel` も拒否する。
**両方要る**——ピッカーは metadata 到着前に組まれることがあり、共有リンクはピッカーを通らない。

⚠⚠ **利用者に見せる文言は `displayed` からしか作らない。** 各レイヤーは
`requested`（選んだもの）/ `loading`（組み立て中）/ `displayed`（塗られているもの）の 3 状態を持ち、
**`displayed` への代入は `commit()` の 1 か所だけ**、走るのは**新スロットを現し旧スロットを落とすのと
同じターン**である。

⚠⚠ **モデルを変えても index ではなく瞬間を保つ**（軸は 109 / 209 / 93 段で刻みも長さも違うので、
同じ index は同じ時刻ではない）。

| `precipitation` | 0.86 | mm | ✓ |
| `cape` | 11.25 | J/kg | ✓ |
| **`pressure_msl`** | **101,458.75** | **hPa**（940…1060） | **× 100** |

この 1 つの食い違いが**同時に 3 つの絵を壊していた**——`getColor` は 100,000 Pa にも 101,458 Pa にも
102,500 Pa にも配色表の**最後の色**を返すので**色ラスタは一面の赤**、等値線は同じ配色表の
breakpoints を高度に使うので**1 本も交差せず**、カーソル欄は場の値に凡例の単位を付けて
**「101237 hPa」**と印字していた。**どこにも例外は出ない。**

→ 関係は **`js/wx-ecmwf.js` の `FIELD_UNITS` ただ 1 か所**で宣言し、消費側は全部そこから導く:

- **レンダラへ渡す配色表**（`omSettings().colorScales`）＝ 読み手の表を `inFieldUnits` で **`× per`**。
  SDK は画素の値をこの表に直接引き当て、**等値線の高度にもこの表の breakpoints を使う**ので、
  場の単位で渡すことがラスタと等値線の両方を同時に正す。
  ⚠ 明暗の 2 つを**両方**問い合わせて対にして戻す（`getColorScale` は先に片方を解決してしまうので、
  片方だけ倍率をかけて保存すると暗色の読み手に明色が出る）。
- **`scale()` / `legend()`** ＝ `displayScales`（SDK の表そのまま）。凡例の帯も目盛も単位も**不変**。
- **`sampler()`** ＝ `valueNow` / `valueAt` の実体。ここで **`÷ per`** する。
  1 か所なので「カーソルの数値は隣の凡例の単位」は**構造上そうなる**（2 ファイルの合意ではない）。
- **等値線のラベル** ＝ SDK が書いた等値線の値を `IntMapECMWF.fieldUnit(variable).per` で `÷`。

⚠ **エントリを増やすのは、その変数のファイルと配色表が実際に食い違うときだけ。**
何もしないつもりのエントリは、既に正しい場を黙って 100 倍する。

⚠⚠⚠ **ベクタのタイルは「何を描くか」を URL で言う。** SDK のベクタタイルは
`arrows=true` なら風の矢羽根、`contours=true` なら等値線を書き、**どちらも書かない URL の MVT には
`contours` レイヤーが存在しない**（実測・同一ファイル同一視野: 素の URL **0 地物** /
`&contours=true` **900 地物**）。`ec-isobars` は素の URL を送っていたので、
**レイヤーは可視・ソースは loaded・タイルは取得済み、その全部が空**という状態だった。
**等圧線が 1 本でも出るには 3 つ全部が要る**——

1. タイルを等値線について頼む（`_tileExtra`）
2. 等値線の高度が場の単位（＝ レンダラへ渡す配色表が場の単位、上の `FIELD_UNITS`）
3. **ラベルが配置できる**——`symbol-placement:'point'`。実測: `'line'` **0 枚**・`'line-center'`
   **0 枚**・`text-allow-overlap` を足しても **0 枚**・`'point'` **25 枚**。`tile_size` を
   512 / 1024 / 2048 のどれにしても変わらないので MVT の extent の問題ではない——SDK が 1 本の
   等値線を短い区間の集まりとして出すため（z3.4 で画面上の中央値 **16 px**）、文字を沿わせる
   長さが無い。**書体も名指す**（`Noto Sans Regular`。このスタイルの glyph 配信元が持つ書体で、
   アプリの他のシンボルレイヤーは全部これを名指しており、ここだけが名指していなかった）。

⚠ `tile_size` は SDK の `DATA_RELEVANT_PARAMS`（`['variable']` のみ）に入らないのと同じ理由で、
`contours=true` も**キャッシュの鍵と読む範囲を変えない**——変わるのは描かれ方だけ。

⚠⚠⚠ **等値線の「高さ」は #R439 から明示する（`&intervals=`）。** SDK は `intervals` が無ければ
**渡された配色表の breakpoints を等値線の高度に使う**。#R439 が気圧の配色表を Windy のものに
差し替え、それを 0.1 hPa で再標本化した＝**breakpoints が 1,801 本**になったので、
色の変更**だけ**をしていたら等値線を 1,801 本頼むことになっていた。**色と等値線は 1 つの決定である。**
出荷バンドルの実測では `intervals` の**要素が 1 つなら「刻み」**として扱われる
（`h.length===1` → その倍数すべてで切る）ので、宣言は数字 1 つで足りる:
`js/wx-ecmwf.js` の **`ISOBAR_STEP_HPA = 4`**（地上天気図の慣習であり Windy が描く間隔）。
⚠ **タイルへは場の単位で渡す**ので、`isobarIntervals()` が `× FIELD_UNITS.per` して答える
——ラベルが `÷ per` するのと同じ 1 つの宣言から導く。`intervals` も `DATA_RELEVANT_PARAMS` に
入らないので、読む範囲もキャッシュも変わらない。

⚠⚠⚠ **等圧線は「レイヤー」ではなく「海面気圧レイヤーのスイッチ」である（#R439）。**
「等圧線レイヤーを取り込み、トグルでオンオフできるように」——レイヤー欄の独立行は廃止した。
実装は `LAYERS` の行に **`sub:'ec-slp'`** を足すだけで、**地図側の機構は 1 つも変わらない**
（2 スロット交代・`applyTime`・`commit`・共有フック・`pruneMissing` はそのまま `activeLayers()` で
この行を見る）。`sub` が取り上げるのは**読み手に見える 2 つ**だけ——レイヤー欄の行と凡例の箱で、
それを分けるのが `legendLayers()` である。スイッチは海面気圧の凡例の中（#R16 / §7.10）、
**親がオフなら等圧線もオフ**、**親のモデルを必ず読む**（`syncSubs()` が両方を 1 か所で満たす）。
⚠ **退役した `dl-ec-isobars` を名指す入口は全部生きたまま**にした——共有リンクは
`js/map-ui.js` が #R409 の `dl-wars` と同じ形で「気圧の行 ＋ スイッチ」に読み替え、
Atlas の別名は `dl-ec-slp` を指し、スイッチ自身は**独自の動詞**を持つ
（`{"type":"isobars","on":bool}`——オンにすると海面気圧の行も点け、返事がそう言う）。
⚠ `js/layer-previews.js` の `omIsobars` とその素描は**行と一緒に消した**（到達不能な描画関数を
機能の顔をしたまま残さない）。

⚠⚠⚠ **等圧線は「不透明なラスタの上」に置く。これは順序であって旗ではない。**
ECMWF のレイヤーは**全部同じアンカー**（`IntMapECMWF.before()`）に置くので、2 つのあいだの上下は
「**あとに追加したほう**」で決まる。そして `lift()` はこれを直せない——`lift` は
「夜側の陰影の下に沈んだレイヤーを救い上げる」ためのもので（#R299）、**すでに上にあるものは動かさない**
と自分で決めている。実測（この形にした直後のビルド）:

```
ec-isobars-0, ec-isobars-0-lbl, ec-slp-0     ← 等圧線 3,299 本が不透明ラスタの下
```

タイルも高度もラベルも全部正しく、**1 本も見えない**。#R398 の「レイヤーは可視・タイルは空」の
裏返しで、**ソースの形を見る検査は全部緑**だった——見つけたのはスクリーンショットである。
→ `IntMapECMWF.toTop(id)`（無条件に動かす版）と `js/weather.js` の `raiseSubs(parentId)`。
**親のスロットが（再）構築されるすべての瞬間**——親の点灯・時刻／モデルの差し替え・スタイル交換——
のあとに、生きている sub のレイヤーを順に載せ直す。
☠ **`idle` では「`lift` が実際に動かしたときだけ」呼ぶ。** レイヤーを動かせば地図は描き直し、
描き直せばまた `idle` が来る——無条件に呼ぶと**毎フレーム 2 回の `moveLayer`** で回り続ける。
`lift` が返す真偽がその輪を切る。

**1 つのレイヤーの気象の数値は、すべて 1 つのモデルから来る。** `window.IntMapECMWF`（`js/wx-ecmwf.js`）が
Open-Meteo の spatial アーカイブ（**ECMWF IFS HRES・O1280 縮約ガウス格子・約 9 km**）を持つ。
配信元は Open-Meteo が AWS Open Data で公開している S3 バケット（綴りは `js/wx-models.js` の `HOST`
だけ。Open-Meteo 自身の CDN は Referer を自サイトに限るので使えない——`Architecture.md` §7.3b）。
色面（ラスタ）・粒子・カーソル下の地点値・共有リンクの4つが**同じ変数・同じ初期時刻・同じ有効時刻**を読む。

- **`.om` ファイルの場所は自分で組み立てる。**
  `<base>/<初期 YYYY>/<MM>/<DD>/<HH>00Z/<有効 YYYY-MM-DD>T<HH>00.om`。
  ⚠ **SDK に `latest.json` を渡してはならない。** `normalizeUrl` は `time=` を無視して
  `valid_times[0]` に解決し、キャッシュ鍵（`DATA_RELEVANT_PARAMS` は `['variable']` のみ）も
  時刻を含まない。**ファイル名に有効時刻が入っていることが、予報時刻が実在する唯一の理由**。
- **予報時刻は全部使う**（実測 145 ステップ＝3日は毎時、6日目まで3時間毎）。既定は「今」に最も近い段。
  **モデル初期時刻（run）と有効時刻の両方を印字する。**
  モデルランが更新されたら、**同じ添字ではなく同じ壁時計の瞬間**へ移す。
- ⚠⚠⚠ **予報時刻は<b>そのレイヤーのもの</b>で、アプリ共通の時計へは流れない。**
  各レイヤーの凡例が自分の時刻選択 UI を持つ（`window.IntMapWxPlayer.timeUI` —— **1つの宣言**を
  風の凡例と ECMWF の凡例が共有する。1つの軸の2つの見え方であって、2つの時計ではない）。
  ⚠ **選択肢は `<select>` で、`IntMapECMWF.times()` が公開している有効時刻だけ**が並ぶ。
  添字を動かす range 入力は**連続に見える**ので、「データのない時間を選べない」は
  コントロールについての主張として成り立たない。
  ⚠ **`window.IntMapTime` との結線は<b>両方向とも無い</b>。** 予報を1時間動かすことが、
  ニュース・歴史的国境・昼夜境界・国別統計を同じ時刻へ引きずっていた（`_pushClock`）し、
  逆にアプリ側の時刻移動が読み手の選んだ時刻を上書きしていた（`_followClock` の購読）。
  `_followClock` は**名前として残して公開**してある——「その時刻の天気」を明示的に求める操作
  （Atlas）は購読ではなく呼び出しである。
  ⚠ **`data-legend-ec-time`（「ECMWF 予報時刻」）という<b>勝手に開く箱</b>は今も無い。**
  各レイヤーの凡例の `.ecl-when` は「**この絵がいつのものか**」の**読み**であって、
  他所のコントロールを開くボタンではない。
  ⚠ Chronos（`js/news-timeline.js`）の **「予報」タブ**はモデルの軸を**直接**動かす第2の見え方として
  残っている——アプリ共通の瞬間には触れない。
- **凡例は「1レイヤー1枚」で、レンダラ自身の配色表から作る**（`IntMapECMWF.legend(variable)`）。
  箱の `<h4>` は**そのレイヤー自身の名前**（`data-legend-ec-<id>`）、中身はそのレイヤーの帯・目盛・
  **不透明度**・データ源・モデル・時刻選択・「いつの絵か」だけ。
  ⚠ **不透明度は凡例にある。** #R16 の絶対規則——「レイヤー欄にスライダー・日付・フィルタを置かない。
  そのレイヤーの**凡例**にだけ置く」——を `css/intmap.css` が `.layer-dropdown .ec-op{display:none}` で
  強制しており、ECMWF の行は凡例側を持っていなかった。実測、`#lyrrow-ec-temp` の `<input class="ec-op">`
  は**レイヤーを入れても `display:none`** で、9 レイヤーすべての透明度に読み手は到達できなかった。
  他のレイヤーと同じ `.dl-op-row` の形で凡例に入る。
  目盛は 5 点・単位つきで、気温は `imUnitTemp`、風は風速単位の選択に従う。
  **凡例の最大値が LUT と食い違うことは構造上起きない。**
  ⚠ **家族名の箱に全部を積んではならない。** 実測（1280×800・ECMWF 3 レイヤー）: `ECMWF weather` と
  題した 1 枚に 3 つの帯が縦に積まれて 354 px あり、**どのレイヤーの帯かはどこにも書かれていなかった**。
  さらに幅の狭い画面では `ensureLegendMinimize` が floating な凡例を自動的に畳むので、
  箱の中身が全部消えて**「ECMWF 気象」という2語だけ**が残る＝「凡例名が ECMWF 気象・凡例が無い」。
  ⚠ 並べるのは既存のタイラー（`js/data-layers.js` の `tileLegends`）で、**id の接頭辞**
  `data-legend-ec-` で拾う（1つの要素を名指しすると、次にレイヤーが増えた日に古くなる）。
- ⚠⚠⚠ **気温は<b>1つのレイヤー</b>で、切り替わるのは<b>ソースだけ</b>。** 「気温」（`ec-temp`）は
  ECMWF IFS の予報**だけ**を答える。
  ⚠ 以前は**2つの行**があった（ここと `js/data-layers.js` の GIBS ラスタ）。ひとつの量に 2 つの
  スイッチ・2 つの凡例・2 つの日付操作・**2 つの配色**があり、`dl-temp` は削除された（保存済み
  セッションは `js/session-tabs.js` の `RETIRED` 表で `dl-ec-temp` に翻訳される）。
  ⚠ **MERRA-2 再解析（第2のデータ源）は撤去した。** 凡例の `Source` プルダウン・月の時計・
  `js/wx-reanalysis.js`（`imwxre://`）は、それだけを養っていたので一緒に消えている。
- ⚠⚠⚠ **時刻を変えても地図は空にならない。** 新しい時刻は**空いているスロット**に不透明度 0 で組まれ、
  古いスロットは新しいほうが**実際に出てから**外れる（#R284）。⚠ その「出てから」の合図は
  **そのソース自身の `sourcedata` ＋ `e.tile` ＋ `isSourceLoaded`** である
  （**タイルが1枚でも届いたとき**。`isSourceLoaded` だけでは「まだ1枚も頼まれていないソース」でも真になる）。
  ⚠⚠ **どのスロットを建てるかは「いま表に出ていないほう」で決め、露出は世代トークンで守る。**
  スロットの添字を建てた瞬間に反転させると、タイルを待っているあいだその添字は**表に出ているほう**を
  指す——連続してステップすると可視スロットを消してから不透明度 0 の新スロットを作ることになり、
  さらに 1 回目の露出処理が「自分の old」＝**もっと新しい時刻**を消す。落とすのは
  「**いま表に出たスロット以外**」で、追い越された露出処理は**何も出さず何も消さない**。
  ⚠ 同じ規則が風の色面と ECMWF のラスタ・等圧線・矢印の両方に要る（片方だけ直すと隣で同じ穴が開く）。`once('idle')` は
  「**いま持っているタイルについて**描くものが無い」という意味なので、まだ1枚も返ってきていない
  ソースでは**即座に**成立し、古いスロットが外れて読み手は残りのダウンロードのあいだ基図を見る。
  2.5 秒の予備タイマーも同じ側に倒れていた。予備は**12 秒**で、届かないソースが2枚のスロットを
  抱えたままにならないためだけにある——それまでは**古い絵が出たまま**、というのが要求そのもの。
  実測、6 段の時刻ジャンプを 250 ms 刻みで 40 回標本化して、**どちらのスロットも見えない瞬間は 0**。
- **時刻の操作盤のアイコンは<b>描く</b>。** 最初へ（棒＋三角）／1つ戻る（**二重**三角）／再生（**単一**三角）／
  一時停止（2本の棒）／1つ進む（**二重**三角）、そして「現在」は**言葉**。
  ⚠ **再生と「次へ」が同じ字だったことがある**（`⏮ ◀ ▶ ▶ ⦿`）。絵文字・Miscellaneous Technical の字は
  10.5 px で読み手の OS 任せに描かれるので、形の違いを**自分で**持つ SVG にする。
  ⚠ 風の凡例の操作盤と ECMWF の箱の操作盤は**同じ宣言**（`IC`）を読む——1つの時計の2つの見え方である。
- **粒子は凡例のトグルで単独に止められる**（`window.Wind.particles()` / `.setParticles(v)`、
  鍵 `intmap_wind_parts`、**既定はオン**）。このレイヤーは 1 つの場から**色ラスタと粒子の2つ**を
  描くので、従来はアニメーションを止める唯一の手段が「レイヤーごと消す」＝色も失うだけだった。
  ☠ **キャンバスを隠すだけにしない**——`_applyParts()` が rAF ループごと止め、`clearTrails()` で
  残像を消す。「オフ」は見えないことではなく、計算が止まることである。
  ☠ スイッチは**凡例の中**（#R16：1レイヤー専用の操作はレイヤー欄に置かない）。凡例本体は
  毎回 innerHTML ごと差し替わるので、チェック状態は**描画のたびモジュールから読み直す**。
  Atlas も同じ口を叩く（`{"type":"windParticles","on":bool}`）ので、凡例と Atlas が食い違うことはない。
- **同じ筋を「他の場の上」に出す箱は、その場のレイヤーの凡例の中にある。**
  ⚠ **これは風レイヤーのトグルとは別の問い**で、鍵も既定も別（上の `intmap_wind_parts` とは無関係）。
  訊けるのは `PARTS_KEYS` に載っている層だけ——**気温 `ec-temp` / 最大瞬間風速 `ec-gust` /
  海面気圧 `ec-slp` / 降水量（予報）`ec-precip`**（鍵 `intmap_wx_{temp,gust,slp,precip}_parts`）。
  箱を出すのは `windPartsRow(cfg)` で、門はこの表 1 つ——**層を増やすのは表に 1 行足すことだけ**で、
  凡例の箱・`pushWindSolo()` の OR・共有 URL の `wp=`・`window._imWxParts(layerId, v)` が追随する。
  ☠ **既定は場ごとに違う**（`PARTS_DEFAULT`）。**最大瞬間風速・海面気圧・降水量（予報）は既定 ON、
  気温だけ既定 OFF**。前3つは読み手がその場を「そこにある気象システム」として読むので、筋がその
  形（低気圧の渦・前線のシア）を読ませる。気温は「その地点の値」として読まれるので同じ理由が無く、
  筋が u と v の2変数を余計に読む分だけが残る。
  ☠ **保存された答えは既定より強い、両方向に。** 既定が効くのは**鍵が無いとき**だけ
  （`'1'`＝オン・`'0'`＝オフ・無し＝既定）。箱を外した読み手が次の起動で戻されることはない。
  ☠ **降水量（予報）に新しいデータ源は要らない。** 筋が読むのは常に**風の場**で、下に敷かれた
  ラスタが何かとは無関係——だからスカラー場でも筋を持てる。
  Atlas は `{"type":"windParticles","over":"temperature"|"gusts"|"pressure"|"precipitation"}` で同じ口を叩く。
- **風の配色は windy.com 自身の表**（`WIND_ANCHORS`・**27 停留点・0〜104 m/s**・全域 α=1）。
  ⚠ **粒子の濃さ**は速度で決まる（静穏 0.34 〜 最大 0.68 の α に、寿命の三角包絡が掛かる）。
  Canvas2D の代替経路も**同じ比**で描く——上限を下げたら最上位のバケットが到達不能にならないよう、
  バケットの除数も一緒に下げる。
  かつては Windy の**区切り値だけ**を借りて色を書き起こした「相当品」で、実測すると 2 m/s から
  乖離し始め **25 m/s で 133/255**（こちらは赤、Windy は青紫）、45 m/s 以上ではこちらが白に
  飽和する一方 Windy はカーキ→灰だった。⚠ **正本は宣言表ではなく<b>塗る関数</b>**——
  `W.colors.wind.defaultColorGradient` は 20 停留点だが `RGBA(v)`（0〜104 m/s を 2,048 段に
  前計算した表）は**その線形補間と一致しない**（実測 32.25 m/s で 20/255）。#R288 が気温で見つけた
  形がそのまま再現した。→ `RGBA` を 0.1 m/s 刻みで 1,041 点標本化し、線形補間でそれを再現する
  最小の停留点集合に落とすと **27 点・最大チャネル誤差 3/255**。104 m/s より上は Windy と同じく灰。
  SDK 既定の風配色は最初の 7 m/s で α を 0→1 に上げるため静穏域が「穴」になるが、
  この表は**全域不透明**（Windy 自身がそうである）。プロトコルは**この表で**登録する。
- **気温の配色も同じ形で、参照は<b>測ったもの</b>**（`TEMP_ANCHORS`・23 停留点・°C）。
  読み手が渡した参照画像は windy.com の既定の気温オーバーレイで、その配色表は Windy 自身の
  「Customize color scale」に出る値である。目視ではなく実測した——`W.colors.temp.defaultColorGradient`
  が 13 停留点（ケルビン）、`_precomputedGradient.RGBA(k)` が実際に塗られる色。203–320 K を 0.05 K
  刻みで標本化し、**線形補間でそれを再現する最小の停留点集合**に落とすと 23 点で
  **最大チャネル誤差 3/255**。0.00–0.85 °C に停留点が 4 つ集まっているのは雑音ではなく、
  Windy が氷点の等温線を「1 度未満で青から緑へ」と強調しているためで、そのうち 1 つ（0.40）を
  落とすと誤差は 3 → 7 に上がる。⚠ SDK の家族名 `temperature` に登録するので、`temperature_2m`・
  `surface_temperature`・土壌温度が**同じ表**を読む。
  刻みは **0.05 °C**（2,341 段）——最も急な 0.35→0.75 °C 区間で青が 0.4 度に 92 単位動くため。
- **気圧・降水量・露点も同じやり方で測った**（#R439・`PRESSURE_ANCHORS` 16 点 hPa /
  `PRECIP_ANCHORS` 17 点 mm / `DEW_ANCHORS` 24 点 °C）。**変更前に何が塗られていたか**——
  気圧は SDK 自身の 17 点 940…1060 hPa（青→白→赤）、降水量は SDK 自身の 15 点 0.01…30 mm（α 傾斜つき）、
  そして**露点は配色表が存在しなかった**: `mQ` は `dew_point_2m` → `dew_point` → `dew` の順に引くが
  SDK はそのどれも宣言していないので `_Q` の `?? Q.temperature` に落ち、**露点レイヤーは
  「気温の配色表」で塗られていた**（実測: SDK の配色表キーは 24 個、`dew` を含む名前は 0 個）。
  ⚠ **宣言表は塗る関数ではない**、が今回は**両方向に**効いた——Windy 自身の `initialColorGradient` を
  線形補間して `RGBA(v)` と比べると、気圧 **2.4/255**・雨 **10/255**・露点 **25/255**。
  そこで**前計算バケット 1 個につき 1 点**（`steps` は 4000 / 1024 / 2048）で標本化した
  ——これより細かく取ると量子化の階段を読み戻して当てはめがそれを追う（同じ表が 81 点になった）。
  結果は **16 / 17 / 24 点**、最大チャネル誤差 **1.82 / 1.97 / 2.64**。
  ⚠ **区切り値は再標本化の刻みに<b>載せる</b>**（0.1 hPa / 0.02 mm / 0.05 °C）。`rampFrom` は
  固定刻みで再標本化するので、刻みに載っていない区切り値は**地図が一度も塗らない色**であり、
  #R284 の「色はそのまま」が近似になる。実測: 載せ替えの代償は最大 0.8/255、
  得るものは**全区切り値が自分の色にぴたりと落ちること**（`tests/r439-checks ①b` が実行して確かめる）。
  ⚠ 3 つとも**全域 α=255**（Windy 自身の表が `opaque:true`）。降水量は 0 mm でも
  `rgb(111,111,111)` の灰を**塗る**——Windy の雨オーバーレイがそうであり、それが
  「RGB レベルで対応」の中身である。透明度は凡例のスライダーで従来どおり変えられる。
  ⚠ **登録キーは `mQ` が実際に引く名前**（`pressure` / `precipitation` / `dew_point`）。
  間違ったキーに置いた表は**誰にも読まれず、誰も何も言わない**——露点がそうなっていた。
  ⚠ この 3 本は**評価時ではなく初回使用時に組む**（`windyRamp(family)`・memo つき）。
  風と気温の 3,382 段に加えて 6,600 段あり、起動時には 1 段も要らない。
- ⚠⚠⚠ **SDK の配色表は<b>補間しない</b>ので、17 色の表は 17 本の帯になる。** 出荷されているコードで
  `rgba` は `colors[floor((v−min)/step)]`、`breakpoint` は `colors[binarySearch(breakpoints, v)]`——
  どちらも最近傍の抽選である。一方 `legend()` が作る CSS `linear-gradient` は**補間される**ので、
  **凡例だけが滑らかで地図が階段**という、色と名前が食い違う状態になっていた。
  → `rampFrom(WIND_ANCHORS, 0.1)` が**同じ色**を 0.1 m/s 刻みへ**再標本化**する（1,041 段）。
  節の値はそのまま自分の色に着地するので「色はそのまま」は近似ではなく厳密、あいだは sRGB で線形。
  **データは一切変わらない**（同じファイル・同じ 9 km 標本・同じ風速）。変わったのは色の分解能だけ。
  実測: 隣り合う段の最大チャネル差 **4/255**、大西洋上の走査線で拾った 51 画素のうち **46 画素**が
  17 色の表では作れない色だった。⚠ 601 段の帯を CSS に書くと 24 kB になるので、`legend()` は
  **描画用の停止点だけ**を 64 以下に間引く（`stops` は完全なまま）。
  ⚠⚠ **画面の1画素は「点の風速」ではなく「その画素が覆う空気」の色である。** ラスタは texel から
  `raster-resampling: linear` で描かれ、`valueNow()` は格子を**点**で内挿する——この2つは別の問い。
  17 本の帯だったころは両方が同じ帯に落ちて**同じ色**になっていたが、0.1 m/s では 1〜8 段ずれる。
  実測（z3・150°E 20°N・上に載る層を消して 81 画素）: **78 画素が表の項と厳密に一致**する一方、
  **点の値の項と一致したのは 78 中 20（26%）**、**1画素以内のどれかの風速の項と一致したのは 78/78**。
  → 検証は「色は厳密・速度は画素の覆う範囲」で行う（`tests/helpers/wind-ramp.js`）。
- ⚠⚠ **気象の面は昼夜シェーディングより上に置く。** `im-night-shade` は装飾、気象はデータ。
  実測（z3・150°E 20°N・夜側）：LUT が要求する `rgb(40,130,180)` に対し実際の画素は `rgb(15,43,64)`＝**0.36 倍**。
  `IntMapECMWF.before()` が夜側スタックの直後を返し、`lift()` が**毎 idle** で位置を再主張する
  （`js/night-side.js` は自分の層をタイマーで貼り直すため）。
- ⚠⚠ **断られたレイヤーは、断られたままにしない。** `addField`／`addLayer` はスタイルが層を受け付けられ
  ない間は false を返すので、**1回呼んで終わりにすると「粒子は出るが色がつかない」になる**
  （実測、梯子なしでは 150 秒待っても付かない／梯子ありで 6.9 秒）。約 16 秒のポーリング＋次の `idle`、着いたら止める。
  時刻変更時の再構築は**先に層を消す**ので同じ梯子が要る。
- ⚠⚠ **読み手は1つ、だから待ち行列も1つ。** SDK の `ensureData` は毎回 `setToOmFile` で**共有リーダを
  張り替える**ので、違うファイルの読み込みが時間的に重なると互いを壊す（同じ state 同士は
  `state.dataPromise` が重複排除するので安全）。`IntMapECMWF` が始める読み込みは全部1本の鎖に並ぶ。
- ⚠⚠ **レイヤーが手放してよいのは自分のフレームだけ**（`release(variable)`）。無条件の `release()` は、
  別の変数の読み込みが飛んでいる最中だとそれを黙って無効にし、地点値が理由もなく空欄になる。
  ⚠ `js/map-ui.js` は起動後 700 / 1,800 / 3,200 ms に保存済みレイヤー集合を再適用するので、
  これは稀な競合ではなく**通常の起動で起きる**。
  ⚠⚠⚠ **「時刻を変えたときの `release()` は無条件で正しい」——これは誤りだった。**
  正しかったのは、その行が `setIndex` の中で**同期に**走っていたあいだだけ。`COALESCE_MS` ぶん
  遅らせた瞬間、それは**140 ms 後の未来**に着地するようになり、その窓の中で始まった読み込みを
  （`release()` が `loadingKey` も消すので）黙って無効にする。**同じ欠陥の時間軸版**である。
  実測（#R287）: 起動後の最初の1歩は必ず負ける（冷えた場は 7〜9 秒、窓は 140 ms）——`valueNow` が
  null を返し、1.5 秒後の再試行は 25.27 °C を返した。暖まった場は窓の内側で解決するので影響を受けない。
  ⚠⚠⚠ **(#R288) そして `fireTime()` は<b>古いフレームすら捨てない</b>。** 窓を外しても、
  **より新しい要求に追い越された読み込み**は同じように null を返していた——ハンドラが
  **自分の復号したフレームではなくモジュール変数 `held` を返していた**からで、
  実測（本番ビルド）読み込み開始 50 ms 後に `release()` を呼ぶと **8.3 秒かけてデータは届いた
  うえで結果は null**。→ ⑴ `load()` は**自分のフレームを返す**（どれが「今のもの」かは単調な
  `seq` が決め、`release()` もそれを進める）、⑵ 古いフレームは**新しいものが着いたら置き換わる**
  ——捨てると地点値が空欄になり、同じ時刻をもう一度復号することになる。
- ⚠⚠⚠ **読むのは<b>読み手が見ている緯度帯</b>であって惑星ぜんぶではない。**
  実測、全球 1 フレームは **6,599,680 標本・274 レンジ要求・17.96 MB・7.8〜8.4 秒**で、粒子が
  1 つも動き出す前にそれを待っていた——「重すぎる」の実体はこれで、描画ではない（レンダラ自身は
  粒子 1,980 個で 2.65 ms／フレーム）。ECMWF の領域は**縮約ガウス格子**なので、SDK の
  `getCoveringRanges` は**緯度でしか**絞れない（経度は 1 本の平坦な添字）。25°–46°N の帯なら
  **935,400 標本・25 要求・1.64 MB**——**同じ 9 km 間隔・同じ数値・同じ色**で、落とすのは画面に
  無い部分だけ。⚠ 帯は**全経度**を含むので、東西のパンでは読み直さない。
  ⚠⚠⚠ **「1枚も持っていない」と「地球を持っている」を同じ値で表してはならない。** `heldBand()` は
  どちらにも `null` を返し、`bandCovers(null, …)` は「地球は全部を覆う」＝真なので、
  **フレームを1枚も持っていない起動直後に narrow 化が飛ばされていた**——そして起動時の視野は地球なので
  `bandFor` も `null`＝**全球 13,199,360 標本**。つまり「最初の読みは画面の緯度帯」という経路は、
  書かれてはいたが**初回に一度も通っていなかった**。持っていないことは `false` で言う。
  ⚠⚠ **色が出るまで、絵に要らない読み込みを始めない。** 読み手は1本しかいないので、
  ⑴ 次の時刻の先読み（**別のファイル**を指すので読み手を張り替える）⑵ 視野全体へ広げる2本目の帯
  ⑶ カーソル下の数値の暖機 の3本は、**色のスロットが実際に表に出てから**走らせる
  （12 秒の予備タイマーで諦めた場合も必ず走る＝永久に走らない経路を作らない）。
  粒子のための最初の読み込みは**遅らせない**——遅らせれば粒子が遅くなる。
  ⚠ 帯は**待ち時間（レイテンシ）律速**になるので、SDK 自身の `prefetchVariable`
  （`prefetchConcurrency: 1000`）で先に温めてから読む。実測、
  **全球 8,436 ms ／ 帯のみ 2,829 ms ／ 帯＋先読み 1,254 ms**。
  ⚠⚠⚠ **冷たい1時刻の待ち時間の3分の2は、データではなく<b>ファイルの索引を取る最初の1回</b>である。**
  `fetch` に細工して Range ヘッダごと時間を測ると、一度も訪れていない予報時刻はこう割れる（本番・
  起動時の視野・時刻 30）: メタデータ 2 本 **526 / 522 ms**（並行）→ **ファイル末尾の 64 kB を1本
  4,130 ms** → データ 93 本・5.63 MB で **約 1,480 ms** → 復号 **1 ms**（＝**復号は待ち時間ではない**）。
  1 時刻＝1 ファイル（約 114 MB）で、**CDN がまだ配置していないオブジェクトへの最初のレンジ要求**が
  4〜5 秒かかり、同じオブジェクトの2本目以降は 26〜100 ms で返る。
  → **読む前にファイルに触る**（`touch`）。軸が決まった瞬間に、SDK の1本しかない読み手の待ち行列の
  **外側で**、そのファイルの**末尾へのレンジ要求を1本**投げる。実測（同じ本番ページ・同じ視野）:
  **触っていない時刻 6,135 ms（索引 4,130 ms）／触った時刻 1,670 ms（索引 11 ms）**。
  ⚠⚠⚠ **その 4〜5 秒を払っているのは<b>要求そのもの</b>であって、大きさではない。**（#R308）
  本番で並べて測ると: `bytes=0-0`（先頭 1 バイト）**562 ms** で末尾は冷たいまま／`bytes=-1`
  （**末尾 1 バイト**）**5,081 ms** で、そのあとの 64 kB は **188 ms**／`bytes=-65536` **4,867 ms**。
  **1 バイトの suffix range が 64 kB と同じだけオブジェクトを配置させる**ので、触るのは
  **`bytes=-1`** である。読み手が来たときはブラウザのキャッシュではなく CDN のヒット（**27〜50 ms**、
  配置されていなければ **4,483〜5,195 ms**）——**20 ミリ秒**を、1 時刻あたり 4 分の 1 メガバイトと
  引き換えにしている。
  ⚠⚠⚠ **そして冷たいオブジェクトは<b>並行に</b>配置できる。** 12 本を同時に投げて実測 **5,329 ms・
  本文は 12 バイト**（順に投げれば約 55,000 ms）。だから触る本数は「バイトがいくらか」ではなく
  「読み手が次に届きうるのはどこまでか」で決める——**進行方向へ `TOUCH_AHEAD`・逆へ `TOUCH_BACK`**
  （＝12 時刻。再生中は `TOUCH_PLAY_AHEAD` まで伸ばす。`playMs` 700 ms で毎時刻を要求されるので、
  8 時刻先までの窓は 6 秒で追い抜かれる）。
  ⚠ **軸の 109 時刻を全部は触らない。** 配置は CDN にさせる仕事なので、読み手が向かっていない時刻を
  配置させるのは、無償の公開サービスに理由の無い仕事をさせることになる。
  ⚠ **「起動から」の答えは、起動時に触ることである。**（#R308）#R307 はこれを明示的に見送った——
  「`fetchMeta` は時刻スライダーとニュース年表のために起動時に走るので、そこから触ると気象レイヤーを
  一度も点けない利用者に 256 kB を払わせる」。**1 バイトになったので、その理由は消えた**。
  `fetchMeta` が成功した時点で**開く時刻の 1 本だけ**触る（同じホストへ `latest.json`（3 kB）を
  既に投げている。その 3,000 分の 1 である）。窓のほうは従来どおり `ready()`——実際に読む人が
  現れたとき——と、`sdk` が既に読み込まれているときの `setIndex` だけ。
  ⚠⚠⚠ **SDK のブロックキャッシュは、読み込みが<b>まだ使っているブロックを捨てて</b>いた。**
  `FileReader` が既定で作るのは `BlockCache(64 kB, 128)`＝**8 MB の天井**で、帯1本の作業集合は
  **8.63 MB**。実測、1回の帯読みで **195 リクエスト（全部ちょうど 64 kB）・12.19 MB** が飛び、
  そのうち **57 本は同じ範囲の2度目**だった。→ **同じ 64 kB のまま、512 個（32 MB）持てるようにする**
  （`blockCache`）。⚠ **ブロックの大きさは上げない**——`blockSize()` は**キャッシュが持つ単位**であると
  同時に、素のままでは**そのまま HTTP リクエストの大きさ**にもなるので、大きくすると帯の両端で
  取りすぎるし、**同じ読み手を共有するラスタタイル**も道連れになる。実測、512 kB ブロックは欲しい
  6.31 MB を **9.00 MB** にする。天井は上げても取りすぎない（全球1枚は約 16 MB で収まる）。
  ⚠⚠⚠ **ただし「64 kB でよい」ではなかった——64 kB は<b>大きさ</b>ではなく<b>回数</b>だった。**
  ブラウザから同じホスト・同じファイル・同じ 8 MB を、**要求の大きさだけ**変えて測ると:

  | 要求の刻み | 本数 | 所要 | 実効 |
  |---|---|---|---|
  | 64 kB | 128 | 2,448 / 2,341 ms | 3.3 / 3.4 MB/s |
  | 64 kB（同時 24 本） | 128 | 3,713 ms | 2.2 MB/s |
  | 256 kB | 32 | 1,255 ms | 6.4 MB/s |
  | 512 kB | 16 | 723 / 683 ms | 11.1 / 11.7 MB/s |
  | 8 MB | 1 | 455 / 708 ms | 17.6 / 11.3 MB/s |

  **バイトはどの行も同じ。** レンジ要求には大きさと無関係な固定費があり、1 時刻ぶんの風 8.6 MB を
  **139 本**に割って払っていた。→ **キャッシュが持つ単位（64 kB）と、ネットワークに頼む単位を
  切り離す**：`coalesceBackend` が、同じマイクロタスクの中で来たブロック要求のうち**ファイル上で
  隣接するものを 1 本にまとめて**発行し、返ってきたバッファを各ブロックへ切り分ける
  （`RUN_MAX` で頭打ち・**中断シグナルが同じものだけ**まとめる・切り出しは `slice` で**コピー**する
  ——64 kB の住人が数 MB の要求バッファを掴んだままにならないように）。**取りすぎは 1 バイトも無い**
  （まとめるのは「頼まれたブロック」だけ）。実測、同じ帯読みが **139 本 → 19〜24 本**（8.63 MB は不変）。
  この経路は `rd.reader.backend.backend`（＝SDK の HTTP バックエンド）を包むだけで、SDK には手を
  入れていない。プロパティ名（`reader` / `backend` / `getBytes`）はコンストラクタで代入されるので
  最小化を生き延びる。
  ⚠⚠⚠ **そして 6 ラウンドのあいだ、測られていた読み込みは<b>2 本のうち 1 本</b>だった。**
  上の全部は**粒子の帯**の話である。色面のタイルは**別の読み込み**で、SDK の
  `omFileReader` を通り、`dataOptions.bounds` を `currentBounds` という 1 つのモジュール変数から
  作る。これが未設定だと `getRanges` は `[{0,ny},{0,nx}]`＝**格子ぜんぶ**を返し、
  設定するのは `updateCurrentBounds` ただ 1 つで、このアプリは**一度も呼んでいなかった**。
  実測（本番ビルド・SDK の読み手を計測・日本上空 z6・1 ステップ）:

  | | 標本数 | 1 ステップの通信 | `readVariable`（主スレッド） |
  |---|---|---|---|
  | 粒子の帯 | 535,608 | — | — |
  | **色タイル** | **6,599,680（惑星ぜんぶ）** | **9.76 MB / 31 要求** | **1,537 ms** |
  | 色タイル（`updateCurrentBounds` 後） | **1,205,092** | **2.82 MB / 11 要求** | **628〜946 ms** |

  → プロトコルのハンドラが毎回 `applyTileBounds(url)` で視野を渡す。**日本 7 枚のタイルが
  地球ぜんぶの復号から作られていた**のが、日本の分だけになる。絵は同一（同じファイル・同じ
  9 km 間隔・同じ配色・同じタイル）。
  ⚠ **箱は「視野 ∪ いま要求されているタイル」**。`getBounds()` は*見えている*範囲で、
  MapLibre が*取りに行く*のは視錐台だから、傾けた視点ではタイルが箱の外に出うる——
  外に出たタイルは遅い絵ではなく**欠けた絵**になる（`tileBox`。⚠ `tile2lon` は右端を −180 で返す）。
  ⚠⚠ **視野が実質「全球」なら箱を言わない**（`WORLD_RATIO`＝格子点の 9 割。⚠ **度ではなく標本数**
  で数える——縮約ガウス格子では行の点数 ∝ cos φ）。起動時の視野は地球で、そこでは
  **粒子側の全球読みが色タイルの状態をそのまま使っている**（`stateKey` が SDK の
  `fileAndVariableKey` と同一なので、帯なしの読み込みは同じ鍵になる）。箱を言うとこの共有が切れ、
  **同じ 6,599,680 標本を 2 回復号する**ことになる——0.33% を惜しんで 1 回ぶんの復号を払う取引。
  ⚠⚠⚠ **そのタイルは、開くところからやり直していた。** `ensureData` は
  `await A.setToOmFile(url)` から始まり、SDK のリーダーはプールの外にいたので、
  **粒子側が `setIndex` で既に開いたファイルを、色タイルがもう一度開いていた**。実測、
  1 ステップの内訳は `setToOmFile` **9 ms → +629 ms** ／ `readVariable` **638 ms → +1,418 ms**
  ——3,073 ms のステップのうち 629 ms が、済んでいる HEAD と末尾読みと変数ツリー走査の再実行だった。
  → `tileReader` が SDK インスタンスの `omFileReader` を**プールへの委譲**に差し替える
  （`config` と `cache` は SDK 自身が読むので転送する。`dispose` は**何もしない**——プールが寿命を持つ）。
  ⚠ 並び順の意味は SDK 自身のもの（シングルトンを誰でも張り替えられる）から変えていない。
  変わるのは、張り替えても相手のファイルの `dispose()` が起きないことだけ。
  ⚠⚠⚠ **12 枚のタイルは、場を 12 回複製していた。** SDK は色付けをワーカーで行うが、
  `requestTile` は `postMessage(E)` を**転送リストなしで**呼ぶので、`E.data` の
  `{values, directions}`（各 Float32Array・全格子点）が**1 枚につき約 53 MB 構造化複製される**。
  実測（起動時の視野・1 ステップ）: **12 枚の送出で 1,276 ms の単一ロングタスク**。
  費用は枚数で決まるので、**タイルを大きくする**：`tile_size`（SDK・64/128/256/512/1024/2048 のいずれか）と
  MapLibre のソースの `tileSize` を**両方 1024** にすると、MapLibre は 1 段低いズームのタイルを使う——

      画素密度 = S·2^Z / (512·2^M),  Z = round(M + log2(512/S))
      S=512, Z=M   → 1          S=1024, Z=M−1 → 1

  ——**同じ密度・同じ色・同じ 9 km 間隔**で、枚数は 4 分の 1（実測 12 → 3〜4）。
  ⚠ **2048 にはしない**（1 枚が RGBA テクスチャなので 1024 で 4 MB・2048 で 16 MB）。
  ⚠⚠ **狭い画面では大きいタイルが画面からはみ出す。その代価は測って承知の上で払っている。**
  実測（390×844・z6・交互に 2 セッション × 3 歩・中央値）:

  | | 色面が出るまで | タイル | ラスタ化される画素 |
  |---|---|---|---|
  | origin/main（512） | 2,944 ms | 3 枚 | 0.79 Mpx |
  | R325（1024） | **1,190 ms** | 2 枚 | **2.1 Mpx** |

  画面は 0.33 Mpx なので、はみ出しは 2.4 倍 → **6.4 倍**になる。それでも 2.5 倍速いのは、
  **主費用が画素ではなく枚数の側にある**から（上の 53 MB の複製）。増えた画素はワーカーの仕事と
  GPU のテクスチャであって、主スレッドの時間ではない。⚠ MapLibre の `maxTileCacheSize` は**枚数**の
  上限なので、保持されるバイトはタイルが大きいぶん増える（見えている枚数の約 5 倍が上限）。
  ⚠ **ベクタのタイル（等圧線・矢印）には渡さない**——そちらの `tile_size` は MVT の extent であって
  画素数ではない。だから `omUrl`（ベクタ）と `omRasterUrl`（ラスタ）が分かれている。
  ⚠ `tile_size` は SDK の `DATA_RELEVANT_PARAMS`（`['variable']` のみ）に入らないので、
  **キャッシュの鍵も読み込む範囲も変わらない**——変わるのは描かれ方だけ。
  ⚠⚠ **次の時刻のファイルは、読むより先に開いておく**（`openAhead`）。開くのは HEAD ＋ 末尾 64 kB
  1 本で、**進行方向の 1 ファイルだけ**。実測、ステップの `setToOmFile` が **389 ms → 0 ms**。
  ⚠ **バイトの先読み（`readAhead`）は今も「軸が動いてから」**——推測でメガバイトは払わない。
  開く費用は 1 時刻あたり 64 kB（その 1 時刻自身の 8.6 MB に対して 0.7%）で、それは述べる。
  ⚠ 保持しているフレームは**要求された帯を含んでいれば**再利用する。帯 `null` は全球を意味し、
  全球はすべてを含む——だから任意地点を要求する呼び出し（`valueAt`）は今までどおり全球を得る。
  ⚠⚠⚠ **手元に残すのは「変数ごとに1枚」ではなく「予算に入るだけ」。** `keepFrame` は同じ変数の
  **別の時刻**まで捨てていたので、「1時間進めて戻す」が必ず再ダウンロードになっていた。置き換えるのは
  **同じ鍵で、新しい帯が古い帯を覆うもの**だけにし、あとは `FRAME_SAMPLES`（24e6）の LRU に任せる。
  帯なら **7〜21 時刻**が残る＝再生で通った時刻の往復は**通信ゼロ**。
  ⚠⚠⚠ **追い越された読み込みは、順番が回った時点で捨てる。** `serial()` の待ち行列に入ったまま
  「もう自分は古い」を確かめていなかったので、スライダーを 20 コマ引きずると **20 回とも最後まで
  通信してから**捨てられていた。世代を見て**1バイトも読まずに**戻る（20 → **1**）。
  ⚠ 戻り値を falsy にしてはならない——`js/weather.js` はそれを「取得失敗」と読んで 900/2,000/4,000 ms の
  再試行に入り、使い切るとトーストを出す。その変数のフレームを1枚返せば、`sampler()` が正しく判断する。
  ⚠⚠⚠ **視野いっぱいへ広げるのは「段」で行う。** `widen()` は時刻を変えるたび `band()`（世界ズームでは
  `null`＝**地球 13,199,360 標本 ≈ 18 MB**）を読み直していた。→ **静止 900 ms ごとに1段**、時刻が動けば
  段はやり直し。⚠ **段は幅ではなく標本数で切る**——縮約ガウス格子では行の点数 ∝ cos φ なので、
  「半幅を2倍」は世界ズームで地球の **86.6%** を掴み、段を挟むと合計が**増える**。目標の 60% を超える段は
  目標そのものにする。⚠ **広い読みを省略はしない**——読み手がその視野に留まれば最後は必ず `band()` に着く。
  ⚠⚠ **粗い領域へ落として速くしない。** `ecmwf_ifs025`（0.25°・標本 1/6.4）は実在するが `valid_times` が
  **3時間刻み（49本）**で、既定の `ecmwf_ifs`（**1時間刻み・109本**）と軸が違う。使えば読み手が選んだ
  時刻がずれる——それは「品質を保ったまま速く」ではない。
  ⚠ `lift()` が呼ぶ `_layerIds()` は `getStyle()`（スタイル全体のシリアライズ）なので、**メモ化して
  `styledata` で捨てる**。以前は idle ごとに最低2回（move を挟むと最大12〜18回）走っていた。
- ⚠⚠⚠ **予報時刻は「ジェスチャに1回」動く。** `<input type="range">` は**ドラッグの1画素ごと**に
  `input` を発火し、その一つひとつが層の作り直しと 26 MB の場の読み込みを1本ずつ待ち行列に積んでいた
  ——**読み手が指を止めた時刻は行列の最後**で、手前には誰も見ない9枚が並ぶ。それが
  「未来や過去に変えたときの読み込みが異常に遅い」の正体である（作業が遅いのではなく、
  **既に用済みの絵のための作業**だった）。→ 軸のイベントは2つ:
  `index`（**即時**・時刻の文字と目盛だけ）と `time`（軸が `COALESCE_MS` 静止してから1回・**取得を伴う**）。
  実測、12 段のドラッグで `index` 12 回・`time` **1 回**。
  ⚠ ボタンと `step()` は `{now:true}` で**即時**に撃つ（クリックは掃引ではない）。
  ⚠ `index` は**箱を作り直さない**——作り直すと、指がつまんでいる `<input>` 自体が差し替わる。
- ⚠⚠⚠ **時刻を変えたときに粒子を消してはならない。** 旧実装は `time` の先頭で
  `renderer.setField(null)` を呼んでいたので、**ドラッグの1画素ごとにアニメーションが消えて戻っていた**
  ＝報告された「点滅」。粒子が読む場は**それが作られた時のフレームを閉じ込めたクロージャ**なので、
  新しい時刻が着地するまで**古い時刻のまま正しく動き続ける**のが正しい。
  実測、12 段のドラッグ中に採った 22 フレームすべてで描画継続（最小 1,513 セグメント）。
- ⚠⚠ **ラスタも「消してから足す」をしない。** 各 ECMWF レイヤーは**2つのスロット**を交互に使い、
  新しい時刻を不透明度 0 で隣に組み立ててから、地図が落ち着いた時点で古いほうを落とす
  （アニメーション風の色面が以前からやっていることと同じ）。
- **隣接フレームの先読みは「時刻変更時」だけ。** 1 フレームの暖機は画面のフレームと同じ範囲読み込み
  （実測 410 リクエスト・約 27 MB）を要求するので、再生器に触っていない読者には課さない。
- ⚠⚠⚠ **暖機は「読まれる範囲」を暖める。** `prefetchVariable(v, null)` は**変数まるごと＝全球**を
  暖める。画面のフレームも全球だったあいだはそれで正しかった（#R288）が、#R288 以降その場は
  **視野の緯度帯**（93.5 万標本 対 660 万）なので、3 変数ぶんの全球暖機は **約 80 MB を、1.6 MB
  で足りるステップの前に**並べることになる。本番実測（風＋気温・z4.5）: 新しい時刻の場が
  **39 秒たっても来ない**。→ 暖機は `load()` と**同じ bounds** で作った state の `ranges` を使う。
  実測 **1,364 ms / 742 ms**。`null`（全球）は世界ズームとラスタタイルのための正しい既定として残る。
  ⚠ 「もう暖めた」の印は**ファイル＋帯**で持つ（帯の暖機が、していない全球を「済み」に見せない）。
- ⚠⚠⚠ **暖機は、暖めている当のものの<b>前に並んではならない</b>。** このモジュールの読み込みは
  **1 本の列**を通る（SDK のリーダーが 1 つだから）。隣の時刻の先読みと、カーソルの読み取り欄が
  欲しい帯が、**粒子が飛んでいる場の前に**並んでいた。同一セッションの A/B、1 ステップから新しい
  時刻の場が手に入るまで: z4.5・風だけ **711/447 → 396/515 ms**、**z4.5・風＋気温ラスタ
  30 秒たっても来ない → 1,073/1,737 ms**、世界ズーム 13.6/18.5 → 11.6/14.3 s（回線律速・差なし）。
  → 暖機は軸が**止まってから** 2.5 秒で走り、さらにステップが来たら**予定を置き換える**。
- ⚠⚠⚠ **1 本の列であることと、FIFO であることは別の決定である。** 上の「前に並ばない」は
  **開始のタイミング**を遅らせただけで、いざ並んだあとの**順番**は先着順のままだった。この列を通る
  読み込みは 2 種類ある——**読み手が待っているもの**と、このモジュールが自分で始めるもの
  （視野へ広げる段・次の時刻の暖機）。世界ズームでは後者が**両方とも地球**を要求するので、
  時刻の1ステップは毎回 18 MB の後ろに並んでいた。実測（起動時の視野・軸を1段ずつ）:
  **7,050 / 7,942 / 8,270 ms**、既に手元にある時刻は **45 ms**——待っていたのは通信ではなく**列**。
  → **同じ「1度に1本」のまま、レーンを2本にする**（`serial(fn, bg)`・`qHi` / `qLo`）。
  読み手の読み込みが先、モジュール自身の読み込みは後。⚠ **走り始めたものは取り消せない**
  （SDK のリーダーに中断が無い）ので、もう半分は「背景の読み込みを小さくする」ことである。
  ⚠⚠⚠ **ただし速くはなっていない。** 「改修後 1,501 / 684 / 1,665 ms」は**私のブラウザの HTTP
  キャッシュ**だった——同じオリジンで何度も走らせた結果、その時刻の `.om` のバイト範囲が既に
  載っていた。**一度も訪れていない時刻**で前後を測り直すと **前 6,849 / 6,357 / 6,858 ms ／
  後 6,699 / 6,779 / 6,784 ms＝差は無い**。世界ズームで「段が走っている最中に1段送る」を狙って
  測っても **6,705 → 6,025 ms** で雑音の範囲。**冷たい1段は帯のレンジ読み込み（約6.5秒）が
  支配的**である。⚠ 手元にある時刻へ戻るのが **41〜46 ms** なのは #R299 のフレーム LRU であって
  この改修の成果ではない。⚠ **前へ進む暖機は改修前から効いている**（9秒空けて前進: 前 2,805 /
  2,299 ms・後 4,079 / 1,891 ms — どちらも冷たい 6.5 秒より速い）。
  ⇒ **ここにある変更は構造として正しいが、速さの主張はしない。**
  ⚠⚠ **「同じ手順」は「同じ条件」ではない**——2回目の実行は1回目が温めたキャッシュの上で走る。
- ⚠⚠⚠ **そして「リーダーは 1 つ」は SDK の掟ではなく、このファイルの 1 行だった。**
  `ensureData(state, reader, …)` は**リーダーを引数で受け取り**、`WeatherMapLayerFileReader` は
  SDK が公開している。**ファイルごとに 1 つのリーダー**（`readerFor` の LRU・`READER_MAX`）にすると、
  別ファイルどうしが互いを `dispose()` する衝突は**源から消える**。ブロックキャッシュは共有してよい
  ——SDK の鍵は `hash(url) ^ hash(eTag) ^ hash(lastModified) + ブロック番号`なので、別ファイルが
  ぶつかることはなく、同じファイルの 2 本は取ったブロックを共有する。
  ⚠⚠ **開き直しはただではない。** `ensureData` は**呼ばれるたび無条件に** `setToOmFile` するが、
  その中身は `dispose()` → **HEAD 1 本** → 末尾の読み出し → 変数ツリーの走査である。実測、1 ステップに
  **HEAD が 2〜3 本**（帯の暖機・色タイル・広げる段。それぞれ 389 / 576 / 236 ms）、そして
  **バイトがすべてキャッシュにある時刻へ戻る操作が 2,118 ms、そのうち HEAD 1 本が 1,870 ms で
  ほかに通信は無かった**。→ `pinReader` が `setToOmFile` を**冪等**にし（同じ URL なら飛行中の
  約束をそのまま返す）、`openReader` を **`setIndex` の中で**呼ぶ——ファイル名が決まった瞬間で、
  読み込みが要求されるより前である。**色タイルが使う SDK 側の 1 本にも同じ栓をする**
  （`registerProtocol`）——タイルは MapLibre から直接呼ばれるので `serial()` の外におり、
  同じファイルの 2 枚が互いのリーダーを `dispose()` し得た。
  ⇒ 列は残るが、意味が変わった。**正しさのための直列化ではなく、帯域の割り当てである**：
  読み手が待っている読み込みは**背景の読み込みが走っていても即座に始まり**（`runHi`）、
  背景の読み込みは**読み手が何も待っていないときにだけ始まる**（`runLo`）。
  #R305 が「取り消せない」と書いた半分は、取り消す必要がなくなることで解けた。
- ⚠⚠⚠ **隣の時刻は「暖める」のではなく「読む」。** `prefetch` はバイトをブロックキャッシュに載せる
  だけなので、ステップは**開き直し・索引の走査・復号**をそのまま払っていた（実測、1 ステップ
  **2,107 / 2,168 / 2,204 ms**——手元にあるフレームは **45 ms**）。しかも 1 本のリーダーを共有して
  いたため**画面の前に並ばないよう 2.5 秒遅らせる**必要があり、2 秒ごとに送る読み手には一度も
  届かなかった。→ `readAhead(VAR, 次の時刻, nearBand()||band())` が**同じバイト・同じ帯・同じ向き**を
  読み、フレームを保持する。
  ⚠⚠⚠ **走るのは「粒子の場が手に入った瞬間」であって「色が表に出た瞬間」ではない**（#R314）。
  #R298 がこの合図を色に結んだ理由は 1 つだけ書かれていた——「SDK のリーダーは 1 本しかないので、
  別の時刻を読むとタイルからリーダーを取り上げてしまう」。#R310 が**ファイルごとに 1 本**にして
  タイル側の 1 本にも栓をした時点で**その理由は消えていた**（#R310 自身の注記も「もう誰の前にも
  並べない」と書いている）。ステップの 2 つの半分を別々に測ると費用が桁違いで——
  **帯の読み込み 513 / 521 / 534 / 537 ms** に対し **色タイル 1 枚 1,266 / 1,381 / 1,772 ms**
  ——遅いほうを合図にすると先読みは**約 2.1〜2.6 秒後**に始まり、**1.2 秒ごとに送る読み手には
  一度も間に合わない**（origin/main の実測: 0 / 1,180 / 0 / 1,279 / 0 / 1,724 ms ＝1歩おきに全額）。
  ⚠ **軸が動いたときだけ**（`opt.step`）——8.6 MB は当て推量で払う額ではない。
  ⚠ **`seq` に参加しない**：まだ誰も居ない時刻は定義上いちばん新しいので、世代を上げれば**画面の
  読み込みを追い越して無効にし**、世代を見れば**役に立つ瞬間に自分が取り消される**。
  ⚠ **フレームは静かに入れる**（`keepFrame(f, true)`）——`sampler()` からは見えるが「最後に着いたもの」
  にはならない。⚠ **走っている最中に読み手がその時刻へ来たら合流する**（`reading[skey]`）
  ——SDK 側の重複排除は `stateByKey` が**2 件の LRU**でタイルに追い出されるので当てにできない。
  A/B は**どちらも冷たい**入力（一度も訪れていない予報時刻）で通す。
- ⚠⚠⚠ **「確定している次の時刻」と「その次」は別のものである**（#R314）。1 時刻ぶんの先読みは
  **ちょうど 1 歩ぶんの余裕**しか作らないので、着いた絵を見てすぐ次を押す読み手は**2 歩に 1 度**
  窓の端に立つ。→ 2 時刻目も読む。ただし**推測なので合図も条件も別**:
  **同じ向きに 2 回以上続けて送った**とき（`_runN >= AHEAD_MAX`・`TRAVEL_MS` = 6 秒の窓）・
  **前景が何も待っていない**とき（`foregroundBusy()`）・**色面が表に出てから**（`afterFieldShown`）。
  ⚠ **この最後の条件は実測で決まった。** 両方を「場が着いた時点」で放すと、粒子の時刻は
  **802 → 447 ms** に縮む代わりに**色の時刻が 1,584 → 1,906 ms に伸びた**——そして
  「パーティクルは比較的すぐ表示されるが、背景のカラーが、時間を変えるとなかなか表示されない」は
  **#R298 でこのプロジェクトが既に受け取っている苦情**である。推測のための帯域を、読み手が
  待っている絵から取ってはならない。2 時刻目だけを色の後ろに戻した実測（origin/main と**1 プロセスの
  中で交互に**・4 セッション×10 歩・クリック間 700 ms の中央値）:

  | | origin/main | #R314 |
  |---|---|---|
  | 1 歩 → 粒子の場 | 763 ms | **0 ms**（40 歩中 **28 歩**が完全に無料。main は 5 歩） |
  | 1 歩 → 色面 | 1,477 ms | 1,772 ms（**+295 ms**・下記） |
  | 1 歩あたりのバイト | 6 MB | 6 MB |
  | 連打（5 歩・150 ms 間隔） | 2,737 ms | 2,569 ms |

  ⚠⚠⚠ **色面は速くなっていない。速い回線では約 300 ms 遅い。** これは「1 歩が無料になったこと」の
  代金であり、隠さずここに書く——**歩が無料になると、次の時刻の先読みは毎回「今の時刻の色タイル」の
  隣で走る**（従来はその色を待っていた）。4 回の独立した実行で色は **−388 / +332 / −185 / +295 ms**
  と動いており、向き自体が実行ごとのぶれ（データホストへの往復が 1.6〜6.8 秒ぶれる）の中にある。
  **最大の標本（片腕 40 歩）が +295 ms** なので、その数を採る。粒子側はどの実行でも曖昧ではない。
  ⚠ **その間も地図は空にならない**——新しい色が塗れるまで前の時刻の色が出たままである
  （#R284 の 2 スロット・#R297/#R298 の公開規則）。読み手が得るのは**粒子と地点値が即座に来ること**、
  失うのは**既に見えている絵が 1 時刻ぶん古いままの約 300 ms** である。
- ⚠⚠⚠ **点灯の 1.36 秒は、クリックを待つ必要がない**（#R314・`IntMapECMWF.warm()`）。冷たい点灯を
  クリックからの経過で刻むと:

  ```
  0 ms        クリック
  121 / 640   340 kB の SDK <script> が解決
  842         ファイルの open が始まる（HEAD）
  976         …HEAD が返る
  1,010       wasm が初めてインスタンス化される
  1,354       …コンパイル完了（344 / 460 / 556 ms・3 回）
  1,355       予報データの最初のレンジがようやく要求される
  3,664       場が手に入る
  ```

  **3.65 秒のうち 1.36 秒が、データを 1 バイトも要求しないうちに過ぎている。**
  しかもその 3 つ——スクリプト・wasm・**軸が既に指しているファイル**の open——は
  **どれもクリックに依存しない**。`warm()` はそれだけを行い、`js/weather.js` が
  **気象レイヤーの行にポインタが乗った／フォーカスが入った**ときに 1 度だけ呼ぶ
  （行は自分のチェックボックスの id `dl-wind` / `dl-ec-…` で見分ける＝「レイヤーの公開名はその行の
  id である」）。⚠ **帯も復号も 12 ファイルの stage-in もしない**——絵のバイトは
  実際に点けた読み手だけが払う（#R307 の規則）。実測 **4,451 → 2,496 ms**。
- ⚠⚠⚠ **暖める帯は「次のステップが実際に読む帯」である。** #R290 追記2 は規則としては正しく
  （「画面のフレームと同じ範囲」）、それを `band()` と綴った——`band()` は `bandFor` であり、
  **緯度幅 120° を超える視野では `null`＝地球**を返す。つまり**このアプリが開く視野では、暖機は
  毎回地球を暖めていた**。次の時刻はフレームを1枚も持たないので `bandCovers` は必ず偽であり、
  そのステップが読むのは常に `nearBand()`。暖めるのはそれ。
- ⚠⚠ **暖めるのは「軸の進行方向」の隣**（`_stepDir`）。「次の時刻」を `index()+1` と綴っていたので、
  **軸を戻している読み手は毎回冷たい読み込みを払っていた**。方向は軸自身から測り、既定は +1
  （再生ボタンは前へ進む）。
- ⚠⚠ **「静止」には<b>到着</b>も入る。** 段の待ち時間は**読み込みを要求した瞬間**から測っていたので、
  2.4 秒かかる読み込みは**答えが返った時点で既に 1.5 秒静止していた**＝読み手が絵を見る前に
  次の段が走り出す。フレームが**着地した時点**でも時計を打ち直す。
  ⚠ さらに、**段が地球そのものになる場合だけ待ち時間を長くする**（`BIG_STILL_MS` = 2,500 ms 対
  `STILL_MS` = 900 ms）——1 秒ごとに軸を送る読み手は地球の読み込みを始めさせず、止まった読み手は
  1.6 秒遅れで同じ絵に着く。
- ⚠⚠⚠ **保持するフレームの上限は<b>個数ではなく標本数</b>で、地点値は<b>全球を要求しない</b>。**
  実測、**世界ズームの風のフレームは 13,199,360 標本**（u と v の 2 本。`bandFor` は緯度幅 120° を
  超えると「地球全部」と答える）。16 M の予算では 2 本目の全球級フレームが来ると 19.8 M で溢れ、
  **風と読み取り欄が互いの場を追い出していた**（風は次のステップで `sampler()` が null＝粒子が止まる）。
  → 予算は **24 M**、そして `bandNear` が地点値用の帯（画面の緯度を中心 ±30°・約 220 万標本）を返す
  ——`bandFor` は「この絵が何を覆うか」に答える関数で、地点値は絵ではない。
  ⚠ `.om` を開く操作は `Content-Length` が示すほど高くない——実測 `setToOmFile` は 260 ms / 1,019 ms で、
  Range 無しの 200（ファイル全体の宣言長）は**本体を読まずに捨てられている**。
- **不透明度は1回だけ掛ける。** 面の α は配色表（風速の意味を持つ）、スライダーはただ1つの倍率で既定 1.0。
- **粒子は WebGL・1フレーム1描画呼び出し**（`js/wx-wind.js`）。移動量・寿命・残像はすべて**実経過時間**基準
  （`dt` 秒／`exp(-dt/τ)`）なので、60 Hz と 144 Hz で同じ絵になる。WebGL が無ければ**束ねた Canvas2D**。
  粒子はネイティブ格子を直接サンプルする（実測 14,000 回 2.2 ms）——低解像度の地点格子は存在しない。
- ⚠⚠⚠ **同じ大きさへの `resize()` は<b>何もしない</b>。** `js/weather.js` は地図の `moveend`——
  **すべてのパン・ズームの終わり**——から `resize()` を呼び、それが無条件に走っていた。
  `canvas.width` への代入は**同じ値でも canvas を消す**し、`makeTargets()` は残像用の
  フレームバッファを2枚とも作り直し、`cleared = true` が streak を捨てる。つまり**読み手が地図から
  指を離すたびにアニメーションが全消しされて組み直されていた**——1フレームの空白と、0.75 秒かけて
  戻る残像。これが報告された「点滅」である。実測、修正後は**5 回のパンで canvas 再生成 0 回**、
  ビューポートを実際に変えると**ちょうど 1 回**。
- ⚠⚠ **粒子数の調速機には<b>ヒステリシス</b>がある。** 閾値は 9 ms / 4.5 ms を 30 フレームごとに
  判定していたので、そのあたりに座る機械は 18% 減らし、次の窓で 12% 戻し、永久に振動する
  ——毎秒2回脈打つ密度も「点滅」である。判定は**2回続けて同じ**でなければ動かず、不感帯は広く
  （11 ms / 5.5 ms）、刻みは小さい（0.90 / 0.08）。
- ⚠⚠ **時刻を変えたら、前の時刻の粒子は<b>そこで終わる</b>。** 新しい時刻が届くまで古い場で動かし
  続けるのは正しい（上）——だが**届いた瞬間に終わらせる**のも同じくらい正しい。終わらせないと、
  新しい時刻の色の上を前の時刻の軌跡が流れる。`opt.step` のときだけ `renderer.reseed()`
  （粒子を撒き直し、残像テクスチャを落とす）。最初の読み込みでは撃たない——残す前の時刻が無い。
- **地点値**：ECMWF ラスタが出ていれば `valueNow(variable, lat, lng)`＝**タイルを描いたのと同じ配列**。
  NASA GIBS のラスタ（`temp`/`sst` など）は地点値サービスを持たないので、**データセット名と表示中の日付**を
  出して止まる。⚠ **別のデータセットの現在値を代わりに出してはならない。**
- **レーダー**：RainViewer の `radar.past`（実測 13 コマ・10 分間隔・直近2時間）を**ループできる**。
  コマ時刻と経過（「13:30 · −11 分 · 13/13」）を出す。タイルは差し替え（`setSourceTiles`）なので
  コマ送りは点滅せずクロスフェードする。⚠ 無料枠の配色番号は**2種類しか返らない**
  （0/2/3/6/7/8 と 1/4/5/9 でバイト一致）ので、`RV_SCHEME` が実際に得られる方を名指しする。
  ⚠⚠ **無料タイルは z7 で終わる。** z8 以降はどこでも**バイト単位で同一の 1,370 B の PNG**
  ——灰色の板に「Zoom Level Not Supported」——が **HTTP 200 で**返る（実測 2026-08-28・4大陸・
  `/256/` と `/512/` の両方）。#R479 の CARTO と同じ形で、**通信は成功し失敗は絵に焼かれる**ので、
  エラー経路もタイル数の計器も鳴らない。ソースの天井 `RV_MAX_Z`（＝7）だけがこれを止める。
  ⚠ 天井より上は**レイヤーを隠すのではなく z7 のタイルを引き伸ばす**（overzoom）。無料モザイクは
  元々 ~2 km/px なので、z7（赤道で ~1.2 km/px）は既にネイティブ解像度であり、引き伸ばしが足すのは
  ぼけであって誤りではない。⚠ **この数字を上げても解像度は買えない。買えるのは灰色の板だけ。**
- **雲（赤外）**：RainViewer の衛星 IR は**廃止済み**（`satellite.infrared` は実測 0 コマ）。
  NASA GIBS の静止衛星 clean-IR（**Himawari + GOES-East + GOES-West**、10 分間隔）に置き換えた。
  ⚠ **Meteosat は GIBS に無い**ので、およそ西経 20°〜東経 75°（欧州・アフリカ）は範囲外。
  凡例が**その旨を文字で書く**（空白を「雲が無い」と読ませない）。
- **地点天気ポップアップ**は `window.IntMapWx`（`js/wx-source.js`）経由。突風・海面更正気圧・
  **データの有効時刻**（ブラウザ時刻ではない）・**実際のモデル名**を出す。
  ⚠ Open-Meteo の `models=` 無指定は **Best match**（GFS ではない）。⟳ は `ttl:0` で
  **両方の**梯子（Open-Meteo と MET Norway）のキャッシュを無効化する。
- ⚠ **Open-Meteo への直接 fetch は残っていない。** すべて `IntMapWx.guardedJSON`（キャッシュ・
  重複排除・日次 429 のサーキットブレーカ）を通る。`IntMapWx.isOpenMeteo(url)` が**ホストで**判定する
  （部分文字列ではない）ので、`sims.js` / `atlas-console.js` の共有ローダも自動的に通る。
- **共有リンク**は選択中のレイヤー（`dl-*`）に加えて **ECMWF の有効時刻（瞬間）と各層の不透明度**を運ぶ
  （`IntMapShareState.register('weatherEC')`）。⚠ 添字ではなく**瞬間**——開いた人のモデルランは別かもしれない。

### 7.11 企業の拠点 (Company facilities)

`js/company-facilities.js`。**選択中の 1 社ぶんだけ**を描く、レイヤー欄に行を持たない表示。

| id | 種類 | 何 |
|---|---|---|
| `co-fac-src` | source (GeoJSON) | `IntMapCompanyData.facilityGeoJSON(profile, groups)` の出力。**`cluster:true` / `clusterRadius:46` / `clusterMaxZoom:9`** |
| `co-fac-cluster` | circle | クラスタ円。`clusterProperties` が本社を含むかを持ち、含むときは縁が本社色になる |
| `co-fac-count` | symbol | クラスタの件数 |
| `co-fac-pt` | circle | 単体の拠点。色は `['match', ['get','group'], ...]` の 6 グループ |
| `co-fac-lbl` | symbol | 名前。本社は常に、それ以外は z9.5 から |

⚠ **このリポジトリで唯一クラスタリングを使うレイヤー。** `GE().layers.addSource` は記述子を
そのまま素通しするので、クラスタ設定は `addSource` の引数に書く。第2エンジンの adapter は
クラスタしないため `point_count` を持つ地物が生まれず、クラスタ 2 枚が何も掴まないまま
`co-fac-pt` が全点を描く（**劣化して壊れない**）。

⚠ **グループの絞り込みは filter だけでは正しくならない。** クラスタリングは source 側で
filter より前に起きるので、filter だけで工場を隠すと「12」と書かれた円のうち 7 個が地図に無い
状態になる。**手元のプロフィールから再導出した FeatureCollection を `setSourceData` で差し替え**、
加えて `co-fac-pt` / `co-fac-lbl` にも filter を張る（source / layer は作り直さない）。

⚠ **`GE().events.onLayer` は解除関数を返さない。** 解除は `GE().events.offLayer(type, layer, cb)` に
**同一のコールバック識別子**を渡す。登録は全部控えておき、`hide()` が 1 件ずつ返す。

⚠ **稼働していない拠点は塗りを落として縁だけにする**（完全透明にしない——クリックは通るが、
忙しい基図の上で消える）。⚠ **`precision !== 'exact'` の施設カードには必ず注記を出す**
（座標が市の代表点であることは、利用者が知らなければ誤解する事実）。

データモデル・施設種別の語彙・出典規約は [`COMPANIES.md`](COMPANIES.md) が正本。

### 7.12 両大戦（日ごと） — WW1 / WW2 の2レイヤー

**レイヤー行は2本**（`dl-ww1` / `dl-ww2`、どちらも既定 OFF、分類は「政治・統治」）。
起動時に走るのは `js/war-fronts.js`（行・ラベル・IntMapOS 命令だけ）で、
層の本体 `js/war-layer.js` は **行が最初に ON になったときに** `js/lazy-modules.js` が取りに行く。

**1つの工場、大戦ごとに1インスタンス。** `makeWar()` が `ww1-` / `ww2-` を接頭辞にして
source 4本（`<id>-src` / `<id>-line-src` / `<id>-evt-src` / `<id>-lbl-src`）と
layer 5本（`-fill` / `-out` / `-front` / `-evt` / `-evtlbl`）を作る。
**共有するのは算術だけ**——`data/wars.json`・CShapes の表・リングのキャッシュは1回だけ読み、両者が同じ
`js/war-geom.js` を通る。**インスタンスは自分の行が ON になったときに初めて生まれる**ので、
WW2 しか開かない利用者は WW1 の source を1つも払わない。

#### 時計は2つあり、片方向にだけ繋がっている

| 操作 | この層の日付 | Chronos |
|---|---|---|
| 行を ON にする | Chronos の日付を取り込む | **期間外なら開戦日へ1回だけ動かす** |
| Chronos を動かす | 追従する（再生中なら**再生は止まる**） | — |
| 凡例のスライダー／再生 | 動く | **絶対に動かさない** |

⚠ **再生ボタンが Chronos を進めると、100 ミリ秒ごとにニュース・国境・昼夜境界・全統計が動く。**
だから凡例側の操作は Chronos を**読むだけ**にしてある。逆向き（Chronos → 層）は残してあるので、
タイムマシンを 1943 年に動かせばこの層もついてくる。凡例の注記がこの規則を9言語で述べる。
`js/chronos.js` は**自分では時を刻まない**（何かが set したときだけ broadcast する）ので、
「Chronos に追従する」が「スライダーと喧嘩する」ことは構造上あり得ない。

#### 凡例の中身（`data-legend-ww1` / `data-legend-ww2`）

- 戦争名 ・ その日の日付
- **輸送ボタン**（最初の日／1日戻る／再生・一時停止／1日進む／**時計に合わせる**）。
  部品は `window.IntMapWxPlayer` の `b` と `IC`——気象レイヤーの再生ボタンと**同じ宣言**で、
  `.data-legend .ecl-b` の CSS がそのまま効く（新しい CSS を1行も足していない）
- **日スライダー**（`.war-range`・`min=0`・`max=` 期間の日数・`step=1`）と両端の日付
- **日付の直接入力**（`input[type=date]`・`min`/`max` は期間に固定）と**再生の刻み**（1日／5日／15日）
- 画面に出ている陣営の色見本 ／ 進行中の戦線とその線の日付 ／ **その日の作戦**（上位10件・
  兵力と死傷を添える）と**残りの件数**／ 画面に出ている**種別の記号一覧** ／ 注記 ／ **出典**

⚠ **制御は1回だけ組み、以後は中身だけ書き換える。** range は1ドラッグの間に何十回も `input` を
出すので、毎回 `innerHTML` を張り替えると**指がつかんでいる要素が差し替わって**ドラッグが1px で
切れる。文章の側（`.war-info`）は毎フレーム書き換えてよい。
⚠ **`_tileLegends()` は再生中に呼ばない**——全凡例の再配置は毎秒9回やる仕事ではない。

#### 記録の側（`scripts/wars/` → `data/wars.json`）

- **種別 `kind` の語彙は `scripts/wars/lang.mjs` の `KINDS` 1か所**（色＋9言語名）。
  ビルドがそのまま `data/wars.json` に載せ、層は**出荷された表から**円の色と凡例を作る。
  語彙に無い綴りは `scripts/build-wars.mjs` の検査⑧が落とす。
  `battle` / `naval` / `air` / `siege` / `landing` / `political` / `conference` / `atrocity` / `uprising`
- **数値** `str`（投入兵力）と `cas`（死傷・捕虜）は、整数または `[低, 高]`。
  **いずれも「一般に引用される両軍合計」**で、ポップアップがそう明記する。検査⑨が形と上限を見る。
  円の半径は `cas` から作った `mag`（0〜3）で決まる——**数値の無い作戦は基準の大きさで描き、隠さない**。
- **層が描く窓は `span`**（ビルドが導出）。戦争の `from`/`to` ではなく**記録が実際に持つ両端**なので、
  開戦30日前のサラエヴォ事件のように「出荷されているのに一生画面に出ない」行が作れない。
  戦闘の外へは最大 120 日まで（検査⑩）。
