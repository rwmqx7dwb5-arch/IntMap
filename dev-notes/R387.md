## R387 — **携帯の数字は全部 Chromium で測られていた**

依頼は「実 iPhone Safari を対象に、起動→最初の pan→最初の zoom→暖機後→気象 ON→警報 ON までを
**1本の性能トレース**として測定し、MapLibre label placement / raster decode / texture upload /
worker clone / GC / IntMap JS を**完全に時間帰属**すること」。

### まず、できないことを先に確定させた

**このマシンから実機 iPhone は測れない。** Windows で Safari が無く、実機への接続手段も無い。
利用者に確認したうえで **Playwright の WebKit**（iOS Safari と同じ JavaScriptCore＋WebCore 系。
実測 **WebKit 26.5**）を代替とした。⚠ **WebKit は iOS Safari ではない**——この区別は報告の
すべての行に付けてある。

そして、代替にした瞬間に**既存の計器が全部使えなくなる**。`scripts/frame-profile.mjs` が
拠って立つものは 6 か所の `chromium.launch({args:['--use-angle=d3d11']})` と CDP で、
**CDP は Chromium にしか無い**——`Profiler.start`・`Emulation.setCPUThrottlingRate`・
`HeapProfiler.collectGarbage`・`Performance.getMetrics` が全部消える。`longtask` の
PerformanceObserver も Safari は出荷していない（`frame-profile.mjs` 自身の observer は
`catch` の中で**黙って数字を出さない**）。

⚠⚠⚠ **だから CPU スロットルは両腕とも外した。** 片方だけ 4× で絞れば、比較しているのは
エンジンではなく**2台の違う機械**になる。歴史的な ×4 の Chromium の数字はそのまま残し、
この計器は `--cpu 1` を既定にした。**ここで出る数はエンジンの比較であって、携帯の数字ではない。**

### 計器（`scripts/mobile-trace.mjs` ＋ `scripts/trace-probe.js`）

正本は [`docs/TESTING.md`](docs/TESTING.md)。設計上の要点だけ:

⚠⚠⚠ **入れ子を差し引かない帰属は帰属ではない。** `Map._render` が `Painter.render` を呼び、
それが `texImage2D` を呼ぶ。3つとも計って足せば**同じミリ秒を3回数える**。1段1エントリの
スタックで親の積算を止め、self time だけを積む。`tests/r387-checks ①` が合成フレームで
**5 / 2 / 5 / 7 ms・和 19 ms＝壁時計と一致**をミリ秒で固定する（inclusive に戻したら赤）。

⚠⚠⚠ **`longtask` の無いエンジンで詰まりを測る。** `MessageChannel` の ping ループを
自分に投げ続けると、**2つの tick の隙間がそのまま主スレッドの詰まり**になる。
実測（両エンジン・390×844）: `MessageChannel` は Chromium 平均 **0.008 ms**・WebKit **1.167 ms**、
`setTimeout(0)` は 6.2 / 15.1 ms、`rAF` は 16.3 / 16.6 ms。**どちらのエンジンでも
MessageChannel が正しい原始関数**だった。

⚠⚠⚠ **その「主スレッドの忙しさ」を引き算で出そうとして、2 回とも列ごと間違えた。**
`busy = wall − pings × tick0`（tick0 ＝ ping ループ自身の空転コスト）としたかったが、
**tick0 のどちらの推定も現実のエンジンに触れた瞬間に壊れる**:

* **静かな `about:blank` の平均**——Chromium 0.011 ms で正しいが、**WebKit は 50 ms**。
  Playwright が駆動していないページは**スロットリングされる**（同じエンジンのビジーループは
  1.17 ms）。50 倍大きい tick は busy を全行 0 にする。
* **走行中の最小間隔（floor）**——Chromium が **floor 0.100 ms に対し平均 0.013 ms** を返す。
  `performance.now()` はそこで **0.1 ms に量子化**されているので、拾えるのは*時計の*分解能で
  あって*キューの*コストではない。実測 **7,011,938 × 0.1 ms ＝ 701 秒**の計器オーバーヘッドを
  90 秒の実行に課していた。

⇒ **引き算をやめ、プローブが直接積む**——**2 ms を超えた gap の総和**。両エンジンの床
（Chromium 平均 0.008 ms / WebKit 1.167 ms）より上なので**校正が要らない**。
⚠ したがって `busy>2` は**下界**である（2 ms 未満で終わる仕事は見えない）。
バケツが busy を上回りうるので、その場合は `overAttributed` として**印字する**（黙って丸めない）。
**バケツの列にはこの制限が無い**——推論ではなく wrapper の実測だから。

⚠⚠⚠ **付かなかったフックは「0」ではなく「不在」。** wrapper は本当にプロパティを差し替えた
ときだけ `hooks[bucket]` を立て、`attachMap()` は3つの MapLibre フックのどれが付いたかを返す。
minifier が `_updatePlacement` を潰し始めたら**欠けたフックとして出る**べきで、
「label placement は 0 ms でした」として出てはならない（`tests/r387-checks ②`）。

⚠⚠ **プローブは boot 中に自分で付く。** 地図は boot の**最中に**作られるので、runner が
boot 後に `attachMap()` を呼ぶ設計だと、最初のスタイル読み込み・最初の配置・最初のテクスチャ
転送が**全部どのバケツにも入らない**。8 ms の poll で地図ができた1フレーム以内に付く。

⚠⚠ **測れないものは測ったことにしない。** GC は**どちらのエンジンでもページスクリプトから
見えない**ので、どのバケツにも入れず `other` にも畳まない。worker 側の decode も
`addInitScript` が届かないので範囲外——測っているのは主スレッド側の半分
（`workerPost` ＝ 呼び出し側が同期で払う structured clone）。heap は Chromium だけ、
WebKit では `—` と印字する（**0 ではない**）。

### 作りながら見つかった欠陥（全部この計器自身のもの）

⚠⚠⚠ **レイヤーを ON にする経路が3回間違っていた。** ⑴ `dl-ec-wind` は**レイヤープレビューの
canvas の id** で、風のトグルは `dl-wind`。警報は `dl-alerts` ではなく `wp-dl-alerts`。
⑵ `IntMapOS.exec` は **Promise を返す**（#R318 の「exec の非同期の嘘」）ので、次の同期行で
`checked` を読むと**動くトグルを stayed-off と報告する**。⑶ ところが **await すると
ハーネスごと止まる**——警報レイヤーのコマンドは、始めた要求が答えられないとき
**永久に解決しない**（診断実行が2回、1つの `page.evaluate` の中で殺されるまで座り込んだ）。
⇒ **利用者の経路（`el.click()`）→ await しない `exec` → `checked`＋`change`** の3段にし、
**どの経路で入ったかを結果に書く**。各段の後に**上限付きのポーリング**。
⚠ **この3つが全部「ran:false」として出たから直せた**——#R322 の「駆動できなかった位相は
0 ではなく ran:false」が無ければ、「警報 ON は無料」という数字を書いていた。

⚠⚠⚠ **`process.argv.push` は argv が2要素以上あることを仮定している。** `frame-profile.mjs` は
**import 時に** `--base` を読み、その replay() は**自分の BASE で始まる URL だけ**を素通しする。
つまり2つのモジュールが1つのポート番号で食い違うと、**アプリ自身の HTML とチャンクが
タイルのキャッシュから答えられる**。`node -e` やテストランナーから import すると argv が
1要素なので、push した `--base` は index 1 に入り **`slice(2)` が落とす**——
frame-profile は黙って既定の 4173 を持ち続ける。⇒ 先に argv を2要素まで詰める。
`tests/r387-checks ⑥` が `PORT=4999` で両者を引き離して一致を要求し、
**「frame-profile 単体では 4999 にならない」ことも確かめる**（赤にできる行）。

⚠⚠ **同じポートに別の worktree が座っていたら、それは自分の dist ではない。** 検査ポートは
パスのハッシュ mod 200 なので衝突しうる（#R282）。到達可能かではなく
**`index.html` がバイト一致するか**で判定し、違えば止まる。

⚠⚠ **`settle` の上限 20 秒が壁時計の列を埋めていた。** キャッシュが冷えていると
`map.loaded()` は真にならず、**1.1 秒の zoom が 38 秒**と印字された。busy の列は影響を
受けないが、**誰も読まない壁時計の列は誰も検算しない**。⇒ 6 秒にして、打ち切った回数を数える。

⚠⚠⚠ **Playwright の `waitForFunction` は既定で rAF ポーリングし、rAF こそが「誰も駆動して
いない WebKit ページ」で止まる唯一の原始関数だった。** 実測 **600 ms に 1 フレーム**（Chromium は
60 fps）。**6 秒の settle が 11 分座り込み**、しかも1行も印字しないまま——WebKit を測ることが
目的の実行で。⇒ 全待機を `polling: 500` にし、その上に `Promise.race` のハード上限を重ねた。
⚠ そして**「長すぎる位相」は長すぎる最中に見えなければならない**——最初の2エンジン実行は
15 分間なにも印字せず、遅い WebKit の起動と永久に終わらない待機を区別する手段が無かった。
位相ごとに1行、閉じた時点で flush する。

⚠⚠⚠ **WebKit は再生キャッシュ無しでは起動を完了しない——遅いのではなく、止まる。**
同じページ・同じ viewport・同じ UA で連続実測:

| 腕 | 起動 | ready | 直後の `page.evaluate` | resources |
|---|---:|---|---|---:|
| WebKit・**実ネットワーク** | 108,556 ms | **いいえ** | **返らない** | — |
| WebKit・ディスクから再生 | 27,060 ms | はい | 答える | 88 |
| Chromium・ディスクから再生 | 13,283 ms | はい | 答える | 128 |

1本目は「遅い」のではなく**主スレッドがプロトコルに答えなくなる**——`page.evaluate(() => 'yes')`
すら返らない。⚠ **最初に route() 傍受を疑ったのは外れで、実測は逆を示した**（傍受のある腕だけが
完走した）。⇒ `--record` は Chromium で1回だけ。以後は再生のみで走らせる。

⚠⚠⚠ **キャッシュされた失敗は粘る。** サマリの `blocked` は「未キャッシュで中断した要求」だけで
なく **`{"failed":true}` のエントリが答えた要求**も数える。実測 **422 blocked が
たった 15 個の毒された URL から**出ていた。`--record` はそれを再取得しない。

⚠⚠⚠ **そして ECMWF の場は、待ちを延ばしても届かない。** 大きな HTTP Range 要求の束で、
`route.fetch()` は 20 秒で諦め、その失敗をキャッシュに書き、以後の実行はそれを再生する。
実測 **記録実行2回（2回目は毒を全部消したあと）とも 187 秒待って `field:false`**。
⇒ **待ちを両エンジン共通の 25 秒に固定し、この位相が何を測っているかを書いた**——
風レイヤーを ON にすること、その裏のモジュール読み込みとレイヤー構築であって、**場の復号ではない**。
`field`（サンプラが在るか）と `windLayers`（**レンダラが実際に風レイヤーを持っているか**）を
**別々に**報告し、下流の汚染判定は `windLayers` に繋いだ（#R353 の「問いはレンダラが何を
持っているかであって、ソースが何を意図したかではない」）。⚠ #R325 の色面 1,190 ms は
**実ネットワークで取った別の計測**であって、ここの数字ではない。

250 requests / 29.8 MB・heap 164 MB、風は `dl-wind` が `change` 経由で ON（`windLayers: 1`）、

**この表が言っていること:**

* ⚠⚠⚠ **暖まった pan は 345 ms、警報レイヤーを載せた pan は 7,074 ms——20 倍。**
  警報を ON にする位相自体も **12,063 ms の busy**（最悪フレーム 250 ms）。#R344 が差分更新に
  変えたあとでも、**警報は今なおこのアプリで最も高くつく1枚**である。
* ⚠⚠⚠ **その 12,063 ms のうち MapLibre のレンダラは 2,668 ms（render 1,493 ＋ mapRender 830 ＋
  placement 345）で、`other` が 8,917 ms＝74%。** 警報の値段は**レンダラの中ではなく、その外**に
  ある。`workerPost` の 351 ms は #R344 が名指しした structured clone の残りで、
  1桁小さい。
* ⚠⚠ **label placement はこの条件では主犯ではない**（boot 76 ms・最も高い alerts-on でも 345 ms）。
  #R209 の「The cost is label placement」は **CPU 4× で衛星ベースマップの上**で測った文で、
  **素の CPU・ベクタ・ディスク再生**ではこの通りにはならない。⚠ 条件の違う2つの数を並べない。
* ⚠⚠ **decode と texUpload がほぼ 0 なのは、この計器の作りが決めている**——全バイトがディスクから
  来て、衛星ベースは OFF。#R206 の「衛星フレームの 58.4%」はこの表の反証ではなく、**別の設定**。
* ⚠ **boot の busy 2,716 ms のうち `other` が 1,582 ms＝58%。** 起動の主犯はレンダラではなく
  アプリ JS 側（#R311 の帰属と整合）。

**WebKit 側で実際に測れたこと**（完全な12位相の表は取れていない。理由は下）:

* **計器そのものは WebKit で完全に動く**——`decode` / `texUpload` / `bufUpload` / `workerPost` /
  `workerRecv` の全フックが付き、**未フック 0 件**。`isMobile`＋DPR 3＋iPhone UA も受け付ける
  （WebKit 26.5）。
* **スケジューラの床**（両エンジン・800 ms の連続ループ）: `MessageChannel` **0.008 / 1.167 ms**、
  `setTimeout(0)` 6.2 / 15.1 ms、`rAF` 16.3 / 16.6 ms。
* ⚠⚠⚠ **起動時間そのものが 2 倍**——**全要求がディスクから答えられる**条件で
  **WebKit 27,060 ms / Chromium 13,283 ms**（同じ分・同じ機械・同じバイト）。
* ⚠⚠⚠ **そして WebKit は、起動を完了しないときは「遅い」のではなく「無応答になる」。**
  実測 **7 回中、ready=true で起動を終えたのは 2 回**（25,226 ms と 27,060 ms、どちらも
  `--record` が有効＝未キャッシュの要求も取りに行ける条件）。残る 5 回は 108,556〜144,087 ms
  経っても ready にならず、**そのあとページはプロトコルに一切答えなくなった**——
  `page.evaluate(() => 'yes')` すら返らない。**同じ条件の Chromium は 3,281〜4,205 ms で ready に
  なり、12 位相すべてを完走する。**
* ⚠⚠⚠ **原因はこのラウンドでは特定できていない。断定しない。**
  最初に疑った `context.route()` の傍受は**外れ**だった（傍受のある腕だけが完走した）。
  次に疑った「未キャッシュ要求のブロック」も**外れ**で、最後の失敗した実行は
  **`18 replayed / 0 missed / 0 blocked`**——1件もブロックしていないのに起動しなかった。
  ⇒ **12 位相の WebKit の表はこの時点では存在せず、その理由も分かっていない。**
  分かっているのは「全要求が答えられる条件では 27.1 秒で正常に起動する」ことだけである。

⚠ **この計器は「固まった」を無言で待たないようになった**（`--phase-timeout`、既定 150 秒）。
最初の版は位相の中でも**位相の外**（boot 直後の最初のスナップショット）でも止まり、
**12 分ずつ何も印字しなかった**。

### 残っていること

* ⚠ **WebKit の 12 位相の表はまだ無く、起動が完了しない理由も分かっていない。**
  7 回中 2 回は完走しているので「WebKit ではこのアプリが動かない」ではない。
  次に測るべきは、**成功した 2 回と失敗した 5 回の差**そのもの——
  ⑴ プローブを外した対照（計器が主スレッドを妨げていないか。これを測ろうとした実行は
  `browser.close()` 自体が返らず、結果を得られていない）、
  ⑵ 並行セッションによる機械の負荷（このラウンド中、同時に node が 23〜51 プロセス動いていた）、
  ⑶ WebKit のコンソールとネットワークのログを wedge の瞬間まで採る。
  **推測で原因を書かない**——このラウンドで2つ書いて2つとも外した。
* **実機 iOS Safari は依然として未観測。** WebKit は同じエンジン系だが、iOS の
  JavaScriptCore の JIT 制約・実機の GPU・メモリ圧・熱制御はここに入っていない。
* **CPU スロットルは WebKit に存在しない。** 携帯の CPU で両エンジンを比べる手段はこの
  マシンには無い。
* **警報レイヤーの `other` 8,917 ms の中身は、この計器の視野の外にある。**
  wrapper が包んでいないアプリ JS なので、次に測るなら Chromium の CDP サンプラ（`--verify`）
  でその区間を取り、どの `js/` ファイルかまで落とす。
* `scripts/frame-profile.mjs` は Chromium 専用のまま。`--engine` を足していない
  （依頼の範囲外で、この計器が同じ replay キャッシュを共有しているので二重にする理由が無い）。
