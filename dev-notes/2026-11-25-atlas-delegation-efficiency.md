〈依頼〉(A) 複数エージェント（子 AI）が使われている気配がない理由を本番の実測で確かめ、構造で直す（強制・回数の下限は作らない）。
(B) 標本「実際の経路をマッピングして」（5 分 45 秒、手順 1「鉄道路線の形状データを取得」が失敗のまま、OSM／raw.githubusercontent／Overpass／ohsome
が全部失敗と表示）の原因を、観測器の誤報・結果が次の手に届かない・冪等でない操作のどれかとして特定する。標本のための対応は足さない。

## 本番の実測（2026-11-25・`public.ai_delegation_journal` と本番ページでの再現）

- **委譲の行は 3 日間 0 件。** 280 呼び出しは全部 `atlas_turn`。子の行（`atlas_delegate`）は、この調査で私が 2 回走らせた分が全て。
- 3 か国を独立に調べさせる質問を委譲を明示して 2 回走らせた（デンマーク・ペルー・ベトナム／フィンランド・ウルグアイ・タイ）。
  6 作業者のうち **5 つが 119〜120 秒でちょうど `provider_unavailable`（0 トークン）に終わり、そのあと Web 無しで 8〜12 秒で
  「記憶から答える・未検証として扱う」版を返した**。残る 1 つは Web 検索を 110 秒（入力 103,276 トークン）かけて成功した。
  120 秒 = `providerBudgetMs(false)`（`EDGE_RESPONSE_START_MS` 150 秒 − 余白 30 秒）。作業者は非ストリームで呼ばれ、
  ストリームの親（370 秒）より窓が短かった。研究という一番長い呼び出しに一番短い窓が与えられていた。
- 委譲を明示せずに 3 か国の比較を訊くと、Atlas は委譲を使わず自分の返信内の Web 検索で 2 分 50 秒・$0.395・4 回の呼び出しで答えた。
  作業者を実際に走らせると 110 秒以上＋（窓切れ時は）120 秒の無駄待ち——選ばない判断は、計測された事実に照らして不合理ではなかった。

## 直したこと

1. **作業者もストリーム窓で答える**（`supabase/functions/ai-proxy/ask.ts` `streamWanted`・`provider-call.ts` `Meter.longWindow`・
   `js/ai-core.js`・`js/atlas-delegate.js`）。ストリームで答える要求は応答が既に始まっているので 370 秒を使える。作業者の鍵・台帳・
   答えの形は変えない（鍵はヘッダのまま、本文の鍵は作らない）。画面には何も出さない。
2. **成功した呼び出しがある手順を「失敗」と言わない**（`js/atlas-plan.js` `stepState`）。手順の状態は「機能ごとの最新の試行のうち最悪」で、
   ある手順に失敗した呼び出しと完了した呼び出しが混ざると「失敗」だった。この状態は読者のチェックリストと、毎手モデルに戻る計画ブロックの両方に出る。
   混在は語彙に既にある「一部のみ（partial）」にした。全部失敗は失敗のまま。
3. **ダウンロードできたが dataset にならなかったファイルの中身を捨てない**（`js/atlas-cap-web.js` `textExcerpt`）。`web.fetchFile` は
   手元にあるバイトを「読めなかった」の一言で捨て、Atlas は持っているものを探し直した（one-pass-or-a-reason §2 の 2 番目の原因）。
   テキストなら先頭 6,000 文字（ページ snapshot の既定と同じ値）が untrusted の `exec.web.excerpt` として次の手に届く。バイナリは何も運ばない。

テスト: `tests/atlas-delegation-efficiency-checks.test.mjs`（①②）、`tests/atlas-stream-replay-checks.test.mjs`・
`tests/ai-no-wallclock-cut-checks.test.mjs` に作業者の窓を追加。

## 否定された見立て（測って外れたもの）

- **「手順 1 の失敗は観測器の嘘」**: 一部は正しい。OSM の HTML ページ・大きすぎる CSV・Overpass のタイムアウトは本当に失敗している
  （本番で同形を再現: 再エネ CSV は「ページまたはファイルが大きすぎて取得できません」）。嘘だったのは「混ざっても失敗」と、読めたファイルの捨て方。
  標本の 5 分 45 秒そのものの実行記録（どの呼び出しがどの手順に属したか）は、ターン台帳がサーバに無く再現できていない。
- **「プロンプトキャッシュの前置きが毎手壊れている」**: 本番 3 日で読み取り率 3%（キャッシュ 326,593／入力 11,360,025 トークン）。
  実際の手 1・手 2 の本文を捕捉して比べると system・tools・依頼文は 1 バイトも違わない（クライアントは安定）。同一本文を 3 回送り直しても
  キャッシュは伸びず、単純な本文では「合計 − 6,284 トークン」に張り付く（8k〜28k トークンで止まる）。item_reference の有無でも変わらない。
  つまりこの挙動は提供側の規則で、こちらの前置きの不安定さではない。**未解決のまま残す**。コスト側の手当ては、毎手 11k トークンの
  system＋5k の tools と、find_capability の 52k 文字の結果が毎手載ること（別の課題）。
- **「委譲の説明が足りない」**: system には Web 検索の実測秒数が既にあり、delegate の説明も事実だけ。足りなかったのは説明でなく、
  委譲が実際に価値を出す条件（窓）だった。説明は変えていない。

## 次に見ること

本番で作業者が `ok`・Web 有りで終わる比率と秒数（`ai_delegation_journal` の `task='atlas_delegate'`）。Atlas が独立な調べものに自分から委譲を選ぶかは、
作業者が実際に速く確かな答えを返せるようになってから測り直す（選択は Atlas のもの。回数の下限は作らない）。
