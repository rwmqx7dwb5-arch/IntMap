### ① 同じ依頼文が5回目に返ってきたので、前ラウンドの答えを容疑者にした

`js/atlas-view-subject.js` の冒頭が、この依頼文を**一字一句そのまま引用して**「THE SAME REPORT, A FOURTH
TIME」と書いている。#R309（4文＋国名）→ #R313（プール化）→ #R337（26候補追加）→ #R392（主語を視界へ）
——4ラウンドどれも実際の改善で、それでも同じ文が返ってきた。#R411 の教訓どおり、**前回の答えを疑う**。

**まず測った。** ブラウザペインは style を読み込めない（既知）ので、本番と同じビルドを実 Chromium で
15か所へ飛ばし、`.atl-chip` の文字列をそのまま読んだ。

```
60枠 / 53種
  x10  Which submarine cables land in {place}, and what happens if one is cut?
   x6  Which climate zones does {place} span, and which of them are shifting?
   x8  {city}: what is it built on, and what does it do that its neighbours do not?
```

**10枠のうちに「…land in Switzerland」があった。スイスは内陸国である。** サハラのど真ん中では
「…land in Algeria」、ドンバスでは「…land in Ukraine」。マンハッタン z13 では
「Part of **United States of America** lies inside the Arctic Circle」。

**53種／60枠は「多様」に見える。多様なのは差し込まれる名前だけだった。**

⇒ **原因は門である。** これらの候補は `on:(f)=>f.st&&f.has('dl-subcables')` の形で、`has()` が訊いて
いるのは **`#layer-dropdown` のチェックボックス**＝レイヤー欄であって地図ではない。そして
`window.IntMapDefaultLayers=['dl-climate','dl-subcables']`＝**この2つは既定でオン**。だから2つの文が
地球上のどの視界でも発火し、60枠の16枠（26%）を占めていた。

### ② 直し方——「在るか」を地図に訊く

`js/atlas-view-subject.js` に `contentInView(box)` を足した。`IntMapLayers.featuresIn(id, box)`
（`js/map-ui.js` の登録簿。news / volcanoes / aircraft / ships / satellites / earthquakes / webcams /
datacenters / pharma）と、登録簿に行を持たない**海底ケーブルの陸揚げ点** `src-subcables-lp` を、
**視界の箱で絞って数える**。⚠ **取得はゼロ**——描画中の geojson を箱で filter するだけで、#R392 が
このモジュールに課した規則をそのまま守る。

⚠ **陸揚げ点であって線ではない。** ケーブルの線は誰も上陸しない大洋を横切る。問いは「どこに陸揚げ
されているか」なので、数えるのは点のほうである。

箱で本当に絞れているかを実測（東京付近・同心の箱）:

```
z=4  139 / 1922      z=8   12 / 1922
z=5   52 / 1922      z=9    8 / 1922
z=6   29 / 1922      z=10   1 / 1922
z=7   21 / 1922      z=12   0 / 1922
```

`P`（国のプール）の5候補は `f.inView(id)===null` を**追加の条件**にした——**数えられる限り、主語を
`V` の数えたチップに譲る**。数えられないとき（層は on だがソースがまだ無い）だけ従来の国スコープの
問いが残る。

⚠⚠⚠ **`null` と `0` は別の答えである。** `null`＝「このアプリには数えられない」、`0`＝「ここには無い」。
片方に潰すと、層を点けた最初の1秒に働いていたチップを消すか、また content を騙るかのどちらかになる。

### ③ 最初の版は、1つの defect を別の defect に取り替えただけだった（実測で分かった）

同じ15視界をもう一度測った:

- **`w:16` が要衝と国境を押しのけ、15視界中7回で第1枠を取った。** 陸揚げ点は視界についての本当の事実
  だが、「ここは地球上に16しかない海上の要衝のひとつ」より特定的ではない。⇒ **w=13**。
- 全球ズームで「**501** submarine cable landings sit inside this view」。**ケーブル網についての事実で
  あって、場所についての事実ではない**——#R392 が消した「真だが主語が違う文」と同じ形。⇒ `world` では拒否。
- **「1 submarine cable landings」**。`L()` に複数形の機構は無い（9言語・9規則）。⇒ 数える名詞は
  **述語が両立しない2候補**（`>=2` と `===1`）を持つ。
- `climate` は数えられない（ケッペンはラスタ）ので `has()` が最良の証拠のまま。ただし
  **「{place} はどの気候帯にまたがるか」は国全体についての主張**なので、`world|continent|country` の
  ときだけ訊く。⚠ `scaleOf` 自身の注記が「a view at `street` is never handed a question about the
  country」と**約束していたが、それを強制するものは何も無かった**（#R399 の形）。
- `arctic` は**国の外接矩形**を読んでいた。⇒ **視界自身の北端**（`viewN>=60`）も要求する。

3回目の測定:


⚠⚠ **足した名前の取り出しは `tests/r392 ③` に殺された。** 火山名とニュース見出しを
`properties.name || properties.title` から拾う版を書いたが、**どのチップも使っていない**うえ、それは
#R313 追記の罠そのもの（en/jp 2言語の固有名詞を、他8言語が訳した文に落とす）。削除した。

⚠⚠ **その検査の初版は、自分の注記を読んで赤くなった**（#R345 の形・15回目）。「この綴りは無い」を

### ④ パーティクルの既定は、場ごとに違う

`PARTS_KEYS` に `'ec-precip':'intmap_wx_precip_parts'` を1行足すだけで、凡例の箱・`pushWindSolo()` の
OR・共有 URL の `wp=`・`window._imWxParts` が追随する（#R439 が正しく1か所にしてあった）。

`PARTS_DEFAULT` を新設。**最大瞬間風速・海面気圧・降水量（予報）は ON、気温だけ OFF。**
前3つは読者がその場を「そこにある気象システム」として読む場で、筋が低気圧の渦や前線のシアを
**形として**読ませる。気温は「その地点の値」として読まれるので #R337 の理由（u と v の2変数を余計に
読む）だけが残る。

⚠ **保存された答えは既定より強い、両方向に。** 既定が決めるのは**鍵が無いとき**だけ
（`'1'`＝オン・`'0'`＝オフ・無し＝既定）。**箱を外した読者が次の起動で戻されることはない。**

⚠ **降水量（予報）に新しいデータ源は要らない。** 筋が読むのは常に**風の場**（`VAR`）で、下に敷かれた
ラスタが何であるかとは無関係——だからスカラー場でも筋を持てる。

実測（まっさらなプロファイル・鍵は4つとも `null`）:
`{"ec-temp":false,"ec-gust":true,"ec-slp":true,"ec-precip":true}`、3つの凡例すべてに箱があり checked。

### ⑥ ボタンの名前は、押すと何が起きるかである

`.ev-sources` は「3 sources」だった。それは数の**表示**であって動作の名前ではない。
**「詳細（3媒体）」/「Details (3 sources)」**——先頭が動作、媒体数は括弧の中に残す（消すのは名前を
直すこととは別の変更・`CLAUDE.md` §3.1）。綴り（`ev-sources`）・tooltip（媒体名の連結）・開く先
（`openDetail`）は不変なので、既存の spec と CSS 規則はそのまま当たる。

⚠ `js/news-ui.js` の `_srcCountLabel()` は**別物**——地図のツールチップと携帯のポップアップに出る
**押せない説明文**なので「3 sources」のままが正しい。2つの文字列はこのラウンドで**意図的に分かれる**。

⚠⚠ **このボタンの文言を読んだ spec は1本も無かった。** `tests/r405` は在ることと押すと開くこと、
`tests/r435` は押したあとの外皮を測る——どちらも綴りとふるまいで、テキストは一度も読んでいない。
だから「3 sources」がボタンの名前である状態は、全部緑のまま出荷され続けられた。`tests/r455.spec.js`
がそれを読む（単数形・複数形・1280px と 375px での収まり）。

⚠ **その spec の初版は `{ page }` を使って3本とも落ちた。** Playwright 既定のページは**どこへも行って
いない**。起動済みのページは `app.page`（`tests/helpers/app.js`）。赤の原因は測っている対象と何の関係も
無かった。

⚠⚠⚠ **そしてその spec は、緑のまま1行だけ何も確かめていなかった。** 単数形を見張る
`expect(l).not.toMatch(/1 sources/)` の `` が、ファイルを heredoc で書き戻したときに
**生の 0x08（backspace）2バイトに潰れていた**（#R435 が実測した形）。たちが悪いのは 2 つある——
`JSON.stringify` すると `"/1 sources/"` と**正しく見える**こと、そして
**どんな文字列にもマッチしない正規表現は `.not.toMatch()` の下で恒真**であること。
⇒ **spec は緑。その主張だけが空。** 「r455.spec.js が core で緑だった」ことは、この行が何かを
確かめた証拠にならなかった。見つけたのは `tests/r394-checks ②b`（正規表現の中の生の制御文字を
見張る門）と `npm run check:static` の `[regex-control-char]` で、**このラウンドの spec ではない**。
潰れた綴りを直したあと `/1 sources/.test('Details (1 sources)') === true` を実測して、
**初めて発火する状態になったこと**を確かめている。
