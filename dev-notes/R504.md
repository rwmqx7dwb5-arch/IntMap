## R504 — **「もっと多くの航空機を」は描画の話ではなく、「訊いてよい空の量」の話だった**（＋計器2つと余白）

> 「航空トラフィックレイヤーはもっと多くの航空機が表示されるように。方位磁針ボタンは、デザインをもっといいものに。いまは簡素すぎ。チープ。」

### 0. 手を入れる前に本番を測った

| 実測（2026-08-31・変更前の本番） | 値 |
|---|---|
| `x-intmap-count`（world チャンネル） | **2,699 機** |
| `x-intmap-coverage` | **`lattice 0/980`**（4回続けて訊いても同じ・どの isolate でも） |
| `x-intmap-oldest-ms` | 214 秒（＝**古い機体を出していたのではない**） |
| 同じ分に provider の網が実際に見ていた機体 | **10,924 機**（位置つき 10,911） |

クライアントには上限が無い（`src/aviation-worker.js` の `CLIENT_DROP_S = 1200` 以外に間引きは無く、
GPU 側の `aircraft-points.js` も枚数で切らない）。**描かれていなかったのではなく、届いていなかった。**

### 1. ⚠⚠⚠ 掃引の進捗が isolate を越えていなかった

スナップショット（`aviation/world.bin`）が運んでいたのは**機体だけ**で、
「どこを既に見たか」——`STATE.cursor`・格子タイルごとの `last` と `miss`・#R434 の訊いた空域の
台帳——は**全部 isolate の記憶**だった。Supabase は冷えた isolate を頻繁に割り当てる（#R341 が
同じ理由でスナップショットを Storage に出した）ので、結果は3つ:

- `coveragePct` は **0 から動けない**。「掃引が遅れている」のではなく、**答える isolate が
  掃引した isolate であることがほぼ無い**ので、探査済みタイルを1枚も報告できない。
- 掃引は毎回 **cursor 0 から**歩き直す。攪拌した巡回順（黄金比ストライド）は「小さい予算で全球を
  粗く標本する」ためにあるのに、**同じ先頭3枚を1日6回買い直して7枚目に到達しない**。
- `miss`（受信機のいない大洋を 1/8 に間引く counter）も毎回 0 に戻るので、**何も間引いていなかった**。

⇒ `aviation/sweep.json`。cursor・`last`・`miss`・台帳・`readAt` を持ち、hydrate で読み、60 秒に
1回だけ書く。**格子の長さ `n` を一緒に置き、一致しなければ捨てる**——タイル #412 が同じ空である
のは格子が同じ間だけで、`RADIUS_NM` を動かした日に古い番号を新しい空へ写せば、
**誰も見ていない空を「探査済み」と主張する**ことになる。

### 2. ⚠⚠⚠ 「間隔」が上流の実力の 1/5 だった

#R434 はこの関数**全体**に「`VIEW_MAX_TILES` 枚を `VIEW_STALE_S` 秒に1回」を課していた
＝ 4 枚 / 45 秒 ＝ **0.089 read/s**。根拠は #R341 の
「約4リクエストのバースト予算が、**間隔によらず**ゆっくり補充される」という読みである。
同じアドレス・同じ User-Agent（この UA は #R341 が測って load-bearing だと書いたもの）で測り直した:

| 間隔 | 200 が返った数 |
|---|---|
| 連続（間隔なし） | 5 / 6 |
| 1.0 秒 | 8 / 12 |
| 2.0 秒 | **31 / 40** |

**間隔で成功数が動かないのに 2 秒間隔で 78 % 通る**のは、四連発の弾倉ではなく
**毎秒 0.5 発ほどで補充される leaky bucket**。⚠ #R341 の測定（10 回の窓）は、
**2 秒に1個補充されるバケツを見るには短すぎた**——「成功数が間隔で動かない」という同じ観測から
「補充は分単位」と読むことも「窓が短すぎる」と読むこともでき、前者を採ると上限が実力の 1/5 になる。

⇒ 上限を **1つの leaky bucket** にまとめ、視野も格子掃引もそこから引く
（`READ_RATE_PER_S = 0.34`・`READ_BURST = 6`）。**膝（0.5）より意図的に低い**——膝で訊けば
45 % 多く読めるが、その分を 429 に払うことになり、429 は全チャンネルを黙らせる。
⚠ **bucket も isolate の記憶である。** それを正直にするのが `sweep.json` の `readAt`:
冷えた isolate は「最後に誰かが訊いた時刻」を引き継いでから補充量を計算するので、
**起動しただけで満タンのバケツをもらう**ことがない。

⚠ **`VIEW_STALE_S` は1つの定数で2つの仕事をしていた。** 「その空は訊く価値があるか」（空についての事実）と
「関数はもう訊いてよいか」（**上流についての事実**）である。剥がしたのは後者だけで、前者は残っている。

### 3. ⚠⚠ `cron: '*/5'` は5分ごとに走らない

`.github/workflows/aviation-sweep.yml` の直近8回の開始時刻（UTC・実測）:
19:26 / 16:42 / 12:14 / 06:42 / 01:15 / 23:13 / 21:02 / 18:25 —— 間隔は 2〜5 時間で、**1日6回**。
GitHub は定期ワークフローを強く間引く。3枚×2スライス＝ **1日 36 枚**の読み取りが 980 枚の格子に
対する掃引の全量で、しかも §1 のせいで**毎回同じ3枚**だった。
⇒ 1回の run が惜しいので、run の中で 10 スライス（`?refresh=1&tiles=6`）を 20 秒間隔で回す
（`timeout-minutes` は 5 → 8）。**速さを決めるのは相変わらず関数側の bucket** で、
この loop にできるのは「訊く」ことだけである。

### 4. ⚠⚠ 429 の休みを、段階的にした

`RATE_BACKOFF_MS` は初回から一律 60 秒だった。0.089 read/s のときの 429 は異常事態の合図なので
妥当だが、0.34 では **「バケツが一瞬空だった」の合図でもある**（実測: 2 秒間隔で 40 回中 9 回）。
それに全チャンネル1分の沈黙で答えるのは、**1枚を惜しんで 20 枚を捨てる**取引になる。
⇒ 8 秒から始めて、断られ続ける間だけ倍々（上限は元の 60 秒）。**成功した読み取り1回で 0 に戻る。**
読めなかったぶんのトークンはバケツへ返す。

### 5. ⚠⚠ 全球を1回で返す道はあった。使わないと決めた

`adsb.lol` の readsb **re-api** は `?binCraft&box=-90,90,-180,180` に**全球を1回**で返す
（実測: 10,924 機・gzip 665 kB・生 1.22 MB・stride 112）。しかしこれは **feeder 専用**である:

- API 説明が明記している——「データを送ってくれると re-api と生データにアクセスできる」。
- 実測でも、**自サイト以外からの呼び出しには HTTP 207・本文0バイト**を返す。
  Referer を `https://globe.adsb.lol/` と偽ればすり抜けられるが、それは**アクセス制御の迂回**である。

同じ理由で `opendata.adsb.fi`（documented 1 req/s・実測 12/12 成功）も採らなかった——
利用条件が **personal, non-commercial use only** で、公開サイトから再配信する形はそこに収まらない。
⚠ この2つは「もっと欲しい」に対して**技術的には効くのに、条件を読むと使えない**選択肢で、
だからこそ記録しておく。全球を1回で返す正規の道は2つ、**どちらも人が決めること**である:
**OpenSky の書面合意**（`AVIATION_PROVIDER=opensky` は既に実装済み・`openskyConfigured: false`）か、
**adsb.lol に受信機を提供して feeder になる**か。

### 6. 方位磁針 — 二等辺三角形2枚から、方位環へ

「いまは簡素すぎ。チープ。」旧実装は `viewBox 0 0 24 24` の **polygon 2枚**
（赤 `#ff3b30` と 固定灰 `#9aa0a6`）だけだった。

新しい図形（`viewBox 0 0 40 40`）は、**リング**・**4方位＋4隅の目盛り**・**二面取りの針**
（北は明暗2面の赤、南は `currentColor` の濃淡2面）・**2重の軸受け**からなる方位環である。

- ⚠ **北の針以外はすべて `currentColor`。** `#9aa0a6` は明るい背景のために選ばれた中間灰で、
  #R480 以来この釦が着ている**暗いガラスの上では泥**になる。`.compass-btn` に
  `color:var(--text-main)` を足したので、環も目盛りも南の針も軸受けもテーマに追従する
  （携帯の `.m-fab` は #R23 から既にそうしていた）。
- ⚠ **デスクトップ 34px と携帯 38px は同じ幾何**で、検査が両者の属性列の一致を見る——
  片方だけ直す事故は、この製品が何度もやっている形である。
- ⚠ **どちらの SVG も `id` を持たない。** 同じ文書に2つ在るので、`<defs>` の gradient を足した
  瞬間に**ページ内で id が衝突**し、後から来たほうが黙って前のを参照する。CSS でも既存の検査でも
  見えない壊れ方なので、「入れられなくする」ほうを門にした（面取りは flat な塗り分けで足りる）。
- 回転の書き手（`js/map-readout.js` / `js/mobile-ui.js`）と #R480 の7つの呼び出し元は**一切変えていない**。
  `rotate(-bearing)` は SVG 全体にかかるので、**方位盤ごと回る**——実物の compass card と同じ。

### 7. 同じ回の追加依頼 — 余白

> 「Map / Satellite / Flat / Globe / ⛰️3D / 📐Measure / 🔗Share / Layers のバーの縦幅を詰めて。地名検索バーも。」
> 「座標標高常時表示バーは、もっと左下に詰めて。」
> 「Chronosボタンも、座標標高常時表示部と同じ幅で右下にそろえて。」
> （「同じ幅」の意味を確認したところ）「いや、UIはそのままで隙間だけ同じように詰めるってこと。
> あと、Chronosボタン内の時計アイコンはもっと時計って感じに。雑多でチープで周囲と不釣り合いなアイコンにするのはNG。」

**字は1つも小さくしていない。** 縮んだのは字の周りの余白だけである（実測 1440×900）:

| | 変更前 | 変更後 |
|---|---|---|
| ピル行（`.map-view-row` / `#map-tools-group`） | 35.3 px | **31.3 px** |
| `.view-btn`（字は 12px のまま） | 28 px（上下 7px） | **24 px**（上下 5px） |
| 地名検索バー `.map-search`（字は 14px のまま） | 42 px | **34 px** |
| 右上スタック全体 | 120.7 px | **112.7 px** |

⚠ **角丸は高さの半分である。** `.map-search` の `border-radius:21px` は高さ 42px のちょうど半分で、
高さだけ詰めるとピルが「角の丸い長方形」に化ける。18px へ一緒に動かし、検査は数値ではなく
**「半径が高さの半分に追随していること」**を出荷される値から導いて見る。
⚠ **携帯には1バイトも届かない。** 携帯の `.map-search` は自分の規則で 46px の丸 FAB（`padding:0`）に
なるので、ここで動かした3つの数はどれも上書きされている。

**下の2つの隅。** 座標・標高バーは左下 9px → **6px**、Chronos は右下 10px → **6px**。
Chronos の UI（大きさ・字・余白・形）は**一切変えていない**——動いたのは隅からの距離だけである。
⚠ **「そろえた」は、2か所に同じ数を書くことではない。** 片方だけ動かせる限りそれは偶然の一致で、
#R500 が9件見つけたのと同じ形になる。だから検査は**2つの数が等しいこと**を門にしていて、
値そのものは `tests/r252` ⑥ と `tests/r485` ⑤ が錨として持っている
（右パネル退避の `calc(var(--lsr-w) + N)` も、各要素**自身の**隅の余白に合わせた）。

**Chronos の字。** 旧アイコンは rotate-ccw ——角の目印と閉じかけの弧、その中に針が入ったもので、
23px では「時計」ではなく**「戻す」**と読める。新しい字は時計そのもの（文字盤・12/3/6/9 の目盛り・
長短の針・軸受け）で、**この回の方位環と同じ作り**にしてある——地図の chrome にある計器は2つだけで、
2つは揃って見えるべきだから。

### 検査

`tests/r504-checks.test.mjs` 12 本。⚠ 守るのは「今の定数が正しいこと」ではなく**構造**である。

1. **上流へ出る道は `takeTokens()` を通ったものしか無い** — `readTile` の呼び出し元は1つ、
   `readSerial` の呼び出し元は2つ、`takeTokens` の呼び出しも2つで**数が一致する**。
   視野側は `ranked` ではなく `spent`（許可された枚数）を渡す。
2. **出荷される bucket の算術そのものを vm で回す**（#R498 の手口）。空のバケツは経過時間ぶん、
   1日待っても `READ_BURST` まで、backoff 中は 0、そして**1時間ねだり続けても平均は上限以下**——
   かつ**上限の 95 % 以上は実際に使う**（使わない上限は上げた意味が無い）。
3. **isolate を越えるべき4つが全部 `sweep.json` に載り、長さが変わったら捨てる。**
   `saveSweep` が**実際に走る2経路の両方**から呼ばれる（#R341: `after()` は応答を越えて生きない）。
4. **45 秒の「間隔」は消え、`VIEW_STALE_S` の「訊く価値」は残っている。**
5. ワークフローは `tiles=` で**要求**するだけで、`SWEEP_TILES_MAX` と bucket が**許可**する。
6. 方位環はデスクトップと携帯で**同じ幾何**。
7. 固定色は北の2面（`#ff453a` / `#d2312a`）だけ・`currentColor` が6箇所以上・
   `.compass-btn` が `color` を持つ（持たなければ継承先は偶然になる）。
8. どちらの SVG にも `id` が無い。
9. #R480 の約束（glass を再宣言しない・`box-shadow` はここにしかない・7つの呼び出し元）が生きている。
