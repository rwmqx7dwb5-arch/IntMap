### ①b ⚠⚠⚠ 「塗りすぎ」——**スライダーがスカラを書き、式を消していた**

本番の絵を見て、警報が出ている国まで斜線が乗っていることに気づいた。読み戻したら理由は 1 行だった：

```
getPaint('wp-alert-hatch','fill-opacity')  →  0.38      ← ただの数
```

このレイヤーは `['case', ['==', ['feature-state','wpAlert'], 0], 0.9, 0]` で宣言されている——
**どの国を斜線にするかを決めているのはこの式である**。`_applyGenericOpacity` はそこへスライダーの
値を書き込んでいたので、**地球上のすべての国が 38% で斜線**になっていた（警報が出ている国も含めて）。
斜線は色を持たない一様なパターンなので、これは地図全面に薄い網を掛けるのと同じである。

⚠ **#R273 は同じ機構の 1 つ隣（境界線の `line-opacity`）に当たり、per-layer の<b>免除</b>で答えた。**
ここでは免除は形が違う——読み手は斜線がスライダーに従うことは望んでおり、望んでいないのは
**スライダーが「誰を」塗るかを決める**ことである。
→ レイヤーは**組み立て関数**を登録できる（`window._opacityExpr`）。条件は残り、スライダーは
その**内側**で掛かる。実測、38% で `['case', …, 0.836, 0]`、80% で `['case', …, 1, 0]`——
式は生きたまま。目視でも、ドイツ・スイス・フランス・イタリア・オーストリアから斜線が消えた。

### ② ⚠⚠⚠ 「境界線解像度が低すぎる」——**同梱の索引は<b>床</b>であって答えではない**

#R290 の `data/admin1-world.json.gz` は Douglas–Peucker 0.01°（≈1.1 km）。それは**この索引が存在する
理由である世界ズームでは見えない**誤差で、読み手が海岸線まで寄ったときに見えるのはまさにそれである。
**同梱を細かくしても解けない**——同じファイルが世界表示を成立させているし、Natural Earth 10m の原本は
簡略化前で 40.7 MB ある。

→ **段階にした。** `UNIT_HIRES_Z`（= 5）以上で、**画面に入っていて、まだ同梱の索引で描かれている国**は、
その国自身の公開境界（geoBoundaries ADM1——配置のはしごが既に信頼している出典）へ差し替える。
視野で切り、2 か国ずつ、そして①のキャッシュに入るので**1つの国につき1回だけ**払う。
`UNIT_SRC` がどの索引から来たかを覚えているので、差し替えは「粗いものだけ」に効く。

### ③ ⚠⚠⚠ 「IntMap独自階級は、灰色、黄色、赤色、紫色、黒に」

この凡例はもともと5行ある——4段階＋「発令なし」。5つの名前は**その5行**だった（読み手に確認した）。
`PAL_NORM` は 黄 `#ffd60a` → 赤 `#ff3b30` → 紫 `#af52de` → 黒 `#141418`、灰は `NONE_COL`。
⚠ #R273 は「どの機関の配色とも被らせない」ために前の4色を選んだ。**並びは気象庁のものと同じになる**が、
値は IntMap 自身のもの（iOS 系統色）で、パネルは今までどおり「IntMap 独自の換算であり、同じ段でも
国どうしの危険度が等しいという意味ではない」と**言葉で**言う。
⚠ **色の「名前」は定数を信じずに計算して検査する**（`tests/r293 ①` が色相・彩度・明度から
黄/赤/紫/黒を判定する）。「灰色塗の色味は少しだけ白に近づけろ」は `#c8c8cb` → `#dcdce0`、
`QUIET_COL` も同じだけ動かし、**実体は1つ**にした（塗り式が定数を名指しするので、灰色はもう
リポジトリに1回しか書かれていない）。

### ④ ⚠⚠⚠ 「日本の特別警報の凡例だけ、図形の形が違う」——**形を選んだコードは無い。輪郭が<b>内側</b>にあった**

どの見本も同じ 12 px の角丸正方形で、**形を変えている場所は無い**。違っていたのは、変わりうる唯一のもの——
`border:1px solid rgba(128,128,128,0.35)` の**コントラストの相手**である。境界線の相手は**塗り**なので、
気象庁の特別警報 `#0c000c`——このパネルのどの見本より暗い唯一の色——だけが**自分より明るい線で
縁取られ**、黄・赤・紫の「塗りつぶされた四角」の隣で**輪だけの四角**に見えていた。

→ **輪郭を外へ出した**（`box-shadow:0 0 0 1px`）。外側の相手は**パネル**なので、どの行でも同じである。
⚠ そして同じパネルが**3つの寸法**を持っていた——実測、国の一覧が 10 px、`keyRows` が 12 px、
`legendFor` の斜線見本が 14 px。1つの考えに3つの大きさ。→ `SW_PX` ひとつ。

### ⑤ ⚠⚠ 「斜線塗をもっと見やすい感じに」／「斜線塗がなんなのか分かるように、凡例に追加しろ」

#R290 はタイルの下敷きを剥がした。それは正しく、**信号の全部を1本の中間灰色の線に預けた**——
明るい基図では読めるが、衛星画像とダークテーマではほとんど見えない。
→ **1本ずつが自分の縁取りを持つ**（薄い太線を先に、濃い線をその上に）。下敷きは戻らない：
**隙間は完全に透明のまま**で、`tests/r293 ②` が被覆率を計算して 45% 未満を要求する。
⚠ そして**凡例の見本はそのタイルそのもの**（`toDataURL()`）。手書きの `repeating-linear-gradient` は
**数値の違うものが2つ**あった——#R270 が払った「凡例が自分の色と矛盾する」形が待っていた。
斜線の行は**両モードの凡例に**入った。

### ⑥ ⚠⚠ 「ポップアップがでかすぎる」——**大きかったのは警報ではなかった**

実測、警報が1件だけ出ている地点のカードは約 300 px あり、そのうち警報は約 90 px。残りは

→ 階級表は消す（凡例にも国のカードにもあり、**この**警報の階級はその行に出ている）。余白は1つ。
幅 316 px。12 件積むのを 6 件に。

**そして2つの時計を書いた。**「いつ発表の情報か、そしてIntMapがいつ取得した情報か」は**別の問い**で、
#R269 は片方だけを見て 83 日凍った feed を「成功」と報告した回である。
⚠ **発表時刻は relay が送っていなかった**——`areas` は `fetchedAt`（relay が読んだ時刻）しか持たず、
CAP 電文自身の `sent` は `warnings` の行にしか入っていなかった。MeteoAlarm と2つの CAP サービスの

### ⑦ ⚠⚠⚠ Chronos の「過去表示中」——**同じ主張をする要素が2つあり、直したのは片方だった**

#R290 は**折り畳みボタンの副題**（`#ntl-open-s`）に瞬間を読ませた。読み手が名指ししたのは

実測、時計を2日先に置いた同じフレームで：

### ⑧ ⚠⚠⚠ 「地図中心の標準時、機能していない」——**三度目、そして三度とも別の原因**

#R289 がアクセサを公開し、#R290 が「40 行下の2つ目の `window.IntMapTimeZones=` が名前ごと上書き
していた」を直した。今回、**6メンバーは全部あり `offsetAt` は正答する**（東京 +9・ニューヨーク −5）。
それでも実測：

```
localStorage intmap_chronos_zone = 'map'   （復元されている）
<select>                          = 'map'   （復元されている）
IntMapTimeZones.ready()           = false
地図はニューヨーク中心、パネルは 17:58 · UTC+09:00   ← 端末（東京）の時計
```

ポリゴンを**取りに行く** `ensure()` の呼び出しは**1か所しか無かった**——`<select>` の change ハンドラ。
localStorage から復元された設定は change を起こさないので、データは一度も要求されず、`offsetAt` は
永久に null を返し、`zSpec()` は `{local:true}` に落ちる——#R290 が「黙るように書かれている」と
書いたその fallback である。
→ 要求は関数（`zoneEnsure`）にして、**2つの扉**から呼ぶ。⚠ そして**カメラに追従する**：
「地図中心の」はいまカメラがどこにあるかについての主張で、選んだ瞬間の答えはパンするまでしか正しくない。

### ⑨ ⚠⚠ 「時刻と予報タブを分けるな」／「Chronosで時間を変更したら…すべての要素を合わせる」

#R288 が予報タブを足し、#R290 が「ECMWF の時間選択を Chronos に受け流さなくてよい」に答えて
**両方向の結線を切った**。今回の2文は、その**片方だけ**を戻す：

- **押す側（レイヤー → Chronos）は切ったまま**（`_pushClock` は no-op）。予報を1時間動かしても
  ニュース・歴史的国境・昼夜境界・国別統計は動かない。各レイヤーは自分の凡例に自分の時刻 UI を持つ。
- **引く側（Chronos → レイヤー）を結線した**（`followClock` を購読）。Chronos はアプリの唯一の時計
  なので、そこで選ばれた瞬間は全部の時間依存レイヤーが見せている瞬間でなければならない。
  ⚠ `covers()` が歯止め：1972 年へ旅することは予報の要求ではないので、軸は動かない。

**そして2つのタブは1つになった。** 4つ目のタブが必要だったのは、再生操作が**モデルの index を直接**
動かし、スライダーが**時計**を動かしていたからである。いまはどちらも時計しか書かないので、
「時刻」タブが両方を持てる。日付ピッカーの上限はモデルの最終有効時刻まで伸びた。

### ⑩ ⚠⚠⚠ 「Windyと完全に同じ風速と色の対応に」——**借りていたのは区切り値だけで、色は書き起こしだった**

現行表は「Windy 相当の独自表」と自称していた。windy.com 自身の塗る関数と比べた実測：

| v (m/s) | IntMap（旧） | Windy（実物） | Δmax |
|---|---|---|---|
| 5 | 36,160,168 | 77,141,123 | 45 |
| 15 | 214,202,60 | 161,108,92 | **94** |
| 25 | 228,68,57 | 95,100,156 | **133** |
| 60 | 240,220,245 | 214,209,127 | 118 |

25 m/s で**こちらは赤、Windy は青紫**。45 m/s から上はこちらが白に飽和し、Windy はカーキから灰へ行く。
「高風速帯でも同じになるように」は、**最も外れていた半分**を名指ししていた。

⚠⚠⚠ **正本は宣言表ではなく<b>塗る関数</b>である**——`W.colors.wind.defaultColorGradient` は 20 停留点だが、
`RGBA(v)`（0〜104 m/s を 2,048 段に前計算した表）は**その線形補間と一致しない**（実測 32.25 m/s で
20/255）。**#R288 が気温で見つけた形がそのまま再現した。**
→ `RGBA` を 0.1 m/s 刻みで 1,041 点標本化し、線形補間でそれを再現する最小の停留点集合に落とすと
**27 停留点・最大チャネル誤差 3/255**（#R288 が気温に課したのと同じ基準）。実測、節では厳密一致、
104 m/s より上は Windy と同じく灰、**α は全域 255**（Windy 自身に静穏の穴は無い）。
`rampFrom(…, 0.1)` は変わらず、段数が 601 → 1,041 になっただけである。

### ⑪ ⚠⚠⚠ 「透明度100%は、全然透明度100%ではない」——**偽だったのは数値ではなく<b>言葉</b>だった**

まず測った。**不透明かどうかは、同じ地点を<b>2つの基図</b>で読めば1回で決着する**——不透明な層は
自分の下に何があるか知りようがないので、2つの読みは一致しなければならない。

| レイヤー・100% | 一致した標本 | 最大チャネル差 |
|---|---|---|
| 気温（ECMWF） | **8 / 9** | **1** |
| 風（色面） | **7 / 9** | **1** |

**どちらも完全に不透明**である。スライダーは正しい。正しくなかったのは**名前**で、同じ操作子が
en/de/es/fr/ko/zh で「Opacity（不透明度）」、**日本語とロシア語だけ「透明度」「Прозрачность」**——
**逆の量**だった。その語のもとでは 100% は「見えない」を意味する。
→ 7 か所を `不透明度` / `непрозрачность` に直した。⚠ これは1つの共有操作子なので、
「ほかの…レイヤーも見つけたら直せ」は**自動的に全レイヤーに効く**。
`tests/r293 ⑪` は「英語側が opacity である組の日本語に『透明度』が単独で現れない」を検査する。

### ⑫ 「タイムスライダーをつけろ」——**`<select>` と<b>両方</b>で、離散性は失われない**

#R290 は range を退けた。理由は「index の range は連続に見えるので、『データのない時間を選べない』は
コントロールについての主張として成り立たない」だった。その議論は**コントロールが何を含意するか**に
ついてのもので、答えは2つを1つにすること——range は**モデル自身の index** を `step=1` で刻むので
**到達できる位置はすべて公開された有効時刻**であり、隣の `<select>` がいま乗っている時刻を**名指す**。
⚠ ドラッグ中は軸だけ動かし、取得は `change`（離した瞬間）——#R286 の「点滅と異常に遅い」を作った
range の性質を、それを生む側で分けた。

### ⑬ 「NATO / EU は赤から紫に連続的に」——**分離度は目的ではなく<b>帰結</b>になった**

#R290 は「どれだけ離れて見えるか」を最大化して色相を1周させ、CIE76 で 26.1 を得た。その集合は
**濃紺で始まり、赤を途中で通り、藤色で終わる**——遠いことは事実で、**順序ではない**。それが
「ランダムな色の分け方」の実体だった。
→ 色相が**赤（最古）から橙・黄・緑・青を経て紫（最新）へ単調に**進む ramp。実測、最接近ペアは
**23.9**（#R290 の 26.1、置き換える viridis 標本の 12.8）で、**最接近ペアは必ず隣り合う波**である——
連続 ramp の署名で、混同しうる2つは時間的な隣どうし、遠い2つは決して混ざらない。
`tests/r290 ⑮` は閾値を下げるのではなく**問いを変えた**（単調性・向き・隣接性を検査する）。

### ⚠⚠⚠ ② 「爆速」——**ローカルで測った 1,240 ms は本番で再現しなかった**

本文 ① は「最長タスク 7,597 → 1,240 ms」と書いた。**それはローカル配信で測った数字で、本番では
そうならない。** 本番実測（deploy 後、同じ計器、80 秒）：

| | R292 本番 | R293 本番・初回 | R293 本番・2回目 |
|---|---|---|---|
| フレーム間隔 p50 | 16.7 ms | 16.7 ms | 16.7 ms |
| **最長タスク** | **7,597 ms** | **7,137 ms** | **6,747 ms** |
| 合計ブロッキング | 20,085 ms | 22,085 ms | 21,099 ms |
| 総通信 | 46.37 MB | 42.40 MB | **17.28 MB** |
| geoBoundaries | 23.07 MB | 20.41 MB | **0.00 MB** |

**キャッシュは効いている**（2回目の geoBoundaries は 0 バイト、総通信は 42.4 → 17.3 MB）。
**固まる時間はほとんど変わっていない。** そして 2 回目——geoBoundaries を 1 バイトも読まない回——
でも 6.7 秒固まるのだから、**その 7 秒は geoBoundaries の復号ではなかった**。

原因を測り直した（2 回目の訪問で、60 ms 以上の復号を全部記録）：

```
2,761 ms  json  apiprevmet3.inmet.gov.br/avisos/ativos          ← ブラジルの警報そのもの
2,051 ms  json  alerts-relay?swicgeo=019                        ← WMO 登録簿の区域の形
1,528 ms  json  ne_10m_admin_0_countries.geojson                ← 高解像度の国境（別モジュール）
  905 ms  json  dwd:Warnungen_Landkreise                        ← ドイツの警報そのもの
最長タスク 2,842 / 1,830 / 1,695 / 1,154 ms（この回は 6.7 秒の 1 本ではなかった）
```

つまり残っているのは**警報の本体と国境そのものの復号**で、この回が狙った境界データではない。
そして最長タスクは**回ごとに 2.8〜7.1 秒とばらつく**——到着の重なり方に依存する。

⚠⚠⚠ **本文 ① の「1,240 ms」は取り消す。** 正しい主張は2つに分かれる：
**⑴ この回が削ったのは<b>通信</b>である**——二重取得をやめ、2 回目の訪問を 42.4 → 17.3 MB にした。
**⑵ 主スレッドの固まりは削れていない。** 次に効くのは復号をワーカーへ出すことで、それは
このラウンドではやっていない。**やっていないことを、やったと書かない。**
