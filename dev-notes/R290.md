### ① ⚠⚠⚠ 「灰色塗と灰色斜線が両方ある」——**斜線のタイルが、自分の下に灰色を敷いていた**

`ensureHatch()` が作る 10×10 のパターンはこう始まっていた。

```js
g.fillStyle='rgba(158,162,170,0.26)'; g.fillRect(0,0,S,S);   /* ← 灰色を1枚 */
g.strokeStyle='rgba(92,96,104,0.72)'; …                       /* ← その上に斜線 */
```

つまりこの地図は、区別しろと言われている 2 つの見え方を**同じ場所で両方描いていた**——
「未対応／未取得」は**灰色＋斜線**、「発令なし」は**灰色**。斜線の国はもれなく、静かな国の見え方を
下に着ていた。「灰色塗と灰色斜線が両方ある地域があるが、どうなっとんねんごら」は、この 1 行のことである。

→ タイルは `clearRect` から始まり、**線だけ**が信号を運ぶ（少し濃く・少し太く：後ろ盾が無くなったので）。
2 つの主張は**見た目として排他**になった。灰色は「読んだ。何も出ていない」以外の意味を持たない。

⚠ **5 ラウンド、状態の<b>数</b>と<b>意味</b>だけを議論していて、<b>絵</b>を見ていなかった。**
`washTier` の戻り値（0 / 1 / 2 / 11–14）は #R284 以降ずっと議論の的だったが、
その 0 が実際にどう塗られるかは #R273 で書かれたきり誰も読み返していない。

⚠ **目視ではなく画素で確かめた**（[[intmap-recurring-lessons]]：**画素の目視で判定するな**）。
レイヤーを入れる前と後で同じ 24×24 の区画を `readPixels` し、差の最大チャネルを数える——
斜線が灰色を敷いていないなら、**線に当たっていない画素は変わらない**はずである。

| 場所 | tier | 変化しなかった画素 | 平均差 |
|---|---|---|---|
| アンゴラ（フィード無し＝斜線） | 0 | **458 / 576（79.5%）** | **2.1** |
| チャド（読んで静か＝区分の灰色） | 2 | 112 / 576（19.4%） | 17.8 |
| ニジェール | 2 | 122 / 576（21.2%） | 16.9 |

旧タイルなら斜線の国も**全画素**が 0.26 の灰色ぶんずれる。79.5% が動いていないことが、
「下に灰色を敷いていない」の証拠である。

### ② ⚠⚠⚠ 「日本以外でも区分単位で」——**95 か国が国 1 枚のままだった**

本番で測った（レイヤー投入 100 秒）。

| | R289 本番 |
|---|---|
| 区分単位で描かれている国 | **50** |
| 国全体の灰色 1 枚のままの国 | **95** |
| 斜線（未対応 102 ＋ 未読） | 106 |

理由は素直で、**閉じた索引を持たない国は geoBoundaries を 1 国ずつ**（0.3–2 MB × 同時 2 本）
取りに行くしかなかった。95 か国ぶんで数十 MB になるので、そのままでは「重すぎる」のもう半分になる。

**ブラウザが払える世界 ADM1 は、公開されていない。** 測った：

| 候補 | 実測 |
|---|---|
| Natural Earth 50m admin-1（現行） | 294 features・**9 か国** |
| Natural Earth 10m admin-1 | 4,596 features・251 か国・**40.7 MB**（gzip 12.1 MB）。jsDelivr は **403** |
| geoBoundaries CGAZ ADM1 | **360 MB** |
| geoBoundaries gbOpen | **1 国ずつ**・0.3–2 MB |

→ **ビルド時に一度だけ間引いて同梱する。** `scripts/build-admin1.mjs` が Natural Earth 10m を
Douglas–Peucker 0.01°（≈1.1 km）＋座標 4 桁で落とし、`data/admin1-world.json.gz` を書く——
**247 か国・4,515 区分・2.38 MB（gzip）**。読み出しは `DecompressionStream('gzip')`（`data/gazetteer-world.json.gz`
と同じ経路）。

⚠ **これは地図が読む索引であって、気象についての第2の意見ではない。** 何が発令されているか・
その階級・その文言は、いまも全部その国の機関のもの。NUTS や国土数値情報と同じ扱いである。

⚠ **そして「視野」と「ズーム」で切る。** 単位の集合は貯まるので、貯まったものを全部 publish すると
コレクションが視点を動かすたびに育つ——実測、**世界ズームで 6,101 区分・10.0 MB**。
`QUIET_UNIT_Z`（= 3）未満では区分の境界線は 0.25 px で、**国 1 枚と 500 枚は同じ絵**になる。
実測、欧州 z4.5 で **34 か国・1,595 区分**。

⚠ `washTier` が問うのは「**いま単位レイヤーがこの国を描いているか**」（`quietSet`）であって
「形を持っているか」ではない。持っているが画面外の国を 2（透明）にすると、**誰も塗らない国**ができる。

### ③ ⚠⚠⚠ 「塗漏れが多すぎる」——**Slovakia は 0 / 48 で、原因は境界データの<b>綴り</b>だった**

本番の `placed / published` を国別に出した。最悪は **SVK 0/48**。SHMÚ は okres（郡）で警報を出し、
geoBoundaries はその 79 件を全部持っている——のに 1 件も当たらない。中身を見た：

```
MeteoAlarm : Michalovce | Trebišov | Košice | Sobrance | Revúca | Rožňava | Piešťany …
geoBoundaries : District of Bardejov | District of Trebi ov | District of Ronnava | District of Piertany …
```

**2 つ欠けていた。** ⑴ `_LEAD`（「先頭の行政語は名前の一部ではない」）に **English の総称**
（`District of` / `Region of` / `State of` / `Governorate of` …）が無かった。
⑵ geoBoundaries の `shapeName` は**非 ASCII 文字が壊れている**——「Trebi ov」「Ronnava」「Piertany」
「Banskk vtiavnica」。正規化しても一致しない。

→ ⑴ 総称を足す。⑵ **最後の段に「一意なら通す編集距離」**を足す：正規化後の長さ差が上限以内・
先頭 1 文字が一致・上限は 9 文字未満なら 1／以上なら 2、そして**候補がちょうど 1 件のときだけ**答える
（既存の語幹段が守っている「2 件に当たる語幹は答えではなく籤である」と同じ規則）。

| | 旧 | 総称のみ | ＋編集距離 |
|---|---|---|---|
| Slovakia | 0 / 48 | 25 | **39** |
| Moldova | 28 / 42 | 28 | **32** |
| Greece | 0 / 15 | 0 | **3** |
| Belgium | 1 | 1 | **2** |

回復した組は全部目視した（Trebišov→「District of Trebi ov」、Rožňava→「District of Ronnava」…）——
**すべて同じ郡**である。

WMO 登録簿側にも同じ形があった：**その機関が名前は出しているのにポリゴンを出していない区域は
まるごと捨てられていた**。その国のために既に組んだ形の索引→世界 ADM1 索引、の順で引く。

本番の合計（同じ計器・同じ 75 秒）：**2,390 / 2,551 → 3,581 / 3,672**。
ITA・BEL・PRT・POL の一部は不足リストから消えた。

### ④ ⚠⚠⚠ 「重すぎる」——**75 秒で 190 回、コレクションを丸ごと上げ直していた**

| 実測（本番 R289・75 秒） | |
|---|---|
| `wp-alert` の `setSourceData` | **48 回**・累計 **85,935 features** |
| `wp-alert-quiet-src` | **98 回**・累計 **266,500 features** |
| `setFeatureState` | **19,578 回** |
| 最長の main-thread タスク | **8,245 ms** |
| フレーム間隔 p50 / p90 / p99 | **166.7 / 1,016.7 / 8,166.3 ms** |

`publish()` が**バッチが着地するたびに最後まで走る**のが原因で、冷たい輪番の 6 枠・MeteoAlarm・
WMO 登録簿・各国フィードで、1 tick に何十回も着地する。**絵は何ひとつ変わっていない**——
同じコレクションを何度も parse し直し、tile し直していただけ。

間引き・簡略化はしていない。**同じ仕事を 2 回しないようにした**だけ：

1. **publish をまとめる**（160 ms トレーリング）。データは着いた瞬間に着く。待つのは告知だけ。
2. **中身が変わっていないコレクションは上げ直さない**（警報側は塗りが読む属性の 32bit ハッシュ、
   区分側は「どの国が何区分」の署名）。⚠ **スタイル再読み込みで source が消えたら署名も消す**——
   でないと最適化が空の地図を残す。
3. **`setFeatureState` は tier が変わった国にだけ**書く。
4. **`countryAt`（全国境の point-in-polygon）は 1 区分につき 1 回**。それまでは publish のたびに
   最大 3,713 区分 × 258 国境を走っていた——これが 2,418 ms のタスクの正体。
5. **形のはしごは (国, 区域名) につき 1 回**（`maFeatures()` は MeteoAlarm のバッチごとに 35 か国を
   全部組み直す＝最大 1.4 万回。今回足した編集距離の段は索引を全走査するので、これが無いと
   直したことが重さになる）。

| 実測（同じ計器） | R289 本番 | R290 |
|---|---|---|
| フレーム間隔 p50 | 166.7 ms | **33.3 ms** |
| p90 | 1,016.7 ms | **633.3 ms** |
| p99 | 8,166.3 ms | **1,866.7 ms** |
| 最長タスク | 8,245 ms | **2,593 ms** |
| `setFeatureState` | 19,578 | **8,627** |
| 区分の上げ直し（世界ズーム） | 98 回 / 266,500 features | **0 features** |
| 区分の上げ直し（欧州 z4.2） | 118 回 | **44 回** |

対照も取った——**同じビルドでレイヤーを入れずに** 75 秒走らせると p50 は **16.7 ms**（60 fps ちょうど）。
つまりこのレイヤーが背負っていた分は **150 ms → 16.6 ms**。

⚠ 「更新が遅すぎる」も同じ修正で動いた。実測、MeteoAlarm **35/35 が t+46 秒**、WMO 登録簿
**93/93 が t+40 秒**（R289 は t+75 秒で未読 18）。残る 3〜4 か国は**未読ではなく上流エラー**なので、
パネルの計器を `pending` と `errored` に分けた——一緒に数えると「輪番が終わらない」ように見える。

### ⑤ 海のタップ

`countryAt` が空で、その地点に発令中のものも無ければ、**カードを開かず、クリックも消費しない**。
⚠ 「国が無い」だけでは条件にならない——**海上警報は水の上に出て、自分のポリゴンを持っている**。
実測、太平洋のクリックでカードは開かず、東京のクリックは 新宿区 / 雷 / 気象庁 を出す。

### ⑥ ⚠⚠⚠ Chronos の「地図中心の標準時」——**アクセサはページ上に存在しなかった**

実測、ビルド済みのページで `Object.keys(window.IntMapTimeZones)` は
**`['highlight','highlighted','clear']`**。#R289 が publish した `ensure` / `ready` / `offsetAt` が無い。

`js/layer-packs.js` には publisher が **2 つ**あり、後ろの 1 つ（#R204）が

```js
window.IntMapTimeZones={ highlight:…, highlighted:…, clear:… };   /* ← 代入。前のを消す */
```

と**名前ごと代入**していた。両方ともモジュール評価時に走るので、後ろが必ず勝つ。
`zSpec()` は `offsetAt` が無いと `{local:true}` に落ちる——**しかもその fallback は黙るように書かれていた**
ので、「地図中心の標準時」を選んだ読み手は全員、自分の端末の時計を見せられていた。

→ 両方 `Object.assign(window.IntMapTimeZones||{}, …)`。実測、6 メンバー・東京 +9・ニューヨーク −5。
`tests/r290 ⑧` が**代入が 2 つとも extend であること**を数える（3 つ目が静かに勝てないように）。

### ⑦ Chronos の折り畳みボタン／「反映内容」

#R288 が予報タブを足して**未来の瞬間が選べるようになった**のに、この行は #R105 以来
「過去を表示中」しか言わない（当時は他の種類が無かった）。→ 瞬間が今より前か後かで言葉を選ぶ。
「タップ」は消した——要素自体がボタンで、そう名乗ってもいる。

「反映内容」の欄（`#ntl-synced`）は markup ごと削除し、それだけを養っていた `kEra` / `hbAt` / `HBY` /
`on()` も一緒に消えた。どのレイヤーが選んだ瞬間で何をするかは**そのレイヤーの凡例の仕事**である。

### ⑧ ⚠⚠⚠ ECMWF の時計を、レイヤーへ戻した

#R288 は「わざわざ分けるな」に答えて、**勝手に開く箱を消し**、予報時刻をアプリ共通の時計へ流した。
読み手はその後半を覆した——「時間選択をChronosに受け流さなくてよい。個別の時間選択UIを使え。」

**受け流していたものは小さくない。** `_pushClock` はニュース・歴史的国境・昼夜境界・国別統計を
その時刻へ引きずり、`_followClock` の購読は逆に**読み手が選んだ時刻を上書き**していた。両方外した。
`_followClock` は**名前として残して公開**——「その時刻の天気」を明示的に求める操作は購読ではなく呼び出し。

各凡例が自分の時刻 UI を持つ（`window.IntMapWxPlayer.timeUI`——**1 つの宣言**を風と ECMWF が共有する。
1 つの軸の 2 つの見え方であって、2 つの時計ではない）。
⚠ **`<select>` であって range ではない。** 添字の range は**連続に見える**ので、
「データのない時間を選べない」はコントロールについての主張として成り立たない。
選択肢は `IntMapECMWF.times()` そのもの——実測 **109 段**、「21 Aug, 03:00」から。

Chronos の「予報」タブは**モデルの軸を直接動かす第 2 の見え方**として残っている（共通の瞬間には触れない）。

### ⑨ ⚠⚠⚠ 「読み込まれるまで地図が何もなくなる」——`idle` は「読み込んだ」ではない

2 スロットの入れ替え（#R284）自体は正しい。間違っていたのは**新しいほうが「出た」と判定する合図**で、
`once('idle')` ＋ 2,500 ms の予備タイマーだった。`idle` は「**いま持っているタイル**について描くものが無い」
という意味なので、まだ 1 枚も返ってきていないソースでは**即座に成立する**——古いスロットが外れ、
読み手は残りのダウンロードのあいだ基図を見る。**予備タイマーも同じ側に倒れていた。**

→ 合図は**そのソース自身の `sourcedata` + `isSourceLoaded`**。予備は 12 秒で、届かないソースが
2 枚のスロットを抱えたままにならないためだけにある。実測、6 段の時刻ジャンプを 250 ms 刻みで
40 回標本化して、**どちらのスロットも見えない瞬間は 0**。

### ⑩ ⚠⚠⚠ 風の「点滅」——**同じ大きさへの resize が canvas を消していた**

`js/weather.js` は地図の `moveend`——**すべてのパン・ズームの終わり**——から `resize()` を呼び、
それが無条件に走っていた。`canvas.width` への代入は**同じ値でも canvas を消す**。`makeTargets()` は
残像用の framebuffer を 2 枚とも作り直す。`cleared = true` が streak を捨てる。
つまり**読み手が地図から指を離すたびにアニメーションが全消しされ、0.75 秒かけて戻っていた**。

→ 同じ寸法・同じ DPR への `resize()` は**何もせず返る**。
実測、**5 回のパンで canvas 再生成 0 回**／ビューポートを実際に 1280→1100 に変えると**ちょうど 1 回**
（新しい寸法で）。

⚠ **調速機にもヒステリシスを入れた。** 閾値 9 ms / 4.5 ms を 30 フレームごとに判定していたので、
そのあたりに座る機械は 18% 減らし次の窓で 12% 戻し、**永久に振動する**——毎秒 2 回脈打つ密度も
「点滅」である。判定は 2 回続けて同じでなければ動かず、不感帯は広く、刻みは小さい。

⚠ **前の時刻の残像**：新しい時刻が届くまで古い場で動かし続けるのは #R284 の意図どおりで正しい。
やっていなかったのは**届いた瞬間に終わらせる**ことで、そのせいで新しい時刻の色の上を前の時刻の
軌跡が流れていた。`opt.step` のときだけ `renderer.reseed()`（撒き直し＋残像テクスチャを落とす）。
最初の読み込みでは撃たない——残す前の時刻が無い。

⚠ 名前は **`Wind (animated)` → `Wind` / `風`**（9 言語）。

### ⑪ 気温レイヤー：透明度・地点値・海岸線

- **透明度**は**存在していて、到達できなかった**。実測、`#lyrrow-ec-temp` の `<input class="ec-op">` は
  レイヤーを入れた状態でも computed `display: none`——`css/intmap.css` が #R16 の絶対規則
  （「レイヤー欄にスライダーを置かない。そのレイヤーの**凡例**にだけ置く」）を強制しており、
  ECMWF の 9 行は**凡例側を持っていなかった**。他レイヤーと同じ `.dl-op-row` の形で凡例に入れた。
- **地点値**は `IntMapECMWF.valueNow` が**モジュールが保持している場**を読む。保持させていたのは
  **風だけ**（ラスタは SDK が `om://` から直接描く）。だから ECMWF ラスタの地点値は
  **一度も出たことがなかった**。⚠ 1 スロットしか無いので「気温を読ませる」と**風の場を追い出して
  粒子が止まる**——`frames` を小さな最近使用順の配列にし、上限は**個数ではなく標本数**で持つ
  （帯は 93.5 万、全球は 660 万＝7 倍違う）。実測、地点値 **17.2°C (62.9°F) · 21 Aug, 18:00**。
- **海岸線**は風と同じラッチ（`_imCoastAuto`）で 1 回だけ提案する。⚠ **気温だけ**——理屈は他の 8 つの
  ラスタにも当てはまるが、指示が名指ししたのは気温である。

### ⑫ 読み取り欄の風向き矢印／NATO・EU の配色／レイヤー検索

- **矢印は向きだけ**。#R289 が入れた速度連動のドリフトと、`innerHTML` の作り直しをまたいで位相を
  運ぶための負の `animation-delay` は、要求ごと消えた（keyframes も、`prefers-reduced-motion` の
  逃げ道も——抑えるものが無い）。回転は残る：それが向きである。
- **加盟年の配色は測れる。** ΔE00 ≈ 2.3 が広い面の弁別限界。11 波の viridis 標本は**最接近ペアが 8.1**
  で、55% 不透明度の国塗りでは足りない——「分かりにくい」は読み手ではなく配色についての事実だった。

  | 波の数 | viridis（旧） | 本ラウンド |
  |---|---|---|
  | 8（EU） | ΔE00 **12.2** | **19.7** |
  | 11（NATO） | ΔE00 **8.1** | **19.7** |
  | 14 | ΔE00 6.1 | 13.0 |

  色相を 1/3 周ではなく**ほぼ 1 周**させたので、波が増えても分離が縮まない（8 でも 11 でも 19.7）。
  ⚠ **標本ではなく<b>項</b>を採る**——10 アンカーから 11 色を補間で取り出したことが 8.1 の原因なので、
  波の数がエントリ数以下なら 1 波が 1 エントリを取る。`tests/r290 ⑮` は**この値を計算して**比べる。
- **レイヤー検索欄**は #R23 の指示で sticky を外してある（＝リストと一緒にスクロールする）ので、
  下までスクロールしてから打つと、絞り込んでいるリストの先頭も、打っている箱自身も画面の外にある。
  入力があったら**自分のスクロール親の最上部へ**来る。⚠ **動かすのはパネルであって地図ではない**
  （CONSTITUTION §3）。⚠ **1 つの定義を 2 つの検索欄が使う**（#R239 の教訓は「2 つのうち 1 つだけ直した」）。
  実測、7,071 px スクロールした状態で入力 → スクロール 0・箱の上端はパネルの padding の内側 13 px。

### ⑬ 追記（本番検証）— **2件。どちらも「読み込みの列に、誰が先に並ぶか」だった**

deploy 後の本番検証はすべて通った（build `R290`・`IntMapTimeZones` 6メンバー・時刻 145 段・
地点値 17.1 °C・海のタップでカード無し・配置 **3,950 / 4,040**・風の canvas 再生成 **0**）。
その最後に、この回が新しく作った経路を**両方のレイヤーを同時に点けて**測ったら 2 件出た。

### ① ⚠⚠⚠ 風の場と地点値の場が、**互いを追い出していた**

`frames` の上限を **標本数 16 M** にした（#R290 ⑪）。本番実測、**世界ズームで風のフレームは
13,199,360 標本**——u と v の 2 本で、`bandFor` は緯度幅 120° を超えると「地球全部」と答えるので、
世界ズームの風は全球を読む。そこへ 2 本目の全球級フレームが来ると合計 19.8 M で上限を超え、
`keepFrame` が**古いほうを捨てる**。つまり風と読み取り欄が**互いの場を消し合い**、
風は次の時刻ステップで `sampler()` が null になって**粒子が止まる**。

⚠ **#R276 追記の欠陥の再演**——「あるレイヤーの後始末が別のレイヤーの場を無効にする」が、
今度は「後始末」ではなく「**予算**」の形で出た。

→ 2つ直した。⑴ 予算を **24 M**（風の 2 本ぶん ＋ 普通の全球 1 枚）に。
⑵ そして本命——**読み取り欄は全球を要求しない**。`bandFor` は「この絵が何を覆っているか」に
答える関数で、世界ズームでは正直に「全部」と言う。地点値は**絵ではない**ので、
`bandNear` が**画面の緯度を中心 ±30° で切った帯**（約 220 万標本）を返す。
実測、両方が同居する（風 13.2 M ＋ 気温 3.5 M）。

### ② ⚠⚠⚠ 「前の時刻の粒子が残る」の待ち時間は、**自分で作っていた**

このモジュールの読み込みは**1本の列**を通る（SDK のリーダーが1つだから——#R287 が測った衝突）。
その列に、**隣の時刻の暖機**と**読み取り欄が欲しい帯**が、
**粒子が飛んでいる場の前に**並んでいた。1 ステップから新しい時刻の場が手に入るまでを実測:

| | 暖機を先に（旧） | 暖機を後ろに（新） |
|---|---|---|
| z4.5・風だけ | 711 / 447 ms | **396 / 515 ms** |
| z4.5・風＋気温ラスタ | **30 秒たっても来ない** | **1,073 / 1,737 ms** |
| 世界ズーム（全球 27 MB） | 13.6 / 18.5 s | 11.6 / 14.3 s（回線律速・差なし） |

暖機とは**定義上あとでよい仕事**である。軸が**止まってから** 2.5 秒で走り、
さらにステップが来たら**予定を置き換える**（積み増さない）。
同じ A/B を 1 セッションの中で取ったので、回線ではなく変更が動かしたことも測ってある。

⚠ **「重すぎる」と「残像が残る」は同じ列の話だった。** 速くする作業が、
速くしたい当のものの前に並んでいた。

### ⑭ 追記2（本番検証）— **暖機は「読まれる範囲」を暖めるものである**

追記②を deploy して本番でもう一度、**風と気温を同時に点けて z4.5** で測ったら、まだ出た——
**新しい時刻の場が 39 秒たっても来ない**（手元のフレームは古い時刻のまま）。列の順番は直ったのに、
**列に入れたものが大きすぎた**。

`prefetchVariable(v, null)` は**変数まるごと＝全球**を暖める。画面のフレームも全球だったあいだは
それで正しかった（#R288）が、**#R288 以降その場は視野の緯度帯**（93.5 万標本 対 660 万）である。
つまり 3 変数ぶんの全球暖機は、**約 80 MB を、1.6 MB で足りるステップの前に**並べていた。

→ 暖機は `load()` と**同じ bounds** で作った state の `ranges` を使う。実測、同じ本番相当のビルドで
**1 歩目 1,364 ms・2 歩目 742 ms**（それまでは 30 秒でも来ない）。
`null`（全球）は世界ズームとラスタタイルのための正しい既定として残る。
⚠ 「もう暖めた」の印は**ファイル＋帯**で持つ——帯の暖機が、していない全球を「済み」に見せないため。

⚠⚠ **「暖機」と名の付くものは、効いていなくても誰も気づかない**（[[intmap-r286-lessons]]）。
今回は**効きすぎて邪魔をしていた**——同じ理由で、**測らないと分からない**。
