## R325 — **6ラウンドが測っていたのは2本のうち1本で、色面のほうは毎時刻ごとに惑星ぜんぶを読んでいた**

「風レイヤーは品質保ったまま、起動から日時変更からすべてに至るまで、爆速にしろ。」（**7回目**。
#R297 #R299 #R305 #R307 #R308 #R310 #R314 の続き）

### ⚠⚠⚠ ① 日本の7枚のタイルが、地球ぜんぶの復号から作られていた

過去6ラウンドは**粒子の帯**を測ってきた——小さくし、早く出し、合流できるようにし、キャッシュし、
最後は1時刻先読みして「ステップの粒子は無料」まで持っていった。**色面のほうは一度も測られていない。**
本番ビルドで SDK 自身の読み手に計器を入れ、日本上空（z6・132.8,32.3 → 143.2,39.6）で1ステップ:

| | 標本数 | 1ステップの通信 | `readVariable`（主スレッド） |
|---|---|---|---|
| 粒子の帯 | **535,608** | — | — |
| **色タイル** | **6,599,680（＝惑星ぜんぶ）** | **9.76 MB / 31 要求** | **1,537 ms** |

原因は出荷されているバンドルの1行だった。タイルの `dataOptions` は
`{domain, variable, bounds: h.currentBounds}` で組まれ、`h.currentBounds` は**モジュール変数で初期値が
`undefined`**。そして `getRanges(grid, undefined)` は `[{0,ny},{0,nx}]`＝**格子ぜんぶ**を返す。
これを設定する関数は **`updateCurrentBounds` ただ1つ**で、このアプリは**一度も呼んでいなかった**。

⇒ プロトコルのハンドラが毎回 `applyTileBounds(url)` で視野を渡す。実測、同じ1ステップが
**1,205,092 標本・2.82 MB・11 要求**になる。**絵は同一**（同じファイル・同じ 9 km 間隔・同じ配色・
同じタイル）で、読まなくなるのは**どのタイルも描かない部分**だけ。

⚠ **箱は「視野 ∪ いま要求されているタイル」**である。`getBounds()` は*見えている*範囲、MapLibre が
*取りに行く*のは視錐台なので、傾けた視点ではタイルが箱の外に出る——**外に出たタイルは遅い絵ではなく
欠けた絵**になる（#R299/#R307 が反対側から2ラウンド追いかけた欠陥と同じ形）。`tileBox` が
そのタイル自身の bbox を必ず含める（⚠ `tile2lon` は右端を **−180** で返す）。

⚠⚠ **視野が実質「全球」のときは箱を言わない**（`WORLD_RATIO`＝格子点の9割。⚠ **度ではなく標本数**で
数える——縮約ガウス格子では行の点数 ∝ cos φ）。起動時の視野は地球で、そこでは**粒子側の全球読みが
色タイルの状態をそのまま使っている**（`stateKey` が SDK の `fileAndVariableKey` と同一なので、帯なしの
読み込みは同じ鍵になる）。実測、起動時の視野で `snapBounds` が答える箱は **6,578,152 / 6,599,680 ＝
99.67%**——**0.33% を惜しんで同じ 6,599,680 標本を2回復号する**取引になるので、そこは言わない。

### ⚠⚠⚠ ② 色タイルは、#R310 が作ったプールの<b>外</b>に置き去りにされていた

同じ計器の同じ1ステップ:

```
tileRd.setToOmFile     9 ms → +629 ms     ← 粒子側が setIndex で既に開いたファイル
tileRd.readVariable  638 ms → +1,418 ms   ← それが終わるまで始まれない
色面が表に出る                3,073 ms
```

`ensureData` は `await A.setToOmFile(url)` から始まる。#R310 は「**ファイルごとに1つのリーダー**」の
プール（`readerFor`）を作ったが、色タイルには `pinReader` で栓をしただけで**プールには入れなかった**ので、
**同じファイルを2本目のリーダーがもう一度開いていた**——3,073 ms のステップのうち **629 ms** が、
済んでいる HEAD と末尾読みと変数ツリー走査の再実行だった。

⇒ `tileReader` が SDK インスタンスの `omFileReader` を**プールへの委譲**に差し替える。実測 **629 → 0 ms**。
⚠ **並び順の意味は SDK 自身のもの（誰でも張り替えられるシングルトン）から変えていない。** 変わるのは、
張り替えても相手のファイルの `dispose()` が起きないことだけ。⚠ `config` と `cache` は SDK 自身が
リーダー越しに読むので転送する（`getProtocolInstance` は `config.useSAB` を比べ、`clearCache` は
`cache.clear()` を呼ぶ）。⚠ `dispose` は**何もしない**——プールが寿命を持っており、粒子側の読み込みが
その同じリーダーを使っている。

### ⚠⚠⚠ ③ 12枚のタイルは、復号済みの場を12回複製していた

SDK は色付けをワーカーで行う。ただし `requestTile` は `postMessage(E)` を**転送リストなしで**呼ぶので、
`E.data` の `{values, directions}`（各 Float32Array・全格子点）が**1枚につき約 53 MB 構造化複製される**。
実測（起動時の視野・1ステップ）: **12枚の送出で 1,276 ms の単一ロングタスク**。

費用は**枚数**で決まるので、タイルを大きくする。`tile_size`（SDK・64/128/256/512/1024/2048）と
MapLibre のソースの `tileSize` を**両方 1024** にすると、MapLibre は1段低いズームのタイルを使う——

```
画素密度 = S·2^Z / (512·2^M),   Z = round(M + log2(512/S))
S=512,  Z=M    → 1
S=1024, Z=M−1  → 1
```

——**同じ密度・同じ色・同じ 9 km 間隔**で、枚数は4分の1（実測 **12 → 3〜4枚**）。
⚠ **2048 にはしない**（1枚が RGBA テクスチャなので 1024 で 4 MB・2048 で 16 MB）。
⚠ **ベクタのタイル（等圧線・矢印）には渡さない**——そちらの `tile_size` は MVT の extent であって
画素数ではない。だから `omUrl`（ベクタ）と `omRasterUrl`（ラスタ）が分かれている。
⚠ `tile_size` は SDK の `DATA_RELEVANT_PARAMS`（`['variable']` のみ）に入らないので、**キャッシュの鍵も
読み込む範囲も変わらない**。

### ⚠⚠ ④ 次の時刻の「ファイルを開く」ことは、「読む」ことではない

#R276 追記の規則——「軸を動かしていない読み手に次の時刻のバイトを払わせない」——は**そのまま**。
ただし**開く**のはバイトではない: HEAD ＋ 末尾 64 kB **1本**で、それが毎回**読み手が今頼んだ時刻の
最初の1バイトの手前**に置かれていた。⇒ `openAhead` が**進行方向の1ファイルだけ**先に開く。実測、
ステップの `setToOmFile` が **389 ms → 0 ms**。⚠ 費用は述べる: 1時刻あたり 64 kB（その1時刻自身の
8.6 MB に対して **0.7%**）で、軸を動かさない読み手はそれを1回だけ払う。

### 実測（origin/main と1プロセス内で交互・3セッション×4ステップ・#R314 の規則）

**日本上空 z6**

```
                    origin/main      R325
点灯 → 粒子           7,790 ms     3,115 ms
点灯 → 色面          13,080 ms     5,868 ms
1歩 → 粒子              634 ms       493 ms
1歩 → 色面            8,100 ms     4,461 ms
1歩の通信              8.98 MB      1.97 MB     ← 揺れない量
連打(5歩/150 ms)      4,352 ms     5,172 ms     ← 下の注記
```

**起動時の視野（世界）**

```
点灯 → 粒子           7,345 ms     6,423 ms
点灯 → 色面          10,326 ms     8,858 ms
1歩 → 粒子              814 ms       739 ms
1歩 → 色面            5,227 ms     5,773 ms
1歩の通信              9.04 MB      9.04 MB     ← 同一。世界表示では箱を言わないので当然
連打(5歩/150 ms)      7,489 ms     6,301 ms
```

⚠ **世界表示の「1歩 → 色面」は速くなっていない。** そこではバイトが1つも減らない（画面が惑星なので、
惑星を読むのが正しい）ので、残るのは開き直しの往復とタイルの複製だけで、**それは open-meteo への
往復の揺れの内側**にある——実測の散らばりは main が 3,602〜8,109 ms、R325 が 3,619〜9,667 ms。
**方向を主張できないので、しない。** 連打も同じ理由で両方向に動く（main 3,914〜5,476、R325 4,352〜6,069）。
主張できるのは**バイトと要求数と主スレッド**（下）と、**ズームした視野の全部**である。

### ⚠ 絵が同一であることは、画素で確かめた

粒子を切って（乱数のシミュレーションなので）色面だけを、**同じ視野・同じ予報時刻**で両方の木から
撮って比較した。視野は world / euro / japan / deep(z9) / **tilt(pitch 60°・bearing 30°)** /
**pan（点灯後にカメラを動かす）**の6つ。

**⑴ 地図の面のうち風の層が塗った割合**（同じ木の中で ON と OFF を比べる＝基図・パネル・時計が相殺される）:

```
             origin/main    R325
world           16.579%   16.580%
euro            36.640%   36.651%
japan           29.214%   28.790%
deep (z9)        6.693%    6.693%
tilt (60°/30°)  20.074%   20.070%
pan (点灯後に移動) 36.603%   36.603%
```

**⑵ タイルそのもの**（origin/main の z6・512 px と、R325 の z5・1024 px の**該当する 512×512**。
同じ地面・同じ画素数・拡大縮小なし）:

```
6/56/25   main 6/56/25@512   R325 5/28/12@1024   差 0%・max 0
6/55/25   main 6/55/25@512   R325 5/27/12@1024   差 0%・max 0
6/57/24   main 6/57/24@512   R325 5/28/12@1024   差 0%・max 0
6/56/24   main 6/56/24@512   R325 5/28/12@1024   差 0%・max 0
```

**1画素も違わない。** ⚠ 最初に書いた比較は**画面全体**を撮っていて、差の 9〜26% は
**サイドバー・凡例・国一覧・航空機マーカー**だった——「同じか」を訊く前に**何を撮っているか**を見ること。

### ⚠ 狭い画面でも 1024 が速い——ただし代価は測って書く

大きいタイルは狭い画面からはみ出すので、「枚数が減るぶん画素が増える」という逆向きの効果がある。
理屈で決めずに測った（390×844・z6・1ステップ）:

```
              色面が出るまで（6歩の中央値）  タイル   ラスタ化される画素
origin/main        2,944 ms                3枚      0.79 Mpx
R325               1,190 ms                2枚      2.10 Mpx
```

画面は 0.33 Mpx なので、はみ出しは 2.4倍 → **6.4倍**になる。**それでも 2.5倍速い**——
主費用が画素ではなく**枚数**の側（③の 53 MB の複製）にあることの、独立した確認でもある。
増えた画素はワーカーの仕事と GPU のテクスチャであって、主スレッドの時間ではない。
⚠ `maxTileCacheSize` は**枚数**の上限なので、保持されるバイトはタイルが大きいぶん増える。

### ⚠ 残っている（この回では直していない）

- **世界表示の色面は、惑星ぶんの復号が主スレッドで走る**（実測、`readVariable` の最中に主スレッドの
  ロングタスクが 1,200〜1,800 ms）。SDK の `WeatherMapLayerFileReader` はワーカーではなく主スレッドで
  動く。プロキシ（`tileReader`）は既に `setToOmFile` / `readVariable` を横取りしているので、
  **その先をワーカーにする**ことは構造的には可能——ただしブロックキャッシュがワーカー側へ移ると
  粒子側の読み込みとバイトを共有できなくなるので、**粒子側も一緒に移すまでは正味で損をしうる**。
  測ってから決める仕事として残す。
- **`useSAB`（SharedArrayBuffer）は使えない。** 使えれば③の構造化複製が消えるが、
  cross-origin isolation（COOP/COEP）が要り、GitHub Pages ではヘッダを付けられない。
  Service Worker で被せる手はあるが、**COEP: require-corp は IntMap が読んでいる第三者データを
  ほぼ全部塞ぐ**ので採らない。
