## R405 — **出来事は手元に証拠を持ったまま、1 文字も見せていなかった**

**依頼**（原文）: 「Event生成時に `desc: ''` と空欄を固定 / カードは地点・日時・タイトル・媒体・「記事を読む」だけ / Event詳細にも要約はなく、媒体別タイトルとメタ情報だけ。読み込み失敗ではなく、実装上、本当に要約が存在しません。現状は『ニュースを理解する機能』ではなく、地図付きニュース索引です。…ニュース機能で今最優先なのはソース追加や見た目ではなく、1つのEventをIntMap内だけで理解可能にすることです。」

### 着手前に測ったこと（本番 DB・2026-08-24）

| 測ったもの | 実測 |
|---|---|
| `news_events.summary` / `summary_evidence` / `summary_version` | **列は既に在り、全 1,176 件が `null`** — 器だけ作られ書き手が一度も実装されていない |
| active な記事 | 1,493 本。`description` を持つのは **757 本（51%）** |
| `description` が 0% の媒体 | **Reuters 246 / Bloomberg 224 / AP 164 / CNN 8**（`google_news_site` 経由。Google が `<description>` にリンク一覧を入れる） |
| Event のうち本文を 1 文字も持たないもの | **48.7%** |
| Google の `CBMi…` リダイレクトの先 | **JS の殻**。`og:description` も `description` も `articleBody` も **0 件**＝発信元へ行く道が無い |

**⇒ 43〜49% は「読み込み失敗」ではなく「上流が配っていない」。だから UI はそう書かなければならない。**

### 利用者が選んだこと

4 つ訊いて 4 つとも決めてもらった: ①要約は**ハイブリッド**（決定論の抽出が土台・複数媒体だけ LLM 統合）／②**Reuters/AP/Bloomberg の直接フィードを足す**／③**日本語翻訳は生成も表示も停止・ニュースは英語**（決定 3 の改訂）／④**「記事を読む」はカードから外して詳細へ移す**。

### 直したもの

- **`js/news-brief.js`（新）** — 出来事の中身を組み立てる**純粋モジュール**。UI と `scripts/news-events-eval.mjs --brief` が**同じ 1 本**を呼ぶ（#R386 が `differences()` を表示の層の奥に書いてブラウザの外から測れなくした形を繰り返さない）。
- **詳細**が出すもの: 何が起きたか（原文の文・1 行 1 出典）／主要な数字／最新の記事で更新された点／媒体間の一致と相違／発信元で読む（**媒体ごと**のリンク）。**カード**は要点 1 文＋出典。
- **`summarise` 段**（`news-ingest`）— **独立 2 媒体以上が本文を持つ Event だけ**を LLM が 1 つの説明にまとめ、**1 文ごとの根拠の断片が原文に実在することをサーバー側で照合**してから保存する。**1 文でも通らなければ Event 丸ごと捨てる**（部分採用しない。捨てても損は無い——ブラウザは決定論の抽出を出し続ける）。
- **`translate` 段は既定 off**（`NEWS_TRANSLATE=on` で復帰）。**実装は 1 行も消していない**——消したのは既定であって能力ではない。`news_event_i18n` の 708 行も残してある。
- **Bloomberg を直接 RSS 5 本へ**（markets/politics/technology/industries/economics・計 80 件・本文 98%・リンクは `www.bloomberg.com` で登録ドメインと完全一致）。Google 経由の行は**消さず** `enabled=false`（`news_articles.feed_id` が参照している）。
- **`parseFeed` が `content:encoded` と Atom `<content>` も読む**——リポジトリ全体で一度も解析していなかった。⚠ 正直に言うと**今日の効果はほぼゼロ**（38 本中それを出しているのは NPR の 2 本だけ）。効くのは 1000→1200 の上限のほうで、Guardian の 9 本が文の途中で切れていた。

### 踏んだ罠

⚠⚠⚠ **ソースの形の門が全部緑のまま、News が丸ごと壊れていた。** `decorate()` はカードの配線より**前**に走るので、そこで外した `.btn-read` を `js/news-ui.js` が無防備に `.onclick` で触り、**null に代入して TypeError**。`appendNewsBatch` の forEach ごと落ちて **Event モードが記事フィードへフォールバック**した。画面には記事が 30 件並び、コンソールに «event mode unavailable … Cannot set properties of null» が 1 行出るだけ。**私が書いた検査⑮は「外す行が在る」を確認して緑だった。** ⇒ 「外す行が在る」は「外したあとも動く」ではない。ブラウザにしか訊けない（#R402 が同じ位置で言っていること）。

⚠⚠⚠ **語の重なりは「同じ配信原稿」を見分けられない。** 別系列どうしの文 **526 組**の分布を測ると、c≥0.9 は **1 組**（本物の重複）で、0.8 帯の 3 組は**全部「短い文 ⊂ 長い文」**——NPR「米が 50% の関税」と France 24「カナダが報復関税」は**別の事実**である。閾値を下げると価値のある独立報道が消える。⇒ **c≥0.9 かつ長さの比≥0.6** の狭い規則にした。⚠ 母数は薄い（526 組中 1 組が発火）。それでも置くのは、外したときの被害が**独立した裏付けの捏造**＝この機能が犯しうる最も重い誤りだから。

⚠⚠⚠ **`status=none` と言った下に数字が並ぶ不整合。** «Vietnam approves additional $3 billion spending for China rail link» は Reuters と Bloomberg の 2 本で構成され、どちらも本文 0 文字。しかし **`$3 billion` は見出しにあり、2 系列が同じ値を言っている**。一律 `none` にすると UI が自分の言ったことと食い違う ⇒ 文の有無と読めるものの有無を分ける `facts` を作った。

⚠⚠ **カードの出典が 2 行クランプで消えていた。** 末尾に `— 媒体名` を置いたので、実データではほぼ必ず切り落とされていた。**スクリーンショットを撮って初めて分かった**（`textContent` を読むだけの検査では出ていた）。⇒ 出典は文の**前**へ。

⚠⚠ **自分で「理由のない緑」を作った。** rebase の解決で `assert.match(fn, /\\["fetch", …\\]/)` と書いてしまい、これは `\`（バックスラッシュ）＋**文字クラス**になるので `fn` にいくらでもある `\s` に当たって**順序が何であっても通る**。変異試験（順序を 1 つ入れ替える）が捕まえた。

⚠⚠⚠ **push 直前の rebase で #R404 が同じ問題を先に解いていた。** 段ごとの kill-switch を、あちらは `providerConfig(offEnv, modelEnv)` として、私は `aiConfig({envKey, defaultOn})` として書いていた。**同じ結論への別の道**なので #R402 の規則どおり**後から入るほうが引き**、私の関数は捨てて #R404 の形に `defaultOn` を足した。

⚠ **Reuters と AP には直接フィードが存在しない。** 11 URL を実測して全部 401/404/DNS 失敗。Google のリダイレクトを解く道も無い（JS の殻）。**この 2 社の Event は見出しだけのままで、UI はそう書く。**

⚠ **登録済みの CNN フィード（`rss.cnn.com/rss/edition_world.rss`）は最新記事が 1,071 日前。** 200 と 29 items を返すので、どの計器も赤くならない（#R388 が overpass で踏んだ形の一般形）。無効化は範囲外なので `news_source_feeds.last_error` に事実を書いた。⚠ 取得成功時に `last_error: null` が書き戻されるので**次の ingest で消える**——恒久的な記録は migration のコメント側にある。

⚠ **このマシンでは `npm run build` が動かない。** `node_modules/.bin/vite.cmd` が `@deno run -A npm:vite` という **Deno 生成のシム**で、Deno は入っていない。原本でも同じなので既存の環境要因。`node node_modules/vite/bin/vite.js build` で迂回した。

### 試験時間の予算

⚠ **全体の上限を実測ぶん 7 秒だけ動かした**（4,529 → 4,536 s）。**core の上限は動かしていない**
——常設 5 本が 33 s の記録に対し `tests/r405.spec.js` はこのマシンで 6.4 / 6.6 s なので、
上限側の 7 を入れて 33＋7＝40＝`BUDGET_S` ちょうど。#R388 が同じことを同じ理由で記録している。

⚠ **stale-high から払えなかった理由も実測である。** #R337 が「まだ stale-high」と名指した
`tests/r184-routing.spec.js`（記録 30 s）を測ったら **4.4 分＝264 s** で、**8 倍の stale-low** だった
（同じ run で `tests/r157.spec.js` は記録 1 s に対し 8.3 s）。30 と言っている表から節約を
取り出してはならない（#R322 の規則）。⚠ 訂正は corpus をきちんと測り直せるラウンドの仕事であって、
2 本を偶然測っただけのこのラウンドの仕事ではない。

⚠ **spec から払うこともしなかった。** 先に払ったものはある——**固定の 4 秒待ち 4 か所を条件待ちに**
（23.8 → 9.1 s）、**4 テストを 1 本に**してワーカー共有の起動を分け合う（9.1 → 6.4 s）。
`loadEvents` 自体は **450 ms** で、残りは app fixture を使う spec が誰でも払う起動である。
これ以上は検査そのものを削ることになり、**このラウンドで本番級の欠陥を捕まえたのはこの spec だけ**
——ソースの形の門は全部緑だった。
