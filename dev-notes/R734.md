## R734 — 「遅延で読む」と書いたものが、起動時に届いていた

〈#R732 の production verification。②③④⑤⑥ は本番で全項目一致し、①だけが合わなかった〉

### 1. ⚠⚠⚠ 動的 import は「いつ取りに行くか」を決めない。チャンクの同居者が決める

#R732 は `js/gis-geometry.js` のヘッダにこう書いた——「**a reader who never runs an overlay never
downloads a sweep-line**」。`import('polygon-clipping')` は確かに動的で、書いたコードは正しい。

**本番のバイトを測ったら偽だった。**

| 測ったもの | 実測 |
|---|---|
| `geo-<hash>.js` が `SweepEvent` を含むか | **含む**（52,137 B） |
| `main-<hash>.js` がそれを静的 import しているか | **している**（`from"./geo-<hash>.js"` 1 件。動的 1 件と**同居**） |
| いつ取得されるか | **t ≈ 16 ms**、最初の 7 リクエストの 1 本 |

⚠ **静的 import が 1 つでも同じチャンクを指していれば、動的 import は無効になる。** モジュール側で
どう書くかは、そのモジュールが**どのチャンクに置かれたか**を変えない。

### 2. ⚠⚠ #R732 は事実を作っていない。事実の反対を書いただけである

R731 のビルドを作り直して測ったら、**同じ `geo-hIIBheTV.js` が同じく `SweepEvent` を持ち、同じく
main から静的に import されていた**。⇒ 退行ではない。⇒ **直すべきは挙動ではなく、主張のほう**だった。

⚠ これを見つけたのは検査ではなく**本番検証の 1 項目**である。ローカルの `check:perf` は
requests 6・module 298・eager raw +3.4 kB を正しく報告していて、**どれも「クリッパが eager か」を
訊いていない**。数は全部合っていて、主張だけが間違っていた。

### 3. ⚠⚠⚠ そして `vite.config.js` 自身も、同じことを違う言い方で間違えていた

`manualChunks` は polygon-clipping に対して `return;`（undefined）していて、#R209 のコメントが
その理由をこう書いている——「turf-jsts と polygon-clipping は **eager な geo チャンクに入らない**。
名前を付けると turf ごと引き戻して split を台無しにするので、undefined にして Rollup が
`import()` の作る動的チャンクへ置くのに任せる」。

**turf-jsts については今も正しい。polygon-clipping については正しくない**——Rollup は
eager な geo チャンクへ置いた。**設定は意図を述べていて、その意図を測るものが無い。**

⇒ この回がしたのは**両方の文を実測に合わせること**だけで、チャンク分割自体は変えていない
（起動から 52 kB を外すのは本当の改善だが、`manualChunks` は全チャンクに効くので、
依頼された範囲の外として**提案に回した**）。

### 4. 残っていること

- **polygon-clipping を起動経路から外す**（`manualChunks` で自分のチャンクに名付ける）。
  実測で 52,137 B raw / 17,082 B 転送ぶんの起動費用。
- **どのチャンクが何を持っているかを測る門**。今は `check:perf` がチャンクの**大きさ**だけを見て
  いて**中身**を見ていないので、この種の主張は 1 つも検査されていない。
  ⚠ 門が無いまま直すと、次に同じことが起きても同じように気づかれない。
