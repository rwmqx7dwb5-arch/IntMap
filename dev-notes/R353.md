## R353 — **3色は「深さについての設計判断」ではなく、そのファイルが知っていることのすべてだった**

### 追記（本番検証） — **本番のコンソールが、ローカルの検査が全部緑のまま消えていたレイヤーを見せた**

本番検証（merge 後）でコンソールにこれが出ていた:

```
layers.volc2-halo.paint.circle-radius: "zoom" expression may only be used as input to
a top-level "step" or "interpolate" expression.
```

**`volc2-halo`（今日どこかの観測機関が話題にしている火山に付く輪）の半径を
`['*', 2.6, volcRadius]` と書いていた。** MapLibre は `zoom` 式が paint プロパティの
**最も外側**であることを要求する——そして**満たされていないときに throw しない**。
`addLayer` は検証し、`ErrorEvent` を上げ、**そのレイヤーを飛ばす**。

だから：レイヤーのファイルは読み込まれ、点は描かれ、4つの色モードは全部動き、
**ローカルの検査はひとつ残らず緑で**、そして**輪だけが地図に無かった**。
症状は「誰もそのレイヤーをONにしていない」ときと完全に同じ形をしている。

⇒ **`volcHaloRadius` を自分の top-level `interpolate` にする**（係数を各停止点に畳み込む）。

⚠⚠⚠ **これを捕まえる問いは「レンダラは何を持っているか」であって「ソースは何を意図したか」ではない。**
`tests/r353.spec.js ②` が3つの描画（`volc2-halo` / `volc2-pt` / `volc2-lbl`）**すべてが
レンダラに在ること**を訊く。⚠ **壊して赤を見た**——バグを戻すと ② が
`volc2-halo was rejected by the renderer` で落ち、戻すと通る。
`tests/r353-checks ⑬` はその安いほうの半分（ソース上、`['zoom']` が他の式の中に入っていないこと）。

⚠ **本番検証をしていなければ気づかなかった。** ローカルの門もブラウザ検査も、
「レイヤーが在るか」を訊いていなかったからである。

> 「火山 → Volcano Intelligence
>  現在はGVPの完新世火山1,215座を全部入れてありますが、視覚上の主要分類は「1950年以降」「1500年以降」
>  「古い／不明」です。ここは恐ろしく深くできます。
>  各火山の全噴火履歴 / VEI / 噴火様式 / 火山タイプ・マグマ組成 / 現在の警戒レベル / VONA /
>  VAAC火山灰域＋高度 / SO₂観測 / 衛星熱異常 / 地震活動 / 火砕流・降灰・ラハール等の既知ハザード域 /
>  周辺人口・空港・航空路への影響」

**正本は [`docs/VOLCANO-INTELLIGENCE.md`](docs/VOLCANO-INTELLIGENCE.md)**（データ源・結合鍵・段・
描くもの／描かないもの）。ここには**なぜそうしたか**だけを書く。

### ① 結合鍵が無い、ということの意味

3色は深さについての設計判断ではなかった。`data/volcanoes_gvp.json` は火山1件につき
**6項目（名前・国・型・標高・最終噴火年・地域）しか持たず、GVP 火山番号が入っていなかった**。
番号が無いということは**結合鍵が無い**ということで、依頼の12項目は**1つ残らず**、上にどんな UI を
載せても到達できない。3色は、そのファイルが知っていることのすべてだった。

`scripts/build-volcanoes.mjs` が GVP の WFS から作り直す:

- `data/volcanoes_gvp.json`（296→303 kB・**レイヤーを ON にしたとき**）——地図が描く／絞り込むものだけ。
  **`v`（結合鍵）**・`x` 記録上の最大 VEI・`q` 確認噴火回数・`p` 半径30 km人口・`k`/`s` 岩石と構造区分の索引。
- `data/volcano-detail.json.gz`（538 kB・**最初にカードを開いたとき**）——**11,089件の噴火履歴**
  （VEI・開始／終了日・証拠方法・確認／不確実）・地質の概要・写真・**半径 5/10/30/100 km の人口**。
  **火山を1つも開かない読者は1バイトも払わず、1つ開いた読者は全部ぶんを1回だけ払う。**

⚠ **1,215 → 1,214。** 同梱ファイルは 1,215 件を持っていたが、上流のカタログは 1,214 件だった。
その「1,215」は**5言語のレイヤー行に書いてあった**。件数はどこにもハードコードしない——
凡例はファイルから読み、`tests/r353-checks ⑧` が code から数字リテラルを禁じる。

### ② 上流が「宣言しているのに壊れている」

GVP の WFS は 6 つの feature type を宣言する。**`E3WebApp_Emissions`（GVP 自身の SO₂ 放出量）は
`DescribeFeatureType` に今も載っているのに、実際に呼ぶと毎回 `Invalid object name 'vrf.Emission'` を
返す**（WFS 1.0.0 でも 2.0.0 でも）。SO₂ の出典に**見えた**まま採用していたら、ビルドが黙って
空の配列を書いていた。

⚠ **GeoServer は失敗したクエリに 200 と XML を返す。** だから
**「JSON としてパースできたか」だけが、生きた feature type と広告されているだけのそれを分ける。**
ビルドがその判定を持つ。SO₂ は実在する観測——NASA GIBS の
`OMPS_SO2_Upper_Troposphere_and_Stratosphere`、**噴煙が現れる高度帯**（境界層の工業由来のもやではない）
——から採る。

### ③ 現在の警戒レベルには「全世界のフィード」が存在しない

**在るふりをすると、「地図が読める形で公表している機関が無い」が 1,150 座の静かな火山に化ける。**
気象警報レイヤーの灰色斜線（`docs/MAP-LAYERS.md` §7.1）が防いでいるのと同じ失敗である。
だから同じ三状態の作法を、**段に名前を付けて**適用した:

| 段 | 範囲 | 何を述べるか | 経路 |
|---|---|---|---|
| ① | 米国 | 航空カラーコードと警戒レベル、直近1年の **VONA**（実測 94件） | USGS HANS・**直接** |
| ② | 日本 | **噴火警戒レベル 1–5**／レベル運用の無い火山は**文言そのもの** | 気象庁・**直接** |
| ③ | 全世界 | 今週報告された火山の活動状況（実測 21件） | 週間報告・**中継** |
| ⓪ | 全世界 | **何も公表されていない**——言葉で述べる | — |

⚠⚠⚠ **①②③ は別の機関の別の計器なので、1つの数に混ぜない。** 気象庁のレベル2と USGS の
YELLOW/ADVISORY は同じ量ではない。カードは**機関自身の語彙**で**機関名を付けて**印字する。
`rank` は**地図が色を並べるための順序としてしか存在せず**、画面に数として出ない。

⚠⚠ **気象庁の発表単位は GVP の火山と一致しない。** 気象庁は「桜島」に警報を出す——それを含む
カルデラ「姶良」ではない。「樽前山」と「恵庭岳」は別々に発表されるが GVP の項目は `Shikotsu` 1つ。
だから結合表は**多対一を意図して持ち**、カードは**気象庁の単位名**を示し、地図は**それを含む GVP の点**を
着色する。85行すべてを「国が Japan の 105 件」と突き合わせてあり、`tests/r353-checks ④` が毎コミット
再確認する——**カタログ改訂で番号が消えたら、日本の警戒レベルが黙って地図から落ちるのではなく、
ビルドが落ちる。**

### ④ 火山灰域は VAAC の advisory ではなく **SIGMET** から採る

VAAC が出すのは整形テキストと画像である。**高度帯を持つポリゴンとしての灰の雲**は、その advisory を
受けて FIR が出す **SIGMET** に存在し、`aviationweather.gov` が実座標の JSON で公表している。
実測（このラウンド）: 国際 SIGMET **127 本中 8 本が火山灰** ——Krakatau `SFC/FL090` 南西へ 5 kt
`INTSF`、Ibu `SFC/FL070` 北東へ 10 kt。**航空当局が実際に発効させた区域を、発効させられたときの
高度帯で**描く（火山のまわりの円ではない）。

⚠ **有効期限は時計が落とす**（取得の失敗ではなく）。期限切れを地図に残すのは、灰がもう無い場所に
あると主張することである。
⚠ **0 件は正常な答えであって失敗ではない。** 応答の `read`（読んだ SIGMET の総数）が
「世界のどこにも出ていない」と「フィードが答えなかった」を分ける。

### ⑤ ハザード域は「データとして存在するものだけ」

火砕流・降灰・ラハールの想定区域は、**多くの火山で紙のハザードマップとしては存在し、機械可読な
GIS としてはごく僅かしか存在しない**。探索の結果、権威があり・鍵が要らず・CORS を返す唯一の公的
サービスは USGS 所有の `Volcano_Hazard_Zones` で、**カリフォルニアの7火山地域・26 ポリゴン**だった。

**その7つは描き、残り 1,207 座については火山ごとに「公表されていない」とカードが述べる。
推定の到達円は1つも描かない。**
「1,200座にハザード域が描かれていない」が「1,200座にハザードが無い」と読まれてはならない。

⚠ USGS の区域名は**そのまま**示す。`Long Valley Volcanic Region` は USGS の作図単位で、
その完新世項目は GVP では `Mono-Inyo Craters` である。画面上で書き換えると、
**USGS が使っていない名前で USGS の地図を提示することになる。**

### ⑥ 「噴火様式」——無い項目は無いと言う

**GVP のデータベースに「噴火様式」という項目は存在しない**（Bulletin の本文中にしかない）。
だから出典を示せない様式ラベルを印字しない。代わりに、記録が実際に持っているものから性格を組み立て、
**画面上でその旨を述べる**：その火山**自身の** VEI 分布（棒グラフ・件数はその火山のもの）、最大 VEI と
その年、VEI 4 以上の回数、**1500 年以降の噴火間隔の中央値**、主要岩石・火山型・地形区分。

⚠ **間隔は観測時代だけから採る。** 先史時代の年代は放射性炭素とテフラ年代学で、分解能は世紀単位。
混ぜた平均は**火山ではなく年代測定法についての数**になる。

### ⑦ 色は4つの問い、大きさは常に「記録上の最大 VEI」

色（最終噴火／爆発規模／現在／周辺人口）と大きさは**独立した2チャンネル**であって1つではない。

⚠⚠ **status モードの灰色は「平常」と別の色でなければならない。** `st` は誰も述べていない火山では
**不在**なので、`step` 式の**基底**が「公表なし」を受け取り、rank 0（機関が平常と述べた）は最初の
停止点になる。同じ色にした瞬間、1,150 座が「確認して静穏」に化ける。
`tests/r353 ②` は paint 式を読み出して**基底と最初の停止点が別の色であること**を主張する。

### ⑧ 掃引器に見えないエイリアスは、4言語で黙って英語のまま出荷される

`js/volcano-intel.js` と `js/volcano-layers.js` に
`const T=(...a)=>window.IntMapLang.t(HOST.lang,...a)` を書いていた。`scripts/i18n-helpers.mjs` の
strict 側（`provenNames`）は **`IntMapLang.pick()` に束縛された名前しか証明しない**ので、
arrow function のエイリアスは**掃引器から不可視**である。

**欠落は 85 件と報告されていた。エイリアスを全部 `L(...)` に戻したら 125 件になった**——
差の 40 件は、**測っていなかったから存在しないことになっていた** 40 件である。
これが `check:i18n` が緑のまま fr/ko/zh/zh-Hans が英語で出荷される経路であり、
このラウンドで新しく作りかけた。

### ⑨ 並行セッションと、番号の取り直し

作業中に `origin/main` が **7 ラウンド**進み、**R346 は他所のラウンドに取られていた**（R346→**R353**）。
rebase で 13 ファイルが衝突。解決の規則は決まっている——
**locale・`durations.json`・`perf-baseline.json`・`test-budget.mjs` は `origin/main` を真として取り直し、
自分の分を再適用する**。i18n は `scripts/i18n/r353-a.json` から `i18n-apply-inline` を再実行するだけで

⚠ **`supabase functions deploy` は Docker を待って無言で固まる**——13 分間・出力ゼロ・エラーも無し。
`--use-api`（サーバー側でバンドル）で 30 秒。
