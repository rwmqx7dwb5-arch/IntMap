夜間 CI で `r410-late:78`・`r424:130`・`r410:141` が 1916 年への移動で 60 秒枠を超えて落ちていた。
前任の計測（2026-09-26）で、その移動でメインスレッドを 1 回で最も長く止めていたのは
`setLayoutProperty('ofm-city','text-field', …)`（1,207,908 バイト・`distance` 条件 7,954 個）で、
1 倍で 557〜607 ms、CPU 4 倍絞りで 2.4〜2.8 s。

## 否定された見立て

- **「`js/hist-eras.js` の評価が原因」**——1916 年は CShapes の帯なので hist-eras は読まれない。
  紀元前 200 年（hist-eras が読まれる年）でも 110 ms・全体の 0.9% だった（前任の実測）。

## 実際の構造（3 つ）

1. **作り直しの条件が日付だった。** `js/hist-cities.js` の `textField` のキャッシュ鍵が日付を含み、時計の購読者が
   毎回キャッシュを空にしていた。時計が動くたびに JS で式を組み直し（6〜14 ms・node で実測）、`applyLabelLang` が
   呼ばれるたびに（1 回の移動で 1〜6 回）MapLibre へ渡していた。MapLibre 5.24 の `Style#setLayoutProperty` は
   同値なら何もしないが、比較の前に保持値を `clone` する（`getLayoutProperty`）ので、同値の書き込みでも
   1 倍で 4〜44 ms、4 倍で 12〜95 ms かかっていた。
2. **同じ距離判定を 2 回書いていた。** `name:en` の `match` と `name` の `match` が、候補群ごとの `case`
   （距離のガード）をそれぞれ自分の写しとして持っていた——3,977 候補 × 2 = 7,954 個の `distance`。
3. **生成した式を毎回検証していた。** 検証（`validateLayoutProperty`）はもう 1 回の完全な解析で、
   実測で 1 回の変更の費用の約半分。

## 直したこと

- **エポック**：式は「その瞬間を含む span の集合」だけの関数で、各 span への問いは `d >= f` と `d <= t` だけ。
  答えが変わりうるのは `f` と `t + 1` だけなので、その境目を `data/hist-cities.json` から導き（3,802 個・
  手で年を並べない）、キャッシュの鍵を「境目をいくつ越えたか」＋言語＋基底式にした。購読者はキャッシュを空にしない。
  `js/place-labels.js` はスタイル層ごとに最後に書いた配列を `WeakMap` で覚え、**同じ配列なら書かない**。
- **距離判定を 1 回だけ書く**：候補群ごとの `case` を `let` の束縛にし、両方の `match` は `['var', …]` で指す。
  MapLibre の `var` は使われた場所で評価される（`Let`/`Var` の `evaluate` を確かめた）ので、地物が訊くのは
  自分の綴りが選んだ群のガードだけで、実行時の費用は増えない。群に当たらなければ `''`、
  `name:en` の答え → `name` の答え → 通常のラベルの順。1916-07-01 で 1,207,908 → 874,655 バイト、
  `distance` 7,954 → 3,977。
- **`{validate:false}`**：`GE().layers.setLayout` とアダプタ（`js/geo-engine.js`）が第 4 引数
  （MapLibre の `StyleSetterOptions`）を落としていたので素通しにした。契約 `types/geo-engine.d.ts` の 2 か所に
  `o?` を足し、Cesium アダプタは受けて無視する。渡すのは `js/hist-cities.js` の `built(expr)` が「自分が作った
  式」と答えたときだけ。MapLibre の API は検証の省略を「先に検証済みの値」に限っているので、その検証を検査に
  置いた（`validateStyleMin` を、記録から選んだ日付 × en/jp で通す）。
- `tests/r427-checks.test.mjs` ④ は式の形を歩く検査なので新しい形に合わせた（主張は同じ: どの分岐も位置で問い、
  落ちる先は通常のラベル。加えて「分岐は群の束縛を指す」「束縛された群はどれもどこかの綴りから届く」）。
  ⑤ の正規表現は第 4 引数を許すようにした。

## 表示される名前は変わっていない

- **`origin/main` の実装と新しい実装を、MapLibre 自身の `createExpression` で解析して同じ地物に評価した。**
  Date で表せる境目 **3,750 個すべての両側 × en/jp = 15,000 組**、地物 42,778 個（全 6,474 都市の座標で
  `name:en` だけ・`name` だけ・両方・他の綴り＋自分の名前・ガードの外、さらに**最寄りの別都市の綴りを
  `name:en` に置いた地物**——両方の欄が別々の歴史名を見つけ、`name:en` が勝たねばならない地物が
  1916-07-01 だけで 2,171 個）＝ **6 億 4,167 万回の評価で差 0**（うち 2 億 3,859 万回が歴史名を返した）。
  記録には Pleiades 由来で約 260 万年前に始まる span があり、そこは Date の範囲外で時計が立てない。
- 恒久の検査 `tests/hist-city-label-epoch-checks.test.mjs`：
  ① 記録から選んだ境目（1916・1939 の近傍と全体の散布、紀元前を含む）の両側で、移動してきたモジュールの式が
  新規の式とバイト同一 ② 同じエポックでは同一の配列（購読者が発火しても） ③ 1916-07-01 以後で最初に改名が
  起きる境目の両側で全都市を MapLibre の評価器で評価し、記録の規則どおり ④ `validateStyleMin` を通り、
  `built` はその式だけを指す。変異で確かめた：鍵からエポックを外す→①②③赤、日付鍵→②赤、`t + 1` を `t`→①②③赤。
- `tests/hist-city-label-epoch.spec.js`：実アプリで、同じエポックの中の移動は書き込み 0 回、境目を跨ぐと
  `{validate:false}` で 1 回書かれ、記録の新しい名前になる。`origin/main` のビルドでは 2 回書かれて赤。
  実測 7.6 / 7.7 / 8.2 s（`tests/durations.json` に 9。同じ条件で r410 は記録 12 に対し 12.3 s）。

## 計測（同じマシンで他セッションが走っており揺れる。`origin/main` のビルドと新しいビルドを交互に走らせた）

**1916-07-01 の式への 1 回の変更だけ**（同じページで保持値の 1 か所を変えて `setLayoutProperty`、各 3 回 × 2 ページ）:

| | 1 倍 | 4 倍 |
|---|---|---|
| 前: 1,207,908 B・`distance` 7,954・検証あり（`origin/main`） | 266–461 ms | 1,188–1,570 ms |
| 前の式で検証だけ外した場合 | 130–153 ms | 593–786 ms |
| 後の式（874,655 B・3,977）で検証あり | 65–96 ms | 295–433 ms |
| **後: 後の式・`{validate:false}`** | **30–57 ms** | **154–228 ms** |

⇒ 1 回の変更は約 7〜8 分の 1。式の統合だけで約 4 分の 1、検証の省略でさらに約半分。

**実アプリの経路**（`現在 → 1916-07-01 → 1939-07-01 → 1916-07-01 → 1916-08-15 → 1916-09-20 → 1917-03-01`、
各 3 回ずつ交互。`ofm-city` の `text-field` の書き込み）:

| | 前（`origin/main`） | 後 |
|---|---|---|
| 境目を跨ぐ書き込み（1 倍） | 153–333 ms | 28–61 ms |
| 境目を跨ぐ書き込み（4 倍） | 642–1,373 ms | 116–400 ms |
| 1 回の移動あたりの書き込み | 1〜6 回（2 回目以降は同値で 1 倍 4–10 ms・4 倍 12–32 ms） | 跨ぐとき 1 回・同じエポック 0 回 |

⚠ 移動の後の最長 long task は前後で変わらない（1 倍でおよそ 200 ms、4 倍で 0.8〜1.4 s）——**この書き込みは
もう最長の仕事ではない**。夜間の 3 本の経路に残る費用は別のところにある（下）。3 本はローカルで緑
（r410 12.3 s・r424 13.3 s・r410-late 41.9 s。いずれも絞りなし）。

## 残したこと（今回の範囲外）

- 移動後の最長 long task の中身は今回測っていない（前任のトレースでは 1916 年への移動に複数の 100 ms 超の
  仕事があった）。
- 観測だけ：1916 年への移動で `imtb-src`・`imtb-ln-src`・`imtb-lbl-src` の `setData` がそれぞれ **3 回**、
  同じ地物数（151・126・153）で呼ばれる（メインスレッド側の呼び出しは 1 ms 未満、ワーカーの作業は
  3 回ぶん）。同じエポックの中の移動（1916-09-20）では 0 回。
- `global-state`（MapLibre 5.24）で式を時刻に依存しない 1 本にする案は試していない。状態を変えると `ofm`
  ソース全体が再読込される（`Style#_applyGlobalStateChanges`）。
