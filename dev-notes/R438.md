## R438 — **オブジェクトの数がベースラインを離れて浮いていた——原因は数字ではなく、ボタンの整形文脈**

報告は 1 枚のスクリーンショットと 1 行だった。「オブジェクトの数がこんな感じで位置がおかしい。」
右上のツールバーの「🗂 オブジェクト」のピルの中で、件数の「1」が上付き文字のように上端寄りへ浮いている。

### 原因

数字のスタイルには何の問題もなかった。`index.html:436` はこう書かれている。

```html
<button class="view-btn" id="btn-tool-objects" …><span data-i18n="objectsBtn">🗂 Objects</span><span id="tool-objects-n" style="margin-left:5px;font-weight:700;opacity:0.85;"></span></button>
```

壊していたのは `js/map-tools.js` の `tickFab` の 1 語で、それは **整形文脈（formatting context）** を変える。

```js
tb.style.display=(n>0)?'inline-flex':'none';   // #R130
```

`inline-flex` にした瞬間、このボタンは **flex コンテナ**になる。中の 2 つの span は
「1 行の文字列」ではなく **flex item** になり、それぞれ**自分の行ボックス**を持つ。
`align-items` は一度も書かれていなかったので初期値 `normal`（＝stretch）で、
**2 つの行ボックスは上端で揃う**。ラベル側の行ボックスのほうが高ければ、
数字はその差の分だけ**ラベルのベースラインより上**に描かれる。

### ⚠⚠⚠ だからこの欠陥は、見る機械によって強さが違う

ずれ幅を決めているのはコードではなく、**その機械でラベルを実際に描いているフォント**である。
12px・「🗂 オブジェクト」対「1」で実測した行ボックスの高さ:

| ラベルを描くフォント | ラベル | 数字 | 数字が上に浮く量 |
|---|---|---|---|
| Noto Sans JP（本来の面） | 16px | 15px | 約 1px |
| Meiryo | 18px | 15px | 約 2〜3px |
| MS PGothic | 19px | 15px | 約 3〜4px |

しかも Noto Sans JP は Google Fonts から `font-display:swap` で届く（`css/fonts.css`）。
**届くまでは Windows のフォールバックが描き、届かなければずっとフォールバックが描く。**
つまり同じビルドが、ある機械ではほぼ正しく見え、別の機械でははっきり上付きに見える。
英語 UI で再現しようとすると何も起きない——Latin のラベルと数字は同じ面で同じ高さだからである。

### 直し方——**揃え方を足すのではなく、flex をやめる**

`align-items:baseline` を足す道もあるが、それは**このボタンだけが flex である理由**を残す。
他の `.view-btn` は全部 inline-block で、とりわけ `#btn-measure-menu` は
「📐 + `<span>` + `<span>`」という**まったく同じ形**を持ちながら、この欠陥を一度も出していない。
インライン整形では 2 つの span が 1 本のベースラインを共有するのが**定義**だからである。

```js
tb.style.display=(n>0)?'':'none';
```

`display` の上書きをやめるだけで、このボタンは隣のボタンと同じ整形に戻る。
外側の `.map-view-group` は `display:flex; align-items:center` なので、
**ボタン自身の箱も、行の中の位置も、「オブジェクトが 1 件以上あるときだけ出る」という表示条件も変わらない。**

### 検査——フォントに依存させない

この欠陥を CI で捕まえるには問題がある。**フォントの揃っていない機械でしか再現しない**ので、
実測値をそのまま書いた検査は Linux の CI で緑になるだけである。
そこで検査は**ラベル側に明示的に高い `line-height` を与えてから**測る。
インライン整形なら 2 つのベースラインは**どのフォントでも一致**し、
flex なら**どのフォントでも 8px 前後ずれる**——両者は完全に分離する。

ベースライン自体はスクリプトから直接は読めないので、**空の inline-block を探針にする**。
空の inline-block のベースラインはその**下マージン端**であると CSS が定めているので、
`getBoundingClientRect().bottom` がその行のベースラインそのものになる。

⚠ **新しい spec ファイルは足さなかった。** `npm run check:testbudget` は core 0.5 分・全体 76.6 分の
**天井ちょうど**で回っており、新しい spec ファイルは worker の起動費を 1 つ買う。
`tests/smoke.spec.js`（core tier・既にアプリを 1 回起動している）に相乗りさせた。
オブジェクトは `window.IntMapAnnotations.add()`＝**公開 API で本物を 1 件作って** 作る（測定後に消す）。
⚠ 両方のベースラインが 0 になる＝ボタンが非表示だと検査は**盲目のまま緑**になるので、
「ボタンが見えている」と「件数が描かれている（`'1'`）」を先に主張させている。

**実測: 旧実装（`inline-flex`）で赤、新実装で緑。**
