## R620 — **「同じ表が2回出る」は二重描画ではなかった——`show` を identity に混ぜていた**

> 利用者の監査指示書:「現在の複合クエリエンジンそのものはかなり良い。…したがって、この機能を
> 作り直してはいけない。」——そのうえで 8 つの欠陥と「二重実行と決め打ちせず必ず trace すること」。

### 1. 二重の表——どこにも二重描画は無かった

**リポジトリ全体で `<table>` を出すコードは 2 か所しかない**（実測）: `js/atlas-query.js` の
`tableHtml()` と、`js/atlas-reply.js` の `_atlBuildTable()`（GFM のパイプ表の字面だけを見る）。
capability の `rows` / `columns` から汎用に表を組む経路は**存在しない**——`js/atlas-toolsurface.js`
の `mechanical()` はモデルに行データを渡さないので、モデルが緯度経度を書くことも原理的にできない。

つまり「1 つ目に緯度経度があり 2 つ目に無い」は、**`show` の違う `data.query` が 2 回実行された**
としか説明が付かない。そして `js/atlas-turn-results.js` は「1 操作 1 ブロック」を守る番人であり、
その `keep()` は `opKey()` で畳む——そこにこう書いてある:

> the identity of an OPERATION: **what it did, not how it rendered**

⚠⚠⚠ **その正しい規則が効いていなかったのは、`data.query` が `meta.resultKey` を名乗っていな
かったから。** 名乗らなければ `opKey` は**引数**に落ちる。`show` は引数である。だから
「同じ 34 件・列づけだけ違う 2 本」は**別の操作**として両方残り、`js/atlas-console.js:4499` の
「完全一致の html を落とす」番人も（html が実際に違うので）素通りした。

⚠ **#R551 が `resultKey` を作ったのは、まさにこの形の失敗のため**だった。仕組みは 2 ラウンド前から
あって、この case だけが使っていなかった。⇒ エンジンが**何を解決したか**（表・条件を正規化した
もの・国スコープ・結合・並び・上限）を名乗る。`show` と `columns` は**入れない**。

⚠ `if (capabilityId === 'data.query') return;` のような特例は書いていない（指示書 §21 の禁止事項）。
足したのは**既にある契約を 1 つの case が守るようにしただけ**である。

### 2. `cities` は都市の表ではなかった

GeoNames cities1000 を `c[6] !== 'P'` だけで採っていたので、feature **code** が失われていた。
公開されている cities1000 に対する実測:

| | 人口100万人以上 |
|---|---|
| `PPLX`（section of populated place） | **14 件** |
| うち報告された 1 件 | `Al Mawşil al Jadīdah` gid 99071 / 2,065,597 |
| **同じファイルにある本物** | `Mosul` gid 99072 / **PPLA** / 1,683,000 |

ほかに Kowloon・New Territories・Hong Kong Island・Puxi・Navi Mumbai・Pest など。
**都市の一区画は都市ではない。**

⚠⚠⚠ **一覧を書かずに直した。** `scripts/build-gazetteer.mjs` が GeoNames の
`featureCodes_en.txt` を取り、`P.*` の**公開された説明文**を 3 つの述語で読む。
「section of …」で始まるものは `part`、historical / abandoned / destroyed / former を含むものは
`defunct`、それ以外は `settlement`。結果を `placeKinds` として同梱する（ブラウザは上流を引けない）。
実測 18 コード: part 8,173 行 / defunct 61 行 / settlement 140,396 行。
**cities1000 に現れた `P.*` が `featureCodes_en.txt` に無ければビルドが落ちる**——既定値に落として
黙らせない。⚠ 逆に**分類の無いコードは採用する**:「まだ分類されていない」は欠陥の証拠ではなく、
黙って落とせば GeoNames がコードを足した日に本物の都市が消える。

⚠ 行は 1 つも捨てていない。`PPLX` はニュースでは実在の地名なので gazetteer には残り、
**都市かどうかを訊く側**が拒む。

### 3. ⚠⚠⚠ 指示書に無かった、いちばん重い欠陥——正解のほうが入っていなかった

測っている途中で見つかった。`cities` に **東京・カイロ・バグダッド・テヘラン・モスクワ・デリー・
ムンバイ・ラゴス・カラチ・ソウル・ジャカルタ・パリ・マドリード・キーウ・ダマスカス・モスル…**が
**1 件も無かった**。人口100万人以上だけで **177 件**。

原因は `admit()` の 1 行だった——「curated に同じ名前があればこの行を採用しない」。

⚠ **これは照合器にとっては正しい。** curated 表（`js/gazetteer.js` の 334 行）は「世界のニュースが
主題にする場所」で、その座標のほうが正確だから、long tail 側の同名行を surface にしてはいけない。
**間違っていたのは、その規則が world ファイル自体からその行を消していたこと**——そして
`cityRows()` は world だけを読む。結果、クエリの母集合が
**「地球上のすべての場所（ただし最重要の 334 件を除く）」**になっていた。

つまり報告された 34 件は「PPLX が混ざっている」だけでなく、**テヘランもバグダッドも抜けていた**。
どちらも人口100万人以上・年降水量500mm未満・外洋から200km以上で、**問いの正解**である。

⇒ 意味を 2 つに割った:

| API | 何の一覧か | 読む者 |
|---|---|---|
| `world()` | **存在する場所** | `js/atlas-query.js`・`js/seismic.js`・`js/shakemap.js`・`scripts/build-wars.mjs` |
| `worldMatchable()` | **照合 surface にしてよい場所**（`cur !== 1`） | `js/gazetteer.js` の `index()`・`js/news-context.js` の `registerSlices` |

照合器に渡る集合は 1 行も変わらないので、ニュース測位の精度は**構造的に**不変。実測でも
`newsgeo-eval` は **100.0% → 100.0%**。副次的に、地震シミュレータと ShakeMap の曝露人口からも
東京・カイロが抜けていた問題が同時に消えた。

### 4. 表示名は照合 surface ではない

`en` 列は GeoNames の `asciiname`——**機械向けの翻字**で、`Ürümqi` はそこに `UEruemqi` と書いてある。
これを英語名として印字していたのが「UEruemqi」の正体（文字化けではない）。

⇒ `disp` 列を足した。優先順位は **英語 preferred name → GeoNames の UTF-8 name → asciiname**。
実測 **32,990 行**が読める名前になった（`Sao Paulo`→`São Paulo`、`Cordoba`→`Córdoba`…）。

⚠⚠ **英語名は表示名の選定にだけ読み、照合 surface には 1 件も足さない。** `alternateNames()` の
走査集合にだけ `'en'` を加え、`LANGS` は 1 文字も変えていない——`extra[]` は `LANGS` を回るので、
`en` が surface に入る経路が**構造的に存在しない**。`en` 列（＝重複判定キー・照合 surface）も不変。

行の id も `c17`（＝「いま読み込まれている版の 17 行目」）から **`geonames:<geonameid>`** へ。

### 5. 国コードが 2 回

`tableHtml()` が名前セルに必ず `r.iso2` を貼り、`country` 列も同じ ISO2 を出していた
（「Wuzhong CN｜CN」）。⇒ **表示している列**に `country` があるときは名前セルに貼らない
（表ではなく**列**に訊く——それが「国が画面に出ているか」を決めるものだから）。

⚠ 列の**値は ISO2 のまま**にして、formatter が国名を出す。値をローカライズ済みの国名にすると
`country == 'CN'` が壊れ、しかも**読者が言語を変えた瞬間に述語の意味が変わる**。
そのために `fmt(c,v)` の順序を直した——`c.fmt` が `kind==='text'` の**後ろ**にあったので、
text 列は自分の印字のしかたを選べなかった。

### 6. 数の意味と、値の由来

**「都市 147,924 ・ 件を評価」は国スコープを適用する前**の数だった。「日本の都市で…」と訊いても
全球の件数を出す——作業量ではなく**探索範囲**を偽る。⇒ 4 段にした:
**元レコード → それ自体で 1 つの場所 → 評価 → 該当**（評価はスコープ後に数える）。

そして列に `origin` を足した:

| origin | 意味 | 例 |
|---|---|---|
| `raw` | 出典レコードの項目の写し | `pop`（GeoNames） |
| `sampled` | この地点で格子を読んだ | `precipMm`（CHELSA bio12 1981–2010） |
| `computed` | 公開形状からここで計測した | `coastKm`（Natural Earth 1:10m ±tolerance） |
| `network` | この行について問い合わせた | `elevM`・気温 |
| `derived` | この行の国を鍵に引いた | 国の統計・World Bank |

⚠ **`cost` からは導けない**——`precipMm` と `coastKm` はどちらも cost 1 で、標本と計測である。
だから宣言する。45 列すべてが有効な `origin` を持つことを検査が**レジストリを歩いて**確かめる。

### 7. 実装中に自分で開けた穴

`scripts/build-gazetteer-phone.mjs` はヘッダを固定リストで写しており、**`placeKinds` を写して
いなかった**。行には `fcode` が入るのに、それを読む判定表が無い——**携帯だけ PPLX が答えに戻り、
デスクトップは拒む。同じビルドから、どちらのファイルにもその旨は書かれない。**
1 行で塞ぎ、`⑥d` が両ファイルの `placeKinds` の一致を測る。

### 8. 検査

`tests/r576-checks.test.mjs` 14 本は **`js/atlas-query.js` を実際に読み込んで走らせる**。
stub にしたのは**データ**（gazetteer の行配列）と言語ピッカーだけで、判断する相手は 1 つも
差し替えていない（#R552 の「実物より高機能な fixture」を避ける）。
`tests/r576.spec.js` 2 本は **`window.IntMapConsole.dispatch()`＝Atlas の planner が通る扉**から
入り、実物の gazetteer（5.29 MB）と実物の海岸線で、報告された問いをそのまま走らせる
——`IntMapQuery.run()` を直に呼ぶと **bind を自分でやってしまう**ので、出荷している配線が
値を渡しているかを原理的に測れない。

変異試験: 分類を撤去 → ① 赤、扉で `resultKey` を落とす → ④c 赤、判定方法の 4 段 → ⑤b 赤。

### 9. 払った値段（`check:perf` の天井を 3 つ上げた）

| 項目 | 前 | 後 | 差 |
|---|---|---|---|
| `async.chunks.atlas-query` | 29,952 B | 35,125 B | **+5,173 B** |
| `dist.data` | 188,172,668 B | 189,444,490 B | **+1,271,822 B** |
| `dist.total` | 243,496,393 B | 244,780,506 B | **+1,284,113 B** |

理由を書く。`dist` の増分は **gazetteer に `gid` / `fcode` / `disp` / `cur` を足した分**で、
このラウンドが直した 3 つの欠陥（行の安定した同一性・都市かどうかの判定・読める名前）は
どれもこの 4 列が無ければ原理的に直せない。`atlas-query` の増分は `origin` レジストリと
`resultKey` と 4 段の数え方。

⚠ **起動費用（EAGER）の天井は 1 つも動かしていない**——gazetteer は遅延取得で起動経路に
無いので、読者が地図を開くまでに払うバイトは増えていない。増えたのは、クエリを実際に
走らせたときに取りに行くファイルと、同梱するデータの総量である。

⚠ **`--update` を走らせていない。** 実測するとそれは **14 項目**を書き戻す（eager 3・
async 2・他の chunk 5・`dist.assets`…）。その 11 はどれも許容幅の内側で、天井としてまだ
何かを主張している——一括で上げると**今回と無関係のものまで黙って緩む**。実際に落ちた 3 つだけを
手で上げた（実測は #R545 の記録と同じ形）。

### 10. このラウンドとは別の修理（Architecture.md の重複）

⚠ **今回の主題ではないが、直さないと CI が赤のままなので同じコミットで直した。**
`tests/r500-checks` ④が clean な `origin/main` で落ちていた（実測。別 worktree に main を出して確認）。

その検査は「正本が数を**言わなくなった**ら門は落ちるか」を測るために、Architecture.md から
能力数の記述を 4 つとも消す。ところがそのうち 2 つが**二重に書かれていた**ので、
1 つ消してももう 1 つが残り、文書は決して黙らず、検査は「黙ったのに門が鳴らない」と報告していた。

履歴から定めた（推測ではなく）:

| | 「カタログは押し付けず」段 | 「索引は説明ではない」段 | find_capability 行 |
|---|---|---|---|
| ～R577 | あり | 無し | 1 |
| **R582** | **無し** | **あり**（意図的な書き換え） | 1 |
| **R585** | あり | あり | **2** |

R585（#568）は**放射線レイヤーのラウンド**で、この節とは無関係。衝突解決が
**R582 が意図的に置き換えた古い方を両方残し**、表の行も 1 つ二重にした。古い方は
「**中核 8 ツール**」と書いており、二画面上の表の「**中核 9 ツール**」と**矛盾していた**。

⇒ 復活した 3 行と重複した表の行だけを消した。他は 1 バイトも触っていない。

⚠ **これは今回の主題と同じ形である**——「一部にだけ成り立つ規則を全体に適用した」。
衝突解決の「両方残す」は DEV-NOTES のような**追記されるファイル**には正しいが、
**置き換えられる文章**には正しくない。

### 11. 残っている

- world gazetteer は 4.11 MB → **5.29 MB**（`tests/r208` ②a の 6 MB 門まで余白 0.71 MB）。
  次に列を足すときはここが先に当たる。

  feature code でそう言えるようにしたが、**都市人口の定義そのものは変えていない**
  （GHSL urban-centre / metropolitan / administrative を別 metric にするのは別の仕事）。
