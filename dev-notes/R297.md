**この回も大半が再送**（警報の段落は #R271 / #R273 / #R275 / #R277 / #R284 / #R288 / #R290 / #R293 と
ほぼ同じ文面、風の空白は #R293、離散的な時刻 UI は #R290）。だから最初にやったのは直すことではなく、
**本番に対照つきの計器を当てること**だった。

### ⓪ ⚠⚠⚠ いちばん大きな数字は、自分の計測環境が作っていた

CPU プロファイルの一位は毎回 **`toDataURL`（50 秒中 47 秒・全体の 64.7%）**、呼び出し元は
`js/layer-previews.js` の `wbChoro`——レイヤーパネルのサムネイル生成だった。
「サムネイルがアプリの CPU の三分の二」は十分に大きな話なので、**別の計器で確かめた**：
`HTMLCanvasElement.prototype.toDataURL` を包んで数えると **72 回・329 ms**。100 倍以上違う。

**同じ実行の中で両方を測って**決着した——

| 起動オプション | toDataURL 呼び出し | 合計 |
|---|---|---|
| Playwright 既定 | 70 回 | **329 ms** |
| `--use-angle=swiftshader`（ソフトウェア描画） | 72 回 | **48,072 ms**（1 回 667 ms） |

**プロファイラは正しく、私の 2 つ目の計器のほうが環境違いだった。** 480×242 の canvas の
`toDataURL` はソフトウェア描画では GPU 読み戻しに 667 ms かかり、実機では 5 ms で終わる。
そして **ablation が決着させた**——`toDataURL` を丸ごと無効化しても警報レイヤーの fps は
**4.2 → 3.6** で改善しない。**これは利用者の欠陥ではなく、計測器の性質**である。

⚠ 教訓は「小さいほうが本当だと決めつけた」こと。2 つの計器が食い違ったときに要るのは
**3 つ目の計器（同じ実行の中で両方）と ablation** であって、もっともらしいほうを選ぶことではない。
⚠ そして**この事実は以降のすべての fps 値の読み方を変える**。ソフトウェア描画で測った 3.4 fps は
実機の体感ではない。**同じ環境どうしの比較**にだけ使う。

### ① 対照つきで測った「重すぎる」、そして本当の相手

本番・z4・欧州中心・60 秒・同じ環境：

| | 主スレッド遮断 | フレーム率 |
|---|---|---|
| レイヤー無し（対照） | 19.5 s | **36.5 fps** |
| **警報オン** | 49.0 s | **3.4 fps** |
| 風オン | 21.3 s | 17.7 fps |

つまり **警報レイヤーは「何も無い」に対して桁が違う**。ここまでは報告どおり。
⚠ ただし**倍率だけが読める**——同じ計器を4回まわすと対照は 36.5 / 27.3 / 20.8 / 35.2 fps、
警報オンは 3.4 / 4.9 / 3.4 / 2.8 fps で、**比は 5〜12 倍**、絶対値は機械の負荷で動く（②の末尾）。
では何が重いのか。78 秒で `wp-alert` に **62 回**（最大 3,792 地物）貼り直し、
`setFeatureState` **9,990 回**。CPU プロファイルの内訳（ソフトウェア描画を外して読む）：

- **`ptInRing ← countryAt ← learnCoverage ← publishNow` = 5,562 ms／50 秒。**
  `countryAt` は**国境の全リングを順に歩く**。`hiResCountries()` がレイヤー投入と同時に
  高解像度の輪郭へ差し替えるので、そのリングは数千頂点ある。
- 残りは `(program)`＝レンダラ本体。z4 の欧州で**発令 2,557 単位＋発令なし 1,839 単位**、
  それぞれに輪郭とラベルが付く。**これは「絵そのもの」であって無駄ではない。**

### ② ⚠⚠⚠ 直したものを 5 つ入れて**数字が動かなかった**——それが手がかりだった

①〜⑤（下表）を入れて測り直したら、貼り直しの回数も `setFeatureState` の回数も**改善しなかった**
（実測、main 64/62 回に対して 72/71 回で**むしろ増えた**）。
合流窓を 160 ms → 1,500 ms にしても回数が 0.96/秒＝**窓が許す上限を超えている**。
つまり**貼り直しは publisher を通っていなかった**。

**MapLibre の `styledata` は「基図が変わった」ではなく「スタイルに何か起きた」である。**
`addLayer` も `setPaint` も `setLayout` も——そして **`setSourceData` も**——この事象を出す。
このファイルの**基図差し替え復帰**（#R72 が「誰も layer を戻さないとどうなるか」を記録している、
あの復帰）はそれを聞いていて、**無条件に**コレクションを貼り直し、`publishQuiet(true)` と
`paintCountries(true)`（＝258 か国ぜんぶの feature-state 書き直し）を強制していた。

> publish → `setSourceData` → `styledata` → 80 ms 後に復帰 → `setSourceData` → `styledata` → …

**publish は落ち着かず、振動していた。** 速度を決めていたのはブラウザが 4 千個のポリゴンを
再タイルできる速さで、それが「重すぎる」の正体である。
→ ⑴ ディスパッチャは**合流**する（一連の変更で 1 回）。
→ ⑵ 復帰は**本当に落とされたときだけ**走る。`ensureLayers()` は新しいソースを作ったときに
   内容署名を消す（#R290）ので、**`featsSig===''` がその信号**である。フラグを別に置かない。
⚠ **復帰そのものは変えていない**——本物の基図差し替えでは今までどおり全部やり直す。
やめたのは、何も落ちていないときにやることである。

そして①〜⑤も**無駄ではない**（同じ絵のためにやり直していた仕事であることに変わりはない）。
⚠ ただし⑴を入れる前は、①〜⑤のうち「形の索引をもっと積極的に取りに行く」変更が
**振動を増やしていた**——publish を呼ぶ人が増えれば、振動の回数も増える。
**土台が振動しているとき、上に足した改善は逆符号で効くことがある。**

| | 何をしていたか | どうしたか |
|---|---|---|
| ① | 機関の発表一覧を**全地物の文字列プロパティ**に入れていた（`items:JSON.stringify(rows)`）。スタイルは一度も読まないのに毎回シリアライズしてワーカーへ複製 | `ROWS`（`rid` で引く手前側の表）へ。カードと国別凡例が読むものは同じ |
| ② | **MeteoAlarm のバッチが来るたびに 35 か国ぜんぶを組み直す**（WMO 側も同様） | 国ごとに組んだ結果を持ち、鍵（索引の顔ぶれ／その国の取得時刻／表示言語）が動いた国だけ組み直す |
| ③ | 貼り直しの合流窓が **160 ms**＝1 フレーム内の 2 件しか合流しない | `PUBLISH_MS`（窓に 1 回・末尾）。国の薄塗りも同じ窓。`force` は即時 |

| ⑤ | 略号ラベル層に**下限ズームが無い**＝世界ズームで 4 千件の衝突判定 | z2.5 未満は色と輪郭が答える |
| ⑥ | タイラーへの許容誤差が既定（0.375 タイル単位） | 発令 1.2・発令なし 2.5。**ズームごと**に効くので、その拡大率で表現できない頂点だけが落ちる |
| ⑦ | **`styledata` を基図差し替えとして扱っていた**（上） | 合流＋「本当に落とされたときだけ」 |

実測（交互に 2 回ずつ・同じ視点・75 秒。⚠ 上流の天気が回ごとに変わるので**隣り合う回どうし**で読む）:

|---|---|---|
| `wp-alert` 貼り直し | 64 / 62 / 67 / 55 | **20 / 19** |
| 「発令なし」貼り直し | 50 / 51 / 52 / 46 | **10 / 9** |
| `setFeatureState` | 10,043 / 9,221 / 9,899 / 8,189 | **577 / 671** |
| 発令中の区域（前提の確認） | 2,820 / 2,823 / 2,834 / 2,835 | 2,844 / 2,572 |

**レイヤー無し（＝完全に同じコード）が 20.8 fps と 35.2 fps** になる——機械の負荷でその幅がある。
だから「警報オン 3.4 fps 対 2.8 fps」に意味は無い。⓪ で分かったとおり、ヘッドレスの
ソフトウェア描画は GPU 読み戻しを 100 倍に膨らませ、描画そのものも実機と別物である。

### ④ 塗漏れ——**MeteoAlarm の区域は 1 つもポリゴンを持っていない**

実測（10 か国・850 区域）: **全部が `EMMA_ID` を持ち、`<polygon>` は 0 件**。
だから 35 か国は**名前で置く**しかなく、その名前を知っている索引は
**同じ機関が WMO 登録簿に出している形**（`?swicgeo=`）だけ。そしてそれは
**毎回空から積み直していた**（#R284 はセッション中の蓄積を入れたが、訪問をまたがない）。
→ Cache Storage（`intmap-swicgeo-v1`・7 日）に**名前と形だけ**を保存し、
読む前に適用し、新しく読めた形と**併合**する。⚠ 発令内容は決してキャッシュしない。
加えて、WMO 側の加盟でポリゴン無しの区域を持つ国も同じ索引を作る。

### ⑤ 境界線解像度——**床は上げず、寄ったときだけ細かくする**

Eurostat NUTS の実測サイズ（LEVL_3）: 20M 1.68 / 10M 2.58 / 03M 6.77 / 01M 28.18 MB。
床を 10M にする版を作って測ったら、**同じコレクションを貼り直す費用だけが増えた**——
欧州全体が画面に入るズームで 20M と 10M は同じ絵である。
→ **床は 20M のまま、`UNIT_HIRES_Z` を越えたら 03M を取って索引に併合**し、
`mkey` が動くので描かれている警報がその場で細かい形に置き直される。

### ⑥ 対応国——**増やせる先が無いことを、数字で示す**

- WMO 登録簿: 加盟 **198**・CAP 実装 Completed **138**・いま発表している **39**。
  **Completed でないのに発表している加盟は 0**。つまりこの登録簿は使い切っている。
- もう一つの世界規模の登録簿（Filtered Alert Hub、231 ソース）は**使えない**。
  実測: 全 231 が自己申告で `operating` だが、マカオ気象局の「最新の警報」は
  **2015 年のルワンダについての `<cap:status>Test</cap:status>`**、
  RSS の `lastBuildDate` は **2018 年**。
  そして国別フィード（`country-<cc>-lang-en`）は**その国の機関のものではない**——
  実測、マレーシアにインドネシア BMKG、ペルーにチリ気象局、モロッコにアルジェリア、
  レバノンにイスラエル、そして **GDACS**（#R273 で撤廃したもの）が入っている。
  「一国一ソース。各国の気象台の情報をもとにしろ」と正面から矛盾する。
- 直接の国営フィードも当たった（トルコ MGM・パキスタン PMD・バングラ BMD・ベトナム・
  マレーシア・ペルー・コロンビア・モロッコ・イラン・南ア・インド・インドネシア・タイ）。
  **機械可読で到達できるものは 1 つも無かった**（HTML／401／404／`Not allowed by MGM`）。
- **増やせる道は 1 つだけ残っている**——`learnCoverage` は「描かれた単位の重心が、
  フィードを持たない国に落ちたら、その形を描いた機関がその国を担当している」と学習する。
  だから**置ける区域が増えれば対応国も増える**（実測、フィンランドは 4/9 しか置けておらず、
  そのため Ahvenanmaa＝オーランドが学習されていなかった）。④ はその意味でも塗り直しである。
  ⇒ **`MA_ALIAS` に `FIN:{'Ahvenanmaa':'FI20'}` を 1 組足した。** MeteoAlarm はフィンランド語、
  Eurostat はスウェーデン語（`FI20 · Åland`）で、正規化では絶対に一致しない。実測、
  **フィンランド 4/9 → 5/9**、学習された国は `KOS`/`LIE` に **`ALA`（オーランド）** が加わった。
  ⚠ 別名表は「1 機関の 1 語 → 1 境界 id」であって対応国の表ではない——誰が担当するかは
  今も**描かれた形**が決める。

### ⑥b 更新が遅すぎる——**床は転送のほうにあった**

定常の一周は #R284 以来「relay のエッジキャッシュ（60 秒）の直下」に張り付いていて、
それより速く聞いても**同じバイトが返る**だけだった。だから今回は**その床のほうを下げた**——
`alerts-relay` の `s-maxage` を **60 → 30 秒**、アプリ側の再読み込み下限（`MIN_AGE_MS`）を
**45 → 25 秒**、tick を **30 → 20 秒**。`stale-while-revalidate` があるのでエッジは即答し続け、
増えるのは**エッジが上流に聞く回数**だけである。
⚠ そして**輪番は必ずキャッシュより速く一周しなければならない**（`tests/r277 ⑧` が両端から計算して
落とす）——30 秒の床に対して 35 か国 ÷（6×3）＝2 tick＝40 秒では**遅い**ので、持続スロットを
**3 → 6** に広げて 1 tick＝20 秒にした。冷たいバーストは **6 → 10**。
⚠ 実測で分かっていること: レイヤー投入から **45 秒で 35/35 か国・93/93 加盟**を読み終えており、
そのあと増えるのは**読み込みではなく形**である（④）。だから「遅い」の残り半分は④が引き受ける。

### ⑦ 風——**起動時の視野は地球なので、地球を読んでいた**

実測、レイヤー投入から粒子が動くまで **14.5 秒**（起動時の視野）／**74.9 秒**（日本上空へ寄せた状態）。
描画ではない——レンダラ自身は 1 フレーム数ミリ秒。**1 回の読み取り**である：
`bandFor` は視野が緯度 120° を超えると `null`（＝全球）を返し、起動時の視野は地球だから
**13,199,360 標本・約 18 MB** を読み終えるまで何も動かない。
全球読みは**帯域律速**で、#R288 の `prefetchVariable` は縮められる小さなレンジが無いので効かない
（実測 A/B: 素 16.4 / 7.8 秒 対 暖機 7.8 / 9.4 秒）。
⚠ **色面も道連れになる**——SDK は `omFileReader` を 1 本しか持たず、ラスタタイルも同じ読み取り機を
通るので、色のスロットが表に出たのは **15.9 秒**、場のすぐ後ろだった。
→ **最初は画面中心の帯（`bandNear`）を読み、その裏で視野全体の帯を読んで差し替える**。
実測（同じローカルビルド・同じ視点）: 保持しているフレームは **13,199,360 → 3,785,000 標本**、
風レイヤーの主スレッド遮断は **20.6 s → 4.7 s**（60 秒中）。
最終的な絵・標本間隔・ファイルは同じ。粒子は読めている帯の中にだけ撒く。

### ⑧ 時刻を変えたときの空白——**`isSourceLoaded` は「頼まれていない」でも真になる**

#R284 の 2 スロットは正しく、外す条件が間違っていた。`isSourceLoaded` は
「このソースについて飛んでいるものがあるか」を答えるので、**追加したばかりでタイルを 1 枚も
頼まれていないラスタソースでは即座に真**になる。だから新しいスロットを表に出し、古い方を消し、
**新しい方には描くものが無かった**。→ **タイルが 1 枚でも届いたとき**（`e.tile && e.isSourceLoaded`）
にだけ表に出す。#R290 が ECMWF ラスタに書いた規則の、1 ソース隣。

### ⑨ 風の凡例は 30 m/s まで／⑩ 気象系の時刻 UI は全部離散

- 配色表そのものは Windy の `RGBA()` に合わせた 27 停留点のまま（104 m/s まで塗る）。
  **凡例が読む範囲だけ**を 30 m/s で切り、**上端の目盛りに `+`**（`legend().capped`）。
  「30 が最大」と言わないための印であり、風の箱と ECMWF の箱の両方に出る。
- ECMWF 系はもともとモデル自身の index を `step=1` で刻んでいた（#R290/#R293）。
  残っていたのは**潮汐**——毎正時の海洋モデルに対して分刻みの `datetime-local` と
  **6 時間 12 分**（＝:12 に着地する）の 1/4 周期ボタン。
  → `step=3600`・`snapHour`・1/4 周期は 6 時間・再生も 1 時間刻み。

### ⑪ 平面地図は自由スクロールに一本化

「範囲固定（ヨーロッパ中心）」は**繰り返さない 1 枚の世界**で、日本から東へ進むと
経度 180° で止まり、止まった枠の中心が経度 0＝ヨーロッパになる。#R223 は既定を自由側に倒し、
明示的な選択だけがラッチで生き残るようにしていた。今回は**モードそのものを削除**した——
選択肢・保存値・ラッチ・設定行、そして `imFlatPan` はアプリのどこにも無い。
9 言語すべてから `lblFlatPan` / `flatPanFixed` / `flatPanFree` を削除。
`tests/r223 ③` は「既定が free か」ではなく「**固定モードが存在しないか**」を検査する。
