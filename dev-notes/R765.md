## R765 — 「作業を再開できる」と「その結果をもう一度出せる」は別のこと（第四段階）

〈#R759 への外部評価の第四段階。#R763（第一・第二）・#R764（第三）の続きで、これで 4 段階が揃う。
指摘の §8・§9 を今日の `main` で確かめてから着手した〉

## 0. 指摘は正しく、しかも `docs/GIS-CORE.md` が先に半分書いていた

「保存・版管理が無いわけではない」——そのとおりで、#R749 が版を、#R752 が台帳を、#R756 が出口を
作ってある。指摘が言っていたのは**その先**で、こう書いてあった:

> 「作業を再開できる」と「以前提示した結果を、そのまま再現できる」は別。

⚠ **足りなかったのは倉庫ではなく文書だった。** 分析を他人に渡すときの問いは
「**この数は何から、どうやって出たのか**」で、その答えは 4 つのモジュールに散らばっていて、
手で歩かないと集まらなかった。作ったのは `manifest(id)`——1 度歩いて書き出すもの。

## 1. ⚠⚠⚠ 記録は、自分を計算したエンジンを述べていなかった

`manifest()` を書こうとして出た欠陥。#R749 は「同じレシピは実装が違えば同じ答えではない」を立て、
**保存する段**に版を書き込んだ。それが覆うのは**開き直したプロジェクトだけ**である。

⇒ **いまレジストリに在る記録**——読者が見ていて、いま書き出そうとしているもの——は、
**何が計算したのかを 1 バイトも述べていなかった。** 後からカーネルに訊くのは**別の問い**
（「いま何が載っているか」）で、**2 つが食い違う場合こそ版が在る理由**である。

⇒ `js/gis-ops.js` が登録の瞬間に `provenance.engine` を刻む。
⚠ **訊くのであって写さない**——どれがカーネルかを見つける規則は `js/gis-project.js` のもので、
ここで 2 度目の走査を書けば、この層が断り続けている「2 つ目の一覧」になる。
⚠ **配る者が居なければ黙る**——その module が載っていない状態で計算された記録は版を持たず、
`manifest()` は**今日の版で埋めずに** gap として報告する。

## 2. manifest — 何を書き、何を書かないか

```
{ id, title, producedAt, manifestVersion, engineNow,
  steps: [ 入力が先の順に { id, origin, recipe, engineThen, acquisition,
                            coverage, crs, time, fields, bands, fingerprint } ],
  answer: { fingerprint, count, kind },
  gaps:  [ { step, gap, means } ] }
```

⚠⚠ **いちばん重要な欄は `gaps`。** このアプリが**自分の答えについて本当に知らないこと**を並べる:

| gap | 意味 |
|---|---|
| `upstream-not-versioned` | 上流そのものに版が無いので、同じ問い合わせが同じ答えを返す保証は無い |
| `source-bytes-not-kept` | 取り込んだ元のバイトは保存していない（同じファイルかは指紋でしか確かめられない） |
| `coverage-unstated` | 求めた範囲のうちどこまで答えられたかを、その供給元は述べていない |
| `engine-not-recorded` | その段を計算したエンジンの版が記録されていない |
| `fingerprint-unavailable` | 内容の指紋を取れなかった |

知っていることだけを並べた文書は「**知らない**」を「**全部だ**」の代わりにする形
（[[intmap-one-store-was-asked]]）で、**他人の数を検算する読者が最初に要るのはこちら**である。
⚠ 各 gap は**読者向けの文**を持つ（`means`）。コードだけでは届かない。

## 3. 指紋は、レシピではなく答えに対して取る

1 つのレシピの 2 回の実行は同じ分析で、**同じ答えかどうかは別の問い**である。
`verify(id, manifest)` は **「同じ」「違う」「測れなかった」の 3 つ**を返す
——⚠ **指紋を取れなかったものは一致ではない**（ここが潰れると、この仕組みは何も保証しない）。

⚠ **正規化しないと指紋ではない。** `JSON.stringify` は挿入順にキーを書くので、同じ地物を別の経路で
組んだだけで別の指紋になる。⚠ **配列の順は保つ**——地物の並びは答えの一部である。
⚠ **格子は画素の並びと「どこに置かれているか」の両方**から取る（同じ画素が別の場所に置かれて
いるのは別のデータ。#R756 の往復検査が捕まえたのと同じ種類）。
⚠ 平台の `crypto.subtle` を使う（ブラウザと node で同じ数が出る）。⚠ **無ければ別のハッシュに
こっそり落とさない**——「指紋」を名乗る関数が 2 つある状態は、指紋が無いより悪い。

## 4. ⚠⚠⚠ 自分の読み手で読み直せることは、他人が開けることではない

#R756 は「書き出せた」と「読み直せた」を分け、3 形式とも既存の読み手で許容幅 0 で読み返した。
正しい第一段で、その註が述べていなかった限界がある:

> **一緒に作られた書き手と読み手は、他の誰にも開けないファイルについて一致できる。**

タグの順を間違えても、述べたバイト順と実際が違っても、**同じ仕様書の同じ読み方から作られた
読み手**は、いちばん許してしまう読み手である。往復は緑のまま、ファイルは他所で開けない。
**不一致を出せない比較は何も測っていない。**

⇒ `tests/r765-gis-external-reader-checks` は **TIFF 6.0 / GeoTIFF 1.0 の仕様から書いた読み手**を
テストの中に持つ。`js/gis-geotiff.js` も `js/gis-export.js` の定数も**取り込まない**——タグは
**番号で**知っている（33550 / 33922）。バイト順の印・magic 42・IFD の項目数・オフセットが
ファイルの中に収まっていること・**述べた `SampleFormat` と実際のバイトが一致すること**を見る。
⚠ **参照が本当に不合格を出せることも測る**（壊したファイルを 3 通り作って、実際に拒むこと）。

**実測: この app が書いた GeoTIFF は、この app を知らない読み手が開けた**
（9×7 の float32、両軸で非対称の値、`ModelPixelScale` と `ModelTiepoint` から場所も一致）。

⚠⚠ **これが主張していないこと。** この読み手は **GDAL ではない**。緑なのは「仕様どおりに
書けている」であって「**QGIS で開ける**」ではない——後者は実際に第三者の実装で読んで初めて
言えることで、**このリポジトリはオフラインではそれを言えない**。その線は埋めずに書いておく。

## 6. 版

- `js/gis-ops.js` **ops-5 のまま**。⚠ **この線が要点**: この回が足した `provenance.engine` は
  **計算についての陳述**であって**データについてではない**。数も拒否も許容幅も動かず、
  再生したレシピの出力は 1 ビットも変わらない。
  ⚠ **#R763 と #R764 が版を上げたのとの対比**——あちらは記録が**数について**述べることが変わった
  （どちらの日付か・単位が残るか・完全だと名乗るか・どの境界規則で出したか）。

⚠ **`gis-core` の async chunk の天井を 355.2 kB → 360.4 kB（+5.2 kB）へ上げた**
（`manifest` ・ `verify` ・ 正規化と指紋）。⚠ **起動側（EAGER）はこの回も 1 バイトも動いていない**
——この層は遅延読み込みで、`js/gis-project.js` は GIS の chunk の中に在る。
⚠ `--update` は使っていない（全項目を書き直すので起動の天井まで黙って上がる）。
