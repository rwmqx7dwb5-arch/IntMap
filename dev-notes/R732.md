## R732 — 任意の形を扱える空間演算と、座標系を実際に変換すること

〈外部評価: 「データセット管理・型判定・処理の連鎖・再計算・保存・Atlas からの問い合わせは実装済み。
増強すべきは汎用的な空間演算・座標変換・数値ラスター・既存データとの接続」。今回の範囲は利用者が
選んだ **整合性 2 件 → 幾何演算と座標変換 → 既存レイヤーの接続**。ラスター・実行基盤・時間は次〉

### 1. ⚠⚠⚠ #R729 の 2 つの拒否は正直だった。正直さの中身は「engine が無い」だった

#R729 は 2 つを名指しで断っていて、どちらも `CONSTITUTION.md` の「偽物・ハリボテを作らない」に
忠実だった:

- `buffer-needs-points` — 線・面のバッファは未実装。頂点ごとの円で近似すれば**凸凹のビーズ**を
  地図に置いて「5km 圏」と呼ぶことになる。
- `clip-window-not-convex` — Sutherland–Hodgman は**窓が凸のときだけ正しい**ので、窓の各環の
  凸性を測って断っていた。穴のある区や凹んだ県は切り抜きの窓になれなかった。

**2 つは同じ 1 つの欠落だった**——本物の多角形クリッピング engine。`js/gis-geometry.js` がそれで、
2 つのコードは**緩められたのではなく、返す場所が無くなった**。

⚠ **boolean 演算を自作しない。** `polygon-clipping`（Martinez–Rueda の sweep line）は**このアプリが
既に持っている依存**で、`js/world-packs.js` と `js/cesium-vector-tiles.js` が同じように動的 import して
いる。穴を穴のまま保ち、答えが複数片なら複数片を返し、両辺に MultiPolygon を取る。ここに 2 つ目の
engine を書くのは `.agents/rules/no-ad-hoc-hardcoding.md` §2-3 の「同じ判断を 2 か所に持たせる」で、
しかも出来の悪いほうになる。**読み込みは遅延**——重ね合わせを 1 度も走らせない読者は sweep line を
ダウンロードしない。

⚠ **バッファはオフセット曲線ではなく Minkowski 和である。** 半径 r のバッファの定義が「その形から
r 以内の点の集合」＝「その形と半径 r の円盤の Minkowski 和」なので、そのとおりに作った: 頂点ごとに
**測地円盤**（`diskFillPolys`＝点バッファがずっと使ってきたもの）、辺ごとに**測地の四辺形**、全部を
union。union が自己交差を消し、円盤が継ぎ目を丸める。`@turf/buffer` を使わないのは 2 つ——
turf-jsts（332 kB。`src/vendor.js` が `ensureHeavy()` の後ろに置いている）に届くことと、
**オフセットを平面で計算するので緯度 60° の「5 km」が 5 km ではない**こと。

**実測**（1° の子午線分を 10 km で膨らませる。解析カプセル `2rL + πr²` = 2538.06 km²）:

| steps | 面積 km² |
|---|---|
| 8 | 2506.80 |
| 32 | 2536.10 |
| 64 | 2537.61 |
| 256 | 2538.09 |
| 1024 | 2538.11 |

⚠ **内接近似であることを検査に書く向きを間違えかけた。** 最初 `got <= 解析解` と書いて落ちた——
**解析解のほうが平面の式**で、球面の測定に対してその符号は何も意味しない。正しい主張は
「steps とともに**内側から**単調に増えて落ち着く」で、検査はそちらを測っている。

### 2. ⚠⚠⚠ 継ぎ目は「拒む」から「ほどいて揃えて戻す」へ

#R729 は経度幅 180° を超える環を断っていた。**「継ぎ目をまたぐ」と「世界を逆回りに巻く」を
区別できないときは、それが正直な答え**である。区別はできる——**両端ではなく隣り合う頂点を見れば**。
隣接頂点の経度差が 180° を超えるのは継ぎ目であって、**半周ぶんの長さを持つ辺**はこの地図が読む
どのデータにも無い。だから環はほどき、両辺を同じ 360° 窓へ揃え、計算し、
`IntMapGeodesy._splitPolyToWindows`（`diskFillPolys` の円盤が通っているのと同じ分割器）で
`[-180,180]` に戻す。

⚠ **いまも拒むのは 1 つだけで、それはデータではなく平面についての拒否**——ほどいても経度幅が
360° 以上になる環（極冠・全球環）は、**どの円筒平面でも単純な環になれない**。

**実測**: 180° をまたぐ 2 つの箱（170..−170 × −5..5 と 175..−175 × −2..2）の交差は 494,473 km²、
解析（10° × 4° を赤道で）494,573 の 0.02% 以内。答えは `[-180,180]` に収まって返る。

### 3. ⚠⚠⚠ 「UI に手書きの一覧を作るな」と書いた段落の真下に、手書きの一覧があった

`js/gis-ops.js` のヘッダは「`buffer` は半径を聞く、という一覧を UI 側に持たせない」と書いていた。
その 20 行下に:

```js
const ORDER = ['filter', 'buffer', 'clip', 'aggregate'];
```

`ops()` はこれを map していたので、**`DECL` に足して `ORDER` に足し忘れた op は `run()` に答えるのに
画面に出ない**——パネルのヘッダがまさに避けようとしていた形が、ops 側にあった。さらに `run()` の
dispatch は **無条件の `else` で終わる if 連鎖**で、配線し忘れた op は**黙って aggregate を走らせ**、
その出力を新しい op の名前で登録していた。⇒ `ORDER = Object.keys(DECL)`、dispatch は op id を鍵に
した表、配線が無ければ `op-not-wired`。検査は**両側を構文から集めて**突き合わせる。

op は 4 → 9: `filter` / `buffer` / `clip` / **`intersect`** / **`difference`** / **`union`** /
**`dissolve`** / **`relate`** / `aggregate`。`buffer` は任意形状を受け、**負の半径は内向き**（面のみ。
点や線は `inward-buffer-needs-area` で断る——0 に丸めない）。`relate` は空間述語で絞り、
`nearer-than` は**測った距離を `_distanceKm` に書く**（「500m 以内」と「そのうち何 m か」は同じ問いで、
数を捨てると 2 回目の走査になる）。`aggregate` の 2 つ目の入力は `Point` → **何でも**で、
「面に含まれる**点**」ではなく「その面に**重なるもの**」を数える。

### 4. ⚠⚠⚠ Atlas に渡っていたのは形ではなく、外接矩形の中心 1 点だった

`js/atlas-query.js` の `userRows()` は、線・面の行を `lng/lat` 2 値に潰していた。註は出ていたが、
**行に `geometry` への参照が 1 つも無い**ので、面積・長さ・重なり・包含・「道路そのものからの距離」が
**原理的に計算できなかった**。しかも註は結果全体に 1 回付くだけで、**どの行が実点でどの行が導出点か**
を読者は区別できなかった。

⇒ 行が元 geometry を**参照で**持ち（コピーではない。`features()` を関数の裏に置いた理由が消える）、
空間の判定は全部その形で行い、表に出る 1 点は代表点のまま**そこからは何も測らない**。行が自分で
「この座標はここで計算した」と述べる。`spatial` 句（`within` / `contains` / `intersects` /
`nearer_than`）が加わり、`within` は相手表を**1 つの集合として**扱う（どの構成員の中にも無いが
和集合の中にある行が正しく入る）。

⚠ **`catalogue()` は実行側の宣言から導出する。** #R582 の実測——**存在を知らない能力のために扉は
開かれない**——なので、`js/atlas-catalog-text.js` の 02a にも `spatial` の書き方と
「`near` はピンとピンを測る。線や面には 1 つのピンが無い」を書いた。

### 5. ⚠⚠⚠ 座標系を「記録する」から「実際に変換する」へ——順序が本質だった

`sourceCrs` は #R729 からレコードに在ったが、**書いていたのは 1 行**（フォーマットの仕様だけを見て
`geojson|kml|gpx → 'EPSG:4326'`、他は `null`）で、**画面に出す経路は実在しなかった**
（`js/gis-datasets.js` と `js/geo-import.js` のコメントは「パネルが表示する」と述べていた）。

`js/gis-crs.js` は proj4 を**遅延**で読み、GeoJSON の `crs` メンバから code を取り、4326 でなければ
**実際に変換して** `sourceCrs` に元の code を残す。⚠ **EPSG の表は 1 行も書かない**——規則 3 つだけ
（proj4 自身が知るもの／**UTM は `EPSG:326NN`・`327NN` の算術**／読者が `define()` で渡した WKT）。
それ以外は `crs-unknown` で断り、近い定義を当てない。出力は常に `[lng,lat]` で、変換後 |緯度| > 90 は
`crs-axis-suspect`——軸順序の取り違えは例外を出さず、地物を世界の裏側へ静かに置く。

⚠⚠ **CRS の決着は `IntMapGeodesy.sanitizeFeatures` より前に置かなければならない。** あれは緯度を
±89.9999 に**クランプ**するので、後ろに置くと northing 4,257,201 m は失敗せず
**「北極に載った正しい形」**になる。証拠が消えるのはそこである。

座標系を名乗らないファイル（区切りテキスト）は `looksProjected()` が**測る**——度の範囲に収まらない
座標は、ファイルが何も言わなくても度ではない。`crs-not-stated-and-not-degrees` で断る。
⚠ これは**新しい拒否**なので、度に収まる既存の CSV が 1 件も落ちないことを確かめてある。

### 6. ⚠⚠ レイヤーを分析の入力にしたら、地図側の窓が線と面を落としていた

`js/gis-layers.js` は `IntMapLayers` の行と geo-engine の geojson source を**数え上げて**（手書きの
一覧は次に足されたものを黙って落とす）、形状も属性も落とさずデータセットにする。

その過程で出た実測: `js/map-ui.js` の `_srcFeatsIn` は**「この地物は箱に入っているか」という問いを
`f.geometry.type === 'Point'` で代用**していた。**レイヤーが持つ線と面は、必ず 0 件だった。**
直したのは事例ではなく問いのほうで、座標を深さ優先で歩く 1 つの述語にした（型ごとの分岐表は無い）。

### 7. ⚠⚠⚠ 整合性 2 件は、どちらも「共有しているものを見ていなかった」形だった

**⑴ 自動採番が、自分の名前空間を見ていなかった。** `ds-N` を作る counter は**自分が作った id でしか
進まない**のに、名前空間は `js/gis-project.js` と共有している——保存から `ds-1` を復元しても counter は
0 のままで、直後の取り込みが `ds-1` を再発行し、`add()` が投げ、`js/geo-import.js` は登録失敗を
握りつぶす。**地図には出ているのに、解析の台帳には存在しない**データセットができる。
⇒ counter は**自分が出しうるどの id も追い越す**。⚠ **下がることは無い**（remove でも）——発行済みの
id は保存されたレシピが名指しているかもしれず、再発行はそのレシピを別のデータに繋ぐ。

**⑵ 失敗した再計算が、2 通りに嘘をついていた。** `setParams` は id を空けるために対象を remove して
から走らせるので、**op が断る値を打った読者は編集中のデータセットごと失い**、次の `setParams` は
`no-such-dataset` としか答えられなかった（パネルの中から戻る道が無い）。そして**その下流は触られも
しない**ので、**古い引数での答えを持ったまま**残り、パネルは並べ、`draw()` は描き、問い合わせは答え、
次の op は食べた。⇒ 各段を **commit-or-restore** にし（古いレコードを保持し、失敗したら戻す）、
`stale` を**下流へ伝播**させ、**`js/gis-ops.js` が `input-stale` で拒む**。

⚠ **伝わるのは根本の理由**（実際に断られたコード）で `upstream-failed` ではない——読者が直すのは
根本のほうで、症状の言い換えに上書きすると診断が消える。
⚠ **地物は消さずに残す**。実際に計算された最後の答えは空のパネルより価値がある——**全員がそれを
何であるかと述べている限り**。だから拒否と、パネルのバッジと、両方が要る。
**誰も検査しない状態は、状態ではなく飾りである。**

### 8. 起動費用

**ブロトリ +1.3 kB・リクエスト 6 のまま・module 298 のまま。** `gis-core` チャンク
（67.0 → 93.9 kB）が増えたのは**配線のぶんだけ**である（実測: `dist/assets/gis-core-*.js` に
proj4 の `ellps`/`towgs84` は 0 件）。

⚠⚠ **この節はもともと「sweep line も proj4 も別チャンクの動的 import」と書いていた。proj4 は
そのとおりだが、sweep line は違う——本番実測で訂正した（#R734）。** polygon-clipping は

（R731 のビルドでも同じチャンクに入っている。両方ビルドして測った）——#R732 は**事実の反対を
書いた**だけである。
