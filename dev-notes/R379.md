## R379 — **飛行機アイコンを元に戻した——「ダート」は誰も頼んでいない設計判断で、SDF を 18 頂点で書かなかった値段だった**

> 「航空機レイヤーの飛行機アイコンのデザインをもとに戻して。」

### 1. 何が変わっていたのか

このアプリのマークは**旅客機のプランフォーム**——胴体・後退翼・水平尾翼を、機体色で塗り、
白い線で縁取ったもの。最初のコミットから #R164 まで一字も変わっていない。#R183 が
「もっと目立つもの」に置き換え、#R187 が判定を受けて**戻し**、#R190〜#R192 が3ラウンドかけて
「平面のグリフと持ち上げた 3-D の機体が**同じマークで同じ画素数**である」ことを証明した。

#R341 が航空レイヤーを GPU 点群へ作り直したとき、マークも一緒に**切り欠き付きの三角形**に
変わった。そのファイルのコメント自身が理由を書いている——

> *「a signed distance field is cheaper to write for three vertices than for eighteen」*

**つまりこれは設計判断ではなく、18 頂点の SDF を書かなかったことの結果だった。**
このラウンドはその 18 頂点を書いた。

### 2. どこまで戻すのか（利用者に訊いた）

#R341 は形だけでなく**色と大きさ**も変えているので、「デザインをもとに戻す」の範囲を確認した。
返ってきた答えは：

| 軸 | 決定 |
|---|---|
| **形** | 元のプランフォーム＋白い縁取りに戻す（依頼そのもの） |
| **色** | **今のまま**——高度グラデーション（低高度 `#35E0FF` → 高高度 `#008CFF`）と緊急・地上・軍用の色分けは #R341 のまま維持 |
| **大きさ** | **高ズームだけ元へ**——z8 以上は元のサイズ、低ズーム側は #R341 のランプのまま |

⚠ **色を訊いたのは、それが機能でもあるから。** 高度で色が変わるのは「マークの見た目」であると
同時に「高度を符号化する計器」でもあり、`CLAUDE.md` §3.1 は指示のない機能削除を禁じている。
#R191 の記録には「元に戻せと言っているのに、色を勝手に変えるな」という苦情が残っているので、
**どちらに倒しても勝手な判断になる**——だから訊いた。

### 3. 宣言を 1 本にした（`js/plane-glyph.js`）

このマークを描くものは 2 つあり、互いのメモリを見られない：`js/aircraft-points.js` は
フラグメントシェーダの SDF として、`js/cesium-engine.js` は BillboardCollection のスプライトとして。
**#R341 は自分のダートを両方へ「書き写し」、2つの写しを結びつけるものを何も置かなかった**
（コメントで「同じ形を描く」と述べただけ）。#R345 が10回目に数えた形——
「繰り返す欠陥の直し方が1ファイルの中にあると、次の occurrence が来る」——そのものなので、
**頂点18・白縁の幅・サイズ表を `js/plane-glyph.js` に1本だけ置き、2つが読む**ようにした。

⚠ **`?aviation=v1` の旧経路（`js/data-layers.js`）は 1 バイトも触っていない。** #R341 が
Phase G の巻き戻し期間のために意図して凍結したもので、そこは自分の `_PLANE_ORIG` を持ち続ける。
代わりに**検査②が両者の一致を固定する**ので、「2つ目の真実」にはならない。

⚠ **起動バイトは 1 バイトも増えていない。** `js/data-layers.js` は eager（`src/main.js` が import）
なので、そこから共有モジュールを import すると**既定でオフのレイヤーのために全員が払う**。
読むのは lazy な 2 本（`aviation-live` 経由と `engine-select` の動的 import）だけ。

### 4. MapLibre — 凹な多角形の SDF

ダートは「3つの半平面の max」で書けた。プランフォームは書けない。
**胴体の両脇、そして翼と尾翼の間——凹が4か所あり、それがシルエットそのもの**だからで、
凸の式ではそこが全部「外側」になる。

```glsl
float planeSD(vec2 p){          /* 18辺の最近点距離で大きさ、交差判定で符号 */
  float d = dot(p - PLANE[0], p - PLANE[0]);
  float s = 1.0;
  ...
    bvec3 c = bvec3(p.y >= PLANE[i].y, p.y < PLANE[j].y, e.x * w.y > e.y * w.x);
    if (all(c) || all(not(c))) s = -s;
  ...
}
```

頂点は `${GLYPH.glsl('PLANE')}` で**生成**する——シェーダと canvas が小数点1つ分ずれる余地を
残さないため。塗りと縁は `ctx.fill()` → `ctx.stroke()` の意味をそのまま再現した
（source-over。**帯の内側半分は「機体色の上の白」・外側半分は「何も無い上の白」**で、
この2つは同じ画素ではない。2領域に分ける近道はその差を全部の縁で失う）。

精度は `mediump` から `highp` へ上げた。18 辺のうち最短は 0.09 単位で、fp16 では危ない。

### 5. Cesium — 乗算ブレンドは「色付きの機体＋白い縁」を1枚で作れない

billboard のテクセルは**自分の色と乗算**される。だから白1枚を機体色で染める #R341 の作りでは、
**縁だけ白く残すことが原理的にできない**。しかも機体色は高度の連続ランプなので、
色ごとにスプライトを焼き込むパレット方式も採れない。

⇒ **1機につき 2 枚**：縁の環（白で染める）と中身（機体色で染める）。
2枚は**重ならない**——中身は輪郭を縁幅の半分だけ内側に縮めたもの、環は `ctx.stroke()` が塗る
まさにその環——なので、**どちらを先に描いても絵は変わらない**。#R192 が 3-D の機体で
「重なる2枚は深度バッファに解けない引き分けを頼む」と書いたのと同じ答え。

⚠ ただし**アンチエイリアスの継ぎ目**だけは重ねる必要がある。中身を正確な内側の位置で切ると、
2つの半透明な縁が出会うところに**背景のヘアライン**が出る。中身を **0.5 画素だけ太らせて**
下に潜り込ませてある。

### 6. 大きさ — 形だけ戻すと別の絵になる

| | z5 | z9 以上 |
|---|---|---|
| 元のマーク（全長・CSS px） | **26.8** | **36.1** |
| #R341 のダート | 9 | 19（z11）／24（z14） |

高ズーム側の値は**ここで選んだ数字ではない**。`icon-size` が掛けていた元の表（44 × icon-size）を
`IntMapPlaneGlyph.boxPx(z)` がそのまま返す。**z9 で頭打ちなのも、元の表の最後の段が z9 だから**——
z14 まで育ち続ける飛行機は元のマークの一部ではなかった。

低ズーム（z0–5）は意図的に従来のまま。**旧レイヤーは 4,000 機で打ち切り z2 未満では消えていた**ので、
数万機を同時に描く世界表示という状況を一度も持っていない。そこに 22 px のマークを並べると
艦隊ではなく染みになる。

⚠ 利用者に選択肢を示したとき「z5 で 27.6・z9 で 37.1」と書いたが、**正しくは 26.8 と 36.1**。
全長を 2×19 で計算していたのが誤りで、機首は中心から 19・尾は 18 なので全長は 37 単位である
（−2.7%）。比も結論も変わらないが、記録は実測のほうに合わせてある。

### 7. 門 — なぜブラウザ検査でなければならないか

`js/aircraft-points.js` はシェーダの失敗を catch し、1回警告して return する。
**コンパイルできないプログラムは何も描かず、何も描かないレイヤーは「誰も ON にしていない
レイヤー」と同じ顔をする。** #R353 が火山の輪でこれを実測している。ダートの場は半平面 3 本
だったが、これは 18 頂点のループと交差判定——**ドライバが拒否しうる種類のシェーダ**であり、
ソースを読む検査は 1 つもそれに気づけない。

`tests/r379.spec.js` は**合成の 1 機を自分で publish** して（ライブのフィードに依存しない）、
プローブを ON/OFF して画素を差分し、行ごとの幅を測る：

- 翼はスプライトの 60% 以上を張る
- **翼より後ろに行がある**（ダートは最も広い行が最後の行）
- 翼の後ろに**胴体だけの細い部分**がある（翼幅の 1/3 未満）
- **そこからまた広がる**（尾翼、細い部分の 1.5 倍超）

**「狭い→広い→狭い→広い」はダートには作れない。** 4本とも落ちる。

⚠ **最初の版は自分の計器のほうが間違っていた。** 行の割合を「いちばん上の変化した行」から
測っていたが、**機首は1画素の点で、そのアンチエイリアスは差分の閾値を越えない**。`top` が
胴体の数行下から始まり、「胴体」として標本した行はもう翼根だった（実測 32 px、胴体は 9.5 px）。
⇒ **検出のいらないアンカー（最も広い行・最後の行）から測る**ようにした。
