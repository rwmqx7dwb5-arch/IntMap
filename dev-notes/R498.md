## R498 — **指の経路が、指が動くたびに DOM を測っていた**

依頼は1本の調査結論だった。「スマホで地図が重くなる最大の理由」として、`touchmove` ごとのレイアウト計測と、
クロスヘア処理の書き込み後の読み取りが**現行コードに残っている明確なホットパス**として名指しされていた。
そのとおりだった。そして**同じ形が5か所にあった**——「ポインタの性質ではない値を、ポインタが動くたびに
訊いている」。

### 1. 長押し判定が `touchmove` ごとに canvas を測っていた

`js/app-body.js` の長押しハンドラは、`touchstart` で `canvas.getBoundingClientRect()` を取って
`startPt = {x: clientX − rect.left, …}` を作り、`touchmove` で**もう一度**矩形を取って

```
dx = touches[0].clientX − rect.left − startPt.x
```

を計算していた。`startPt.x` 自身が `start.clientX − rect.left` なので、**2つの `rect.left` は打ち消し合う**。
つまりこの矩形は、**自分自身を引くために**、指が動くたびに測られていた。

⚠ **そして「長押しを諦めたあと」も測り続けていた。** 12 px を越えると `cancel()` がタイマーを消すが
`startPt` は残り、ハンドラの唯一の早期 return はその `startPt` を見ていた。だから
**1 touchstart ＋ 100 touchmove ＝ 101 回**の強制同期レイアウトで、**そのうち 100 回は、もう存在しない
長押しのため**だった。

⇒ 開始点を**クライアント座標**で持ち、クライアント座標どうしで比べる（矩形は不要）。`cancel()` は
**武装を解く**ので、残りの `touchmove` は最初の行で戻る。しきい値は同じ（`hypot>12` と
`dx*dx+dy*dy>144` は同じ述語）、550 ms も同じ、メニューへ渡す `startPt` は canvas 相対のまま
（`unproject` が要るのはそれ）。

### 2. クロスヘアが、1つのコールバックの中で「書く→測る→書く」をしていた

`js/runtime.js` の存在理由は、ヘッダにそう書いてある——**「READS BEFORE WRITES … so that the layout
that used to be recomputed N times a frame is recomputed once」**。ところが携帯のクロスヘアのカメラ仕事は
**既定の WRITE 相**に1本で登録され、その中で

1. `cross.style.display` と `btn.style.display` を書く
2. `mc.getBoundingClientRect()` を読む
3. `getComputedStyle(mc)` で `--sheet-cover` を読む
4. `unproject` して座標文字列を書く

をやっていた。**位相を分ける仕組みの内側に、位相分割が見えない強制同期レイアウトが入っていた。**
1 と 2/3 は、`touchmove` ごとの矩形読み（上）と交互に起きる。

⇒ 3つ直した。**どれも1ピクセルも変えない。**

- タスクを Runtime 自身の継ぎ目で割る——`phase:'read'` の半分が中心の経緯度を採り、WRITE の半分が
  `display` と読み出し文字列を書く。
- コンテナの箱は **ResizeObserver**（`js/map-tooltip.js` が #R311 で採った計器・同じ理由）。
- `--sheet-cover` は `js/mobile-ui.js` が**インライン宣言**として書くので、**そのインライン文字列
  （＋ `document.body.className`）が変わったときだけ** `getComputedStyle` を引き直す。
  ⚠ `getComputedStyle` のままなのは、`js/playground.js` が `body.pg-we{--sheet-cover:0px !important}` を
  書くから——インライン値だけ読むと、`!important` で上書きされている場合に**別の答え**を返す。
- `style.display` は**値が変わったときだけ書く**（同じ文字列の代入もレイアウトを無効化する。#R311 が
  ツールチップの `left`/`top` で学んだのと同じ欠陥）。

**実測**（`tests/r498-checks ②`。シップされたブロックを vm で走らせて数える）: 最初のフレームのあと
**60 フレームで `getBoundingClientRect` 0 回・`getComputedStyle` 0 回・`display` の書き込み 0 回**、
読み出しは 61 回以上（＝仕事は移しただけで、落としていない）。

### 3. この2本は、どの計器からも見えていなかった

`scripts/mobile-trace.mjs` の `pan` / `zoom` は `IntMapGeoEngine.camera` の `panBy`/`easeTo` である。
それは #R352 が**マウス**について正しく決めたこと（合成 `MouseEvent` は MapLibre のハンドラに届かない）
だが、**カメラ命令は `touchstart` も `touchmove` もピンチ認識も生まない**。だから
**この repo が持つ携帯の数字は全部、アプリ自身の touch ハンドラが一度も呼ばれないまま取られていた** —— 1 と 2 の
寄与は、どの fps にも **ちょうど 0** として入っていた。

⇒ `Input.dispatchTouchEvent`（trusted touch）で駆動する相を足した: **`pan-touch`・`pinch-touch`
（2点）・`pan-alerts-city`**。座標は canvas 自身の矩形から取る（#R352 のもう半分）。
この3相だけが、カメラ命令には出せない2つを出す:

| 列 | 何か |
|---|---|
| `rect/move` `style/move` | **touchmove 1回あたりの** `getBoundingClientRect` / `getComputedStyle` 回数。`fps` は強制同期レイアウトを他のミリ秒と区別できない。これはできる |
| `lat p50/p95/max` | touchmove →それに答えるフレームまでの ms。「指に付いてこない」を測定として述べたもの |

⚠ **Chromium だけ**（CDP は Playwright の WebKit に無い）。WebKit 側では**この相が「無い」と印字**される
——0 ではなく（#R322 の規則）。

### 4. #R232 は「携帯か」を端末の問いにしたが、3か所しか動かしていなかった

#R232 は正しい規則を立てた——「携帯か」は**端末**の問いで、768 px のメディアクエリは横向きで嘘をつく——
そして `antialias` / `pixelRatio` / `maxTileCacheSize` に適用した。**それ以外は幅のまま**だったので、
**横向きの iPhone（844 px）**はこれを全部払っていた:

| 何 | 横向きで起きていたこと |
|---|---|
| `_hiDPITiles` | @2x の CARTO タイルと @2x の Esri stitch＝**1タイルあたり 512²・4倍のピクセル**を復号して GPU へ上げる |
| `maxCanvasSize` | 4096² の RAM ガードではなく GPU の上限（最大 8192²） |
| 毎フレームのマーカー遮蔽 | #R33 が「毎移動で最も重い」と測って携帯で切ったもの——ドラッグの全フレームで復活 |
| `_DEM_CACHE_MAX` / DEM 先読み | 140→560、settle ごとに 49 点の DEM 読み |

⇒ 5か所とも `_imPhoneClass()`（#R232 の述語の改名——「携帯 GPU か」より広い問いになったので）。
⚠ **`maxZoom`（携帯 18／それ以外 19）は幅のまま**にした。ここで分かれているのは費用ではなく
**到達できる能力**で、横向きの端末から 1 段取り上げるかどうかは性能の判断ではない（確認して据え置き）。
⚠ **レイアウトの問いも幅のまま**——`isMobile()` はシート・クロスヘア・携帯用読み出しを駆動していて、
片方だけ端末に移すと**横向きの携帯が読み出しを1つも持たない**状態になる（デスクトップ側は
クロスヘアが担当する場面で早期 return する）。

### 5. #R311 の「同じ markup なら書かない」を使っていたのは1ファイルだけだった

`setMapTooltipHTML` は #R311 が**まさにこのため**に足した——ポインタが同じフィーチャの上に留まっている
間、毎 mousemove で同一文字列を `innerHTML` に入れると部分木が作り直され、レイアウトが無効化され、
直後の `positionTooltip` の `offsetWidth` が**強制リフロー**になる。採用していたのは
`js/news-ui.js` だけで、**他に14か所**が `el.innerHTML=` を直に書いていた
（`js/data-layers.js` ×9・`community-board`・`layer-packs`・`satellites-live`・`wb-layers`・`world-packs`）。
全部 `window.setMapTooltipHTML(el, html)` へ。**DOM は同一**——同じ文字列のときに書かないだけ。

⚠ **ホバーの「いま見えているレイヤー一覧」も、ポインタの性質ではない。** #R195 は26回のヒットテストを
1回にしたが、`ids()` の走査——登録数ぶんの `getLayer` ＋ `getLayoutProperty`、この枝は **74 登録**——は
ポインタ経路に残っていた。一覧が動くのは**スタイルが変わったとき**と**登録が変わったとき**だけなので、
その2つで無効化するキャッシュにした（実測: 50 移動で追加 0 回、`queryRenderedFeatures` は 1移動1回のまま）。
⚠ **合流させるのはフレーム内の2件目以降だけ。** #R195 は同期配送を意図して選び、理由も書いてある
（「ツールチップが、それを起こしたイベントで出る」・#R182）。だから**フレーム最初の1件は同期のまま**で、
同じフレームに来た残りだけが最新1件に畳まれて次のフレームへ回る。60 Hz では何も変わらない。

### 6. 衛星の大気が、毎フレーム 256 段の積分を2本回していた

`js/theme-sky.js` の `_skyFollowCamera` は `_horizonColour()` と `_skyColour()` を呼ぶ。どちらも
`js/sky-model.js` の **N=256 の視線マーチ ＋ M=8 の太陽サブマーチ**である。#R220 の注記はこう書いてある
——「Nothing draws per frame from here」「four times per camera settle … against a 60-second re-aim
interval」。**#R234 がこの follower を毎フレームのカメラ登録に載せた時点で、それは偽になっていた。**
実測（node で `js/sky-model.js` を直接）: 多重散乱テーブルの初回生成 **17.5 ms**、以降 **1色 0.23 ms**
＝ 毎フレーム **0.47 ms**、デスクトップ CPU で。

⚠ **#R234 が毎フレーム必要としていたのは安いほうである。** 報告は「ズーム中に大気が消える」で、原因は
`_limbOwnsRim()`（真偽値と高度1つ）が `moveend` でしか訊かれていなかったこと。#R241 の `_airAtZoom` も
#R240 の re-aim も `setLimb` / `setLight` が1回ずつ。**3つとも毎フレームのまま**にして、いまは
**先に**走る。

⇒ 色の2本だけを2段で守る。**どちらも画質を下げない。**

- **メモ化**——モデルは（中心の太陽高度・視点高度・相対方位）の**純関数**なので、同じ3つなら同じ2色。
  近似ではなく**同一**である（`tests/r498-checks ⑥` がその純粋性を測る）。
- **ジェスチャ中は 100 ms 間隔**、そして**ジェスチャが終わるフレームでは必ず計算する**。読者が
  最後に見る絵は、いままでどおり**そのカメラから厳密に**計算される。ドラッグ中は全画面グラデーションが
  60 Hz ではなく 10 Hz で更新される——同じ積分・同じ定数で、**訊く回数だけ**が変わる
  （#R229 の線引き：重複を消すことと、フレームを買うために品質を静かに落とすことは別）。

### 7. コメントの分だけ、面をシェルの外へ出した

この 6 つの説明は `js/app-body.js` を **124 行**太らせた。shell 予算（`tests/r168 #8`・その2枚目の
写しである `tests/r479 ⑧`＝**8,050 行未満**）は `origin/main` で **8,049 行**——**残り 1 行**だった。

⚠ **天井は上げない。**「ceiling follows the floor DOWN、通すために上げない」は #R194/#R195/#R196 が
書いた規則である。そして**コメントを削って払うのも間違い**——今回いちばん壊れやすいのは
「なぜこの読みが要らないのか」という説明のほうで、それを消したら次のラウンドが同じ `rect` を書き戻す。

⇒ #R311 がホバー用ツールチップでやったのと同じ払い方：**面をまるごと外へ出す**。
`js/mobile-map-input.js`——長押し・クロスヘア・中心の読み出し・「地点を追加」ピル。**1 つの面である**
（携帯の述語・コンテナの箱・「シートに覆われていない領域の中心」規則を共有する）。
幾何は 1 文字も打ち直していない。変わったのは、クロージャが供給していた 10 個の名前
（`toolMode` / `isMobile` / `renderCoordReadout` / `demElevAt` / `elevText` / `lastElev` /
`updateLayerReadout` / `handleMapClick` / `showContextMenu` / `currentLang`）が **HOST 経由**になった点だけ
——移した先でクロージャ名を継ぐと、**落ちずに枝ごと黙って飛ぶ**（#R162・`scripts/check-split-scope.mjs`）。

⚠ **マウント点は2つのまま**。`longPress()` は地図イベント配線から、`crosshair()` は約 2,400 行あとの
位置から呼ぶ——どちらも canvas やウィンドウにリスナーを張るので、**隣との登録順が観測可能**である。
1 つにまとめれば 2 行節約できるが、片方が動く。

**結果: shell は 8,049 → 8,024 行**（天井 8,050）。**このラウンドは足したのではなく、25 行返した。**

### 実測（A/B・同じ機械・同じ replay キャッシュ・chromium 390×844 DPR3 cpu 1×・各1 rep）

新しい相そのものが A/B の道具である。変更前のソースで dist を作り直し、**同じ計器**で測った。

| 相 | `style/move` | `rect/move` | lat p50 / p95 |
|---|---|---|---|
| `pan-touch` 前 | 1.12 | 9.59 | 4.3 / 8.4 ms |
| `pan-touch` 後 | **0** | **7.47** | 4.9 / 9.4 ms |
| `pinch-touch` 前 | 1.11 | 9.94 | 4.0 / 5.9 ms |
| `pinch-touch` 後 | **0** | **7.83** | 3.5 / 5.5 ms |

**`style/move` は 3 相すべてで 0 になった**（実数で 38 / 40 / 19 回 → 0）。これは構造的な結果である
——毎フレームの `getComputedStyle` は、シートが動いていない限りもう呼ばれない。
`rect/move` は −22 % / −21 %。⚠ **この列は phase 全体 ÷ touchmove 数**なので settle 中の DOM 仕事も入る
（ページ全体のラッパで数えているので、地図以外の要素も含む）。**指の相は 2 rep とも小数点まで同一**
（7.47 / 7.83）だったので、この 2 つは再現する。

⚠ **警報レイヤーの相については、この環境では何も主張しない。** `pan-alerts-city`（z11・16 移動の短い
指ドラッグ）は busy 7.0–7.5 s・35–41 fps で、**このラウンドで速くなっていない**——それどころか
`rect/move` は前 300 に対して後 523 / 610 と **2 rep の間で 17 % ばらついた**。原因は判っていないが、
両腕とも replay キャッシュが冷たく（`MISSES WERE BLOCKED`、blocked 7,955 / 8,343 / 9,948）、
到着した警報データの量が run ごとに違う。**1 rep ずつでは比較になっていない**ので、
「警報レイヤーは依然としてこの相の支配的な費用である」以上のことは書かない
（#R387 が 12,063 ms / 34.2 fps を測ったのと同じ層で、そこは**手つかず**である）。

### 検査

`tests/r498-checks.test.mjs`（14 本）。①②④は**シップされたコードを走らせる**——`js/app-body.js` の
長押しブロックとクロスヘアブロック、`js/geo-engine.js` の `_hoverHub` を切り出して vm に入れ、
**レイアウトの問い合わせ回数を数える偽の canvas / コンテナ / カメラ登録簿**に対して実行する。
正規表現は「その呼び出しが行から消えた」しか言えないが、走らせれば「**しきい値は同じで、メニューは
いまも 550 ms で出て、DOM には1回しか訊かない**」まで言える。
⚠ **反証も測った**: 変更前のソースに対して同じ13本を走らせると **11 本が赤**（緑のまま残る2本は
「長押しはいまも出る」「モデルは純関数」＝**両方で成り立つべき不変条件**）。
