〈依頼〉時計（Chronos）で年や日付を動かすと、その時点の国境・都市名・地方区分を取り直すまで待ちが出る。隣の時点を先に取れば速くなる見込みだが未測定。まず計器を作り、待ちの原因を特定し、先読み（または原因の修正）を入れ、前後の数字を示す。歴史地図の正しさは落とさない。

## 0. 計器

- **「描いた」は描いた当人が言う。** `IntMapTime.drawn(layer, when)` / `drawnState()`（`js/chronos.js`）。国境（`js/time-borders.js` の `apply` と同じ集合の再表示）、地方区分の各段（`js/time-admin1.js`、`subdivisions:a1` など）、都市名（`js/hist-cities.js`。ラベル書き手がこの時点のエポックの式を受け取ったとき）が、地図へ渡した瞬間に「どの時点を渡したか」を残す。ソースの件数を数える観測器は、空のソースと前の時点を持ったままのソースを区別できない。
- `scripts/chronos-latency.mjs` が build 済みのサイト（年で切ったタイルは build にしか無い）で時計を 1 歩ずつ動かし、層ごとに「時計が動いてから当人が渡すまで」と「地図が `idle` になるまで（描き終わり）」と、その歩で読んだバイトを測る。4 本の歩み（CShapes 前進・後退、OHM 前進、深い過去を 10 年刻み）× 6 歩、各歩の後に 1 秒の間（読者が年を眺める時間の見積もり）。
- ⚠ **headless の既定 GPU（SwiftShader）では描画を測っていた。** 同じ 1 年送りで国境が 2.6 s、ページのスレッドの大半が native の描画。機械の GPU（ANGLE D3D11）では 0.9 s。計器は既定で GPU を使う（`--swiftshader` で旧来）。

## 1. 原因（1900→1901、GPU、ローカル配信）

| 区間 | 時間 | 中身 |
|---|---|---|
| 時計 → 国境が扉に問う | 約 240〜310 ms | `setYear` の同期分（都市名の式と `setLayout` で約 100 ms）＋ 45 ms の合流 |
| 国境の問い | 約 250 ms | CShapes → OHM 後期 → Cliopatria → 海岸の印、記録ごとに `need` → Range 読み → `feed` → `at` を**直列** |
| 国境を渡す → 地方区分が扉に問う | 約 0.4 s | 解決済みの 2 つの Promise の `await` が、先に積まれた MapLibre の国境の取り込み（ページのスレッド）の後ろで待つ |
| 地方区分の問い | 約 0.1〜0.55 s | Range 5 本・`feed` 5 回を Worker が直列に。この間ページのスレッドは**空いていた** |
| 渡す → 描き終わり | 1〜5 s | MapLibre が数 MB の GeoJSON を取り込み描く（この変更の外） |

1 歩で読むのは 30〜180 kB で、ローカルの往復は数十 ms。待ちは通信量ではなく、**読む → 解く → 答えるが記録ごとに直列で、しかも国境の取り込みでページが詰まっている間に Worker と通信が遊んでいる**こと。

## 2. 直したこと（`js/hist-bundles.js`・`js/time-admin1.js`）

1. **一歩先**（`follow`）。1 つの記録が `at(a)`、`at(b)` と訊かれたら `at(b + (b − a))`（月日が同じなら年、違えば日の歩幅）が読むチャンクを Worker へ読む。答えず、ページの写しにも載せない。1 接続だけの別の列で、訊かれた読みが待っていれば始めず、読者がもう先へ進んでいれば捨てる。`maySpeculate` が否なら読まない。保持の上限は記録そのもの（チャンクは元々捨てない）。
2. **受け渡しの瞬間に読む**（`warm`）。地方区分は国境を地図へ渡した瞬間に、その時点のチャンクを Worker へ読み始める。国境が先という順序（deep-tier-reds）は保つ。
3. 先読み・`warm` の読みが失敗したら、それを待っていた問いは自分で読み直す（全体読みへ戻らない）。

どの行を描くかは訊かれた時点の `rowsFor` が決めるので、読んだ時点が別の時点に混ざる経路は無い。それを回帰で固定した（§4）。

## 3. 前後（同じ build で `--before` と交互に 3 回ずつ、6 歩の中央値の中央値）

| 歩み | 国境 | 地方区分 | 描き終わり |
|---|---|---|---|
| CShapes 前進（1901〜） | 431 → 292 ms | 978 → 702 ms | 3.76 → 3.06 s |
| CShapes 後退 | 437 → 312 ms | 1058 → 783 ms | 3.39 → 3.30 s |
| OHM 前進（1751〜） | 305 → 260 ms | 666 → 608 ms | 2.41 → 2.20 s |
| 深い過去・10 年刻み | 360 → 279 ms | 543 → 419 ms | 1.57 → 1.32 s |

測った機械では他セッションの build が 7 本同時に走っており、1 回ごとのばらつきが大きい。数はローカル配信なので、往復が数十〜百数十 ms ある本番では読みの分の差はもっと大きいはず（本番では測っていない）。

**残っている最大の待ちは「渡してから描き終わるまで」の 1〜5 s**——MapLibre の GeoJSON 取り込み（ページでの複製と Worker での再索引）。年の差分だけを渡す（`updateData`）などで縮む見込みがあるが、描画の受け口（`js/geo-engine.js`・Cesium）にまたがる別の仕事なので手を付けていない。都市名は 1 歩 50〜90 ms で、待ちの原因ではなかった。

## 4. 検査

- `tests/chronos-prefetch-checks.test.mjs`（8 件）: 一歩先の算術、先読みあり／なしの 2 つの扉で同じ歩みを歩き**答えとページが持つ行・環が完全に一致**すること、続けた歩は自分で何も読まないこと、`maySpeculate` 否で読まないこと、先読み・`warm` の読みの失敗が答えの失敗にならないこと、本物の第 2 スレッド。
- 混ざらないことの検査が生きているかを変異で確かめた: 先読みした時点を `at` で答えてページへ送る扉にすると「1903: the page holds other rows than the same walk without the read-ahead」で落ちる。
- 否定された見立て: 「隣の時点の通信を先に取れば大きく縮む」——ローカルでは 1 歩の通信は数十 ms で、効いたのは直列の解消と、ページが詰まっている間に Worker を働かせたこと。
