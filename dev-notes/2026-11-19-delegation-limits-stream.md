〈依頼〉 本番で委譲を計測して見つかった原因を直す。

## 0. 測った（本番 2026-11-19・ビルド印 734d229・資源輸送ルートの依頼 1 回）

- Atlas は自分から `research.delegate` を使い、原油・鉄鉱石と石炭・LNG の 3 件に分けた。
- 原油は 200、58.3 秒、実費 $0.12、出典 10 件。
- 鉄鉱石と石炭は 409 `delegation_children`（サーバの上限は 2）。
- LNG は 503 `provider_unavailable`、90.7 秒。
- ターンは 10 分を超えても終わらなかった。台帳 `ai_turns` を見ると、親は `calls 12`（`TURN_MAX_CALLS`）を使い切っていた。実費は家族全体で $1.01。
- LNG の子の行は払い戻しで消えていて、なぜ失敗したかは記録に無い。90.7 秒は Web 検索の期限 `WEB_TIMEOUT` 90 秒（`providers/openai.ts`）に近い。ただ、期限切れのあとの検索なしの答え直しが 0.7 秒で終わった理由は分からない。
- **否定した見立て**: 「子は 55 秒で切られ、ストリームなら防げる」は誤りだった。Web つきは 90 秒で、ストリームでも期限は同じ（`relay-guard.js` の `onChunk` の注記）。だからストリーム化はしていない。

## 1. 直したもの

- ai-proxy は Atlas のターンの応答に、毎回 `meta.delegationPolicy` を載せる。ページはそれを覚え、ターンの文脈で Atlas に上限を伝える。
- `research.delegate` は、上限を超える件数や `off` を、費用を使う前に `too_many_tasks`（上限の数つき）や `delegation_off` で返す。どの仕事をまとめるかは Atlas が決める。
- 子の失敗は、サーバが述べた理由（時間切れの有無と HTTP ステータス）を `detail` で運ぶ。

## 2. 残っていること

- LNG の 503 の本当の原因は、次に起きたときに `detail` で分かる。
- 親が 12 回を使い切った件は、委譲とは別の、Atlas の 1 ターンの手数の問題。直す前に測り直す（この変更のあと、同じ依頼で）。

## 2b. 容量の上限（check:perf）

- `eager.modules` が 908 から 909 になった。この PR では起動時のモジュールは増えていない。2026-11-18 の main（`025caa33`）のビルドと比べると、増えたのは `js/antimeridian-seam.js` と `js/hist-sheet-pick.js` で、どちらもこの PR の土台にした main の別の作業が足したもの。上限が実測より 1 つ少なかったので、`perf-budget --update` で超えた行だけを実測まで上げた。

## 3. 検査

- `tests/atlas-delegation-checks.test.mjs` ⑭〜⑯ を追加した。失敗の理由、上限を超えたときに費用を使わず数を返すこと、応答が方式を述べることを確かめる。
- ai-proxy の写真を撮り直した。差分は `delegationPolicy` だけ。
