## R790 — 添付ファイルは、読み取った瞬間に末尾を捨てていた——取り寄せても戻らない理由

〈利用者の指摘「Atlasに添付したファイルは、長すぎると先頭部分しか読み込んでくれない問題をどうにかして」〉

### 1. 原因

`js/atlas-attach.js` の `textDesc()` が、ファイルを読み取った**その場**で `LIMITS.textPerFile`
（120,000 字）を超える分を `slice` して捨てていた。#R773 が作った `attach.recall`（一度手放した
添付を取り戻す道具）で同じファイルを取り寄せても、台帳（`js/atlas-attach-log.js`）に載っていたのは
既に切り詰められた同じ先頭だけ——**取り寄せが「もう捨てたものを取り寄せる」という、届きようのない
依頼になっていた**。カタログの説明文（`js/atlas-catalog-text.js`）も「テキスト添付は常に全部届く」と
Atlas に誤って伝えていた。

xlsx の複数シート・名前を持たない ZIP（epub 等）は、抽出そのものの予算にも同じ `textPerFile` を
流用しており、2 件目以降のシート／エントリが丸ごと抽出されないことがあった（docx/pptx/odf/kmz は
元から抽出時にこの予算を見ていなかったので無傷だった）。

### 2. 直したこと

- `textDesc()`: 読み取り時には切らない。全文を保つ。`truncated` は「自動で送る量より長い」という
  情報フラグに意味を変えた（消えたことの印ではない）。
- 抽出予算（xlsx・汎用 ZIP）: `LIMITS.textPerFile` ではなく、読み取り自体の ceiling
  `LIMITS.readBytes` を流用——docx/pptx/odf/kmz と同じ「全量抽出」に揃えた。
- `js/atlas-attach-log.js`: `page(rec, offset, limit)` を新設し、`carry()`（毎ターン自動掲載）が
  これで先頭 1 窓だけを切り出すようにした。台帳自身は全文を持ち続ける。
- `attach.recall`（能力・`js/atlas-console.js` の dispatch）: `offset` を受け取れるようにし、
  応答の `exec` に `offset`/`next`/`total`/`more` を積んだ。`more` が真の間 `offset:next` で
  呼び直せば、長いファイルの残りを窓ごとに読み進められる（画像・PDF は無関係、丸ごと戻る）。
- `js/atlas-schemas.js`: `attach.recall` のスキーマに任意の `offset` を追加。
- `js/atlas-catalog-text.js`: 「テキストは常に全部届く」という誤った前提を消し、窓と `offset` の
  使い方を説明する文に差し替えた。
- `js/atlas-file-view.js`: 「先頭部分のみ送信」という、直った今では誤りになる文言を
  「自動で送るのは先頭部分のみ。続きは尋ねれば読み込みます」に改めた（5 言語）。

### 3. 検査

`tests/r790-atlas-attach-full-text-checks.test.mjs`（新規・7件）。既存の `tests/r540-checks.test.mjs`・
`tests/r773-atlas-attach-preview-checks.test.mjs`・`tests/r783-attach-recall-checks.test.mjs`
（計31件）は無改造のまま全て緑——枠の値（`textPerFile`=120,000／`textTotal`=400,000）自体は
変えていない。

この PR を merge しようとして発見（この回の主題とは無関係）。`.github/workflows/db.yml` は

## 1. ⚠⚠⚠ 「Static checks」は 28 個のゲートを 1 台で直列に回していた

実測（run 35172906802・570 秒）の分布は平らではなく、頭が 4 つある長い尾だった:

```
check:histfill 176s · check:assets 115s · check:bordercoast 79s · npm run build 42s
check:i18n 39s · check:static 26s · check:docs 14s · check:borderdetail 12s
…残り 20 個の合計が 21s
```

⇒ この job は「28 個ぶん長い」のではなく「**histfill ぶん長い＋その他**」だった。
`scripts/ci-gates.mjs` が集合を 3 台へ詰める。**被覆は 1 ミリも落ちない**（全ゲートが 1 回ずつ走る）。
予測 **最長 178 秒**（直列 533 秒）。

- ⚠ **一覧を書かない。** ゲートは `package.json` の `check:*` から**発見**する
  （[[intmap-gate-universe-is-declared-gates]] と同じ母集合）。「どのゲートがどの台か」を CI に
  手で書くのは `.agents/rules/no-ad-hoc-hardcoding.md` §1 の埋め込み一覧で、**足した日に黙って
  古くなる**——しかも壊れ方が最悪（**新しいゲートが走らないまま CI が緑**）。
  `--check` が「bin が宣言集合の**分割**であること」を測る。
- ⚠ **build を読む 2 つも発見する。** 各ゲート自身のソースが `dist/` か `.perf/build-report.json` を
  literal で名指しているかで判定し、**build ごと 1 つの task** にまとめる（build を 2 回払わない）。
  実測でちょうど `{check:perf, check:assets}`。**失効条件**: この regex が見えない書き方で build の
  出力を読むゲートが現れた日。そのときは**黙って落ちず**、dist/ 無しで走って自分の理由で赤くなる。
- ⚠ **1 つの shard は最初の赤で止まらない。** bin を最後まで走らせて**落ちたゲートを全部一緒に
  報告**する（`fail-fast: false` と合わせて、1 回の run で全部の赤が出る）。これが
  「1 つ直して 12 分待ってまた別のが赤」を消す。
- ⚠ **必須チェックの名前は matrix の脚にできない**（#R586 と同じ理由）⇒ 集約 job が
  ruleset の要求する `Static checks` の名を持つ。
- コストの台帳 `.github/gate-cost.json` は**均衡だけ**を決め、**所属は決めない**
  （載っていないゲートも中央値で計画されて走る）。測定日と run id を自分で述べる。

### R621 — **#R585 の凡例は本番で空で、観測局のポップアップは一度も開いていなかった**

〈#R585 の production verification。ローカルの検査は全部緑、CI も全部緑、コンソールにもエラー無し〉

### 1. ⚠⚠⚠ 出ていなかったのは、レイヤーが存在する理由そのものだった

本番で `#data-legend-imrad-obs` の箱は出る。中身は **`innerHTML` の長さ 0**。
色スケールも、どの観測網が答えたかの一覧も、そして4つの注意文——
**「50〜200 nSv/h はほぼ全世界で通常の自然放射線量」「降雨だけで最大3倍」「大半は未検証」
「1局が高いことは放出の証拠にならない」——が、1つも表示されていなかった。**
読者には**放射線の点だけが、注意書き無しで**見えていた。

原因は 1 行の形:

```js
S(L(LA('50–200 nSv/h is normal…', '50〜200 nSv/h は…', …)))
```

**`pick()` は位置引数を取る。** `arguments[0]` を英語鍵として他言語を引く。
`pickArgs()` が作るのは**配列**なので、それを渡すと**配列がそのまま返る**。
その配列が `.split('{n}')` に届いて TypeError になり、**囲みの `try/catch` が飲んだ**ので
`key.innerHTML = …` に一度も到達しなかった。

### 2. ⚠⚠⚠ ポップアップは一度も開いていなかった

`GE().popup({lngLat, html})` は**存在しない扉**である。レンダラ契約は
`GE().ui.popup(options)` を返し、`GE().ui.attach(...)` が地図に載せる
（`js/app-body.js`・`js/atlas-console.js`・`js/beta-overlays.js` の全呼び出し側がその形）。
この回は 1 呼び出しの形を**発明し**、`undefined` への呼び出しになり、`try/catch` が飲んだ。
結果、**値も時刻も量も出典もライセンスも履歴も、そして 720 局ある「検出器の下限未満」の説明も、
一度も画面に出ていない。**

### 3. ⚠⚠⚠ 検査が見えなかったのは「不十分」だからではない——**そう作られていた**

**言語の stub は、バグを通り道で直していた。** テストの中では文字列に見え、ブラウザでは配列だった。
レンダラの stub は手書きなので、**そもそも存在しない扉**をいくらでも持たせられる。
⚠ **実物より高機能な fixture は、その欠陥を原理的に見られない**（#R552 と同じ。今度は 2 か所で同時に）。
