## R576 — **外部データ投入が GeoJSON で止まっていたのは、判定が「拡張子の一覧」だったから**

> 「外部データ投入がGeoJSONで止まっている。GeoJSONアップロード自体は既にあります。ただ、KML / GPX /
>   CSV座標 / Shapefile / PMTilesあたりはRepo検索では見つかりませんでした。特にCSVをドラッグ →
>   緯度経度列を自動認識 → 即ピン化はIntMapにはかなり合います。」

### 1. 実測 — 入口は 6 つあり、地理データが通れるのは 1 つだけだった

全数調査（`git grep` 母集合 2,946 追跡ファイル）の結果:

| 入口 | 何を受けるか |
|---|---|
| Atlas 添付（`js/atlas-console.js`） | **バイト列で判定**（#R540 の `ATL_FILE`）。`accept` 無し |
| **地図への取り込み（`js/map-ui.js:2220-2277`）** | **`JSON.parse` だけ**。58 行 |
| 写真ジオロケータ / 投稿画像 / アバター | `/^image\//` |
| `admin.html` | `.html` |

地図の取り込みは `accept='.geojson,.json,…'` と名乗りながら、実際にしていたのは
`FileReader.readAsText` → `JSON.parse` → 4 つの GeoJSON の形に正規化、だけだった。
**サイズ上限も、件数上限も、座標の妥当性検査も、永続化も無い。**
KML/KMZ/GPX/CSV/TSV/Shapefile/PMTiles/WKT/GeoPackage という綴りはリポジトリに出るが、
**取り込み経路としては 1 つも無い**——エクスポート（GPX・CSV）、外部タイル URL（PMTiles）、
ビルド時の Node 専用リーダー（GeoPackage）、Atlas 添付のテキスト抽出（KMZ）のいずれかだった。

### 2. 本当の欠陥は「読めない」ではなく「1 文で嘘をつく」

読めなかったものは全部これを言われていた:

    「有効なGeoJSONではありません」

KML に対しても、GPX に対しても、港湾の CSV に対しても、Excel が吐いた Shift_JIS の表に対しても。
**4 つとも間違いである。** しかも 3 つ目と 4 つ目は、このアプリが**すでに読める部品を持っていた**。

⚠ **#R540 は同じ問題をもう解いていて、その答えが地図に配線されていなかった。**
`ATL_FILE`（`js/atlas-attach.js`）は バイト署名・ZIP 中央ディレクトリ・**レガシー文字コードの
判定**（Shift_JIS の CSV が文字化けしていた当のもの）を持っていて、`js/atlas-console.js` からしか
import されていなかった。同じことが `js/geodesy.js` の `sanitizeFeatures`（座標をクランプして
feature を落とさない修復器）と `js/atlas-geo-object.js` の `validLngLat` にも起きていた。

### 3. 直し方 — 形式ごとに if を足さず、問いを 2 つに割った

`.agents/rules/no-ad-hoc-hardcoding.md`: 報告された 1 件のための分岐を足さず、**その事例を生んだ構造**を直す。
この事例を生んだ構造は「**判定が名前の一覧だったこと**」で、#R540 が添付経路から消したのと同じ形である。

新設 `js/geo-import.js`:

| 問い | 訊く相手 |
|---|---|
| これは何の**容器**か | **バイト列** — `ATL_FILE.sniff` / `decodeText` / `zipOpen` / `gunzip` |
| これは何の**文法**か | **中身** — decoder レジストリ（JSON として解けるか・XML の根要素・表として読めるか） |

⚠ **`ATL_FILE` は写しではなく import である。** `gunzip` が内部関数だったので **1 語だけ export に足した**。
天井（`readBytes`）も `ATL_FILE.LIMITS` をそのまま使う——#R504 の「そろえた＝2 つの写しではなく 1 つの数」。
⚠ **`accept` 属性を消した。** 拡張子の一覧は、decoder が読めるファイルを**選択ダイアログから隠す**。

### 4. CSV の列選び — 最初の実装は売上表を Guinea 湾にピン留めするところだった

⚠⚠⚠ **これが今回いちばん危なかったところで、検査が捕まえた。**
`product,units,price` という表で、`units`（12/7/3/44）も `price`（4.50/19.99/…）も
**±90 に収まる有限の数**なので、書いたばかりの veto を全部通り、**1 行 1 ピンで海の上に並んだ**。
しかも見た目には完全に正しく見える。

最初に思いついた対処は「行数が少なければ断る」（`NAMELESS_MIN_ROWS`）で、**これは場当たりである**
——4 行の売上表は通ってしまう。構造としての答えはこうだった:

- **veto は値の性質**（帯・比率・定数でないこと・半球記号の矛盾）。**列名は veto を解除できない。**
- **score は根拠の重み**（9 言語の列名・半球記号・±90 を超える値）。負にもなる。
- ⚠ **そして「veto を通った」は根拠ではない。** 列名・半球記号・±90 を超える値の**どれか 1 つ**が
  積極的に「これは座標である」と言わない限り、`coordinates-not-identifiable` で**断る**。
  見出しの無い表で全列が ±90 に収まるなら、**どちらが緯度かを言い当てる根拠は実際に無い**。
  #R515（推測した座標が 宇部港 を 浜松市 に置いた）と同じ形なので、断るのが正しい。

veto と score を分けた副産物として、**見出しが逆さまに付いた表**（`lat` 列に 139.76）も正しく落ちる
——名前は −120 点になるが失格にはならず、値が `lat` 列を緯度から失格させるので、残る割り当ては 1 つ。

⚠ **選んだ列は必ずトーストで名乗る**（「CSV · 1,240 · 列: lat / lon」）。推測を含む処理の結果は、
推測を見せない限り検算できない。

### 5. 拒否は文でなくコードで返す — そして検査が両者の集合を突き合わせる

`js/geo-import.js` は `{ok:false, why:'shapefile'}` を返し、9 言語の文面は `js/map-ui.js` の
`reasonText()` が持つ。⚠ `tests/r576-checks.test.mjs` ⑩ が**両方のファイルを構文解析**して
「返しうるコードの集合」⊆「文を持つコードの集合」を測る（手書きの一覧は #R529 が消した形）。
**書いた直後に 3 つの穴を見つけた**——`not-a-table` / `xml-no-parser` / `unreadable` が
既定の 1 文に落ちていた。

⚠ `.shp` を含む zip は「Shapefile はまだ対応していません」と**名指して**断る。
これは web 地図に落とされるものとして最も多いのに、機能の一生を通じて
「有効な GeoJSON ではありません」と答えていた。

### 6. Node に DOMParser が無いので、XML はブラウザで測る

KML/GPX は `DOMParser` で**構文解析**する（正規表現ではない——`<coordinates>` がどの `<Placemark>` の
中のどの `<Folder>` にあるかが**データそのもの**だから）。Node にはそれが無い。

⚠ **代替パーサを検査に渡すのは #R552 の「実物より高機能な fixture」そのもの**なので、そうしなかった。
- `tests/r576-checks.test.mjs`（node・11 本）— CSV/TSV/WKT/DMS/GeoJSON/zip と、**⑨ で
  「node では `xml-no-parser` と正直に答えること」**を測る（`DOMParser` が生えたら ⑨ が赤くなる）
- `tests/r576.spec.js`（Chromium・7 本）— **実際の `#map-container` に実際の File を落とし**、
  `IntMapGeoEngine.layers.sourceData()` で**レンダラが持っている中身**を読む。KMZ は
  `tests/helpers/zip.mjs` が組んだ**本物の archive**

### 7. 変異試験 — 検査が本当に効いているか

⚠ #R548 の「変異したのに緑＝テストが弱いのではなく変異が入っていない」を避けるため、
**8 件すべてについて置換前に適用可能性を確認**してから走らせた。全部赤くなった:
経緯度の順序を逆に／根拠の要求を撤去／緯度帯の veto を撤去／見出し判定を反転／
ヨーロッパ式小数点を無視／区切り文字をカンマ固定／WKT の SRID 検査を撤去／
MultiPoint と GeometryCollection の展開を撤去。

### 8. 副次的に直ったこと

- **MultiPoint と GeometryCollection が消えなくなった。** `toFC` は受け取っていたが、
  `sanitizeFeatures` が両方落とすので、**受理された直後に地図から消えていた**。decoder 側で
  単一 geometry へ展開する（どちらの経路でも feature は失われない）。
- **Shift_JIS の CSV が文字化けしなくなった**（`ATL_FILE.decodeText` の共有）。
- **座標修復が取り込みにも効くようになった**（`sanitizeFeatures` の配線）。
- `tests/helpers/zip.mjs` — #R540 のテスト内にあった ZIP 生成器を**共有に移した**（写しを作らない）。

### 9. ゲートが 2 つ、正しく赤くなった

**① `tests/r175 ③`「no js/ module has an UNEXPORTED top-level declaration」**
`js/geo-import.js` をトップレベルに 38 個の宣言を持つ形で書いていた。この規則は移行の根幹
（古典スクリプトのトップレベル宣言は global になる）で、`js/atlas-attach.js` は
`export const ATL_FILE = (function(){…})()` という形で守っている。**同じ形に包んだ**
（`export const GEO_IMPORT` 1 本、中身は全部その中）。

**②「every export is imported by name」は、生きている経路を 1 つ見落としていた。**
包んだあと、今度は `GEO_IMPORT` が「dead code」と言われた。検査が数えているのは**静的な**
`import { X } from './…'` だけで、`js/map-ui.js` は

    (await import('./geo-import.js')).GEO_IMPORT.readGeoFile

と**動的に**取っている——`eager/modules` の予算を壊さないために、意図的にそうしている。

⚠ **そして同じ形が既に `js/screenshot.js:44` にある**（`(await import('./atlas-view-capture.js')).makeViewCapture`）。
それが赤くならないのは、`js/atlas-console.js:36` が**別の理由で**同じ名前を静的 import している
からで、**検査はこの経路を一度も見たことがなかった**。#R488 の形（生きている経路を綴りで固定した
検査は、綴りが変わった日にその経路を見失う）なので、**問いを事実に戻した**——「どの js/ モジュールか
がこの export に到達するか」。到達の 2 つ目の形（動的 import のプロパティ参照）を acorn で数える。

⚠ **緩めていないことを変異で確認した**: 使われない `export` を足す → 赤、
`js/map-ui.js` の動的 import を消す → `GEO_IMPORT` が dead として赤。

### 10. テスト予算 — 先に spec から払い、それから天井を 5 秒動かした

`tests/durations.json` の合計は `TOTAL_BUDGET_S` と**ちょうど一致していて余白は 0 秒**なので、
新しい spec は必ず超過する。この repo は #R405 / #R435 / #R494 で stale-high の候補を実測しては
「表は**過小**申告している」と結論しており（#R322 の規則で、そこから節約は取れない）、precedent は
**測った分だけ天井を上げて理由を書く**ことである。

⚠ **上げる前に spec から 2 回払った。** 最初の実測は 10.9 s だった。

1. **⑤（拒否されるファイル）が、起こり得ないことを待ちきっていた。** `drop()` は「レイヤーが増えたか」
   だけを見ていたので、**拒否される場合は定義上それが起きず、6 秒のタイムアウトを毎回払っていた**。
   アプリ自身のトースト（`#ai-toast`）も見るようにして、**どちらの結末も起きた瞬間に観測**する。
2. **そのあとも「念のため」のループが 1 秒待っていた。** `addFC()` は item を push してから**同期で**
   トーストするので、**トーストが変わった時点で件数はもう確定している**。

⑤ は **7.6 s → 2.7 s → 0.63 s**、ファイル全体は **10.9 s → 4.1 s**。固定 sleep は 1 つも残っていない。

そのうえで実測（温めたサーバ・1 worker・レポータのテスト**本体**時間・7 本の合計）:
**3,234 / 3,340 / 4,109 / 2,827 ms**、上限 4,109 を保守側に切り上げて **5**。
`shard-plan --update`（各 testcase を丸めてから足す）なら同じ実行から 4〜6 と書く。
#R435 は 4,309 ms を 5 と入れており、同じ読み方である。

⚠ **方法がこのマシンで甘く出ていないかを、数字を信じる前に対照した**（#R416 / #R435 と同じ手順）:
同じ方法で `tests/r550.spec.js` は **11.4 s**、表の値は **12** ——**0.95 倍**。このマシンは表を書いた
マシンより速くはないので、上の数字は割り引く理由が無い。

⇒ `TOTAL_BUDGET_S` **4,669 → 4,674**（理由は `scripts/test-budget.mjs` の block comment）。
core は 26 + 5 = 31 で `BUDGET_S = 38` の中に収まり、**上げていない**。

### 11. CodeQL が名指した——KML の <description> は仕様上 HTML である

CI の code scanning が `js/xss-through-dom`（high）で `js/geo-import.js` の `DOMParser` 行を名指した。
**スクリプト実行という意味では偽陽性**——`application/xml` で解析しており、その document は生きた DOM に
一度も挿入されず、`innerHTML` もどこからも読まれない。だが**指摘の下にある心配は本物だった**。

⚠ **KML の `<description>` は仕様上 HTML**（OGC 07-147r2 §12.2）。バルーンの markup で、しばしば表が
まるごと入り、敵対的なファイルなら `<script>` や `onerror` が入る。`textContent` はそれを
**markup を含んだ文字列**として返すので、そのまま property に入れると「このアプリが文字として扱う欄」に
敵対的な HTML が座る。**今この property を HTML として描く経路は無い**ので、穴ではなく**罠**である
——#R138 が「自分のコードの外から来た値は全部 HOSTILE」と書いたのは、まさにこれを置き去りにしないため。

⇒ `<description>` は**その文字**に落とす。⚠ **除去器は書き直さず共有した**——`js/atlas-attach.js` は
既に XML を散文にしており、しかも難所を先に踏んでいる: #R540 は（同じ CodeQL の
`js/incomplete-multi-character-sanitization` に、まさにそのファイルで名指されて）**markup を 1 回消すと
元に戻ることがある**ことを見つけ（`<scr<b>ipt>` は閉じてタグに戻る）、`strip()` を**不動点まで**回している。
ここに 2 つ目の実装を書けば、間違える場所が 2 つになる。`xmlText` を 1 語 export に足しただけ。

⚠ `tests/r576.spec.js` ① は `<![CDATA[a <b>port</b><img src=x onerror=alert(1)>]]>` を落とし、
property が `a port` になり **山括弧を 1 つも含まない**ことを測る。

### 12. まだ読めないもの

**Shapefile**（`.shp`/`.dbf`/`.prj` のバイナリ＋投影変換）と **PMTiles**（独自プロトコル＋range 取得）は
性質が違うので今回に入れていない。**どちらも黙って落とさず、名指して断る**。
