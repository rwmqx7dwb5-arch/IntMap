## R283 — **ローカルで必ず赤くなる2件は、改行コードだけが理由だった**

> 「In `C:\Users\gyuuk\OneDrive\IntMap`, two node check files fail locally on Windows
> (git `core.autocrlf=true`) purely because of line endings, while CI (Linux, LF) is green.
> This has been re-diagnosed by hand in many rounds (#R274, #R279, #R282 all recorded it),
> which wastes time and trains people to ignore red.」

### 1. まず数えた — 1,480 件のうち赤は 2 件

`npm run test:checks` が回す 126 ファイルを Windows の作業コピーでそのまま走らせた結果：

```
ℹ tests 1480    ℹ pass 1478    ℹ fail 2
  ✖ R232 i18n: the locale directory IS the language list, and the generated copy follows it
  ✖ R261 ③: continuous/one-shot is a property of each source, and every tap is fed
```

つまり報告どおり **2 件で全部**であって、「改行に弱い検査が散らばっている」のではない。
`\n` を含む正規表現を持つ検査ファイルは **53 本**あるが、その大半は `\s*` や `[\s\S]*?` を
挟んでいて `\r` を吸収する。**壊れるのは「改行が特定の文字の直後に来ること」を要求した場合だけ**。

### 2. 何が起きていたのか

**`.gitattributes` は Linux で実行・解析される拡張子だけを LF に固定している**
（`*.sh` / `*.sql` / `*.mjs` / `*.yml` / `*.yaml` / `*.toml`）。`js/` `css/` `*.html` は
`core.autocrlf` に任されていて、この開発機では `true` ＝ **チェックアウトが CRLF を返す**。
CI は Linux なので同じファイルを LF で読む。**改行はファイルの性質ではなく、チェックアウトの性質**。

- **`tests/r261 ③`** — `/function feedTaps\(dt\)\{[\s\S]{0,400}sources\.forEach\(sc=>\{\n\s*const left=owed\(sc\);/`。
  `\{` の**直後**に改行そのものを要求する。CRLF では間に復帰文字が入るので一致しない。
  実測：生バイト → false、LF 正規化 → true、`git show HEAD:js/terrain-water.js`（LF）→ true。
  ⚠ **いつから赤かったのかは測れる**——`git log -S` で **#R275**（`34151f9`）。それ以前
  （#R267 `a9b3668`）は `sc=>\{ if\(!sc\.cont\) return;` で、**壊れる改行を含んでいなかった**。
- **`tests/r232 ①`** — 赤かったのはテストではなく、テストが呼ぶ **`scripts/i18n-langs.mjs --check`**。
  `current !== text` で**生成物とレンダリング結果を1バイトずつ**比較していた。レンダラは LF を出し、
  チェックアウトは CRLF を持つ。**git が commit の際に消してしまう差**で「stale」と言い続けていた
  ——しかも `node scripts/i18n-langs.mjs` で書き直しても、commit できる中身は1バイトも変わらない。
  ⚠ こちらは **#R232**（`d1fa187`＝この生成器を書いたラウンドそのもの）から赤かった。

**これは「Windows だけの小さな不便」ではない。** 毎回同じ2件が赤いということは、
**失敗一覧そのものが読まれなくなる**ということで、#R274・#R279・#R282 の3ラウンドが
それぞれ独立に手作業で同じ診断をやり直して記録だけ残した、という形で実際に代償を払っている。

### 3. 直し方 — 検査は「バイト列」ではなく「内容」を読む

**`scripts/eol.mjs`**（新規）が改行を知っている唯一の場所になった。

```js
export const lf       = (s) => String(s).split('\r\n').join('\n');
export const readLF   = (p) => lf(readFileSync(p, 'utf8'));
export const sameText = (a, b) => lf(a) === lf(b);
```

- `tests/r261-checks.test.mjs` / `tests/r232-checks.test.mjs` の `read` が `readLF` を通る。
  **主張は1つも変えていない**——③ の正規表現も、他の 30 件の主張も一字も触っていない。
- `scripts/i18n-langs.mjs` の `--check` と書き込み判定が `sameText` を通る。
  **違う一覧なら今も stale**、**違うチェックアウトならもう stale ではない**。

⚠ **正規化は「緩める」ことではない。** 落ちるのは改行の前の復帰文字だけで、
**改行を要求するパターンは今も改行を要求する**。`tests/r283 ①` はそれを明示的に検査している
（1行に潰した入力は正規化後も一致しない）。

### 4. 計器 — `tests/r283-checks.test.mjs` は Linux でも赤くなる

2つのファイルを直せば Windows は緑になる。だが**この欠陥が見えるのは Windows だけ**なので、
それだけでは「次に誰かが同じ書き方をしたとき」を止められない。だから § ① と § ③ は
**CRLF を disk から読まず、その場で組み立てる**：

- ① 「CRLF のバイト列では一致しない／内容にすれば一致する／**改行が本当に無ければやはり一致しない**」
- ② 2つのファイルが `readLF` を通っていること（＋生の `readFileSync(…,'utf8')` が戻っていないこと）
- ③ `--check` が `sameText` を通っていること＋**1文字違う `_langs.js` は今も stale** であること
- ④ CRLF で書いた実ファイルを `readLF` が内容として返すこと

**赤くなることを先に確かめた**（#R274 ③ / #R282 ③ と同じ作法）：両方の修正を一時的に戻すと
② と ③ が落ち、戻すと 4/4 緑。緑が「見ていない」ではないことの確認。

### 5. 残した欠陥（測って残す）

**同じ1行が、まだ 5 ファイル 7 か所にインラインで残っている**
（`tests/r168-checks:164` / `tests/r169-checks:38,42,192` / `tests/r241-checks:135` の
`.replace(/\r\n/g, '\n')`、`tests/r282-checks:37` の `body()`、および `tests/r211-checks:53` の
`[\r\n]+`）。どれも**現に正しく動いている**ので、今回の指示の範囲外として触っていない。
`scripts/eol.mjs` に寄せるなら、それは別の指示として行う。

⚠ この数はこのラウンドの間に増えた。**#R282 が同じ欠陥に3例目として当たり**（「書いた期待値は
`'two\n'`。主張しているのは中身なので改行を正規化した」）、`body()` という7つ目の写しを足して
merge されたのが、この作業の最中だった。**知識が家を持っていない間は、当たった人がその場で
書き直し続ける。**
