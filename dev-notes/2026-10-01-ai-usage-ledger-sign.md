**誰が書いたか**
- 本番の関数本体（`pg_proc.prosrc`）: `increment_ai_usage` は上限未満で +1、`refund_ai_usage` / `refund_ai_turn` / `refund_ai_gloss` は `greatest(0, count - 1)`、`record_ai_usage` は `count` に触れない。**負にできる RPC は 1 本も無い**（リポジトリの migration も同じ）。トリガも無い。
- `pg_stat_statements`（2026-05-31 にリセット）に、
  `update public.ai_usage set (count) = (select count from json_populate_record($1::public.ai_usage, $2)) where user_id = $3 and usage_date = $4` が **49 回**。これは Supabase Studio の表エディタがセルを編集したときに出す文で、隣に表エディタの一覧読み（`with _base_query as (select * from public.ai_usage order by … )`）が数百回ある。
- 値の形は「打ち込んだ値 − その日の使用」に見える: −99,999,938 = −10⁸ + 62、−9,999,985 = −10⁷ + 15、−99,872 = −10⁵ + 128、−9,980 = −10⁴ + 20、−991 = −10³ + 9。**これは形からの推定**で、−35 や −27 には一意の読みが無い。
- 負の `count` は「`limit − count` 回まで使える」を意味する（`increment_ai_usage` は `count < limit` で通す）。−10⁸ はその日の上限を外していた。

**否定した見立て**
- 返金 RPC・settle・開発者アカウントの経路・テスト用の巨大値をコードが書いた——いずれも違う。開発者は `openTurn` で台帳に触れず（`count` を動かさない）、返金はすべて 0 で止まる。
- 「返金が課金を超えた」——返金は 0 未満に行けないので、負の値は返金の積み重ねでは作れない。

## 1. 根本原因

`baseline.sql` の表コメントと `docs/DATABASE.md` の保証 3「`ai_usage` は SECURITY DEFINER RPC だけが書く」は **grant についての文**で、grant が縛るのは `anon` / `authenticated` だけ。表の所有者（Studio の表エディタ・SQL エディタが走るロール）はどの grant にも縛られず、**列には値の制約が無かった**。不変条件「`count >= 0`」は書き手の算術（`greatest(0, …)`）の中にしか無く、その算術を持たない唯一の書き手が破れた。

- `supabase/migrations/20260718090000_baseline.sql:86-91` — `ai_usage.count integer not null default 0`（下限なし）
- `supabase/migrations/20260828090000_r491_gloss_quota.sql:29-33` — `ai_gloss_usage.count` も同じ形
- 同じ型の 3 つめの表 `client_errors` は `check (count >= 1)` を最初から持っていた

## 2. 影響

- **期間**: 2026-06-21〜2026-09-17（最後の書き込み）。**現在、上限が外れているアカウントは無い**——行は日ごとで、10-01 時点で当日の行に負は無く、09-18 以降に負の行は 1 つも作られていない。
- **一般利用者**: 2 アカウント・各 1 日。07-10 に +100 回、09-14 に +10 回まで上限が外れていた。最終値がちょうど −100 / −10 なので、打ち込み値がそれなら**その後の使用は 0**（推定。`ai_turns` は 1 日で消えるので実使用は確かめられない）。
- **費用リスク**: 過去分は確定できない（トークン列は 09-29 から）。上限が外れた日の大半（23 / 25 行）は管理者アカウント。今後の発生は下の制約で塞がる。
- **読み手**: 表の合計（月別・全期間）を負に歪めていた。1 日の判定は当日の行しか読まないので、過去の負の行は今日の誰の判定にも効かない。

## 3. 直したこと

- `supabase/migrations/20261002100000_ai_counters_never_negative.sql` — `ai_usage` と `ai_gloss_usage` に `check (count >= 0)`。**NOT VALID で足し**（以後のすべての INSERT/UPDATE に効き、既存行は触らない）、違反行が無い表ならその場で VALIDATE（新規 DB と本番の `ai_gloss_usage`）。本番の `ai_usage` は 25 行のため NOT VALID のまま。
  - どの RPC もこれに当たらない: 加算は 0 以上から +1、返金は `greatest(0, …)`、`record_ai_usage` は `count` に触れない。既存の負の行を UPDATE すると落ちる（NOT VALID でも新しい行は検査される）が、書き手は当日か 1 日以内のターンの日しか触らず、最新の負の行は 09-17。
  - ⚠ **運用上の変化**: 表エディタで負の `count` を打つと 23514 で拒まれる。アカウントの回数を増やすのは `profiles.plan`（`PLAN_LIMITS`）か `DEV_USER_IDS`。
- 返金の不変条件（課金を超えない・課金した日へ）は #R801 の `refund_ai_turn`（`delete … returning` の 1 文・`usage_date` で戻す）が既に持っていた。今回はそれを pgTAP と評価型の検査で固定した。
- Edge Function は変えていない（台帳の呼び出しはすでに条件を満たしていた。下の検査で評価して確かめた）。

## 4. 既存の 25 行（メインが判断する）

修正 migration（`ai_usage_negative_rows_repair`）に **0 に揃えて VALIDATE する**版を書いた。制約とは別ファイルなので、外しても制約は以後の書き込みを守る。

| 選択 | すること | 得るもの | 失うもの |
|---|---|---|---|
| A（ファイルの内容） | `count < 0` を 0 にし VALIDATE | 制約が表全体を述べる・合計が正しくなる・その行の UPDATE が通る | 元の値（この記録の §0 の表に残した） |
| B | 何もしない（NOT VALID のまま） | 元の値がそのまま残る | 合計は負のまま・その行への UPDATE は 23514 |
| C | 行を削除 | — | 「その日に行があった」ことと費用列（0）が消える |
| D | 打ち込み値を推定して足し戻す | — | 誰も述べていない数をコードが代入する（`historical-verification.md` §2-3）——採らない |

## 5. 残っている

- ターン鍵の無い依頼の返金（`refund_ai_turn(…, '')` → `refund_ai_usage`）は**今日の行**へ戻る。課金した日を運ぶものが無いため、UTC の日付をまたいだ失敗は翌日の行から 1 引く（0 未満にはならない）。
- 表の所有者は今も**正の** `count` を自由に書ける（例: 0 に戻して回数を与える）。それを塞ぐには「`count` は RPC の中でだけ変わる」をトリガで述べる必要があり、運用の手段を 1 つ消すので提案に留める。
- 本番の `increment_ai_usage` / `refund_ai_usage` は baseline と本文が違う（戻り値 `(allowed, used, lim)`・UTC 日付・`updated_at`）。`consume_ai_turn` は列名で読むので動いているが、ドリフトとして記録する。

## 6. 検査

- `supabase/tests/17_ai_counters_never_negative_test.sql` — カタログ全体で「`count` 列を持つ表は下限の CHECK を持つ」、所有者ロールの UPDATE / INSERT / 表エディタの文が 23514、0 での返金がエラーにならない、同じターンの 2 回の返金は 1 回ぶん、settle 後は返金なし、昨日課金したターンは昨日の行へ。⚠ このマシンは Docker が止まっていて `supabase test db` は CI で走る。
- `tests/ai-usage-ledger-sign-checks.test.mjs` — `ai-proxy` を評価（開始 2 種 × 終わり方 3 種 × ターン鍵の有無）して、返金の数 ≤ 課金の数・返金は課金したターンを名指す・継続と回答済みは返金しない・開発者は課金も返金もされない。`_shared/ai-ledger.js` は台帳に負の数を渡さない。変異（`if (isDev || !charged)` → `if (isDev)`）で ① が赤になることを確かめた。


## 修正 migration は出荷していない

既存の 25 行を 0 に揃える migration は書いたが、この PR には入れていない。過去の本番データを書き換える判断は利用者のもの（`AGENTS.md` §5 の「データ損失」に当たりうる）なので、最終報告で選択肢 A〜D を示して確認を取る。制約は NOT VALID なので、修正の有無にかかわらず以後の書き込みはすべて拒まれる。
