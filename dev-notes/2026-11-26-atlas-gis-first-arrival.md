〈依頼〉Atlas の地理分析で、計算できるデータを揃えるまでの待ち（11/20 実測: 全カタログ横断 16.7 秒、NASA だけで 16.0 秒）と、画像起点の分析が GIS に繋がらない問題。

## 1. 先着採用（`js/gis-remote.js` `search`）
- `search` に `until:"ready"`（＋`bounds`・`width`・`height`）。カタログが答えるたびに、そこまでに届いた記録で検索をやり直し、**窓を覆うと述べ（解像度を問われたなら、述べた解像度が条件を外れていない）る STAC の候補を、`acquire` で実際に読み値を検査**する。`ready`（空でも全 nodata でもない）になった最初の 1 件を `early` として返す。
- 残りのカタログへの問い合わせは止めない。`follow:"<handle>"`（または `action:"follow"`）で完了後の一覧（後から届いたもの込み）を取れる。早く届いたものが最良とは限らないので、**どれを使うかは Atlas の判断**に残し、固定の選択規則は足していない（`early` は「使える 1 件」であって「採用された 1 件」ではない）。
- 試すのは 1 回の到着につき最大 2 件、同じ ref は 1 度だけ。`until` なしの挙動は変えていない。
- 判定は記録の文面でなく読んだ値。検査 B1: 窓を覆うと述べても全 nodata に読めた候補は早期に返さない。

## 2. 画像添付ターン（`js/atlas-image-continue.js`・`js/atlas-console.js`）
- 画像読解の返答に `continueWithTools`（任意）を足した。**依頼が画像の外（外部データ・Web・IntMap のレイヤーとの照合）に及ぶと読解モデル自身が判断したときだけ** true。質問文への文字列規則ではない（検査 D1: 文面に「標高」等があっても true にならない）。
- true のとき、読解の回答はこれまでどおり先に表示され（読み・検算・ピン留めの能力は変えていない）、`recordTurn` は二重に積まず、同じターンで通常のエージェント経路が続く。エージェントへは読解結果を「画像の読み。検証済みの事実ではない」と印を付けた文脈で渡し、元の画像は `_atlRecallImgs` 経由の画像チャネルで届く。false なら従来どおり読解で終わる。

## 3. 植生境界の切り分け実験
本番（2026-11-26・ログイン済みブラウザペイン 1280x800・内部の `IntMapGisRemote.search` を直接呼んだ測定）。⚠ 元の問いは利用者の画面に出ていた事例の標本で、この問いのための対応は足していない。

### 3.1 先着採用（`until:"ready"`）
| 条件（q:"elevation"・maxGsd 40・64x64） | 所要 | `early` | 備考 |
|---|---|---|---|
| ベトナム北部 [104.5,21.5,105.5,22.5]・until なし | 15.1 秒 | - | 一覧 25 件・全体 92 件 |
| 同じ窓・`until:"ready"` | 17.9 秒 | **出なかった** | 全件待ちに戻った |
| 1 タイル内の窓 [104.6,21.1,104.9,21.4]・`until:"ready"` | **4.6 秒**（全体の完了は 15.6 秒） | `earth-search/cop-dem-glo-30`・`ready`・dataset 1 件 | NASA CMR は後から届いた（`stillAsking`→`follow`） |

- **限界（実測）**: 窓が 2 タイルにまたがると、候補は読めても `ready-partial`（`window-extends-past-the-file`）で、`early` の条件（`analysis==='ready'`）を満たさず、先着採用は効かない。窓の一部しか読めない値を「範囲を満たす」とは言えないための仕様どおりの挙動だが、広い窓では効果が出ない。次に直すのは、窓を覆う複数アイテムを 1 つの `ready` として扱う（別々の dataset を `combine` する）か、`ready-partial` を欠けた所つきで早期に渡す部分。
- Planetary Computer の `cop-dem-glo-30` は `source-unreadable`（Content-Range が使えない）で読めなかった。
- `IntMapConsole.dispatch` 経由で `early` が見えなかった理由は未確認（内部 `search` の直接呼びだけ確認した）。

### 3.2 植生境界（問い「なぜ山の稜線を挟んで植生が全然違う？」・北海道南西部の視点）
| | ① データ探しから | ② 標高 DEM を先に登録 |
|---|---|---|
| 最初の有効な地理データまで | 到達せず（dataset 0 件） | 登録は問い送信前に 9.8 秒。問いの中では新たな登録なし |
| 実測の比較が回答に出るまで | 出ず | 出ず |
| 総時間・手 | 51.3 秒・3 手（視点移動と画像観察・Web 検索） | 50.4 秒・3 手（同じ） |
| 回答 | 画像と Web 出典による説明。原因は「絞れない」 | 同じ。標高・植生の数値は出ない |
- どちらの条件でも `gisRemote` も標高・土地被覆の比較（gis 系）も一度も呼ばれなかった。②で登録済みの標高データも使われなかった。土地被覆（ESA WorldCover）は Planetary Computer が `source-unreadable` で ready にできず、②は標高だけ。
- **結論**: ②でも説明だけで終わったので、次に直すべきは「データ探し」ではなく**「問いを空間比較に落として実行する部分」**（稜線の両側で標高・土地被覆・植生指標を取って比べる、という実行へ進まず、視点観察と Web 検索で完結してしまう）。この問題は別の作業にする。
- 注: 条件①の最初の視点移動でハッシュから `t3=1` が落ちていた。呼び出しごとの秒数は画面の進行表示から取り、`ai_delegation_journal` では取っていない。

### 3.3 画像ターン（本番）
最初の試行は無料の AI 利用上限で読解が生成されず観測できなかった。利用枠が戻ったあとの再測定（合成した風景風 PNG・文字入り）:
- 画像＋「この画像の場所を標高と土地被覆のデータで検証して」: 画像読解の回答が 29.3 秒で先に出て、**同じターンで通常の道具が続いた**（地図描画・レイヤー切替・視点移動・Web 検索・標高の照会・Python 計算 2 件。24 ステップ・140 秒）。
- 画像＋「この画像の文字を書き起こして」: 1 ステップ 17.0 秒の読解だけで終わり、道具は続かなかった（従来どおり）。
- 限界: 続きの手が使ったのは IntMap 内蔵の標高・土地被覆で、`data.gisRemote`（先着採用）は呼ばれなかった。`continueWithTools` の値そのものは見ておらず、進行表示の挙動から判断した。書き起こしの回答は文字そのものでなく要約だったが、この変更の対象外なので判定していない。

## 4. 費用（perf 天井）
`gis-core` チャンクが +4.4 kB（705.3→709.7 kB）、その中の `gis-remote` が +2.1 kB（35.3→37.4 kB）。先着採用の実装（`js/gis-remote.js` の `search` の再構成と `follow`）の分で、削れる重複は無い。天井は CI が測った値へ上げた。
`atlas-console` チャンクは、main 側で #1445・#1446 の能力追加が合算して天井を超えており（main の測定 1452.9 kB）、天井は main 側で先に改められた。この変更の画像継続（`atlas-image-continue.js` の取り込みと分岐）の増分はごく小さく、main の天井に収まる。
