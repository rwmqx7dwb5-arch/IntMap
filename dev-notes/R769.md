## R769 — GDELT は 0 件だった。上流が死んでいて、IntMap はそれを一言も言っていなかった

〈#R764 の production verification 中に観測された、GIS とは無関係の既存問題。本番のコンソール
エラー 5 件が**全部この 1 経路**だった。まず「本当に 0 件なのか」を本番で測ってから着手した〉

### 0. 測った。読者に届いていたのは 0 件で、失敗は 1 文字も表示されていなかった

未ログインの本番（build R765）で実測:

| 面 | 実測 |
|---|---|
| News パネル | **30 行 / 200 件** — ⚠ **これは GDELT ではない**（Supabase の `news_events`）。壊れていない |
| GDELT 由来の行・マーカー | **0 件** |
| DOM 中の "GDELT" の出現 | **0 回** |
| 「取得できません」等の文言 | **0 件** |

⚠ **GDELT はレイヤーでもパネルでもない。** 呼ぶのは Atlas の証拠収集（`js/atlas-sources.js` の
`_gdeltNews`）と、ページ読み込みごとに 1 回走る健全性プローブの 2 か所だけ。梯子 6 段を本番で
再現すると、**200 で本文を返した段は 1 つも無い**:

```
1 own relay  gdelt-relay      502    10,910 ms   {"error":"upstream_unavailable"}
2 direct     api.gdeltproject 失敗    1,330 ms   CORS（ACAO なし）
3 allorigins                  408     7,618 ms   "Oops... Request Timeout."
4 corsproxy.io                401        25 ms   {"error":"A valid API key is required…"}
5 corsfix                     403       670 ms   {"corsfix_error":"domain_not_registered"…}
6 codetabs                    ERR     8,009 ms   中止（8 秒の締切）
```

⚠ **依頼にあった「発信先不明の 401」は corsproxy.io だった**（Supabase auth ではない）。推測せずに
本文まで取って確かめてある。

### 1. ⚠⚠⚠ 上流は「拒む」だけではなく、通ったぶんも空だった

`api.gdeltproject.org` を 2026-09-17 に 29 回叩いた:

- **429 が 24 回**（9.4–13.4 秒かけて返る。#R464 の「約 8 割」と同じ）
- **200 が 5 回。その本文は `{}`——2 バイト。**

⚠ **IntMap の組み立ての誤りではない。** 5 通りのクエリ形と 2 つの mode で確かめた:
`sort=hybridrel` / `sort=HybridRel` / `sort=DateDesc` / `query=Ukraine` / `query=climate` /
`mode=artlist` / `mode=timelinevol` —— **どれも `{}`**。User-Agent も無関係
（IntMap の UA と Chrome の UA を交互に 8 回、どちらも同じ）。

⇒ **この上流は今日 0 件しか届けられない。** relay の `upstream_unavailable` は誤報ではなく、
**正しい答え**だった。直すべきは上流ではなく、**それが読者に届いていないこと**である。

### 2. 公開プロキシ 4 段は全滅していて、誰も測っていなかった

**既知の正常なターゲット（`https://example.com/`）**に対して測ったので、GDELT の問題ではない:

| 段 | status | 本文 |
|---|---|---|
| api.allorigins.win | 522 | Cloudflare / nginx 500 |
| corsproxy.io | **401** | `A valid API key is required` ＝**無料提供の終了** |
| proxy.corsfix.com | **403** | `domain_not_registered` ＝**ダッシュボード登録が要る** |
| api.codetabs.com | 522 | Cloudflare origin down |

**うち 2 つは恒久的な提供条件の変更**であって、一時的な不調ではない。この一覧は #R212・#R452 に
書かれて以来**一度も測り直されていない**——[[intmap-discovered-list-is-a-photograph]] そのもの。

⇒ 直したのは**綴りを新しい綴りに書き換えること**ではない（それは同じ写真をもう一度撮ること）。
`scripts/probe-relay-ladder.mjs` は **`js/proxy-fetch.js` を評価して**、その梯子が実際に組み立てる
URL を**発見**し（`fetch` を記録して必ず reject するスタブに差し替え、梯子を底まで下ろす）、
それを叩く。⚠ ソースの正規表現読みも綴りの列挙もしていないので、**明日 1 段足されたら翌日には
測られている**。⚠ **HTTP 200 を生存と呼ばない**——ターゲットの中身が通ってきたかで判定する。

`.github/workflows/uptime.yml` に 6 時間おきのジョブとして載せた。⚠ **1 段死は警報ではない**
（そのための梯子）。全段死のときだけ `status:relay-ladder-down` で**重複排除された issue を 1 件**
開き、1 段でも生き返ればコメントして自動的に閉じる。⚠ **run は赤くしない**——4 段中 2 段は
恒久的な理由で死んでいるので、赤くすれば 6 時間おきに永久に赤い＝**読まれない警報＝計器ではなく
雑音**。⚠ **スクリプト自身の exit code の意味は変えていない**（手で走らせれば全滅で 1）。
正本は `docs/MONITORING.md` §1c。

### 3. ⚠⚠⚠ `null` が 2 つの問いに答えていたので、読者は何も知らされなかった

`fetchViaProxy` は「どの段も答えなかった」と「答えは来たが中身が無かった」に**同じ `null`**
を返し、`_gdeltNews` もそれをそのまま渡していた。だから analyze は GDELT と Google News が
**両方空のときだけ**「取得不可: ライブ Web ニュース」と言い、**そのどちらが起きたかは
言えなかった**。片方は IntMap の配管の故障で、もう片方は世界についての事実である
（#R763 が GIS 側で引いたのと同じ線）。

⇒ 梯子が `opts.note` に**自分の評決**を書く: `reason` が `ok` / `refused` / `aborted` /
`no-budget`、`via` が答えた段。analyze は
**「各取得先は応答したが該当記事なし」**と**「どの取得先にも到達できず」**を別の文で出す。

- ⚠ **評決はすべての出口で書く**——誰かが覚えていた経路でだけ記録される評決は評決ではない。
- ⚠ **note を渡さない 13 の既存呼び出し元の戻り値は 1 つも変わらない**（検査 ⑧ が実測する）。
- ⚠ **1 呼び出しに 1 note、共有しない。** Google News は最大 2 エディションを試すので、共有すると
  **応答した版の評決を、拒否された版が上書きする**（「読者の言語版は応答して該当なし、英語版は
  拒否」→ 対として「到達できず」と表示される）。

### 4. ⚠⚠⚠ キャッシュが空という唯一の場合が、キャッシュに何も書かれない唯一の場合でもあった

`gdelt-relay` の分岐 2（stale）は #R464 から読者の後ろで温め直していた。分岐 4（**cold かつ
上流が拒否**）は**何も残さずに 502 を返していた**——本番実測、連続 8 回すべて `cold`。
読者は毎回満額の拒否を払い、棚を見つけたときと同じだけ空のまま立ち去っていた。

⇒ `EdgeRuntime.waitUntil` で温め直す（分岐 2 と同じ機構）。**再試行が割に合うのは、
最初の 1 回が落ちる側だから**——同日実測、同一要求の背中合わせの対を 6 組:

```
429 を引いた要求そのもの      6 回中 0 回成功    429 が  9.4–13.4 秒で返る
その直後の再試行              6 回中 3 回成功    200 が 14.9–19.6 秒で返る
```

⚠ **読者の時計の中では成立しない。** `js/proxy-fetch.js` がこの関数に与えるのは 28 秒で、
最初の試行が 10 秒使う。成功に 15–20 秒かかる再試行は、在線で始めれば**通るのと同じくらいの
頻度で中断される**。⇒ 在線は 1 回に固定し、再試行は返答の後ろに置いた。

⚠ **増幅は自己限定的でなければ許されない。** warm は cold のときだけ走り、1 回温まれば
15 分 fresh・6 時間 stale になって cold が消える——**warm はうまくいったから止まる**。

⚠ **再試行するのは、再試行で変わるものだけ。** 429 は待ち行列の判断なので引き直しだが、
`{}` は上流の**答え**である。それを再試行すれば、拒む上流への負荷を 3 倍にして見返りは 0 になる
——`WARM_BUDGET_MS` が存在してよい理由の正反対。⇒ `not-artlist` / `not-json` では**打ち切る**。

### 5. ⚠⚠⚠ 走らない warm と、走って拒まれた warm は、外から同じに見える

#R464 は cache write についてこう書いていた——「黙って永続化に失敗するキャッシュは、
動いているキャッシュと**まったく同じに見える**」。**それは 1 段上でも真だった。** isolate が
waitUntil の前に壊されたのと、45 秒かけて 429 を引き続けたのとは、外からは同じ観測
（次の読者もやはり `cold`）を生む。

⚠ **実測中、まさにこれで詰まった**——上流が 5 回連続で拒否した瞬間、この 2 つを区別できず、
**自分の修正が動いているのかどうかを言えなかった**。

⇒ warm は**失敗したときも**受領証を残し（`warm-<key>`）、次の cold / stale の答えが
`x-intmap-gdelt-warm` で運ぶ。これで初めてこう測れた:

```
x-intmap-gdelt-warm: started/miss:not-artlist/3@37s
```

＝ **warm は起動し、37 秒で 3 回試し、最後は `{}` だった。** §1 の発見はここから出ている。

### 6. 502 は、上流が何と言ったかを名乗る

`x-intmap-gdelt-upstream`（上流の status か `not-artlist` / `not-json` / `unreachable` ＋
試行回数）。これが無い間、「拒まれた」「artlist でないものが返った」「到達できなかった」は
外から**同じ 1 つの出来事**だった。⚠ #R468 がこの endpoint に診断を入れた理由そのものが、
**拒否自身には適用されていなかった。**

### 7. 自分の変更を 4 回、自分で落第させた

- 註が「1 回だけ試す」と書いてある下のループが、**時間でしか縛られておらず 2 回試せた**
  （429 が 10 秒で返れば 25 秒の予算に 15 秒残る＝床の上）。**#R764 とまったく同じ形**なので、
  回数の上限を時計とは別の引数にした。
- 502 が名乗る理由が、**2 文の並び順**に依存していた（`UPSTREAM_NOTE` は module 状態で、
  warm がそこへ書く）。⇒ warm を始める前に値を取る。
- 読者の **Stop が `refused` と報告されえた**（signal が立つと `left()` が 0 になり、
  失敗側の出口を「誰も答えなかった」と共有する）。IntMap の配管を、読者がしたことで裁くことになる。
- `say()` が**読むものより前に宣言**されていた。今日は呼ばれる時点で初期化済みなので動くが、
  それは「いつ呼ばれるか」で答えた巻き上げの問いである（#R545）。

### 8. 検査

`tests/r769-gdelt-relay-liveness-checks.test.mjs`（9 本・**ネットワークに出ない**）。
Edge Function は**評価して**ハンドラを捕まえる（#R505）。⚠ **検査が本当に赤を出せることを
確かめた**（[[intmap-co-designed-reader-cannot-falsify]]）——実装の複製に 2 つの変異を入れ、
「分岐 4 の warm を外す」で ①④ が、「warm を 1 回で打ち切る」で ④ が赤になった。
⑤ は **実際に返ってきた Response のヘッダ名**から `x-intmap-*` を集めて Expose 一覧と突き合わせる
ので、今回増えた 2 ヘッダも自動で対象に入った（綴りを固定していない）。

### 9. 残したもの（直していない）

- **梯子そのもの。** 公開 4 段は今日全部死んでいて、2 つは恒久的な条件変更。**削っていない**
  （§3-1 の承認が要る）。計器が毎日それを述べるようにしただけ。
- **GDELT の `{}`。** 上流の状態であって、IntMap から直せるものではない。復旧すれば
  この回の warm と受領証がそのまま効く。
- **健全性プローブの費用。** ページ読み込みごとに 1 回、この経路に ~14 秒を払っている
  （実測 `AbortError`）。上流が 0 件しか返さない間これは純粋な費用だが、無効化は機能の縮小なので
  提案に留めた。
