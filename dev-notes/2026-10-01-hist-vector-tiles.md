〈依頼（構造改革・全面委任）〉歴史の束を「丸ごと読む JS」から「表示範囲と年で必要な分だけ取る時間つきベクトルタイル」へ。すべての読み手（ラベル・クリック・coverage・Atlas の currentFC・border-coast・戦争レイヤー・比較ウィンドウ）が新しい源から同じ答えを得ること。主要な年と場所で描画が前後でバイト一致すること。門・data-assets.json・sw.js・CSP を一貫させ、携帯の条件で初回の年移動の転送量・待ち・メモリを前後比較する。

## 0. 測った（着手前）

**1 つの瞬間が要る量**（`data/*.js` を読み、その日に有効な行が名指す環の JSON バイト）:

| 記録 | 行 / 環 | 環の総量 | 1900-06-15 に要る環 |
|---|---|---|---|
| cshapes.js | 710 / 2,165 | 12.9 MB | 151 行・3.6 MB |
| hist-borders.js | 1,411 / 3,607 | 33.6 MB | 102 行・1.9 MB |
| hist-admin1.js | 4,837 / 8,269 | 39.8 MB | 643 行・5.1 MB |
| hist-admin2.js | 22,691 / 23,416 | 35.1 MB | 4,158 行・6.1 MB |

行の表（`feats`）と日付は記録の 3% 未満（第 2 層だけ 8%）で、残りは全部環。

**GitHub Pages の Range（本番で実測）**: `Accept-Encoding: gzip` を付けると、`application/javascript`（`data/cshapes.js`）も
`application/octet-stream`（`data/stars.bin`）も `Content-Encoding: gzip` の **206** を返し、`Content-Range` は
**圧縮後の長さ**（`bytes 0-99/3961350`）に対する範囲だった——ファイルの位置としては使えない。`application/gzip`
（`data/crust1.bin.gz`）と `image/png` は無圧縮のまま、ファイルの位置で 206 を返した。⇒ PMTiles をそのまま
（`.pmtiles` は octet-stream）置いても Range は効かない。アーカイブは `.gz` にする。

**読み手は全世界を読む**（scout の全数調査）: 表示範囲で絞る読み手は 0。Atlas の名前検索（`atlas-geo-resolve`）・
比較ウィンドウの `geomForCode`（`stats-compare`）・`coverage()`・クリック救済（`app-body`）・ナレーター・`edges` は
どれも「その瞬間の全世界」を同期で読む。⇒ 表示範囲で切るとそれらが待ちか欠けになる。**利用者に確認し、
「年で切る・全世界」を選んだ**（第 2・3 層もズームの門 z6・z8 は従来どおり）。

## 1. 形式

- **記録ごとに 2 本**: `data/hvt/<名>.idx.json`（索引）と `data/hvt/<名>.jsonl.gz`（独立した gzip メンバーの
  連結。1 メンバー＝JSON 1 行のチャンク。ファイル全体も普通の gzip の JSON Lines）。名前は扉の `tilesOf` が
  記録の名前から導き、ビルダーも同じ関数に訊く。
- **索引**: 扉が `open` で答えていた head（そのもの）・全行の `[開始, 終了]`（YYYYMMDD の整数）・各行の
  チャンクと環のチャンク・時代の各 1 枚のチャンク・各チャンクのバイト範囲。
- **座標は整数差分**（記録の小数桁数 d の 10^d）。IEEE の除算は正しく丸めるので int/10^d は記録が書いた
  小数そのもの。**8 本・全座標で `Object.is` が一致**（一致しない環は書かれたまま持つ規則だが、該当 0）。
  gzip は約半分（hist-borders 11.30→5.89 MB、admin1 10.90→5.61 MB）。varint の二進も測ったが gzip 後で
  12% しか小さくならず採らなかった（admin1 7.00→6.13 MB、cshapes 2.84→2.59 MB）。
- **チャンクの大きさ**: 環 64 kB・行 16 kB（gzip 前）。128 kB・256 kB も測った（並びを決める前の
  段/桶→場所の並びで）。アーカイブは 2〜4% 小さくなるが 1900 年に読む量が増えた——admin1 2.33→2.67→3.20 MB、
  admin2 2.48→2.55→2.83 MB、cshapes 1.11→1.23→1.54 MB（要求数は 16→14→11 と減る）。
- **並び**: 区間木の段（⌈log2 期間⌉）と桶→開始→終了→場所（22.5° の升）→番号。開いた終了（OHM の 9999）は
  記録の**最後の開始年**で切って並べる（並べるためだけ。データは変えない）。5 通りを 8 つの年で測った
  （admin1 の 8 年合計で読む量: 段/桶→場所 13.0 MB・開始/終了だけ 19.1 MB・終了/開始 13.4 MB・
  段/桶→場所→開始 12.6 MB・**段/桶→開始→終了 8.9 MB**）。

## 2. 扉（js/hist-bundles.js）

- `histJob`（Worker とページが同じ関数を走らせる）に `openTiled`・`need`・`feed` を足した。扉は索引を読み、
  「その問いが読むチャンク」を job に訊き、それだけを `readWithin`（同じ時計・idle）と `Range` で読み、
  バイトのまま Worker へ移譲して展開させ（`DecompressionStream`）、それから問いを訊く。
- **`at`・`during`・`edges` は行ではなく期間の表を歩く**（記録を丸ごと持つときも同じ表を行から作る）。
  問いの述語は `rowsFor` の 1 か所で、答えと「要るチャンク」の両方がそれを使う。
- **穴埋め記録の継ぎ足しはタイルでも Worker で**: 各記録は自分の索引とアーカイブを持ち、`openTiled` が
  `splice` と同じ規則（環は後ろへ、行は 13 列へ書き直し）で継ぎ足す。head のキーの順まで同じ。
- 隣り合う要るチャンクは、間の要らないバイトが 32 kB 以下なら 1 回の Range にまとめる。同時は 6 本。
  別の問いが読み中のチャンクは待つ（二度読まない）。
- **チャンクは自分の番号を名乗る**（`c`）。gzip の CRC と合わせ、別の範囲・二重に圧縮された本文は
  形になる前に拒まれる。
- **戻り道**: 索引が無い（`npm run dev` は記録を切らない）・別の記録の索引・チャンクでないバイトは
  観測された失敗なので、記録を丸ごと読む側へ戻る（同じ答え）。期限切れ（観測できなかった）では戻らない。

## 3. ビルド（scripts/build-hist-tiles.mjs・vite の histTiles()）

## 4. 同一性

`origin/main`（281e584c）のビルドとこの branch のビルドを同じ `scripts/serve.mjs` で出し、Playwright Chromium で
年を -200・1000・1600・1871・1900・1918・1945・2000 の順に動かし、各年で `imtb-src`・`imtb-ln-src`・
`imtb-lbl-src`・`imta-src`・`imta-ln-src`・`imta-gap-src` の地物列、`IntMapTimeBorders.currentFC()`・
`IntMapTimeAdmin1.currentFC()`・両方の `coverage()`、比較ウィンドウの `geomForCode`（FRA・JPN・IND・USA・RUS・
TUR・AUH・GMY）、地域（日本・欧州・南北アメリカ・インド）ごとに重なる地物の名前の集合を FNV-1a で要約した。
加えて 1900 年 z7（中欧）の第 2 層 `imta2-src`・`imta2-ln-src`、戦争の層 WW1（1916-07-01）・WW2（1942-11-19）。

**264 項目すべてバイト一致**。新しい側はどの瞬間も全記録が `tiled`（戻り道は 0 回）。
例: 1900 年＝国境 151・区分 688、1871 年＝国境 168・区分 665、2000 年＝区分 1,160、第 2 層 4,158、
WW1 156・WW2 172。

⚠ 最初の比較では 1871 年の国境と線ラベルの 3 項目だけ違った。地物を書き出して比べると、幾何も出典の属性も
同一で、違いは**ラベルの読み手が後から地物に書き足すメモ `_locName`** だけだった——しかも**古いコード同士**でも、
1871 年へ直接飛ぶとメモが無く、-200→1000→1600 を経ると付く（タイミング次第の既存の振る舞いで、この変更とは
無関係）。そのメモを除いて要約し直したのが上の 264/264。

## 5. 携帯の条件での前後

Playwright Chromium、390×844・DPR 3・タッチ・Android の UA（`maySpeculate` が携帯と判定し、意図の先読みは
しない＝最初の年移動が全部を払う）。起動して落ち着いてから CPU 4× 減速と低速 4G（150 ms・下り 1.6 Mb/s・
上り 750 kb/s、Lighthouse の携帯条件）を掛け、年を 1900 に。「描けた」は描く source と両方の読み手の答えが
変わらなくなり、扉に問いも読み中の Range も無い状態が 3 秒続いた時点で、その**最後の変化**までの時間。
旧と新を交互に 3 回ずつ。

| | 旧（丸ごと） | 新（タイル） |
|---|---|---|
| 描けるまで | 148.2 / 149.1 / 159.4 s | **25.5 / 23.9 / 22.6 s** |
| 歴史の Worker のヒープ（GC 後） | 206 MB | **26.5 MB** |
| ページのヒープ（GC 後） | 99.4 MB | 99.5〜101.2 MB |
| data/ の要求 | 10 本（丸ごと 5 本を含む） | 35 本（索引 5・Range 25・共通 5） |
| 歴史の記録の転送 | **27.2 MB**（cshapes 3.92・hist-borders 11.41・hist-admin1 11.22・穴埋め 0.65。gzip） | **2.40 MB**（索引 0.06・cshapes 0.96・hist-admin1 1.34・穴埋め 0.04） |

描かれた数はどれも同じ（国境 151・線 126・区分 688・区分の線 630・穴埋めの線 51）。
⚠ 転送の行は**ファイルの大きさから数えた**。DevTools の `encodedDataLength` は旧の `hist-admin1.js` など
`getReader()` で読み切る本文を 0 と報告し（`docs/architecture/07-map.md` §7.4 の既知の振る舞い）、新の Range も
回によって 1.70〜2.53 MB とばらついたので、合計は扉の `need` が返すバイト範囲と、丸ごとのファイルの gzip
（Pages と同じ level 6）から出した。
⚠ 旧は 1900 年にも `hist-borders.js`（11.4 MB）を丸ごと取っていた——エポックの境目（`edges`）を訊くために
開くからで、新では索引（14 kB）だけで答える。
⚠ この測定の途中で、観測器が「描けた」を早く言う欠陥を扉自身に見つけた: タイルの問いは Range を読んでいる間
どちらのスレッドにも仕事が無いので、`counts().inFlight` が 0 のまま。`counts().reading`（読み中・待ち中の Range）を
足した（判断には使わない計器）。

デプロイの大きさ: `dist/` は +26.6 MB（アーカイブと索引）。`check:perf` の `dist.total`・`dist.data` の天井を
`--update` で上げた（754,907→781,503 kB・698,892→725,501 kB）。アーカイブは Range でしか読まれないので、
この増分は誰かが払う転送ではない。記録の丸ごとのファイルは源で、タイルの無いサーバへの戻り道なので残した。

## 6. 一貫させたもの

- **門**: 記録を測る門（check:cshapes・histborders・histadmin・histeras・histnames・wars・histfidelity・
  bordercoast）は記録を読み、記録は変えていない——タイルはそこから導かれ、ビルドが毎回読み戻して照合する。
  回帰は `tests/hist-vector-tiles-checks.test.mjs`（同じ記録を「丸ごと」と「タイル」の 2 つの扉で開き、
  8 つの年で行・環・日付・head・環の出自が一致すること、戦争の期間と 54 枚の時代、1900 年が Range だけで
  記録の 5 分の 1 未満を読むこと、戻り道、壊したチャンクと指していない索引をビルドが拒むこと、
  `serve.mjs` の Range、Service Worker が素通しすること、名前の導出）。
- **check:assets**: `data/hvt/` は名前が導出されるので orphan の許可に 1 行、アーカイブは Range でしか
  読まないので大きさの理由に 1 行。記録 5 本の理由にも「アプリはタイルで読む」を足した。
- **data-assets.json**: 変更なし——タイルは記録から導く生成物で、記録（`hist-eras.js` は data-assets の
  集合）がビルドの前に置かれていれば足りる（CI の `.github/actions/data-assets` は build の前に走る）。
- **sw.js**: 変更なし——`data/` は `isTileRequest` の外なので、`Range` はそのままネットワークへ行く
  （素通しを検査で固定した。キャッシュから丸ごとの本文を返せば Range に違うバイトを答えるため）。
- **CSP**: 変更なし——同一オリジンの `connect-src 'self'` と `worker-src blob:`、Worker の
  `DecompressionStream` で足りる。
- `scripts/serve.mjs` に Range を足した（Pages と同じく「送るバイト列」に対する範囲。だから圧縮される型の
  範囲はローカルでも Pages と同じように使えない）。
- `tests/history-prefetch-on-demand.spec.js`: 意図で読むのは記録ではなく索引（扉の `tilesOf` に訊く）、
  旅行はアーカイブを 206 で読み、記録を丸ごとは一度も取らないこと。

## 7. 否定した見立て・残った問題

- **否定**: 「PMTiles を置けば Range が効く」——Pages は octet-stream を gzip で送り、Range は圧縮後に効く（§0）。
- **否定**: 「チャンクを大きくすれば速い」——要求は減るが読む量が増える（§1）。varint の二進も 12% しか縮まない。
- **否定**: 「答えが同じなら速い経路が使われている」——時代の 1 枚の `blank` を 1 段浅く読んだ索引は `null` を
  指し、全シートが黙って丸ごとへ戻ったが、答えは同じなので比較は緑だった。いまはビルドが「索引が各行・各シートの
  読むものを全部指すこと」を照合し、検査は戻り道が 0 回であることを見る。
- 残り: 第 2 層の索引は 650 kB（gzip 前）で、z6 に入った最初の 1 回に読む。期間の表を差分で持てば縮むが、
  この回は測っただけで変えていない。
- 残り: `npm run dev`（ビルドしないサーバ）は索引が無いので丸ごと読む——前と同じ振る舞い。
