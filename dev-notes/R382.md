## R382 — **絵は正しかった——テストが、描かれる前のフレームを読み、色の距離で速度を並べていた**

`Deploy (production, Pages)` の post-deploy smoke が 2026-08-24 から赤のままになり、
**4 回連続で同じ数字**を出した（`gh run rerun --failed` を含む）。

```
and the eyewall nearer the entry for its own (49.6 m/s): ring [144,104,178]
expect(received).toBeLessThan(expected)
Expected: < 2954      // 眼の表エントリまでの二乗 RGB 距離
Received:   18741     // 自分（49.6 m/s）の表エントリまでの二乗 RGB 距離
```

**本番は正常で、赤かったのは deploy の検証段だった。** ただし放置すれば、以後のラウンドは
全部この赤い門の上を通ることになる。

### 1. 「CI だから」で終わらせない——環境を変数にして、否定した

最初に疑うべきものを先に潰した。**どれも再現しなかった**（全部実測）。

| 疑い | 実測 | 結果 |
|---|---|---|
| ソフトウェア WebGL | `--use-angle=swiftshader` で同じ画素 | 無関係 |
| カメラの pitch（前段の #R179 が 120° まで倒す） | pitch 0/30/45/60/70 で ring は 49.3–50.2 m/s | 無関係 |
| 祖先タイル（z3 を引き伸ばして表示） | その時刻では 48.9 m/s＝ほぼ正しい | 無関係 |
| 遅いランナー | CPU 10 倍絞りでも 6 秒時点で 48.9 m/s | 無関係 |

決め手は、**CI そのものに同じ計測を走らせたこと**（`uptime.yml` を自分の branch で一時的に
差し替え、`workflow_dispatch` で ubuntu ランナーに実行させ、終わってから元に戻した）。返ってきたのは

```
CAM {"zoom":5,"pitch":0,"bearing":0} canvas {"w":880,"h":720,"cw":880,"ch":720,"dpr":1}
```

——**手元と1バイトも違わない。環境は変数ではなかった。**

### 2. 絵のほうを見た——失敗時のスクリーンショットを1画素ずつ ramp に通した

CI の成果物（`post-deploy-report`）には失敗時のスクリーンショットが入っている。
それを取り出し、**全画素を風の色表に通して m/s に読み戻した**。

- 眼の壁に **52 m/s まで届く淡色の芯**があった（`[223,214,158]` 近傍の bbox **924,346 … 940,351**）
- その周囲に、失敗が名指した `[144,104,178]`（＝**38.1 m/s**）の帯（bbox 878,344 … 953,356）

**絵は嵐を持っていた。読んだ画素のほうが芯を外していた。**

### 3. 失敗した時刻に本番を合わせて、画素が落ち着くまでを測った

スクリーンショットのパネルが実行時のモデル時刻を印字していた——
**run 2026-08-23 18:00Z / valid 2026-08-24 01:00Z**。その時刻はまだ予報軸に残っているので、
本番をそこへ合わせて同じ操作を再現できる（台風の峰 **49.610327 m/s @ 24.5°N 136.0°E**、
テストが選ぶ「眼」**19.236341 m/s @ 23.0°N 134.5°E**）。

| 時点 | 眼の壁の画素 | 読める速度 |
|---|---|---|
| 0 – 1.2 秒（z3 の祖先タイルが乗っている） | `[191,160,197]` | **42.1 m/s** |
| 1.2 秒以降（z5 のタイルが着いた） | `[232,216,213]` | **46.2 m/s** |
| `valueNow()`（点の値） | — | **49.61 m/s** |
| **本番が実際に読んだもの** | `[144,104,178]` | **38.1 m/s** |

そして **CPU を 10 倍絞ると、タイルが着くのは 11.4 秒**。テストが読んでいたのは
**jumpTo のあと一律 6 秒**——`hasField && hasLyr && rasterOpacity > 0` は前段のテストが
z3 で風を点けた時点で既に真なので、**この視点のタイルが描かれたかを誰も訊いていなかった**。
本番が読んだ 38.1 はどちらより粗い＝**同じ沈み込みのもっと早い瞬間**である。

### 4. もう1つの欠陥——**この ramp では RGB 距離が速度を並べない**

仮に待ちが正しくても、この問いは眼の壁では成立しない。
`valueNow()` は**点**に答え、画素は**自分が覆う大気の面**に答える（#R287 が測って直した当のこと）。
±1.5 px の面はその時刻 **45.20 … 50.72 m/s** で、点の 49.61 とは別の量である。

そのうえで、比較そのものが壊れている。**出荷している表 1,041 エントリのうち 195**
（**34.5 m/s 以上の強い側ぜんぶ**）が、

> **速度では「眼の壁」に近いのに、色では「眼」に近い**

**本番が読んだ 38.1 は、その 195 の 1 つ。** 38.1 は 49.61 から 11.5 m/s、19.24 からは 18.9 m/s
——**遠いほうが色では近い**。これは #R276 追記が
「red − blue はこの ramp で単調でない」と書いた欠陥と**同じ形**であり、
**表から距離を読むようにしても単調にはならなかった**（ramp は色空間を一周する:
青→緑→茶→マゼンタ→紫と折り返し、そこから淡色・カーキへ抜ける。
35.9 → 46 m/s の 1 区間だけで **189 RGB 単位**）。

### 5. 直したのは2つとも**テストの側**（本番のコードは1行も触っていない）

1. **`jumpTo` のあと、この視点のラスタが実際に着いたかを地図に訊く。**
   `isSourceLoaded` を使い、着くまでの秒数を印字して `settled` を assertion にする。
   ⚠ **スロットIDは生きた style から読む**——`js/weather.js` は `wind-field-a` / `wind-field-b` を
   交互に使うので、片方を書き込むと**画面に無いほうのソース**を訊くことになり、
   `isSourceLoaded` は `undefined` を返す。**`undefined` は待ちではなく通過である。**
   ⚠⚠ **そして最初の一瞥はフレームの後でなければならない。** 書いている最中に実測した——
   `jumpTo` 直後に訊くと `isSourceLoaded` は **true** を返す（ソースキャッシュはまだ新しい視点を
   知らず、**古い視点について答えている**）。その版は **「settled in 0.0 s」** と印字し、
   **避けるはずのフレームをそのまま読んだ**。**何も起きないうちに満たされる待ちは、待ちではない。**
   ⇒ 各回の判定を `render` の後に取り、**連続2回一致**を要求する。同じ実行が **1.5 秒**と印字し、
   これは同じジャンプを単独で測った値（1.24 秒）と一致する。
2. **画素の問いを #R287 の `readPixel()` に替えた**（`inRange` ＋ `speedInFootprint`。
   どちらにも許容値は無い）。そのうえで「眼が見える」を **m/s で**言う——
   **眼の壁の画素が読む速度は、眼の下にモデルが持つ全部より上**。
   **眼の画素が読む速度は、壁の下にある全部より下**。
   **両方の境界は場から読む＝選んだ数は1つも無い。**

⚠ **数字を緩めて緑にしたのではない。** 緩めるべき許容値はどこにも無く、
**問いのほうが画素に答えられないことを訊いていた**。

### 6. 検査（`tests/r382-checks.test.mjs`・8件）

ブラウザの中でしか走らない判定は、誰も失敗を見たことがない判定である（#R274/#R287）。
この失敗そのものを Node に持ち込んだ。

- ① 本番が読んだ画素は **自分の下にある場の外**（±3 px に広げても外）
- ② **18741 / 2954 を整数で再現**——旧い問いが赤くなった形そのまま
- ③ **195 / 1,041** を数え、38.1 がその中にあることと、区間が 34.5 m/s から始まることを見る
- ④ 落ち着いた画素（46.2）は新しい判定を**通る**
- ⑤ 「眼が見える」を m/s で
- ⑥ **拒否すべきものは今も拒否する**——祖先の 42.1・#R276 の 0.36× の灰色・
  表の上にあって尤もらしい 30 m/s、いずれも同じ足跡の上で拒否される
- ⑦ 出荷テストが**時計ではなく絵**を待っていること（コメントを剥がしてから読む）
- ⑧ スロットが本当に2つあること（⑦が名指しを禁じる理由）

⚠⚠⚠ **そして #R287 自身の門が、置き換えた当の一行を留めていた。**
`tests/r287-checks.test.mjs` ⑦ は「兄弟のテストを巻き添えにしていないこと」を示すために
**`the eye is painted nearer the entry for its own speed` という文言そのもの**を留めていた——
つまり **#R287 が測って捨てた点の値の問いを、隣のテストでは残せと要求していた**。
`npm test` の checks 半分がこれ 1 件で赤くなって気付いた。**門は、その理由より長生きする**
（#R314/#R340 と同じ形）。文言を消すのではなく、**今アサートしているもの**——同じ判定を
各画素の足跡の上で取ること——に**留め直した**。

⚠ **緑は効く証拠ではない**ので、**4つの変異を入れて4つとも赤にした**——
待ちの条件を外す／6 秒の固定待ちを戻す／連続一致を1回に緩める／46 m/s のアンカー色を変える。

### 7. ついでに直した文書の事実

`tests/prod-smoke.spec.js` の見出しと `docs/TESTING.md` が、この検査は
**「uptime のスケジュールでも走る」**と書いていた。走らない——`uptime.yml` は
app shell の HTTP プローブ1本で、**playwright を一度も呼んでいない**。
走るのは `deploy.yml`（deploy 後）と `rollback.yml`（rollback 後）だけである。
つまり**この検査は deploy のときにしか動かない**ので、赤いまま放置すると
監視が先に気付くのではなく、**次のラウンドが門の上を通る**ことになる。

### 8. 残っている既知のこと（挙動は変えていない）

眼の探索は「峰から 1.5° の箱を `dla = -1.5` から走査し、最初に `0.6 × peak` を下回った点」なので、
**選ばれる「眼」は嵐の中心ではなく箱の南西の縁**であることが多い。カメラはそこを中心に据えるため、
**絵の中で嵐は中心から外れて写る**。判定には影響しない（2点とも自分の足跡に対して判定される）が、
失敗時のスクリーンショットを読むときに知らないと混乱する。
