## R295 — **開発運用そのものを恒久化した。調べて最初に分かったのは「どこに置くか」で結果が変わることだった**

> 「今後、このIntMapリポジトリで新しいClaude Codeセッションを開始した場合、セッションに関係なく、私が普通に
> 自然言語で開発要求を出すだけで、Claude自身が可能な限り高速・安全・高品質に作業を進める状態にしてください。」
> 「私にworktree、subagent、agent設定などの手動管理を要求しない。」
> 「CLAUDE.mdを巨大化させないでください。」

### ① 置き場所によって「値段」が違う——それを確かめてから配った

Claude Code の公式機構は 4 つあり、**context に載る量が三者三様**である。確かめずに配ると、
「CLAUDE.md を巨大化させない」を**満たしたつもり**になれる:

| 置き場所 | 何が常時 context に載るか |
|---|---|
| `CLAUDE.md` | **全文** |
| `.claude/rules/*.md` | **全文**（`paths:` を書かない限り） |
| `.claude/agents/*.md` | **`name` と `description` だけ**。本文はその agent が起動されたときだけ |
| `.claude/skills/*/SKILL.md` | **`name` と `description` だけ**。本文は呼ばれたときだけ |

⚠ **rules は「軽い CLAUDE.md」ではない。**同じ値段である。だから rules へ移すだけでは
**1 バイトも減らず、置き場所が分かれるだけ**になる。配置はこうした:

- **常時 1 本だけ** — `.claude/rules/execution-strategy.md`（4.7 KB）。分解・並列化・委譲の判断基準、
  並列編集の隔離、検証の段の表、context の節約。**毎回効く原則だけ。**
- **本文が無料の側へ詳細** — `.claude/agents/` 5 本と `.claude/skills/intmap-round/`。
- **CLAUDE.md には §5.0 として 12 行**（原則と、正本への 2 本のリンク）だけ足した。

そして常時側に**上限を付けた**（`tests/r295 ⑥`・1 ファイル 6,144 バイト）。
`scripts/test-budget.mjs` と同じ「**下がるだけの数**」で、次に誰かが常時側へ長文を足せば赤くなる。

### ② `isolation: "worktree"` は使えない——それは OneDrive の中に作る

Agent tool には worktree 隔離の設定がある。**IntMap では使ってはならない。**
それが作る worktree は `<repo>/.claude/worktrees/` ＝ **OneDrive の中**で、#R282 が
そこに **611 MB・11,615 ファイル**があり OneDrive が実際にアップロードしていたことを実測している
（追跡対象の本体は 113.8 MB なので、**同期量の約 9 割が一時物**だった）。

隔離は `scripts/worktree.mjs` が `os.tmpdir()` の下に作る。そして
**agent 定義がその設定を持っていないことを検査で固定した**（①）——規則を文章で書いたら、
その規則を測る検査を同じラウンドで書く（#R278）。

### ③ 手で組み立てていた 6 工程を 1 コマンドにした（`scripts/worktree.mjs`）

`CLAUDE.md` §6 は毎ラウンド「空き番号を決める・branch を切る・OneDrive の外に worktree・
`node_modules` を貼る・preview を足す・パスを控える」を要求していて、全部**手作業**だった。

```
node scripts/worktree.mjs status   # §1 の Git 側の確認が 1 回で終わる
node scripts/worktree.mjs new <slug>
node scripts/worktree.mjs done
```

原本の場所は**書かない**——`git rev-parse --git-common-dir` から導出する（#R282 と同じ）。

⚠ **ラウンド番号の衝突（3 回）は「読む場所が足りない」ことが原因だった。**
3 回とも `DEV-NOTES.md`＝**merge 済みのもの**だけを見て決めており、**いま走っている
`feat/r<N>-…`** を見ていなかった。索引・branch・worktree・`launch.json`・`tests/` の
**5 つ全部**から最大値を取る。⑦ が「提示する番号は、誰かが主張したどの番号よりも大きい」ことを検査する。
実際このラウンドでは **R296 が 2 セッション使用中**で、R295 になった。

### ④ 書いた直後に走らせたら、2 つ嘘をついていた

### ⑤ `done` の最初の版が、部分的な成功を全面的な失敗として扱っていた

実測: `git worktree remove` は**チェックアウトを消し、`worktree list` からも外れる**のに、
原本の `.git/worktrees/` にある管理ディレクトリだけ **`Permission denied`** で残る
（原本の `.git` は OneDrive の中で、OneDrive がそのファイルを掴んでいる。
**そこには既に 95 個の孤児が溜まっていた**）。

旧版はそのエラーで `exit 1` した。結果は——**worktree は消え、管理ディレクトリは孤児になり、
branch だけが生き残る**。誰も望まない唯一の結末である。
→ **エラーを判定にしない。`prune` してから `worktree list` に訊く。**

### ⑥ 自分の検査の「緑」を 2 回信じかけた

1. **`⑫`（本物のリポジトリを建てて `done` を走らせる）は、⑤ の欠陥を捕まえられない。**
   fixture は temp ディスクにあるので `remove` が**成功し、回復の枝に入らない**。
   → 構造を読む `⑬` を別に書いた（`prune` してから一覧に訊いているか・`catch` が `exit` しないか）。
   ⚠ **1 つの欠陥に 1 つの検査、ではない。「その検査が通る道」を確かめる。**
2. **その判定に使った最初の変異が、そもそも当たっていなかった。**
   bash の二重引用符の中に書いた `\n` が本物の改行に化けてアンカーが一致せず、
   「変異させたのに緑」を「検査が弱い」と読みかけた。
   → **変異スクリプトはアンカー不一致を `exit 2` で叫ぶ**ようにしてからやり直した。
   ⚠ **変異試験は「変異したこと」を先に証明しなければ、何も証明していない。**

### ⑦ 追記（終了処理で発見）— **安全な `git branch -d` は、この規程の下では「毎回断る」という意味だった**

merge した直後、自分で書いた `done` を自分に使って気づいた。

`done` は `git branch -d` を使う。`-D` ではないのが安全規則で、
**未 merge の branch は git 自身が断る**——これは正しい。しかし `CLAUDE.md` §5 は
**`--squash` で merge する**。squash された branch の commit は `main` の祖先に**ならない**ので、
`-d` は**完了したラウンドを全部「未 merge」と呼ぶ**。

つまりこの安全規則は、**技術的に正しく、実務では毎回外れる**。断り続ける片付けは使われず、
branch は溜まる（このリポジトリに 17 本の worktree と古い branch が残っているのがその結果）。

→ **`-d` が断ったら、`-d` が代理で訊いていた問いを直接訊く**:
`git diff --quiet origin/main <branch>` ——**木を比べる**。squash の後は内容が同一なので通り、
merge 後に何か commit されていれば通らない。同一のときだけ `-D` する。

⚠ そして**この変更で ⑪ が赤くなった**。⑪ は「`-D` を書くな」と書いてあったからで、
**検査のほうが古かった**。ここで緩めるのではなく、**測る対象を「動詞」から「番人」へ変えた**
——`-D` があるなら、その手前に木の比較がなければ赤。
⚠ `⑭` が**両方向**を実証する（squash 済みは消える／main に無い変更を持つ branch は残る）。
片方だけ書くと、「常に同一」と答える比較で「直った」ことにできてしまう。

### ⑧ 追記（自己監査）— **作った scout に自分の設定を監査させたら、自分が書き写していた**

merge 後、この round が定義した `intmap-scout` の指示書どおりに全数調査をかけた。
問いは「R295 は `CLAUDE.md` §9 の『同じ事実を 2 か所に書くな』を守れているか」。

**守れていなかった。** 4 つの事実のうち 3 つが書き写されていた:

1. **検証の段の表が 3 か所**——正本の rule に加え、`intmap-verifier.md` が**同じ段番号の 9 行の表**を
   持ち（しかも**その 3 行上で正本へリンクしておきながら**）、`SKILL.md` が段 3・段 4 の条件を
   コードブロックで再現していた。→ verifier は「**どのゲートが何を主張するか**」だけ持ち
   （段の割り当ては持たない）、SKILL は正本へリンクするだけにした。
2. **`isolation:"worktree"` の根拠に使った実測値（611 MB・11,615 ファイル）が 3 か所**
   ——`CLAUDE.md` §6 が持ち主なので、rule はそこを指すだけにした。
3. **5 役の名簿が `CLAUDE.md` と `docs/README.md` に**——これは残す（読み手に要る）。
   代わりに**古くなれない**ようにした。

⚠⚠⚠ **そして本当の発見はそこではない。`npm run check:docs` は `.claude/**` を 1 バイトも
走査していない。** `scripts/doc-facts.mjs` の `DOCS` はルート直下の `*.md` と `docs/*.md` だけ。
つまり **§9 の執行機構は、R295 が作った設定一式に対して被覆ゼロ**だった——
6 本目の agent を置いても、2 つの名簿が静かに古くなり、**全ゲートは緑のまま**。
#R280 の「**一覧に無いものは、その一覧では落ちようがない**」がそのまま出た。

→ `tests/r295 ⑮`（**ディレクトリを掃いて**、見つかった agent 名が両方の名簿にあるか）と
`⑯`（段番号をコマンドに結びつけているファイルは正本 1 本だけか）を足した。
⚠ **⑯ の最初の版は何にも一致しなかった**——正本の markdown 表では `段` は**列見出し**で、
番号は別の行にある。**守ろうとしている当のものに一致しない署名は、何も証明しない**（#R272）。

⚠ 教訓は「重複するな」ではない。**自分が今書いた設定は、自分が今書いた検査の外にある**。
規則を足したら、**その規則を執行しているゲートの母集合に、自分が入っているかを数える。**
