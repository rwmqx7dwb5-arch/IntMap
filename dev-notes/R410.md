## R410 — **地図の国名は、同じ画面の一覧より一手前の年を出していた**

依頼は #R409 が Playwright で実測した1件——「歴史地図の国名ラベルが、Countries 一覧と食い違う。
しかも2通りに」。

| | 地図 | 同じ画面の Countries 一覧 |
|---|---|---|
| 初回描画 → 1916 | Germany / France / Italy | German Empire / French Third Republic / Kingdom of Italy |
| 1939 → 1916 | **Nazi Germany** / French Third Republic / Kingdom of Italy | German Empire / … |

**着手前に両方を自分で再現した**（#R390 の規則）。1件目は**このマシンでは既定では出ない**——
起動が速いと勝ってしまう競走なので、`ne_110m_admin_0_countries.geojson` を route で 8 秒遅らせて
**決定的に再現**した。2件目は何もしなくても毎回出た。そして測ってみると、報告より悪かった。

### 1. 同じ時計に二つのリスナーが答えていて、歩調が合っていなかった

- `js/time-borders.js` … 時計の **45 ms** 後に `go(year)` → `apply()` → `tagSame()`
- `js/time-countries.js` … **340 ms** 待って、そこから国別表・Maddison・HDI を **await** してから
  `IntMapHistStates.apply()` / `IntMapHistId.apply()` で `countryStats` をその年の名前に改名

`tagSame` は**その改名を読んでいた**（`s._histId` が立っている国だけ、`countryStats[code]` の
現在の表示名を「Germany → いまの名前」に写す）。つまりラベルは**常に一手前の年**を描き、
そして**二度と書き直されなかった**——同じ年へ戻っても `shownY` の早期 return に当たる。

実測（`js/time-borders.js` の生の値を時系列で読んだ）:

```
1939 t=2s  map —                 histId=CHN,DEU,ITA,IRN,THA,IDN,ESP,EGY,FRA,HUN,ETH
1939 t=4s  map imtb-lbl2:Germany           ← 1939 の表は既に「Nazi Germany」なのに地図は Germany
1916 t=2s  map imtb-lbl2:Nazi Germany      histId=CHN,DEU,ITA,IRN,THA,IDN,GBR,FRA,ETH
1916 t=12s map imtb-lbl2:Nazi Germany      ← 10 秒経っても直らない
```

⚠ **報告は「前進では適用される」と書いていたが、それも時計の運だった**——1939 でも地図は
«Germany» のままになりうる。前進・後退の別ではなく、**どちらのリスナーが先に着いたか**だった。

### 2. 直し方——年に訊く。他人の出力に訊かない

`IntMapHistId.at(code, year)` と `IntMapHistStates.activeAt(date)` は**年だけの純関数**である。
`tagSame(fc, year)` はそこへ訊くようにした（`shownYear` は `go(year)` の**最初の行**で置く——
`shownY` はスナップショットの鍵で、1枚のスナップショットが何年ぶんも答えるから）。
改名が当たっている国の**現代名**は `IntMapHistId._applied()` の退避側から取る（そうしないと
「1916 で Germany という多角形」が、`countryStats.DEU` が別の年の名前になっている間、
どの鍵にも当たらなくなる）。

⚠ **適用する年の範囲は一覧側と同じ式で書いた。** `js/time-countries.js` は
Maddison の下限より下では `restore()` して**現代名に戻す**ので、そこで地図だけが改名すると
**逆向きの食い違い**を新しく作る。`(window.IntMapMaddison&&window.IntMapMaddison.minYear)||1900` を
両方が読む（`tests/r410-checks ⑤` が2つを突き合わせる）。

### 3. 測ったら、報告されていない3つ目の食い違いがあった

1916 年の画面を全部読み出したら、**旧国家（`IntMapHistStates`）の側にもう1種類あった**——
§1 の競走とは**別の機構**で、勝っても負けても食い違う:

| ポリゴン名 | 地図（当時） | Countries 一覧 |
|---|---|---|
| Russia | Russia | **Russian Empire**（RUE 行。RUS は `_histHidden` で一覧から消える） |
| Japan | Japan | **Empire of Japan**（JEM 行） |

（同じ読み出しに China→Republic of China・Iran→Persia も出ていたが、あれは §1 の競走のほうで、
`countryStats` が届けば直る側である。上の2つは**届いても直らない**。）

`js/history.js` には **`hbRe(code)`** ——旧国家コードと era データのポリゴン名を結ぶ正規表現表——が
#R94h から在り、**クリック経路（`resolveHist`）はずっとそれを使っていた**。ラベルだけが使って
いなかった。利用者に範囲を確認したうえで（**「改名国＋旧国家」を選択**）、ラベル側も同じ表を引く
ようにした。⚠ 引く順は **旧国家が先**——`countryStats.RUS` は隠されているだけで表には残っている
ので、名前で引くと «Russia» が先に当たってしまう。

⚠ **`MODNM`（現代のポリゴン名→コード）から KOR と ETH が落ちていた。** 1939 年の地図に
«Ethiopia» と描かれているのは実測、一覧が «Ethiopian Empire» になるのは表からの導出——
ETU（1952–1993）が効かない年なので ETH は隠されず、`histId.at('ETH',1939)` が改名する。
**手書きの表は落ちる**ので、`tests/r410-checks ②` が
`js/history.js` の `ID` の鍵を**構文解析して**突き合わせる（KOR は朝鮮系の旧国家が全期間を覆うので
今日は挙動が変わらない——それでも入れた。**偶然だけで正しい表**は、その検査が止めたいものそのもの）。

### 4. 表がまだ届いていない回は、届いたときに貼り直す

年に訊くだけでは1件目は直らない——`countryStats` が**空**なら現代名の対照表が作れず、
`tagSame` は何も書かずに戻る。`js/time-countries.js` の `repaint()` が身元の変わった瞬間に
**`intmap-hist-identity`** を投げ、`js/time-borders.js` が表示中のスナップショットを貼り直す。

⚠ **札が動いたときだけ `setSourceData` する。** `repaint()` は1回の移動で**2回**鳴る
（ローカルの overlay → World Bank の系列）ので、素直に貼ると数百 KB を意味なく往復させる。
⚠ **`repaint()` から投げるのは、それが全分岐が通る1点だから**——Now へ戻る分岐も、
Maddison の下限より下で**現代名に戻す**分岐も通る。

### 5. 実測（本番と同じビルド・英語）

```
1916（属性 8 秒遅延）  前: Germany France Italy Spain United Kingdom
                      後: German Empire / French Third Republic / Kingdom of Italy /
                          Spain / United Kingdom of Great Britain and Ireland / Russian Empire
1939                  前: Germany               後: Nazi Germany
1939 → 1916           前: Nazi Germany・Spanish Republic・United Kingdom
                      後: German Empire・Spain・United Kingdom of Great Britain and Ireland
```

一覧側は全ケースで一致した。

### 6. 検査

- **`tests/r410-checks.test.mjs`（6件・Node）** — 表を**実際に走らせて**年に訊けることを確かめ
  （`histId.at('DEU',1916)`/`activeAt('1916-07-01')`/`hbRe('RUE').test('Russia')`）、`MODNM` の
  被覆・年駆動であること・イベントの**両端**・両ファイルが同じ下限式を読むことを見る。
  **12 通りに変異させて赤を実測**した。
  ⚠ そのうち1本は最初**理由のない緑**だった——`HS.hbRe(` という綴りは `_eraLocName` が #R129 から
  持っているので、「ラベル経路が使っている」の証拠にならない。**集めた配列と読む順**を主張に変えた。
- **`tests/r410.spec.js`（門・core）** — 1939 へ進んでから 1916 へ戻し、**描かれた文字**を読む。
  ⚠ 地物プロパティ `NAME` は**どちらの場合も «Germany»** なので、ソースを読む検査は
  画面が間違っているあいだ緑になる（報告がそう名指ししている）。読むのは
  ①どちらのレイヤーが実際に描いたか（`queryRenderedFeatures` はレイヤーの filter を適用する）
  ②そのレイヤーが**今宣言している** `text-field` 式をその地物に当てた結果、の2つ。
  同じ瞬間に Countries 一覧の DOM も読み、**両者の一致**を主張する。
- **`tests/r410-late.spec.js`（deep）** — 属性ファイルを route で遅らせ、地図が一覧に追いつくこと。
- ⚠⚠⚠ **そして `npm test` の中で、この門が「Nazi Germany」で落ちた——製品ではなく検査の欠陥だった。**
  `npm test` は node 側 2,602 件とブラウザ側を**同時に**走らせる。その負荷の下で、
  `arrived()` が待っていた**ソースのデータ**はもう 1916 なのに、`queryRenderedFeatures` は
  **1939 のタイルから答えていた**——`setData` のあとタイルは非同期に再解析されるからで、
  «Germany» は**どちらの年のデータにも在る**ので「名前が出てきたか」を待つ検査では
  古いタイルと新しいタイルを見分けられない（#R382 の「`jumpTo` 直後の `isSourceLoaded` は
  古い視点について true」と同じ形）。⇒ 待ちを**主張の前提そのもの**に書き換えた:
  **画面に出ている era ラベルが全部、ソースが今その多角形に与えている札と一致するまで待つ**。
  ⚠ これは**欠陥を隠さない**——誤って札を付けたビルドでは画面とソースが**一致したまま**なので、
  そのあとの主張が落ちる（実測: 修正前の `js/time-borders.js`／`js/time-countries.js` を
  `origin/main` から戻して再ビルドし、**2 本とも赤**になることを確かめた）。
- ⚠ **1つの視野で全部を訊くと flaky だった**（実際に1回落ちた）。era レイヤーも他の記号レイヤーと
  同じように衝突するので `queryRenderedFeatures` は**置かれたもの**を返す——それが正しい問いであり、
  だから視野の中身で答えが変わる。Russia のラベル点はアジアにあり、ヨーロッパの視野には無い。
  **主張ごとに視野を分けた。**

### 7. 試験予算——**天井を上げた（2ラウンド続けて。前は #R405 の 7 秒）**

`scripts/test-budget.mjs` の総量は **4,536 秒に対して合計も 4,536 秒**、余裕ゼロで渡ってきた

| r186 | 150 | 186 |
| r184-drone | 145 | 378（2件失敗＝どちらにせよ支払いにならない） |
| r173 | 61 | 162 |
| r204 | 49 | 144 |

**どれもこのマシンでは entry より遅い**——#R379 と #R384 が書いた所見と同じで、ラチェットを
長く回した結果、緩みが残っていない。⚠ r175 だけは「実測 120 < entry 159」だが、この台帳が
使っている local→CI 換算（#R201 の 0.68 倍）でも対照比でも **entry を上回る**ので取らなかった。

実際に取れたのは **8 秒**だけ。台帳が要求する**同一走行・対照つき**の方法で
（対照 `tests/r341.spec.js` entry 4／実測 1.98 s）:

monitors（5.36 s × 2.02 = 10.8 対 entry 10）と r355-cables は**過小評価**なので取っていない。
smoke は #R388 の実測（72 s 対 entry 8）があるので触らない。

⚠ **最初の対照走行は捨てた。** 背景で別の測定が dev サーバを掴んでいて **7 ファイル全部が落ちた**
——静かなマシンで測り直した（29 件通過）。

そのうえで、利用者に確認して **`TOTAL_BUDGET_S` を 4,536 → 4,595（+59 秒・+1.3%）**に上げた。
このファイル自身が「決して上げるな」と書いているので、台帳の先頭と `HISTORY` の両方に、
上げたこと・探した 8 ファイル・取れた 8 秒を明記した。
⚠ **1つ前の #R405 が同じことを 7 秒でやっており**（そして #R388 は core の天井で）、
それが先例である。#R405 は `tests/r184-routing.spec.js` を**実測 264 秒・entry 30** と測って
「30 と書いてある表から節約を取り出してよい回ではない」と支払いを見送った——**その判断はこちらでも
同じで**、上の 8 ファイルはどれも「取れる節約が無い」側だった。取った 2 件が違うのは、
**同じ走行の対照つき**で測ってあることと、それが core の天井を守っている当のものだからである。
⚠ **core の天井（40 秒）は動かしていない**——core は 8+4+2+10+1+12 = **37 秒**
（#R405 の時点で 33+7 = 40 ちょうど＝余裕ゼロだったので、動かさずに済ませるには払うしかなかった）。
deep 側が deep なのは**測ってあるから**（55 > `CORE_MAX_S`）で、
**測っていない spec は core** という規則が「一度も測らずに門を回避する」を止めている。
