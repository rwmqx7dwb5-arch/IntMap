〈依頼〉第 4 波・運用／品質／性能／信頼性（全権委任）。「修正だけを成果物にしない——利用者に届く速さ・信頼性を上げる新しい仕組みを」。既知の状況として deep tier nightly の赤、Atlas 夜間評価の secret 不在、main の Database checks と deploy.yml の失敗（別の担当が調査中なので触らない）。

## 0. 測った（前）

| 事実 | どこにあったか |
|---|---|
| 速さの計器は全部「研究室」——起動が読むバイト数（`check:perf`）と 1 台の携帯プロファイル（`frame-profile.mjs --boot`）。**読者が実際に何秒待ったかを測るものは無い** | `scripts/perf-budget.mjs`・`tests/perf-baseline.json` |
| 起動画面は「いつ・どう上がったか」をすでに自分で記録している（`__imBoot.marks()` の `idle` / `timeout` / `no-renderer`） | `index.html`・`js/app-body.js` |
| 夜の警報の節「Regressions and their suspects」は、作られた日（10-04）から **毎晩「読めた 0 晩」**（10-04・10-06・10-10・10-11 の deep-alarm job の log）。Issue #275 は「No test has been red on two consecutive read nights (window: 14 nights, 0 read)」——読んでいない晩についての判定。同じ履歴は手元では 14 晩全部読める（`.intmap/deep-history.json`）。理由はどこにも出ていない（`render` は件数だけ、`gh` の失敗は 1 行目の「Command failed」だけ） | `scripts/nightly-blame.mjs`・`scripts/deep-history.mjs` |

選んだ理由: 利用者に届く速さを上げる仕組みは「速さを測る」ところから始まるが、IntMap は読者の速さを一度も測っていない。起動画面の記録・匿名の利用統計・状態ページ・Atlas の診断・worktree status という既存の基盤は全部そろっていて、欠けていたのは**その間の 1 本の線**だけだった。版ごとに測れば、遅くした変更を名指せる（研究室の門を通った退行も）。夜の警報は、その「遅くした変更を名指す」仕組みの既存の 1 本が一度も働いていなかったので、同じ作業で直した。

## 1. 作ったもの

**数える（ブラウザ）。** `supabase/functions/usage-count/shape.js` に `ready`（起動画面が上がるまでの時間の区間: 1・2・3・4・6・8・12・20 秒以内とそれ超）と `boot_end`（上がり方: `idle`・`timeout`・`no-renderer`）。次元は `<版>.<m|d>.<区間>`、版は build stamp の分と短い sha（`202610121710-6830fff`）。区間の縁の根拠と失効条件、`maxDims`（main は 2026-09-13〜10-13 で 1 日最大 30 merge——新しい次元を拒む天井は「最新の版」を拒むので最も忙しい日に合わせた）は宣言のコメントに。`js/usage-counts.js` ⑥ が `js/boot-stage.js` の `interactive()`（「起動画面が上がった」を 1 か所で答えている）を待って 1 回だけ足す。隠れて始まった・使えるようになる前に隠れた・プリレンダー・版の無い読み込みは数えない（誰も待っていない）。同意の規則・送信・保持は既存の匿名統計のまま。

**公開の読み（DB）。** `supabase/migrations/20261013130000_field_speed.sql` の `public.field_speed(p_days)`——版と端末ごとの**割合**と帯（30+〜10000+）だけ。30 回未満の版は返さず、件数と日は返さない（件数＝通信量は管理者のもの）。SECURITY DEFINER・anon 可・理由はコメントに（pgTAP 11 の規則）。pgTAP `43_field_speed_test.sql`。

**読み手と判定。** `scripts/field-speed.mjs`——鍵は `src/vendor.js` から読み、PostgREST の上限で頁をめくる。分位（半数・4 人に 3 人が何秒以内か）と判定: 帯 300+ の 2 版で、新しい版が前の版の「4 人に 3 人」の時間以内に使えた割合が 10 ポイント以上減れば「遅くなった」（300 ずつで差の標準誤差 ≈ 4.1 ポイント、10 ポイント ≈ 2.4 SE）。時間は同じで「地図が落ち着いてから開いた」割合が 10 ポイント減れば「信頼性が下がった」。2 版そろわなければ「判定なし」で、「変化なし」とは言わない。

**文も同じ場所で作る。** 状態ページの節の文（en / jp・版の時刻は UTC）は `field-speed.mjs` の `sentences()` が束に入れ、ページは言語を選ぶだけ。最初はページ側で組み立てていたが、`service-status` の非同期チャンクが天井 21.1 kB を +4.7 kB 超えた（`check:perf`）。天井は上げず、数を決める場所で文も決める形に移して +1.8 kB（幅 2.0 kB の内）に収めた。

**読者へ。** `scripts/build-service-status.mjs` が `data/service-status.json` に `fieldSpeed` を載せ（読めなかったら `null` と `unread` の理由、前回のものを今夜のように繰り返さない）、状態ページ「IntMap のいま」に節「読者の手元で開く速さ」（版と端末ごとの分位、遅くなった・速くなった版、見出しに「最新の版は一部の読者で開くのが遅くなっています」）と、この端末の節に「今回は N 秒で使えるようになりました」（`__imBoot.marks()` をそのページで読むだけ、送らない）。Atlas `system.speed`（at 880）が同じ読みを返す（`statusPage.speed()`・計算を写さない）。`node scripts/worktree.mjs status` は origin/main の束から 1 行（brief は悪化したときだけ）。プライバシーポリシー §1・§3（en / jp）に数えるものと公開することを書いた。

**夜の警報が「読めなかった」を言う。** `nightly-blame.mjs` が読めなかった晩を理由ごとに数え（`unreadReasons`）、1 晩も読めなかった窓は Issue に「**No night could be read … NOT KNOWN**」と理由つきで書く（「赤なし」と言わない）。`deep-history.mjs` の `gh` の失敗は stderr の gh 自身の言葉（HTTP の状態と GitHub の文）を運び（`ghWhy`）、晩の `why` は落ちた shard の理由を持つ。CI で 0 晩になる原因そのものは、手元の資格では再現できない（手元は 14 晩読める）——次の nightly の Issue がその理由を名指す。

## 2. 測った（後）

- `node scripts/field-speed.mjs`（本番）: 「不明（field_speed answered HTTP 404 (the function is not deployed yet)）」——migration が本番に届くまでの正しい答え。`node scripts/build-service-status.mjs --print` も `unread: [{ half: 'fieldSpeed', … }]`。
- `tests/wave4-ops-checks.test.mjs`（9 件）: 本物の `js/usage-counts.js` を偽のページで起動して送られる本文を読む（1 プロセス 1 ページ——`interactive()` は 1 ページ 1 回の promise）。⑥ の `counter.add` を外すと ② が、`if (!b.read)` を外すと ⑥ が落ちることを確かめた。

## 3. 残り

- **本番に出るまで速さは何も述べない**: migration（`field_speed`）と Edge Function `usage-count`（shape.js を import している——宣言を変えたので配備が要る）。CI の配備に載る。出るまでは関数が 2 つの metric を拒み、状態ページは「速さの記録を読めませんでした」と言う。
- **判定には 2 版で 300+ ずつの読み込みが要る。** 通信量しだいで「判定なし」が続く。そのときは窓（`--days`、最大 90）か帯の閾値を、`field-speed.mjs` の失効条件に照らして見直す。
- **deep-alarm で 0 晩になる原因**（CI の `GITHUB_TOKEN` と job log の API の組み合わせと推定——未確認）。次の nightly の Issue に理由が出る。
- pgTAP はこのマシンで Docker が動いておらず走らせていない（CI の Database checks が走らせる）。
