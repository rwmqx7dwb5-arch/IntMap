## R622 — **本番でしか出なかった 2 つと、推定の上に判断を重ねていた粒子の速さ**

〈#R577 で出荷した波レイヤーの本番検証。粒子については利用者の指示「全部 Windy と同じ挙動に」〉

**実装の正本は [`docs/MAP-LAYERS.md`](docs/MAP-LAYERS.md) §7.14**（重ね順・速度則・計測手法）、
重ね順の契約は `Architecture.md` §7.3。ここに書くのは**どうしてそうなっていたか**だけである。

### ① 1 回目のトグルが必ず失敗する——同じ tick の 2 本目が 1 本目を打ち切っていた

本番で 2 セッション再現し、ビルド済みページでも 2 回中 2 回。赤いトーストが出てチェックが自動で外れ、
**2 回目は必ず成功する**。

```
6007 ms  load(wave_height) 呼び出し     6007 ms  load(wave_period) 呼び出し
6010 ms  load(wave_height) → NULL（3 ms・リクエスト 0 本）
8363 ms  load(wave_period) → frame
```

`js/waves.js` は `Promise.all([wave_height, wave_period])` で 2 変数を**同じ tick**に読んでいた。
`js/wx-ecmwf.js` の `load()` は**追い越す**——前景の読みは整理券（`var mine = ++seq`）を取り、券が
最新でなくなった読みは**自分の変数の frame** を返すか、無ければ null を返す。⚠ **その券はモデルの読みを
数えていて、変数の読みを数えていない。** だから 2 本目の券が 1 本目を即座に古くし、冷えたレイヤーには
返せる frame が無いので **3 ms で null** が返った。**fetch も例外もコンソール行も 1 行も残らない**のが
この欠陥の性質で、2 回目が必ず通るのも同じ理由——手元に period の frame があると `load` は
**券を取る前**に `frameCovering` で返すので、波高の券が最新のままになる。

⇒ **逐次読み**（`loadEach`）。⚠ **所要時間は増えない**——engine は全ての読みを **1 本の直列キュー**に
通すので、この 2 本は元々同時に走っておらず、**競合していただけ**である（実測 height 2,938 ms →
period 474 ms）。

⚠⚠ **上流の構造的な原因は残っている。** 整理券がモデル単位で変数単位ではない。#R622 は
**呼び出し側を engine の追い越し規則に従わせた**だけなので、**別のレイヤーが同じモデルに読みを出せば
同じ形が再発しうる**（現在、波モデルを読むのはこのレイヤーだけ）。

### ①-b その欠陥を見つけにくくしていたのは、理由を握り潰す 1 行だった

`.catch(() => fail())` と引数を取らない `fail()` で、**5 つの終わり方**——追い越された読み・
レンダラが受け取れない格子・死んだ GL コンテキスト・拒否されたアップロード・投げられた例外——が
**トーストの 1 文だけ**になっていた。`console.error` / `console.warn` / `unhandledrejection` を捕まえた
本番セッションが**この最中に 1 行も記録していない**のがその代償で、① は `E.load` に手を入れて初めて
見えた。いまは `fail(why, detail)` が `console.warn` と **`state().failure`** に理由を残す
（`no_field` / `grid_mismatch` / `no_renderer` / `upload_rejected` / `exception`）。
⚠ **利用者に見える文言は 1 文字も変えていない**——増やしたのは、トーストより長生きする宛先だけ。

### ② 海洋ラスタと同時に点けると波が沈む——アンカーが帯の「底」だった

`IntMapWaves.state()` は `painted:true` と答えるのに、画面には 1 画素も無い。スタイル自身の順は
`… im-night-shade, im-waves, lyr-sst, coast-only-casing, borders-only-line, ofm-* …`。

`E.before()`（気象レイヤーのアンカー）は「夜側の陰の 1 つ上」＝**データ帯の底**で、風や地上場のような
**基図の参照レイヤーの下に敷く陰影**にとってはそれが正しい。ところが GIBS ラスタは帯の**上端**に
足され、そのあと `js/label-occlusion.js` にラベル直下まで沈められる。⚠ **海面水温固有ではない**
——起伏でも海氷でもクロロフィルでも、次に足される何かでも同じで、だから直したコードはレイヤー名を
1 つも名指していない。

⇒ 波は**全面を覆うデータ画像**なので、この app でその種のものが置かれる場所——**ラベル直下**——へ。
⚠ その 5 id の一覧は `js/data-layers.js`（ケッペン）・`js/layer-packs.js`・`js/precip-annual.js` に
**すでに 3 つ写されていた**。**4 つ目を書かずに** `window.IntMapBelowLabels()` として 1 本化し、
ケッペン側もそれを読むようにした（残る 2 本は今回の担当外で未統合）。
一覧は重ね順で**最初に見つかったものが勝つ**ので、Esri のラベルラスタを退役させたスタイルでも
アンカーが無くならない。`E.before()` は**規則ではなく退避先**として残る。

**場所は取り直す**——波のあとに海洋ラスタを点ければ、それは波の上に入る（沈められる先が同じだから）。
`styledata` で **スタイル自身のレイヤー順の署名が変わったときだけ** `move` する。⚠ custom layer は
`getStyle()` に載らないので、**自分の `move` は署名を動かさない**＝帰還ループにならない。

⚠ **既知の限界を、直したふりで隠さない。** 波も海洋ラスタも不透明な色の場なので、同時に点ければ
どちらかは必ず隠れる。両方見たい読み手のための道具は**凡例の不透明度スライダー**で、それは
**上に居るときにしか効かない**——だから上に置いた、という判断である。

### ③ 粒子の速さ——推定の上に判断を積み、その上に推測を重ねていた

⚠⚠⚠ **#R577 の「粒子速度は位相速度 `c = gT/2π`」は間違いで、その後の「群速度 `cg = gT/4π` が正しい」
という判断も間違いだった。** 2 度とも物理からの推論で、2 度とも**同じ前提を疑っていない**
——`glMaxSpeedParam = 10` が**速度の天井**だという前提である。位相速度では海の 84.9% が天井に張り付く、
という実測はその前提の中では正しく、そこから「では群速度だ」と進むのは前提の外へ一歩も出ない動き方だった。

**正解は「波の周期（秒）そのもの」**で、根拠は推定ではなく **Windy 自身の関数**（実測 2026-09-10・
バンドル v51.2.1、逐語）:

```
W.utils.wave2obj = ([e,t,n]) => ({ period: hypot(e,t), dir: …(e,t,10), size: n })
```

⇒ タイルの R,G はベクトルで**その大きさが周期**、B が波高。`glMaxSpeedParam = 10` は
「**周期 10 秒で上限**」の意味で、**重力加速度は 1 度も出てこない**。

**直接証拠**——Windy 自身の補間器 `W.interpolator.getLatLonInterpolator()` で開放北大西洋
（25–60N・55–15W・0.25° 刻み）を叩き、こちらのデータと突き合わせた:

| | p5 | p25 | p50 | p75 | p95 | n |
|---|---|---|---|---|---|---|
| Windy | 6.21 | 6.84 | **7.40** | 7.91 | 8.69 | 22,690 |
| ours | 6.30 | 6.90 | **7.35** | 7.80 | 8.70 | 22,617 |

**全分位数が約 1% 以内。** 位相速度なら 1.56 倍、群速度なら 0.78 倍ずれていなければならない。
⚠ **陸上では Windy の補間器は詰め物（周期 14.87 s・波高 2.7 cm の定数）を返す**ので、視野全体で取ると
「25% が天井」という嘘をつく。**海だけで取ること。**
⚠ **周期は速度ではない**、と分かったうえで Windy に合わせている。ここに速度を戻すのは
**不具合の修正ではなく、Windy に合わせるのをやめるという製品判断**である。

同じ照合で 2 つの倍率も落ちた:

- **ズーム**——Windy の facade は 256 px タイル基準で数えるので **MapLibre の +1**（実測
  `getZoom()` = 3 に対し `maplibreMap.getZoom()` = 2）。**本数の分母と `zoom2speed` の両方**が
  この番号で引かれるので、ずらしたまま引くと**常に 1.30 倍の粒子**と **0.86 倍の速さ**になる。
  #R577 は +1 を「疑い」として書き、証拠が無いので入れなかった——上の実測がその証拠。
- **伸長**——Windy は `gl.canvas.width`（デバイス px）で割るのに、こちらはトレイルテクスチャの幅で
  割り、さらに `·dpr` と `·2` が乗っていた。進行方向の厚みが **dpr1 で 2 倍・dpr2 で 5 倍**
  ＝報告された「短く太いダッシュ」の正体で、Windy の印は **1 デバイス px の毛髪**である。

**足した Windy の挙動 3 つ**: 登場時の alpha ランプ（`appear += dt·1.8`。premultiplied なので
**合成全体**に掛ける。入れ直すたびに 0 へ）／携帯分岐（本数 ×0.5・`glBlending` ×1.15。判定は既存の
`window._imPhoneClass`。⚠ Windy はタブレットも mobile 扱いだがこちらは phone のみ＝**より狭い**）／
高ズームの色分岐（z ≥ 10.5 で `(0.5,0,0.4)`。⚠ **向こうの名前は「基図が灰色になる終端」なのに、
分岐は基図を 1 つも読んでいない**ので、挙動を合わせるならズームで合わせるのが正しい。実測 z11 で
ΔE00 10.4・極性は反転するが可読）。
**入れなかったもの**: 頂点バッファの列優先（描画本数も見た目も同一で、違いは GPU の仕事量だけ
＝「Windy と同じ挙動」に何も足さない）。

**実測**（同 preset・同海域・z3）: 速度 **ours 4.13 px/s 対 Windy 4.13 px/s**。
被覆率 **ours 25.5% 対 Windy 19.4%**——⚠ **まだ 1.3 倍重い。原因は特定できていない**ので、
**当てずっぽうの係数では合わせていない**（合わせれば数字は揃い、次に測る人が理由を探せなくなる）。

### ④ 計測手法そのものが 3 回嘘をついた

- ⚠⚠⚠ **フレーム相関で粒子速度は測れない。** |Δ| マスクの相関面は 2% しか立たず（ピーク 0.0508 対
  ゼロシフト 0.0499）、ours について「7.6 px/s」と答えた——**真値は 3.8**。位置は `positions()` を
  読み戻して数える。
- ⚠⚠ **headless SwiftShader の壁時計で割ってはいけない**（バースト描画＋Windy 自身の 0.1 s フレーム
  クランプで 1.0 px/s になる）。**積分器は正確で、フレームの供給が正確でない** ⇒ 積分器自身の Σdt で割る。
- ⚠⚠ **被覆率は同じ手法どうしでしか比べられない**（canvas の読み戻しでは同じフレームが 11.6% と出る）。

### ⑤ 形として残すこと——この 2 件は「自分だけが動いているページ」では原理的に出ない

(A) も (B) も、**ローカルの 3,440 本と CI が全部緑のまま本番で起きた**。

- (A) は「**2 変数を同じ tick で読む**」という**呼び出しの形**の欠陥で、モジュールを単体で走らせる
  検査は engine の整理券を持たない——**モジュールを走らせたことは、アプリを走らせたことではない**
  （#R552 と同じ形）。
- (B) は**他人が同じ帯に何かを足したとき**にだけ現れる。1 レイヤーだけを点けた検査には見えない。

⇒ `tests/r622-checks.test.mjs` は、この 2 つを**出荷しているコードそのもの**に対して測る
（アンカーは `js/data-layers.js` が公開している式を持ち出して評価し、`js/waves.js` が
**自分の一覧を持たずに訊いている**ことを要求する）。
