## R552 — **#R551 はブラウザでは 1 行も効いていなかった——文脈は、渡す側ではなく受け取る扉で落ちていた**

> #R551 の production verification で実測。本番で `IntMapAtlasCompose.run(args, {turnId})` は
> revision 1 → 2 になるのに、`IntMapAtlasExec.execute('map.compose', args, {turnId})` は
> `map:solo3` / `map:solo4` と**別々の artifact** になった。

### 文脈は、渡す側ではなく受け取る扉で落ちていた

#R551 は実行文脈を引数から追い出して `cap.execute` の第3引数に載せ、
`js/atlas-capabilities.js` の `legacyExecute` が `runtime.dispatch(a, ctx)`
と**第2引数**で転送するようにした。**ここまでは正しく、node でも本番でも動いていた。**

落ちていたのは**その先の 1 行**である。

```js
CAPS.bindRuntime({ dispatch:a=>dispatch(a), … })   // ← 1 引数のラッパ
```

`runtime.dispatch(a, ctx)` はこのラッパを呼び、ラッパは `a` だけを渡す。**`ctx` は扉で消える。**
`ctx.turnId` が届かないので `turnKey` は空、artifact は `map:solo<n>` の連番になり、
**ターン内の 2 回目の compose は 2 枚目の地図になる＝ #R551 が直したはずの症状がそのまま残る。**

### ⚠⚠⚠ なぜ 3,376 本が全部緑だったのか

`tests/r551 ⑧` は「実行文脈が引数ではなく第3引数で届くか」を測っていて、**それは正しく届いていた**。
検査は自分で 2 引数の dispatch を束ねてアダプタを試したからである。

**問題はアダプタではなく、出荷側のラッパが「包んでいる関数より狭い」ことだった。**
⚠ **実物より高機能な fixture は、この欠陥を原理的に見られない。**

⇒ 検査 ⑫ は出荷している `js/atlas-console.js` の**束ね方そのものを acorn で構文解析**し、
「カーネルが渡す引数より少なく受け取っていないか」「受け取った分を全部渡しているか」を訊く。
綴りではなく構造なので、引数名を変えても効く。変異試験（1 引数に戻す）で赤を確認した。

⚠ **本番でしか出なかった欠陥がまた 1 件**（#R546 と同じ形）。node の検査は出荷モジュールを
走らせていたが、**モジュール同士を実際に繋いでいる行**は誰も走らせていなかった。
