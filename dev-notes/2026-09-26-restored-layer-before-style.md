## 何が起きていたか（本番 38d0463 で観測）

`&l=dl-planes,dl-radar,…` を持つリンクを**隠れたタブ**で開くと、2 回とも:

- 航空機: `Uncaught Error: Style is not done loading.`（`startTraffic` がスタイルを待たずに同期で `addSource`）
- レーダー: `Uncaught (in promise) Error: Style is not done loading.` ×2（`whenStyleReady()` が**約 6 秒で強制解決**し、
  未解析のスタイルに `addRainViewer` させた）
- タブが見えてスタイルが読めても `lyr-planes` / `lyr-radar` は現れず、aviation-feed への要求も 0 件。
  **チェックは入ったまま描かれない**。外して入れ直すと描かれる。
- 海底ケーブルだけは同じ条件から回復した——#R187/#R355 がそのレイヤーにだけ再試行を持たせていたから。

## 根本原因（3 つ、どれも構造）

1. **観測器の嘘。** `whenStyleReady()`（`js/data-layers.js`・写しが `js/time-borders.js`・`js/time-admin1.js`）は
   `canDraw()` を待ちつつ、**41 回 × 150 ms のポーリングが尽きたら無条件に解決**していた（#R41 が `idle` だけを
   待って永久に止まった件の保険）。#R170 以降は待つ述語が `canDraw()`（スタイル解析済みか）になり、タイルの
   往来で偽にならないので、保険の理由は消えていた——残ったのは「見えなかった準備を『準備できた』と答える」
   ことだけ（`.agents/rules/one-pass-or-a-reason.md` §2-1 の形）。
2. **入口が 1 つなのに、関門が無かった。** 指・共有リンク（`js/map-ui.js`、`load` が来なければ 8 秒で走る）・
   セッション復元（`js/session-tabs.js`）・既定 ON（`js/app-body.js`、600 ms で走る）・Atlas・お気に入り・パック
   ——どれも最後は**箱の `change`** で、行の持ち主（20 前後のモジュール）がそこで addSource/addLayer する。
   スタイルが受け取れるかを訊くのは個々のハンドラ任せで、訊かないもの（`startTraffic`）と、訊いて期限で
   諦めるもの（上の 1）があり、**再試行を持つのはケーブルだけ**だった。

3. **起動そのものが MapLibre の `load` に結び付いていた。** `js/app-body.js` の起動処理（地球全体の衛星ベース・
   既定レイヤー・起動画面の段階）・共有リンク復元（`js/map-ui.js`）・セッション復元（`js/session-tabs.js`）は
   `events.on('load')` を入口にしていた。`load` は MapLibre が**描画の内側で**、その時点の**全 source が読めた**ときに
   しか発火せず、描画が例外で止まるとそこへ届かない。多数のレイヤーを載せたリンクでは来ない（4 倍の CPU 絞りで
   通常起動を測り、311 秒待っても来なかった＝修正前からある欠陥）。

隠れたタブで起きる理由: MapLibre はスタイルを**アニメーションフレームの中で**解析する（`browser.frame`）。
隠れたタブはフレームを走らせないが、タイマーは走る——復元の予備の時計だけが先に進む。

## 直したこと

- **`GE().whenCanDraw()`**（`js/geo-engine.js` のファサード・型は `types/geo-engine.d.ts`）: `canDraw()` が真に
  なるまで**決して解決しない**待ち。`styledata`/`load`/`idle` の購読＋150 ms ポーリングを、待ち手の数に
  よらずビューごとに 1 組。待ち手は**登録順に**解ける。3 つの `whenStyleReady()` はこれを返すだけにした（写しと期限を消した）。
- **`holdUntilDrawable`**（`js/layer-rows.js`）: document の capture リスナで、manifest が宣言する箱の `change` を
  **レンダラが在って `canDraw()` が偽のあいだ**止め（`stopPropagation`——同じ document のセッション保存は利用者の
  クリックをそのまま見る）、`whenCanDraw()` の解決で箱ごとに 1 回、着いた順に、配る時点のチェック状態で出し直す。
  預かり中の一覧は `window.IntMapLayerHold.pending()`（新しい window 名。`check:surface` の基準に足した——
  spec が「全部配り終えた」という状態を待つための読み口で、ほかに持たせる所が無い）。レンダラが無ければ素通り。
- **起動処理・共有リンク復元・セッション復元・既定 ON の発火の入口を `load` から `whenCanDraw()` へ。**
  起動処理の待ちは箱が生まれる前に登録されるので、預かったレイヤーより**先に**答えられる。共有リンク復元の
  8 秒の予備の時計は残した（スタイル解析前に走っても、レイヤーの変化は関門が預かるので安全）。
- ケーブルの梯子は残した（削除には承認が要る。いまは「待ちと追加のあいだにスタイルが消えた」場合だけの網）。
  註だけ現状に合わせた。

## 実測

再現は `page.addInitScript` で `requestAnimationFrame` を保留し `document.hidden` を真にする（＝隠れたタブの条件
そのもの。応答の遅延もモジュールの差し替えもしない）。12 秒保持してから解放（共有リンク復元の予備の時計 8 秒＋
3 回目の適用 +3.2 秒を内側に入れるため。解放時に関門が実際に預かっていることを spec が確かめる）。

| | 修正前 (HEAD 8d6ffd42) | 修正後 |
|---|---|---|
| `dl-planes,dl-radar` | `Style is not done loading.` ×2・`lyr-planes`/`lyr-radar` 不在 | 両方が関門に預かられ、解放後に描かれる・例外 0 |
| `sharedIds()` 全 87 件（通常起動と突き合わせ） | **23 レイヤー欠落**（180 秒待っても）: 航空機 5・船・放射線観測 3・火山 6・基本表示の道路/鉄道/州境/海岸線・地球全体の衛星ベース と極冠 | 欠落 0（素 2/2・CPU 4 倍絞り 2/2） |

報告された 2 つだけでなく、基本表示（`cb-roads`・`cb-rail2`・`cb-admin1`・海岸線）まで同じ形で失われていた。

## CI で落ちた第 1 版（PR #760）——関門の配る時刻を `load` に結んでいた

第 1 版は「起動時に預かったものは最初の `load` の直後に配る」にしていた。解析の瞬間に 87 件を配ると、その source が
`load` を遅らせ、`load` に結ばれていたアプリの起動処理が 28 秒たっても走らなかったため。CI（Browser rest 2/2）で
②が落ちた: 保留起動のほうは **180 秒後も配達 0 件・アプリの起動処理も未実行**（通常起動の 159 図層が丸ごと無い。
retry では 202）。

- **製品の欠陥（a）。** 待ちの行き先が「来るとは限らない event」だった。`load` は描画の内側で全 source が揃ったときに
  しか発火せず、ローカルで CPU を 4〜6 倍に絞ると `drawRaster` の `Cannot read properties of undefined (reading 'bind')` が
  1 回の実行で 44〜54 回出て描画が途中で止まる（MapLibre 側。修正前からあり、通常起動でも出る）。関門が箱の変化を
  全部止めているので、`load` が来なければ誰も何も足さない——一発で決まるはずの待ちが**待ちの連鎖で詰まった**。
  直し方: 関門は `whenCanDraw()` だけで配る。`load` を待つ理由だった「起動処理が後ろに並ぶ」は、起動処理の入口を
  `whenCanDraw()` にして根元から消した（待ちは登録順に解けるので起動処理が先）。
- **観測器の誤り（b）も 1 つあった。** spec が「起動処理が走った」を `__imBoot.progress() >= 88` で見ていた。起動画面の
  進捗は、画面自身の 20 秒の逃げ道が発火すると止まる——CPU 6 倍絞りで `load` が 20.6 秒に来た回は、起動処理は走ったのに
  進捗が 58 のままで赤になった。この表明は外した（起動処理の産物＝`layer-world-base` などは②の突き合わせが見ている）。
- **待ち方も状態に変えた。** 解放後は時間ではなく「スタイルが受け取れ、関門に何も残っていない」
  （`IntMapLayerHold.pending()` が空）を待ち、その後はデータを取ってから足すレイヤーだけを 60 秒まで見る。
- CPU 6 倍絞りでは、3 ページ同時の負荷でページが 60 秒以内に `evaluate` に 1 度も答えなかった回があった（欠落の判定
  以前に観測できない）。CI の①が 23.7 秒で、ローカル 4 倍絞りの 21.7 秒と同じ桁なので、CI の代わりは 4 倍絞りとした。

## 否定された見立て

- **「起動時は最初の `load` まで預かる」**——上の節。来るとは限らない event を待ちの行き先にしない。
- **「期限を延ばす／retry で塞ぐ」**——延ばしても、見えないものを見えたと答える形は同じ（`one-pass-or-a-reason.md` §3）。
- **「各レイヤーに try/catch と再試行を撒く」**——ケーブル以外の 20 前後のモジュールに写すことになり、次に足される
  レイヤーは黙って漏れる（`no-ad-hoc-hardcoding.md`）。守る事実は「箱の `change` はスタイルが受け取れるときに
  届く」で、それは入口の 1 か所が持てる。

## 残っている懸念

- `load` を入口にしている読み手はまだある（`js/hist-places.js`・`js/sidebar-style.js`・`js/runtime.js` のカメラ配線・
  `js/app-body.js` のコミュニティ層・`js/compare.js` の副地図）。今回の失敗の経路ではないので触っていない。
- MapLibre の `drawRaster` が texture の無いラスタタイルで投げる例外（上）は修正前から出ている。原因のタイルは未特定。
- 起動処理が `load`（全 source が揃い最初の描画が済んだ瞬間）より前に走るようになった。Cesium では `canDraw()` が
  最初のフレームより前に真になる（`setStyle` が構築時に呼ばれる）ので、起動処理が最初のフレーム前に走る。
