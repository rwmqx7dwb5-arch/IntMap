〈依頼〉本番の携帯の計測（390×844 DPR 3・CPU 4×・9 Mbps/150 ms）で見つかった 6 つの手を構造の規則として入れ、同じ build で測る。
アームは `IntMapSatProto.setTuning` で切り替え（起動時に効くものはプロパティの setter で即時に）、seed ごとにアームの順を入れ替えた。
携帯 3 seed・PC（1440×900 DPR 2、CPU/回線の制限なし）3 seed、起動は携帯 6 seed（順序を相殺）。数字は headless で実機ではない。

⚠ **計測器の穴を 3 つ直してから測った**: ① Playwright の `route` は文脈の HTTP キャッシュを止める（本番の診断も worker への shim に route を
張っていたので、HTTP キャッシュは効いていなかった）——shim は既定で外した。② CDP で Service Worker に掛けた回線制限は起動直後の取得に
効かず（ローカルで TTFB 16 ms）アーム間で条件が揃わない——全アームを Service Worker 無しで測った。③ 自分の実装の正規表現の `\b` が
ツールで制御文字（0x08）に潰れて一度も一致せず、b の最初の計測は「優先も保留解除もされていない下敷き」を測っていた（`check:static`
regex-control-char が捕まえた）。直した build で測り直した結果が下の表。

| 手 | 結果 | 携帯（前 → 後） | PC（前 → 後） |
|---|---|---|---|
| a. 投機は必要に譲る | **採用**（上限 1） | ピンチ後の鮮明化 1.22 → 0.75 s・移動中の不鮮明 87 → 63 %・パンのフレーム p95 133 → 50 ms・TBT 882 → 305 ms・ジャンプ中の空白 35 → 29 %（タイル待ち p95 は 502 → 672 ms と悪化） | 3D 傾け 2.35 → 1.27 s・ズーム 0.37 → 0 s・通信量 ジャンプ 3.4 → 2.7 MB／ズーム 8.7 → 6.7 MB。退行なし |
| b. 新しい場所の粗い下敷き | 不採用（コード削除） | ジャンプ中の空白 27 → 38 %・パンの TBT 546 → 1,345 ms と悪化 | ジャンプ中の空白 37 → 30 % だが 3D 傾け 0.78 → 2.03 s |
| c. ピンチ中の保留を外す | 不採用 | ズーム 0.93 → 0.88 s・不鮮明 85 → 69 % だが ジャンプの要求 89 → 160（0.9 → 1.7 MB） | ジャンプの要求 385 → 600（3.4 → 5.8 MB）、ジャンプ・パン・ズームに 1.4〜2.6 s の外れ、3D 0.65 → 0.82 s |
| d. 起動直後に開幕の画面を取る | 不採用（コード削除） | 最初のタイル要求 8.2 → 3.5 s なのに 最初の鮮明 8.6 → 9.7 s・層の表示 5.2 → 6.7 s | — |
| e. 3D のシェーダを先に作る | 未実装（下） | — | — |
| f. 2 つ目の Esri ホストへ preconnect | 不採用 | 最初の鮮明 7.0 → 8.6 s（相殺済み 6 seed）、相殺前の 4 seed では逆向き。一貫した差なし | — |

- **a の規則**（`src/sat-worker.js` `specPump`）: 投機（目的地の先読みと `js/tile-warm.js` の Esri の輪）は worker の 1 つの待ち行列が持ち、
  同じホストに描画側のタイルが待っている間は出さない・そのホストの 6 ソケットに空きがある時だけ・同時に 1 本まで（`priority:'low'`）。
  出た取得は取り消さず、描画側の同じタイルはそれに合流する。目的地専用の 4 レーンは消した。輪を sw.js に流す経路は worker が無い時と
  Esri 以外の提供元の代替として残る。上限 0（投機なし）はパンの後に不鮮明が残り（0 → 100 ms・移動中 9 → 16 %）、2 は 1 より速い所が無く
  19〜40 % 多く取った。
- **b を捨てた理由と、分かったこと**: MapLibre 6.13 は表示中のタイル集合にある親しか代わりに描かない（`tile_manager.ts _updateRetainedTiles`:
  親は理想タイルが失敗した後にしか要求されず、表示外キャッシュは見ない）ので「キャッシュに親を入れる」では効かず、試せたのは別のソース
  （同じ画像を 2048 px/タイルと宣言、3 段浅い）だけだった。直した build では携帯で悪化・PC で混在。描くレイヤが 1 枚増える費用（主スレッド・
  3D の描き込み）が、空白の減り（数 %）を上回った。
- **d が悪かった理由**: 開幕の globe（z1.7）の要求を長方形で近似したので半分が外れ（44 → 82 要求）、起動中の 9 Mbps を JS・データと奪い合って
  層の表示そのものを遅らせた。**残っている問題**: 描画側の最初の要求から worker の最初の取得まで約 2 s——専用 worker の起動が主スレッドの
  起動処理の長いタスクを待つ（6 KB の worker スクリプトが 4.3 s に作られ 8.9 s に揃った。MapLibre の worker も同時刻）。
- **e をやらなかった理由**: 初回の傾けで `getProgramParameter` が 1.1 s（本番プロファイル）。MapLibre 6.13 はプログラムの鍵に `useTerrain` を含める
  （`frame_render_context.ts useProgram`）ので、地形を付けると地形のシェーダだけでなく使用中の全レイヤのプログラムが作り直しになる。
  先に作るには地形を一度付けて 1 フレーム描く（DEM 取得が衛星と回線を奪い合う）か、各レイヤの ProgramConfiguration を内部 API で組むしかなく、
  どちらも 1.1 s の主スレッド停止を「押していない瞬間」に移すだけで、3D を押さない大多数にも払わせる。綺麗にはできないと判断した。
- 検査: `tests/sat-mobile-speed-checks.test.mjs`（worker を偽のネットワークで、`js/tile-warm.js` を偽のカメラで実行）、
  `tests/sat-arcgis-3d-checks.test.mjs` ⑥ を新しい意味（目的地は投機）に。計器と生データは追跡しない場所（scratchpad の `speed/`）。
