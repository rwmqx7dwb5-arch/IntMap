## R310 — **待っていたのはバイトでも列でもなく、レンジ要求の「回数」だった**

依頼1件・**5回目の同じ文**。「風レイヤーは品質保ったまま、起動から日時変更からすべてに至るまで、爆速にしろ。」

### 0. 4ラウンドが測っていなかったもの

#R297 は 18 MB を 6 MB にし、#R299 は段にし、#R305 は列にレーンを足し、#R307 は
「冷たいオブジェクトの初回レンジ要求 4〜5 秒」を突き止め、#R308 はそれを **1 バイト**で前倒しした。
どれも正しく、どれも**「何メガバイト読むか」と「どの順で読むか」**の話だった。

今回まず測ったのは、**同じバイトを、要求の刻みだけ変えて**読む値段である。ブラウザから、同じ
ホスト・同じファイル・同じ 8 MB・同じ瞬間:

| 要求の刻み | 本数 | 所要 | 実効 |
|---|---|---|---|
| 64 kB | 128 | 2,448 / 2,341 ms | 3.3 / 3.4 MB/s |
| 64 kB（同時 24 本に絞る） | 128 | 3,713 ms | 2.2 MB/s |
| 256 kB | 32 | 1,255 ms | 6.4 MB/s |
| 512 kB | 16 | 723 / 683 ms | 11.1 / 11.7 MB/s |
| 8 MB | 1 | 455 / 708 ms | 17.6 / 11.3 MB/s |

**どの行もバイトは同じ。** レンジ要求には大きさと無関係な固定費があり、風の 1 時刻 8.6 MB を
**139 本**に割って払っていた——それが 4 秒である。

⚠⚠⚠ **#R307 は正しい問いを、間違った対象について答えていた。** 「ブロックを大きくするな」は
今も正しい（`blockSize()` は**キャッシュの粒度**でもあるので、上げれば帯の両端で取りすぎ、
**同じ読み手を共有するラスタタイル**も道連れになる。実測 6.31 → 9.00 MB）。見落としていたのは、
**キャッシュが持つ単位と、ネットワークに頼む単位は別の数でよい**ということである。

### 1. まとめて頼む（`coalesceBackend`）

SDK のキャッシュ付きリーダーは、必要なブロックを**同期のループで1つずつ**バックエンドに頼む
——つまり 1 スパンぶんの要求は**同じマイクロタスクの中**に揃う。そこを包んで、
**ファイル上で隣接するものを 1 本にまとめて**発行し、返ってきたバッファを各ブロックへ切り分ける。

- ⚠ **隣接だけ。** 束ねるのは「頼まれたブロック」だけなので、**取りすぎは 1 バイトも無い**。
  これがブロックを大きくすることとの違いである。
- ⚠ **`RUN_MAX` で頭打ち**（上の表は 512 kB より上でほとんど改善しない。青天井の 1 本は、
  読み込み全体を全か無かの 1 要求にしてしまう）。
- ⚠ **中断シグナルが同じものだけ**束ねる。1 本の要求は 1 つの signal しか運べないので、
  混ぜると片方の中断がもう片方のバイトを消す。
- ⚠ **切り出しは `slice`＝コピー。** 64 kB の住人が 32 MB の LRU の中で数 MB の要求バッファを
  掴んだままにならないように。

包んだ先は `rd.reader.backend.backend`（SDK の HTTP バックエンド）。**SDK には手を入れていない**
——`reader` / `backend` / `getBytes` はコンストラクタで代入されるプロパティ名なので最小化を生き延びる。

**実測、同じ帯読みが 139 本 → 19〜24 本。バイトは 8.63 MB で不変。**

### 2. 「リーダーは 1 つ」は SDK の掟ではなく、このファイルの 1 行だった

`serial()` は #R288 以来「SDK のリーダーが 1 つだから」という理由で存在していた。バンドルを読むと:

- `ensureData(state, reader, cb, signal)` は**リーダーを引数で受け取る**;
- `WeatherMapLayerFileReader` は**エクスポートされている**;
- ブロックキャッシュの鍵は `hash(url) ^ hash(eTag) ^ hash(lastModified)` に**ブロック番号を足したもの**
  ——**別ファイルは絶対にぶつからず、同じファイルの 2 本は取ったブロックを共有する**。

そして `ensureData` は**呼ばれるたび無条件に** `setToOmFile` する。その中身は
`dispose()` → **HEAD 1 本** → 末尾の読み出し → 変数ツリーの走査である。実測:

```
1 ステップの HEAD    223 ms 地点 389 ms（帯の暖機）· 227 ms 地点 576 ms（色タイル）· 1,878 ms 地点 236 ms（広げる段）
バイトが全部キャッシュにある時刻へ戻る   2,118 ms   ← うち HEAD 1 本が 1,870 ms、ほかに通信は無し
```

→ **ファイルごとに 1 つのリーダー**（`readerFor` の LRU・`READER_MAX`）＋ `pinReader` で
`setToOmFile` を**冪等**に ＋ **開くのは `setIndex` の中**（ファイル名が決まった瞬間で、
読み込みが要求されるより前）。色タイルが使う SDK 側の 1 本にも同じ栓をする
（`registerProtocol`）——タイルは MapLibre から直接呼ばれるので `serial()` の**外**におり、
同じファイルの 2 枚が互いのリーダーを `dispose()` し得た。

⇒ 列は残るが**意味が変わった**。正しさのための直列化ではなく**帯域の割り当て**である:
読み手が待っている読み込みは**背景の読み込みが走っていても即座に始まり**（`runHi`）、
背景の読み込みは**読み手が何も待っていないときにだけ**始まる（`runLo`）。
**#R305 が「走り始めたものは取り消せない」と書いた半分は、取り消す必要がなくなることで解けた。**

### 3. 隣の時刻は「暖める」のではなく「読む」

`prefetch` はバイトをブロックキャッシュに載せるだけなので、ステップは**開き直し・索引の走査・復号**を
そのまま払っていた（実測、1 ステップ **2,107 / 2,168 / 2,204 ms**——手元にあるフレームは **45 ms**）。
しかも 1 本のリーダーを共有していたため**画面の前に並ばないよう 2.5 秒遅らせる**必要があり、
2 秒ごとに送る読み手には**一度も届かなかった**。

→ `readAhead(VAR, 次の時刻, nearBand()||band())`。**同じバイト・同じ帯・同じ向き**を読み、
フレームを保持する。走るのは**色が表に出た直後**（もう誰の前にも並べない）。

- ⚠ **軸が動いたときだけ**（`opt.step`）。#R276 追記の規則は不変で、これが正直な線引きである
  ——プレイヤーに触れていない読み手は別の時刻を求めていないし、8.6 MB は当て推量で払う額ではない。
- ⚠ **`seq` に参加しない。** まだ誰も居ない時刻は定義上いちばん新しいので、世代を上げれば
  **画面の読み込みを追い越して無効にし**、世代を見れば**役に立つ瞬間に自分が取り消される**。
- ⚠ **静かに入れる**（`keepFrame(f, true)`）——`sampler()` からは見えるが「最後に着いたもの」に
  ならない。「最後に着いたもの」は画面の時刻のものである。
- ⚠ **走っている最中に読み手がその時刻へ来たら合流する**（`reading[skey]`）。SDK 側の重複排除は
  `stateByKey` が**2 件の LRU**で色タイルに追い出されるので当てにできない。
- ⚠ **1 時刻だけ。** `touch` が 12 時刻を触るのは 1 バイトだからで、こちらは帯まるごと動かす。

### 4. 実測 — origin/main と交互に、毎回まっさらな context で

**A/B は片方を測ってから片方ではない**（#R305 の罠）。`origin/main` のビルドを :4311、この
ブランチを :4310 に置き、**1 往復ごとに順番を入れ替えて** 4 往復。毎回新しい browser context
＝ HTTP キャッシュは**どちらも冷たい**。中央値:

```
3.5 秒ほど眺めてから次へ進む読み手（DWELL 4,000 ms）
  レイヤー点灯   6,001 → 3,714 ms     要求 154 → 32     バイト 8.7 → 8.7 MB
  1 歩目         3,512 → 1,850 ms     要求 142 → 27
  2 歩目         3,010 →    26 ms     ← 先読みが着いている
  3 歩目         3,031 →   271 ms

連打する読み手（DWELL 300 ms — 先読みが終わる前に次を押す）
  レイヤー点灯   5,186 → 3,767 ms     要求 108 → 25
  1 歩目         3,046 → 1,492 ms
  2 歩目         2,968 → 1,709 ms
  3 歩目         3,408 → 1,640 ms
```

**正直に書く二つのこと。**
⑴ **連打する読み手には「瞬時」を渡せていない。** 先読みは 1 時刻ぶんの帯（約 8.6 MB）を動かすので、
読み手がそれより速く進むと間に合わない。そこで残るのは①と②の効果（**約 2 倍**）だけである。
⑵ **点灯（起動から）は 1.25〜1.6 倍**で、10 倍ではない。残りは **SDK 本体と wasm のインスタンス化**
——実測、同じ data URI を **2 回・各 2.1 MB** 読み、合わせて 1.6 秒前後かかる。これは風の読み込み
経路ではなく、このラウンドでは触っていない。

⚠ **試して外したもの**: 「ファイルの末尾 64 kB を `ready()` から先に取る」（SDK が同じ範囲を要求した
ときブラウザのキャッシュから返る＝#R307 の実測 11 ms）。**2 つの理由で入れていない。**
① **一度も走らなかった**——#R308 の起動時 stage-in が既にそのファイルを台帳に入れているので、
二つ目の台帳が要る。② 勝てる窓が**その 1 本ぶん**しかない: 実測、SDK 自身の末尾読みは
**75〜221 ms**（冷たい点灯 **3,855 ms** のうち）で、**測定のばらつきの下**である。
**示せない速さを主張することになるので入れない。**

⚠ **粒子・色・標本間隔・帯の決め方・モデル・ファイルは 1 つも変えていない。** バイトも同じである
（表の「バイト」列）。速くなったのは**同じバイトの頼み方**だけである。

### 5. 検査 — 11 本が正当な変更を退行に見せた（**25 連続**）

9 本は**綴りの逐語固定**で、題は今も真だった（`EC().prefetch([…],nx,nearBand()||band())` の逐語・
`var mine = ++seq;`・`function load(variable, i, bounds, bg) {`・`function keepFrame(f) {`・
`rd.prefetchVariable(…)` の受け手の名前・`return serial(function () {` という書き出し）。
**関係に書き替えた。**

残る 2 本（`#R276 ⑲`・`#R305 ⑦`）は**このラウンドが本当に変えた規則**を固定していた。消したのは
この 1 行で、消したことを名前ごと書いておく:

```js
assert.match(s, /pumping = true;[\s\S]{0,200}?pumping = false; _pump\(\);/,
  '…and exactly one read runs at a time');
```

**「同時に 1 本」から「前景 1 本 ＋ 背景 1 本」への契約変更**である。**綴りを直したのではなく、
理由ごと書き直した**: その規則は #R288 が本番で捕まえた衝突——**共有された 1 つのリーダーが
`setToOmFile` で別ファイルへ差し替わり、読んでいる最中の相手を壊す**——の帰結であって、
リーダーがファイルごとになれば衝突源そのものが消える。残るのは**レーンの順序**で、それは
正しさではなく**帯域**についての決定である（`HI_MAX = 1, LO_MAX = 1`——どちらのレーンも自分どうしは
1 本。2 本走らせれば読み手の取り分が半分になる）。
⚠ **合流には優先度が付いて回る。** ステップが読み進み中の `readAhead` に**合流**するとき、その仕事が
まだ**低いレーンで待っている**なら、読み手は「読み手が待っている間は始まらない」仕事を待つことになる
——`promote()` が待ち行列の中の仕事だけをレーンごと引き上げる（走り始めているものは何も要らない）。

新しい検査は `tests/r310-checks.test.mjs`（7 本）。`origin/main` に当てて **7 中 6 が赤**になる
ことを確かめてから採用した（緑のままの 1 本は「絵は 1 つも変わっていない」を訊くもので、
**赤くならないのが正しい**）。

### 6. 本番検証 — 上の主張を本番で数え直した

⚠ **§4 の表はローカルである。** 本番（`INTMAP_BUILD='2026-08-23-R310'`）で、冷たい context・
起動時の視野・カメラを一度も動かさずに測り直した。**1 回目（完全に冷たい走行）の値**:

**⑴ 併合は効いている。** 1 予報時刻ぶん（同じ 8.6 MB）の内訳:

2026-08-22T2200.om              20 本 / 9,043,968 B  = 138            HEAD 2   stage-in 1

きっかり 65,536 B の要求は索引ブロック 2 本だけ（改修前は**全部**が 65,536 B・139 本）。

HEAD 1 本・データ 0 本**。

**⑷ 先読みは着いている。**
