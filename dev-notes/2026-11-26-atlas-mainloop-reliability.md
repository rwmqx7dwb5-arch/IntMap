〈依頼〉主ループの一時失敗の再試行・失敗表示・要約拒否、OpenAI のキャッシュ・送信量、Anthropic 経路（切り替え時）を 1 本で直す。
着手前に各件を測り、再現しないものは理由を記録して外す。

## 本番の実測（2026-11-26・`public.ai_delegation_journal` と `usage_counts`、`supabase db query --linked`）

- **#1 一時失敗でターンが終わるのは実在する。** 直近 7 日の AI 要求 1,054 件のうち `provider_unavailable` が **22 件（2.1%）**・`provider_quota` 4 件。
  再試行は Gemini 経路にしか無かった（本番は OpenAI）。`ai_rungs`（1 要求あたりの提供元への要求数）は 1 が 919、2 が 57、3 が 78。
- **#4 キャッシュ率の食い違い 3% と 24.4% は測り方の差で、実体はどちらでもない。** `cached_tokens` の列はジャーナルに 2026-11-25 から入った
  （#1419）。それ以前の日は 0 ＝ 記録なしで、「直近 3 日」「直近 1 週間」の平均に 0 の日が混ざっていた。記録のある日だけ:
  11-25 が **20.7%**（221 ターン・入力 9.49M トークン）、11-26 が 30.3%（9 ターン）。窓を揃えると 20〜30%。
  ターン内の位置別（11-25 以降の `atlas_turn`、`root_key` 内の順位）: 1 手目 26.3%（64）・2 手目 21.3%（30）・3 手目以降 19.6%（136）。
  **同じターンの 2 手目以降が 1 手目より上がらない**——前置きが同一なら 2 手目以降は大半が読み取りになるはずで、ここが本題。
  入力は 1 呼び出し平均約 41k トークン、読み取りは平均約 4.4k ＝ tools 相当の長さで止まっている。
  `prompt_cache_retention:"24h"` の効果は **未観測のまま**: 同じ日（11-25）にジャーナルの列と同時に入ったため、前後比較の相手がいない。
- **#9 空応答の全入力再送は再現しない。** `provider_empty` の失敗は 7 日で 0 件、`ai_incomplete` は `max_output_tokens` が 2 件のみ。直さない。
- **#7 `atlas_verify` の待ちは測れなかった。** ジャーナルの行は `atlas_turn` と `atlas_delegate` だけ（`atlas_verify` は記録されない）。12 秒は
  待ちの上限で、実際の秒数は run ledger（`ledger.model({model:'atlas_verify'})`・開発表示の run 行）にしか残らない。**変えない**。
  最終回答の本文が検証の入力なので、検証を回答の前に走らせることはできず、短くする道は「回答を先に見せて、未達が出たら差し戻す」しか
  ない——それは仕様（読者が見る回答が後から変わる）の判断になるので、実測が取れてから別に訊く。
- **#8 DB 往復の並行化は見送り。** `openTurn`（課金）→ `reserveSpend`（費用の予約）、限度の `take` は共有枠 → 全体枠、はどれも前段の拒否が後段を
  止める順序で、並行にすると拒否された側の分を返す手続き（返金）が要る。待ちの内訳（秒）を測っていないので、台帳の整合を壊す価値のある短縮かは
  言えない。測る手順: `ai-proxy` の各 RPC の前後に経過時間を足して `usage_counts` に出す（次の課題）。

## 直したこと

1. **一時失敗の再試行を `provider-call.ts` の 1 か所に**（`transientRetry`・`isTransient`）。観測された失敗だけ（5xx・状態なし＝到達不能／ストリーム切断・
   per-minute の 429）を、待ちを置いて最大 2 回。タイムアウト・容量超過・quota・4xx・安全ブロックは再試行しない。前回の試行が要した時間より窓が
   残っていなければ試行しない。回数は `meter.retry`（応答の `meta.retries`、失敗時は `meta.retries` も）とログに残る。OpenAI・Anthropic・Gemini の
   呼び出し点が全部これを通る（Gemini の `geminiRetry` は同じものへの委譲になった）。
2. **2 手目以降の失敗の表示**: `stopped:'transport'` のとき、原因（`trace.transportErrorInfo` の文）・再送が効くか・集めた結果が下にあること
   を述べる（`js/atlas-agent.js transportSay`、`js/atlas-console.js` の回答文）。en+jp。
3. **要約の拒否**: 400 の本文が要約（`summar`）に触れているときだけ `summaryRefused` を立てる。以前は任意の 400 で isolate の寿命まで要約が消えた。
4. **キャッシュ**: 依頼の先頭に「変わらないもの」（レイヤー名一覧・委譲ポリシー）を 1 つの項目として履歴の前に置いた（`composeInput` の `stable`）。
   履歴の窓は 48 を超えた 1 件ごとに先頭がずれていたのを、56 を超えたら 48 に戻す（常に 48 以上・ずれは約 8 件ごと）。
   効果は本番で測り直す（下記）。
5. **添付**: OpenAI の Atlas ターンは PDF を最初の呼び出しで Files API に上げ（`expires_after` 1 時間・`purpose=user_data`）、以後の手は
   アカウントで署名した参照だけを送る（`doc-refs.ts`・`meta.docRefs`・`docRefs`）。全部が上がったときだけ参照に切り替わり、失敗すれば従来どおり inline。
   Anthropic・Gemini の添付は従来のまま（毎手 inline）。
6. **Anthropic 経路**: 会話の最後のブロックにキャッシュ境界（ターンのときだけ）／`server_tool_use`・`web_search_tool_result` を `provider_block`
   として持ち越す（次の手に検索結果が残る）／`pause_turn` を継続（上限は窓と費用の栅であって回数ではない）／`max_uses: 3` を外す。
7. **キャッシュ書き込みの単価**: 公式（platform.claude.com の prompt-caching「Pricing」・2026-11-26 読み取り）は 5 分 TTL の書き込みが入力の
   **1.25 倍**（1 時間は 2 倍）。`costMicros` は 1.0 倍で計上していたので 1.25 倍にした（`ANTHROPIC_CACHE_WRITE_X`）。
8. `ask.ts` の `/^Bearers+/i` を `/^Bearer\s+/i` に（`jwtSubject` は署名済みでない値を読むだけの早期用で、判定は `getUser`）。

テスト: `tests/atlas-mainloop-reliability-checks.test.mjs`（新規）・`tests/atlas-live-stream-checks.test.mjs`（要約を名指さない 400 の追加）。

  伸びないという 11-25 の記録と合わせ、提供側の規則か、前置きのどこかが手ごとに動いているか）。**次に見る**: 本番で、修正後の
  位置別の読み取り率（上の SQL をそのまま）。1 手目と 3 手目以降が同じなら、動いているのは tools／instructions の側。
