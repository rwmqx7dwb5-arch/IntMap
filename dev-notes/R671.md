## R671 — **上限は上限ではなかった——DEM タイル置き場は自分の数を守っていなかったし、峰を持っていなかった**

> 利用者の調査報告書:「スマホでズームやホバーに相当する操作が遅い。操作によってはブラウザ／ページが
> 落ちる。スマホのメモリを使い切っている可能性を疑っている。」
> ⚠ 端末は iPhone。**実機での計測は行わない**・**§4（横向きの計算予算）は対象外**、と利用者が指示した。

### 1. 上限が守られていなかった3つの扉（`js/map-readout.js`）

`_demCache` は「携帯 140 枚／それ以外 560 枚」という数を持っていた。守っていなかった。

| 扉 | 何が起きるか |
|---|---|
| trim が `'loading'` を飛ばす | 同時に出せる要求に上限が無かったので、480 枚頼むビルドは **trim が触れない 480 エントリ**を登録できる。trim からは免除だが**メモリからは免除されない**——届いた瞬間に 1 枚 262,144 B の `Float32Array` になる |
| 完了経路が trim しない | ビルドが終わっても常駐したまま。trim を回すのは「未キャッシュのタイルを訊く呼び出し」**だけ**だった |
| trim が挿入の**前** | 定常状態が「上限＋1」 |

**そして峰に上限が無かった。** DEM の要求は `new Image()` で、レンダラの画像キュー
（`js/app-body.js` の `_imgConcurrency`）を通らない。だから **要求したタイル1枚につき** Image・
在庫の応答・復号が1つずつ生きていた——**出ている要求1本につき**ではなく。

実測（出荷モジュールを vm で走らせ、偽の `Image` を数えた）:

| | 修正前 | 修正後 |
|---|---|---|
| 480 枚を一度に頼んだときに作られた `Image` | **480** | **24** |
| 全部届いたあとも `demElevAt` が即答するタイル（＝常駐） | **480 / 480** | **≤ 140** |

24 は `_DEM_HOSTS.length × 6`＝**選んだ数ではなく導いた数**。#R223 が同じバケットの 4 ホスト名に
散らしたのは HTTP/1.1 の 6 接続制限のためで、**ブラウザが実際に開ける本数なのだから、ここで抑えても
通す量は変わらない**。変わるのは峰だけ——同時に何個の Image・応答・復号を持つか。

置き場は状態を書き下した store になった（queued / loading / ready / failed）。上限は**状態が変わる
たびに**、**挿入したあとに**適用される。追い出しは **ready から**行い、in flight のものは他に出せる
ものが無いときだけ落とす（落としても即座には何も解放されず、取り直しの往復が増えるだけだから）。

### 2. pin はリースになった

#R221 の pin は Set 1本と、引数なしの `releaseDEMHold()` 1本だった。**2つのビルドが重なると、
先に終わったほうが相手の pin を外す。** pin が要るのはまさに2つ重なったときなので、必要な瞬間に
効かなくなる設計だった。

- 鍵は **token ごとに参照数**で持つ。あるビルドの解放が別のビルドの留め置きを外すことはない。
- **`warmDEMTiles` は必ず1本開く。** `hold` を渡さない6つの呼び出し元（可視領域・標高プロファイル・
  地形彫刻・日射・津波細分・経路プロファイル）も #R221 の保護を受けるようになった——
  「warm-up が自分で温めたタイルを追い出す」ループは、震度分布だけの問題ではなかった。
- **pin にも天井が要る。** 「trim から免除」は、天井が無ければ「無制限」と同じ文である。
  `_DEM_LEASE_MAX`（携帯 608／それ以外 2,112）は**震度分布1枚が留める作業集合そのもの**——
  `js/seismic.js` の `TILE_BUDGET`（480／1,600）＋ `TILE_BUDGET_FAR`（128／512）。⚠ これより
  小さくすると、フィールドが「要る」と決めたタイルを断ることになり、#R221 が直した同心円が戻る。
  数が2つのファイルにあるので、**検査 ⑨ が両者を突き合わせる**。
- **リースを離れたあとに届いた応答は捨てる**（`stale`）。取り消した仕事が、あとからデータを戻す
  経路になってはならない。

⚠ **同時要求に上限を付けると、上限が無ければ起こり得なかった止まり方が1つできる。** load も error も
発火しない `<img>`（携帯が回線を切り替えたときに残る接続）は 24 本の枠を1つ握ったままになり、24 本
揃えば DEM が完全に止まる。**自分の修正が作った故障なので、自分で答える**——45,000 ms（この
リポジトリのどの呼び出し元が渡す締切よりも長い。`js/viewshed.js`）で枠を返す。要求は**取り消さない**
——**手放す**だけで、届いたら上の `stale` の門が捨てる。検査 ⑫。

### 3. 分からないメモリ量を、余裕とみなしていた

`maxTileCacheSize` は `navigator.deviceMemory && navigator.deviceMemory <= 4` で分けていた。
**WebKit は `deviceMemory` を実装していない**ので iPhone では常に `undefined` で、`undefined&&…` は
偽——つまり「答えなかった端末」が「4 GB より多いと答えた端末」と同じ 1024 を取っていた。
⚠ 数値は #R21 のまま。変えたのは**未知の答えがどちらを選ぶか**だけ。

### 4. 計器が、自分で負荷を足していた（報告書 §7）

- **`?perf=1` が `CMD.detail` まで点けていた。** detail は `_contentSig` を通じて **source の payload
  全体に `JSON.stringify`** を掛ける。**HUD を見るための URL が、測ろうとしている負荷を自分で足す。**
  ⇒ 軽い段（`?perf=1`＝集計だけ）と重い段（`?cmdlog=1` / `?cmddetail=1`）に割った。
- **`sceneStats().tiles` は MapLibre 5 系にした時から常に 0 を印字していた**——
  `style.sourceCaches` は同梱の 5.24.0 の dist に**1回も現れない**（5.x は `tileManagers`）。
  ⇒ 表示中と待機を分け、**どちらの保持先も無ければ `null`**。取得できない量を 0 と書く計器は、
  「無い」と「取れない」を区別できない。統計は `getStyle()` のディープコピーではなく公開 API から
  取り、**どちらの経路で答えたかを名乗る**。
- **`setLayersOn` の A/B は復元ではなかった**——元から非表示だったレイヤーを点けて戻していた。
  id ごとに元の可視状態を控える。⚠ これは**描画を止める試験**であって**資源を解放する試験ではない**
  ことを、HUD 自身が本文に書く。
- **DEM 置き場の保持量は、どの計器にも出ていなかった。** レンダラのタイル数は自前の DEM について
  何も言わない——そしてそれが報告書の言うメモリだった。HUD に 1 行足した。

### 5. ホバー：規則を関数ではなく事実に付ける（報告書 §6）

`window._imPipGeo` は共有の点-多角形判定器で、**外接矩形を1つも持っていなかった**。
`countryGeo` は起動後 10m に差し替わって **258 feature・約 548,000 頂点**あり、数値レイヤー表示中の
画面外・レンダラのミスでは、そこを毎回線形に走っていた。

矩形は **`_imPipGeo` 自身**に付けた（`WeakMap`・座標配列がキー）。だから **5つの呼び出し元は
1バイトも変わっていない**——数値レイヤーの地点値・World Bank 面・タイムゾーン・データセンター。
⚠ **矩形は「断る」ためだけに使う**ので、答えは1つも変わらない。実測（実データ 847 feature の
ecoregions から 120 polygon・54,246 頂点）: **25,856,028 → 10,672 頂点読み取り（0.04%）**。

⚠ **同値性の検査が退行を1件見つけた**: NaN／null を含むリングを矩形で断ると、NaN の辺が交差数から
黙って抜けるので「閉じた環の交差数は偶数」が壊れ、**素朴な走査のほうが矩形の外に true を返しうる**。
使えない座標が1つでもある形には矩形を作らない。

⚠ `choroValueAt` の「直前に当たった国」の記憶は**入れなかった**——`find` は**最初に**一致した
feature を返す契約なので、記憶を先に試すと重なる輪郭がある場合に返る feature が変わる。
矩形を入れたあとの残りは 258 回の矩形比較で、548,000 頂点の走査は既に消えている。

### 6. 検査（`tests/r671-dem-store-checks.test.mjs` ⑪本・`r671-diagnostics-checks` ⑩本・`r671-hover-checks` ⑤本）

⚠ **ソースを読む検査は順序を見られない**（#R505）。**この欠陥は順序だった**（trim と挿入の順・
完了経路に trim が無いこと）。だから `js/map-readout.js` の factory を **vm で実際に走らせ**、偽の
`Image` を手で着火して、報告書が訊いている問いをそのまま訊く——バーストで何個の Image ができるか、
全部届いたあと何枚が常駐するか、エントリを失った応答が何をするか。**修正前 11/11 赤・修正後 11/11 緑**。

⑨⑩ だけは配線の事実なので別扱い: ⑨ は2つのファイルの数を突き合わせ、⑩ は **出荷している
`js/seismic.js` を acorn で構文解析**して「そのビルド自身の token を渡しているか」を訊く
（自分で token を束ねる fixture は、出荷側が何を束ねているか原理的に見られない——#R552）。

⚠ **既存検査を2本、主張を保ったまま書き換えた**:
`tests/r191` は「export されていること」を主張する文の**すぐ下で隣接する名前まで綴りで固定**して
いたので、正しい追加を欠陥として報告した（返り値を分解して名前の集合を訊く形に）。
`tests/r221` は `warmDEMTiles(...,true)` という**綴り**を固定していた（「pin を頼んでいるか」を
全呼び出しに対して訊く形に。4本目が pin 無しで足されたら落ちるので、こちらのほうが強い）。

### 7. 天井（#R491 の再演）

app-body への追加は shell の行数天井（`tests/r168` #8）に当たった。**余白は 0 行**だったので、
`_DEM_LEASE_MAX` は `_DEM_CACHE_MAX` と同じ行に、`_tileCacheMax()` は `_imgConcurrency` と同じ行に
畳み、散文は機構が住んでいる `js/map-readout.js` へ置いた。**app-body は HEAD と同じ行数**。
新しい2つの export（`lease token` / `demStoreStats`）は `direct`（shim を作らない側）にした——
shim は shell の行だから。
