## R351 — **器はあったが、中身が 1 行も無かった**

依頼は「IM-20260823-001 の **Phase B の残り**」——ingest・Event への割り当て・カテゴリ・
日本語訳・計測・保持。**UI は 1 バイトも変えない**（Phase D まで shadow）。

#R334 は 8 表・pgvector・RLS・pgTAP 123 件・18 媒体 / 33 フィードを本番に入れた。着手時の実測は

```
news_sources 18 / news_source_feeds 33 / news_articles 0 / news_events 0
```

——**器は完成していて、中身を入れるものが無かった**。作ったのは Edge Function 1 本
（`news-ingest`、11 本目）と、その論理を持つ `_shared/news-ingest.js`（**サーバー専用**）。

### ⚠ 沈黙で失敗する欠陥から始まった

`news_sources.domains` は `www.bbc.co.uk` の形で入っている。`normaliseUrl()`（#R334）は
ホストの `www.` を落とすので、正規化後の記事 URL は `bbc.co.uk` になる。素で突き合わせると
**18 媒体すべてが「これは自分の記事ではない」と判定され、ingest は 0 行を書く**。しかも
どこもエラーを出さない——「登録外のホスト」を数えるだけである。

⇒ 突き合わせる前に**両側へ同じ関数を掛ける**（`normHost`）。`tests/r351-checks ①` は
**素の比較が本当に外れること**まで書いてある（直したことではなく、直した対象を残す）。

### ⚠⚠⚠ #R76 の穴は「国」だけの話ではなかった

#R334 は「国レベルに解決された subject は座標が完全一致するので、距離ゼロを『近い』として
扱ってはならない」を突き止めた。実データで動かすと、**同じ形が組織で開いていた**——
`IntMapNewsGeo` が `kind:'org'` に解決した subject はその組織の本部座標なので、
**同じ会社についての無関係な 2 件は必ず距離ゼロ**＝閾値が最も低い `tight` に入る。

実測: Yonhap の «Samsung Electronics が株主還元に最大 110 兆ウォン» と
«Samsung SDI が Samsung Display 株を 4.45 兆ウォンで売却» が 1 件の Event になっていた。

⇒ **代表点しか持たない解決は 3 種類**——`country` / `admin1` / `org`。
`DEFAULTS.representativeKinds` がその一覧で、そこに入る種類は閾値を**上げる**側に入る。
`city` / `seat` / `flashpoint` / `feature` は「出来事が起きた場所」なので入れない。

### ⚠⚠⚠ 増分では、最初の 1 本が誰にも検算されていない

新着を候補 Event に載せる条件は「メンバーの 34%（`transitivity`）以上と一致すること」。
**メンバーが 1 件の Event では、その条件が 1 本の辺で必ず満たされる。** 決定の履歴が
そのまま原因を言っている:

```
592 Samsung SDI（別の発表）→ 新規 Event（メンバー 1）
591 URGENT             → SDI と一致 1/1 = 100%  ⇒ 参加
590 LEAD               → 2 件中 1 件と一致 50%   ⇒ 参加
588 2nd LD             → 3 件中 2 件と一致 67%   ⇒ 参加
```

`docs/NEWS-EVENTS.md` §5.3 は「edge を結んだ後に **cluster 全体**で再検証する」と最初から
書いていた。増分の側でそれをやる。**新しい定数は足さない**——同じ `transitivity` を、
育ったあとの塊の全員に当てる。他のメンバーの 34% 未満としか合わない者は外して自分の Event へ
移す。実測: 上の例では **SDI だけが外れ、残る 3 本は残った**。1 回の取り込みで 3〜4 件。

### ⚠⚠⚠ 「その媒体が書いた」は「それは記事である」ではない

#R334 は CNN の World RSS に混ざったアフィリエイト広告 6 件を見つけて、canonical URL の
ホストを完全一致で突き合わせることにした。実データで回すと、**同じ形が一段上で出た**。
`google_news_site` の `site:` 検索は「そのホストで索引されている何か」を返す:

| 落ちた形 | 実測 | 例 |
|---|---|---|
| 語数 5 未満 | 34 | `HILLEL ITALIE`（AP の記者ページ）/ `Tech Life`（BBC のポッドキャスト回）/ `FEIA.DE` |
| 定型の非記事表題 | 60 | `…: Profile and Biography`（**Bloomberg の寄与 99 本の 34%**）/ `About … (HBF.TO)` / `(EDITORIAL from …)` |
| 多主題のまとめ | 5〜6 | `PODCAST: …` / `…, Trump's Ballroom, More` / 要約が `The following is …` |

⚠ **語数だけでは 3 群を分けられなかった。** 語数 5 未満の 63 本を 1 本ずつ読むと、
Google News 経由の索引ページ 36・直接 RSS の非記事 18（**要約が 1 文字も無い**）・
**NYT の短い特集見出し 9（11〜27 語の要約を持つ）**。⇒ 3 つの独立した根拠で決める:
①語数 5 未満 ②ただし媒体自身の要約が 8 語以上あれば通す ③ただし canonical URL が無ければ通さない。
実測 63 本のうち **54 本を落として 9 本を通す**。

⚠⚠ **まとめ記事は「惜しいから残す」ではなく「橋になるから落とす」。** 実測で誤って結ばれた
塊の 1 件はこれだった——Reuters の «PODCAST: Trump tariffs hit Canada … and Somali piracy» が
**カナダ関税**と**ソマリア海賊**をつなぎ、NYT の海賊の記事が Quebec 分離独立の記事と同じ
Event に入った。#R334 が閾値 ×0.70 で観測した「両方に触れた 1 本が橋になる」の、
閾値ではなく**入力側**の形である。

⚠ **この門は近似**なので、落とした数と理由を `news_ingest_runs.rejects` に必ず出す。

### ⚠⚠⚠ タグを消してから実体参照を戻すと、1 文字も剥がれない

`refresh-news` の `stripHtml` は「タグを消す → 実体参照を戻す」の順である。フィードが
`&lt;a href=…&gt;` のように **HTML を XML の実体参照で包む**と、タグ消しの時点では `<` がまだ
`&lt;` なので何も消えず、そのあと実体参照を戻すので**生の HTML が本文として残る**。
実測: Google News 経由の約 300 件の description が `<a href="…">…</a>` そのものだった。

⇒ **戻してから剥がす。** 直した瞬間、**記事の地点あり 64.5% → 74.1%**——地点解析エンジンが
初めて要約を読めるようになったからである。⚠ そして Google News の description は要約ではなく
**リンクの一覧**なので、剥がしても保存しない（見出しの写しを要約として持てば、分類器が
見出しを二度数える）。

### ⚠⚠⚠ 黙って 0 件になる AI 経路を、もう一度作るところだった

翻訳の段は最初 **0 件**を返した。例外を握り潰していたので理由がどこにも残らない——
**#R334 が測った「`analyzed_by='ai'` が 1,651 行中 0 件」と同じ形**である。まず理由を
持ち帰るようにしてから走らせると `openai 403` だった。

`AI_MODEL` は Atlas 用の secret 1 つを 11 本の Function が読む形で、実測では
`AI_MODEL=gpt-5.6-terra` がこのプロジェクトの鍵で 403 を返す。`ai-proxy` はそれを知っていて
403/404 のとき `gpt-5.6-luna` へ 1 回だけ retry する (#R148/#R150)。
**`refresh-news` にはその retry が無い。** ⇒ `news-ingest` は ① `NEWS_TRANSLATE_MODEL` で
翻訳のモデルを独立に選べるようにし、② 同じ fallback を持ち、③ **失敗した理由を応答と
`news_ingest_runs` の両方に出す**。

### ⚠⚠ ついでに見つけた、リポジトリ側の欠陥

`origin/main` の `supabase/config.toml` で、**`[functions.aviation-feed]` に `verify_jwt` が
無かった**。#R347 (`routing-relay`) が #R341 (`aviation-feed`) の上に乗ったときの merge で

と書いたその欠陥が、その節の対象ファイル自身に起きていた。⇒ 復元した。

### 追記 — **有料な段だけ、別の間隔で**

#R351 の cron は `fetch` / `assign` / `prune` の 3 段だけだった。翻訳はこのパイプラインで
**唯一の有料な段**なので、cron に入れた時点で継続課金が確定する——だからそこだけを
残して、見積・上限・送信されるもの・代替案を示して利用者の判断を仰いだ。

選ばれたのは「**頻度を落として cron に入れる**」。⇒ `news-ingest-translate`（`7 * * * *`）を
追加し、`news-ingest-tick`（`*/20`）は 3 段のままにした。cron が 2 本になったのは、
**間隔が違う理由が違う**からである（収集は鮮度、翻訳は費用）。

### ⚠ 間隔を伸ばして安くなるのは、単価が下がるからではない

翻訳は **Event 1 件あたり**に払うもので、run の回数ではない。`source_title_fp` があるので
**代表見出しが変わったときだけ**払う（実測: 全体の取り込みが済んだあと、再翻訳が必要だったのは
**622 件中 18 件**）。間隔を 20 分から 1 時間に伸ばして安くなるのは、**1 時間のあいだに
代表見出しが 2 度変わっても 1 回しか払わない**からで、それ以上ではない。
上限 80 件/run は 1 日 1,920 件分なので、実測の生成量（約 620 件/日）に backlog は残らない。

止め方は 2 つある——`select cron.unschedule('news-ingest-translate');` か、
`supabase secrets set NEWS_TRANSLATE=off`。後者は cron を残したまま止められ、
`news_ingest_runs.notes.translate_skipped` に `not_configured` として残る。
