## R664 — **read が、自分自身を打ち切っていた**

〈#R622 の production verification。波レイヤーの 1 回目のトグルは**まだ失敗していた**——本番で 3 回中
3 回、赤いトーストが出てチェックが自動で外れ、2 回目は必ず成功する。#R622 が残した計器が
`state().failure = {why:"no_field", detail:"wave_height"}` と答えた〉

**実装の正本は [`docs/MAP-LAYERS.md`](docs/MAP-LAYERS.md) §7.14**（券の規則・窓の長さ・3 つの引き金）。
ここに書くのは**どうしてそうなっていたか**だけである。

### ① 本番検証が 2 度必要だった——#R622 が直したのは「同じ規則の別の実例」だった

#R622 は `js/waves.js` の `Promise.all([wave_height, wave_period])` を逐次読みに変え、**それは正しく、
その欠陥は実際に消えた**。消えなかったのは同じ規則のもう 1 つの実例で、**呼び出し元が違うので
一緒には直らなかった**——こちらの 2 本目は 2 変数ではなく、**同じ 1 変数への 2 回目の呼び出し**である。

⚠ **それが分かったのは本番で触ったときだけ**だった。ローカルの検査も CI も緑のままで、症状は
#R622 の前と 1 文字も変わらない（同じ赤いトースト・同じ自動オフ・2 回目は必ず成功）。
⚠⚠ **そして #R622 が入れた計器が無ければ、ここもまた当てずっぽうになっていた。** 以前の
`.catch(() => fail())` は 5 つの終わり方をトーストの 1 文にしていて、**リクエストも例外もコンソール行も
1 行も残さない**この欠陥は、そこからは原理的に見えない。`{why:"no_field", detail:"wave_height"}` は
「波高の場が返ってこなかった」と名指しており、探す場所を `js/waves-gl.js` ではなく `E.load` に決めた。
⇒ **理由を残す計器は、次のラウンドの調査費用そのものである。**

### ② read が、これから合流しようとしている当の read を打ち切っていた

```
0 ms    load(wave_height) — トグル。ready() が 340 kB の SDK を取りに行く
300 ms  load(wave_height) — 2 度目の paint からの、同じものへの 2 回目の呼び出し
609 ms  SDK が着き、両方の continuation が走り —— 両方が 3 ms で null（リクエスト 0 本）
```

`load()` は整理券を**呼び出しの側で `ready()` の前に**取る（`var mine = ++seq`）。ところが合流
（`reading[skey]`）は**ファイル名が確定する continuation の中**にある。だから 2 回目の呼び出しは、
**自分がこれから合流しようとしている read を、先に古くしていた**。job は起きて `seq !== mine` を見つけ、
「読み手はもう別のものを見ている」出口を通る——その代替は**この変数のどれかの frame** であって、
⚠ **何も読んだことのないモデルにはそれが無い**。合流した側も、同じ null を受け取る。

⚠ **同じ read への 2 回目の要求は「読み手が別のものを見た」ではない。もう一度訊いただけである。**
`seq` が答えるべき問いは「読み手はこれより新しいものを要求したか」で、**同じ read の再要求は
その問いに対して「いいえ」**でなければならない。

### ③ 「最初の 1 回だけ」の両半分は、冷たいものが 2 つあることから出る

- **窓の長さ = `ready()` の長さ。** SDK が冷たければ約 600 ms、**他の気象レイヤーが既に束を引いていれば
  metadata 1 本ぶん**（`sdk` / `sdkP` は**ページ単位**でモデル単位ではない）。
- **代替が空なのは `frames` が空な間だけ** ＝ **モデルにつき 1 回**。

両方が「最初の 1 回」と言うので、2 回目のクリックは必ず通り、海面水温・気温・風のどれかを先に点けると
**欠陥そのものが隠れた**。⚠ **「2 回目は成功する」は直った証拠ではなく、窓が閉じた証拠である。**

### ④ 2 度目の paint の引き金は 3 つあり、そのうち 1 つは起動時の復元を殺していた

`js/waves.js` が `paint()` を上げる経路は `styledata` / `moveend` / エンジン自身の `time` イベントの 3 つで、
**どれも実在する**。3 つ目は**冷えたインスタンス固有**——`setIndex` の番人が `i === idx && idxSet` なので、
**軸が着いたあとの最初の live ブロードキャストが、動いていない index に対して `index` + `time` を出す**。

⚠⚠⚠ **起動時の復元経路が落ちていたのはこれである。** 失敗はページ開始から **2,456 ms 後**——
人の操作ではない。**利用者が保存した状態から `dl-waves` が黙って外れていた**（トーストは出るが、
読み手はまだ地図を見ていない）。

⇒ **どれが先に来ても答えは同じでなければならない**ので、直しは 3 つの呼び出し側ではなく
`js/wx-ecmwf.js` の側に置いた。

### ⑤ 直しかた——リトライではなく、券を付ける場所を変える

**整理券を「呼び出し」ではなく「read」に付けた。** 券は read が同定される場所（`skey` が確定する
continuation）で発行し、**合流する呼び出し元は自分の券を取らず `renew(join)` で相手の券を更新する**。

券が担っていたものは 1 つも失っていない:

- 別のファイル・時刻・帯への read は今までどおり新しい券を取り、古い read を**キューに入る前に**
  打ち切る（#R299 の性質）
- `release()` は今までどおり飛行中の全てを追い越す（#R276 追記2）
- `ahead` の read は今までどおり `seq` に一切参加しない（#R310）

**できなくなったのは「read が自分自身を打ち切ること」だけ**で、既存の呼び出し側（気温・風・降水・
地点値）から見える挙動は 1 つも変わっていない。

⚠ **呼び出しの側で同定することはできない。** `i == null` は「軸が今いる時刻」であって解決は遅く、
軸が動いていなければ 2 つの呼び出しは同じ要求、スライダーを引きずっていれば 20 の別の要求である。
呼び出し側は `ready()` の前にその区別を付けられない——**合流が continuation に居る理由そのもの**。

### ⑥ 正しい変更で、検査 7 本が赤くなった

`js/wx-ecmwf.js` の**ソース文字列を固定していた**検査 7 本（r276 ⑱・r287 ⑧・r288 ⑦・r299 ⑥・
r310 ⑤⑥ ほか）が、この変更で落ちた。**#R488 の形**——綴りを固定する検査は、その規則が生きているかを
守れないので、**正しい変更を退行と呼び、死んだ規則は緑のまま通す**。

⚠ **綴りを満たすためにコードを歪めることはしなかった。** 7 本を「出荷モジュールを評価して**挙動**を
測る」形に書き換えた（#R505 の答えがここにも効く）。`tests/r664-checks.test.mjs` は同じ土台の上で、
ブラウザと SDK だけを stub した**このモジュール自身**に対して欠陥を再現し（①）、別の時刻の read が
今までどおり打ち切ること（②）・`release()` が今までどおり追い越すこと（③）・`ahead` が券を取らない
こと（⑥）を測り、さらに**出荷しているレイヤーを出荷している engine の上で、冷たい状態から、
3 つの引き金それぞれについて**点けてみる（④）。⑤ は引き金そのものが実在すること——冷えた軸で
最初の live ブロードキャストが `time` を再送すること——を測る。

### ⑦ 形として残すこと

- **「同じ規則の別の実例」は、呼び出し元が違うだけで生き残る。** #R622 は規則を正しく理解して
  1 か所を直したが、直したのは**呼び出し側**だった。規則そのものが壊れているとき、呼び出し側の
  修正は**その呼び出し側だけ**を守る（`.agents/rules/no-ad-hoc-hardcoding.md` §3 の 2 問目）。
- **本番でしか出ない欠陥に対しては、計器が唯一の投資対象である。** #R622 の `state().failure` は
  利用者に見える文言を 1 文字も変えずに、次の 1 件の原因を 1 回の再現で名指した。
- **「2 回目は成功する」を安心の材料にしない。** それは窓が閉じたことしか意味しない。
