〈依頼〉「構造改革とイノベーション。足し算。全権を委任する」。主題: 多段の問い（例「台湾海峡が封鎖されたら影響は」）で、Atlas が立てた計画（目標・手順・各手順の状態: 未着手／実行中／完了／失敗／観測できず）を地図の上の HUD に出し（iOS 風・控えめ・地図を覆わない・モバイル対応・絵文字なし）、各手順が地図に描いたもの（層・経路・ピン）と結ぶ（手順を押すとその描画へ）。計画の本体は Atlas 自身の宣言、状態は実行器の観測。「観測できず」を ✓ にしない。ターンが終わっても計画は会話の中で参照でき、各手順の結果は次の手のモデルに届く。手数の上限は触らない。

## 0. 測った・読んだ

- **計画を表す器が 1 つも無かった。** `js/atlas-agent.js` の 1 手は「最終回答か、道具の呼び出しか」で、`FINAL_SCHEMA` は `turn`・`answer_mode`・`final_text` の 3 欄。atlas-live-stream（#857）が地図に出したのは**操作**の開始と終了（`js/atlas-live.js` の HUD）で、その操作が問いのどの部分に仕えているか・まだ先の部分・うまくいかなかった部分は**モデルの中にしか無かった**。
- 次のターンの入力（`_agentInput`）は会話の履歴と地図の状態と添付の台帳で、**前のターンの作業の構造**は持たない。「さっきの手順 2」は何も指せなかった。
- 地図の HUD の色: `--glass-bg` / `--glass-border` はどこにも定義されておらず（`css/intmap.css` に無い）、HUD は常に代替の暗い背景で塗られ、文字は明るいテーマの `--text-main`（#1d1d1f）——**明るいテーマでは HUD の文字が暗い背景の上の暗い字だった**（スクリーンショットで確認）。計画のカードを同じ HUD に置くので、両方を両テーマで定義されている `--sidebar-bg` に替えた。
- 携帯（390 px）: HUD は上端中央。計画のカードを全幅にすると左の基図切替（サムネイル）と右の丸ボタンの列の下に入る（スクリーンショットで確認）。両側の列は各約 76 px なので、カードはその間の帯（`min(300px, 100vw − 156px)`）に置いた。

## 1. 作ったもの

**計画は Atlas の宣言（`js/atlas-plan.js` `PLAN_TOOL`）**
- `plan` 道具: `{goal, steps:[短い題], current}`。どれも任意で、各呼び出しは**変わったことだけ**を言う。最初の宣言は手順 1 の呼び出しと**同じ返答の中で**、次の手順へ移るときは `{current:n}` をその手順の呼び出しと同じ返答で。新しい `steps` を送れば計画を差し替える（題を変えなかった手順は観測を引き継ぐ）。計画が要らない問いには呼ばない——**決めるのは Atlas**。
- 計画の無い状態での `{current}`・範囲外の手順は型付きの注記（`no_plan` / `no_such_step`）で返し、何も変えない。

**ループ（`js/atlas-agent.js` runTurn、`opts.plan`）**
- 台帳が渡されたときだけ `plan` を申告する。位置は**基本の道具の直後・昇格した道具より前**で固定——提供元がキャッシュする接頭辞は毎手・毎ターン同じバイト。渡されない呼び出し元（node の検査・再生）では道具の列は以前と同一。
- `plan` の呼び出しは**返答の中の呼び出し順に**、呼び出しの組み立て（`plans` の map）の中で台帳へ適用する。だから同じ返答の後ろの呼び出しは、実行がどう並列になってもその手順に属する。`plan` は footprint `pure`（app に触れない）で、実行器には届かず、同一呼び出しの再利用（callKey）にも入らない。
- app に届く呼び出しは、実行の直前に `started`、判定の直後に `settled`。同じ呼び出しの再利用（#R489）は、その手順に**前回の判定**を置く。
- `endTurn(stopped)` でターンの終わりを台帳に告げる（step 0 の転送失敗も `error` で）。

**台帳（`makeAtlasPlan`。DOM なし）**
- **状態は観測**: 手順の状態は、その手順の間に走った呼び出しのうち**能力に届いたもの**（結果に `capability` がある＝実行器が判定したもの）から導く。能力ごとに**最後の試み**が残り（失敗の後の再試行が成功すれば成功）、手順は**最も悪いもの**——実行中 → 失敗 → 停止 → 入力待ち → 一部のみ → 観測できず → 完了。`opState`: `unobserved`→観測できず、`partial`→一部のみ、`needs_input`→入力待ち、`cancelled`/`superseded`→停止、`ok:false`→失敗、それ以外→完了。**`unobserved` と `partial` は決して完了にならない**。
- 呼び出しが無い手順は、ターン中のいまの手順なら「実行中」、通過した（current にした）手順は「操作なし」、触れていない手順は「未着手」。
- **どの手順に属するかは、そのターンで `current` を述べたあとだけ。** 述べていないターンの呼び出しを、前のターンが残した手順に入れない（さもないと無関係な次の質問の操作が古い計画に混ざる）。
- ターンの終わりで判定の無い呼び出しは、停止なら「停止」、それ以外は「観測できず」（`not_settled`）。背景で続く操作（`status:'running'`）も、終わりを見ていないので「観測できず」（`still_running`）。
- **モデルへ戻る**: `plan` の結果が台帳の写し（`forModel()`）を返し、console の `_agentInput` が**毎手の tail** に `promptBlock()` を載せる——目標・各手順の状態・能力ごとの最後の判定（前のターンのものは `[earlier turn]`）・いまの手順・「このターンで current を述べるまで呼び出しはどの手順にも属さない」。tail はキャッシュされる接頭辞の後ろなので、キャッシュは動かない。

**地図の上（`makePlanView`、`js/atlas-live.js` の HUD の列）**
- カードは HUD の列に立つ（atlas-live-stream が計測で決めた場所——デスクトップは下中央、携帯は上端）。ヘッダは目標と「完了数／手順数」（失敗があれば赤、観測できず・一部のみ・入力待ちがあれば橙）、たたむ／開く、×で隠す。手順ごとに印（完了だけが緑の ✓、失敗・停止は赤の ×、一部のみ・観測できずは**橙の輪**、未着手は灰の輪、操作なしは破線、入力待ちは青の輪、実行中は回転）と状態の語。
- **ターンが終わると HUD は休む**: これまでは 2.6 秒後に消えていた。計画が出ているときは、生きた語と操作のチップだけが退き、計画は**たたまれて残る**（押せば開く）。隠したら、次に計画が宣言されるまで出ない。HUD は地図へのクリックを通し、カードだけがクリックを受ける（消えている間はカードも通す）。
- **手順が描いたもの**は地図を見て見つける: 台帳の `started`／`settled` の時点で、レンダラに申告された面（`render.drawn`）の指紋（地物数＋先頭の地物）とオブジェクト一覧（`IntMapObjects.list()`）を取り、その間に**現れた／変わったもの**がその呼び出しの描画（`drawnDiff`）。地図を生んだと判定された呼び出しは、その時点のカメラも持つ。手順を押す（Enter／Space も）と、①まだ地図にある面の外接矩形へ（`bboxOf`）、②無ければ一覧に残っているオブジェクトへ、③それも無ければ描いた時点のカメラへ移る。描いたものが無い手順は押せない。⚠ 並んで走った呼び出しは共通の窓の変化を両方が持つ——描いていない時刻のものは持たない。
- 文字は DOM で組む（モデルが書いた題を markup として解釈しない）。言葉は en+jp（`CONSTITUTION.md` §7）。作業一覧の「次: …」では `plan` を「計画を立てる」と言う（能力ではないので category が無く、「作業中」になっていた）。
- `window.IntMapAtlasDebug.plan()` が HUD と同じ写しを返す。

**変えていないもの**
- 上限（`maxSteps`・`maxToolCalls`・`TURN_MAX_CALLS`・`maxOfferedTools`）は読みも動かしもしない。`plan` の呼び出しはほかの呼び出しと同じく 1 回として数える（Atlas が選んだ呼び出しである）。
- `FINAL_SCHEMA`・ai-proxy・観測器・実行器は無変更。Edge Function の配備は要らない。
- 能力の宣言（`js/atlas-cap-*.js`・`atlas-capabilities.js`・`atlas-caps*.js`・`atlas-catalog-text.js`・`atlas-toolsurface.js`）は触っていない——別作業 atlas-capability-single-source が作り替え中で、`plan` は能力ではなくループの道具（`read_result` と同じ扱い）なので、その必要も無かった。`js/atlas-state.js` も触っていない。

## 2. 採らなかった案

- **`FINAL_SCHEMA` に `plan` 欄**: 返答の JSON は呼び出しより後に書かれる文の器で、計画は呼び出しの前に決まるもの。厳格な schema と 3 社の出力順（ai-proxy）にも触れる。道具なら呼び出しの列の中に順序ごと入る。
- **実行の記録から手順を組み立てる**: それは計画ではなく履歴。まだ先の部分も、うまくいかなかった部分の意味も持たず、コードが Atlas の代わりに問いを分解することになる（`CONSTITUTION.md` §5）。
- **手順の状態をモデルに申告させる**: 観測器が嘘をつかないように直してきたもの（#R736・#R742・#R768）の上に、観測しない申告を載せることになる。
- **能力ごとに「何を描いたか」を申告させる欄**: すべての能力に欄を足す仕事で、申告と実際がずれる場所をもう 1 つ作る。描いたものは地図を見ればわかる（`js/atlas-state.js` の取り消しが同じ見方をしている）。
