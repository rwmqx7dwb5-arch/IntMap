### ① 「地形をリセット」は 1 度も何もしていなかった — 同じ door の抜けは 3 回目

パネルの handler はこうだった。

```js
panel.querySelector('.tw-resetT').onclick=()=>{ if(!G) return; pushUndo();
  sculpt=new Float32Array(G.NX*G.NY); levees=[]; solve(); };
```

`sculpt` と `levees` は確かに空になる。しかし**この場を読む側は誰も新しい値を見ない**——
`editField()` は `editStamp` でメモ化されており、それを進めるのは `editDirty()` だけだからである。
`editField()` を読むのは、

* ソルバ（`surface()` = `G.base + editField()`）、
* 座標読み出しのフック（`IntMapElevEdit` → `js/map-readout.js`）、
* 3-D 地形の raster-dem タイル（`editStamp` がそのままタイルの版）

の 3 つ全部。つまり**押しても、絵も、標高の読み出しも、3-D の起伏も、1 ミリも動かない**。

⚠ **これは同じ door の 3 回目の抜けである。** #R255 は Atlas の `brush()` が、#R258 は `addLevee` が
同じ呼び出しを落としていて、どちらも `editDirty` の上に「**この関数を通らない道は無いこと**」という
注記を書いた。注記を 4 本目にしても 4 回目が来る。**リセットを 1 本の関数にして、ボタンと Atlas の
door の両方がそれを呼ぶ**——`resetTerrainNow()`——ようにした。呼び忘れる先が構造として無い。

### ② 「水がある直線を境に一切描画されない」— 格子が標高キャッシュを追い越していた

#R267 で作業矩形の外へ**同じ格子を継ぎ足す**ようになった。その `growBasin` は、新しい範囲の
**全体に 28×28 の固定格子**でタイルを温め、そのあと**新しいセル全部**に `demAt` を掛けていた。

```js
const STEP=Math.max(1,Math.round(Math.max(nNX,nNY)/28));
…
if(pts.length) await warmDEMTiles(pts.slice(0,1600),B.z,25000,null);
```

壊れるところが 2 つある。

* **28 は「セル」の密度で、覆わなければならないのは「タイル」。** z14 のタイルは赤道で約 2.4 km。
  basin が川を追って 200 km に育つと 1 軸あたり 83 タイルあり、それを 28 点でしか叩いていない——
  **3 枚に 2 枚は一度も要求されない。**
* **DEM キャッシュは 560 タイルの LRU**（`js/app-body.js` `_DEM_CACHE_MAX`）で、ここは何も pin して
  いない。だから**要求したタイルすら、bed を読む前に追い出され得る。** #R264 が精細化窓について
  書いた教訓と同じ形である——**`demAt` の `null` は「そこに地面が無い」より「キャッシュに無い」で
  ある方が多い。**

どちらの経路でもそのセルの bed は NaN になり、ソルバは **NaN に触れる面を全部閉じる**。これは
#R265 の設計どおりで、正しい。そして**未取得のタイルはメルカトル上の矩形**である。だから水は
その辺でぴたりと止まる——**谷の途中を横切る直線、その先には何も描かれない。** 報告の言葉どおり。

→ 新しい地面は **DEM タイルのブロック単位**で読む。1 タイルにつき 1 点だけ温め、ブロックは LRU に
丸ごと収まる大きさにし、**キャッシュに載っている間に**そのブロックのセルを埋め、それでも `null` の
ままだったものは**1 回だけ**狙って温め直す。ブロックの上限はプラットフォーム別
（携帯 100 / デスクトップ 280 に対し LRU は 140 / 560）で、`tests/r268-checks` はこれを**数値では
なく関係として**検査する（#R264 の教訓）。

⚠ **そして、残った穴は数えて印字する。** 旧コードも `basinVoid` に数えてはいたが、パネルには
**一度も出していなかった**。5 ラウンド幾何の側を探し続けた理由の一部はそれである。

### ③ 盛る／削るの着色はトグルになった

`sculpt` と堤防の合成場は、編集した所を茶／青の淡い被せで描いている。それは「どこを触ったか」の
答えで、地形が出来上がったあとは「その地形はどう見えるか」の邪魔になる（起伏そのものは #R255 以来
3-D の relief と陰影が持っている）。パネルにチェックボックスを 1 つ足し、**この被せだけ**を止める。
`sculpt` にも堤防にもソルバにも触れないので、切っても数字は 1 ビットも変わらない。設定は
`localStorage` に残る。

### ④ 年降水量の凡例が「降」だった — 文字列を表として index していた

`window._registerLayerOpacity(id, names, layerIds, cbId)` の `names` は
`LA('Annual precipitation','年降水量',…)` の**表**である。`js/precip-annual.js` は**解決済みの文字列**
`NAME()` を渡していた。`ensureGenericLegend` は

```js
GENERIC_LEG[id]=[names[0], names[1]||names[0], names[2]||names[0], …]
```

を作る。文字列に対して `names[1]` は **2 文字目**である。だから凡例の見出しは言語 index で 1 文字ずつ
選ばれ、英語で「A」、日本語で「降」、ドイツ語で「水」、ロシア語で「量」になっていた。

呼び出し側を表に直し、**受け側でも文字列は「全言語で同じ 1 つの名前」として正規化**した。片方だけ
直すと、次に文字列を渡した人がまた 1 文字を見ることになる。

### ⑤ 宇宙基地・地上局 — ライブがスナップショットを「置き換え」ていた

#R266 と**同じ文（外交公館の側だけ削ったもの）**が再送された。だからまず測った。

| 見ている所 | ソースの件数 | 凡例 |
|---|---|---|
| 本番・初期の全球ビュー | **13,310**（描画 2,548） | 同梱スナップショット |
| 本番・z6 日本 | **100** | ライブ |
| 本番・z10 東京 | **1** | 同梱スナップショット |

つまり「何も出ない」ではなかった。しかし **z6 日本ではスナップショットが 102 件を置いた直後に
ライブの 100 件が上書きしていた**——ビューポートの問い合わせは全球スナップショットの上位集合では
ない（`out center 1200` の上限、bbox の丸め、タグが編集されて外れた object）。**ズームすると絵が
減り得る**のは、この層の趣旨と正反対である。→ **OSM id で合成**し、凡例も「ライブ＋同梱の合成」と
言う。読者がズームして**減ることはもう無い**。

データの薄さの方も測った。東京 z10 の枠で `man_made=satellite_dish` は **2 件**しかない。一方
`communication:satellite` は全球で **1,861 件**あり、そのうち **960 件は `man_made=antenna`**——
つまり従来のタグ集合には**見えていなかった本物の地上局**である。ライブ問い合わせと
`scripts/build-osm-sparse.mjs` の両方に足し、同梱スナップショットを再構築した：
**13,310 → 14,965 件**（地上局 9,977 → 11,621）。

### ⑥ 気象・災害警報 — 実際に叩いてから足した

「対応する国をもっと増やせ」も 2 回目である。今回は候補を**この app 自身の origin から実際に
リクエストして**選んだ。

| 機関 | 結果 |
|---|---|
| `api.weather.bom.gov.au/v1/warnings` | **200 · ACAO `*` · 4 KB** → オーストラリア、直接 |
| `apiprevmet3.inmet.gov.br/avisos/ativos` | **200 · ACAO は当方の origin** → ブラジル、**ポリゴン付き** |
| `data.weather.gov.hk/…?dataType=warnsum` | **200 · ACAO `*` · 161 B** → 香港、直接 |
| `alerts.metservice.com/cap/rss` (NZ) | 200 だが ACAO が `about.metservice.com` → ブラウザからは読めない |
| `mausam.imd.gov.in/api/…` (印) | **401「IP needs to be whitelisted」** |
| `ws.smn.gob.ar/alerts/type/AL` (亜) | 503 |
| METMalaysia / SAWS / CONAGUA / BMKG | 401 / 404 / 500 — 公開エンドポイントを見つけられず |
| **WMO SWIC**（`severeweather.wmo.int` の GeoServer WFS） | 200 で **51 機関 4,028 件のポリゴン**が本当に返る。ただし **35 MB**（フィルタ無しでは 420 MB）で `Access-Control-Allow-Origin: null`。**60 秒周期のリレーに載る大きさではない。** 次のラウンドが「思いつき」からではなく**この実測**から始められるよう記録する |

⚠ **そして、ヨーロッパは名目だけ覆われていた。** MeteoAlarm の 37 機関は**対応**していたが、
実際に取得していたのは `MA_DEFAULT` の 4 か国だけで、残り 33 は**タップされて初めて**取りに行って
いた。毎 tick 数か国ずつ取り切るようにし、凡例に「読めた数 / 全数」を出す。

**リアルタイム。** #R266 は間隔を 300 秒 → 60 秒にし、**HTTP キャッシュには触っていなかった**。JMA の
`map.json` も NWS も普通のキャッシュヘッダを付けて配っているので、**60 秒のタイマがブラウザの持って
いる複製を読み直す**ことがある。ライブの警報 fetch はすべて `cache:'no-store'` にした（JMA の
`area.json` ＝区域コードと名前の**定義**と、県境ジオメトリは除く。年単位でしか変わらない）。
パネルには**最終取得時刻**を出す——「追い付いていない」は読者が確かめられる事実であるべきだから。

**タップ。** #R266 は同じ文を読んで grouping を書き、確かに都道府県でまとまってはいた。今回、
何も触る前に本番で測った：**日本のタップは 785 行・HTML 111,000 文字**、Hokkaido の折り畳みを開くと

```
宗谷地方 洪水 · 宗谷地方 暴風 · 宗谷地方 濃霧 · 稚内市 洪水 · 稚内市 暴風 · 稚内市 濃霧 ·
猿払村 洪水 · 猿払村 暴風 · … +170
```

——**まさに指示が言っている市町村の列挙**が、#R266 が見た所の 1 段下にあった。直したのは 2 つ。

* **1 つの単位は 1 行で、その災害はチップで並べる。** 「宗谷地方 洪水／暴風／濃霧」は 3 行ではなく 1 行。
* **間の段を作る。** 各行は `sub` を持つ——JMA の class10 地方（宗谷地方）、BoM の警報種別、INMET の
  警戒レベル。3 段目を持たないフィードでは `sub` は区域そのものなので、どこも退行しない。
  既定の見え方は **都道府県 → 地方**、市区町村はもう 1 段折り畳みの中に**全部**ある。

すべてのフィードがこの 1 つの renderer を通るので、「どの国でも」は自動的に満たされる。

### ⑦ 年で変わることに意味があるレイヤーを全部変えられるようにした

**NASA GIBS の 6 ラスタ**は「今日−2 日」に固定されていて、日付を選ぶ手段が無かった——海氷密接度、
海面水温**偏差**、NDVI、土壌水分、CO、エアロゾル指数、つまり**年ごとの差こそが主題**の層である。
ピッカーを付けるには 1 つだけ推測してはならないものがある：**その製品がどの日付を持っているか。**
範囲を捏造したピッカーは、空の海を出して「データ」と言う。

GIBS は範囲外の日付に **404**、範囲内に **200** を返す。`scripts/probe-gibs-range.mjs` はそれを使って
**実リクエストの二分探索**で期間を求め、`data/gibs-range.json` に書く。それが見つけたもの：

* `MODIS_Terra_NDVI_8Day` は **2000 年からではなく 2025-02-18 からのローリング窓**。
* `AMSRU2_Soil_Moisture_SCA_Day` は **2025-09-01 で終わっている**。2026 年の日付はすべて 404。
  つまり**土壌水分レイヤーは、出荷時の設定（今日−2 日）では何も描いていなかった**——静かに。
  既定を「その製品が実際に持つ最新の日」にすることが、そのまま直しになる。凡例は期間を印字し、
  終わっている製品はオレンジでそう言う。

⚠ ここで**自分の計器に 1 度掴まった**。2 層を同時に点けると、1 つ目が fetch を始めて「もう試した」
フラグを立て、2 つ目は**まだ着いていない答え**として `null` を受け取り、**ソースを貼り直さなかった**：
ピッカーは 2025-09-01 と表示し、タイルは 2026-08-17 を要求し続けていた。**フラグではなく飛んでいる
Promise を共有する**のが答え。実測で貼り直しを確認してある。

ほかに 2 エポックのもの：**夜間光**（`VIIRS_Black_Marble` は 1 タイルずつ叩いて **2012-01-01 と
2016-01-01 だけが 200**、他年は 404）、**ESA WorldCover**（Terrascope が v100=2020 と v200=2021 の
両方を配っている。レイヤー名は Terrascope 自身の「Invalid LAYER parameter」応答の一覧から読み、
タイルを取って確かめた）。既に年・月を選べたもの（世界銀行の全指標 #R266、年降水量 #R266、
ケッペン、米大統領選挙、海流の月、気温／SST／積雪／AOD／降水の日付、歴史的国境）はそのまま。

### ⑧ 旧ユーゴの言語を 1 つにまとめるのをやめた

`scripts/build-culture.mjs` は Serbian / Croatian / Bosnian / Montenegrin / Serbo-Croat を**全部 `sh`**
に入れていた。`Intl.DisplayNames.of('sh')` は日本語で**「セルビア語 (ラテン文字)」**、英語で
「Serbian (Latin)」——だから**クロアチアの地図ラベルがセルビア語**だった。不正確であり、名称として
危うい。

出典は分けている。「Bosnian (official) 52.9%, Serbian (official) 30.8%, Croatian (official) 14.6%」
——#R266 が英国について書いた規則の逆側である：**出典が分けていないものを地図が分けてはいけない**
なら、**出典が分けているものを地図がまとめてもいけない。** `sh` は「Serbo-Croat(ian)」と書いてある
行にだけ残る（スイス・スロベニア・モンテネグロ）。**塗りは 1 色のまま**（`LANG_ONE_COLOUR`）——
指示どおり、絵は割らない。

再構築後：SRB→sr 88.1 %、HRV→hr 95.2 %、BIH→bs 52.9 %、MNE→sr 42.9 % / **cnr 37 %**。
`cnr` は `Intl` が日本語で「セルビア語 (モンテネグロ)」と言うので、これも自分で名前を持つ。

⚠ **ついでに測ったら、12 の言語コードが全言語で生のまま出ていた**：`ff` `rar` `gil` `niu` `bi` `na`
`pau` `mh` `tvl` `tpi` `kl` `dz`。Chromium は CLDR の「modern」部分集合しか積んでいない。しかも
**11 個は、ある国の第一言語**（キリバス・ナウル・バヌアツ・パラオ・マーシャル・ツバル・パプア
ニューギニア・グリーンランド・ブータン・クック諸島・ニウエ）。9 言語ぶんの名前を持たせた。

### ⑨ ポップアップに棒グラフとデータの年

宗教・言語の構成は数字の列だった。それは「48.6 % と 46.4 % はほぼ同じ」も「79.8 % と 2.3 % は桁が
違う」も**同じ見え方になる**唯一の形式である。各行にその国の最大シェアで正規化した棒を付けた。
年は Factbook 自身の「(2011 est.)」から `scripts/build-culture.mjs` が取り出して `y` に持つ
（宗教 186/202・言語 90/196）。**年が書かれていない出典には年を書かない**——「年の記載なし」と出す。
`sikh` と `unspecified` は data には有るのに色も名前も無く、両方「その他」に落ちていた。名前を付けた。

### ⑩ そのほか

* **GDP 成長率**：`[-6 赤 … +9 緑]` は 0 が黄でも緑でもなく、**−1 % と +1 % が同じ暖色の濃淡**だった。
  0 を白に、負を赤に、正を青に、0 について対称に。検査は**配色ではなく指示の性質**（0 は白／負は
  赤寄り／正は青寄り／0 から離れるほど白から離れる）を見る。
* **レイヤー検索の ×**：2 つある検索欄の両方から背景の円板を外した。
* **年降水量のホバー数値**：`valueAt` は #R266 から**正確な点値**（絵ではなく 8bit の log(mm) 格子）を
  持っていて、誰も訊いていなかった。座標行に「1,429 mm/年 · 1981–2010」のように出す。年が違えば
  数字の意味が違うので、年も一緒に出す。
* **年降水量のサムネイル**：この層は `js/layer-previews.js` に**行が無かった**。実際にこの app を
  Playwright（実 Chromium）で開き、モンスーンアジアの上でこの層だけを点けて撮った。作り直し方は
  `scripts/shot-layer-preview.mjs` として残す。⚠ 最初の 1 枚は**既定で点いている海底ケーブル層**が
  全面に色線を引いていて、2 枚目は**セレクタで隠す一覧が地図の祖先（`.operation-room`）に当たって**
  真っ白だった。canvas の祖先チェーンの**兄弟だけ**を隠すのが正解（`intmap-headless-preview-limits`）。
* **カテゴリ 4 件**：`wbforest` 森林面積率 → 地形・土地被覆（`worldcover` の隣）、`wbagri` 農地率 と
  `gxsoil` 土壌水分 → 農業（`wbagremp` の隣。土壌水分は自分の説明文が「干ばつ・農業の指標」と
  言っている）、`wbpm25` PM2.5 → 気候・大気（AOD・UVエアロゾル・CO と同じ棚）。#R233 の 7 行と
  #R254 の一覧は動かしていない。**同じ id が 2 つの群に書かれていないこと**も検査に足した
  （`order.push` は移動なので、2 つ書くと後の 1 つにしか出ない）。

### 測ったもの / 残っているもの

* **本番で測ってから直した**：宇宙基地レイヤーの 13,310 / 100 / 1 件、日本のタップの 785 行・
  111,000 文字、`man_made=satellite_dish` 2 件 対 `communication:satellite` 1,861 件。
* **自分の計器に掴まった**：GIBS の範囲を待つ 2 層目が `null` を受けてソースを貼り直さなかった件
  （ピッカーとタイル URL が別のことを言っていた）と、ブロック上限 280 が**携帯の LRU 140 に入らない**
  件（`tests/r268-checks` が落ちた）。

### R268 追記 — 年を変えられる層をパネル全体で数え直したら、残っていたのは 1 km 人口密度だった

出荷後に「年を変えることに意味があるレイヤー」をパネル全体で突き合わせた。結果は 3 通りに分かれる。

* **既にマスタークロックで変えられる**: 1 人当たり GDP・合計特殊出生率・人口・平均寿命・軍事費。
  #R94/#R200 の `js/time-countries.js` が、時計が過去の年へ行くと**その年の世界銀行の実数**を
  `countryStats` に重ねる——choropleth も国カードも一覧も、その年の世界になる。
* **年系列そのものが無い**: HDI（UNDP）と民主主義指数（EIU）。#R94 は「WB の年系列を持たない指標は
  **間違った年でラベルし直さない**」と書いてあり、それは正しい。凡例は今も「2022 UNDP」「2023 EIU」と
  版を明示している。
* **本物の穴が 1 つ**: **1 km 人口密度（`popgrid`）**。GPW は GIBS に**エポックごとに別プロダクト**として
  載っている（`GPW_Population_Density_2000` … `_2020`）のに、この層は 2020 に固定されていた。
  1 タイルずつ叩いて **2000 / 2005 / 2010 / 2015 / 2020 が全部 200** を確認し、凡例に年セレクタを付けた。
  実測: 2020 → 2000 でソースの URL が `…_2020/…` → `…_2000/…` に入れ替わる。

⚠ **「年を変えられるか」は層ごとに 3 通りの答えを持つ**——同じ問いに「クロックが持っている」「データが
存在しない」「本当に抜けている」が混じっている。一覧を作って 1 本ずつ当たらないと、抜けている 1 本は
「他のと同じで大丈夫だろう」に紛れる。
