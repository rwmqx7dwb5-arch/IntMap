## R339 — **追跡をやめるコミット自身が、原本へ早送りできない**

> 「`node scripts/master-sync.mjs --sync` が繰り返し塞がれていて、そのたびに
> `scripts/backup-usb.ps1` が `RESULT skipped master-not-synced` で終わる
> ——つまり USB バックアップが黙って行われていない。」

#R338 の診断は正しく、処置（`.gitignore` ＋ `git rm --cached`）も正しい。**それでも詰まりは直らない。**

### 早送りは履歴の再生ではない

`git merge --ff-only` は **HEAD の木から目標の木への 1 回の checkout** であって、間のコミットを
順に適用するものではない。だから `.claude/launch.json` を木から外すコミットは、**原本でも
そのファイルを消さねばならない**。そして git は消せない:

| 原本側の状態 | git の答え |
|---|---|
| 追跡されていて、ローカルで変更されている | `error: Your local changes to the following files would be overwritten by merge:` |
| `git rm --cached` 済み（＝追跡外・まだ ignore されていない） | `error: The following untracked working tree files would be removed by merge:` |

**合成リポジトリで両方とも実測した。** つまり #R338 だけでは、原本は**その 1 コミットの境界で
止まり、そこから動けなくなる**——断続的だった詰まりが、**その一点で永久化する**。

### だから中身は `--sync` が運ぶ

`scripts/master-sync.mjs` に `MACHINE_LOCAL`（**現在 1 件**）を宣言し、早送りが拒否されたときだけ:

1. 中身を**バイト列のまま**退避（文字列にしない＝改行も文字コードも触らない）
2. 追跡されていれば `git rm --cached`、ディスクからも消す
3. 早送りを再試行
4. `finally` で**必ず**書き戻し、**書けたことではなく SHA-256 が一致することを確かめる**

**commit もしないし、捨てもしない**(§6)。§6 が守られたことは「他セッションの中身が
byte-for-byte で出てくる」という等式で測る。

### ⚠ 救済は「git の答えへの反論」ではない

発動するのは、**git が名指ししたパスが 1 つ残らず**「宣言済みのマシン固有」かつ
「origin/main が追跡をやめた」ものであるときだけ。1 つでも外れれば**拒否のまま**報告する。
`origin/main` がまだ追跡しているパスは**わざと対象外**——書き戻せば、そのコミットが
そのファイルについて言っていた内容を捨てることになる。

これを緩めると「都合の悪い変更を上書きする道具」になる。#R339 の検査 ③⑤ がその境界を測っている。

### 原本は実際にこの境界で詰まっていた（2026-08-23）

着手時の実測: 原本は **R325→R335 の 4 コミット遅れ**、`.claude/launch.json` に他セッションの
**3 件**（`intmap-r328-pwtest` / `intmap-preview-r349` / `intmap-preview-r328`——いずれも
`C:/Users/.../Temp/intmap-worktrees/…/dist` への絶対パス）。**手で越えた**——退避 → `checkout` →
早送り → 書き戻しで、**115 件すべてを byte-for-byte 保全**（tracked 側の欠落 0・local 側の欠落 0）。
原本は R323 → R337 へ追いつき、`--check` は exit 0 に戻り、USB バックアップが再び動くようになった。

**その手作業をツールに入れたのがこのラウンドである。** 手で越えられる詰まりを手で越え続けるのは、
`master-sync.mjs` 自身の注記が言うとおり「**ツールを迂回する習慣を教える**」ことにほかならない。

### ⚠ 緑を信じず、3 通りに壊して赤を見た

| 壊し方 | 赤くなった検査 |
|---|---|
| 救済ごと無効化（＝ #R338 だけの世界） | ① ⑥ |
| 救済を**全パス**に発動させる | ③ ⑤ |
| 失敗時の index 復旧を消す | ⑧ |

### ⚠⚠⚠ ④ は当初「index も戻る」と主張していたが、実際には測っていなかった

復旧行を消しても ④ は**緑のまま**だった。理由: 混在した障害では救済が**そもそも始まらない**ので、
戻すべき `rm --cached` が存在しない。**git は両方の分類を 1 つのメッセージで名指しする**
（`local changes` と `untracked working tree files` が同時に出る）ことを実測したので、
「片方だけ救済して半解体で終わる」状態は**このスイートからは到達できない**。分岐した原本も、
パスを 1 つも名指しせずに `Not possible to fast-forward` で終わる。

半解体が起きうるのは**本番の競合**だけ——preview ツールは並行セッションがプレビューを開いた瞬間に
原本の `launch.json` を書くので、`rmSync` と再試行の間に**書き戻しうる**。
⇒ **④ の主張を「実際に測っている内容」へ書き換え、⑧ を「弱い主張だと明示した source 検査」として
分けた。** 消されたことは捕まえる、誤動作は捕まえない——**その差を検査自身に書いた。**
