## R404 — **地点解析の AI は「止められていた」のではなく、書かれた日から一度も動いていなかった**

**依頼**: 「ニュースの地点解析システムはAIを使うようにしろ。復活です。」

### ① まず測った——「復活」させる相手が 2 つあり、どちらも死んでいた

#R29 が「AI が第一手段・辞書がフォールバック」を作り、#R40 がその数日後に**読み出し**を止めた
（`USE_SERVER_NEWS = false`）。5 か月後の実測 (2026-08-24):

| 測ったもの | 値 |
|---|---|
| `current_news` の行数 | 1,548 |
| そのうち `analyzed_by='ai'` | **0**（`dict` 1,321 / `none` 227） |
| `news_articles` の行数 / 地点を持つ行 | 1,481 / 1,120 (75.6%) |
| そのうち `subject_type='country'` | **543**（地点を持つ行の **48.5%**） |
| `intmap-refresh-news` の cron | **今も 20 分ごとに走っている**（`fetched_at` は当日 08:20） |

- **止まっていたのは読み出しだけではなかった。** `analyzed_by='ai'` が 0 なのは cron の不調でも
  モデルの質でもない——`AI_MODEL=gpt-5.6-terra` がこのプロジェクトの鍵で **403** を返し
  （#R351 が特定済み）、`refresh-news` には `ai-proxy` が持つ 403 リトライが無く、
  `catch (_) {}` が理由ごと捨てていた。**書かれた日から一度も成功していない。**
- **そして UI が実際に読むのはそちらではない。** `NEWS_EVENT_MODE = true`（#R386）なので
  読者が見ているのは `news_events`（`news-ingest`）で、**そこは AI を 1 度も呼んでいなかった。**
- 決定論エンジンだけだと、地点を持つ記事の **48.5% が国単位**で止まる。国の代表点は
  「その国のどこか」としか言っていない。

⚠ `docs/NEWS-EVENTS.md` §12 は「`USE_SERVER_NEWS=true` に切り替えて完了としてはならない」と
明示している（永続 Event・カテゴリ・Source Registry・merge/split を失う）。**利用者に 3 点確認**し、
「`news-ingest`（現行の本番経路）／全記事に AI（#R29 と同じ）／記事モードは決定論エンジンのまま」を選んだ。

### ② 実装——`locate` 段（AI 第一手段・決定論エンジンはフォールバック）

`ORDER` は 7 段になった: `fetch` → **`locate`** → `embed` → `assign` → `link` → `translate` → `prune`。
`locate` が `fetch` の**後**なのはこの run で届いた記事も掛けるため、`assign` の**前**なのは
Event が AI の座標で組まれ、代表地点もそれで決まるようにするためである。

- 規則の正本は `supabase/functions/_shared/news-geo-prompt.js` **1 本**で、`refresh-news` と共有する。
  呼び出し側が足すのは**返し方だけ**——同じ散文を 2 か所に置くと、片方だけ直った日に
  同じ製品の 2 つの経路が同じ見出しを違う場所に置く。返し方が違うのは書き込み先の列が違うからで
  （`current_news` に種別の列は無い）、それは共有すべき事実ではない。
- 返答の検証は `_shared/news-ingest.js` の `parseAiPlaces()`。**Edge Function の中に置かない**——
  Node のテストから直接呼べる場所に置けば、返答の壊れ方を実データで試験できる。

### ③ 一番危ない罠は「入れる」側ではなく「消される」側だった

記事は保持期間の 72 時間ずっとフィードに居る。`fetch` は毎 run 決定論エンジンの結果を
`onConflict: url_fingerprint` で upsert しているので、そのままだと **AI が置いた座標を 20 分ごとに
踏み潰す**。`toArticleRow` のすぐ隣に「`first_seen_at` は**送らない**——送れば毎 run 上書きされる」
という #R351 の注意書きがあり、**同じ罠のもう 1 つの口**だった。

⇒ AI 済みの指紋については `subject_*` を**送らない**。⚠ PostgREST の一括 insert は**鍵の揃わない
オブジェクトを混ぜられない**（欠けた鍵は既定値か NULL で埋まる＝踏み潰しが名前を変えて戻ってくる）ので、
**2 本の均質な upsert に分けて**送る。

### ④ 記事の行を直すだけでは、地図には一生出ない

代表地点を選び直すのは `summariseEvent` を呼ぶ `assign` の**1 か所だけ**で、そこは
**所属が動いた Event しか数え直さない**（#R351 が「今この run で作った Event を数え直さない」で
638 件の無駄な UPDATE を消した、その最適化の裏側）。地点だけ変わって所属が動かない記事は
その網に入らない。⇒ `locate` が置き直した記事 id を `assign` に渡し、`finalOf`（**実 ID に解決済み**。
仮の負 ID で引くと何も更新されない）から `dirty` に足す。

### ⑤ 「AI が見た」と「AI が置いた」は別の列（#R394 の形をもう一度作らない）

| 列 | 意味 |
|---|---|
| `subject_located_by` | いま入っている座標を**誰が置いたか**（`ai` / `dict` / `none`） |
| `subject_ai_at` | AI が**この記事を見た時刻**（null＝まだ見ていない） |
| `subject_locator` | AI が答えたときの `provider:model` |

2 つ目が要るのは、**AI が「場所の無い記事」と判断したものを二度と送らないため**である。
`subject_located_by <> 'ai'` で候補を引くと、置けないと判断された記事を毎 run 送り直し、
**上限を同じ記事で使い切って新しい記事に一生届かない**。
⚠ AI が省いた記事の決定論エンジンの答えは**消さない**（上書きするのは AI が場所を返したときだけ）。
⚠ 返答が届かなかった batch では「見た」印を**押さない**——押すと、一度も見られていない記事が
永久に候補から外れる。

### ⑥ 確度は自己申告させず、一致を測る

模型の自己申告は較正されていないのに、`location_confidence` として画面に出る。代わりに、
独立に走っている決定論エンジンと**一致したかを測って**入れる——50 km 以内なら 0.95、
相手が答えを持たなかったなら 0.8、50 km を超えて食い違ったなら 0.7。理由も
`subject_reasons` に残る（`agrees-with-gazetteer` / `differs-from-gazetteer` ＋ 相手の名前と距離）。
2 つの別々の仕組みが同じ場所を指したことは後から人が確かめられる本物の証拠であり、
**食い違った行はそのまま運用者の待ち行列**になる。

### ⑦ 種別の語彙がずれると、AI の都市が辞書の国に代表を譲る

`summariseEvent` は「具体性 × 支持」で代表地点を選ぶ（`KIND_RANK`）。AI が語彙の外の種別を
返すと具体性が 0 になり、**同じ Event の中で、決定論エンジンが置いた国のほうが勝つ**。
⇒ AI に渡す語彙は `js/newsgeo.js` の `KIND_LOCAL` と同じにし、検査は**あちらのソースから
導出して**照合する（書き写すと、同じ誤りが 2 か所になる）。種別が読めなかったときは
**座標は採り、種別だけ null にして数える**。

### ⑧ 採らない返答

渡していない id ／ 同じ id の 2 度目 ／ 実在しない座標 ／ **(0,0)**（ギニア湾の海上で、
模型が「わからない」を返すときの既定値でもある）／ 名前が空。

⚠ **`Number(null)` は 0** ——#R394・#R397 に続いて 3 度目。地点の無い記事を
`Number(a.subject_lng)` で読むと**ギニア湾に置いた記事**になり、AI の答えが
「決定論エンジンと大きく食い違った」と誤って記録される。**自分で書いた検査が、書いた直後に捕まえた。**
読む口は `lngOf`/`latOf` の 1 つに寄せた（変換しないので null は null のまま落ちる）。

### ⑨ 呼ばれない段は、存在しない段である

cron の body は段を名指しする（`{"stages":["fetch","assign","link","prune"]}`）ので、
`ORDER` に足しただけでは**本番で一度も走らない**。migration が `news-ingest-tick` の
command の**段の一覧だけを置換**する——このリポジトリは public で、command には
`x-news-ingest-secret` の値が入っているので、**command を書き直さない**。
pg_cron の無い環境（`supabase db reset` / CI）では `to_regclass` を見て何もしない。

### ⑩ プライバシーポリシーは「この経路は非AI」と明文で書いていた

> Placing those stored articles uses the same non-AI deterministic engine, server-side.
> The one exception is the Japanese translation of an event's headline…

これは #R404 で嘘になる。ポリシーは文章ではなく**コードについての事実の主張**なので、
同じ変更で EN/JA 両方を直し（送信されるのは既に公表されている見出しと要約の冒頭だけで、
利用者の情報は 1 バイトも含まない）、`scripts/doc-facts.mjs` §15 に
**`locate` 段 ⇔ ポリシー**の門を足した。3 通りに退行させて赤を実測している
（JA だけ消す／EN を元の文に戻す／`locate` 段を外す）。

⚠ 同じ §15 の既存の走査（「サーバー側でAI事前解析」を live と書いている文書を落とす）は、
**`news_events` / `news-ingest` / 出来事**を免除語に足した。足さないと、**正しい文章が門に
引っかかり、直し方が「事実を薄める」しか無くなる**。

### 費用

翻訳の実測（60 件で $0.0147・`gpt-5.6-luna` が応答。`AI_MODEL` は 403 なのでラダーが効いている）から、
同じ単価・同じ batch の大きさで新規記事 約 780 件/日 ⇒ **約 $0.15〜0.25/日 ＝ 月 $5〜8**。
1 run の上限 240 本・20 本ずつ。止め方は `supabase secrets set NEWS_GEO_AI=off`（cron を残したまま止まる）。

### テスト/CI/デプロイ

新規 `tests/r404-checks.test.mjs`（19 件）。**10 通りに変異させて赤を実測**——壊れた batch で
「見た」印を押す／`SUBJECT_COLS` から 1 列落とす／`locate` を `assign` の後に動かす／
cron の置換を末尾追加にする／語彙を `js/newsgeo.js` からずらす／`dirty` への合流を消す／
索引を `subject_located_by` で引く／(0,0) を通す／`Number(null)` に戻す／指紋を `.in(…)` に詰める。

既存の主張で古くなった 3 件を直した（`tests/r351-checks` ⑮⑱・`tests/r386-checks` ⑭）。
⚠ ⑮ は「ブラウザに配られるコードがこのモジュールを読み込んでいないか」を素の語 `news-ingest` で
引いていたので、**プライバシーポリシーの注釈がその関数を名指しただけで落ちた**。
名指しをやめる方向へ直すと監査可能性が下がるので、**モジュールのパスで引く**ようにし、
本物の import を入れて赤を実測した。

⚠ 検査を 1 本足したので `docs/TESTING.md` の「**N Node test files**」が 208→**209**。
`node-tests` 規則が即座に落とした——これは正しい動作で、#R399 が同じところで捕まっている。
（`tests/*.test.mjs` を数えると 208 で、こちらの分母は `test:checks` の一覧＝`security-logic.mjs` を
含む 209 である。**同じ「テストの本数」に 2 つの分母がある**ので、比べる相手を間違えない。）

**Edge Function は 2 本デプロイが要る**（`news-ingest`＝本体、`refresh-news`＝共有プロンプトの
import のみで挙動は不変）。**migration も適用が要る**（列・索引・cron）。

### ⑪ 本番検証の 1 回目が赤——そして自分で足した計器が、その場で理由を言った

deploy 後に `news-ingest-tick` を手で叩くと `ok:false` で、`notes.error` に
`news_articles(ai fingerprints): Bad Request` と入っていた。AI 済みの指紋を
`.in(<1,000 件>)` で訊いていたので、PostgREST への URL が**約 65,000 文字**（指紋は 64 桁）に
なり、上流が 400 を返していた——**`fetch` 段が丸ごと落ちて 1 行も取り込めない**。

⇒ **逆から訊く**（`selectAll` で AI 済みの指紋を全部もらう。保持期間が 72 時間なので、この集合は
表そのものと同じ大きさで頭打ちになる）。⚠ `.in()` が悪いのではない——**64 桁の値を 1,000 個**が
悪い（同じファイルの bigint の `.in()` は 6,000 文字なので無事）。

⚠ **これが「黙って 0 件になる AI 経路を作らない」の配当である。** 同じ欠陥が #R29 の形
（`catch (_) {}`）で入っていたら、`fetch` が静かに 0 行になり、次に気づくのは
「ニュースが更新されない」と報告される日だった。
