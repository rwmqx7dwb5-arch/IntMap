## R355 — **海底ケーブルは「模式図」を描いていた——702本すべての経路を、公開された実測と海底地形から組み直した**

依頼はこうだった。「網羅性を一切落とさず、全ケーブルの経路を可能な限り実際の敷設位置に近いものへ
置き換えろ。**見た目は変えるな。**表示信頼性も落とすな。クリックすれば情報が出るようにしろ。」

### 3. 回廊ポリゴンから中心線を取り出す

NOAA は経路を**線ではなく回廊**で出す。幅の中央値 61 m の細長い buffer で、経路はその**中心軸**である。

⚠⚠⚠ **最初の版は「両側を弧長の割合で対応づけて平均する」だった。**曲がるところで外側の壁は内側より
`w·Δθ` だけ長いので、「両方の壁の 40% の点」は互いに向かい合っていない。誤差は曲がるたびに積み上がり、
**実測で回廊自身の半幅の 2.9 倍（中央値）**——つまり「中心線」が回廊の外に出ていた。

⇒ **片方の壁を密にして、もう片方の壁（頂点ではなく折れ線そのもの）へ射影する。** 細い形の中心軸は
両壁が最も近いところなので、これは定義そのもの。実測: 壁から中心線までの距離 **p50 74 m・p75 182 m・p90 351 m**。

⚠⚠⚠ **「両端」は2つとは限らない。**枝分かれした回廊（幹＋分岐、複数の島を1つのポリゴンで出したもの）を
2点で切ると、説明できるのは1本の肢だけになる。実測 `SCCN`（ハワイ諸島・周長 2,870 km）で、
**自分のポリゴンから 449 km 離れた「軸」**が出た ⇒ **すべての tip を見つけて全部で切り、
各 chain の頂点に「相手はどの chain にいるか」を投票させて壁を組にする。**

⚠⚠ **「ring に沿ってどれだけ離れているか」は頂点数ではなくメートルで測る。**これらの ring は
0.5 m と 100 km の線分が混ざっているので、「k 頂点以上離れていること」では**2 m 先の同じ壁の隣**が
「対岸」として採れてしまい、tip の判定は**頂点が最も密なところ**で最小値をとった。

⚠ **抽出した軸は必ず検算して、落ちたものは捨てる**（`axisFit` ≤ max(4×幅, 500 m)）。実測 **380 肢中 357 を採用**。
33.9 km 幅の「保護区域」ポリゴンは中心線を持たないので、そもそも拒否される。

### 4. 接続構造は模式図から、経路は模式図から**取らない**

§8 が許すのは「どこに陸揚げし、何と何が繋がっているか」だけ。その通りにした。

⚠⚠⚠ **分岐は幹の「端」ではなく「途中」に着く。**模式図は分岐ユニットを、幹の ring の**内部**に
端点を置いた spur ring として描く。端点だけで graph を作ると両者は繋がらない。
実測（702 本全部）: ring の端点 3,794 のうち **自分の陸揚げ地点に 2,971**・**他の ring の端に 135**・
**他の ring の<b>内部</b>に 664**・どこでもない 24。2Africa は **37 個の破片**として出ていた。
⇒ 内部に着く端点で**幹を切り**、その点へ spur を寄せる。実測 **破片 236 → 69 本**、
**経路の端が陸揚げ地点にある割合 79.0% → 99.4%**。

⚠⚠ **±180° は継ぎ目であって節点ではない。**TeleGeography は太平洋のケーブルを ±180° で止まる2本の
ring に割る（実測: 端点 81 個がちょうどそこにあり、180° を超える経度跳びは**どの ring にも無い**）。
放っておくと大洋の真ん中に**架空の分岐ユニット**ができる ⇒ 何より先に、展開した経度で繋ぎ直す。

### 5. 残りは海底地形の上の最小コスト経路

`scripts/subcables/seafloor.mjs` が **1/12°（4,320 × 2,160・赤道で 9.28 km）**の格子を1枚作る
（terrarium z6・4,096 タイル。**同梱しない**——`.cache/` の build 入力）。1セルあたり:
平均水深・**セル内の水深の標準偏差**・海率。

⚠ **セル間の勾配では 3 km の海底谷は見えない。**大陸斜面は分かるが、ケーブルを切るのは谷のほう。
**1セルの中の標本のばらつき**なら見える（平坦な深海平原は σ 数 m・谷壁は数百 m）。実測の分布は
p50 34 m・p90 134 m・p99 387 m。

コスト＝距離 × (1 + 大陸棚 + 極浅 + 超深 + セル内粗さ + **その一歩が実際に登る勾配** + 陸との隣接)。
陸は**費用ではなく壁**。A\* の heuristic は素の大圏距離なので admissible。

⚠⚠⚠ **1/12° の格子にとって、スエズ運河は存在しない。**幅 200 m のものは 9.28 km のセルに入らないので、
紅海と地中海は**別々の大洋**になる。実測: ポートサイド→スエズの 151 km が **アフリカを回って 25,141 km**。
これが Red2Med を公表値の **117 倍**、EMC West-1 を 13.9 倍、India-Europe Xpress を 6.0 倍にしていた。
⇒ **`data/subcable-overrides.json` の `channels`**（スエズ運河・ボスポラス〜ダーダネルス）。
コードに緯度経度は書かない。各項目は `why` を必須にし、**開けたセル数を build が報告する**
（何も開けなかった channel が黙っていられない）。実測 Suez +20 セル・Bosphorus +9 セル。

⚠⚠ **標高で作った格子は「海面より高い湖」を陸と読む。**五大湖の水面は +176 m なので NOAA の
五大湖回廊には置き場所が無かった（実測: シカゴ→ラディントン、**経路なし**）⇒ Natural Earth 1:10m の
湖を焼き込む（**+45,099 セル**）。

⚠⚠⚠ **端点をどこまで海へ寄せてよいかは「細部」ではなく問いの一部。**`snapToSea` は水を求めて
40 セル歩く。アマゾン川を遡上するケーブルではそれが「そこに無い2点の間を引く」意味になる。
実測（この上限が無いとき）: Norte Conectado Infovia-05 が公表 1,116 km に対し **6,287 km**。
⇒ 上限を超えたら**経路なし**（正直な答えで、呼び出し側が落ちられる答え）。

⚠⚠⚠ **迂回率の天井も同じ機構の一部。**自分の直線の何倍にもなる経路は「賢い回り道」ではなく
**別の大洋**を見つけている。天井が無いときの detour は p99 **21.41**、天井を入れて **1.90**。

### 7. 検算（生成物そのものを統計で見る）

- **702/702** のケーブルが geometry を持つ（入→出で1本も失っていない）
- 62,005 頂点に **NaN/∞ 0・範囲外 0・経度跳び 0**（±180° は分割済み）
- **経路の端が陸揚げ地点にある: 2,479/2,494（99.4%）**
- **公表長との比**: p05 0.582・p25 0.903・**p50 0.989**・p75 1.109・p95 1.664。0.6〜1.8 の外は 611 本中 **60**
- 公表長が分かる **629 本の合計 1,927,783 km に対し、組み上げた合計 1,958,262 km（+1.6%）**
- 迂回率: p50 1.084・p90 1.265・p99 1.902
- 自己交差 **8 地物・18 交差**／重複 feature_id **0**／破片になっているケーブル **69 本**
- **陸地横断**: 259 地物・4,085 標本点（**陸揚げ前後 12 km を除いた範囲**）。
  その大半はアマゾン川の河川ケーブル（`norte-conectado-infovia-*`・`projeto-amaznia-conectada-*`）——
  **9.28 km の格子は川を水として持てない**。ここは正直に `estimated` と名乗っている。

### 8. 見た目は1ビットも変えていない

`lyr-subcables` / `-glow` / `-pts` の宣言は**ソース文字列として凍結**した（`tests/r355-checks.test.mjs ①`）。
色・幅・不透明度・ぼかし・cap/join・半径・stroke・minzoom・挿入順のどれを触っても赤くなる
（実測: glow の `line-width` を 3.2 → 3.4 にして赤、戻して緑）。
ブラウザ側でも同じ 11 の値をレンダラ自身に訊いて比べる（`tests/r355.spec.js`）。

⚠ **`quality` で色や太さを変えていない。**内部では区別できるが、線は1種類のまま。

### 9. クリック（`js/subcable-info.js`・動的 import）

- **当たり判定は箱**（マウス ±8px・**タッチ ±16px**）。**線は太くしていない**——§13。
- 重なっているときは同じポップアップの中で選べる（実測: Bude 沖で **8本**、chip で切り替え）。
- 陸揚げ地点は名前・国・座標・**ここに来るケーブル一覧**。
- 文言は9言語（`window.IntMapLang.t(HOST.lang, …)` を**その場で綴る**——
  ⚠ 矢印関数の `L` に包むと `scripts/i18n-helpers.mjs` が「証明できない名前＝shadowed」と見なし、
  **20 本の文字列が監査の視野から丸ごと消える**。ゲートは 100% と言い続けたはずだった）。
- ⚠ **数は連結ではなく `{n}`**（`n + ' cables here'` はリテラルではないので inline 表に入らない）。

### 10. 表示は前より丈夫になった（§3）

取得は4段: **自オリジン `data/subcables.json`** → その Cache API の写し → TeleGeography の写し → 中継。
実測、本番ビルドで `data/subcables.json` は **461 KB（gzip）を 11〜20 ms**。

⚠⚠⚠ **速くなったぶん、スタイルとの競争は<b>きつく</b>なった。**#R187 の梯子は 750 ms × 12＝約9秒で、
「遅いスタイル」に対して測られたもの。ベースマップが 429/503 を返しているマシンで実測すると
`isStyleLoaded()` は **22 秒たっても false** で、梯子は尽き、箱は `imAutoOff` で外れた。
⇒ **梯子をストップウォッチから外し、`styledata` に繋いだ。**箱が入っている限り 90 秒まで待ち、
**スタイルが使えるようになった瞬間**に組み直す。

### 追記（本番検証） — **「経路の出典」が、クリックされていない区間の出典を借りていた**

本番検証で1件。**Havfrue/AEC-2 の再構築された区間**をクリックすると、こう出ていた。

```
経路の精度    再構築
経路の出典    NOAA Office for Coastal Management (Marine Cadastre)
```

どちらの行も、それ自体は正しい。このケーブルには NOAA が実測した区間が**在る**——ただし
**クリックされた区間ではない**。`js/subcable-info.js` はこう書いていた。

```js
const srcName = SRC_NAME[props.src];
if (srcName) body += row(T.routeSource(), esc(srcName));
if (m && m.sources && m.sources.length) {
  const names = m.sources.map(s => SRC_NAME[s]).filter(Boolean);
  if (names.length && !srcName) body += row(T.routeSource(), esc(names.join(' · ')));   // ← 借りている
}
```

`recon` には `SRC_NAME` が無いので `srcName` は null になり、**ケーブル単位の一覧が同じラベルの下に
入る**。⚠ **それぞれ真である2つの文が、並ぶと1つの偽の文に読める。** 依頼の §11 が禁じているのは
まさにこれ——「情報が存在しない値を推測して事実のように表示してはいけない」。

⇒ `else` にして、ケーブル単位の一覧には**自分のラベル**を与えた（`Surveyed sections` /
「実測区間の出典」・9言語）。

⚠ **ローカルでは見えなかった。** 手元で開いたポップアップは `verified` な区間か、実測区間を
1つも持たないケーブルばかりで、**「実測区間を持つケーブルの、実測でない区間」という組み合わせに
一度も当たらなかった**。本番で最初に当たった1本がそれだった。

⚠ **前ラウンドの検査はこれを捕まえられない形だった**（ポップアップが paint を触らないことしか
見ていない）。`tests/r355-checks ②` に、**借りていた分岐が復活したら赤くなる**検査を足した。
