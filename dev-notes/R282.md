## R282 — **原本（OneDrive）が 15 コミット遅れていた——同期は正常で、原本に何も書き込まれていなかった**

> 「最近あなたがたくさん作業しても、One driveがあまり変わってなさそうなのはなぜですか？
>   One driveの"IntMap"が原本なはずですが。」
> → 「いやそもそもOneDriveが原本やろが。なんでOneDriveを編集しとらんねん。」

欠落は **15 コミット・159 ファイル・+14,331 −7,112 行**、中身は **R272〜R279 と handoff**
（PR #207〜#224）。決定的な数字が2つある。

- 原本内の追跡ファイルの最終書き込みは **2026-08-20 15:29**。これは `git reflog show main` の
  最後の `pull --ff-only` と**同じ分**。以後 12 時間、このフォルダには 1 バイトも書かれていない
  （唯一の例外が `.claude/launch.json` の未コミット差分＝別セッションが 02:26 に足したプレビュー設定。

### なぜ書かれなかったか（原因は規程の側にあった）

`git worktree list` に出る 12 個の worktree が全部
`C:\Users\gyuuk\AppData\Local\Temp\claude\<セッションID>\scratchpad\wt-r###` にある。
これは `CLAUDE.md` §6 の「各セッションは必ず独立した worktree」に**従った結果**で、
そこは OneDrive の外。そして——

- §5 のワークフローは `branch deletion` で終わっていた。**原本を最新化する工程が無かった。**
- §11 の USB バックアップは「そのセッションの working directory の `git ls-files`」から
  ミラーを作る。R279 の台帳自身が «mirrored from the session worktree wt-r279» と書いている。
  **原本を一度も経由していない。**

結果、GitHub と USB は毎ラウンド確実に更新され、**原本だけがどの工程も責任を持たない写し**に
なっていた。ラウンドは完璧に完走しながら、原本を一度も触らずに終われた。

### 直したこと

1. **原本を `dec64f6` へ早送り**（159 ファイルが実際に書き込まれ、OneDrive の同期対象になった）。
2. **`scripts/master-sync.mjs`** — 原本を**ツールが知る**。場所はハードコードせず
   `git rev-parse --path-format=absolute --git-common-dir` の親。主リポジトリの `.git` は
   linked worktree からも同じものが返るので、**どの worktree から実行しても原本を指す**
   （実測 `wt-r281` から `--path` → `C:\Users\gyuuk\OneDrive\IntMap`）。
   `--check` は「`main` にいて `origin/main` と一致して clean」でなければ exit 1、
   `--sync` は fetch して早送り。`npm run master:check` / `npm run master:sync`。
   ⚠ **作業ツリーが汚れている場合と、`origin/main` に含まれない branch にいる場合は何もせず断る**
   ——他セッションの作業を奪わない（§6）。
3. **`CLAUDE.md` の3か所**——§5 のワークフロー鎖の末尾に `→ 原本 (OneDrive) の最新化` を足し、
   §6 を「原本と、並行セッションと Git」にして**原本の定義と、temp の worktree は回避策であって
   既定ではないこと**を書き、§11.4 に**ミラー元は必ず原本**であることと `--check` を通す条件を書いた。
4. **`Architecture.md` §15.1** にツールの説明を追加（ラウンド参照は書かない——`arch-rounds` ゲート）。

### 追記 — **原本を「作業場」にした瞬間、並行セッションの隔離が壊れていた**

> 「複数平行Claude Codeセッションへの対応はまだありますよね？」

あった。**3 つあり、うち 2 つは #R282 自身が入れたもの**だった。

### ① 「原本が空いている」の判定手段を書かずに「原本で作業しろ」と書いていた

#R282 は §6 を「作業は原則として原本の中で行う。原本が空いている（他セッションが使っていない）
なら…」と書き換えた。**空いているかをどう判定するのかは、どこにも書いていない。**
`git status` が clean で `main` にいることは証拠にならない——2 セッションが同じ秒にそれを見れば
**両方が原本を取る**。旧規程は「**セッション間で同一の working directory を共有してはならない**」の
1 行でこれを丸ごと回避していたのに、その 1 行を私が消していた。

### ② `--sync` が他セッションの branch を奪った（実測）

最初の `--sync` は「`origin/main` が既に**含んでいる** branch なら、それは merge 済みだから
離れても安全」という理屈で `git checkout main` していた。合成リポジトリで再現した：

```
セッションA の branch (実行前): feat/session-a
master-sync: C:\...\master is main @ fc81313 (already current).      ← 成功メッセージ
セッションA の branch (実行後): main                                  ← 奪われた
```

**「`origin/main` に含まれる」は「そこに誰も立っていない」を意味しない。**
これは §6 が名指しで禁じている「別セッションの branch を変更する」そのものだった。

### ③ 原本が占有されていると、終了工程が完了できない

`--sync` は拒否する（それ自体は正しい）が、**拒否されたセッションが次に何をすべきかが規程に無い**。

### 直した形——原本を `main` 専用にする

**原本は「作業場」ではなく「`main` の置き場」**とした。常に `main` にあり、`origin/main` と
一致し、clean。作業は必ず OneDrive の外の worktree で、専用 branch。

こうすると**切り替える branch がそもそも存在しない**ので、①②③ が同時に消える。

- ロックが要らない（**失効ロックという新しい壊れ方**を作らずに済む）
- 競合時に並行度が 1 に落ちない
- `--sync` は `main` を `origin/main` へ**早送りするだけ＝冪等**。何セッションが同時に走っても
  結果は同じで、**1 回の実行がその時点で merge 済みの全セッション分を運ぶ**
  ＝拒否されたセッションも何も失わない（次の実行が同じ commit を運ぶ）

> **教訓の一般形: 排他が必要になったら、まず「排他が要らない形」に変えられないかを見る。**
> ロックは正しく書いても、失効・再入・回復という 3 つの新しい問題を連れてくる。

### ④ 並行セッションは 1 台の dev サーバを共有していた（このラウンド自身のテストが捕まえた）

`tests/helpers/session-seed.js` は `PORT || 4173` の**固定ポート**、`playwright.config.js` は
`reuseExistingServer: !isCI`。つまり**同じマシンの全チェックアウトが 1 台のサーバを共有する**。
壊れ方は 2 通りあり、**どちらも静か**：

- 2 つ目の実行は自分の `npm run build` を**飛ばして相手の `dist/` を試験する**
  ——緑になるが、変更したコードを一度も見ていない
- 1 つ目が終わってサーバを落とすと、2 つ目は `net::ERR_CONNECTION_REFUSED` で途中死する

**実測**: このラウンドの `npm test` が **2 failed / 25 did not run**。同じ木を私有ポートで走らせると
**52 passed**。落ちたのは私の変更のせいではなかった。

そして `docs/TESTING.md` には**既に**「`set PORT` when another worktree already has a server on
4173」と書いてあった。**`npm test` と打つ瞬間に誰も読んでいない指示**で、だから起き続けていた。

→ **ポートをチェックアウトから導出する。** linked worktree の `.git` は**ファイル**、
main worktree の `.git` は**ディレクトリ**——stat 1 回、サブプロセスも設定も要らない。
**原本と CI は 4173 のまま**（文書がそう書いており、それは真であり続ける）、
各 worktree は 4174〜4373 の自分専用ポート。環境変数 `PORT` は従来どおり優先される。

### ⑤ そして私のゲート自身が、正しい作業に迂回された（出荷当日）

並行セッション（R283）の USB 台帳にこう書いてあった——`--check` が
「the master has 1 uncommitted change(s)」で exit 1 したので、`git merge --ff-only` を**手で叩いた**。
その汚れは `.claude/launch.json`＝**別セッションが足したプレビュー設定**で、
§6 が「別セッションの作業を commit も移動もするな」と禁じているもの。

**最初の `--sync` は「汚れていれば何であれ拒否」だった。** 用心深く聞こえるが間違いで、
**早送りが触らないファイルを害することはできない**。拒否は安全を足さず、
**ツールを迂回する習慣だけを教える**。

→ **邪魔かどうかを判定するのは git。** `git merge --ff-only` は
「ローカルの変更を上書きすることになる場合だけ」正確に拒否するので、それを走らせて**その理由を表示する**。
`--check` も「遅れている」と「汚れている」を分け、汚れは**警告として印字するが exit 0 を妨げない**
（USB ミラーは作業ディレクトリをそのまま写すので、汚れたまま写すのが §11.5 の要求そのもの）。
`tests/r282 ④c` が両側を測る——**邪魔なときは止まり編集が残る／邪魔でないときは通り編集が残る**。

### テスト

- `node --test tests/r282-checks.test.mjs` — **7 件緑**。
  - ④ を**この欠陥の回帰テスト**に書き換えた。(a) `origin/main` が**含んでいる** branch
    （旧規則が素通りした当のケース）(b) 未 merge の作業を載せた branch (c) `main` 上の未コミット変更
    ——**3 つとも拒否し、branch も編集も無傷であること**を見る。
    ⚠ 前提条件で先に `fetch` する。しないと `origin/main` は HEAD と同じ commit のままで、
    「含まれる」が**測りたい理由ではなく自明な理由で**成立してしまう。
  - ④b **冪等性**——4 連続実行が同じ commit に着き、2 回目以降は `already current` と言う
    ＝ロックが要らないことの根拠そのものを測る。
  - ⑤ に「原本で branch を切って作業してはならない」「同一の working directory を共有しては
    ならない」「冪等」の 3 つが §6 に**残っている**ことを足した——**消えたのがこの 3 つだったから**。
