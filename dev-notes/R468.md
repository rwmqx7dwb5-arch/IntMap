## R468 — **ブラウザが読めない診断ヘッダは、診断ではない**

#R464 の production verification が出した所見。#R464 自身の後始末なので、同じ主題の続き。

### 1. 何が起きていたか

#R464 は `supabase/functions/gdelt-relay` に `x-intmap-gdelt-cache` / `-age-ms` / `-store` を
足した。理由も書いてある——**黙って永続に失敗するキャッシュは、動いているキャッシュと
見分けがつかない**（全要求が「実データを返す miss」になり、読者は答えを見るので誰も気づかない。
気づくのは上流だけ）。実際そのヘッダは deploy 当日に `http400:AccessDenied` を吐いて、
platform 注入の `SUPABASE_SERVICE_ROLE_KEY` が Storage に通らないことを名指しした。

**そして production verification は、その1本も読めなかった。**

本番オリジンから4回叩いた実測: **200 / articles 14** が4回とも返るのに、JS が見られた応答ヘッダは
**CORS 安全リストの3本だけ**（`cache-control` / `content-length` / `content-type`）。
値そのものは存在していた——同じ URL を curl で叩くと
`x-intmap-gdelt-cache: stale` / `x-intmap-gdelt-age-ms: 5,941,649` が返る。

⚠ **ブラウザは、サーバーが `Access-Control-Expose-Headers` で名指ししていないヘッダを読めない。**
この関数は1本も名指ししていなかった（`_shared/relay-guard.js` の `corsFor()` は
`Allow-Headers` は設定するが `Expose-Headers` は設定しない）。
⇒ **診断は、アプリが動く面と、ラウンドを検証する面の「両方」にだけ存在しなかった。**

`aviation-feed` は #R341 から自分の `x-intmap-*` を並べている。同じ理由で、同じ並べ方をする。

### 2. ⚠⚠ 502 は診断を1本も持っていなかった

実測: キャッシュに無いクエリは **12.7〜14.8 秒**かけて `502 {"error":"upstream_unavailable"}` を返し、
**`x-intmap-*` が1本も付かない**（上流 GDELT は同じクエリに 13.65 秒後 429）。

つまり**読者が実際に苦情を言う唯一の結末が、外から説明できない唯一の結末**だった——
「キャッシュに何も無かった」と「持っている物の更新を GDELT に断られた」が区別できない。
片方だけが再試行に値するのに。⇒ 502 も `x-intmap-gdelt-cache: cold` と `-store` を載せる。

### 3. 検査（`tests/r465-checks.test.mjs` 3 本）

⚠ **①は露出リストを持たない**——**ソースが実際に `set` している `x-intmap-…` を数え上げて**、
その全部が `Access-Control-Expose-Headers` に入っているかを見る。
あとからヘッダを1本足して露出を忘れたら、**検査が自分で赤くなる**（手書きの一覧なら黙る）。
②は 502 が `cold` を名乗ること。③は `corsFor()` が**共有の既定として露出を持たない**こと
（持たせると、露出するつもりの無かった関数のヘッダまで publish される）。

⚠ **3通りに変異させて赤を見た**（露出リストから1本落とす→2本赤／`Access-Control-Expose-Headers`
ごと削除＝#R464 の状態→2本赤／502 から `cold` を外す→2本赤）。

### 4. ⚠ この変更が**直していない**こと

キャッシュに無いクエリは、relay 経由でも**依然として約8割が取れない**（GDELT が 429 を返すから）。
#R464 が変えたのは「**繰り返されるクエリ**は 0.3〜0.5 秒で確実に読める」ことと、
取れないときの待ちが **45 秒 → 12〜15 秒**になったこと。**新しいクエリの成功率は上流のまま。**
本ラウンドはそこには触れておらず、**触れたのは「どちらの結末だったかが外から分かる」ことだけ**。
