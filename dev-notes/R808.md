## 0. 測った

`.agents/roles/` の 5 役はどれも `model:` を書いていなかった。`scripts/agent-sync.mjs` は
**#R503 の時点で既に `r.claude.model` を frontmatter へ書き出す実装を持っていた**（163–164 行）——
配線は在り、通電していなかった。したがって 5 役とも親を継承し、成果物が `file:line` の数え上げ
でしかない `intmap-scout` が、実装を決める `intmap-implementer` と同じ単価で走っていた。

## 1. 線は「機械的か」ではなく「観測器か」で引いた

| 役 | 既定 | なぜ |
|---|---|---|
| `intmap-scout` | `sonnet` | 正解が機械的に決まる。漏れは網羅性の問題で、判断の問題ではない |
| `intmap-i18n` | `sonnet` | 機械的な掃引。言語体制は凍結中（`AGENTS.md` §3-5）なので出番自体が少ない |
| `intmap-verifier` | `sonnet` | ログから失敗行を抜くのは機械的。**ただし下の昇格条件が付く** |
| `intmap-implementer` | 継承 | 実装判断そのもの。落とすと `AGENTS.md` §3-3 の暫定実装を踏む |
| `intmap-prod-verifier` | 継承 | 本番で**観測器の嘘**を見抜く役。ここを弱めるのは下の実測に真っ向から反する |

⚠⚠⚠ **`intmap-verifier` が危ない。** `.agents/rules/one-pass-or-a-reason.md` §2 が数える繰り返しの
原因の 1 番は「**観測器が嘘をついた**」で、実測は #R736（成功した描画を毎回 `not_rendered` と呼び、
**21 手・10分29秒**が全部その再試行に消えた）・#R742（**207 操作中 52 件＝25%**）・#R768。
**誤判定 1 回ぶんの再試行は、その役の全ラウンドぶんの節約より高い。**

⇒ 既定を下げたうえで、割り当ての表と昇格条件を **`.agents/skills/intmap-round/`** に置き、**呼び出し側が上げる条件**を
恒久で書いた: 「その赤は環境要因か本物の退行か」「緑だが実は死んでいないか」「失敗が**観測された
事実**か、**観測できなかっただけ**か」（§5 が分けろと言う 2 つ）を訊くときは `model: "opus"`。
⚠ **安い既定は、この昇格が在って初めて成立している。** 片方だけ残すと条件つきの節約が無条件になる。

## 1b. ⚠⚠ 常設の規則ファイルには 6144 バイトの天井があり、`execution-strategy.md` は**余白 8 バイト**だった

この回は表と昇格条件をまず `.agents/rules/execution-strategy.md` に §2b として書き、
**`tests/r295-checks.test.mjs` ⑥ に拒まれた**（6136 → 8953 バイト・超過 2,809）。
天井は `.agents/rules/*.md` の**1 ファイルあたり**で、理由は「**毎セッションが払う**」。
⚠ 検査自身が「`scripts/test-budget.mjs` と同じで**下がるだけの数**。決して上げない」と述べており、
**閾値を上げるのは方針違反**。検査の文言がそのまま移動先を指している——「Move detail into an agent
or a skill」。

⇒ **表と昇格条件は `.agents/skills/intmap-round/` へ**（ラウンドの手順として読まれる）。
⇒ **呼び手に 1 行だけ届けばよい部分は `.agents/roles/intmap-verifier.md` の `description` へ**
——Agent tool が呼び出し側に見せるのはこの欄なので、**規則がそれの governs する当のものに付く**
（[[intmap-hist-names-rule-belongs-to-the-name]]）。skill を開いていない呼び手にも届く唯一の経路。

⚠ **これは「置き場所が無かった」ではなく「置き場所を間違えていた」。** 常設の規則は
**全セッションが毎回払う**ものだけを持つべきで、5 役の単価表はその条件を満たさない。

⚠ 発見したのは段 3 の `npm test`——**そしてそれを判定したのは、この回が `sonnet` に下げた当の
`intmap-verifier` を `model: "opus"` に昇格させて走らせた回**だった（§1 の昇格条件の初回適用）。
同じ run の 15 failed のうち **9 件は tree lock の枠切れ**で、verifier は 8 本を単独で走らせ直して
45 件すべて緑を実測し、「**観測できなかった**」と「失敗した」を分けて返した
（`one-pass-or-a-reason.md` §5）。**下げたままなら、この分離は期待できなかった。**

## 2. ⚠⚠ 綴りを間違えると、無言で元に戻る

Claude Code は知らないモデル名を**報告せず、継承に戻す**。宣言はファイルに残り、下流の読み手は
それを信じる——[[intmap-declared-capability-never-executed]] と同じ形で、**欠陥が無言**。

⇒ `scripts/agent-sync.mjs` に `CLAUDE_MODELS` を置き、**その値を書き出す当人が綴りを拒む**。
⚠ この一覧は**ハーネスの語彙**であって「どの役にどのモデルが相応しいか」の方針ではない
（失効条件: Claude Code が受け付ける別名を変えた日）。方針は `.agents/skills/intmap-round/` にある。

## 3. ⚠ Codex には届かない。それは明記された差である

`.codex/agents/*.toml` は Codex の**設定レイヤー**として読まれ、そこで走るモデルは**アカウント側**
**が決める**。`model` を写せば**読み手の居ないキー**になるだけ（[[intmap-records-with-no-reader]]）
なので写さず、差は `docs/AGENT-SETUP.md` §6 に書いた。

⚠ これは `AGENTS.md` §0-5 の「片方だけが知っている状態」には**ならない**——**どの役に何をさせるか
という判断は両方が読む `.agents/skills/intmap-round/` にあり**、届かないのはそれを機械に伝える
**手段**のほうだけだから。帰結として Codex 側の scout / i18n / verifier は Claude Code 側より
高いモデルで走ることがあり、昇格条件はそこでは自動的に満たされている。

## 4. 検査

`tests/r808-subagent-model-tiers-checks.test.mjs`（5 本）。⚠ **測るのは「sonnet と書いてあるか」
ではない**——それはこの回が到達した答えであって、守るべき欠陥ではない
（[[intmap-restate-the-defect-not-the-fix]]）:

1. 宣言された名前が、**それを書き出す当人の語彙**に在る（一覧を写さず `CLAUDE_MODELS` をソースから読む）
2. Codex 側の生成物に `model` が漏れていない
3. 生成された frontmatter が、正本と同じことを述べている
4. **散文の割り当て表と役ファイルが両方向で一致**——表が実体から離れると**両方の読み手が自信を持つ**
   ので、表が無いより悪い（[[intmap-comment-contradicted-the-table-below-it]]）
5. **昇格条件の段落がまだ在る**——後のラウンドが安い既定を残したままこれだけ消せる

⚠ 3 通りの変異（綴りの誤り・表の食い違い・昇格条件の削除）で**実際に赤くなることを確かめた**。
