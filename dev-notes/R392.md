## R392 — **プリセットの送信文は、4ラウンドかけて「述語」を磨き、一度も「主語」を変えていなかった**

「Atlasにはプリセットの送信文が用意されていますが、それは今地図で見ている地域に応じて用意して変えるようにして。
（追記：まだほぼ定型文みたいなものしかない。もっとその場所にあったものに。）」

**この一文が届くのは4回目**。#R309 がチップを切り出し（4つの固定文＋国名の差し込み）、#R313 が「汎用文でごまかすな」を
受けて**述語つき候補プール**にし、#R337 が「まだほぼ定型文」を受けて候補を **35→65** に増やした。3回とも実装は良く、
3回とも**同じものを変えていた——どの文が適格か**。変えていなかったのは**その文が何について語っているか**である。

### 何が壊れていたか（本番で数えた）

`exFacts()` は視界全体を `codeAtPoint(中心画素)` の**国コード1個**に畳み、残りを捨てていた。`exKey` が証拠で、
`国コード|言語|live/年|レイヤー集合` のどこにも**位置も縮尺も無い**。`js/atlas-examples.js` はそれを**機能として**書いていた:

> 「The guard above means a pan that stays inside one country costs one `codeAtPoint` and redraws nothing.」

本物の Chromium で本番を測った（プレビューペインは `document.hidden` で rAF が止まるので測れない）:

| 視点 | 結果 |
|---|---|
| 渋谷 z14 / 大阪 z14 / 稚内 z10 / 日本全体 z5 | **4文とも同一**。しかも B・C・D は**行を作り直してすらいない** |
| NY z13 / カンザス z10 | **4文とも同一**（F は再描画なし） |
| 太平洋 z4 / ジブラルタル z9 / マラッカ z8 | **3つとも同一**の世界プール4文 |
| 20か国 × 4チップ = 80 | 雛形は**27種類**。任意の2か国が共有する雛形は**平均 1.84 / 4** |

ジブラルタルでは `codeAtPoint(-5.6,35.95)`→null に対し `(-5.6,36.10)`→**ESP**、`(-5.6,35.80)`→**MAR**。
**中心画素が水に落ちた瞬間に、両岸の国も海峡そのものも4文から消える。**

### 何をしたか

**主語を視界にした。** 測定は `js/atlas-view-subject.js`（新設）に置き、`js/atlas-examples.js` は候補プールのままにした。
視界プール `V` は国プール `P` ／世界プール `W` より**必ず強い**（重みの下限 11 対 上限 10）——街区を見ている読者に
とって「この国は世界有数の人口密度」は**真だが主語が違う**文だから。**`P` と `W` は縮小も削除もしていない**。

測るのは、すべて**視界そのものから**:

- **視界に入る国** — 箱の 6×6 標本を国ポリゴンに当てる。**2か国なら国境、3か国以上なら三国境**で、どちらも
  国別の表には存在しない事実。`countryStats` の `bbox` は ray-cast を減らす**足切りにだけ**使い、答えには使わない
  （`codeAtPoint` は bbox 前置きを持たず、36標本×全ポリゴンは長タスクになる）。
- **陸と海の割合** — 内陸／海岸／外洋を分ける。
- **名前のある水域** — `window.SEA_LABELS` 120行（eager・既にメモリ上）。
- **タイルが名指す地名と山** — `querySourceFeatures`。**`queryRenderedFeatures` ではない**（ラベルを消している
  読者も大阪を見ている）。山は標高という**実測の数**を持つ。
- **戦略拠点143件の種別** — `IntMapRefData.dashCards`（eager）。チョーク16・港湾39・軍37・宇宙16・技術15・エネルギー13。
- **km単位の縮尺** — ズーム番号ではない。同じズームでも赤道と 70°N では幅が違う。

**地図クリックの3文も同じプールから選ぶ**（`pointExamples`）。「なぜこの辺りはこうなっているの？」が海峡でも砂漠でも
湖でも同じ、という**最も location-specific なジェスチャーが最も定型文だった**状態を消した。箱は**クリックされた座標**
の周りで作る（`flyTo` は900msかかるのでカメラはまだ前の場所を映している）。

### 測って直したもの（どれも実際に本番／実ブラウザで見た）

⚠⚠⚠ **`reach` は「大きさ」の答えであって「そこに在るか」の答えではない。** 両方に使ったので、**渋谷 z14（幅2km）に
60km外の霞ヶ浦**が第1チップとして出た（霞ヶ浦の reach 156km が距離を覆い、最も具体的なので勝った）。逆向きにも壊れ、
**熱帯太平洋 (-150°,10°) に「北極海」**（北極海の reach 11,516km は北太平洋の 28,336km より**小さい**）。
⇒ 2つの問いを分け（① この視界の大きさに見合うか ② 実際にこのフレームに在るか）、**最も近いものが勝つ**。

⚠⚠ **…そして行は1点しか持たないので、外洋のクリックは「水域なし」になっていた。** 実測: 太平洋のど真ん中
(−150°, 10°) は「North Pacific Ocean」のラベル点から **2,600 km** あり、②の「フレームに在るか」を通らず、
世界プールの汎用4文に落ちていた。⇒ **その行自身の reach の 1/4** までは「同じ水域の内側」と認める
（太平洋なら 7,084 km・霞ヶ浦なら 39 km なので、**外洋を入れても 60 km の湖は戻ってこない**）。

⚠⚠⚠ **「タイルが答えた」は「呼び出しが返った」ではない。** 渋谷へ飛んで4秒後 `querySourceFeatures` は**0件**、
さらに4秒後**1,437件**。`known=true` を無条件に立てていたので、「この視界には名前のついた集落が1つも無い」が
**東京都心で発火する**ところだった。⇒ `known = feats.length>0`（**箱の外**の地物も「タイルは届いた」の証拠になる。
ゴビ砂漠はそれで正しく発火する）＋ **`idle` で描き直す**（タイルは600msのデバウンスより後に着く）。

⚠⚠ **チョークポイントを名前で当てにいかない。** `SEA_LABELS` の「Strait」は**バス海峡とデービス海峡だけ**で、
ホルムズ・マラッカ・ジブラルタル・ボスポラス・ドーバーは**1行も無い**。名前で照合するチップは、無名の2海峡で発火して
重要な全部で沈黙する。⇒ 種別を持つ**キュレート表**と、「**2か国が水を挟んで向き合っている**」という測れる形。
⚠ dashCards の `title` は **en/jp の2言語しか無い**ので、**名前を差し込まず種別だけ**を門にした（#R313 追記が
`CAPITAL` で踏んだ罠と同じ）。おかげで6つの拠点チップは**補間を1つも持たず**、9言語すべてが本物になる。

⚠⚠ **120行のうち33行は淡水。** 海洋・海・湾・湖で**問いを分ける**（バイカル湖に「誰が哨戒しているか」と訊かない）。
⚠ カスピ海とアラル海は「Sea」と名乗る湖だが、プールが訊くことは全部当てはまるので**意図して海側に置いた**。

⚠⚠ **生の `name` は3つの文字体系を1行に混ぜる。** 「Tanger ⵟⴰⵏⵊⴰ طنجة」「خصب」「珠穆朗玛峰 ཇོ་མོ་གླང་མ། सगरमाथा」。
⇒ 地図のラベルと**同じ鍵順**（`window.IntMapOsmNameKeys`）で解く → Tangier / Khasab / Mount Everest。

⚠⚠ **列マップは5言語しか届かない。** `{en:3,jp:4,de:5,ru:6,es:7}` は `npm run check:i18n` が
「呼び出しでなくデータとして持たれた翻訳の組」として落とす。落として正しい——**fr/ko/zh-Hant/zh-Hans は
海の名前が英語のまま**だった。⇒ `IntMapLang.pick().arr()`（`js/place-labels.js` が同じ行に対して開いている扉）。

⚠⚠ **z14 の東京で地名が0件だった。** 4km の箱に在る `place` は `quarter`/`neighbourhood`/`borough` で、
`city|town|village|suburb|hamlet` しか受けていなかった（東京自身の city 点は箱の外）。
⚠ そして逆に、**546km の視界を1つの村（Усть-Ордынский）が代表していた**。
⇒ **縮尺ごとに要求する等級を変える**（street なら quarter まで、region なら city|town だけ）。

⚠⚠ **「ほぼ切れ目のない市街地」は密度の主張なので縮尺が要る。** 件数だけで門を作ったらジブラルタル海峡と
ハサブ（どちらも z9・180km）で発火した。180km に十数個の集落は**田舎**である。⇒ `city` 縮尺（15–80km）限定。

### 検査

⚠⚠⚠ **最初に書いた検査は2つとも「赤にできなかった」——変異させて確かめた。**
① は `exKey` の**宣言**（`VIEW.viewKey(f.vw)` が本文に在るか）を読んでいたので、視界を鍵に**連結する行**を消しても
緑のままだった（チップは `examples()` から来るので鍵とは無関係に違う）。② の「位置が変われば鍵も変わる」は、
比べた2つの視界が**水域と縮尺でも違っていた**ので、鍵から位置を消しても緑だった。
⇒ ①は連結そのものを固定し、鍵を**直接**比べるようにした。②は**位置だけが違う**組（同じ大きさ・同じ国・同じ水域・
同じ空のタイル）に置き換え、**そのことを検査自身が先に assert する**。両方とも**変異させて赤を見てから**緑にした。

⚠ **検査が自分の散文の中の `L()` に当たった——12回目。** `scripts/code-only.mjs`（#R345 がこのために切り出した）。

⚠ #R337 の合成世界は**カメラが (0,0) に固定**で、そこでは**赤道が全フレームを横切る**ので、240か国すべてが同じ
視界チップを受け取り「1つの事実で問いが変わる」が壊れた。カメラを合成世界自身の bbox（[10,30,11,31]）へ動かした
——**視界が何も寄与しない**状態にして、その検査が測りたかった国プールだけを測らせる。

### 追記（報告された「文字化け」と、宙に浮いた参照）

**① 「文字化けしている」と報告した1行は、文字化けしていなかった。**
本文（上）は `js/locales/ui.fr.js` の `"Surveyed sections"` を「U+FFFD が2つ入っており、フランス語利用者には
`Tron?ons relev?s` と見える」と記録した。**実測すると、そのバイト列は正しい UTF-8 だった**:

```
$ grep -n "Surveyed sections" js/locales/ui.fr.js | cat -A
5641:  "Surveyed sections": "TronM-CM-'ons relevM-CM-)s",$
          M-CM-' = 0xC3 0xA7 = ç        M-CM-) = 0xC3 0xA9 = é
$ node -e … →  "Tronçons relevés"  ／ code points … 6e e7 6f … ／ has U+FFFD: false
$ 9つの locale ファイル全体の U+FFFD: 0 件
```

⚠⚠⚠ **U+FFFD を見たのはファイルではなく、読んだ道具のほうだった。** Windows の shell 出力が非 ASCII を潰すので、
`grep` の結果を目で読むと `Tron?ons` に見える。**そこで「欠陥だ」と結論すると、正しい行を「直して」壊す。**
実際、この追記は「1行の置換」として着手された——あと一歩だった。
⇒ **「壊れている」という報告は、報告したのと別の道具で確かめてから直す。** `node -e` で code point を印字すれば
1コマンドで済む。#R313 追記2（**Node の ICU を測って、ブラウザを一度も測っていなかった**）と同じ形で、
**計器そのものが嘘をつく**類。

**② #R375 の「#R358 の本番検証」を #R392 に直した**（`DEV-NOTES.md`・`js/countries-ui.js`・
`tests/r375-checks.test.mjs` の3か所）。**R358 はこのラウンドのブランチ名であって、ラウンド番号ではない**——

R375 が引用した時点の番号は残らなかった。

### 追記2（本番検証で見つかった1件）

本番（`fcdb056`）を本物の Chromium で 12 視点掃引した結果は**すべて期待どおり**だった——4文の集合は
**12/12 が一意**、merge 前に同一だった**7組すべてが「異なる」**、DOM は **12/12 で作り直され**（以前は
B・C・D が作り直されてすらいなかった）、**uncaught page error 0 件**、期待した具体例7件（要衝・国境・

タンジェ／チュクン／ハサブ／サニーヴェイル／エベレストと現地語化されていた。

**そのうえで1件だけおかしかった。** D（日本全体 z5・中心 138E/37N）が
`This is where Japan meets East China Sea` と言った。中心から測ると:

| 行 | ラベル点 | 中心からの距離 | rank |
|---|---|---|---|
| **Sea of Japan** | `[134.5, 40]` | **452 km** | z=3 |
| East China Sea | `[125, 29]` | **1,501 km** | z=3 |

⚠⚠⚠ **枠に入った行を全部「距離0」にしていた。** `d: inBox ? 0 : d` は「枠内を枠外より優先する」つもりの
一行だったが、**枠内どうしの順序を消していた**——両方 0 になり、どちらも rank z=3 なので reach の同点判定も
効かず、**勝者を決めていたのは `js/tables.js` が先に並べているほう**だった。
⇒ **枠内は距離ではなくソートの第1鍵にする**: 枠内が枠外に勝ち、**同じ群の中では実距離が決める**。

⚠⚠ **2つの鍵を別々に変異させて、両方が赤になることを確かめた。** 最初に書いた `inBox` の主張は
**行の並び順を入れ替えても緑**で、つまり何も測っていなかった（本当に効いていたのは `d=0` を外したほうだけ）。
中心を枠の東端に置き、**「近いが枠外」対「遠いが枠内」**が逆を向く構図に書き直して、ようやく両方が赤にできた。
[[R392 本文]] の①と同じ失敗を、同じラウンドの中で2度目に踏んでいる。
