## R333 — **一つのコミットの半分だけが本番に届いていた**

利用者の報告は「Atlas に『ポーランド』と訊いたら `Failed to fetch` になる」だった。

**Atlas の判断処理にも、質問の内容にも、一度も到達していなかった。** ブラウザが
AI サーバへ POST する**手前**で止まっていた。

### 1. 二つの配信経路と、その間に無かった門

| 半分 | 本番へ届く方法 | 自動か |
|---|---|---|
| `js/`（フロント） | `main` へ push → `deploy.yml` が build して Pages へ公開 | **自動** |
| `supabase/functions/`（Edge Function） | 人間が `supabase functions deploy` と打つ | **手動** |

#R318 は「1 user turn＝1利用」を実現するため、`x-intmap-turn` を**両方**に載せた。
フロントは届いた。Function は届かなかった。**両者のズレを見る検査は一つも無かった。**

### 2. なぜ `Failed to fetch` という形になるのか

独自ヘッダを含む別オリジンへの要求では、ブラウザが本体の前に OPTIONS プリフライトを送る。
サーバがそのヘッダを `Access-Control-Allow-Headers` に列挙しなければ、**本体の POST は送信されない**。
`fetch()` は 4xx/5xx では reject しない——**ネットワークまたは CORS の拒否でだけ** reject する。
だから JS には 401 も 429 も 500 も届かず、素の `Failed to fetch` だけが残った。

本番の実測（修復前）:

```
access-control-allow-headers: authorization, x-client-info, apikey, content-type
```

`x-intmap-turn` が無い。リポジトリの `supabase/functions/ai-proxy/index.ts:86` にはあった。

### 3. 因果を閉じた対照実験

修復後、**本番ページと同じオリジンから**3本投げた。

| 経路 | 結果 |
|---|---|
| `x-intmap-turn`（壊れていた経路） | **HTTP 401** — CORS 通過 |
| `x-intmap-bogus`（未許可・対照） | **`Failed to fetch`** — 報告された症状と同型 |
| ヘッダ無し（対照） | HTTP 401 — CORS 通過 |

対照が「未許可ヘッダは**今も**落ちる」ことを示すので、`x-intmap-turn` がもうその状態ではない
ことが言える。**片方だけでは「たまたま通った」と区別がつかない。**

### 4. デプロイの順序に唯一の正解があった

#R318 の migration `20260823090000_ai_turn_quota.sql` も**本番に未適用**で、
`consume_ai_turn` / `refund_ai_turn` / `sweep_ai_turns` は存在しなかった（実測）。
新しい `ai-proxy` は RPC 失敗を `catch` して **`quota_unavailable` の 500 を返す fail-closed**。

⇒ **migration を先に適用しないまま Function だけ出すと、全利用者が 500 になる。**

`docs/MIGRATIONS.md` §5 の手順がこの状況をそのまま予見していた。`supabase db push` は
**リモートが記録していない全部**（baseline `20260718090000` を含む4件）を live DB に流そうとする
ので使わず、`db query --file` で1本だけ適用して `migration repair --status applied` で記録した。
SQL は `create table if not exists` / `create or replace function` / `drop policy if exists` で
**完全に冪等**であることを先に確かめている。

復旧後、本番で機能そのものを検証した（すべて `rollback`・`ai_turns` に残骸0）:

| 呼び出し | `charged` | `calls` |
|---|---|---|
| 1回目 | **true** | 1 |
| 2回目（同一ターン） | **false** | 2 |

これが #R318 の目的そのもの——1つの質問が3回課金されない。

### 5. 「4本デプロイ漏れ」は私の誤検出だった

commit 時刻と本番 `updated_at` を比べて、`cable-geo` / `delete-account` / `news-relay` /
`sv-cov` の4本が古く見えた。**squash merge は commit 時刻を実デプロイ順と食い違わせる。**

⇒ 8本すべてを `supabase functions download` して**実際に diff** した結果、`_shared` の2本を
含めて**全一致**。漏れていたのは `ai-proxy` 1本だけだった。**時刻で疑い、中身で確かめる。**

### 6. 本番にはリポジトリに無い9本目が居る

`aviation-feed` が ACTIVE（v9）。リポジトリにも `config.toml` にも docs にも**0件**。
`wt-r321-aviation-platform` の**並行セッションが開発中で、main に未 merge**——正常な運用の一部。

⇒ 検査は**リポジトリ側から回して ⊆ を見る一方向**にした。本番が宣言より多く許可しているのは
異常ではない。逆向きの検査にすると、並行ラウンドが本番に先行デプロイするたびに赤くなる。

### 7. 直したもの

`tests/helpers/fn-cors.js`（新規）が契約をリポジトリから読む。**spec と node 検査の両方が
同じコードを使う**ので、抽出器そのものが検査対象になる。

⚠ **最初の版は8本中4本しか読めていなかった。** `alerts-relay` / `cable-geo` / `news-relay` /
`sv-cov` は `_shared/relay-guard.js` の `corsFor(extra)` で表を組み立てる。そのまま出していたら
**半分を「検査済み」と称していた**（#R320）。`corsFor()` の結合規則ごと解決し、どちらの経路でも
読めない Function は `via:'unknown'` として**検査を落とす**——黙って一覧から外さない。

| 場所 | 何を見るか | ネットワーク |
|---|---|---|
| `tests/prod-smoke.spec.js`（#R333） | リポジトリの宣言 **⊆ 本番の OPTIONS 応答**、全 Function | **要**（`deploy.yml` の post-smoke） |
| `tests/r333-checks.test.mjs`（9本） | フロントが送るヘッダ ⊆ どれかの Function が許可／曖昧さの番人／`_shared` を関数に数えない／`index.gemini-backup.ts` を読まない／本番側の検査が消えていないこと | 不要 |

### 8. 緑は検査が効く証拠ではないので、壊して赤を見た

| 壊し方 | 結果 |
|---|---|
| `ai-proxy` から `x-intmap-turn` を外す | node 側 ②③⑥ が赤 |
| リポジトリだけが宣言するヘッダを足す | prod-smoke が赤: `production allows [...] and is missing [x-intmap-notdeployed] — deploy it: supabase functions deploy ai-proxy` |

置換のたびに**出現回数がちょうど1であることを確かめる番人**を通した（#R323）。
