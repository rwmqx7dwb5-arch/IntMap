## R388 — **「軌間別」と名乗っていたレイヤーは、一度も軌間を読んでいなかった**

> 「現在の『世界の鉄道（軌間別）』は、各線路そのものの軌間を読んでいるわけではありません。変換コードを見ると、
> 線路の中点が入る国を判定し、その国の『主要軌間』をその線路全体に割り当てています。（…）
> さらに電化方式、最高速度、複線/単線、高速鉄道、旅客/貨物、運行状態、建設中、駅、路線会社まで持てます。
> 現在のIntMap規模に対して、この鉄道レイヤーはまだ初期世代です。」

### 1. 何が壊れていたのか — 「粗い」ではなく「読んでいない」

`_rail_convert.py` は Natural Earth 10m の線を取り、**各線の中点をどの国のポリゴンが含むか**を ray-casting で
判定し、ハードコードされた「その国の主流軌間」を**線全体**に割り当てていた。出荷物は 25,242 本の LineString で、
`properties` の鍵は全 feature を走査して **`g` ただ1つ**。

OSM の実タグと突き合わせた実測:

| 箱 | OSM が書いている軌間 | 旧レイヤーの塗り |
|---|---|---|
| イベリア | 1668×6,444 way / **1435×169** / **1000×145** / 1067×4 / 600×2 | 全部 1668 mm |
| インド | 1676×20,014 / **762×249** / **1000×195** / 610×7 | 全部 1676 mm |

**マドリード–バルセロナの AVE の上に「イベリア軌間 1668mm」と書いてあった。** これは粗いのではなく、
**そのレイヤーが専門性を主張している唯一の項目で間違っている**。

### 2. OSM が実際に持っているもの（付与率は地域差が大きい）

| | イベリア | インド |
|---|---|---|
| `gauge` | 99% | 92% |
| `electrified` / `voltage` | 99% / 75% | 87% / 81% |
| `usage` | 63% | 87% |

⇒ **どの軸にも「OSM に記載なし」のバケットがあり、その灰色はどの回答の色とも一致しない。**
灰色は「記載がない」以外の意味を持たない——既定値でも、その国の主流値でもない。
**旧レイヤーの灰色は 25,242 本中 342 本**で、残りは全部推測だった。正直な答えが最も珍しい地図は、
自信を持って嘘をつく地図である。

### 4. 高くついた実測

**⚠⚠⚠ 「答えたインスタンス」は「惑星を持っているインスタンス」ではない。**
最初の完走は 540 セル中 **505 が「空」**・分割 0・**177,602 way**。何もエラーを出していない。
原因は `overpass.osm.ch` が**スイス専用**インスタンスで、他の bbox に **200 と `{"elements":[]}`** を返すこと。
疎通確認は**ジュネーブの箱**で行っていたので、「サーバが生きている」ことしか証明していなかった。
同じ質問を4地域で実測: インド 0 / ブラジル 0 / ドイツ 0 / 日本 0 —— maps.mail.ru は 183 / 1,063 / **5,650** / 12,686。
⇒ **健全性検査ではなく被覆検査**にした。**答えを知っている箱**（ルール地方・`railway=rail` 5,650本）を訊き、
空を返したインスタンスは planet インスタンスではないので落とす。

**⚠⚠⚠ 拒否されたセルは「答えられたセル」ではない。**
唯一選出されたインスタンスが 10° クエリを拒み始め、リトライ梯子を使い切った **34 セル**（中央アジア 40–50°N）が
帳消しにされ、掃引は "done" と出力した。しかも再選出は `done % 60` で数えていたので、
**成功が止まると再選出も止まる**——**うまくいっている間しか走らない復旧検査は、復旧検査ではない。**
⇒ 拒否は**遅延**であって答えではない（キュー末尾へ・120秒の冷却・再選出、**試行回数**で数える）。

**⚠⚠⚠ 構文エラーを「混雑」に分類していた。**
`convert item ::geom=center()` は不正（`center` は集合の集約で引数を要る）。OSM3S は «parse error» を返すが、
分類器の**既定が「一時的」**だったので、駅の掃引は**プログラミングの誤りをリトライし続け、過負荷サーバーのふりをした**。
⇒ `bad-query` を明示的に分類して即座に throw する。**既定が「もう一度」の分類器は、恒久的な失敗を名指ししなければならない。**

**⚠⚠⚠ ファサードの名前を「もっともらしいほう」で呼んでいた。**
`layers.setVisibility` / `camera.zoom()` / `camera.bounds()` は存在しない（`setVisible` / `getZoom` / `getBounds`）。
3つとも `try{ }catch(_){ }` の中なので **TypeError は飲まれ、レイヤーは一生表示されず、詳細セルは一度も要求されない**
——生きているように見えて何もしないトグル。⇒ 検査⑫が `GE().<ns>.<method>(` を抽出して `js/geo-engine.js` の
名前空間表と突き合わせる（**3つの綴りを戻して、3件だけが赤くなることを実測**）。

**⚠⚠⚠ i18n ゲートが緑のまま誤訳が出た。**
`In service` は既に `js/datacenters.js` / `js/osm-facilities.js` / `js/subcable-info.js` の鍵で、
4言語の値は**「就役年月」の欄ラベル**。鉄道の運行状態の凡例が zh 「啟用時間」・ko 「가동 시작」と印字され、
隣に「建設中」が並ぶ。**欠落 0・全面 100%。** ⇒ **鍵の共有は意味の共有**。`In operation` に変えた
（`js/company-data.js` が同じ意味で使っているので、そちらとは共有してよい——9言語の掃引が実レジストリで確認）。

**⚠⚠ 素の「鉄道」は既定 ON の基図参照線に向いていた。**
`js/atlas-console.js` の別名表で `railway`/`railways`/`rail`/`trains`/`鉄道` の5綴りが全部 `cb-rail2` を指しており、
それは既定 ON。つまり「鉄道を表示して」は**何も起こさずに成功を報告していた**。
⇒ 素の語はアトラス（`beta-dl-rail`）へ。**参照線には自分を名指しする語を与えた**——片方の到達性を奪って
他方に与えるのは、欠陥の解消ではなく移動。

**⚠⚠ 連結は「出荷する粒度」で行う。**
世界図の鎖を**生の値**（電圧・最高速度・線路数）で切っていたので、同じ線の 158 km/h と 160 km/h が別 feature になり、
z5 では同じ色の同じ画素になる。世界図はバケットを出荷するのだから、**バケットが同一性**である。

**⚠⚠ 短い断片を長さだけで落とすと、本線に穴が空く。**
鎖は**属性が変わるたびに切れる**ので、駅構内の 2 km が両端に本線を持つ。長さだけで落とすと、
地上では連続している線に穴が開き、**欠測とまったく同じ見た目**になる。
⇒ **孤立しているものだけ落とす**（両端のどちらも「残す鎖」と共有していないとき）。
実測: **74,219 本が救済**され、落としたのは路線長の **2.1%**。

**⚠⚠ 払っていたのは頂点ではなく定型文だった。**
世界図を素の GeoJSON で出すと raw 3.28 MB、うち頂点は 0.9 MB。残りは
`{"type":"Feature","geometry":{"type":"LineString","coordinates":` の反復と、同じ属性オブジェクトを
16,000 回書き写したもの。⇒ **属性タプルの辞書＋線ごとの索引＋差分整数の座標**（`js/rail-schema.js`）で
raw 3.28→0.62 MB。⚠ **行ごとに一意な値（OSM way id）は辞書に入れてはならない**——全タプルが別物になり、
辞書がデータの長い写しになる。

**⚠⚠ 共有モジュールは名前空間 1 本で export する。**
`tests/r175 ③` は「js/ の export は js/ のどこかから名前で import されること」を要求する。
29 個を個別に export すると、ブラウザが使わない 20 個が**「死んだコード」**として赤くなる。
`js/war-geom.js` が同じ理由で `export const WarGeom = (function(){…})()` の形をしている。

**⚠⚠ 試験予算は古い過大評価から払った。**
`tests/r184-imagery.spec.js` は 76 秒と記録されていて、**実測 37.2 / 42.9 秒**（2回・直列・サーバ起動済み・4本合格）。
台帳の作法どおり**上限側の 43** を採り、主張する節約は測った額より小さい **33 秒**。
total 4,808 → **4,792**。core は 50 のまま（現ラウンドの spec が 7 秒で、`r355` が門を出て空けた 8 秒に収まる）。

### 追記（本番検証）— カードが同じ事実を2回印字していた

本番の実機検証で1件。**電化の欄が「1.5 kV DC · 1.5 kV DC」と出ていた**——日本語では
**「直流 1.5kV · 1.5 kV DC」**で、**後半が英語のまま**。原因は行が**バケットのラベル**と**実測値**を
必ず両方 join していたことで、`dc15`/`dc3`/`ac25`/`ac15` の4つでは**その2つは同じ文**である。
（実測値は数字から組み立てるので表を通らない＝翻訳もされない。）
同じ形が副題にもあった: `bk` は**線種**で、建設中の線ではその線種が `construction` なので、
状態を足すと「Under construction · Under construction」になる。

⇒ **実測値が主で、ラベルはそれが無いときの代役**（実測値は周波数を持つぶん情報が多い）。
副題は**線種がすでに状態を含んでいるときは足さない**。

⚠ **検査は「赤にできる」ほうをソースに置いた。** ブラウザ側（`tests/r388-detail.spec.js`）にも
同じ主張を書いたが、**その spec が開くのはスペインの高速線（25 kV AC 50 Hz）で、実測値とラベルが
周波数のぶん違うため、この欠陥は現れない**——欠陥を意図的に戻してビルドし直しても**合格したまま**だった。
噛むのは `tests/r388-checks.test.mjs ⑭`（戻すと 14→13 pass / 1 fail、直すと 14 に戻ることを実測）。
**固定サンプルの上で通る否定の検査は、通ることの証明にならない。**

⚠ 同じ検証で確認できたこと（本番実測）: `window.IntMapRailways.count()` = **111,660**、
レンダラが実際に描いた線 **4,624 → 40,244（欧州 z4.2）**、イベリアの `g` は **1668×2,431 と
1435×892 が同居**、軸の切り替えで `getPaint('rail-ln','line-color')` が `["match",["get","bg"]…]`
から `["match",["get","be"]…]` へ**実際に変わる**、東京 z9 で `c/35_135.json.gz`（138 kB）と
`st/35_135.json.gz`（111 kB）を取得、駅の点は z9・ラベルは z10 から、レイヤー ON で増える鉄道由来の
通信は **1,157,256 B**、鉄道由来のコンソールエラー **0 件**、9言語のうち日本語で凡例・カードとも日本語。
