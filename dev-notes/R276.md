### ⚠⚠⚠ ① 時刻スライダーは、一度も時刻を選んでいなかった

`js/weather.js` はタイル URL をこう組んでいた：

    om://…/latest.json?variable=temperature_2m&time=<ISO>

Open-Meteo の SDK の `normalizeUrl` を**実際に呼んで**測った：

    normalizeUrl('…latest.json?variable=temperature_2m&time=2026-08-21T00:00Z')
      → 'om://…/2026/08/20/0600Z/2026-08-20T0600.om?variable=temperature_2m'

**`time=` は読まれていない。** SDK が時刻を受け取る口は `time_step=valid_times:<i>` の方で、しかも 0.0.19 では
それが `NaN-aN-aNTaN00.om` に解決される（これも実測）。さらに SDK のキャッシュ鍵は
`DATA_RELEVANT_PARAMS`＝**`['variable']` だけ**なので、仮に URL が時刻で違っていても**同じ状態を掴む**。

→ **`.json` を SDK に渡すのをやめた。** `window.IntMapECMWF`（新規 `js/wx-ecmwf.js`）が
`reference_time` と `valid_times[i]` から実ファイルを自分で組む：

    <base>/<初期 YYYY>/<MM>/<DD>/<HH>00Z/<有効 YYYY-MM-DD>T<HH>00.om

**ファイル名に有効時刻が入っている**ので、鍵も内容も時刻で分かれる。検証（Playwright・実データ）:

    setIndex(+24) 前  …/2026-08-20T1300.om  値 4.793 m/s
    setIndex(+24) 後  …/2026-08-21T1300.om  値 3.898 m/s

### ⚠⚠⚠ ② 未来を捨てるフィルタが、6日分の予報のうち 8 段しか残していなかった

`fetchMeta` が `valid_times` を「今＋1時間」で切っていた。実測、フィードは **109 段**（3日は毎時、
6日目まで3時間毎）を公開しているのに、スライダーの `max` は **7** だった。→ 撤去。既定は「今」に最も近い段、
⏮ ◀ ▶/⏸ ▶ ⦿ の再生器つき。**モデル初期時刻（run）と有効時刻の両方を印字する。**
モデルランが変わったときは**同じ添字ではなく同じ壁時計の瞬間**へ移す（06Z の 6 番目と 12Z の 6 番目は 6 時間違う）。

### ⚠⚠⚠ ③ 風は「9 km のネイティブ場」ではなく、855 点の地点格子だった

旧実装は `api.open-meteo.com` に **2,232 地点**の現在値を 5 本のチャンクで問い合わせ、届いた点を
1024×512 の Web-Mercator キャンバスへ塗って image source に渡していた。実測、**細かい方は間に合わず
8°の粗い方（855 点）が勝つ**。地球全体で 855 点である。

→ 色面・粒子・地点値の3つが、**同じ `Float32Array`** を読むようにした。ECMWF IFS HRES・O1280 縮約ガウス格子＝
**6,599,680 点**（実測）。SDK の派生規則が u と v を読んで `values`＝風速・`directions`＝風向を返すので、
粒子はそこから u,v を再構成する。**低解像度の地点格子は存在しない。**

- 全球の初回読み込みは 8.7 秒、同じランの別変数・別時刻は **1.0〜1.6 秒**（ブロックキャッシュが温まるため）。
  だから次の時刻を `prefetch` で温める。
- 粒子は毎フレーム**ネイティブ格子を直接**サンプルする（実測 **14,000 回 2.2 ms**）。格子への再サンプルは不要だった。
- ⚠ **風向は最近傍、風速は線形補間。** 角度を線形補間すると 0/360 の継ぎ目で風が一瞬逆を向く。
  O1280 の半セルは 4.5 km ＝ 粒子が見える倍率では 1 画素未満。

### ⚠⚠⚠ ④ 二重透過だと思っていたら、3つ目の掛け算があった——**夜のシェード**

指示は「ピクセルαと Raster opacity を二重に掛けるな」。両方直したうえで**画素を読んだ**
（flat・z3・150°E 20°N・現地 23 時）:

    その風速 4.67 m/s に LUT が要求する色   rgb(40,130,180)
    実際に描かれていた画素                   rgb(15,43,64)      ← 0.36 倍

`firstSymbolId()` が返すのは**最初の symbol レイヤー**＝経緯線ラベル `grid-tropic-label` で、
「最初の symbol の下」は 60 層のうち **13 番目**だった。`im-night-lights-lyr`(29) と `im-night-shade`(30) の
**下**である。z3 の夜側シェードは不透明度 0.75 前後——**惑星の半分が灰色の膜越しに気象を見ていた**。
スライダーでは直しようがない。

→ **気象の面は装飾の上、ラベルと国境の下**（Windy と同じ並び）。`IntMapECMWF.before()` が夜側スタックの
直後を返し、`lift()` が **毎 idle** で位置を主張し直す（`js/night-side.js` は自分の層をタイマーで貼り直すので、
一度置いただけでは元に戻る）。修正後の実測は **`rgb(40,130,180)`——LUT と 1 バイトも違わない。**

### ⚠⚠ ⑤ 凡例は「レンダラ自身の表」から作る

「CAPE 不安定度（ECMWF）レイヤーの凡例名が ECMWF気象になっている。また、凡例がない。説明もない。」——
そのとおりで、ECMWF 系レイヤーの凡例は**時刻スライダーが入っているだけの箱**だった。
→ `IntMapECMWF.legend(variable)` が SDK の配色表そのもの（`getColorScale`）から
**単位・端点・目盛・グラデーション**を作る。凡例に出るのは**そのレイヤーの名前**、その**説明文**、
その**数値目盛**（気温は `imUnitTemp`、風は風速単位に従う）。
風の凡例の最大値は手書きの「40 m/s」だったが、**実際の LUT は 60 m/s まで**あった——半分ハリケーン分ずれていた。
もう手書きしていないので、ずれようがない。

### ⚠⚠ ⑥ 「Open-Meteo GFS」は 11 ラウンド、**一度も本当ではなかった**

風の凡例の下の行がそう書いていた。Open-Meteo の forecast API は `models=` 未指定なら **Best match** の
ブレンドで、GFS ではない。そして今回から、その面はそもそも forecast API ではなく **ECMWF IFS HRES** である。
→ 凡例はモデル名・解像度・初期時刻・有効時刻を**モデルから読んで**出す。地点天気ポップアップは
`_src`（どのサービスが答えたか）と `model`（その中のどのモデルか）を分けて持ち、
**Best match は翻訳しない**（Open-Meteo 自身の設定名なので、言語で変わると誰も調べられない）。

### ⚠⚠ ⑦ `sea_surface_temperature` はこのフィードに存在しない

`latest.json` の `variables`（35 個）に無い。**9 ラウンド、ec-sst は存在しない子を要求して黙って何も描いて
いなかった。** → 目録から外し、空いた行に `wind_gusts_10m`（最大瞬間風速）を入れた。海水温は GHRSST の

### ⚠⚠ ⑧ 重複 ID `ec-time` / `ec-validtime`

`IntMapWeatherEC.open()` が作る別パネルと、凡例が、**同じ id を 2 つずつ**持っていた（実測 2/2）。
→ パネルを廃し、`open()` は凡例を出す。風の凡例にも再生器を置いたが、id は `wind-time`/`wind-validtime` で

### ⚠⚠ ⑨ 地点値は、画面の絵と同じデータから

NASA の `temp` レイヤー（MERRA-2 **月平均**・日付は利用者が選べる）を出しているとき、カーソル下の数値は
`api.open-meteo.com` の **今の気温**だった。**別のデータセットの、別の時刻の数字**である。
→ ECMWF ラスタが出ていれば `valueNow(variable, lat, lng)`＝タイルを描いたのと同じ配列。
GIBS ラスタは地点値サービスを持たないので、**データセット名と表示中の日付**を出して止まる。
検証：読み出しが `30 J/kg · 20 Aug, 14:00`、同じ緯度経度の `valueNow('cape')` が **30**。

### ⚠⚠ ⑩ RainViewer は最新1枚しか出しておらず、その半分は**もう存在しない**

実測（2026-08-20）：`radar.past` は 13 コマ（10 分間隔・直近2時間）、`satellite.infrared` は **0 コマ**。

→ レーダーは**ループ**（コマ送り・再生・スライダー、「13:30 · −11 分 · 13/13」）。
雲は **NASA GIBS の静止衛星 clean-IR**（ひまわり＋GOES-East＋GOES-West、10 分間隔）に置き換え、**行を作った**。

`RV_SCHEME` が実際に返ってくる方を名指しする。

### ⚠⚠ ⑪ 更新ボタンがキャッシュを無効化していなかった／「更新時刻」がブラウザ時計だった

⟳ は `open()` を呼び直すだけで、10 分のローカルキャッシュと `IntMapWx` の 5 分キャッシュに当たっていた。

突風・海面更正気圧・モデル名を追加し、風速は地図の風速単位に従う。
⚠ `surface_pressure` は観測点の高度の気圧なので、山では 200 hPa 低い——**海面更正は別の欄**。

### ⚠⚠ ⑫ Open-Meteo への直接 fetch を全部 `IntMapWx` に通した

`IntMapWx.isOpenMeteo(url)` を公開し（**部分文字列ではなくホストで**判定——`?x=open-meteo.com` を含む
別ドメインで日次ブレーカが落ちてはならない）、`sims.js` と `atlas-console.js` の共有ローダが**先頭で**そこへ
振り替える。残る生 fetch（map-ui の地点プローブ・標高3か所・widgets の AQI・flight-sim の高層風・
layer-previews の一括グリッド・world-packs の潮位2か所）も `guardedJSON` へ。
**風場を大量の地点リクエストで取る方式は、コードから消えた。**

### 粒子——WebGL・1 描画呼び出し・実経過時間

旧ループは粒子ごとに `beginPath/moveTo/lineTo/stroke`（最大 7,000 回/フレーム）で、
**すべての量がフレーム単位**だった：`p.age++`（寿命）・`dt=0.05*mPerPx`（移動量）・
`fillRect(α=0.08)`（残像）。**144 Hz の画面では風が 2.4 倍速く吹き、残像は 2.4 分の1だった。**
→ `js/wx-wind.js`：全セグメントを 1 本の頂点バッファ（線分＝三角形2枚。`gl.lineWidth` はどのブラウザでも
1 に丸められるので、太さを本物にするには三角形が要る）に書いて **1 回 drawArrays**。残像は塗りではなく
**テクスチャ**——2枚の FBO を ping-pong し、前のフレームを `exp(-dt/τ)` で焼き戻す。
`dt` は秒、寿命は秒、τ は秒。WebGL が無ければ**束ねた Canvas2D**（幅・αでバケツ分けし、バケツごとに 1 stroke）。
フレーム時間を測って粒子数を上下させる調速器つき。

### 配色は Windy に合わせた

SDK 既定の風配色は最初の 7 m/s で α を 0→1 に上げる＝**静穏域が穴**になり、送られてきた参考画像にならない。
→ `WINDY_WIND`（静穏＝青紫 → 青 → 青緑 → 緑 → 黄 → 橙 → 赤 → マゼンタ → 白、**全域 α=1**）で
プロトコルを登録する。**タイルも凡例も同じ 1 つの表**から来る。

`IntMapShareState.register('weatherEC')`。レイヤーの選択は `dl-*` として既に運ばれていたので、

### 追記3 — 「厳密に一致」が正しい問いなのは、勾配が緩い場所だけだった

追記2 を deploy したあと、台風の眼のテストだけが落ちた:

    Error: the eye is painted with the table entry for the speed at the eye (13.2 m/s)

眼の画素が 13.2 m/s の停留点と**厳密には**一致しない。理由は物理でも実装でもなく、**読んだ場所**である：
このペアは z5 で**眼の壁**——大気で最も急な勾配——を挟んで読むので、1つの画面画素が複数のモデルセルを
覆い、MapLibre の `raster-resampling: linear` がそれらを混ぜる。フィルタ1段分ずれる。

地図中央・z3・外洋を読む方のテスト（画素＝LUT）は**バイト単位で一致**し続けている。それがこのラウンドの
不変条件——夜のシェードが気象を 0.36 倍にしていない、という主張——であり、そこは緩めない。

⚠ **正しい絵が通るまで数値を緩めるのは、テストを無意味にする。** なので**問いの方を変えた**：

    各画素は、相手の停留点より「自分の速度の停留点」に近いか

これは「眼が見える」という主張そのものであり、フィルタに耐える——フィルタは画素を少し動かすが、
ramp の反対端へは動かさない。加えて2つの画素が互いに十分離れていることも見る。

実測（本番、3回）: `3 passed`。


### 追記2 — 本番検証で2件目: 1つのレイヤーを消すことが、全体の「全部忘れろ」になっていた

追記1 を deploy したあと、本番テストの3本目（予報時刻）が落ちた。`valueNow` が **null**。
`held` も `loadingKey` も空で、例外は無い。`release()` に呼び出し元のスタックを一時的に仕込んで確定した:

    Error: rel at release … at r … at Object.toggle … at oi (data-layers の toggleLayer)

**風レイヤーの OFF が犯人だった。** `Wind.stop()` は `EC().release()` を**無条件で**呼び、`held` と
`loadingKey` を両方消す。別の変数（この場合 `temperature_2m`）の読み込みが飛んでいる最中だと、それが
解決したときに `loadingKey === key2` が偽になり、**黙って null を返す**。読者から見れば「ECMWF レイヤーの
地点値が理由もなく空欄」である。

⚠ **作為的な競合ではない。** `js/map-ui.js` は起動後 **700 / 1,800 / 3,200 ms** に保存済みレイヤー集合を
再適用し、共有ハッシュに無いレイヤーを OFF にする——つまりプログラムから点けたレイヤーは1秒後に、
**他人の読み込みの真ん中で**消される。

→ `release(variable)`。**自分のフレームだけ**落とす（`held` があればその `variable`、無ければ飛んでいる
`loadingKey` が自分の変数かどうかで判定）。`setIndex` の中の `release()` は無条件のままで正しい——
時刻が変われば全部の変数が無効になる。

### ⚠⚠ 読み手は1つ、だから待ち行列も1つ

追う過程で分かったもう1つ。SDK の `ensureData` は毎回

    await reader.setToOmFile(state.omFileUrl);   // dispose() して開き直す。共有リーダに対して
    const data = await reader.readVariable(…);

を実行するので、**違うファイル**の読み込みが時間的に重なると互いを壊す（同じ state 同士は
`state.dataPromise` で重複排除されるので安全。**別のファイル**だけが衝突する）。このモジュールが始める
読み込み——`load()` と `prefetch()`——は全部1本の鎖に並べた。**衝突の2人目には決してならない。**

### ⚠⚠ 「熱さ」を色表の外で定義したら、正しい絵で落ちた

台風の眼のテストも本番で失敗した。実測:

    眼      rgb(160,195,55)   ← 13 m/s の停留点
    眼の壁  rgb(210,40,110)   ← 30 m/s の停留点

**絵は完全に正しい。** 落としたのは私が書いた指標のほうで、`赤 − 青` を「熱さ」と定義していた:
160−55 = **105**、210−110 = **100**。この ramp は強い側でマゼンタから白へ抜けるので**青が再び上がり**、
`赤−青` は単調ではない。

→ 両方の画素を**その地点の速度に対する `getColor`** と照合し、さらに**互いに異なる**ことを見る。
**表の横に自分で作った量を書くな、表から読め**——#R270（凡例が自分の色と矛盾していた）の一段上の同じ形。


### 追記 — 本番検証で1件: 「粒子は出るが色がつかない」が #R85 の欠陥として戻っていた

このラウンドが書いた本番テストが、このラウンドの欠陥を捕まえた。post-deploy smoke、CI ランナー、
**75 秒の待ちが4回**（retry 3 まで）:

    TimeoutError: page.waitForFunction: Timeout 75000ms exceeded.
    > 566 |  … return d && d.hasField && d.hasLyr && d.rasterOpacity > 0;

`hasField` は真になっていた——データは届いている。`hasLyr` が真にならない。

**原因。** `addField()` は先頭で `_imCanDraw()` を見て、スタイルが層を受け付けられない間は
**false を返して終わる**。そしてその呼び出しは `load()` からの**1回だけ**だった。スタイルがデータより
**後**に落ち着く機械では、そこで終わり——風は粒子だけになり、**何も再試行しない**。
これは #R85 が「Wind(animated)は粒子のみで地図に色がつかない」という報告に対して作った再試行の梯子で、
今回の書き直しがそれを落としていた。**16 ラウンド前に一度払った代金を、もう一度払った。**

**決定的な再現。** `IntMapGeoEngine.ready()` が真になる**前**に風をオンにする、という 20 行のテストで確定した:

| js/weather.js | 結果 |
|---|---|
| merge 済みの main（修正前） | `hasLyr` は **150 秒**待っても偽 |
| 梯子あり（修正後） | **6.9 秒**で `hasLyr:true` / `rasterOpacity:1` |

`readyAtToggle: false` — つまりトグルの瞬間、スタイルは本当に受け付けられない状態だった。

**直したもの。**

- `ensureField(key)` — 約 16 秒のポーリング（200 ms × 80）＋ 次の `idle`。**着いたら止まる**（`liveKey===key`）。
- ECMWF ラスタの `toggle` も同じ梯子に。`once('idle')` **だけ**では足りない——断られる理由は2つあり
  （スタイルがまだ／メタデータがまだ）、idle で解けるのは片方だけ。
- `applyTime()`（時刻変更時の再構築）も。**先に層を消してから追加する**ので、断られると地図に何も残らない。
- `idle` でも「データはあるのに層が無い」状態を見つけたら貼り直す。

**⚠⚠ 先読みは「時刻変更時」だけにした。** 指示は「時刻変更時は隣接フレームを先読みし」。初回ロードでも
暖めていたのは読みすぎで、しかも高くつく：1フレームの暖機は画面に出ているフレームと**同じ範囲読み込み**
（実測 **410 リクエスト・約 27 MB**）を要求する。再生器に触っていない読者の帯域を、見ないかもしれない絵に
使い、**見ている絵と競合させる**。`load({step:true})` は時刻イベントからしか来ない。

**⚠ `Content-Length` の合計は転送量ではない。** CI の失敗を追う途中で「1つの風の場に 265 MB」という数字が
出た。内訳を取ると、**Range 無しの 200 が 2 本**で 238 MB——`.om` ファイル全体の宣言長である。慌てる前に
**開く操作だけを計った**:

    setToOmFile(現在の時刻のファイル)   260 ms
    setToOmFile(次の時刻のファイル)   1,019 ms

本体は読まれずに捨てられている（範囲読み込みのための索引だけが要る）。実データは 410 本の 64 KB Range＝
**約 27 MB**。**測る前に「重い」と言わない**——そして測る対象は合計ではなく、その操作。
