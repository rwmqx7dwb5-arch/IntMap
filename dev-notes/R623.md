## R623 — **錠は持ち替えのたびに 2.7% で破れており、診断はその破れを「木は綺麗」と印字していた**

> 報告: CI run 34389623083 の「Static checks」で `tests/r403-checks.test.mjs:98` が
> `green()` の前提で落ちた。文言は
> **「edge-count — Architecture.md no longer states how many Edge Functions there are」**、
> そして木の様子は **`(clean)`**。ところがその文言は `tests/r399-checks.test.mjs:113-114` が
> **わざと作る**変異そのもの（`### 6.2 Edge Functions — **16本**` と
> `**Edge Functions を16本デプロイする**` を消す）で、同ファイル :120 が
> `/edge-count[^\n]*Architecture\.md no longer states/` を**要求している**当の赤である。
> **2つのプロセスが同時に木を書いていた**——両方 `withTreeLock` を通っているのに。

### 1. 何が窓だったか（推測ではなく測った）

`node --test` の実行形態をまず測った。**ファイルごとに別プロセス・ファイル内の top-level test は
逐次**（Node 24.18.0 で実測）——だから「同一プロセスで `depth` が壊れる」という筋は消える。

そこで錠そのものに 8 プロセスを当てた。保持は**同期的にイベントループを塞ぐ**（ゲートは
`execFileSync` で走るので実物がそう）。**320 保持のうち 24 件で相互排除が破れた。**
`abandoned()` を計器つきにして窓を特定:

> **`reclaim:dead-owner ["", 0]`** — 所有者の記録が**空文字列**として読まれていた。

`writeFileSync(OWNER, String(process.pid))` は **O_TRUNC で開いてから書く**ので、その隙に
`readFileSync` すると `''` が返る。`Number('')` は **0**、`alive(0)` は false、よって
`abandoned()` は「**生きている保持者は死んでいる**」と報告し、待ち手はその錠を消して入った。
実測 **480 回の持ち替えのうち 13 回 (2.7%)** がその隙に当たっている。

⚠⚠⚠ **これは #R403 が直した時計バグの、帽子を変えただけの再演である。** あのときは
「時間が経った＝死んだ」、今回は「読めなかった＝死んでいない証拠が無い＝死んだ」。
**どちらも、所有者の生存を確かめられなかったことを、所有者が居ないことの証拠として使っている。**

⚠⚠ **1 件の悪い回収は連鎖する。** 錠を奪われた保持者はそれを知らないので、仕事の最後に
`finally` で「自分の」錠を消す——**そこに居るのは奪った側の錠**である。同じ傷が次の待ち手へ渡り、
24 件という数はここから出ている（悪い回収は 4 件しか記録されていない）。

### 2. 直し方——読み直すのではなく、**中途半端な stamp が見えないようにした**

- **stamp は rename で公開する。** `LOCK/pid.writing.<pid>.<rand>` に書き切ってから
  `renameSync` で `LOCK/pid` にする。rename は原子的なので、**読み手には「全部」か「無い」しか
  見えない**。「読めなかったら少し待って読み直す」は窓を狭めるだけで塞がない。
- **読めない stamp は「まだ書かれていない」であって「死んでいる」ではない。** `stampPid()` が
  0 を返したら `UNCLAIMED_MS` の時計へ落ちる（＝所有者がまだ刻んでいない錠と同じ扱い）。
  これで、**将来 stamp を読み損ねる新しい経路ができても、それが削除の許可にはならない。**
- **回収は「削除」ではなく「主張」にした。** `abandoned()` はある瞬間の錠を判定し、`rmSync` は
  別の瞬間にそこに在るものを消す——同じ死んだ錠を 2 人が判定したら、**2 人目は 1 人目がいま
  取った生きた錠を消す**。so `reclaim()` はまず **stamp を rename して自分のものにする**。
  rename は原子的で、勝てるのは 1 人だけ。負けた側は ENOENT を受けて見直すだけ。

**実測: 直す前 320 保持中 24 件破れ、直した版は 18 プロセス・1,080 保持で 0 件。**

### 3. そして診断は、捕まえるために置いた当の場合で答えを逆に言っていた

`tests/r403-checks.test.mjs` の `green()` は `git status --porcelain` を
**`docFacts()` が返ったあとで**採り、自分のコメントで「**汚れていれば錠の破れ・綺麗なら
ゲート自身の問題**」と宣言していた。ところが妨害する書き込みは**ゲートの実行中に入れて戻される**
——それが変異テストという仕事そのもの——なので、採ったときには木はもう綺麗である。
**`(clean)` と印字して、読み手をゲートへ送った。** この回、それで実時間を溶かした。

⚠⚠⚠ **木は、この問いに答えられる立場にない。** 「他に誰か書けたか」は**錠についての問い**で
あり、書き手は全員錠を取る。だから `tests/helpers/gate-precondition.mjs` は**錠に訊く**——
`lockIntact()` が「自分が取った錠が、いまも自分の錠か」を stamp の照合で答える
（stamp は pid ＋ nonce なので、同じプロセスの**次の保持**とも区別がつく）。
git は前後 2 回サンプルするが、それは「そもそも最初から汚れていた」という**第3の答え**のためで、
見えない瞬間について証言させることはもうしない。

⚠⚠ **見えない場合を黙って除外しない。** 錠を取らずに書いて戻す書き手は、この仕組みには見えない。
だから判定文はそれを**名指しして**から「ゲート自身の問題」と言う。
`tests/r623 ⑤` が、錠が破れていた入力に対して「ゲートのせい」とは**決して**言わないことを測る。

### 4. 検査（`tests/r623-checks.test.mjs`）と、その正直な限界

| | 何を測るか | 壊した錠に対する検出 |
|---|---|---|
| ① | 競争のもとで相互排除が実際に成り立つ | **4 回中 1 回**（圧力試験） |
| ② | 読めない stamp は「死んだ所有者」と読まれない | **4 回中 4 回・80ms**（門） |
| ③ | 本当に死んだ所有者の錠は今でも回収される（生存性を失っていない） | — |
| ④ | 保持者は「自分の錠がまだ自分のものか」を訊ける | — |
| ⑤ | 診断は、錠が破れていたときに「ゲート自身の問題」と言わない | — |

⚠ **①を門と呼ばない。** 窓は持ち替えの一瞬にしか開かないので、そのとき何人が覗いていたかという
運が効く。20 秒かけても 4 回に 1 回のままだった（保持を短くすると 0/2）。それでも置くのは、
**②が既知の窓しか見ないのに対し、①は「二人入った」という事実そのものを見る**から——まだ名前の
ついていない壊れ方に対して赤くなれるのは①だけで、しかも**偽陽性が構造上あり得ない**
（他人の token を読んだのなら、他人が中にいた）。

⚠⚠ **①は書いている途中で一度、何も測っていなかった。** `spawnSync` は子の終了まで待つので、
`spawnSync` のループは 8 つの保持者を**順番に**走らせる——競争ゼロの 320 保持である。
**相互排除がまったく無い錠に対して 2 回とも緑になり、それを 10〜19 秒かけて証明していた。**
`spawn` にして全員の終了を待つ形に直した。

⚠ **`docs/TESTING.md` は「四つのファイルが…」と書いていた**——実際に錠を取るのは 9 ファイル。
手で並べた一覧は次に足されたものを黙って落とすので、**数えるコマンドに置き換えた**
（`.agents/rules/no-ad-hoc-hardcoding.md` §2 の 4）。

### 5. 波及

`tests/r399 ①` と `tests/r280 ①` も同じ「ゲートは緑のはず」という前提を、診断なしで主張していた。
両方 `runGate()` 経由にした——**赤くなったときに誰を疑うかを、読み手が推測しなくてよいように。**
