## R307 — **四度目にして、直したのは「症状の下流」ではなく「索引が同じ分割ではないこと」だった**

依頼3件、3件とも繰り返し。警報の塗り漏れ（**4回目**）／風の速さ（**3回目**）／地点を訊く UI（**4回目**）。

### 1.「何も発令されていないのに、灰色に塗られていない場所がある。五條市のように、同じ市町村でも発令単位では分かれている場合なども考慮して。」

#### 測った

本番（#R306 のビルド）を、**同じカメラ・同じキャンバス・同じ標本格子**で点ごとに問い合わせた。

```
本番 · z2 · center(20,30) · canvas 1000×820 · 陸 6,133 点
    728 点 (11.87 %) が何にも塗られていない
    CAN 329 · RUS 197 · BRA 133 · DZA 25 · KAZ 17 · UZB 6 · USA 4 · ほか 16

層ぜんぶ:  灰色になった単位 1,942 ／ 捨てられた単位 2,123 ／ **穴を開けられた単位 6**
```

**穴が開けられたのは 6 個**である。#R305 が足した `punchQuiet` は「発令が単位の中に**収まる**とき」しか
使えず、それ以外は捨てるしかない。そして #R306 の追記が名指ししたとおり、
**警報を公表している索引と、この地図が灰色を描く単位の索引は、同じ分割ではない**——
カナダの ECCC は自前の予報区、ロシア・カザフ・アルジェリアは WMO 登録簿が持つそれぞれの形。
分割が違えば発令は単位の**内にも外にもまたがる**ので、「収まるか」で分けているかぎり
ほとんど全部が捨てる側に落ちる。**#R305 も #R306 もその下流を1つずつ潰していた。**

#### 直した — 穴を開けられるかを訊くのをやめ、差を計算する

灰色は **`単位 − ∪(その単位に重なる発令)`** である（`subtractWarnings`）。
またぐ発令は切り取られ、単位より小さい発令は穴になり、単位を覆う発令は結果を空にする
——**3つの場合が、1つの式の3つの答えになる。**

- ⚠ **候補は「境界箱が重なる発令すべて」**（`warnsNear`）。以前は点の判定に当たったものだけを避けて
  いたので、**辺にまたがる発令の上には灰色が残り得た**——重ねないという #R298 の規則は、
  緩むどころか**強くなる**。
- ⚠ **クリッパは遅延・別チャンク・任意。** `polygon-clipping` はレイヤーを最初に点けたときに届く。
  届くまで（あるいは届かなかったとき）は #R305 の穴と #R298 の切り捨てがそのまま動く
  ——**機能が減る瞬間は無い。**
- ⚠ **推移的に届いている依存は依存ではない。** `@turf/union` の下に入っていたが、上流が版を変えれば
  黙って消える。`package.json` の `dependencies` に宣言した。
- ⚠ **入力が 6 万頂点を超えたら差を計算しない**（従来の経路に落ちる）。この地図が持つ最大の単位は
  **ヌナブト準州の 15,133 頂点**で、そこから 20 区域を引くのに **129 ms**——1回払って覚える価値はあるが、
  上限なしに払う価値は無い。
- ⚠ **巻き方は自分で揃える**（#R305 の ⚠）。`polygon-clipping` は外環と穴を逆符号で返すが、
  MapLibre の `classifyRings` が読むのは巻き方なので、**それが将来も真であることに絵を賭けない**。

```
同じカメラ・同じキャンバス（1000×820）・陸 6,133 点
    CAN 329 → 4     （13 州すべてが灰色を持つ）
    BRA 133 → 0
```

⚠ **ロシアはこの計測では証明できない**——ローカルは WMO 登録簿の掃引が途中で **RUS / KAZ / DZA が
未読（斜線）**だった。#R305 追記と同じ制約なので、確認は**本番検証**で行う。

#### 五條市 — 1つの市町村が複数の発令単位に分かれている

気象庁自身の `area.json` を数えると、**40 市町村が 89 の class20 単位として発表されている**。

```
14100  横浜市北部 | 横浜市南部          29207  五條市北部 | 五條市南部
09206  日光市（今市・日光・藤原・足尾・栗山）  30206  田辺市（5つ）  16201  富山市（3つ）
```

**そして 89 のどれも `…00` で終わらない。** `jpShape` は class20 コードの**上5桁**を市町村コードとして
引くので、これらはすべて**市町村ぜんぶ**に解決していた。実測、いまの r8 の現況は

```
2920701 五條市北部  乾燥注意報 継続      ← 発表あり
2920702 五條市南部  （何も無し）
```

で、地図は**五條市の全面**を注意報の色で塗っていた。

→ 気象庁は class20 ごとの輪郭を `common/const/geojson/class20s/<code>.json` で配っている
（1〜3 kB・`Access-Control-Allow-Origin: *`）。**89 は、#R273 が退けた 1,805 とは別の数である。**
発表中のコードのぶんだけ、同時4本の**待ち行列**で取る。

⚠ **細かい単位で置いた警報は、市町村の「発表なし」を消費しない**（`used` が空）。市町村の灰色はそのまま
出て、上の差が発令された半分だけを切り取る。実測:

```
五條市北部  norm 1  面積 0.01772        五條市（灰色）  norm 0  面積 0.01136 · 15 ポリゴン
合計 = 市の全面。1画素も共有していない。      40 単位すべてが自分の輪郭で描かれた。
```

⚠ **最初の版は 40 のうち 4 しか届かなかった**——「同時4本」を上限として書き、超えた分を**忘れて**いた。
上限は待ち行列の幅であって、要求の集合ではない。

#### ⚠⚠ そして、40 全部が手元にあっても五條市はまだ丸ごと塗られていた

`refresh()` は `if(busy) return;` で始まる。輪郭が届いたときに投げる合流呼び出しは、
**掃引中なら黙って捨てられる**。#R299 の県別境界の昇格（`askJpFine`）も同じ1行の形をしていたので、
両方とも **`busy` なら 700 ms 後に再武装する**ようにした。

### 2.「風レイヤーは品質保ったまま、起動から日時変更からすべてに至るまで、爆速にしろ。」（3回目）

#### 測った — バイト数ではなく、リクエストを1本ずつ

`fetch` に細工して **Range ヘッダごと**時間を測った。一度も訪れていない予報時刻、起動時の視野:

```
本番 · 時刻 30（未訪問）
    メタデータ 2 本（Range 無し）        526 / 522 ms   並行
    ファイル末尾の 64 kB を 1 本      4,130 ms         ← ここ
    データ 93 本 · 5.63 MB           約 1,480 ms      （1本 26〜100 ms）
    復号                                  1 ms
    ───────────────────────────────────
    合計                              6,135 ms
```

**`afterNetMs = 1`。復号は待ち時間ではないし、データも 4 分の 1 でしかない。**
待っていたのは「**CDN がまだ配置していないオブジェクトへの最初のレンジ要求**」で、
1 予報時刻＝1 ファイル（約 114 MB）だから、**時刻を変えるたびに毎回1回払っていた**。

#### 直した — 読む前にファイルに触る

`touch`：**末尾 64 kB を1本**（SDK が最初に要求するブロックと**同じ範囲**なので、読み手が来たときは
ブラウザのキャッシュに載っている）を、軸が決まった瞬間に、**SDK の1本しかない読み手の待ち行列の
外側で**投げる。

```
同じ本番ページ・同じ視野・次の未訪問時刻
    触っていない (idx 30)   6,135 ms   索引 4,130 ms
    触った     (idx 33)     1,670 ms   索引    11 ms   （6.75 MB＝より多い）
```

⚠ **前後の時刻も触る**（進行方向へ2つ・逆へ1つ・各 64 kB）。#R305 の暖機は正しいが
「軸が 2.5 秒静止してから、読み手の後ろに並んで、1つだけ」なので、**1秒ごとに送る読み手は永久に
追い抜けない**。連続5段、どちらも冷たい入力で:

```
前（本番 R306）  6,279 / 6,731 / 5,907 / 6,299 ms
後（R307）      6,341 / **1,229 / 1,640 / 2,425 / 1,110** ms
```

**最初の1段以降は 3.9 倍速い。**

#### ⚠ 最初の1段は速くなっていない。そう書く

索引を取る4秒は**軸が決まるまで始められず**、始めた瞬間に読み手も同じものを要求する。
レイヤーを点けて冷たい時刻を選ぶまでは **前 6,539 ms → 後 6,156 ms**——差は雑音の範囲である。
「起動から」は**達成していない**。

⚠ **触るのは「読む人がいるとき」だけ。** `fetchMeta` は時刻スライダーとニュース年表のために起動時に
走るので、そこから触ると**気象レイヤーを一度も点けない利用者に 256 kB を払わせる**。

#### ⚠⚠ ついでに: ブロックキャッシュが、読み込みの使っているブロックを捨てていた

SDK の `FileReader` が既定で作るのは `BlockCache(64 kB, 128)`＝**8 MB の天井**で、帯1本の作業集合は
**8.63 MB**。実測、1回の帯読みで **195 リクエスト（全部ちょうど 64 kB）・12.19 MB** が飛び、
**57 本は同じ範囲の2度目**だった。→ **同じ 64 kB のまま、512 個（32 MB）**。

⚠ **ブロックを大きくしてはならない。** `blockSize()` が**そのまま HTTP リクエストの大きさ**で、
512 kB にすると欲しい 6.31 MB が **9.00 MB** になり、時間は 11% しか縮まず、**同じ読み手を共有する
ラスタタイル**まで道連れになる。**間違っていたのは粒度ではなく天井である。**

⚠ `ecmwf_ifs025` は今回も採らない——実測 **`valid_times` 49 本 対 109 本**（3時間刻み）。#R299 の判断は正しい。
⚠ **粒子・色・標本間隔・ファイル・モデルは1つも変えていない。**

### 3.「一回地点選んだらそのあとのやつも全部その地点で強制開始とかあほか。」（4回目）

#R298 はこう書いていた——「読み手が既に選んだ地点は二度訊かない: 落としたピンか、**前のツールで選んだ
地点**」。それが今回名指しされた行である。最初のツールだけが訊き、**そのあとのツールは全部その座標で
黙って開いていた**。

→ **一覧の行は毎回訊く。** 記憶した地点（`_picked`）もピンの代用（`HOST.userPins`）も、この経路から
消した——**誰も選んでいない座標が戻ってくる扉が無い。**

- ⚠ **機能は1つも減っていない。** 地図の右クリック（開いた座標を持っている）・Atlas・各パネルの
  ◎「地点を変える…」は、**名指しされた**座標でそのまま開く。消えたのは推測だけである。
- ⚠ #R299 の残り半分（**地点が要らない行は訊かない**）は不変——実測、`sim.terrainWater` と
  `sim.drone` は訊かない。
- ⚠ #R305 の「1つのジェスチャは1回だけ喋る」も不変——実測、armed のとき出るのは
  **赤いトースト1つだけ**で、#R196 の共有バーは要素として作られてすらいない。

### 検査

`tests/r307-checks.test.mjs`（10本）を `package.json` の `test:checks` に**同じコミットで**登録。
主張は**関係**で書いてある——「差が punch より先に訊かれる」「候補は境界箱で選ぶ」「クリッパが無ければ
答えない」「巻きは外環と逆」「分割の規則にコードを1つも書かない」「合流は busy を待つ」
「ブロックは 64 kB 以下・天井は全球1枚以上」「触る範囲は最初のブロックと同じ大きさ」
「行は毎回訊く」。
⚠ ④ は**ライブラリの契約そのもの**を実行して確かめる（またぐ矩形が切り取られること・穴の巻きが
外環と逆であること・覆う矩形が空を返すこと）。
⚠ **`origin/main` のソースに当てて 10 本中 9 本が赤くなることを確認した**（緑のままなのは④＝
ライブラリの契約だけ）。空虚に緑ではない。
