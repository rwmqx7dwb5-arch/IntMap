〈依頼〉 #963（map-motion 第 2 段）の退行。夜側の 1024² の画像を、長いフレームを避けるために
`requestIdleCallback` で区切って計算するようにした結果、マスタークロックを動かしても塗り直しが終わらない。
CI（GPU なし・2 worker）で `tests/r200.spec.js` ③ が赤——時計を動かした 2.2 s 後のキャンバスの α が、
東京の真夜中も正午も 37 のまま。読者にとっては「遅い端末で時計を動かしても昼夜の境界が古いまま」。

## 1. 原因——アイドル時間は忙しいページには来ない

- 刻みは `requestIdleCallback`（timeout 500 ms）で、アイドルが来ない間は 500 ms ごとに 6 ms ずつしか進まない。
  1024² の計算は手元の desktop で約 20 ms、GPU の無い runner や CPU を絞った端末ではその数倍なので、
  時計を動かしてから絵が届くまで秒単位になる。
- 実測（手元・同じ手順・東京を見て時計を 正午→真夜中→正午 と動かし、キャンバスの東京の α が切り替わるまで）:
  - 前（HEAD のビルド）: CPU ×1 で 694 / 3,111 / 676 ms、CPU ×4（CDP `Emulation.setCPUThrottlingRate 4`）で
    **12,291** / 2,222 / 1,044 ms。最初の手元実測では ×4 の 2 回目が 9,772 ms。
  - 後: 粗い絵が着くまで CPU ×1 で 49〜444 ms、×4 で 203〜3,209 ms。全解像度の絵まで ×1 で 390〜1,999 ms、
    ×4 で 688〜10,352 ms（最大値はいずれも throttle を掛けた直後の最初の 1 回で、その間の長いフレームは
    `Response.text.then`・`setTimeout` 由来の別モジュールの処理＝LoAF の帰属で確認）。
  - 夜側自身の 1 タスクの長さ（LoAF の `MessagePort.onmessage`・main チャンク）: ×1 で最大 6 ms、×4 で最大 8 ms。
  - ⚠ 14 セッションが同時に走る機械での実測で、絶対値は揺れる。比べるべきは「アイドル待ちで秒単位」と
    「最初の刻みで粗い絵が届く」の差。

## 2. 直したこと（`js/night-side.js`）

- **刻みはアイドルを待たず、普通のタスクとして取る**: MessageChannel のメッセージ（`js/seismic.js` の `_yield` と
  同じ理由——入れ子の setTimeout は 4 ms に丸められる）で、1 回あたり `PAINT_SLICE_MS`（5 ms、React の
  scheduler の yield 間隔と同じ）まで計算して即座に次を投げる。タスクの間でイベントループが回るので
  長いタスクは作らない（#963 の主張はそのまま）。
- **先に粗く、すぐ正しく**: 最初の段は 1/4 辺（画素数 1/16）の同じ計算で、キャンバスが拡大して描く。
  続く全解像度の段が置き換える。行は描画側の縦座標に線形（`imageRowLatitudes`）なので拡大しても位置は変わらない。
- **新しい目標は置き換え、同じ目標はやり直さない**: 仕事は「時計の分・モザイク・大きさ」の鍵を持つ。
  時計がまた動けば走っている計算を捨てて新しい時刻から始め（追いつけない計算を積まない）、
  同じ絵の再要求（build 直後の `refresh(true)`・時計のイベント・公開の `refresh()`）は何もしない。
- **状態を公開する**: `IntMapNightSide.state().paint` = `{ at, full, pending, stage, lastMs }`
  （キャンバスが持つ時刻・全解像度か・描いている時刻・段・直近の全解像度の所要時間）。
  `state().built` は「組み立て済みで、全解像度の絵を一度描き終えた」（readers: r200・r201・map-motion）。
  公開の窓口は既存の `window.IntMapNightSide.state()` の欄が増えただけ。

## 3. 検査

- `tests/night-side-catchup-checks.test.mjs`（新規）: `js/night-side.js` を**モジュールとして評価**し
  （レンダラと時計を import の辺で差し替え）、**アイドルが一度も来ないページ**で ①呼び出しの中では塗らない
  ②粗い絵→全解像度の絵の順で必ず終わる ③複数のタスクに分かれ、どれも 50 ms 未満 ④時計がまた動けば
  古い時刻の全解像度は完成させない ⑤同じ時刻の再要求ではやり直さない ⑥`state().paint` と `built` の意味。
  HEAD のコードに対しては全部赤になることを確かめた。
- `tests/r200.spec.js` ③: 固定の 2.2 s ではなく `state().paint` が「その時刻の全解像度」になるのを待つ。
  上限 31 s は ×4 で測った最も遅い全解像度（10.4 s）の 3 倍。主張（地平線・太陽・モデル・キャンバスの α 差 > 200）は
  1 つも弱めず、「その時刻の全解像度の絵が載った」という主張を足した。
- `tests/map-motion.spec.js`: 「呼び出しの中では塗らず、あとで完成した絵が届く」の順序の主張は同じ。題を
  「idle slices」から「slices」に直しただけ。
