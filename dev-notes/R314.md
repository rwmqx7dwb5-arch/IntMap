## R314 — **1歩を2つの半分に分けて測ったら、粒子の場はとっくに手元にあって、色タイルの後ろで待っていた**

> 「風レイヤーは品質保ったまま、起動から日時変更からすべてに至るまで、爆速にしろ。」（**6回目**）

#R305・#R307・#R308・#R310 の5ラウンドは、**1歩を1つの数として**測っている。その数はバイトで、
5ラウンドはそのバイトを早く出し・並行に届け・二度取りをやめ・最後には**先読みして復号済みで持つ**
ところまで来た。今回やったのは測り方を1つ変えただけである——**色ラスタのソースを止めて、同じ1歩を
もう一度測った。**

```
1歩 (opening view, 1280×800)          帯の読み込み          色タイル1枚
                                      （粒子と地点値）       (`omProtocol`)
  実測                              513 / 521 / 534 / 537   1,266 / 1,381 / 1,772 ms
  要求 / バイト                      6 req / 4.5 MB          +8 req / +2 MB
  main thread を止めた時間           116 / 121 / 125 / 124   587 〜 970 ms
```

同じ1歩の中に、**費用が 2.5 倍違う2つの仕事**がいた。5ラウンドが測っていた「1歩 = 1,208 ms」は、
**520 ms で終わっていた仕事が、1,300〜1,800 ms かかる仕事の後ろで待っている**という形だった。

### ⚠⚠⚠ そして「次の時刻の先読み」は、遅いほうを合図にしていた

`readAhead` は #R310 が作ったもので、正しい。合図が違った。`afterFieldShown` ——「色面が表に出るまで
待つ」——に結ばれており、#R298 がそこに結んだ理由は**1つだけ**書かれている:

> one reader, one queue … so the next hour's prefetch (**A DIFFERENT FILE, WHICH RE-POINTS THE
> READER**) … queued ahead of the tiles

**#R310 がファイルごとに1本のリーダーを与え（`readerFor`・4本）、タイルが使う SDK 側の1本にも栓を
した時点で、この理由は消えていた。** #R310 自身の注記が「with a reader per file it is no longer in
front of anything」と書いており、それでも門はそのまま残った。

門が残っていた費用は上の表がそのまま示す。色は 1.3〜1.8 秒後に出るので、先読みは**約 2.1〜2.6 秒後**
に始まり、そこから 520 ms 走る。**1.2 秒ごとに送る読み手には一度も間に合わない**——origin/main の
1歩が **0 / 1,180 / 0 / 1,279 / 0 / 1,724 ms** と1歩おきに全額になるのはこれである。

→ **確定している隣の時刻は、場が手に入った瞬間に読む。** 背景レーンのまま（`serial(fn,true)`）、
`opt.step` のまま、`nearBand()` のまま。変えたのは「何を合図にするか」だけ。

### ⚠⚠⚠ 2時刻先も同じ合図にしたら、粒子が速くなったぶんだけ色が遅くなった

1時刻ぶんの先読みは**ちょうど1歩ぶんの余裕**しか作らないので、着いた絵を見てすぐ次を押す読み手は
2歩に1度は窓の端に立つ。そこで2時刻目も同じ合図で放った版を測った:

```
                     origin/main      両方を「場」で放つ
  1歩 → 粒子            802 ms            447 ms      ← 速くなった
  1歩 → 色            1,584 ms          1,906 ms      ← 遅くなった
```

**「パーティクルは比較的すぐ表示されるが、背景のカラーが、時間を変えるとなかなか表示されない」は、
#R298 でこのプロジェクトが既に受け取っている苦情である。** 推測のための帯域を、読み手が待っている
絵から取ってはならない。

→ **確定と推測で合図を分けた。** 2時刻目だけを色の後ろに戻し、そのうえで
**同じ向きに2回以上続けて送ったときだけ**（`_runN >= AHEAD_MAX`・`TRAVEL_MS` = 6 秒の窓）、
**前景が何も待っていないときだけ**（`foregroundBusy()` ——#R305 がこの用途に作って、**呼び出し元が
1つも無かった**扉）読む。1歩は看板であって旅ではない。

```
A/B（origin/main と交互に1プロセスの中で・4セッション × 6歩・クリック間 700 ms・中央値）

                      origin/main       #R314
  1歩 → 粒子の場          763 ms         0 ms      40歩中 28歩が完全に無料（main は 5 歩）
  1歩 → 色面            1,477 ms     1,772 ms      +295 ms — 下記
  1歩あたりのバイト         6 MB         6 MB
  連打 (5歩・150 ms 間隔)  2,737 ms     2,569 ms
```

### ⚠⚠⚠ 色面は速くなっていない。速い回線では約 300 ms 遅い——これは代金であって、隠さない

**1歩が無料になると、次の時刻の先読みは毎回「今の時刻の色タイル」の隣で走る**（従来はその色を
待っていたので、遅い歩のあいだ色はネットワークを独り占めしていた）。4 回の独立した実行で色は
**−388 / +332 / −185 / +295 ms** と動いており、**向きそのものが実行ごとのぶれの中にある**
——データホストへの往復は run ごとに **1.6〜6.8 秒**ぶれる。最大の標本（片腕 40 歩）が **+295 ms**
なので、その数を書く。**粒子側はどの実行でも曖昧ではない。**

⚠ **その間も地図は空にならない。** 新しい色が塗れるまで前の時刻の色が出たままである
（#R284 の 2 スロット・#R297/#R298 の公開規則）。つまり読み手が**得る**のは「粒子と地点値が即座に
来ること」、**失う**のは「既に見えている絵が 1 時刻ぶん古いままの約 300 ms」である。
「日時変更から爆速に」という依頼に対して、この向きの取引を選んだ。

### ⚠⚠⚠ 点灯の 1.36 秒は、クリックを待つ必要がなかった

冷たい点灯をクリックからの経過で刻む:

```
  0 ms        クリック
  121 / 640   340 kB の SDK <script> が解決
  842         ファイルの open が始まる（HEAD）
  976         …HEAD が返る
  1,010       wasm が初めてインスタンス化される
  1,354       …コンパイル完了（344 / 460 / 556 ms・3 回）
  1,355       予報データの最初のレンジがようやく要求される
  3,664       場が手に入る
```

**3.65 秒のうち 1.36 秒が、データを1バイトも要求しないうちに過ぎている。** そしてその3つ——
スクリプト・wasm・**軸が既に指しているファイル**の open ——は**どれもクリックに依存しない**。
`ready()` がクリックで始めるのは、そこが「確実に要る」と分かる最初の瞬間だからにすぎない。

→ `IntMapECMWF.warm()` は同じ仕事を、「**要りそうだ**と分かる最初の瞬間」＝**気象レイヤーの行に
ポインタが乗った／フォーカスが入った**時点で1度だけ行う（行は自分のチェックボックスの id
`dl-wind` / `dl-ec-…` で見分ける＝「レイヤーの公開名はその行の id である」）。
⚠ **帯も復号も12ファイルの stage-in もしない**——絵のバイトは実際に点けた読み手だけが払う
（#R307 の規則）。⚠ 二重に何かをすることは無い（`loadSDK`/`fetchMeta` は memoise、`registerProtocol`
は自分の戻り値でラッチ、`openReader` は `pinReader` でファイルごとに冪等）。

**実測 点灯 4,451 → 2,496 ms**（4回の中央値・毎回まっさらな context・ポインタが行に乗ってから
500 ms 後にクリック）。

### ⚠ 試して外したもの——「示せない速さを主張しない」

- **`coalesceBackend` に隙間を跨がせる案。** 帯は2次元格子の縞なので隣接だけでは1本にまとまらない
  はずだ、と考えた。**実際のレンジを全部捕まえて数えたら、冷たい帯読みは 4 要求・4.63 MB・取りすぎ
  0 バイト**で、GAP 0 と GAP 1 MB が**同じ4本**だった。跨ぐ隙間が存在しない。書かなかった。
  （その計測でついでに分かったこと: **stage-in の窓の外にある時刻は、末尾を読んでから次の要求まで
  4.5 秒あく**。CDN が origin から取ってくる時間で、#R308 の stage-in が存在する理由そのもの。）
- **SDK の 2.1 MB wasm を自前ホストする案。** バンドル 2.99 MB のうち **2.81 MB が base64 の wasm**
  で、`Q.locateFile` を渡せば実ファイルから `instantiateStreaming` できる——が、**渡す口が無い**
  （`hB()` が `qB()` を引数なしで呼ぶ）ので同梱＋改変が要る。`@openmeteo/weather-map-layer` は
  **GPL v2**（npm の `license` フィールドは空・GitHub の LICENSE がそれ）で、**IntMap は public
  リポジトリ**なので同梱してはならない。調べた時点で捨てた。
  ⚠ ついでに #R310 の「data URI を2回・計 1.6 秒」は**このマシンでは再現しない**——
  `instantiateStreaming` が data URI で成功し、**93 / 75 ms**で終わる。wasm の 344〜556 ms は
  初回インスタンス化そのもので、2回取りではない。

### ⚠⚠ 最初の3時間は、測れない場所で測っていた

「`setIndex` から `ready()` まで 875 ms の空白がある」という所見を2回書いた。**全部これだった**——
Browser ペインは `document.hidden === true` に固定されており、**rAF が1回も回らず、
`setTimeout(…, 140)` が 1,001 / 1,032 / 1,135 ms で発火する**（背景タブのタイマ clamp）。
`?rafshim=1` は rAF を `setTimeout` に置き換えるだけなので、この環境では救わない。

→ 計測は **Playwright の可視ページ**へ移した。さらに **A/B は1プロセスの中で木を交互に開く**——
open-meteo への往復は run ごとに **1.6〜6.8 秒**ぶれるので、片方ずつ測ると**差より大きい**。
（`intmap-recurring-lessons` の「測れない環境で測るな」の、たぶん何度目か。）

### 検査

新設 `tests/r314-checks.test.mjs`（5本）は **`origin/main` に当てて5本とも赤**になることを確かめて
から採用した。既存3本が赤くなり、内訳は:

- **#R276 ⑰ / #R310 ⑤** — `if(opt&&opt.step){` に `on&&` を差し込んだだけ。題は今も真なので
  `if(on){` を**中**へ入れて元の綴りに戻した（検査は1文字も触っていない）。
- **#R298 ⑧** — **本当に覆した規則。** その検査自身が前提として書いている「リーダーは1本」が
  #R310 で失効していることを注記し、**主張を推測の2時刻目（`aheadMore`）へ付け替えた**
  ——「読み手が見られないものは色より先に読まない」という規則そのものは生きている。
