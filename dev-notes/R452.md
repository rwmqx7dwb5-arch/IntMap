## R452 — **止まっていたのは時計の不在であって、ループの存在ではなかった**

報告は本番での実測つきだった。News タブで出来事カードの `.ev-sources` を押して詳細を開き、Atlas に
「この出来事について詳しく」と訊く。**`ai-proxy` は 200 を2回とも返している**（5.1 秒 / 33.3 秒）。
それでも吹き出しは `Searching` のまま**2分以上**動かず、最後には**レンダラごと応答不能**になって、
同一オリジンの別タブまで巻き添えになった。記事を開かずに同じ質問をすると**約10秒で完了する**。

つまりモデルも、アカウントも、通信路も健全だった。**返ってこなかったのは証拠である。**

### 上限は5つあり、どれ1つ時間を測っていなかった

`js/atlas-agent.js` の `LIMITS` は `maxSteps` / `maxToolCalls` / `maxPerStep` / `maxMalformed`。
`js/atlas-answer-pipeline.js` の `MAX_MODEL_CALLS` は 2。**全部が回数である。**
「Atlas が道具を選んだ」から「回答が描かれる」までのあいだで、締切を持たない `await` はこれだけあった。

| 場所 | 何を待っていたか | 締切 |
|---|---|---|
| `js/atlas-agent.js` | `out = await execute(call)` | **無し**（しかも1手ぶんの呼びは**逐次**に await される） |
| `js/atlas-toolsurface.js` | `res = await runAction(built.action)` | **無し** |
| `js/atlas-console.js` | `await Promise.all(jobs)` | **無し**（＝いちばん遅い出所を待つ） |
| `js/atlas-console.js` `_fetchJSON` | 公開 relay 3 本を**逐次**に 9 秒ずつ | ヘッダまで |
| `js/atlas-sources.js` `_fetchText` | 同じ梯子をもう1本 | ヘッダまで |
| `js/atlas-geo-resolve.js` `geocode()` / `_nomExtent()` | Nominatim | **signal すら無い** |
| `js/atlas-verify.js` `_atlGeocodeStrict()` | Nominatim。しかも **1回の回答で最大24本を逐次**、**描画の直前** | **無し** |

掛け算をすると数字ではなく「ずっと Searching」が出てくる。**8手 × 1手あたり8呼び=32呼び × relay の
悪い日。** 上限はどれも正しく効いていて、それでも上限が無かった。

### 「締切がある」ように読める書き方が、締切ではなかった

3つの写しが同じ形をしていた。

```js
const t2 = setTimeout(() => c.abort(), 9000);
const r  = await fetch(p(url), {signal: c.signal});
clearTimeout(t2);                  // ← ヘッダが着いた
if (r && r.ok) return await r.json();   // ← ここには何も掛かっていない
```

⚠ **`clearTimeout` が走るのはヘッダが着いた時点で、本文の読み出しはその外側にある。**
200 を返してから本文が止まった相手を止めるものが、この書き方には存在しない。
実測（2026-08-25・このマシンから）: `api.allorigins.win` は Google News RSS を **8.72 秒**でヘッダごと
返す——**8 秒/9 秒の締切のすぐ外側**。同じ秒に `corsproxy.io` は **403 を 0.09 秒**で返した。

⚠⚠ **ただし、本番で実際にターンの時間を食っていたのはこの穴ではなかった。** 本番で観測した
`AbortError` は **9 本すべてが 9.3〜10.2 秒**——つまりヘッダ側の締切は**発火していた**。時間を食って
いたのは**その締切が 1 出所につき 3〜4 段ぶん逐次に積み上がること**と、**自前 relay を通っていない
こと**のほうである（本番のコンソールでは GDELT 直＝CORS 拒否、`corsproxy.io`＝**408/503**、
`api.allorigins.win`＝10 秒で中断、Google News 直＝CORS 拒否で、**この記事に対するライブ Web 検索は
1 件も成功していなかった**）。本文まで届かない締切は**まだ塞がっていなかった穴**であって、
この報告の主因ではない。両方とも直したが、**どちらが主因だったかは取り違えない。**

そして GDELT。`api.gdeltproject.org` は **`Access-Control-Allow-Origin` ヘッダを持たない 429** を返す
（実測2回、15秒あけて同じ）。ブラウザはヘッダの無い応答を CORS 違反として報告するので、
報告書に並んだ「api.gdeltproject.org → CORS 拒否」の正体は **CORS 設定ではなく GDELT のレート制限**
だった。⚠ この違いは方針を分ける（下）。

### 直したもの

### ⚠ そして、この欠陥が localhost では見えない理由も #R216 と同じだった

Atlas の `_fetchText` が歩いていた順に、**ページから**同じ 1 本のフィードを測った
（`http://127.0.0.1:4442`・2026-08-25・`news.google.com/rss/search?q=Paris&hl=ja&gl=JP&ceid=JP:ja`）。

| 脚 | localhost から | 意味 |
|---|---|---|
| 直（`x => x`） | **CORS 拒否・177 ms** | 費用ゼロで落ちる（だから新しい梯子の `direct:true` は安い） |
| `corsproxy.io` | **200・634 ms・134,063 B・feed** | ⚠ **ここで勝つので、開発機では梯子が健全に見える** |
| `api.allorigins.win` | **12 秒で中断**（12,014 ms） | 旧梯子の 9 秒締切より遅い |

同じ秒に、このマシンの curl から `corsproxy.io` は **403 を 0.09 秒**で返した。#R216 が測った本番
オリジンからは **403 / 503**。⇒ **corsproxy が勝つ限り欠陥は出ず、勝たなくなった瞬間に
「allorigins を 9 秒待って null」だけが残る。** 報告が「本番でしか出ない」形をしていたのは
そのためで、#R216 が「localhost で検証した relay は、そのサイトで検証した relay ではない」と
書いた同じ落とし穴に、**Atlas の写しのほうがまだ落ちていた**。

自前の relay を同じページから測ると **200・813 ms・134,063 B・feed**（`news-relay` 経由）。
⚠ これも localhost からの数字なので、**本番オリジンからの再測は deployment 後に行う**（下）。

⚠⚠ **同じ file を、同じ日に、別のラウンドが半分だけ先に直していた。** #R446 は記事リーダー側から
入って、`js/proxy-fetch.js` に **`opts.as`（feed／html）と `opts.budgetMs`** を——このラウンドが
書いていたのと**同じ2つの考えに独立に到達して**——先に merge した。⇒ **上書きせず、向こうを土台に
こちらの3つを足した**（`json` の受理・**本文まで掛かる締切**・`opts.direct` と `opts.signal`）。
#R402／#R441 と同じ形だが、今回は**両方が必要**だったので捨てずに合流している。⚠ 向こうの検査2本
（`R446 ③`／`⑤`）は綴りを固定していたので、**守っている性質のほうに向け直した**——「予算は旗では
なく時計」（signal で 0 を返すようになった＝より時計）と「受理条件は1つの表」（行が1つ増えた）。

**① 取得の梯子を1本にした。** IntMap には「ACAO を返さない相手から文書を取る」ための正本が
`js/proxy-fetch.js` に既にある（#R212 が時計を、#R216 が自前の Edge Function を先頭に置いた）。
**Atlas はその存在を知らない写しを2つ持っていて、どちらも #R212 以前の版だった。**
だから Atlas が投げる Google News の要求は、**#R216 が用意した `news-relay` を一度も通らず**、
news.google.com が拒む origin から、直・corsproxy・allorigins の順に逐次で出ていた。写しを消し、
`_fetchJSON` / `_fetchText` は `fetchViaProxy()` を呼ぶ。

**② 締切を本文の読み終わりまで掛けた。** `fetchDeadline` は Response ではなく**本文そのもの**を返す。
返す前に時計を止められないので、この形なら次に書く人も同じ間違いをしない。

**③ 呼び出し側が上限を名指しできるようにした。** `fetchViaProxy(url, {as, direct, budgetMs, signal})`。
Atlas は 1 取得 **14 秒**、証拠集め全体 **32 秒**、GDELT の梯子 **20 秒**。⚠ `direct:true` は
「この相手はブラウザが読んでよい」の意味で、CORS 拒否は1バイトも動かさずに落ちるので費用ゼロ。

**④ Google News を GDELT の後ろから外に出した。** 3つの取得は1本の列で await されていた——GDELT、
GDELT もう一度、そのあと Google News。GDELT を逐次にしている理由（**IP ごと**のレート制限）は
news.google.com について何も言っていない。別のホストなので**先に始めて最後に待つ**。

**⑤ 証拠集めを締切つきにし、間に合わなかったものを名指しした。** `_gatherWithin(jobs, ms)` は
**まだ飛んでいる件数**を返し、それが `missing` に 1 行として入る（この pipeline が最初から読み手に
見せてきた「取得不可」の一覧）。⚠ **黙って落とさない。**

**⑥ ターンに時計を2つ足した。** `toolTimeoutMs`（1 呼び出し）と `turnBudgetMs`（ターン全体）。
⚠ **どちらも中断ではない。** 締切を過ぎた道具は `tool_timeout` として **Atlas に機械的に報告され**、
次に何をするかは Atlas が決める。ターンの時計が尽きたら道具を呼ぶのをやめ、**持っているもので回答を
書く**。`maxSteps` も `maxToolCalls` も `maxPerStep` も**1つも下げていない**（`CONSTITUTION.md` §5・
`tests/r452 ③b` がそれを検査する）。

⚠⚠⚠ **そして、この2つの数は最初に書いたとき間違っていた。** 初版は **45 秒 / 180 秒**で、根拠は
「健全なターンはおよそ10秒」という**推定**だった。本番で測ったら、**記事を開いた状態の普通のターン
1本が 191 秒**——`ai-proxy` を **4 回**（8.1 / 51.2 / 48.9 / 17.2 秒）——で、**1 回の呼び出しの最長は
73.2 秒**。1 つの道具呼び出しはさらに長くなりうる（`analyze` は `MAX_MODEL_CALLS`＝2 回ぶんの
モデル呼び出し ＋ 32 秒の証拠集め ＋ 20 秒の地名解決＝**約 200 秒**で、しかもそれは**正常動作**）。
⇒ **初版の 2 つはどちらも、成功しかけているターンを切るところだった**——「制限を増やす方向」その
ものである。`toolTimeoutMs` = **240 秒**、`turnBudgetMs` = **600 秒**（測った最長ターンの約3倍）。
**推定で置いた数を、測った数で置き換えた。**

**⑦ Nominatim に時計を付けた。** `js/fetch-deadline.js` の `jsonWithin(url, ms, init)`。
1回 8 秒、そして**回答の地図セルフチェックが24本を逐次に叩く「パス全体」に 20 秒**——間に合わな
かった地名は、この監査が元から持っている `unplaced` のままになる。⚠ 新しい判定を作っていない。

**⑧ 停止と「次の質問」が取得に届くようにした。** ターンごとの `AbortController` は作られていて、
モデル呼び出しと executor には渡っていた。**いちばん時間のかかる証拠取得だけが、それを見ていなかった。**
だから停止は吹き出しの見た目を変えるだけで、待ちきれずに質問を送り直すことは前の試行を**置き換えず、
足していた**。

**⑨ そして本番の計測が、まだ直っていない欠陥を1つ名指した。** ⚠⚠⚠ **「もう一度訊く」は前のターンを
置き換えていなかった。** `js/atlas-console.js` の `run()` は毎ターン `_abortCtl` に新しい
`AbortController` を入れるが、**前のものを abort せずに上書きしていた**。`_runGen` は既にその
ターンの結果を**捨てる**ようにしていたので、**誰も見ない答えのための仕事が最後まで走り続けていた。**
本番実測:

- 追い越された `ai-proxy` の呼び出しが**さらに 12.6 秒**走って **200** を返した（`id 8`: 15.2 s 開始 →
  30.1 s に追い越し → 42.7 s に完了）
- 追い越されたターンが、**追い越された 3.7 秒後に新しい外部取得を発行した**（GDELT）
- 最後の送信から **280 秒後**にも `ai-proxy` が呼ばれ続けていた。⚠ **その時点で送信ボタンは idle に
  戻り `.atl-stage` は 0 個**——**画面が「終わった」と言っている間、ターンは走っていた**

⚠ **停止ボタンのほうは正しく動いていた**——押下から **約 3 ms** で 1 本を中断し、以後 1 本も出さない
（実測）。`_stopRun()` は最初から abort していたので、**欠けていたのは「待ちきれない読者が実際に取る
経路」、つまり停止ではなくもう一度訊くほうだった。**

### レンダラの応答不能については、まだ原因を名乗らない

⚠ **この症状は、計測できる形では再現しなかった。** 2回の本番計測で、`longtask > 200 ms` は送信後
**0 件**、1 秒ハートビートの最大 gap は **1,017 ms**（基準 1,010 ms）、heap は 175 → 155 MB／
110 → 104 MB と**どちらも減っていた**。未完了 fetch も単調増加せず（0→1→2→2→**3**→3→2→2→2→2→2）、
**上限 3 で頭打ちして減る**——ターン内のモデル呼び出しが直列なので、生きているターン 1 本が同時に開く
のは 1〜2 本にとどまる。⇒ **「無限に増える通信」でも「メインスレッドの閉塞」でもなかった。**

再現しなかったこと自体は「起きない」の証明ではない。ブラウザペインは `document.hidden` が最後まで
`true` で `requestAnimationFrame` がセッション通算1回しか発火せず、**描画が要る不具合はそこでは
原理的に出せない**（`memory/intmap-headless-preview-limits.md` の形）。利用者の環境は
**Windows 11 / Edge**、それ以外の条件は記録が残っていない（訊いたが覚えていないとのこと）。

**だから、この記録は原因を名乗らない。** 名乗れるのはここまで——**ターンは何十分でも続きえて、
「もう一度訊く」がそれを止めず、送り直すたびにもう1本のターンが並走し、画面が終わったと言ったあとも
モデルを呼び続けていた。** ⑥⑧⑨ がその全部を終わらせる。それが応答不能の原因だったかどうかは、
**次に同じ報告が来るかどうかでしか分からない。**

### 検査

`tests/r452-checks.test.mjs`（node・11本）。⚠ **6本は実装を走らせる**——本文が止まる `fetch` を差し込み、
`fetchViaProxy` と `jsonWithin` が本当に諦めること、返らない道具を渡された `runTurn` が本当に
先へ進むこと、注入した時計で `turnBudgetMs` の枝が本当に踏まれること、停止が本当に梯子を畳むこと。
残る4本は「消えた綴りが本当に消えたか」で、⚠ **注釈を剥がしてから読む**——今回触った全ファイルが
「以前はこうだった」を散文で書いているので、生のまま読むと**欠陥の説明文が検査を満たす**
（#R345 の形・14回目）。

⚠ `tests/r212 ⑬` の第1 assert をゆるめた。守っていた性質は「**競争する各要求が自分の時計を持つ**」で、
第3引数の綴りはその一つの持ち方でしかない。今は `Math.min(PROXY_TIMEOUT_MS, left())` ——**依然として
各自の時計であり、かつ呼び出し側の budget を超えられない**＝厳密に強い。古い綴りを固定していたら、
**保証が良くなった日に赤くなる**検査だった。
