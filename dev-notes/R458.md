## R458 — **問いが成立しない時刻があった**（重なった2つのフットプリント／直列が消していた4本）

> 「`tests/prod-smoke.spec.js:914-917` は、ある時刻には構造的に成立しない主張になっている。
> 閾値を緩めて通すのは違う。あわせて `mode:'serial'` を検討する。」

### 1. 何が起きていたか — 主張の2つの半分が、互いを否定していた

#R455 のデプロイ（run 32818517323）の Post-deploy smoke が、初回＋retry×3 の**4回とも同じ値**で落ちた。

```
expect(eyeRead.nearest.v).toBeLessThan(pic.ringFoot[0])   期待 < 15.045 / 実際 15.5
そのとき ringFoot = [15.045, 36.9]
直前の eyeRead.speedInFootprint は 通っている
```

**通っていることが証拠になる。** `speedInFootprint` は「その画素が読める表の項が、画素の下の
±1.5 px の大気が実際に取る速度と交わる」——つまり `eyeFoot[1] >= 15.5`。そして
`15.5 > 15.045 = ringFoot[0]`。**2つのフットプリントは速度の区間として重なっていた。**

重なると、③ の2つの半分は**同時には成立しえない**:

| 半分 | 要求 | 正しい描画が選べる値 |
|---|---|---|
| 眼の壁 | `ring画素 > eyeFoot[1]` | `ringFoot[0]`（= 15.045）を選べる |
| 眼 | `眼画素 < ringFoot[0]` | `eyeFoot[1]`（= 15.5）を選べる |

⚠⚠⚠ **どちらの選択も #R287 の per-pixel 判定が受理する。**
重なりの帯に載る**1つの色が、眼の合法な読みでもあり、眼の壁の合法な読みでもある**
（`tests/r458-checks.test.mjs ①` がそれを実際に `readPixel` に通して見せる）。
**だから閾値を緩めるのは間違いだった**——同じ色を許す幅まで緩めた瞬間、その assert は
「眼が見える」を一切主張していない。⚠ **緩めれば通るからといって、通ったことが意味を持つとは限らない。**

同じ本番ビルドに対して1時間後に走らせると緑（`eyeFoot [15.377,15.713]` / `ringFoot [27.180,34.003]`）。
**動いたのはコードではなく、その時刻の眼壁の幾何**（全球最大点が眼壁の内縁のどこに載るか）。

これは #R382 が同じファイルに残した「点の問いをパッチに投げている」形の**残り半分**である。
#R382 は判定を RGB 距離から風速の単位へ移したが、**比べる2点がその比較を担えるか**は問うていなかった。

### 2. 直したのは閾値ではなく「どの2点を比べるか」

- **候補を集める**（ブラウザ側・`tests/prod-smoke.spec.js`）——探索器が使ったのと**同じ ±1.5° の箱**を、
  **同じ 0.1° 格子**で歩き、**探索器自身の `0.6 × peak` の線**で「calm / strong」に割る。各点は
  「その画素」と「その画素の下の速度の区間」を持って出てくる。⚠ **新しい定数は1つも入れていない。**
  ⚠ **`gl.readPixels(` の綴りは 2 のまま**（既存の `read()` を使い回す＝`tests/r287-checks ⑦` が数えている）。
- **決めるのは node 側**（`separablePair()` in `tests/helpers/wind-ramp.js`）——探索器の2点が離れていれば
  **そのまま使う**（＝離れている時刻の挙動は1バイトも変わらない）。重なっていたら、
  **フットプリントの天井が最も低い calm 点**と**床が最も高い strong 点**を採る。
  ⚠ **順位付けの鍵は、主張自身が名指している境界そのもの。**同点は緯度→経度で決める（実行ごとに
  答えが変わると「選択が動いた」と「地図が動いた」が区別できない）。
- **それでも重なるなら、その時刻は担えないと言う**——⚠ **`test.skip` ではない。**
  重なり幅を **m/s で印字**し、report に annotation を付け、**③ だけを差し控える**。
  ①（色が包絡の中）②（速度が本当に在る）と粒子の assert は**毎時刻そのまま走る**。

### 3. 実測

本番（build 2026-08-25-R455）に対して、予報軸を 3 時間ごとに歩いて**眼を持つ 33 時刻**を測った:

| | 最小 | 中央 | 最大 |
|---|---|---|---|
| 探索器の2点の gap | **10.58** | 約 15 | 39.18 |
| 選び直した2点の gap | **22.52** | 約 28 | 41.29 |

- 33 時刻すべてで両方とも正（＝今の台風では選び直しは発火しない）が、**最悪ケースの余裕が 2 倍以上になる**。
- 候補の走査は **961 点で 429 ms**（本番実測・285 calm + 676 strong）。1 フレームの中で読み切る。
- **本番 smoke 24 本すべて緑**（2.0 分）。この時刻の判定は `as found`＝**選び直しは起きていない**。
  ⚠ 選び直しと差し控えの分岐は、**本番では呼べない**（その幾何を注文できない）ので
  `tests/r458-checks.test.mjs` が run 32818517323 の実測値で**実際に落として**確かめている。

### 4. `mode: 'serial'` を外した — 直列は「サイトが死んだとき」を守っていなかった

この1本の赤が、下の4本（`:924` 予報軸 / `:984` #R398 単位 / `:1066` #R398 等圧線 / `:1161` #R333 CORS 契約）を
**「did not run」**にしていた。**デプロイが、4つの検査を訊かないまま出荷された。**
同じ形は #R287 ⑧ が既に書いていた（1本の赤が2本目の本物の欠陥を1ラウンド隠した）。

⚠⚠⚠ **直列がその仕事をしていない理由**: 本番が落ちている場合、そもそもテストに到達しない——
`beforeAll` が goto と boot 待ちをして**throw する**ので、mode に関係なく全テストが本当の理由で赤くなる。
直列が抑えていたのは、**boot 済みのページについての独立な判定**だけだった。

4本のテスト（`beforeAll` 1つ・2本目を強制的に赤に・`retries: 3`・この config の設定）で実測:

| mode | beforeAll | 赤の前のテスト | 赤の後のテスト |
|---|---|---|---|
| `'serial'` | 4回 | **4回とも再実行** | **一度も走らない** |
| 既定 | 5回 | 再実行しない | **走る・通る** |

**既定のほうが安い**——眼のテストは 24 本中 16 番目なので、直列は retry のたびに前 15 本の
実ネットワークテストを引き連れて走り直していた。
⚠ ファイル内は**今までどおり順番に・1 worker**（`playwright.prod.config.js` に `fullyParallel` は無い）。
共有 `page` も書いた順序も変わらない。赤が出たあとは worker が入れ替わるので、残りは**新しく起動した
ページ**で走る＝以前より綺麗な状態。

### 6. 測ったが直していないこと（範囲外）

⚠ **`found.eye` は「台風の眼」ではない。** 眼の探索は `dla=-1.5, dlo=-1.5` から走査して
**最初に `0.6 × peak` を下回った点で break** するので、実測では**毎回きっかり `peak −1.5°, −1.5°`**
＝箱の南西の角（今回なら 25.5N 128.5E、峰は 27N 130E）。つまり比べているのは
「峰から約 230 km 離れた静かな点」であって、眼の中心ではない。名前と実体がずれている。
今回の選び直しは重なった時刻にはここを自動的に離れる（calm 側の天井で順位付けするため）が、
**離れていない時刻では今までどおりこの角を読む**。指示の範囲外なので変えていない。
