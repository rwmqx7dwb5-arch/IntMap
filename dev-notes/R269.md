## R269 — **「気象庁とは全く違うデタラメ」の原因は2つあり、どちらも計器が全部緑のまま起きていた**

> 全く警報レイヤーが機能していない。気象庁とは全く違うデタラメが表示される

### ① 読んでいたエンドポイントは3か月前に止まっていた

`https://www.jma.go.jp/bosai/warning/data/warning/map.json` は、

* HTTP **200** を返し、
* **正しい JSON** で、
* **期待どおりの形**（`areaTypes[].areas[].warnings[]`）で、
* **空ではない**（58官署・142の一次細分区域）。

そして中身の `reportDatetime` は**全部 2026-05-21 〜 05-28**だった。測ったのは **2026-08-19**——**83日**。
この層は 60 秒ごとにそれを読み直し、パネルに「Updated: いま」と印字しながら、**5月の注意報**を
描いていた。

⚠ **止まったフィードは、失敗したフィードではない。** 失敗なら `FEED_STATE` が 'error' になり、凡例が
そう言う。止まったフィードは HTTP も JSON も形も件数も**全部「成功」を報告する**。#R262 が
「取得の失敗を『ここには何も無い』としてキャッシュしていた」を直し、#R266 が「エンドポイントが 400 に
なっていて世界の残り全部が静かに空」を直し、#R268 が更新間隔と `cache:'no-store'` を直した——それでも
これは通り抜けた。理由は 1 つで、**このファイルは一度もフィードに「お前は今いつだと思っているのか」を
訊いていなかった**からである。

→ 気象庁自身の警報ページが読んでいるのは **`…/bosai/warning/data/r8/map.json`** で、隣に
`…/r8/map_time.json`（`latestControlDatetime`、実測で数分前）がある。形が違う：**速報の一覧**
（実測 287件・58官署）で、`warning.class10Items` / `class20Items` を持つ。

⚠ **現在の状態は「官署ごとの最新1件」であって、ファイル全体の和ではない。** 全部を足すと、後の速報が
解除した警報が復活する——「1つのファイルに複数の世代」という同じ罠の新しい場所である。実測、
最新1件だけを採ると全国の絵が正確に再現される（class10 142区域・class20 1,805区域）。落とした分は
`supersededBulletins` に数える（実測 229件）。
⚠ **そして年齢は仮定せず検査する。** 最新速報が **72時間**より古ければ `loadJMA` は **throw** する——
「発表中」として出さない。旧エンドポイントなら初日に鳴っていた計器である。

### ② 気象庁の警報コード表を、気象庁を見ずに書いていた

コード 10 以降がほぼ全部、**別の災害で、別の階級**だった。実測（そのとき実際に発表中だったコード）:

| コード | この層の表示 | 気象庁 |
|---|---|---|
| 10 | 大雨・**警報（赤）** | 大雨**注意報** |
| 13 | 大雨・**警報（赤）** | 風雪注意報 |
| 14 | **洪水・警報（赤）** | **雷注意報** |
| 15 | **暴風・警報（赤）** | **強風注意報** |
| 16 | **大雪・警報（赤）** | **波浪注意報** |
| 17 | **波浪・警報（赤）** | **融雪注意報** |
| 19 | 雷 | 高潮注意報 |
| 25 / 26 | 着雪 / 融雪 | 着氷 / 着雪 |

さらに **04・18・27 は気象庁の体系に存在しないコード**で、**09・29・39・43・48・49**（土砂災害と
レベル4の「危険警報」）が**表から抜けていた**。階級は `tierOf` が**コードの範囲**で決めていた
（`19–27 なら注意報、それ以外は警報`）ので、10 / 12 / 13 / 14 / 15 / 16 / 17 —— **全部注意報** ——が
**赤い警報として塗られていた**。書いている時点で気象庁は**日本のどこにも警報を出しておらず**、
この層は国土の大半を警報で塗っていた。これが「デタラメ」の中身である。

→ **表は書き直さず、気象庁自身の警報ページが持っているオブジェクトを読み出して置いた。**
コード → 要素 ＋ **レベル**（20 注意報 / 30 警報 / 40 危険警報 / 50 特別警報）で、階級は**レベルだけ**
から決まる（`jmaTier`）。強風/暴風・風雪/暴風雪のように**レベルで語が変わる**要素は、気象庁が変える
とおりに変える。

⚠ **指定河川洪水予報の表は入れない。** 同じページにもう1つ、`20/21/22 → 氾濫注意報`,
`30/31 → 警報`… という表がある。**20/21/22 が濃霧/乾燥/なだれと衝突する**——混ぜれば日本中の濃霧
注意報が河川の氾濫警報になる。配信ファイルも別（`bosai/flood/data/r8/…`）なので、入れない理由を
テストにも書いた。

**実測（修正後）**: 29 都道府県すべて**注意報**、内訳は 雷 819・濃霧 134・乾燥 115・波浪 54・強風 16・
大雨 3。気象庁自身の見出し文と突き合わせると、稚内地方気象台「**宗谷地方では、強風に注意して
ください。**」＝ コード 15、札幌管区「…**落雷**に注意してください。」＝ コード 14 と一致する。

### ③ 全フィードに時計を付けた

①が通り抜けた理由は「このファイルがフィードの時刻を見ていなかった」ことなので、直し方も
**JMA だけではなく全部**である。各ローダは**自分のペイロードの中で一番新しい時刻**を `seenAt()` に
記録し、パネルが機関ごとにその年齢を印字する。

実測（同一時刻）: JMA **29分** · NWS 16分 · ECCC 40分 · CMA 8分 · BoM 2.4h · INMET 33.5h ·
HKO 19.3h · GDACS 9.1h。

⚠ **閾値は「最近か」ではない。** 33.5 時間前に発表された多日間の警報は**現行**であって古びていない
——「最近でなければ黄色」にすると生きているフィードで狼を叫ぶ。国の気象機関が**まる1週間何も出さ
ない**ことは無いので、そこに置いた。年齢そのものは常に印字される。

⚠ **CMA だけ時計が付かなかった。** `2026/08/19 17:22` はスラッシュ・秒なし・タイムゾーンなしで、
`Date.parse` は **NaN** を返す——**この計器が存在する理由そのものの国が、計器から見えていなかった。**
しかも最初の直しに `/\x2f/g` を使ったら、**このリポジトリのコメント除去計器が `//` と読んで行を切り
落とした**（[[intmap-recurring-lessons]]「自分の検査が自分のコメントに当たる」の11回目）。
→ 正規表現ではなく `split('/').join('-')`。**パターンを賢くせず、入力を変える。**

### R269 追記 — 本番検証で2件、どちらもこの回の計器が自分で捕まえた

**⑴ MeteoAlarm の「新しさ」が −82.9 時間だった。** リレーの要約が持っているのは `onset` と `expires`
——**有効期間**であって、発表中の警報は普通**明日切れる**。未来の時刻を「一番新しい」として採れば、
フィードは常に「たった今より新しい」ことになる。**有効期間は発表時刻ではない。**
→ `seenAt` は**未来の時刻を拒否**する（一般の防護）。そのうえで MeteoAlarm は、リレーが**実際に
MeteoAlarm を読んだ時刻** `fetchedAt` を使う——リレーが保証できる唯一の時刻がそれだから。

**⑵ 中国 CMA が本番で「取得不可」。** 実測: リレーは **20,140 ms** で `502 upstream unreachable` を
返し、**同じ URL を手元から叩くと 1.0 秒で 300 件**返った。`www.nmc.cn` はエッジのリージョンからは
届くが、常に速くはない。**上流の悪い日より短い制限時間は、生きているフィードをランダムに
「取得不可」にする。** → 45 秒 ＋ **1回リトライ**。60 秒のエッジキャッシュがあるので、読者が何人いても
上流への要求は毎分1回のままである。

⚠ **そして、投げっぱなしのローダには自前の in-flight ガードが要る。** `refresh()` の `busy` は
`Promise.all` する側しか守っていない。CMA と MeteoAlarm は着地を待たずに投げるので、実測 90 秒
かかった呼び出しに 60 秒タイマが2本目・3本目を重ねていた——**答えていないホストに向かって**。
1つずつ。
