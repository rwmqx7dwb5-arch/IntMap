〈依頼〉 2026-11-18〜19 に `supabase-deploy.yml` の push run が誤判定で止まり続け、手で配備して埋めた。誤判定そのものを直す。

## 0. 測った・確かめた
- 赤の run は 3 本: 44325999621（f20ec5e8）・44340692025（734d2299）・44347983183（7a3dc295）。いずれも「db push would NOT apply 20261118090000 … although this push added them」で止まり、22 関数も出なかった。
- 3 本とも起点に **65aad08b（run 44250850150）** を選んでいた。その間に緑の push run **44283726249（550726ac・#1205）** があり、それが 20261118090000 を適用していた。だから差分に 090000 が「足された」と出て、dry-run は（本番に記録済みなので）流さず、不一致と判定された。
- 見立て「夜間の schedule run が起点を狂わせた」は**否定**: 起点の問い合わせは元から `--event push --status success` だけを読む。11-17 にも schedule run（44096277131）が挟まったが、次の push run は正しく直前の緑を選んでいる。さかのぼって 8 本の push run の起点を読むと、外れたのはこの 3 本だけ。
- 同じ問い合わせを 11-19 に手元で走らせると 44283726249 が先頭に出て、起点は正しく 550726ac になる（`--plan` で確認）。つまり**その時の CI の一覧から 44283726249 が欠けていた**。なぜ欠けたかは後から取れない（run は読んだ一覧を記録していなかった）——未解明として残す。
- 本番の履歴（`supabase migration list --linked`）は 62 本が local と一致し、最後は 20261118120000。**#1193 の 20261118130000 は main にあるが本番に無い**（44347983183 が止まったため）。

## 1. 直したもの
- `migrationMismatch(pending, added, remoteApplied)`: 「足されたのに dry-run が流さない」を本番の履歴で分ける。**記録済み → 適用済み（拒まない）**／**未記録 → remote head より前の時刻で永遠に流れない（拒む）**／**履歴が読めない → 拒む**（測れなかったを適用済みにしない）。逆向き（足していないものまで流れる＝baseline の再実行）は従来どおり拒む。
- 起点が古いのは安全側（関数を余分に出すだけ）で、migration についても足されるのは適用済みのものだけになった——**どの緑を起点に選んでも赤にならない**。一覧が欠けた原因を突き止めなくても判定が正しくなる。
- 起点の説明に「読んだ緑の push run の数と新しい 3 本」を印字する。次に起点が外れたら、一覧に何が載っていたかがログに残る。
- `supabase-deploy.yml` の push の paths に `scripts/supabase-deploy.mjs` と workflow 自身を足した。赤い配備の差分は次の緑が拾う設計だが、配備器の修正はこの 2 ファイルしか触らないので、無ければ merge しても配備が走らず 130000 が残ったままになる。
- 検査 `tests/deploy-applied-migrations-checks.test.mjs`: 当日の dry-run 出力と version で ⑴⑵・読めない場合・逆向きを評価する。
- 文書: `docs/RELEASE.md`（正本）・`docs/architecture/15-ops-quality.md`・`docs/AGENT-SETUP.md` §9・`docs/FILES.md`。
