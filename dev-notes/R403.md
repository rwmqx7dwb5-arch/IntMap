## R403 — **番人は「全現行文書」を見ていたが、セッションが行動する前に読む文書はそこに無かった**

依頼は1行で言える。`.claude/skills/intmap-round/SKILL.md` §6 が deployment の手順として
「Edge Function を変えたなら本番へ出す（**9 本**: …）」と書き、9つの名前を並べている。実体は
**12本**（`ls supabase/functions/` と `supabase/config.toml` の `[functions.*]` が完全一致）。
欠けているのは `aviation-feed` / `routing-relay` / `volcano-feed`。

古いのは3ラウンド前からではない。**#R399 がまさにこの事実を全文書で監査し、`scripts/doc-facts.mjs`
の規則を作り直した、その次のラウンドから**である。#R399 の記録はこう締めている——「走査する文書名が
手書きの2件だった」「発火しない検査は通った検査と見分けがつかない」。

その監査がこのファイルを捕まえられなかった理由は、**このファイルが読まれていなかったから**だ。

### 1. 「全現行文書」は全現行文書ではなかった

`scripts/doc-facts.mjs` の走査集合はリポジトリ直下の `*.md` と `docs/*.md` だった。`.claude/` の
8文書——常設規則2本・ラウンド手順1本・subagent 定義5本——は**一度も開かれていない**。

これは軽い抜けではない。**それらは、セッションが行動する**前**に読む文書である。** 散文の文書が
古いと読者は誤解する。手順書が古いと、セッションは**そのとおりに実行する**。9つの名前は deploy の
指示であり、従えば3本の Edge Function を黙って飛ばす。

⇒ 走査を `.claude/` へ広げた（25文書 → **33文書**）。

⚠ **別のチェックアウトは、このチェックアウトの文書ではない。** ハーネスは `.claude/worktrees/` の
下に repository 全体の写しを作る（#R282 実測: 2本・11,615ファイル）。そこへ降りると、**別のコミットに
載った文書を「この木の文書」として読む**。止める目印は**フォルダ名ではなく `.git` の有無**にした
——チェックアウトをチェックアウトたらしめているものであって、誰かが思いついた名前ではない。

### 2. 走査を広げても捕まらなかった。そして報告は緑のままそう言った

**これが本題である。** `.claude/` を走査に入れ、誤った「9 本」をそのまま残して `check:docs` を
走らせた。**緑だった。**

数の規則（`edge-count`）は**名詞に直結した数**しか読まない——「Edge Functions **は** 12 本」の形。
手順書はこう書いていた:

```
Edge Function を変えたなら本番へ出す（9 本: ai-proxy / …）
```

名詞と数のあいだに述語が丸ごと入っている。#R399 が塞いだ3つの沈黙（手書きの一覧・リテラルの
アスタリスク・`.match()` の最初の1件）に続く**4つ目**で、しかも同じ形をしている——**規則は落ちて
いない。見ていない。**

⇒ **数ではなく一覧を読む規則 `edge-roster` を足した。** 在庫は言い回しに依存しない。実名が並んで
いれば、それは「これらが Edge Function である」という主張である。

### 3. 「3本以上の実名が並んでいたら在庫」では、正しい文を3つ落とす

素朴な規則を書く前に、**木にある実名の並びを全部数えた**。5件あり、うち**3件は正しく部分的**だった:

| 文書 | 並び | 正しいか |
|---|---|---|
| `Architecture.md` | 「**5本の無認証中継**（`alerts-relay` / `cable-geo` / …）」 | ✓ 無認証中継について完全 |
| `Architecture.md` | `for f in refresh-news monitor-run sv-cov …` | ✓ deploy ループ。2つに割れている |
| `docs/SECURITY-ARCHITECTURE.md` | "All twelve are declared there now (`aviation-feed` #R341, …)" | ✓ **最近足した4本**を挙げている |
| `CLAUDE.md` | 「**Edge Functions は 12 本**（`ai-proxy` / …）」 | ← 本物の在庫 |
| `SKILL.md` | 「…本番へ出す（9 本: `ai-proxy` / …）」 | ← 欠陥 |

**3/5 が誤検知になる。** そして正しい文の上で赤を出す規則は、次のラウンドで緩められる。

本物の2件が持っていて、部分的な3件が持っていないものは**名詞**だった——**`Edge Function` という語が
その一覧を導入している**こと。先行窓を **40 / 60 / 90 文字**で測ると、**どれでも同じ2件と同じ3件に
割れる**。閾値を合わせ込んだのではなく、判別子である。`など` / `ほか` / `etc.` と自分で断っている

### 5. `npm test` は11門、CI は6門だった

`scripts/test-parallel.mjs` の source 半分は11の門を回す。`ci.yml` はそのうち6つしか回していない。
**`check:docs` はその回されていない5つの中にあった**——つまり、この回が直している当の門は、

厳密に言えば無防備ではない。`tests/r399-checks` と `tests/r403-checks` が `doc-facts` を子プロセスで

⇒ 5件を `ci.yml` の static job へ足した。足す前に実測: **5件とも緑・ネットワークに出ない・`dist/` を

文書の失敗はバンドルを待たない）。`arch-files-check` だけ npm 別名が無かったので `check:archfiles` を
足した。

⇒ 規則 `ci-gates` が以後の乖離を落とす。⚠ **比較は npm 別名ではなくスクリプトファイルで行う**
——`ci.yml` は `npm run check:docs`、`test-parallel.mjs` は `node scripts/doc-facts.mjs --check` と

⚠ 逆向き（`check:perf` / `check:assets`）は**意図的**で、build が要るので CI だけが回す。

`check:docs` が赤」で落ちた。**環境要因の赤は本物の退行と見分けがつかない。**

⚠⚠⚠ **そして、素直に test を丸ごと錠で囲んだら `npm test` が別の形で落ちた。**
`tests/r274 ③` が **180 秒待って諦めた**（`gate-lock: waited 180000ms`）。この回の検査は
test 単位で囲むと ① だけで **82 秒**・1ファイル合計 **264 秒**を保持する。

⚠ **これは遅いという話では済まない。** `tests/helpers/gate-lock.mjs` は
「保持は数百ミリ秒」を前提に書かれており、**`STALE_MS = 120_000` を超えて保持されている錠は
死んだプロセスのものとみなして他の待ち手が壊す**。つまり長く持つほど、**錠が防いでいるはずの
「同時に2人が書く」に自分から近づく**——しかもそのときの壊れ方は、赤の原因が自分の変更に
見える形をしている。

⇒ **`breaking()` 自身が錠を取る**形にし、保持を1回の変異（数秒）に縮めた。
4ファイル（r403 / r274 / r280 / r399）だけを同時に走らせると **31/31 緑**。

⚠⚠⚠ **ところが `npm test` 全体では、今度は 12 件が同じ timeout で落ちた。** 待ちの上限 180 秒は
**2ファイルが数回ずつ取っていた頃の数字**で、今は4ファイルが各テストで数回ずつ取る。しかも
`npm test` は 200 本超を並列に走らせるので、単独なら約 6 秒のゲート実行がその数倍かかる。
⇒ 上限を 900 秒へ。これは**性能の予算ではなく**「suite が本当に詰まった」と判定する最後の砦で、
他の保持者が正当に要求しうる合計を超えていなければならない。
併せて**復元の確認をゲート実行からバイト比較へ**——「復元された」が何を意味するかを**そのファイル
のそのバイト列**として言うほうが、「どの規則も気づかなかった」より**強く、かつ錠の中でのゲート
実行1回分だけ安い**。この検査だけで4回分減った。

⚠⚠⚠ **それでも 8 件落ちた。そしてそこに、錠そのものの欠陥が2つ在った。**
どちらも前からあり、**保持が「少数回・長時間」のうちは到達できなかった**だけだった。

- ⚠⚠⚠ **生存判定は時計ではなく pid でなければならない。** 錠は「mtime が古ければ死んだ保持者の
  ものとみなして壊す」形だった。**負荷の下では正当な保持者が簡単にその閾値を超える**——実測
  `tests/r399 ①` は **208 秒**保持した——そして待ち手は**生きている保持者の錠を消して同じファイルを
  書き始める**。これは錠が防ぐはずだった「同時に2人が書く」そのもので、しかも現れ方は
  **運の悪いファイルの「the restore left the tree failing」**＝本物の退行と見分けがつかない。
  ⚠ **heartbeat では直らない**——callback は `execFileSync` でゲートを回すので**保持中ずっと
  イベントループが止まっており、タイマーは1つも発火しない**。OS に「その pid はまだ居るか」と
  訊けば、どちらの問題も無い。生きている錠は決して壊されない。
- ⚠⚠⚠ **Windows では取得の競合が `EEXIST` ではなく `EPERM` を返す。** 他プロセスが同じ
  ディレクトリを削除している最中の `mkdir` は pending-delete 状態に当たる。旧コードは
  **`EEXIST` 以外を再 throw** していたので、ごく普通の競合が**テストを即死させていた**
  ——実測、**7 件がミリ秒で `EPERM … mkdir`**。**錠が取れなかったことは錠が取れなかったこと**
  であって、プラットフォームがどの errno を選ぶかとは関係が無い。

⇒ `mkdir` の失敗は `EEXIST` / `EPERM` / `EACCES` のいずれでも「まだ自分のものではない」として
待ち、保持者は自分の pid を錠の中に書き、待ち手は**その pid が実際に消えているときだけ**回収する。
⚠ **claim できなかった錠は返す**——`writeFileSync(pid)` を best-effort にすると「所有者の記録が
無い錠を保持したまま作業する」状態になり、それは `abandoned()` が回収する当のものである。

### 13. **錠はチェックアウトごとに1つでなければならなかった**——`node_modules` は junction である

それでも赤が消えず、12 → 8 → 4 → 0 → 8 → 10 と**同じ木で結果が動いた**。0 が出た回もあるので
「直った」と言えてしまう場面があった。⚠ **1回の緑は、点滅している赤の反証にならない。**

原因を機械に訊いた（`Get-CimInstance Win32_Process`）。**別の Claude セッションが3つ、同時に
それぞれの worktree でテスト一式を回していた**（`wt-r401` / `wt-r406` / `wt-r409`）。そして錠の
置き場は `<checkout>/node_modules/.intmap-tree-lock` ——**`node_modules` は
`scripts/worktree.mjs` が原本へ張る junction** なので、**このマシンの全チェックアウトが
1つの錠を共有していた**。

⚠⚠⚠ **これは「無関係な suite が順番待ちする」という遅さの話では済まない。** 他の worktree の
待ち手は**そのブランチにある版の** `gate-lock.mjs` で動いており、時計式の生存判定を持っている。
つまり**別のチェックアウトで生きているプロセスが保持している錠を、古い版の待ち手が「死んでいる」
と判断して消す**。保持者はそれを知らない。すると**保持者と同じ worktree の次の取得者がそのまま
入ってきて、2つのプロセスが同じ木を書く**。実測された現れ方は、`Architecture.md` に別のテストの
探針（CSP の文）が載ったまま `check:docs` が赤くなること——**どのテストがそれを見るかは運**で、
見たテストの退行のように読める。

⇒ 錠を **`os.tmpdir()` の下、チェックアウトの絶対パスのハッシュで名付けた場所**へ移した。
`tests/helpers/session-seed.js` が dev サーバのポートについて出している答えと同じで、理由も同じ
——**チェックアウトに固有のものは、そのチェックアウトで名指す。**

⚠ **そして、この環境では「ローカルの `npm test` 全体」は信頼できる計器ではない。** 3セッションが
CPU を奪い合っている最中の測定は、自分の変更ではなく機械の状態を測っている（実測: 同じ木で
`tests/r274 ③` が 21 秒から 380 秒まで振れた）。**4ファイルだけを同時に回すと 31/31 緑**で、
これはこの回が触った範囲についての決定的な測定である。全体の門は**隔離された CI** に測らせる。

⚠ **そして、走っている変異テストを外から kill してはならない。** 途中で殺すと `finally` の復元が
走らず、**木が壊れたまま残る**（実測: `tests/r280 ②` の CSP 変異が Architecture.md に残り、
`check:docs` が `csp` で赤になった。commit 済みだったので `git checkout HEAD -- Architecture.md`
で戻せたが、未コミットなら失っていた）。
