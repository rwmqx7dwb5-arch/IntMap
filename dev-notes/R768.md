## R768 — 「動かなかった」と「動いたかを見られなかった」が同じ答えだった

〈本番実測 2026-09-16、ログイン済み。#R740 がカメラの判定を「動いたか」から「求めた視界にあるか」へ
直した続きで、今回はその**手前**——カメラが動かなかった理由のほうを区別していなかった。〉

### 1. 実測

同じモデル（gpt-5.6-luna）に、同じ問い「アイスランドに飛んで」を 2 回。違いはタブが前面か背面かだけ。

| | モデル呼び出し | 操作の結果 | 終了理由 |
|---|---|---|---|
| タブが背面 | 9 回 | 8 件中 **7 件が `partial / no_change`** | `step_budget` |
| タブが前面 | **1 回** | 1 件 `completed / ok` | `answered` |

背面のターンで読者が受け取ったのは「このターンは作業の上限に達したため…」という文である。**上限には
達したが、上限が原因ではない。**

### 2. 根

合成されていないページは `requestAnimationFrame` を 1 回も回さない（[[intmap-raf-zero-is-not-a-product-defect]]
が #R747 で測っている）。フレームが無ければ `flyTo` は本当にカメラをその場に残すので、`view.flyTo` の
検証器は `no_change` を返した——それは**依頼が効かなかった**ことの符号である。Atlas は正しく再試行し、
8 手を使い切った。⚠ **欠陥は Atlas の判断ではなく、Atlas に渡された文にある。**

`.agents/rules/one-pass-or-a-reason.md` §2 が挙げる 3 つの原因のうち 1 番（観測器が嘘をついた）。

### 3. 直し方（縛らない側）

⚠⚠⚠ **利用者の指示は 2 段階だった。** 「一発で全部決めるようにするのを恒久方針に。失敗したら
フォールバックするのはいいけど、数回やるのが当たり前は怖すぎ」——そのあとに追補で「AI モデルが決定権を
もっていて、なにをやるか決めるというのはそれでいい。コード側で変に縛ったりするのは嫌。ハーネスとして、
性能向上につながるならいいけど、縛るのはやめてほしい」。**`CONSTITUTION.md` §5 と同じ線**（上限は
暴走を止める最後の柵であって予算配分の道具ではない）。

⇒ **呼び出しは 1 件も拒まない。手数の上限は 1 も動かさない。**（`tests/r452-checks.test.mjs:134` が
`maxSteps===8` を固定しており、今回それは無傷。）変えたのは**渡す文**だけ。

- `js/geo-engine.js` の `render` に **`onNextFrame(ms, fn)` / `ticking(ms)`** を置いた。両アダプタとも
  `render` を発火する（Cesium は `scene.postRender`＝`js/cesium-engine.js:1759`）。
- `js/atlas-view-capture.js` は**自分で書いていた同じ待ちを捨てて**これを呼ぶ。⚠ コールバック形で
  なければならない——`preserveDrawingBuffer:false` の WebGL バッファはその刻みの中でしか読めず、
  解決した promise のあとで取ると黒い矩形になる（同ファイルが 628/628 画素で測っている）。
- `js/atlas-capabilities.js` の**カメラ観測器**が AFTER の標本の隣でそれを測り、**判定は同期のまま**
  その読みを読む。動きが無く描画も回っていなければ **`partial / not_rendering`**。読者向けの文は
  「地図が描画されていませんでした——IntMap が背面にあるため…前面にして、もう一度お尋ねください」。

⚠ **この問いは主張を弱めることしかできない。** 答えられないエンジン・例外（`null`）は `no_change` の
ままで、**測れなかった問いを根拠に失敗へ格下げしない**（#R740 の「判定は格上げにしかならない」の裏側）。

⚠⚠⚠ **最初の版は判定のほうを `async` にして、契約を壊していた。** `js/atlas-capabilities.js` の
カメラ検証器は `view.flyTo` 専用ではなく **bearing / pitch / resetNorth と共有**なので、1 つの
`async` が**カメラの全能力の契約**を変え、同期で呼んでいた `tests/r740-isochrone-verdict-checks.test.mjs`
が 12 件落ちた。**検査のほうが正しい。** 置換スクリプトで 33 か所を `await` に書き換えようとして
`CAPS.resolve('view.resetNorth').verify(…)` を壊し（[[intmap-shell-budget-has-one-line]] の
「置換後は必ず差分を見る」）、巻き戻して**設計を直した**——「このページは合成されているか」は*見る*こと
であって決めることではないので、属するのは観測器のほうだった。⚠ ただし**観測の標本には入れない**
（`changed()` は標本全体の JSON 比較なので、before/after で反転すると「カメラが動いた」と読める）
⇒ 観測器が書き判定が読む 1 スロット。カメラ操作は `writes` の競合キーで直列化されるので 1 つで足りる。

⚠ **天井が 2 つ、余白ゼロで待っていた。** app shell は `origin/main` が **8,049/8,050**（[[intmap-shell-budget-has-one-line]]）
＝**1 行も入らない**ので、facade の 2 メソッドは**既存の行へ畳んだ**（散文はここと非 shell 側へ）。
`.agents/rules/` の各ファイルにも **6,144 バイト**の天井があり、**この回が足した規則ファイル自身**が
6,968 バイトで落ちた——毎セッション全員が読むので正しい制約。規範だけ残し、実測はこの記録へ寄せた。

### 4. 門

`npm run check:atlasrepeat`（`scripts/atlas-repeat.mjs`・`npm test` に内包）。3 点だけ測る——
⑴ 刻みを訊ける場所がエンジンに 1 つあるか ⑵ Atlas の観測器（50 モジュール）が 2 つ目を書いていないか
⑶ **出荷される検証器を評価**して、非合成ページを「失敗した移動」と呼ばないか。

⚠⚠⚠ **手数は数えない。** 「そのターンは何回呼んだか」で落とす門は、方針 §3 が禁じた上限を
テストの形で作ることになる——Atlas が続けて正しかったターンを落とし、5 回ではなく 2 回嘘をつかれた
ターンを通す。

### 5. ⚠⚠⚠ 測定環境を製品の欠陥として報告していた（このセッションで 2 度目）

同じ日の別の計測（Luna / Sol / Terra の比較）で「Sol が同じハイライトを 6 回」「Sol と Luna が同じ場所へ
2 回飛んだ」と報告したが、**3 タブを背面で回していた**ので同じ汚染を受けている。モデルの性質として
報告したのは誤りで、利用者に訂正した。[[intmap-raf-zero-is-not-a-product-defect]] はそれを warning として
持っており、セッション開始時に読んでいた。**読んでいる警告と、踏まない警告は別である。**
