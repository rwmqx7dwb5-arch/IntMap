## R265 — **地形データの穴が「地面」として使われていた／水が時間をかけて進むようになった／表示範囲内の集計は不要**

> 「データセンター、AIインフラレイヤーに表示範囲内のものを表示する機能はいらない。
>   地形編集・水流でたまに、直線で地形を完全無視するクソ区間がある。経過時間に対する水の動きが、
>   現実と乖離しすぎ。リアルなモデルにしろ。」

### 1 · ⚠⚠⚠ 5回目にして、歩き方ではなく**地面**を見た

「直線で地形を完全無視するクソ区間」は #R258・#R261・#R264 と3ラウンド直してきた。3つとも本物の修正で、
3つとも今も生きている。**4回目までは全部「歩き方」を見ていた。** 今回まず測ったのは地面のほうで、
バケットから直接タイルを取ると:

```
https://…/terrarium/14/9101/5896.png   256×256・読み込み成功・α=255・
                                        65,536 画素すべて RGB(0,0,0)
```

terrarium の符号化は `R·256 + G + B/256 − 32768` なので、これは **−32,768 m** と復号される。
**同じ地点は1段下（z12）では 85.61 m** と正しく読める。

| 場所 | z14 タイル 49枚のうち「全面 0,0,0」 |
|---|---|
| サヴァ川氾濫原（20.0/44.93） | **14 枚** |
| 琵琶湖 / デスバレー / 西シベリア / 東京湾 / レマン湖 | 各 **0 枚** |

これが「**たまに**」の正体だった。作業グリッドで測ると **7,680 標本中 2,240（29.2%）が −32,768 m**、
それでいて `demMissing` は **0**——数値が返ってきているのだから「欠損」ではない。

**なぜそれが直線になるか。** 1.7 km 角の −32.8 km は、優先度フラッドには**底なしの穴**であり、
横断の精細化（`refineCrossing`）にとっては `max(0, e − lo)` が全域 0、すなわち**通り抜けが無料**の
領域である。最小費用経路は穴へ飛び込み、穴の中では**距離しか費用が無い**ので**まっすぐ**走る。
琵琶湖の最大窪地が溢流位 81 m に対して `level: −7,800.7 m` を報告していたのも同じ原因で、
void 1隅と実測3隅の**バイリニア混合**である。

**直し（`js/map-readout.js`、根本原因の層）**

1. 復号に**物理的な下限**を置く。チャレンジャー海淵は −10,935 m、符号化の最小は −32,768 m なので、
   **−12,000 m** はその間の唯一まともな線引きである（`tests/r265 ①` は**定数ではなく関係**を検査する）。
   下限を割る値と α=0 の画素は **NaN**。
2. **穴は終わりではない。** `demElevAt` は**ピラミッドを1段ずつ降りて**親タイルで答える（上限4段・z6 まで）。
   穴のあるタイルが復号された瞬間に**その親を要求する**ので、フォールバックには読むものがある。
3. `demElevBilinear` と `demSnapshot` の行サンプラは、**穴でない隅だけで重みを正規化**する
   （穴が無いときの式は**1文字も変えていない**——地震・津波の場は同じサンプラを通る）。
4. どの段でも答えられなかった標本は数え、`demVoidStats()` から読める（#R185: 黙って諦めない）。

**実測（同じ矩形・同じ z14）: −100 m 未満 2,240 → 0、最低標高 68 m。**

⚠ 効く先は水だけではない——座標表示・断面図・可視領域・日射・地震の地盤増幅・津波が**同じ復号**を通る。
⚠ 3D の terrain タイルも同じ穴を踏むので、ツールが開いている間の `imapterr://` は**そのタイル自身の
中央値で穴を埋め、全滅タイルは拒否**する（MapLibre が親へ落ちる）。**アプリ全体の terrain ソース
（`js/dem-source.js`）は今回の依頼の範囲外なので、直さずにここに書く。**

### 2 · ⚠⚠⚠ 時計が意味を持つようになった

パネルは自分で「**波の到達速度は扱いません**」と書いていた。そのとおりで、注水のティックは
**累積した総量を定常状態へ解き直す**だけだったので、水は **t = 0⁺ で最終地点に居た**。
経過時間の表示は、何も使っていない量のラベルだった。

**`js/water-dynamics.js`（新設）** — 2次元浅水方程式の**局所慣性形**:

- Bates, Horritt & Fewtrell (2010), *A simple inertial formulation of the shallow water equations for
  efficient two-dimensional flood inundation modelling*, J. Hydrology **387**(1–2) 33–45（LISFLOOD-FP の定式化）
- **q 中心化**による安定化: de Almeida, Bates, Freer & Souvignet (2012), WRR **48**, W05528（θ = 0.7）
- 摩擦は**マニング n = 0.035**（Chow, *Open-Channel Hydraulics* 1959, 表5-6 の自然河道・氾濫原の中央値）
- Δt は CFL `α·Δx/√(g·h)`、α = 0.7（Bates 2010 §2.3）
- 境界は**壁ではなく落ち口**。ただし**外向きに地面が下がっている辺だけ**——最初の版は `|dz|/2Δx` で
  向きを見ておらず、**上流側の辺からも水が抜けて**一様斜面の定常水深が 0.046 m（等流水深 1.611 m）になった。

**検証（Node・`tests/r265-checks`、すべて閉じた形の答えに対して）**

| 検査 | 結果 |
|---|---|
| 一様斜面の定常水深 vs マニング等流水深（S₀ = 0.0005 / 0.001 / 0.005 / 0.02） | **比 1.0000**（プロファイルは min=max で一様） |
| 静水（凹地の湖・400 ステップ） | **max\|q\| = 厳密に 0**・体積不変・流出 0 |
| 質量保存（起伏地に 5×10⁶ m³・2時間） | **相対誤差 5×10⁻¹⁰** |
| 洪水波の到達（14.9 km・S₀=0.002・q=3 m²/s） | **2.26 時間・平均 1.84 m/s**（等流流速 1.80、運動学的波速 3.00 の間） |

⚠ **「漏れ 0.33%」は計器のほうだった**——`storedM3` は**描かれる量**（深さ 2 cm 以上）であって
保存量ではない。薄膜を数えていなかっただけで、`totalM3` で測れば 5×10⁻¹⁰ である。

**実測（本番ビルド・甲府盆地に 5×10⁶ m³ を1回配置、`advance()` で時計を進める）**

| 経過（模擬） | 先端の到達距離 | 最大水深 |
|---|---|---|
| 0 | （置いた池: 18.6 m） | 18.57 m |
| 60 秒 | 2,276 m | 7.99 m |
| 10 分 | 2,810 m | 8.36 m |
| 50 分 | 3,526 m | 8.84 m |
| **1.8 時間** | **3,914 m** | 8.49 m |
| ⏭ **定常状態（t → ∞）** | **5,979 m** | 10.69 m |

**従来モデルはこの 5,979 m を t = 0⁺ で描いていた。**

- **▶ は「進めるものがあるか」で決まる。** 定常ソルバでは置いた水に何もすることが無かったので蛇口が
  無いと無効だったが、動く水にはやることがある。1回きりの水量を置くと時計が動き出す。
- **⏭「定常状態まで」** は従来の答え（優先度フラッド＋MFD＋カスケード窪地）をそのまま `sim.h` に入れる。
  何も失われていない——**それが t → ∞ の極限**である。
- ⚠ **時計は1つ。** 最初の版は要求した秒数で時計を進め、モデルは刻み予算の中でしか進まなかったので、
  フッタが「経過 2.0 時間」・詳細が「Flow: 経過 35分」と**同じ実行に2つの時刻**を出した（実測）。
  いまは**先にモデルを進め、実際に積分できた秒数で**時計も蛇口も進める。刻み上限に当たったティックは
  数えて印字する。
- ⚠ **`clearWater()` が浅水の状態を消していなかった**（実測: 5 Mm³ を2回置くと「湛水 14.48 Mm³」）。
- **水は1回だけ届く。** `x.m3` は蛇口が太らせ続ける累計で、ルーティングはそれを毎回読み直すので、
  毎ティック総量を注ぐと**ティック数だけ水が増える**。各水源は `_fed`（すでに入れた量）を持つ。
- **1点に注いだ水は柱ではなく池。** 72 m セルに 10⁶ m³ は 193 m の水柱で、正しい初期条件ではあるが
  絵としては馬鹿げている。種セルから**最も低い隣を取り続ける体積制限フラッドフィル**で水平面を作る
  （窪地なら池、斜面なら下向きの薄い舌＝バケツをひっくり返した形）。自由度ゼロ。
  ⚠ 最初の版は**水位が下がるのを許して**いたので、10,000 m³ のバケツが **154,901 m³** を置いた
  （フロンティアが池より低い地面に出たときに差を引いていた）。水位は優先度フラッドの `filled` と同じく
  **単調増加**で、最終水位は標高順の累積和で厳密に解く。実測 誤差 **0.000%**。

### 3 · 下流トレースにも到達時刻

断面は #R188/#R189 以来 `A ∝ 1/√S`、すなわち `v = K·√S`（K = 40）という**出典の無い** Chézy 型の
係数で決めていた。グリッドがマニングで走るようになった以上、**1つのツールに摩擦則が2つある**のは
#R255 が消したはずの欠陥である。断面は**マニングの等流水深**で「その流量を流せる水位」を解く:

```
Q(h) = A(h) · (A(h)/W(h))^(2/3) · √S / n        （h について単調 → 同じ二分探索）
```

流量が指定されていなければ、**継続水源の流量の合計**（それ自体が m³/s である）、それも無ければ
#R188 の規則どおり「配置した水量を経路に沿って敷き詰める」——ただし今度は**係数ではなく Q** を
二分探索する（`∫A ds` は Q について単調増加）。到達時刻は**運動学的波速 c = (5/3)v**
（Lighthill & Whitham 1955）で積分する。パネルは**使った流量とその出所**を必ず併記する。

⚠ **速度は Q/A ではなくマニングから読む**。解いた水位では同じ数だが、Q/A は谷が流しきれない断面で
0 に近い面積で割る——実測、琵琶湖の1断面で **57 m/s** になった。あれは水ではない。

### 4 · データセンター・AIインフラ層の「表示範囲内」集計を削除

#R261 が足し、#R264 が浮遊ウィンドウから凡例へ移した集計（件数の収録/OSM 内訳・公表容量とその分母・
分類別の内訳・容量順の上位）を、**隠さずに削除**した。`moveend` の再描画も、`stats()` の窓口も落ちている。

⚠ **他は何も減っていない。** 詳細カード（指の下の点についての答え＝浮くべきもの）、色キー、
**#R258 の分類フィルタ**（凡例の行がそのままスイッチで、1つの式が1つのレイヤーに掛かる）、
そして表示範囲の OpenStreetMap 取得（これはレイヤーがデータを得る手段であって、ビューについての読み物ではない）
はそのままである。

⚠ **前ラウンドのテスト2件が、今回の正当な変更を退行に見せた**（4ラウンド連続）。
`tests/r261 ⑫` は `dcStats` / `dcRender` / `stats:` を、`tests/r264 ③` は `mountSummary` / `.dc-krow` を
——つまり**機構**を固定していた。消さずに**性質**へ書き換えてある（⑫＝「1つの式でフィルタできること」、
③＝「浮くのは点についてのカードだけであること」）。

### 5 · 残っている問題

- **琵琶湖を横切る直線は残っている**（実測 12,773 m・387脚・**起伏 1.1 m・落差 0.0 m**、脚は 33 m ＝
  最細標本 23 m の 1.4 セルで、**すべて実測の DEM 読み**）。ここには void は無く（z14 タイル 49枚中 0枚）、
  **平らな水面上では最小上昇経路は定義上まっすぐ**である。これは今回の void とは別の主題で、
  「湖を渡る区間を水域として描くか」は依頼の範囲を超えるので**直さずに記録する**。
- **`js/dem-source.js`（アプリ全体の 3D terrain / 陰影起伏）は同じ void タイルを MapLibre へ直接渡す。**
  今回はサンプラ側と、ツールが開いている間の `imapterr://` だけを直した。
