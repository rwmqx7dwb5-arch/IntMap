## R465 — **10分間、戻ってきた読者は「もう存在しないファイルを名指す文書」を自分のキャッシュから受け取っていた**

#R452 の production verification 中に観測した別件。deploy 直後の1回目のロードが**前のラウンドの `index.html`** を
返し、そこに書かれた `assets/main-HWuheMpu.js` が **404**、`window.IntMapConsole` も `window.IntMapAtlasAgent` も
**undefined**——**本体 bundle が1バイトも load されていない**。Service Worker を unregister して Cache Storage を
消すと直ったので worker が疑われたが、そうではない。

### ① 直せる場所は3つあり、2つは使えないことが実測で分かった

**ヘッダ**：本番の全応答を測ると、GitHub Pages は `Cache-Control` を**返す先で区別していない**。

```
index.html                   Cache-Control: max-age=600   text/html
assets/main-Dynkym-Y.js      Cache-Control: max-age=600   application/javascript
assets/main-DCmI0bdb.css     Cache-Control: max-age=600   text/css
sw.js                        Cache-Control: max-age=600   application/javascript
build-info.json              Cache-Control: max-age=600   application/json
```

**名前に自分のハッシュを持つ不変の資産にまで同じ値が付いている**ことが決め手だった——どんな静的ホストでもそこは
`immutable` にする。つまりこれは**こちらが書いた設定ではなく GitHub の一律方針**であり、Pages には `_headers` も
`.htaccess` も無いので、**「`index.html` だけ no-cache」という選択肢は存在しない**。

⚠ `index.html` には #R16 が置いた `<meta http-equiv="Cache-Control" content="no-cache, no-store, must-revalidate">`
があるが、**ブラウザは HTTP キャッシュについて meta を見ない**。ここは最初から塞げていなかった。

**Service Worker**：`sw.js` の `fetch` は `isTileRequest` 以外を素通しするので navigation に触っていない。
そして `sw.js` を登録するのは **`js/tile-warm.js`＝バンドルの中**——**この失敗に遭う読者が worker を持っている
とは限らない**。判断の記録は `DECISIONS.md`。

### ② 既にある受け手は、この失敗だけは原理的に見えない

#R372 が `vite:preloadError` を受けて `.im-reload` を出す。しかしそれを発火させるのは Vite の preload helper＝
**`assets/main-<hash>.js` の中身**である。**404 したのがエントリ自身なら、案内を出すはずのコードが届いていない。**
再現（実 `dist/`・実ブラウザ）:

```
404s               : main-*.js, main-*.css, maplibre-gl-*.js, maplibre-gl-*.css, supabase-*.js, geo-*.js
IntMapConsole      : undefined
IntMapAtlasAgent   : undefined
maplibregl         : undefined
.im-reload prompt  : false          ← 出ない
visible body text  : "Loading…"     ← 起動画面のまま
```

⚠ **全部がキャッシュに在るなら 404 は起きない。** 古い文書と古い資産が揃っていれば、読者は10分間ただ前の版を
使うだけで何も壊れない。壊れるのは**文書だけが残って資産が残っていないとき**で、エントリは **3.3 MB**＝実キャッシュ
が最初に捨てる大きさである。報告された観測（文書は R451・エントリは 404）はまさにその状態だった。

### ③ `__imDocStale()` — インラインで、エントリの失敗だけを、確認してから1回だけ

`index.html` のブート用 `<script>`（#R372 の受け手の隣）に置いた。**`assets/` にも `sw.js` にも置けない**——
前者は**欠けている当のもの**、後者は**そのバンドルの中で登録される**。

- capture 相の `error`（**resource error は bubble しない**ので、これが無ければ全部が死にコード）
- **エントリの `<script type="module">` の失敗だけ**。同一オリジンかつ `/assets/` 配下
- **キャッシュを迂回して自分自身を取り直す**（この取得が HTTP キャッシュを入れ替えるので、続く再読み込みが
  現在の文書を読む）
- 取り直した文書が**別のエントリを名指しているときに限り**、`sessionStorage` に印を書いてから 1 回だけ再読み込み

実測（実 HTTP キャッシュ・`max-age=600`・内容の整合した2ビルド）:

```
  433ms  NAV  /                             ← 古い文書がブラウザのキャッシュから出る
  443ms  404  /assets/main-Dynkym-Y.js      ← 報告された失敗
  514ms  DOC → build B  [cache-control: no-cache]    ← 確認のための取り直し
  529ms  DOC → build B  [cache-control: max-age=0]   ← 再読み込み（1回だけ）
  547ms  200  /assets/main-NEWBUILD1.js     ← 新しいエントリ
  → booted: true / 案内: 出ない / 印: 1
```

### ④ 初版はループした。見つけたのは「実 HTTP キャッシュに対する end-to-end」だけだった

最初は印を「404 を見なかった load」で消していた——「復帰できたのだから、次の deploy でもまた守ればよい」。
これが**ループ**だった。**復帰しても古い文書はキャッシュから消えず、残りの10分は新鮮なまま**なので、同じタブの
次の遷移がまた同じ死んだ文書を受け取り、再武装した門がまた再読み込みする。

⚠ **route で文書を差し替える試験ではこれは永久に出ない**——ブラウザのキャッシュを一度も通らないからである。
⇒ **印は二度と消さない**（1タブ1回）。2回目以降は再読み込みせず案内を出す。

### ⑤ 触ってはいけないもの — 遅延チャンクの 404

そちらは**アプリが生きていて**読者の地図位置と Atlas の会話を持っている。#R372 が**押せる案内**にしたのは
意図的で、勝手に再読み込みすればそれを捨てる退行になる。Vite の helper が挿すのは `<link rel=modulepreload>` で、
動的 `import()` は要素を作らない⇒ **`<script type="module">` に限れば2つの経路は交差しない**。
（試験の途中で `atlas-console` チャンクが 404 したとき、実際に自動再読み込みは起きず #R372 の案内だけが出た。）

再読み込み**しない**道は5つ: サーバーが本当に失っている（取り直した文書が同じ名前を名指す）／2回目／保存領域が
無い／オフライン／取得できない。**確認が取れないときは再読み込みしない**、が全体の規則である。

### ⑥ 検査

`scripts/test-budget.mjs` は **77.1 min / 天井 77.1 min ＝ちょうど**で、規則は「足すなら同じだけ削れ」。
無関係な spec を削るのは範囲外なので、**`tests/r465-checks.test.mjs` 11本**を node 側に置き、
**出荷される `index.html` からコードを切り出して `new Function` で実際に実行する**。

⚠ **綴りを見る検査なら、ループした初版も緑だった。** 4通りの mutation（確認の削除／capture 相の削除／
エントリ限定の削除／印の消去の再導入）で**どれも赤くなること**を確かめてある。
