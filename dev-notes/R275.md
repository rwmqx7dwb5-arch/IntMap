### ⚠⚠⚠ ①「一回きりの水源、再生できない」——直っていなかったのは ↺ ではなく、1回きりが**走っていなかった**こと

#R273 は ↺ を作った。実測（本番相当ビルド、甲府盆地、1,000,000 m³ を1回きりで設置）:

    設置直後          running:false  simSeconds:0  storedM3:1,000,000  maxDepth 13.17 m
    advance(4,200 s)  running:false  simSeconds:4,200
    ↺                 running:false  simSeconds:0  storedM3:1,000,000   ← 時計も水も戻る。**動かない**

↺ は正しく戻していた。**戻した先が動かない状態**だった。1回きりの水は `pool()` で置かれていて、これは
「体積を水平な水面としてその場に敷く」——つまり **t=0 の時点で既に静止した湖**である。`simMoving()` は
`maxUnitQ > 1e-4`、置いた直後の流束は厳密に 0、したがって

    canPour() = contSources().length || simMoving()   → 0 || false → **false**

で ▶ は無効、`pourStart()` は即 return。**1回きりの水は一度も「走る」ことがなかった**——⏭ を押して
静止状態へ飛ぶ以外に見る方法が無かった。

> 「一回きりと継続の差は、水が継続的に発生し続けるか否かしかないようにするべき。」

これが**2つ目の差**であり、指示はそれを名指ししている。→ **供給の仕組みを1つにした**。

| | 旧 | 新 |
|---|---|---|
| 1回きり | `pool(k, m3)`＝最初から静止した湖 | 蛇口。`rate` m³/s で `cap` を出し切ったら止まる |
| 継続 | `addVolume` を毎ステップ | 蛇口。`cap` が `Infinity` なので止まらない |
| `m3` | 1回きり＝目標／継続＝供給済み | **両方とも「これまでに出した量」** |
| ▶ | 継続の水源があるときだけ | **まだ出し切っていない水源があるか、水が動いていれば** |
| ↺ | 継続だけ `m3=0`、`_fed=0` | `m3=0` の1行（**両方**同じ） |

`owed(x) = cap − m3` が唯一の分岐で、`feedTaps(dt)` は `sc.cont` を**一度も見ない**。実測（同じ地点）:

    設置直後            running:**true**   t=0     出した量 0
    +60 s               t=60    出した量 1,000,000  先端 89 m   最大 33.3 m
    +4,260 s            t=4,260 先端 1,771 m
    ↺                   running:**true**   t=0     出した量 0
    ↺ のあと +60 s      t=60    出した量 1,000,000  先端 **89 m**  最大 **33.3 m**   ← 同一

⚠ **⏭ も蛇口に注ぎ続けなければならない。** `settle()` に `onStep` を足した——注がない静止状態は
「置いた水の**一部**の静止状態」であって、答えではない。実測 ⏭ 単独で 1,000,000 m³ 全量を配り、
209,656 秒（58 時間）で静止・湛水 0.97 km²・最大 3.93 m。

### ⚠⚠⚠ ②「解像度が低すぎる」——格子は選べるようになっていた。**読んでいる地面**が格子より粗かった

#R273 は `RES_D=[384,512,768,1024]` を作り、既定を 512 に上げた。**セルの数**の話としては正しい。
今回まず**セルが何から埋まっているか**を測った（カメラ z6・甲府盆地）:

    作業矩形   47.2 km          ← MAXKM=60 で切った後
    格子       512 × 379、セル **92 m**
    DEM        **z10** ＝ 標本 **124 m**            ← 格子より粗い

`build()` は

    const spanKm = Math.max(...);      // ← 視野。ここで測る
    if (spanKm > MAXKM) { …矩形を切る… } // ← 矩形はここで小さくなる
    let z = _demZoomForSpan(spanKm)+2;  // ← **切る前の数字**を使っている

つまり**格子は矩形に合わせ、地面はカメラに合わせていた**。z6 では視野が 500 km 級なので DEM は z10 まで
落ち、92 m のセルが 124 m の標本を再標本化していた——**セル1つ1つが、自分より粗いものの平均**。

→ `viewKm`（視野）と `spanKm = min(viewKm, MAXKM)`（矩形）に**名前を分けた**。実測 同じ z6 で **z13
＝標本 15.5 m**。格子 88.9 m に対して地面が 5.7 倍細かい（従来は 1.35 倍**粗い**）。

⚠ **これが ③ と同時でなければ直せない理由**：従来は開いた瞬間に z11 へ飛んでいたので視野が小さく、
2つの数字が**偶然**一致していた。ズームをやめるだけなら、この欠陥が表に出るだけになる。

### ⚠⚠⚠ ③「開くと勝手にズームする」——ツール欄は**カメラの中心そのもの**を渡していた

`js/map-ui.js` のツール行は `open(_hereLL())`、つまり**いま見ている中心**を渡す。`open()` はそれを受けて

    GE().camera.flyTo({ center:[o.lng,o.lat], zoom: Math.max(getZoom(), 11), duration:600 })

を実行していた。実測 **z6 で開く → z11**。読み手が既に見ている点へ、5倍に寄って飛ぶ。

→ **画面の中にある点ではカメラを動かさない**。矩形は `build({center})` が直接狙う（#R255 が
クリックについて書いたのと同じ作り）。⚠ **画面の外の点だけは動かす**——Atlas は見えていない場所を
名前で指定できるので、見せずに矩形を作るのは「見えない所で動く道具」になる。そのときも**ズームは変えない**。

### ⚠⚠⚠ ④ MeteoAlarm の「緑」を、発令中の警報として塗っていた

「発令されていないだけの地域は灰色に」の面を測ったら、**緑が黄色になっていた**。実測（live）:

    イタリア    474 件中 **201 件が「Green Thunderstorm Warning」**（awareness_level = `1; green; Minor`）
    ベルギー    **フィード全体**が緑（heatwave 67・rain 18、10 区域すべて tier 1）

relay は `severity` だけを読んでいて、緑の行の CAP severity は `Minor`/`Moderate`。`SEV` はそれを
警報の階級に写す。→ **ベルギーは「10 区域が警報中の国」として描かれていた**。

⚠ **災害名の文字列で代用してはならない。** イタリアは event に色語を書く（「Green …」）が、
オーストリアは書かない（`Thunderstormwarning` 796 件、すべて awareness 2）。色語を読む実装は
イタリアを見つけてオーストリアを丸ごと取り逃がす。→ **`parameter[awareness_level]` を読む**。
緑（1）は**落として数え**、2/3/4 を CAP の 1/2/3 に写す。落とした数は `green` として返す（黙って消さない）。

### ⚠⚠⚠ ⑤「更新が遅すぎる」——欧州35か国は、初回に読んだきり**一度も更新されていなかった**

#R273 は tick を 60 秒から 30 秒にした。tick は問題ではなかった。実測（ビルド済みページ、レイヤーON、
`refresh()` を 8 分間に 80 回駆動）:

    MeteoAlarm へのリクエスト  **3本**（35/35 到達）→ **以後の 77 回でゼロ**

原因は1つの述語を2度使っていたこと:

    loadMA( maAsked.filter(k => !maData[k]).concat(maNext()) )
                         ~~~~~~~~~~~~~~~              maNext() も同じ条件で絞る

どちらも「**まだ持っていない国**」なので、国が届いた瞬間に候補から永久に外れる。**初回読み込みの
待ち行列**であって、更新の輪番になったことが一度も無かった。→ **最後に読んだ時刻の古い順**
（未読が先）で 6 か国 × 2 本／tick。実測、最古の国の年齢は **47〜89 秒で振れ、増え続けない**。

### ⚠⚠⚠ ⑥「対応国も増やせ」——1つずつ叩くのをやめ、各国が**自分で出している登録簿**を読む

#R273 は台湾とニュージーランドを手で足した。今回まず候補を一通り叩いた（実測・同一分）:

    インド IMD          401「IP を whitelist しろ」      トルコ MGM      500「Not allowed by MGM」
    アルゼンチン SMN    503                              メキシコ SMN    HTML
    南アフリカ SAWS     HTML                             韓国 KMA        ポータルの HTML
    チリ                404                              マレーシア      200（唯一の当たり）

**手で足す方式が限界だった**のではなく、**ほとんどの NMHS が自前の CORS 付き機械可読フィードを
公開していない**。公開しているのは **WMO の CAP 登録簿**の方で、そこには**幾何ごと**入っている:

    severeweather.wmo.int/f/wfs   GeoServer `local_postgis:postgis_geojsons`
      → CAP の `<area>` 1つ＝1 GeoJSON 地物。発表機関（`mem`）・その機関自身の `event`・
        CAP severity（`s` 0–4）・`sent`・`expires`・`capurl`

実測（同一分・live）: 警報ポリゴン 4,358 件、カザフスタン 150 区域・ロシア 84・サウジ 37・
インドネシア 5・韓国 6・チリ 4・タイ 1・ウクライナ 1。**#R266 が「機械可読な公開フィードが無い」と
記録したロシアと韓国が、両方とも入っている。**

⚠ **これは GDACS の復活ではない。** GDACS は**事象**フィードで、独自のモデル・独自の階級・単位は
**国全体**だった。これは**その国の機関自身の警報**で、単位は**その機関が描いたポリゴン**、言葉も階級も
その機関のもの。パネルは**発表機関の名前**を出す（WMO は経路であって作成者ではない）。
⚠ **他のフィードがある国は絶対にここから読まない**——カナダは ECCC のまま、イタリアは MeteoAlarm のまま。

⚠ **「対応」は WMO 自身の登録簿で決める。** `/json/cap-status.json` が加盟国ごとに
1 Completed / 2 Development / 3 Not started を持つ。**1 だけ**を配線する——何も出していない国に
「発表なし」の灰色を塗るのは、斜線がまさに避けるための主張だから。実測 **未対応 206 → 112**。

⚠ **93 か国を6件ずつ取ると初回一周に4分**かかり、その間ずっと「読んでいない国」を灰色に塗ることになる。
→ **幾何を外した同じ問い合わせを1本だけ先に投げる**（`propertyName` から `wkb_geometry` を抜く）。
実測 **1.53 MB・1.5 秒で全世界 4,427 区域**、そこから「どの加盟国に何件あるか」が分かる。形を取りに
行くのは出ている国だけなので、**93 か国が最初の tick で読み終わる**（実測 `loaded 93/93`）。

⚠ そして `propertyName` に `wkb_geometry` を**書き忘れると GeoServer は全地物を `geometry: null` で返す**。
実測、韓国 37 区域が「200・37件・形なし」で返ってきて、要約は成功しているように見えた。

### ⚠⚠ ⑦「今発表されている警報欄は、一国一行までにしろ」

実測（修正前、14行）:

    中国 5行（雷电黄色／暴雨黄色／暴雨橙色／暴雨红色／强对流黄色）・イタリア 4行・豪 2行 …… ＋「+59」

`key = iso + kind` だったので、1国が災害の種類だけ行を取る。「どこで何が起きているか」を訊いた読み手に
**同じ国を5回**見せていた。→ 1国1行（色・国・災害〈最悪順、入り切らない分は `+N`〉・階級・区域数）。

⚠ **行に印字していた階級が、その行の階級ではなかった。** 旧実装は地物の `lv`（＝その**区域**の最悪値）を
1つの災害名の横に出していたので、**CMA の黄色に「Red (I)」**と書いていた。国の行なら国の最悪値が
正しい階級なので、この食い違いは構造的に起きなくなる。

### ⚠⚠ ⑧「押した地点の警報情報が別ポップアップで」

タップは**凡例の中身を国全体の一覧で置き換えていた**——つまり「この地点は？」への答えが国の文書で、
それを見ると「いま世界で何が起きているか」が消えた。1つの面で2つの問いを共有していた。

→ #R264 の規則どおり、**指の下の点についての答えは浮く**。`.country-popup`（アプリ共通の詳細カード）に、
**その点を含む地物**を出す（日本なら市町村、ドイツなら郡、その他はその機関のポリゴン）。凡例は概観のまま。
国全体の一覧はカードのボタンから開く。同じ答えは `__wpAlerts.at(lng,lat)` でも取れる。
実測 東京〈139.69, 35.69〉→ 「新宿区／Advisory／Thunderstorm／気象庁 JMA」、ミンスク→ SWIC のベラルーシ、
パリ→ MeteoAlarm、台北→ CWA。

### ⚠⚠ ⑨ パネルの寸法を、**隣に出ている凡例と比べた**

「他の凡例やポップアップに比べて内部要素のサイズが大きすぎる」。実測（ビルド済み・デスクトップ）:

| | 警報凡例 `#data-legend-wpalerts` | 地形パネル（修正前） |
|---|---|---|
| 見出し | 11 px | 13 px |
| 本文 | 10.5 px | 12 px |
| 行 | 13〜16 px | **44 px** |
| 操作 | 約 22 px | 30〜36 px |
| 余白 | 8×10 px | 10×12 px |

#R270 と #R273 は「行の高さを1種類にする」ことを正しくやり、その1種類に **44 px**（iOS の
グループ化リストの行高）を選んだ。**デスクトップの凡例の列では、画面上の他のどの行の3倍近い。**
律動は直したが、**寸法を何かと比べたことが一度も無かった**。

→ 寸法は**1か所の宣言**（`TW_FS`/`TW_ROW`/`TW_CTL`/`TW_IN`/`TW_PAD`/`TW_GAP`/`TW_INSET`）で、
**端末クラスで2組**：デスクトップは凡例と同じ（本文 11・行 30・操作 28）、携帯は指の寸法（12・44・36）。
実測 修正後の行は 30 px（罫線のある行は DPR 1.5 のヘアラインで 30.67）で1種類。

### ⚠ ⑩「ツールは上部にスティックしろ」

ツール選択はスクローラの**中**の先頭にあったので、堤防を選んで下の設定まで下げてから「削る」に戻りたい
と思うと、**選択そのものを探しに戻る**ことになる。→ `.tw-tools` を `.tw-body` の**兄弟**に
（`.tw-foot` と同じ作り）。⚠ ピン留めは CSS ではなく **DOM の親子関係**——`position:sticky` は
スクローラの中では効かない。実測 `head → tools → body → foot`、`tools.parentNode === panel`。
