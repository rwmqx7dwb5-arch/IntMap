## R350 — **最終回答が文字列だったので、何一つ突き合わせられなかった**

利用者の報告は中国経済についての 1 通の回答だが、そこに**六つの欠陥が同時に**現れていた。

1. 冒頭で「巨大な**国内市場よりも**製造業・投資・輸出が支えている」と断定し、本文では
   **消費が需要構成でも成長寄与でも最大**であるデータを自分で提示していた。
2. **GDP に占める構成比・成長率への寄与・長期的な供給能力**を、どれも「支えている」の一語で束ねていた。
3. 「工業付加価値」「製造業付加価値」「規模以上工業の増加率」——**定義の異なる統計系列**を
   一続きの数値として扱っていた。
4. 本文に `stats.gov.stats.gov.cn` という**存在しないホスト名**が現れ、リンクになっていた。
5. テキスト回答は成立しているのに、**暗黙に実行された地図移動の失敗**が
   「⚠ 実行できなかった操作が 1 件あります」として**回答の先頭**に出ていた。
6. ソースカードはあったが、**どの主張をどれが支えているか**は誰も保証していなかった。

### 1. 一件のプロンプト調整では直らない理由

`analyze` が返していたのは**プロース（文字列）1 本**である。出典はその末尾に
`SOURCES: <url> | <url>` として書かせ、正規表現で剥がしていた。地名はさらにその後ろの
`PLACES: [{...}]` を、もう 1 本の正規表現で剥がしていた。その呼び出し自身の meta と引用は
`window._aiLastMeta` / `window._aiLastCitations` ——**最後に返ってきた呼び出しが上書きするグローバル**
——から、await の**後で**読んでいた。

**文字列には、冒頭と本文の関係が無い。`dimension` が無い。`seriesId` が無い。出所が無い。**
上の六つは「たまたま悪い生成が来た」のではなく、**その形が許していたこと**である。
だから直したのは回答ではなく、**回答の形**にした。

### 2. 入れたもの

| 部品 | ファイル | 何の正本か |
|---|---|---|
| 証拠レジストリ | `js/atlas-evidence.js` | ソースが入ってよい唯一の入口 |
| 回答の schema と意味区分 | `js/atlas-answer-contract.js` | `AnswerEnvelope`・claim の `dimension`・単位クラス・文中の数値の読み取り |
| 監査 | `js/atlas-answer-audit.js` | 30 超のコードを**構造から**判定する（モデルの自己点検ではない） |
| 実行順 | `js/atlas-answer-pipeline.js` | 1 回の呼び出し → 監査 → 最大 1 回の修復 → 劣化 |
| 描画 | `js/atlas-answer-render.js` | 引用記号と出典カードを**レジストリからのみ**生成 |

**モデルは URL を書けない。** schema に URL を置く場所が無く、証拠は ID でしか参照できない。
本文に URL やホスト名が現れた回答は監査で落ち、描画側は**通ってしまった場合でもリンクにしない**
（`stripModelUrls`）。止め方が二重なのは、片方だけでは「監査を通り抜けた 1 件」が読者に届くからである。

**「支えている」は 1 つの意味ではない。** claim は必ず `dimension` を持つ——
`level` / `share` / `growth_contribution` / `structural_capacity` / `trend` / `causal_driver`。
比較は**同じ dimension の中でだけ**成立する。冒頭が「A より B」と排他的に断じるには、
**同じ dimension に測定済みの claim が 2 つ**要る。報告された冒頭文はこれで落ちる。

**数値は系列に属する。** 数値を含む claim は `metric{seriesId, concept, value, unit, basis,
geography, period}` を持ち、**文中の各数値は引用した証拠が実際に持つ事実と突き合わされる**。
1 つの文に 2 つの異なる seriesId の数値が結ばれていれば `series.mixed_series_in_claim`。
禁止語句の一覧ではなく**数値の出所**で判定するので、言い回しを変えても通らない。

**「Web検証済み」は見出しではなく事実になった。** hosted web search が**その呼び出しで実際に走り**、
provider の注釈が**その呼び出しの ID を持つ**証拠だけがその見出しに入る。
レジストリは 1 回の呼び出しに束縛される——だから**同時に走る 2 つの回答が引用を取り違えられない**。

**⚠ `askAIEnvelope` は #R132 から実装されていて、一度も export されていなかった。**
だから analyze には「自分の呼び出しの meta」を読む手段が無く、グローバルしか無かった。
`js/ai-core.js` の返り値に加え、呼び出しごとの `callId` も envelope に載せた。
`brief` と planner 由来の `answer` からもグローバル参照を外したので、
**Atlas の回答面から `window._aiLast*` は消えた。**

### 3. 補助的な操作の失敗は、ターンの失敗ではない

`_atlCompose` の要約は**失敗した action の数**を数えていた。誰の目的だったかは訊いていない。
`goalImpact`（`js/atlas-planner.js`）が依頼のプロファイルから導く:

| 依頼 | `flyTo` の失敗 | 表示 |
|---|---|---|
| 「実際に支えているのは何？」 | `secondary` | 回答の**後ろ**に小さく「地図の表示は変わりませんでした」 |
| 「中国へ移動して」 | `primary` | 先頭に警告・ターンは `partial` |
| 「中国経済を説明し、地図も表示して」 | `primary` | 説明成功・地図失敗＝`partial` |

`_requestProfile` に `outputs.navigation` を足した——「地図」の語を含まない
「中国へ移動して」を、`wantMap`（「地図上で教えて」のための信号）と混ぜずに見分けるため。

### 4. 意図的に外したもの（隠していない）

**analyze の「関連記事」フォールバック（#R159）は削除した。** 引用が 1 つも無いときに
収集済み記事を並べる仕組みで、これは**支えていない記事を主張に貼り付ける**ことに他ならない。
代わりに監査が「primary claim に証拠 ID が無ければ落とす」ので、
**証拠があるならば引用しなければ通らない**——弱いフォールバックより強い保証になっている。
