## R287 — **「厳密に一致」を守るために緩めたのは色ではなく問いのほう／そして直した瞬間、その裏に隠れていた 2 件目が出てきた**

> 「the post-deploy production smoke test has been failing since round R284 … The judgement call
> belongs to whoever owns R284's change — please decide and implement one of:
> (a) the assertion should compare against the RESAMPLED ramp … or (b) the ramp should stay
> nearest-neighbour and R284's resampling was wrong.
> Do NOT "fix" it by loosening the comparison to a tolerance.」

**(a) でも (b) でもなかった。(a) の前提が事実ではなかったからである。**

### 1. 依頼の前提を最初に測った——`EC.scale()` は既に再標本化された表を返していた

失敗した表明は `expect(m.px.slice(0,3)).toEqual(m.want.slice(0,3).map(Math.round))` で、
CI が印字した 2 つの数は `- [43,167,127]` と `+ [42,166,132]`。
**この 2 つは両方とも、アプリ自身の 601 段の表の項である**——それぞれ **6.7 m/s** と **6.5 m/s**。

`m.want` は `EC.sdk().getColor(sc, sp, true)` だが、その `sc` は `EC.scale(…)` ＝
`sdk.getColorScale(variable, dark, omSettings().colorScales)` であり、`colorScales.wind` は
`WINDY_WIND = rampFrom(WIND_ANCHORS, 0.1)` に**差し替えられている**。本番で実測: `scale()` の
`breakpoints.length` は **601**・刻みは **0.1**。つまり **表明は最初から再標本化された表と
比べていた**。(a) は「今やっていることをやれ」という指示になっていて、1 バイトも変わらない。

(b) も違う。段彩をやめてグラデーションにすること自体が依頼（「Wind(animated)は色味は段彩では
なくグラデーションに。色はそのまま。精度も一切落とすな。」）で、実装は正しい——本番の画素は
**81 画素中 78 画素が表の項と厳密に一致**していた。戻すのは要求された機能の削除にあたる（§3.1）。

### 2. #R284 が壊したのではなく、**表明が寄りかかっていた偶然を取り除いた**

ラスタは texel から `raster-resampling: linear` で描かれる＝**画素はそれが覆う空気に答える**。
`valueNow()` は格子を**点**で内挿する＝**別の問い**。17 本の帯だったころは、この 2 つの読みが
**同じ帯に落ちて同じ色**になっていた。0.1 m/s では 1〜8 段ずれる。

本番実測（z3・150°E 20°N・上に載る 56 層を消して 81 画素）:

| 問い | 一致 |
|---|---|
| 画素が表のどれかの項と**厳密に**一致するか | **78 / 81** |
| 画素が**点の値**の項と一致するか（**旧・表明**） | **20 / 78（26%）** |
| 画素が**1 画素以内のどれかの風速**の項と一致するか | **78 / 78（100%）** |

**旧・表明は 4 回に 1 回しか通らない籤になっていた。** 落ちた 3 画素は気象ではなく、
`wind-field-a` の**上に載っている 31 層**（海底ケーブル・境界線・地名・ニュースの点）だった。

### 3. だから緩めたのは色ではなく**問い**——#R276 追記3 と同じ手

「正しい絵が通るまで数値を緩めるのはテストを無意味にする」（#R276 追記3）。色の許容差は
入れていない。**厳密な主張を 2 つ**にした（`tests/helpers/wind-ramp.js`）:

- **① 画素は表の色そのものである**（バイト単位）。夜のシェードが乗れば **128 RGB 単位**離れるので、
  #R276 が存在する理由——0.36 倍の灰色——はここで即座に落ちる。
- **② その項が意味する風速を、場がその画素の下で実際に取っている**（`[lo,hi]` は 1 画素ぶんの範囲）。

空間の曖昧さは**空間で**決着させた。`getColor` は捨てていない——`colourFor(m.ramp, m.sp)` が
SDK 自身の答えと一致することを表明して、**表の読み方が描画側とずれない**ことを固定している。

### 4. 直したら、その裏に **2 件目**が出てきた

`tests/prod-smoke.spec.js` は `test.describe.configure({ mode: 'serial' })` なので、**19 番目が
落ちた時点で 20・21 番は走っていなかった**（deploy ログの `-` はそれ）。19 番を直したら 21 番が
落ちた——`typeof r.b.v === 'number'` に `object`（＝ null）。**単独で走らせても 4/4 で落ちる。**

原因は `fireTime()` の 1 行:

```js
if (held && held.key !== stateKey(held.variable, '', idx)) release();
```

`release()` は `held` **と `loadingKey` の両方**を消す。この行は **#R276 では `setIndex` の中に
あって同期に走っていた**ので、新しい時刻の読み込みが始まる**前**に終わっていた。**#R284 が
`COALESCE_MS`（140 ms）ぶん遅らせた**ことで、**その窓の中で始まった読み込みの最中**に着地する
ようになった。読み込みは完了し、`loadingKey` が自分の鍵と違うのを見て**自分を入れずに null を
返す**——27 MB を解いたあとで捨てる。**遅い絵のための作業をやめさせる仕組みが、正しい絵のための
作業を捨てていた。**

⚠⚠⚠ **これは #R276 追記2 の欠陥の、軸違いの再演である。** あちらは「あるレイヤーの後始末が
別の**変数**の読み込みを無効にした」、こちらは「**時刻**軸が、自分がいま告げようとしている
時刻の読み込みを無効にした」。`docs/MAP-LAYERS.md` には「時刻を変えたときの `release()` は
**無条件で正しい**」と書いてあった——**同期に走っているあいだだけ**正しかった。

→ `fireTime()` は**古いフレームを捨てるだけ**にし、`loadingKey` を消すのは
**いま告げる時刻以外**の読み込みに限る（`fileUrl(idx)` の前方一致で判定）。
**他のふるまいは 1 つも変えていない。**

実測: 起動後の最初の 1 歩は**必ず**負ける（冷えた場は 7〜9 秒、窓は 140 ms）。1.5 秒後の再試行は
25.27 °C を返した。暖まった場は窓の内側で解決するので影響を受けない（実測、待ち 0 ms のみ null・
60/130/160/300/600 ms はすべて成功）。

### 6. 残す

### 7. 追記 — 本番検証で1件。「画素は表の項そのもの」はまだ強すぎた

deploy 直後の post-deploy smoke が落ちた。**そして落ちた文面は、このラウンドが書いた診断そのものだった**:

```
the painted pixel IS a colour the wind table can produce — pixel [44,168,123] is NOT any table
entry — nearest is [44,168,122] (6.9 m/s) at distance 1.0, and the field under that pixel runs
6.69…8.69 m/s
```

**距離 1.0。** 青チャンネルが 1 だけ違う。理由は節（アンカー）である:

⚠⚠⚠ **17 の節は「角」である。** ramp は節と節の**あいだ**が sRGB で線形で、**節で曲がる**。
だから画素が覆う範囲が節をまたぐと、`raster-resampling: linear` は**角の両側の色**を混ぜ、
結果は**弦**に乗る——曲線の**そば**であって、**上ではない**。
`6.69…8.69` は **7 m/s の節**をまたいでいる。

**「81 画素中 78 画素が表の項と厳密に一致」という最初の実測は、レンダラの性質ではなかった。**
その時刻の空気がたまたま 1 区間に収まっていた、というだけだった。
⚠ **1 画素・1 時刻の実測を「性質」と読んだ**のがこのラウンドの誤りである。

→ 色の主張を**包絡**にした: **場がその画素の下で実際に取る速度を、表が塗る色の範囲**に、
チャンネルごとに収まること。**調整値はやはりゼロ**——境界は場と表だけから出る。
⚠ **空気が一様な画素では包絡が 1 項に潰れ、厳密一致がそのまま戻る**（`tests/r287 ②`）。

**弱くなっていないことは測ってある**: `tests/r287 ③` が 0.36× / 0.5× / 0.75× / **0.9×** の減衰を
すべて拒み、1.0× だけを通す。**10% の減衰でも赤になる。**

#### 足跡の半径は、導出してから実測で確かめた

`wind-field-a-src` の `tileSize` は **512**。整数ズームでは **1 texel = 1 画面画素**、線形カーネルは
**±1 texel** に届き、画素自身の半幅 0.5 を足して **±1.5 px**。実測（**6 視点・477 画素**、うち
**138 が節をまたぐ**）:

| 足跡 | 通過 |
|---|---|
| ±1 px | 467 / 477 |
| **±1.5 px** | **476 / 477** |
| ±2 / ±3 / ±4 px | 476 / 477（**それ以上良くならない**） |

**カーネルの外で平らになる**ことが、「これは支持であって当てはめた数ではない」の根拠である。

#### この追記そのものの教訓

⚠⚠⚠ **最初の検証が「1 画素・1 時刻」だった。** ローカルで 1 画素、本番で 3 件しか見ずに merge し、
**deploy して初めて 2% の側に当たった**。→ 今回は**本番の 477 画素**に**実物の判定関数**を当てて
476/477 を確認し、さらに prod-smoke を**本番に対して 6 回連続**で緑にしてから出した。
**「本番で 3 件緑」は「通る」の証拠であって、「いつも通る」の証拠ではない。**
