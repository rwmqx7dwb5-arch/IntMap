〈依頼〉gis-result-handoff の本番検証で、取得→絞り込み→集計を質問を変えて確かめる。

**測った（本番・main 157030b、atlas-jobs v32）。** 4 件のジョブのどれも受け渡しの経路に着かなかった。Atlas が組んだ `data.gis` の 2 段では、1 段目の入力を `"url:https://…geojson"`（ページの `data.gis` の書き方）と書き、2 段目は前段を素の仕事名 `"africa_filter"` で指した（`inputs:[{from}]` は付いていた）。サーバの twin は `https://` で始まる文字列しか読まず、両方を `part_unsupported_on_server` で断った。断る文も世界グラフの twin の文（「永続した世界グラフだけを読む」）の流用で、書き方を直す手がかりにならなかった。そこで Atlas は data.gis を諦め、全行を文字列にして worker に渡す方法に逃げた（177 行を正しく持っていたのに、worker が「169 件」と読み誤った）。

**直したこと（構造で）。** サーバの `data.gis` がページと同じ語彙を読む:
- `"url:https://…"` は、その後ろのアドレスのファイル。
- `inputs` に書かれた素の名前が、この仕事の入力の仕事の id（または出力 id `job:<job>/<task>`）なら、その出力。runner は入力の出力を名前で引ける表（`outputs`）を twin に渡す。ページの `data.gis` がデータセット id で読むのと同じで、入力でない名前は推測しない。
- 読めないものは、data.gis が読むものを自分の言葉で述べて断る（`notHere`）。
- `jobs.start` の説明に、前の仕事の結果を次の仕事の入力にする書き方（`"@<task>:data.result"`・仕事の id）と、ファイルの読み方を明記した。

**検査。** `tests/gis-result-handoff-checks.test.mjs` に、本番で Atlas が書いたそのままの形（`url:` 付きの URL・前段を素の id で指す）を足した。1 段目が読み、2 段目が全件を受け、出典が残り、ジョブが done になる。入力でない名前は推測せず、断る文が data.gis の語彙を述べることも確かめる。

**範囲外で見つかったこと（別件）。** 本番検証で次の 3 つを観測した。
- 「実行／やめる」の確認カードは回答が書かれている間しか押せない。
- ジョブを始めても、回答の終わりにジョブのカードが消え、最終回答が「まだ開始していません」のまま残る。
- 1 回目の「実行」で 400 が出た（どの要求の 400 かは未確定）。
