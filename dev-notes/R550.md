## R550 — **夜間光は Chronos に従うようになり、その年を名乗るようになった**

> 「夜間光レイヤー `dl-nightsat` を、Chronosの時刻に応じて過去の夜間光へ切り替わる時系列レイヤーに。
>   **最重要条件は、現在の夜間光表示の画質・解像感・見た目を劣化させないこと。**」
> 「夜間光独自の別時計を新設しないでください。正本は `window.IntMapTime`。」
> 「Chronosと凡例セレクトに二つの正本を作らない。どちらが正本かを1か所で決めてください。」

### 1. 直した欠陥は「年が変えられない」ではなく「年が 3 つあった」

同じ 1 つの製品（NASA GIBS `VIIRS_Black_Marble`）について、「いつの絵か」を **3 か所が別々に**
持っていた:

| どこ | 何を持っていたか |
|---|---|
| `js/data-layers.js` | `window._nightsatEpoch` — 凡例の 2 択セレクトだけが書く |
| `js/night-side.js` | タイル URL の中に **`2016-01-01` を直書き** |
| `js/compare.js` | `.replace('/default/','/default/2016-01-01/')` |

⚠ **そしてその欠陥は実際に起きていた。** 手動の層を 2012 に切り替えても `js/night-side.js` は
2016 年の同じ製品を地球に合成し続ける——**1 枚の絵の中に同じ写真の 2 つの年**が出ていた。
`CONSTITUTION.md` §1 が名指しする「片方だけが直る」の形そのもので、しかも片方は
「Chronos に対応していない」ですらなく「**Chronos を一度も読んでいない**」だった。

⇒ epoch を**変数ではなく時計の関数**にした。新しい `js/night-lights.js`
（`window.IntMapNightLights`）が唯一の正本で、`_nightsatEpoch` は無くなった。凡例の年の行は
他の 6 つの階級区分と同じ `legendClockYear`（#R270）——つまり**読むのも書くのも Chronos** なので、
2 つ目の時計は構造として作れない。⚠ **UI は削っていない**: 2 択で届いた年は全部届くうえに、
いまは地図全体がその年へ動く。

### 2. 年次の夜間光は、探し方が足りないのではなく**存在しない**（2026-09-08 実測）

依頼は「VIIRS 系で年次夜間光を提供している実データを調査」だった。調査し、**取得して確かめた**。

- **GIBS に年次は無い。** `VIIRS_Black_Marble` も `VIIRS_Night_Lights` も、best / std / nrt の
  どの入口でも Time 次元は `2012-01-01` と `2016-01-01` の **2 値だけ**。他の年は 404 を返し、
  **無言の代替はしない**。EPSG:4326 側も同じ。
- **日次の Black Marble は同じホスト・同じ z8・鍵なしで 2012→現在を持つが、品質が別物。**
  `VIIRS_SNPP_GapFilled_BRDF_Corrected_DayNightBand_Radiance` の東京 z8 タイルを 2013/2014/2016/
  2019/2022/2024/2026 について取得し、ブラウザで復号して測った: **ラプラシアン・エネルギー 44〜68**
  （Black Marble は **18.3**）、**タイルの 99 % が点灯閾値より上**。単夜のグレースケール放射輝度で
  あって合成ではなく、依頼の「背景ノイズが増えていない」を満たさない。⚠ **「500 m と書いてあるから
  同品質」で済ませない**という指示のとおり、採らない理由は分解能ではなく**測った見た目**である。
- **EOG の年次 VNL は OpenID の裏**（配布パスは全部認証へ 302）、**OGC の口は無い**。
  NASA の VNP46A4（年次）は Earthdata Login。NOAA の DMSP-OLS 配信は消えている。
- **鍵もログインも要らない年次タイルは 2 つ見つかったが、どちらも採れない。**
  ひとつは第三者の GeoServer（**CORS を返さない**うえ、公開側の同じ製品はトークンでホットリンクを
  拒んでいる——自前の中継で回すのは相手のアクセス制御を迂回することになる）。もうひとつは
  CC BY 4.0 で CORS も通る 33 年ぶんだが、**LERC・EPSG:4326 の独自グリッド・最大 z7（≒927 m）**で、
  **いまの 500 m / z8 より粗い**。

⇒ 利用者に選択肢（2 epoch のまま完成／第三者の月次を足す／自前でピラミッドを同梱）を提示し、
**「2012/2016 の 2 epoch だけで完成」**を選んでもらった。判断そのものは `DECISIONS.md`。

### 3. だから 2012/2016 の画素は 1 バイトも動いていない

`tests/r548-checks.test.mjs` ④ が、`js/night-lights.js` の作る URL を **#R268 が出していた文字列と
突き合わせる**（ホスト・製品・TileMatrix・拡張子）。品質経路は移動していない。

### 4. epoch の選び方——「近いほう」だけでは足りない

- 時計が **LIVE** なら最新の epoch（＝ 2016）。
- **2012 年より前は epoch 無し。** 「最も近い epoch」ではない——Suomi NPP は **2011-10-28** 打ち上げで、
  1900 年に近い夜間光は**存在しない**。層は**何も描かず**、凡例が理由を言う。
  この床はセンサーの事実であって調整値ではない（`.agents/rules/no-ad-hoc-hardcoding.md` §4）。
- それ以外は「年と epoch の年の差」が最小のもの。ちょうど中間（2014）は**新しいほうへ倒す**ので、
  スクラブは 1 回・1 か所でだけ絵を変える。
- ⚠ **購読者に届くのは epoch の変化だけで、年の変化ではない。** 2017→2018→2019→2020 は同じ epoch に
  解決するので通知が起きず、source も貼り替わらない。**ブラウザで実測: 要求 0 件**。

### 5. 3 つの状態は 3 つの文である

「取得失敗とデータ未提供を同じ状態にしないこと」——凡例と Atlas の状態文は、次を別々に言う。

| 状態 | 凡例 | Atlas |
|---|---|---|
| 絵がある | `VIIRS Black Marble · 2016` ／ `VIIRS / Suomi NPP · NASA EOSDIS GIBS · 500 m` ／ `Chronos: 2020 → 最も近い記録: 2016` | `Night lights on screen (layer): … 2016 … the NEAREST published epoch. Report 2016 …, never the clock year` |
| 記録が無い | `No data` ／ `Chronos: 1900 — 2012年より前の衛星夜間光の記録はありません` | `Night lights: NO DATA — … no satellite night-lights record exists before 2012` |
| 取得に失敗 | `夜間光のタイルを取得できませんでした` | （上の 2 つと混ざらない） |

失敗はレンダラ自身の `error` イベントが `src-nightsat` について言ったときだけ立つ。

### 6. 地球の夜側は同じ epoch を引き、遅れて着いたモザイクは捨てる

`js/night-side.js` は同じ `js/night-lights.js` にタイル URL を訊く。**同じ URL なのでブラウザの
HTTP キャッシュが両方に効き、二重ダウンロードにならない**（依頼の「二重ダウンロードしない設計」）。
64 枚の画像読み込みは時間がかかるので、**完了時点の時計と照合**して、epoch が動いていたら
モザイクを**捨てて現在の epoch を取り直す**——開始時に捕まえた値と比べる書き方だと、それが
まさに「古いリクエストが後から到着して表示を巻き戻す」になる。
⚠ terminator・per-pixel alpha・極冠・ズームランプ・性能設計は 1 行も触っていない
（`tests/r201` / `r220` / `r228` は緑）。⚠ 2012 年より前は `lights=null` に戻すので、夜側は
**灯りの無い夜**になる——1900 年について正しい絵である。

### 7. 自分で書いた i18n が、自分で計器から消えていた

`_nightsatWhenHTML()` の最初の版は `const T = window.IntMapLang.t;` と別名を取っていた。
`scripts/i18n-audit.mjs` は positional 呼び出しを**形**で見分けるので、**Identifier の別名は
offset 0 と読まれる**。結果、新設の 6 文字列は inline 監査からも positional 監査からも
**丸ごと外れ**、fr / ko / 中文で永久に英語のまま、**ゲートは 100 % と言い続ける**——#R535 が
測った欠陥と同じ形が、同じ月に、別のファイルで再現した。
⇒ 呼び出しごとに `window.IntMapLang.t(HOST.lang, …)` を書き、年は連結ではなく **`{y}`
プレースホルダ**にした。母数が 5,673 → 5,677 に増えたのが直った証拠である。

### 8. spec は 3 回書き直した——1 回目は Atlas、2 回目は NASA を測っていた

| 版 | 本文（3 回の実測） | 何を測っていたか |
|---|---|---|
| ① | 19.2 / 24.6 / 29.3 s | Atlas の状態文のために **1 MB のカーネル**を読ませていた |
| ② | 12.6 / 20.7 / 39.3 s | **NASA の応答**。連続実行では GIBS が 429 を返し、**テストのほうが落ちた** |
| ③ | 12.2 / 14.2 / 16.4 s | この製品——ただし「要求が出たか」を固定の 500 ms で**標本抽出**していた |
| ④ | 9.7 / 10.5 / 11.4 s | この製品を、**主張する対象を待って** |

- ① → ② : Atlas の主張は `js/atlas-state.js` を **Node で評価**して確かめる形にした
  （`tests/r534-checks.test.mjs` が作った作法）。provider と renderer の**両方**を走らせるので、
  ブラウザで文字列を読むより強い。
- ② → ③ : タイル要求を**横取りして即座に返す**。主張は「正しい年を asked for したか」であって
  「GIBS が速いか」ではない。
- ⚠ **ズームは z6.2 でなければならない。** z4.6 では `js/night-side.js` が自分からモザイクを取りに
  行くので、「レイヤー OFF なら通信 0」を測ると**別の機能を測ってしまう**（実測 7〜16 件）。
- ⚠ 途中で 1 回落ちたのは**私のアサーションの欠陥**だった: resource timing の entry は**完了時**に
  現れるので、年をまたいだ瞬間にまだ飛んでいた前の年のタイルが「新しい年が古い年を取り直した」と
  読めていた。数えるのは `startTime`＝**発行時**である。
- ⚠⚠ **③ → ④ は、`npm test` を 2 回通して初めて見えた。** 1 回目は緑、2 回目だけ赤——しかも
  **並列プールの位置は同じ**（どちらもその worker の最後、直前も同じ spec）。原因は順序ではなく、
  「ON にしたら要求が出る」「epoch をまたいだら要求が出る」という**肯定の主張を、固定の 500 ms で
  標本抽出していた**こと。`tests/helpers/app.js` のページは **spec ファイルをまたいで共有される**
  （fixture の scope は worker）ので、温まったキャッシュのもとでは製品が正しくても要求は 0 件になる。
  ⇒ 温まり得る側（②）は「**間違った年は 1 件も要求されていない**」という否定形に、
  キャッシュに無い年（③）は `expect.poll` で**主張する対象そのものを待つ**形にした。
  ⚠ 閾値は 1 つも緩めていない——測っている対象と主張がずれていたのを揃えた。

`scripts/test-budget.mjs` の core は 35 → 43、total は 4,648 → 4,665（どちらも**実測ぶん**）。
