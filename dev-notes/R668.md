## R668 — **横向きの iPhone は、この app にとって別の端末だった——39 か所で**

〈利用者から「スマホでズーム・パン・タップが遅い。操作によってはブラウザが落ちる。
メモリを使いすぎているのではないか」という構造改善報告書 1 本。根本・構造解決の要求つき〉

### 0. 報告書の主張のうち、実測で確認したもの・訂正したもの

報告書は「測ってから直せ・過去のコメントの数字を今回の実測として報告するな」と要求している。
最初にやったのはそれで、**訂正が 2 件出た。**

| 報告書 §2 の主張 | 実測 |
|---|---|
| §2.2 `_tick()` は「なぜそのフレームが要求されたか」を問わず全 READ/WRITE を走らせる | **正しい。**ただし `onCamera` の購読者は**8 本**しかなく、支配的な費用である証拠は取れていない。今回は触っていない（§6） |
| §2.3 `skipData` は revision で決まる場合でも先に内容比較する | **正しい。**順序だけ入れ替えた |
| §2.5 長押しの `getBoundingClientRect()` が指1回ごとに走る | **もう直っている**（#R498/#R499）。`--attribute` の実測で、素の pan の rect 260 回のうち **252 回は MapLibre 自身**、IntMap 由来は 1 回 |

そして計器は**作らなかった**——`scripts/mobile-trace.mjs` が CDP の本物のタッチで pan/pinch を打ち、
`rect/move`・touchmove→フレームの遅延・heap を既に出す（#R387/#R498）。

**基準値**（Chromium・iPhone13 profile・`--cpu 4`・reps 2）:
`pan-touch` rect/move **7.47**・遅延 p50 57–69 ms・max 160 ms／`pan-alerts-city` rect/move **11**／heap 56 MB。

⚠ **IntMap 由来の強制レイアウトが出るのは、レイヤーが点いているときだけだった。**
`pan-alerts-city` の 182 回のうち **48 回**が凡例のタイル配置（`tileLegends()`）で、これは
**開いている凡例の数に比例する**——「機能数が増えても操作経路の仕事は増えない」という
`js/runtime.js` の header の約束が破れている箇所。**今回は直していない**（§6）。

### 1. ⚠⚠⚠ 落ちる話の中心は、幅で端末を訊いていたこと

`isMobile()` は `matchMedia('(max-width:768px)')`。**横向きの iPhone は 844 px** なので
「携帯ではない」と答える。#R232 がこの規則を立て、#R498 がもう一度掃いた。
**掃いたのは現場であって規則ではなかった。**

全追跡ファイル **1,016 本**を掃引して、**18 ファイル・39 か所**が費用・メモリ・能力の判断を
幅で訊いていた。横向きの iPhone が**同時に**取っていたもの:

```
メモリ圧の見張り            設置されない            js/label-occlusion.js
ケッペン作業キャンバス      16 MB → 67 MB           js/data-layers.js
2つ目の WebGL context       フル解像度 PNG          js/compare.js   ← #R29.1 が直した当のクラッシュ
ケッペンの解放（OFF時）     解放されない (~150 MB)  js/data-layers.js
地震・遠方ラスタ            6.6 MB → 48 MB          js/seismic.js
地震・pinned DEM            123 MB → 410 MB         js/seismic.js
津波の格子                  ×2.8                    js/tsunami.js
風の粒子                    2,200 → 6,000           js/weather.js
水の解法                    9,000 → 120,000 ステップ／2.5 s → 6 s  js/terrain-water.js
先読みリング                60 → 150 枚             js/tile-warm.js
タップの許容半径            15 px → 6 px            js/map-ui.js ほか2本
```

⚠ **一番効くのは 1 行目である。**落ちる寸前に助けるはずの弁が、
**落ちると報告された当の端末では設置すらされていなかった。**

### 2. ⚠⚠⚠ なぜ 3 ラウンド生き延びたか——検査が 1 ファイルの綴りだったから

`tests/r498-checks ③` はこういう形をしている:

```js
assert.match(b, /antialias:!_imPhoneClass\(\)/, 'MSAA follows the device');
```

`b` は **`js/app-body.js` のソース文字列**。8 本並んでいて、**8 本とも今日も緑**。
緑のまま、他の 300 ファイルで 39 か所が育った。**それらはそもそも母集合に入っていない。**
#R429 の形そのもので、`.agents/rules/no-ad-hoc-hardcoding.md` §3 の 2 問目——
「この規則は次に同じ経路を通る新しいコードにも効くか」——が 3 ラウンド続けて「いいえ」だった。

⇒ **`tests/r668-checks ③` は全追跡ファイルを歩き、「幅で選ばれた数」を数え、既定は失敗する。**
幅が本当に正しい問いである場所だけを**理由付きで**許可リストに置く（現在 4 件——`maxZoom` の
18:19 が 2 本、平面地図の最小ズーム、水パネルの CSS の inset）。

⚠⚠ **綴りを探すだけでは足りない。**39 か所のほとんどは `isMobile()?110:420` とは書かず

```js
const _mob = (typeof isMobile==='function' && isMobile());
const budget = _mob ? 110 : 420;
```

と書く。だから検査は**まず局所名を解決**する: その宣言が幅のテストを含む識別子は、それ自体が
幅の託宣。⚠ ただし**委譲している名前は除く**——直した現場は `deviceIsPhone(旧テスト)` と書くので
旧テストの綴りは宣言に残っており、綴りだけを見る検査は**直した現場を全部赤にする。**

### 3. ⚠⚠⚠ 述語の手書きの写しが 3 本あり、3 本とも同じ節を落としていた

正本（`js/app-body.js:159`）は 3 節。`js/dem-source.js`・`js/precip-annual.js`・`js/vs30-mask.js`
は先頭 2 節だけを写しており、**#R499 が足した第 3 項（画面の短辺 ≤500）が無い**。
`(any-pointer:fine)` はスタイラスや Bluetooth マウスで真になるので、
**それらを繋いだ携帯がデスクトップ予算を取る**——#R499 が直した当の欠陥の再発。

⚠ `js/vs30-mask.js` のコメントは「正本を **EXACTLY** 複製している」と**主張していた**。
#R499 の時点で偽になり、誰もコメントを直さなかった。**写された述語は必ずずれる。**

⇒ 全部 `window.IntMapMemBudget.deviceIsPhone(旧テスト)` へ委譲。
⚠ **fallback は呼び出し元の旧テストであって `true` ではない**。これは起動中にも走るので、
「まだ `_imPhoneClass` が公開されていないから携帯」と答えると**早く訊いただけのデスクトップ**の
予算が縮む。**今日より悪くならない**ことを保証するほうが安い。
（⚠ **予算側の既定は逆で、意図的に逆である**——誰も教えていない置き場は**小さい**上限を取る。
そこで賭けているのは死んだタブだから。）

### 4. ⚠⚠⚠ 同じタイルを 5 か所が溜めており、4 か所は端末を見ていなかった

復号済み terrarium タイルは `Float32Array(65536)` ＝ **262,144 B**。これを溜める置き場が 5 つ:

```
src/photo-geo-worker.js         1400 枚   367 MB   端末を見ない
js/map-readout.js               携帯 140          （#R651 が別セッションで直した）
js/cesium-layers.js              400 枚   105 MB   端末を見ない
js/terrain-water.js              360 枚    94 MB   端末を見ない
src/photo-geo-worker-client.js  上限なし           ← ページ側フォールバック
```

合計で**約 600 MB を携帯に許可**していた計算になる。
⚠⚠ **上限が無いのがページ側フォールバックであることが、いちばん悪い。**
そこは `new Worker` が**失敗した**ときに通る道＝**メモリの足りない端末でだけ通る道**である。
上限を無視するほうが、上限を持たないより上等だった。

⇒ **`js/mem-budget.js`**: 1 枚の値段・端末・取り分を 1 か所で持ち、**1 つの予算**
（携帯 48 MB／他 192 MB）を `SHARE` で分ける。
⚠ **worker は `matchMedia` を持たない**ので、ページが `adopt()` で教える。
⚠ **走っている仕事のタイルはリースして上限から除外する**——`buildField()` は取得済みの全域を
読むので、途中で捨てると**キャッシュミスではなく答えの穴**になる（#R221 が同心円として観測した
のと同じ機構）。リースは `finally` で必ず返す。**返し忘れたリースは、切った上限と同じ。**

⚠ **正直な限界**: 予算 1 つより大きい探索範囲は、依然としてその範囲を丸ごと持つ。
予算が縛るのは**残すもの**であって**1 つの答えの費用**ではない。後者を縛るのは探索範囲を
縛ることで、それは製品の判断であって今回のものではない。

### 5. ⚠⚠ 圧迫時の解放は、手書きの 2 つにしか届いていなかった

`intmap-mem-pressure` を聞いていたのは `js/beta-overlays.js` と `js/layer-packs.js` の 2 つだけ。
上の 5 つは**1 つも含まれていない**。名指しの一覧は次に足されたものを黙って落とす
（`.agents/rules/no-ad-hoc-hardcoding.md` §1）⇒ **登録**（`register()`／`relieve()`）にした。

⚠⚠⚠ **ただし弁は答えではない。** `performance.memory` は **Safari に存在しない**ので、
報告された端末では弁は何も測れない。しかも 8 秒ごとのポーリングは、
1,600 枚を要求する 1 枚の絵の**間**に越えられる。
だから中心は**確保前の予算**であって圧迫検出ではない（報告書 §2.1・§8.3 の要求そのもの）。

### 6. ⚠ 今回やっていないこと（測って、やらないと決めたもの）

- **`_tick()` の変更**（報告書 §2.2）。事実は確認したが、`onCamera` の購読者は 8 本で、
  これが支配的だという実測が無い。**測らずにスケジューラの意味を変えるのは報告書自身が禁じている。**
- **`tileLegends()` の呼び出し経路**（§0 で実測。`pan-alerts-city` の rect の 48/182）。
  凡例が開いている数に比例して指の経路が重くなる。直すべきだが、
  カメラ移動→警報再描画→凡例再表示という**呼び出し側の連鎖**の問題で、今回の主題と別。
- **実機での計測。**Windows・Safari 無し・端末ブリッジ無しなので、Chromium の iPhone13 profile と
  WebKit（同じエンジン族）でしか測れていない。**「実機で直った」とは言えない。**——6 項目のうち 5 項目は WHO 自身が構造化して持っていた**
