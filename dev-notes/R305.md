## R305 — **「塗られていない」を点ごとに数えたら、灰色を描く役が誰もいない窓が2つあった**

依頼4件（警報の塗り漏れ／風の速さ〈2回目〉／地点を訊く UI が2つ同時に出る／不要な PDF の削除）。

### 1. 「何も発令されていないのに、灰色に塗られていない場所がある」

**推測せず、レンダリングされたレイヤーを点ごとに問い合わせた。** 各標本について
`wp-alert-fill`（警報 / 発表なし）・`wp-alert-choro`（国1枚の薄塗り）・`wp-alert-hatch` の
どれが実際に当たるかを `queryRenderedFeatures` で数える。

**改修前後は同じカメラ・同じキャンバス・同じ標本格子で通した**（`git show origin/main:js/world-packs.js`
を入れてビルドし直し、測ってから戻す——「同じ入力に両方のコードを通す」）。

```
z2 · center(20,30) · canvas 880×800 · 7,154 点 · うち陸（このレイヤーの下にある国）3,404 点
    前  759 点 (22.3%) が「何にも塗られていない」   CAN 386 · CHN 186 · USA 101 · BRA 58
    後  217 点 ( 6.4%)                              CAN 206 · CHN   4 · USA   0 · BRA   0
z5（中欧）· 3,213 点 → 73 点 (2.7%)  うち CHE 25
```

⚠ **残差の 206/217 はカナダ1国**である（②の最後を見よ）。カナダを除くと **373 → 11**。

原因は**2つ**あり、どちらも「灰色を描く役が誰もいない窓」だった。

#### ① `drawnISO` は「何かを描いている」であって「地面を塗っている」ではない

`washTier` は `(quietSet[c]||drawnISO[c])?2:1` を返していた。2 は「単位レイヤーがこの国を
塗っているから、国1枚の薄塗りは要らない」という意味である。ところが

- `quietSet[c]` ＝ **いま単位レイヤーがこの国の静かな地面を塗っている**
- `drawnISO[c]` ＝ **この国は何かを描いている**

は、単位レイヤーが動いている場所でしか同じ文にならない。`QUIET_UNIT_Z`（= 3）未満では
単位レイヤーは何も描かないので、**警報が1つでも出ている国は世界ズームで完全に透明**だった。
#R299 が「発令中の国に『読んだ。何も出ていない』の灰色を敷いてはならない」と決めたのは正しく、
その判断を**肩代わりする層が動いていない場所へ持ち込んだ**のが欠陥である。

→ **直すのは `washTier` ではない。** 2つの腕はそのまま——`drawnISO[c]` が国1枚を取り下げるのは正しく
（#R270 ⑧ / #R299 ② の題そのもの）、間違っていたのは**引き継ぐはずの `quietSet[c]` が動いていない**ことだった。
そこで **`QUIET_UNIT_Z` を「発令中の国には適用しない」**。
床は「**区別が見えるか**」についての規則（Landkreis は世界ズームで1画素の何分の1か）であって
「**地面が塗られるか**」についての規則ではない。発令中の国かどうかは `warnedISOs()` が
`feats` から直接引く——`drawnISO` は publish の**あと**に書かれるので、それを使うと1周ぶん遅れる。
単位を**取りに行く**側にも同じ条件を足した（`askUnitsInView`）。

⚠ ついでに、**publish する集合と取りに行く集合が別の箱で切られていた**のも直した
（`paddedView`）。`quietISOs` は半画面ぶん padding し `askUnitsInView` は素の bounds を見ていたので、
その差の帯にある国は「灰色として出されるが、単位を取りに行かれない」状態になり得た。

#### ② 単位より**小さい**発令が、単位の灰色を丸ごと捨てていた

`coveredByWarning` は3つの判定の or だった。3つ目は「**発令の重心がこの単位の中にある**」で、
#R298 が「Valais の灰色の上に Monthey - Val d'Illiez の色」を消すために足したものである。
正しい問題意識だが、remedy が「Valais を描かない」だった——Monthey は**州の中の谷**である。

→ **発令を単位の「穴」にする**（`warnMeeting` → `punchQuiet`）。GeoJSON のポリゴンは
2本目以降のリングが穴なので、単位の外環に発令の外環を足すだけで「単位 − 発令」になる。
重ねないという #R298 の規則はそのまま（2つは1画素も共有しない）で、塗り漏れだけが消える。

- ⚠⚠⚠ **MapLibre は巻き方で外環と穴を区別する。** `classifyRings` は、あるリングの符号付き面積が
  最初のリングと**同じ符号**なら**新しいポリゴン**を始める。つまり出所の巻きのまま入れた穴は
  **塗られて**、#R298 が消した二度塗りが**いちばん気づきにくい場所で**復活する。両方の面積を測って
  逆向きに揃える。
- ⚠ **「重心が中にある」は「覆っている」ではない。** 中国はこれで **86 点**残っていた——四川の
  阿壩・甘孜は小国ほどの大きさの州で、CMA は**その中の県**で発表する。県の中に州の重心が落ちると
  州ごと捨てられていた。境界箱で「どちらが大きいほうか」を先に決め、**大きいほうが覆う・小さいほうは穴**。
- ⚠ **はみ出す環は穴にできない。** 却下された環について「頂点のうち何割が単位の中か」を計装して
  測ったところ、**289 環の分布は 0.5〜0.6 に山**があった。共有境界の頂点の取りこぼしではなく、
  **MeteoAlarm のスイス・オーストリアの区域が NUTS-3 と本当に重なっていない**（実測、スイスは
  警報 74 地物に対し単位 26）。半分が外に出ている環を内環にすると三角形分割が壊れるので、
  許容誤差では解けない——その単位は**従来どおり捨てる**。

**実測（改修後）**: z2 **22.3% → 6.4%** ・ z5 **2.7% → 1.24%**。
⚠ **残差はほぼ全部カナダで、原因は上と同じ「入れ子にならない」である**——ECCC は**自前の予報区
ポリゴン**で発表し、この地図がカナダについて持っているのは**州・準州 13 個**なので、112 件の警報の
どれかがその中に落ちるたびに州が丸ごと消える。穴にできた分だけは戻った（**386 → 206**）。
これは #R305 が作った欠陥ではなく、#R305 が**半分しか直せなかった**欠陥である。
`IntMapWorld.alerts()` に `quietPunched` / `quietSuppressed` / `quietNoPunch` / `quietUnitISOs`
を足したので、「穴を開けて残せた単位」と「捨てるしかなかった単位」は**数えられる**。

### 2. 「風レイヤーは品質保ったまま、起動から日時変更からすべてに至るまで、爆速にしろ」（2回目）

#R297・#R298・#R299 は**帯の大きさ**と**読み込みの順序**を直した。今回測ったのは**その隣**である。

```
起動時の視野（z1.7）で軸を1段ずつ（前の実装）
    +1        7,050 ms
    +1        7,942 ms
    既に手元にある時刻へ戻る   45 ms      ← 通信は待っていない
    +25       8,270 ms
```

**45 ms** が答えを決めた。バイト数が待ち時間ではない——**列**が待ち時間だった。

`js/wx-ecmwf.js` の `serial()` は「SDK のリーダーは1つなので `.om` の読み込みは一度に1本」を
守る正しい機構で、同時に**先着順**でもあった。そこを通るのは2種類ある:

1. **読み手が待っている読み込み**（時刻ステップ・パン）
2. **このモジュールが自分で始める読み込み**（視野へ広げる段・次の時刻の暖機）

そして**世界ズームでは 2 が両方とも地球を要求する**（`bandFor` は緯度幅 120° を超えると `null`＝
全球 13,199,360 標本 ≈ 18 MB）。1 ステップは毎回その後ろに並んでいた。

→ **同じ「1度に1本」のまま、レーンを2本にする**（`serial(fn, bg)`・`qHi` / `qLo`）。
読み手の読み込みが先、モジュール自身の読み込みは後。
⚠ **走り始めたものは取り消せない**（SDK のリーダーに中断が無い）ので、対になるもう半分は
**背景の読み込みを小さく保つ**ことである:

- **暖める帯は「次のステップが実際に読む帯」**（`nearBand()`）。#R290 追記2 は規則としては正しく
  （「画面のフレームと同じ範囲」）、それを `band()` と綴った——`band()` は `bandFor` であり、
  **このアプリが開く視野では `null`＝地球**を返す。つまり**暖機は毎回地球を暖めていた**。
  次の時刻はフレームを1枚も持たないので `bandCovers` は必ず偽であり、そのステップが読むのは常に
  `nearBand()` である。
- **暖めるのは軸の進行方向の隣**（`_stepDir`）。「次の時刻」を `index()+1` と綴っていたので、
  **軸を戻している読み手は毎回冷たい読み込みを払っていた**。方向は軸自身から測る。
- **「静止」には到着も入れる。** 段の待ち時間を**要求した瞬間**から測っていたので、2.4 秒かかる
  読み込みは**答えが返った時点で既に 1.5 秒静止していた**＝読み手が絵を見る前に次の段が走り出す。
- **段が地球そのものになる場合だけ待ちを長くする**（`BIG_STILL_MS` = 2,500 ms 対 `STILL_MS` = 900 ms）。
  1 秒ごとに軸を送る読み手は地球の読み込みを始めさせず、止まった読み手は 1.6 秒遅れで同じ絵に着く。
- `index.html` に `unpkg.com` と `map-tiles.open-meteo.com` の **dns-prefetch**（preconnect ではない
  ——最初の視野はどちらも使わない）。

```
同じ手順（改修後）
    +1        1,501 ms
    +1          684 ms
    既に手元にある時刻へ戻る   41 ms
    +25       1,665 ms
```

### ⚠⚠⚠ その速さは私の HTTP キャッシュだった（この節の訂正）

上の「改修後」は**自分のブラウザが温めたキャッシュ**を測っている。同じオリジンで何度も走らせた
結果、その時刻の `.om` のバイト範囲が既にブラウザのキャッシュに載っていた。**一度も訪れていない
予報時刻**を使い、改修前後を**どちらも冷たい**状態で通し直すと:

```
localhost · 風だけ · 300 ms 間隔 · 一度も訪れていない時刻
    前（#R304・時刻 100-102）  6,849 / 6,357 / 6,858 ms
    後（#R305・時刻  96- 98）  6,699 / 6,779 / 6,784 ms
```

**差は無い。** 冷たい1段は**帯のレンジ読み込み（約 6.5 秒）が支配的**で、列の順序では動かない。
世界ズームで「段が走っている最中に1段送る」——このラウンドが名指しした状況そのもの——を狙って
測っても **6,705 ms（前）→ 6,025 ms（後）** で、この環境の雑音の範囲である。
本番でも同じで、風だけを入れた1段は **6,322 / 6,495 / 6,399 ms**。

⚠ **手元にある時刻へ戻るのが 41〜46 ms なのは #R299 のフレーム LRU** であって、この改修の成果
ではない（前も後も同じ）。
⚠ **前へ進む暖機は改修前から効いている**（9 秒空けて前進: 前 2,805 / 2,299 ms・後 4,079 /
1,891 ms——どちらも冷たい 6.5 秒より速い）。

⇒ **ここにある4つの変更は構造として正しい**——世界ズームで暖機が地球を要求するのは誤りだし
（`band()` は `bandFor`＝この視野では `null`）、進行方向を無視して `index()+1` を暖めるのも誤りだし、
読み手が待っている読み込みが自分の背景読み込みの後ろに並ぶのも誤りである——**が、この依頼が
求めた「爆速」は達成していない。そう書く。**

⚠⚠⚠ **「同じ手順」は「同じ条件」ではない。** 2 回目の実行は 1 回目が温めたキャッシュの上で走る。
A/B は**どちらも冷たい**入力で通す——このプロジェクトが #R297 で「同じ実行の中で両方測る」と
書いたのと同じ規則を、時間軸方向に破っていた。

⚠ **粒子・色・標本間隔・ファイル・モデルは1つも変えていない。** 変えたのは
「**そのバイトをいつ・どの順で取りに行くか**」だけである。

### 追記（本番検証）— **本番に残っていた塗り漏れの、いちばん大きな塊は「隣の単位」だった**

#R305 を本番へ出してから、**同じ測り方・同じキャンバス（880×720）・同じカメラ**で測り直した。

```
本番 · z2 · 陸 3,400 点 → 275 点 (8.09%) が何にも塗られていない
    CAN 140 · RUS 83 · SAU 15 · DZA 13 · KAZ 13 · USA 2 · UZB 2 · ほか 7
```

#### 「隣」は「中にあるもの」ではない

ロシアの警報は、**この地図自身の admin-1 単位に置かれている**——タップカードが
`Republic of Karelia` / `Novosibirsk Region` と行政単位の名前を出す。**同じ索引から出た2つの
地物は重ならない**ので、**どちらも他方の穴にはなり得ない**。

にもかかわらず `warnMeeting` が「この単位の中に発令がある」と読んでいた理由は `geomCentre` である。
これは**最大の環の頂点の平均**——安く、そして凹んだ単位や多島の単位では**自分の形の外**に落ちる。
落ちた先が隣の単位の中なら、その隣は「中に発令がある」ことになり、`punchQuiet` は
**どこにも入っていない形**を穴にできず、**静かな隣が丸ごと落ちる**。
その発令が本当に属している単位のほうは、`sameOutline` が既に落としている。

→ **輪郭がこの国の単位のどれかと一致する発令は、その単位であって「中にあるもの」ではない**
（`unitBoxes`）。判定は `sameOutline` と同じ——国が同じで境界箱が小数4桁（≈11 m）まで一致すれば
同じ単位。集合は `UNITS[iso]` の**同一性**でキャッシュするので、publish あたり国ごとに一度作る。

⚠ **隣は「覆う」こともできない。** 覆い判定は「この単位の中心が発令の中にあり、かつ発令の境界箱が
こちらを含む」で、**大きな隣**（ヤクーチアやクラスノヤルスクのような）ならその条件を満たしてしまう。
同じ除外を覆い判定の側にも入れた。

#### ⚠ ローカルでは証明できなかった

このラウンドの計測時、ローカルは WMO 登録簿の掃引が途中で **19 か国が未読**（ロシアを含む）だった。
未読の国は**斜線**であって穴ではないので、**ローカルの 152 点は「ロシアが居ない」ことの数字でもある**。
だから確認は**本番検証**で行った——同じ測り方で、ロシア・サウジ・アルジェリア・カザフが
どうなったかを数える。

#### 残差

**カナダ**。ECCC は**自前の予報区ポリゴン**で発表し、この地図がカナダについて持っているのは
**州・準州 13 個**なので、112 件の警報のどれかがその中に落ちるたびに州が消える。
#R305 の穴で 386 → 206 まで戻したが、そこまでである。
