> 「気象警報はまだ対応していない、もしくはデータがまだ入っていないところは灰色斜線で、発令されていない
>   だけの地域は灰色に。個々の区別はちゃんとやれ。」
> 「警報レイヤー、日本以外でも区分単位、発令単位ごとに色分けしろ。正確にリアルタイムな情報に基づき正確で

>   言っている。対応地域まで斜線で塗るのを辞めろ。」
> 「ECMWF系レイヤーを開くと勝手にECMWFの時間ポップアップが出るのを辞めろ。わざわざ分けるな。」
> 「Wind(animated)は色味は段彩ではなくグラデーションに。（色はそのまま。制度も一切落とすな。点滅してしまう
>   バグが発生する。未来に変えたとき、風データを取得できませんでした となる。あと、重すぎるから、品質は

**再送された文の中で、変わっていた語が新しい面を指していた。** 警報の 5 つの要求は #R271 / #R273 / #R275 /
#R277 / #R284 とほぼ同じ文面だが、**2 か所だけ変わっていた**——「まだ対応していない**、もしくはデータがまだ
入っていない**ところは」と「対応**地域**まで斜線で塗るのを辞めろ」（#R284 では「対応**国**」）。前者は #R284 の
判断を**読み手自身が覆した**もので、後者はその判断が守ろうとしていた性質が今も成り立つことを求めている。
不明確な 3 点（未取得の見た目・「個々の区別」の粒度・「わざわざ分けるな」の意味）は **AskUserQuestion で確認**した
（§8）。答えは「未対応と同じ灰色斜線」「区分単位で判定して塗る」「アプリ共通の時計に統合」。

### ① 斜線は「この地図はここについて何も述べていない」に戻った

`washTier` は `readState(iso) !== 'ok'` に **0（斜線）** を返す。#R284 の −1（何も描かない）は無くなった。

これは #R284 の判断の**取り消しではなく、読み手による決着**である。#R284 が測った defect——レイヤー投入
45 秒で **22 の対応国が斜線**——は本物だったが、その原因は「斜線を塗ったこと」ではなく「**冷たい輪番が遅い
こと**」で、#R284 は**同じラウンドでそちらも直している**（`COLD_CALLS = 6`）。実測、いまは

| 時点 | 未読（`unread`） |
|---|---|
| レイヤー ON 直後 | 29 |
| t+20 s | 29 |
| t+80 s | **3** |

——斜線は一過性で、「対応地域まで斜線で塗るな」は**データが入った国は決して斜線にならない**という形で
成り立っている。**どの沈黙なのか**（未対応／順番待ち／取得できなかった）はタップしたカードが**言葉で**言い、
見本は**地図と同じ斜線**に戻した（#R284 の破線の空枠は、地図に無い模様だった）。

### ② 「発令なし」は国ではなく**区分単位**の主張だった

発令中は #R271 から発令単位で描いていたのに、発令なしは**国ぜんぶを覆う 1 枚の灰色**だった——警報の出た
Landkreis の隣にある静かな Landkreis が、国の他の部分と区別できない。主張は単位ごとに真なので、塗りも
単位ごとにする（`wp-alert-quiet` ＋ 境界線 `wp-alert-quiet-line`、**発令単位の塗りの下**）。

⚠ **単位はこの地図が既に持っているものだけ**——気象庁の市町村、Eurostat NUTS-3、CMA の行政区画、CWA の
郷鎮市区、Natural Earth admin-1、geoBoundaries ADM1。すべて**置き場所を探すはしごが自分の都合で作る索引**で、
つまり**灰色に塗れる単位は、警報が出れば色を塗れたはずの単位**である。それが灰色を「主張」にしている。
持っていない国は**国全体の灰色**のままで、パネルが**その差を数えて印字する**（`unitLine`）。

**実測**（レイヤー ON、欧州を表示、t+80 s）: **53 か国・1,813 区分**が単位単位、**99 か国**が国単位。
⚠ geoBoundaries は**視野内の国**にだけ、同時 2 本までしか聞かない（全世界分は数十 MB になる）。

### ③ 対応国は**書き足す**のではなく**学習する**

#R284 は NWS の UGC を読んで 8 か国・地域を手で書き足した。**同じ形が他にもある**——実測、フィンランドの
機関は 「Ahvenanmaa」（**オーランド**＝この地図では独自の国）に発令していて、そのポリゴンは既に描かれて
いるのに、国の層は下で「未対応」の斜線を塗っていた。手書きの一覧は**その一覧に増える日に嘘になる**
（#R271）ので、`learnCoverage` が**描いた単位の重心**を `countryAt` に通し、自分のフィードを持たない国に
落ちたら**その形を描いた機関がその国を担当している**と記録する。証拠はポリゴンそのもの。

- ⚠ **重心であって頂点ではない**——粗い輪郭が国境を数 km 越えても隣国を主張してはならない。
- ⚠ **足すことしかしない**——自分のフィードを持つ国は決して割り当て直さない（「ソースは一国一ソース」）。
- ⚠ **保存しない**——いま地図にあるものから毎回導くので、発令をやめた機関は担当から外れる。

実測、この仕組みだけで**コソボとリヒテンシュタイン**が自動的に対応国になった。

⚠⚠ **WMO 登録簿の側はもう伸びない、ということも測った**: 加盟 **198**・CAP 実装 Completed **138**・
**その 138 すべてが既に配線済み**（`completedNotWired` = 0）。全球スキャンに現れる **40** 機関のうち
Completed でないものは **0**。国を増やす道は「登録簿の外の各国フィードを1本ずつ実装する」しかなく、
候補を実際に叩いた結果は **IMD 401 / SAWS は SPA の外殻 / BMKG 404 / MeteoAlarm の EDR は API キー必須**
（`/metadata/v1/regions` は 401）——**このラウンドでは足せなかった**ので、足せた分（学習された territory）と
足せなかった理由の両方を記録する。

### ④ 「更新が遅すぎる」（5回目）は**誰の時計か**だった

定常の一周は #R284 から転送の床（relay の 60 秒エッジキャッシュ）に乗っている。遅かったのは**読み手の国の
順番**で、年齢順の輪番は目の前の国も地球の裏側の国も同じに扱う。→ **同じ**輪番を「**視野内が先、その中で
古い順**」にした（`viewFirst`）。追加のリクエストは 0。塗り漏れの側は、WMO 登録簿の形の索引を
「まだ置けない区域が残っている国」については **10 分ではなく 3 分**で聞き直すようにした（同時 2 → 3 本）。

### ⑤ 表示・非表示が 3 つのリストに散っていた

**実測**、`wp-alert-fill` と国の 2 枚が `visibility:none` のまま、隣の輪郭と文字だけが見えている状態になった
——警報が**塗り無しの細い線**だけで描かれる。犯人は外部（起動直後に `js/map-ui.js` が保存レイヤー集合を
再適用して一度消す）で、次の publish が走るまで誰も戻さない。→ `applyAlertVis()` 1 本にまとめ、
`idle` と 30 秒 tick が**再主張**する。

### ⑥ ECMWF 専用の時計を廃止した

#R284 は予報軸に floating な箱（「ECMWF 予報時刻」）を与え、ECMWF レイヤーを入れると**勝手に開いた**。
それは #R94 から存在するマスタークロック `window.IntMapTime` の**隣に立つ 2 つ目の時計**だった。

- 箱は**無くなった**。予報の瞬間は**マスタークロック**にあり、`js/wx-ecmwf.js` がそれを**モデルが公開して
  いる最寄りの時刻へ丸める**（`_followClock`）。軸を動かせば**その瞬間が時計へ書き戻る**（`_pushClock`）。
- 読み手が操作するのは**タイムマシンの「予報」タブ**——モデルの軸がそのままスライダーになり、操作盤は
  風の凡例と**同じ宣言**（`IntMapWxPlayer.IC`）を読む。
- 各レイヤーの凡例が持つのは「**この絵がいつのものか**」の 1 行で、押すと**その共通の時計を開く**。
- ⚠ **書き戻しはまとめて**（220 ms トレーリング、再生中は撃たず停止時に 1 回）。`IntMapTime.set` はニュース・
  日付つきラスタ・歴史的国境・昼夜境界を全部起こすので、700 ms の再生フレームごとに撃つと、読み手が
  通り過ぎるだけの瞬間のために十数のレイヤーを組み直すことになる。

### ⑦ 「風データを取得できませんでした」は、**成功した読み込みが失敗として解決していた**

**本番ビルドで再現**した: 読み込みを始めて 50 ms 後に `release()` を呼ぶと、**8.3 秒かけてデータは届いた
うえで結果は null**。原因は 2 つで、どちらも 1 行:

1. `load()` のハンドラが**自分が復号したフレームではなくモジュール変数 `held` を返していた**——
   `release()` はその `held` を消すので、飛行中の読み込みは null に解決する。
2. `fireTime()` が時刻変更のたびに**無条件の `release()`** を呼んでいた。

→ ⑴ `load()` は**自分のフレームを返す**（どれが「今のもの」かは単調な `seq` が決め、`release()` もそれを
進める）、⑵ `fireTime()` は**何も捨てない**——新しいフレームが着いたら置き換わる。#R284 が粒子について
書いた規則そのもので、`fireTime()` はそれを 1 段下で否定していた。

⚠ **#R287 が同じ defect を「140 ms の窓」の側から先に narrower に直しており、その診断（起動後の最初の
1 歩は必ず負ける・冷えた場 7〜9 秒 vs 窓 140 ms・再試行は 25.27 °C）はそのまま生きている。**

### ⑧ 「重すぎる」の実体は描画ではなく **18 MB の読み込み**だった

**実測**（1280×800 相当のヘッドレス、東京 z4→z9）:

| | |
|---|---|
| 全球 1 フレーム | **6,599,680 標本・274 レンジ要求・17.96 MB・7.8〜8.4 秒** |
| レンダラ自身 | 粒子 1,980 個で **2.65 ms/フレーム**（38 fps、最悪フレーム 33 ms） |

つまり待っていたのは**絵ではなくバイト**である。ECMWF の領域は**縮約ガウス格子**なので、SDK の
`getCoveringRanges` は**緯度でしか**絞れない（経度は 1 本の平坦な添字）——が、それで足りる:

| | 標本 | 要求 | バイト | 時間 |
|---|---|---|---|---|
| 全球 | 6,599,680 | 274 | 17.96 MB | 8,436 ms |
| 25°–46°N の帯 | 935,400 | 25 | 1.64 MB | 2,829 ms |
| 帯 ＋ 先読み | 935,400 | 25 | 1.64 MB | **1,254 ms** |

**同じ 9 km 間隔・同じ数値・同じ色**で、落とすのは画面に無い部分だけ＝「品質は一切落とさずに」。
⚠ 帯は**全経度**を含むので、東西のパンでは読み直さない。⚠ 帯は**レイテンシ律速**（25 要求 × 約 220 ms）に
なるので、SDK 自身の `prefetchVariable`（`prefetchConcurrency: 1000`）で温めてから読む。
⚠ 保持しているフレームは**要求された帯を含んでいれば**再利用し、帯 `null`＝全球はすべてを含む——だから
任意地点を要求する `valueAt` は今までどおり全球を得る。

**アプリ上の初回描画**: **8,109 ms → 2,673 ms**。

### ⑨ 気温は **1 レイヤー 2 ソース**になった

「気温 2m（ECMWF）」と「気温（2m・再解析）」は**ひとつの量に対する 2 つのスイッチ・2 つの凡例・2 つの
日付操作・2 つの配色**だった。1 行になり、凡例の `Source` が切り替える。帯・目盛・単位・説明・並びは
**どちらでも同じ**で、変わるのは数値の出どころと「いつの絵か」の行だけ。

⚠ **再解析タイルは色から値へ戻してから塗り直す**（`js/wx-reanalysis.js`・`imwxre://`）。GIBS の
`MERRA2_2m_Air_Temperature_Monthly` は **8bit インデックス PNG**（実測 IHDR colour type 3・768 バイトの
PLTE）で、その配色表は NASA が公開している（183 エントリ・ref 0 = 欠測・ref 2–181 が 220–310 K の 0.5 K
刻み）。**183 色に重複が 1 つも無い**ので色→値は全単射であり、各画素をケルビンの階級へ戻して予報と同じ
表で塗る。**値は NASA のもので、変わるのは配色だけ**。実測 タイル 35 枚・失敗 0・未対応画素 0。
⚠ 保存済みセッションの `dl-temp` は `js/session-tabs.js` の `RETIRED` 表で `dl-ec-temp` に翻訳される。

### ⑩ 配色は**目視ではなく実測**した

参照画像は windy.com の既定の気温オーバーレイで、その配色表は Windy 自身の「Customize color scale」に
出る値である。`W.colors.temp.defaultColorGradient` が 13 停留点（ケルビン）、`_precomputedGradient.RGBA(k)`
が実際に塗られる色——**両者は一致しない**（Windy は節のあいだを線形ではなく滑らかに補間する）ので、
**塗られる側**を 203–320 K・0.05 K 刻みで標本化し、**線形補間でそれを再現する最小の停留点集合**に落とした:
**23 停留点・最大チャネル誤差 3/255**。0.00–0.85 °C に 5 点集まっているのは Windy が氷点の等温線を
「1 度未満で青から緑へ」と強調しているためで、そのうち 1 点（0.40）を落とすと誤差は **3 → 7** に上がる。

⚠ SDK の**家族名** `temperature` に登録するので、`temperature_2m`・`surface_temperature`・土壌温度が
**同じ表**を読む（`dew_point` は別家族なので触らない）。刻みは **0.05 °C**（2,341 段）——最も急な
0.35→0.75 °C 区間で青が 0.4 度に 92 単位動くため。

### ⑪ `om://` を、プロトコル未登録のまま MapLibre に渡していた

このラウンドの probe が **CSP 違反**として捕まえた:
`Connecting to 'om://https//map-tiles.open-meteo.com/…' violates connect-src`。
`om://` は**この app 自身が登録するスキーム**なので、それがネットワークに出ること自体が
「登録が無い」という診断である（**#R286 と同じ形**）。原因は `registerProtocol()` が `protoReg = true` を
`try` の**外**で立てていたこと——登録が失敗しても「済んだ」ことになり、以後 MapLibre は未知スキームを
**ネイティブに fetch** する。`addProtocol` は既に真偽値を返しているので、それを読む。
そして**レイヤー側**は、プロトコルが無い間は `om://` のソースを**組み立てない**（再試行の梯子が既にある）。
